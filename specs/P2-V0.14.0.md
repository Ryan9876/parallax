# Parallax 2.0 v0.14.0 — Parallel Development Foundation

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.14.0
Depends on: P2-V0.12.0 plus active P2-V0.13.0 workstream isolation
Method: GitHub-authoritative multi-chat workstream coordination

## 1. Objective

Establish the minimum durable development-control foundation required for multiple ChatGPT conversations to develop Parallax concurrently without treating chat history as the source of truth, overwriting each other's work, or weakening the existing spec-first and evidence-based release methodology.

The immediate product outcome is higher safe development throughput so Parallax can reach app-builder readiness faster while preserving integrity, security, evaluation discipline, and deployment evidence.

## 2. Scope

- Make GitHub the concurrency and integration authority for parallel ChatGPT development.
- Define an explicit worker-chat and integration-chat operating model.
- Require one isolated branch and one open `[WS]` GitHub issue per active implementation workstream.
- Require each active workstream to declare objective, branch/base, owned paths, integration-sensitive paths, dependencies, acceptance gate, and completion condition before substantive implementation.
- Require every worker chat to inspect authoritative records, open `[WS]` issues, and open PRs before modifying code.
- Define path-overlap behavior: later workstreams pause, narrow scope, or explicitly coordinate rather than independently editing the same subsystem.
- Serialize final integration even when implementation happens in parallel.
- Require latest-main integration and appropriate gates again before a worker PR is merged after another dependency/conflicting PR lands.
- Extend `AGENTS.md` and the pull-request template with the parallel-workstream protocol.
- Add a reusable GitHub workstream issue template and a durable `PARALLEL-DEVELOPMENT.md` operating guide.
- Record the durable governance change in `PROJECT-CONSTITUTION.md`.
- Preserve the existing v0.13.0 visual workstream without modifying its product implementation files.

## 3. Security

Parallel development must not broaden authority or weaken existing security boundaries.

- Worker chats do not receive additional production credentials merely because they run in parallel.
- Secrets, provider credentials, session material, and root/break-glass credentials remain outside repository content and workstream issues.
- Workstream issues may identify components, paths, dependencies, and deployment environments but must not contain secrets.
- Production deployment remains serialized and evidence-based through the integration role by default.
- Security-sensitive, destructive, expensive, or hard-to-reverse changes continue to require human approval under the Project Constitution.
- A worker PR may not bypass protected evaluation, authentication, authorization, persistence, or deployment checks applicable to its scope.

## 4. Operating model

### Worker chats

A worker chat owns one bounded implementation objective at a time. It reads the project authority files, checks active workstreams, registers scope, creates an isolated branch, follows the spec-first process, validates its work, opens a PR, and stops before merge/deployment unless it has explicitly been designated the integration chat.

### Integration / Control Tower chat

One conversation acts as the default integration authority. It monitors active `[WS]` issues and PRs, identifies collisions and dependency ordering, serializes merges, requires latest-main refresh/revalidation, deploys validated candidates, and updates authoritative release state only from evidence.

### GitHub workstream ledger

Open GitHub issues with the `[WS]` prefix are the live ownership ledger. GitHub PRs are the implementation/integration ledger. Chat history may provide context, but it does not grant ownership or prove current state.

## 5. Non-goals

- Building a distributed autonomous agent scheduler in this release.
- Automatically rebasing or merging arbitrary branches without review/evidence.
- Introducing a new database or service solely for workstream coordination.
- Replacing GitHub issues/PRs with a custom Parallax task tracker.
- Changing current product runtime behavior, authentication, API contracts, persistence, Work Specification semantics, Reason, Code, Engineering Runs, or deployment topology.
- Refactoring application files simply to create more parallelism; subsystem decomposition should be done later only where evidence shows collision pressure.
- Allowing simultaneous production deployments.

## 6. Acceptance criteria

### AC-01 GitHub-authoritative coordination
Repository guidance explicitly states that GitHub authoritative records, open `[WS]` issues, branches, PRs, CI evidence, and deployment evidence outrank individual chat history for concurrent development state.

### AC-02 Workstream reservation contract
A reusable workstream issue template requires objective, state, branch, base, owned paths, shared/integration-sensitive paths, dependencies, acceptance gate, collision policy, and completion condition before a workstream is treated as ACTIVE.

### AC-03 Worker isolation protocol
`AGENTS.md` requires parallel worker chats to inspect active workstreams before implementation, use isolated branches, remain inside declared scope, and avoid merging/deploying by default.

### AC-04 Serialized integration protocol
The durable operating guide defines one integration/control role, one-PR-at-a-time final integration, latest-main refresh, and revalidation after dependency/conflicting merges.

### AC-05 PR integration metadata
The pull-request template records workstream issue/ID, declared ownership scope, dependencies, collision review, latest-main integration state, validation evidence, and generated/validated/deployed/deployment-verified state without conflating them.

### AC-06 Existing workstream protection
The foundation records active v0.13.0 visual work as an owned workstream and does not modify its product implementation paths, preventing the governance foundation from colliding with PR #20.

### AC-07 ChatGPT bootstrap usability
`PARALLEL-DEVELOPMENT.md` includes concise copy/paste bootstrap instructions for a worker chat and an integration chat so additional project conversations can begin safely without reconstructing the protocol from prior chat history.

### AC-08 App-builder acceleration lanes
The operating guide defines an initial set of parallelizable development lanes oriented toward app-builder readiness, while making clear that lane names do not replace concrete path reservations and dependency analysis.

### AC-09 Authoritative governance maintenance
`PROJECT-CONSTITUTION.md` is versioned forward to record concurrent-development governance as a durable principle; `CURRENT-STATE.md` remains unchanged until a meaningful validated release/deployment/material decision is actually merged or verified.

### AC-10 No runtime regression surface
This foundation changes governance/docs/templates only. It does not alter application runtime files, API behavior, authentication, authorization, persistence, evaluation algorithms, deployment configuration, or production environment state.

## 7. Risks

- **False confidence from parallelism:** multiple branches can still be logically incompatible even without text conflicts. Mitigation: serialized integration plus latest-main revalidation.
- **Ownership becoming stale:** open issues may outlive active work. Mitigation: close workstream issues at merge/completion and use the integration chat as ledger custodian.
- **Overly broad reservations blocking throughput:** workers may claim whole subsystems unnecessarily. Mitigation: require concrete owned paths and narrow objectives; shared paths require explicit coordination rather than blanket ownership.
- **Governance overhead outweighing speed:** process can become heavier than the work. Mitigation: keep the reservation contract minimal and use it only for material implementation work.
- **Current PR collision:** introducing enforcement workflows while PR #20 is active could unexpectedly fail legacy branches. Mitigation: this release establishes protocol/templates first; automated blocking enforcement can be added after active legacy workstreams are integrated.

## 8. Release gate

Before this foundation is merged:

- the spec contract must validate;
- changed files must remain within the declared governance/documentation scope;
- existing active product implementation paths owned by PR #20 must remain untouched;
- the updated governance files must be internally consistent;
- the new workstream issue template and PR template must be usable without secrets or private reasoning;
- the foundation PR must be reviewed against latest `main` before merge;
- `PROJECT-CONSTITUTION.md` must reflect the durable coordination rule;
- `CURRENT-STATE.md` must not claim a new deployed product version merely because the governance foundation exists;
- production deployment is not required because this release does not change product runtime behavior.
