# P2-V0.23.26 — server-compiled source outputs

Workstream: #517

## Objective

Remove the production implementation-generation failure class exposed by authenticated Engineering Run `3a1ba66a-5649-42b6-81ee-91684fe06bbc` after P2-V0.23.25. Preserve the existing protected engineering lifecycle while moving mechanical acceptance binding and unified-diff construction from the model boundary to deterministic server-owned code.

## Scope

1. Replace the live hosted implementation-generation output contract with bounded typed file outputs containing only `path`, `expected_base_sha256`, and complete UTF-8 `content`.
2. Bind `acceptance_ids_covered` from the immutable approved Work Specification after typed model output is decoded; the model no longer echoes or claims acceptance coverage.
3. Deterministically compile every generated file output into the existing internal `GeneratedSourcePatch` / `ImplementationProposal` representation before any downstream candidate validation.
4. For an existing file, require the output path and expected base digest to exactly match a file in the protected source-context snapshot.
5. For a new file, require the SHA-256 of empty content as the expected base digest. Safe nested missing-parent handling remains governed by Architecture v3.36 and the existing patch engine.
6. Generate canonical single-file unified diffs exclusively from server-owned source-context text and generated target content. Model-provided diff headers, hunk coordinates, and counts are eliminated from the live hosted generation contract.
7. Add bounded non-sensitive rejection reason codes sufficient to distinguish typed-output decoding, source-output compilation, and downstream safe-implementation rejection without recording raw model output, generated source text, provider payloads, source context, paths, secrets, or arbitrary exception messages.
8. Preserve compatibility of the internal `ImplementationProposal` and downstream safe implementation / lineage / BUILD / TEST / VERIFY / REVIEW contracts.

## Acceptance criteria

- AC-01: The hosted DSPy implementation signature no longer exposes `acceptance_ids_covered` or model-authored unified diffs as outputs.
- AC-02: Successful typed model output is converted into an internal `ImplementationProposal` whose `acceptance_ids_covered` exactly equals the server-owned required acceptance IDs in order.
- AC-03: Existing-file output is accepted for compilation only when its path exists in protected source context and its expected base digest exactly equals the authoritative source-context digest.
- AC-04: New-file output is accepted for compilation only when its path is absent from protected source context and its expected base digest equals SHA-256(empty).
- AC-05: Server compilation produces strict canonical single-file unified diffs for existing and new files, including deterministic no-newline handling, and these diffs pass the unchanged strict patch engine for admissible content.
- AC-06: Duplicate generated target paths, no-op outputs, stale/mismatched base digests, malformed typed outputs, and downstream unsafe/secret/unsupported/symlink/size/hierarchy failures remain fail-closed before canonical source mutation.
- AC-07: Bounded diagnostic evidence/logging uses fixed reason codes only and never persists or logs raw model output, generated source text, source-context text, provider payloads, paths, secret material, or arbitrary validation exception messages.
- AC-08: Existing candidate-recovery limits remain unchanged: no additional model identities, repair generations, hidden retries, or timeout increases are introduced.
- AC-09: Existing safe implementation, disposable candidate validation, accepted source lineage, Git/deployment authority, lifecycle-transition authority, and human REVIEW ceiling remain unchanged.
- AC-10: Focused tests and the full protected regression suite pass, including new/existing/nested source-output compilation and unchanged safe-patch enforcement.
- AC-11: Production deployment reaches READY and `/health` and `/ready` return HTTP 200.
- AC-12: An authenticated retry of the same real engineering path progresses beyond the P2-V0.23.25 model-diff / proposal-validator rejection class or records the next bounded blocker without weakening controls.

## Non-goals

- No additional implementation-agent or validator-repair budget.
- No provider/model roster change.
- No hosted-model timeout increase or hidden provider retry.
- No relaxation of path, extension, secret, symlink, byte, source-lineage, Git, deployment, lifecycle, or REVIEW controls.
- No direct model write authority and no bypass around `SafeImplementationEngine`.
- No queue or worker architecture redesign.
- No claim that server-bound acceptance IDs mean acceptance criteria have been satisfied; BUILD/TEST/VERIFY/evaluation remain authoritative.

## Security and reliability

The model remains a non-authoritative proposal source. Generated content is bounded typed text only. Existing-file identity is anchored to the protected source-context digest; new-file identity is anchored to SHA-256(empty). The server creates canonical diffs from authoritative source text and then submits them through the unchanged patch engine and safe implementation boundary. Generated content continues to undergo secret-content, target, extension, symlink, byte, no-op, hierarchy, and source-lineage enforcement. Diagnostics are allowlisted fixed codes and may not carry generated content or arbitrary exception material.

Removing model-authored acceptance IDs does not widen authority: exact acceptance ownership already belongs to the immutable Work Specification, and downstream validation/evaluation continues to determine whether the implementation actually satisfies it. Removing model-authored diff syntax similarly reduces non-semantic failure without bypassing the existing strict patch verifier.
