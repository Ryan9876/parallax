## 1. Objective

Remove the remaining implementation-generation blocker exposed by authenticated Engineering Run `3a1ba66a-5649-42b6-81ee-91684fe06bbc` after P2-V0.23.25 removed the missing-parent restriction.

The production retry on exact application source `3d53599c4659162cfe45bbc4809f3f329d0abb73` reached IMPLEMENT and no longer emitted `unsafe_target`. It still failed before BUILD because the hosted model boundary requires models to author strict unified diffs. Luna returned an implementation intent that failed strict/canonicalized diff parsing (`canonicalization_format`); Terra returned typed proposals rejected by the unchanged safe proposal validator; Sol hit the existing bounded 60-second timeout; and the single fresh Terra validator-repair proposal was also rejected. No canonical source mutation occurred.

Unified-diff headers, source SHA binding, hunk coordinates, line counts and unchanged context lines are mechanical facts already owned by the protected server because it holds the authoritative source snapshot. Making the model reproduce those facts adds failure surface without adding useful semantic capability.

P2-V0.23.26 changes only the hosted generation boundary. Models will propose bounded typed file-content intents. The server will bind those intents to authoritative source context and deterministically render the existing canonical `GeneratedSourcePatch` / `ImplementationProposal` representation. The unchanged safe patch engine remains the authority that validates and commits source changes.

## 2. Fixed decisions

- `ImplementationProposal`, `GeneratedSourcePatch`, `SourcePatch`, `CanonicalizingTextPatchEngine`, `SafeImplementationEngine`, protected candidate validation, source-lineage acceptance, BUILD/TEST/VERIFY, delivery policy and the human REVIEW ceiling remain the canonical downstream contracts.
- The hosted model no longer supplies `expected_base_sha256`, diff headers, hunk coordinates/counts or context lines.
- The hosted model returns only exact acceptance coverage plus bounded typed file intents containing normalized relative `path` and desired UTF-8 `content`.
- Existing selected source paths are bound server-side to the exact path, SHA-256 and content in the protected `SourceContextSnapshot`.
- A path not present in selected source context is represented as a new-file candidate bound to SHA-256 of empty content. This grants no authority: the existing safe engine still rejects collisions with unselected existing files, unsafe paths, unsupported targets, symlinks, secrets, hierarchy conflicts and other violations.
- Server-side diff rendering is deterministic and produces one strict single-file unified diff per file intent. The rendered proposal is then processed exactly like the current model-authored `ImplementationProposal`.
- Duplicate targets and no-op intents are rejected before candidate admission.
- Raw rejected model output is not persisted or logged.
- Bounded agent recovery, one final validator repair per work unit, Luna/Terra/Sol routing, 60-second hosted timeout and zero hidden provider retries are unchanged.
- Validator-repair guidance is updated to repair semantic paths/content and explicitly states that SHA/diff mechanics are server-owned.
- Architecture advances to v3.37 because model-to-runtime implementation authority changes from model-authored patch mechanics to server-canonicalized content intent while downstream mutation authority remains unchanged.

## 4. Non-goals

- Replacing or relaxing `TextPatchEngine`, `CanonicalizingTextPatchEngine` or `SafeImplementationEngine`.
- Letting the model write files directly or bypass canonical source-lineage acceptance.
- Allowing arbitrary filesystem commands, file rename, chmod, symlink creation, binary writes or recursive directory authority.
- Relaxing path traversal, workspace containment, secret-sensitive target/content checks, supported extension rules, patch/result byte limits, stale-source checks or hierarchy-conflict checks.
- Increasing model retry count, final repair count, hosted-model timeout or hidden transport retries.
- Adding a model, provider, credential, queue or background-worker redesign.
- Changing Git mutation, deployment, lifecycle-transition or REVIEW-completion authority.
- Persisting raw rejected model output.
- Solving unrelated source-context selection quality in this release unless a focused regression proves it is required for deterministic content canonicalization.

## 5. Required behavior

### 5.1 Typed model content intent

The DSPy implementation signature must return:
- `acceptance_ids_covered`: the exact supplied acceptance IDs in order; and
- a bounded list of file intents, each containing only `path` and desired full UTF-8 `content`.

The model-visible contract must state that paths are repository-relative source targets and that the server owns base SHA binding and unified-diff mechanics. Models must not be asked to calculate or emit SHA-256 values, diff headers, hunk coordinates, line counts or source context lines.

The typed envelope remains extra-forbid and bounded. Duplicate target paths are invalid. Model-output parsing/typing failures remain `ModelOutputValidationError` and therefore route as validation failures.

### 5.2 Authoritative base binding

For each file intent, the server resolves the exact path against `request.source_context.files`.

If the path exactly matches a selected source file:
- `expected_base_sha256` is copied from the protected snapshot;
- before-content is the protected snapshot content; and
- diff headers use `--- a/<path>` / `+++ b/<path>`.

If the path is absent from selected source context:
- `expected_base_sha256` is the SHA-256 of empty content;
- before-content is empty; and
- diff headers use `--- /dev/null` / `+++ b/<path>`.

This classification is only generation-time intent. If a supposedly new target actually exists outside selected context, the unchanged safe engine must reject it because the empty base digest cannot match authoritative workspace state.

### 5.3 Deterministic unified-diff rendering

A server-owned pure renderer converts before-content and desired after-content into a strict single-file unified diff.

The renderer must:
- be deterministic for identical path/before/after inputs;
- preserve UTF-8 text and line-ending semantics supported by the current patch engine;
- use exact canonical target headers;
- emit valid hunk coordinates/counts derived from the actual before/after content;
- never include timestamps or unrelated metadata;
- reject a no-op where before and after content are identical;
- produce a result accepted by the existing strict patch parser for supported source text.

The renderer grants no filesystem or lifecycle authority.

### 5.4 Canonical downstream proposal remains unchanged

After rendering, the server constructs the existing `ImplementationProposal` with the exact acceptance IDs and generated `GeneratedSourcePatch` objects.

All existing downstream code receives the same proposal type and therefore continues to apply:
- exact acceptance ownership;
- candidate `proposal_validator` through `SafeImplementationEngine.validate()`;
- canonicalizing patch verification;
- commit-time workspace/source checks;
- nested new-file parent creation from P2-V0.23.25;
- source-lineage acceptance;
- disposable BUILD/TEST/VERIFY;
- delivery policy; and
- human REVIEW boundary.

### 5.5 Repair guidance becomes semantic

`VALIDATOR_REPAIR_GUIDANCE` and final repair guidance must no longer instruct the model to correct diff headers, hunk coordinates/counts, expected base SHA values or copied context lines.

They must instruct the model to re-check:
- target paths;
- desired file contents;
- source-context compatibility;
- acceptance coverage; and
- prohibited/unsupported/secret-sensitive targets.

They must explicitly state that the protected server binds source digests and renders unified diffs after generation.

The one-repair ceiling and fresh final-repair context token remain unchanged.

### 5.6 Failure evidence remains bounded

No raw generated file content, rejected proposal text, repository source or provider payload may be added to durable routing diagnostics or ordinary runtime logs.

Mechanical renderer failures are normalized as protected output validation failures. Safe-engine rejection remains candidate validation failure. Provider/transport failure remains provider failure.

## 6. Security and reliability

This release narrows, rather than widens, model authority. The model stops supplying security-sensitive mechanical claims about the source base and patch structure. The server derives those facts from its own protected source snapshot.

A file intent is non-authoritative until the server has converted it to the existing canonical proposal and that proposal has passed the unchanged safe implementation validator. New-file classification based on absence from selected context does not override the workspace: a collision with an existing unselected path still fails when the safe engine checks the empty base digest against current source.

No direct file-write API is exposed to the model. Existing path normalization, supported-target rules, secret checks, symlink rejection, workspace containment, mutation rollback and source-lineage controls remain unchanged.

The deterministic renderer is pure and side-effect-free. It may fail closed on unsupported text/newline states rather than weakening patch parsing.

## 7. Acceptance criteria

### AC-01 Existing-file content intent binds authoritative source
Given selected source `src/app.py` with protected SHA/content, a typed intent for `src/app.py` produces a canonical `GeneratedSourcePatch` using the exact protected SHA and a strict diff that applies to the protected content.

### AC-02 New nested-file content intent uses empty base
Given no selected source entry for `prototypes/fml-data-readiness/index.html`, a non-empty typed intent produces a canonical new-file patch with `EMPTY_SHA256`, `/dev/null` old header and exact target new header. The unchanged P2-V0.23.25 safe engine can validate/apply it when the target truly does not exist.

### AC-03 Model does not own patch mechanics
The DSPy typed output schema for live implementation generation contains path/content intent and does not require or accept model-supplied `expected_base_sha256` or `unified_diff` fields.

### AC-04 Canonical downstream contract is preserved
`ImplementationGeneration.proposal` remains the existing `ImplementationProposal`, and `ProtectedImplementationRuntime` / agentic candidate validation require no alternate mutation path.

### AC-05 No-op and duplicate edits fail closed
Duplicate target paths and after-content identical to authoritative before-content are rejected as protected output validation failures before candidate admission.

### AC-06 New-file collision remains fail-closed
If a path absent from selected context actually exists in the workspace, the generated empty-base proposal is rejected by the unchanged safe proposal validator. No source mutation occurs.

### AC-07 Newline and deterministic rendering are proven
Focused fixtures cover ordinary trailing-newline text, text without a trailing newline, empty existing text to non-empty content, and stable identical renderer output. Every supported fixture round-trips through the strict patch engine with exact expected after-content.

### AC-08 Existing safety rules remain authoritative
Traversal, absolute paths, secret-sensitive target/content, unsupported extension, binary/NUL content, symlink and hierarchy-conflict cases remain rejected by existing protected boundaries.

### AC-09 Structured-output failure classification remains truthful
Malformed typed file-intent output is classified `validation_failed`; provider timeout/rate/transport behavior remains separately classified.

### AC-10 Validator repair is semantic and finite
Repair guidance no longer asks models to repair diff mechanics. The existing one final validator repair per work unit, cache-distinct final context token and admitted agent rules remain unchanged.

### AC-11 Protected release gates pass
Focused tests, full API regression, client checks, protected promotion evaluation, Bounded Autonomy, Workstream Spec Validation and required DSPy compilation/verification pass on the exact reviewed head.

### AC-12 Exact production deployment is healthy
After merge, the exact application source reaches READY production deployment. `/health` and `/ready` are HTTP 200 with database/providers ready, and required production preflights remain green.

### AC-13 Real build progresses beyond patch mechanics
An authenticated retry of Engineering Run `3a1ba66a-5649-42b6-81ee-91684fe06bbc` or equivalent real work must no longer fail because the model cannot produce mechanically valid unified diffs. Success is progression into BUILD or a later bounded failure whose evidence is unrelated to model-owned diff syntax.
