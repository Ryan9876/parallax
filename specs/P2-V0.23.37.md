## 1. Objective

Correct the real-provider greenfield baseline mechanism without changing the accepted security or product boundary.

P2-V0.23.36 is deployment-verified and its frozen W9-S1 retry proved exact Vercel Project discovery now succeeds. That retry then exposed a later GitHub failure in the P2-V0.23.7 empty-repository initializer. Production created the fixed `.parallax-greenfield` root marker through the Contents API and successfully deleted it through the Contents API, but GitHub subsequently returned HTTP 409 for both the canonical default ref and the cleanup commit SHA returned by the delete response. The repository returned to provider-level empty state rather than retaining the durable readable empty-tree cleanup commit assumed by P2-V0.23.7.

Preserve the accepted deterministic two-commit baseline, zero persistent bootstrap source, exact repository scope, REVIEW-only mutation authority, and existing branch -> accepted-lineage commit -> pull request -> Vercel Preview path. Replace only the invalid second-commit mechanism: after the documented Contents API root initialization makes Git Database operations available, create the empty cleanup tree/commit through Git Database endpoints and non-force fast-forward the exact canonical default ref to that cleanup commit.

## 4. Architecture requirements

### 4.1 Positive empty inspection remains authoritative

Greenfield initialization remains available only after authenticated exact-repository inspection proves the canonical repository exists and has no default-branch head. GitHub HTTP 409 is normalized to empty only when its exact provider message is `Git Repository is empty.` under the existing v3.32 contract. Missing repository, authorization denial, outage, malformed response or arbitrary conflict cannot imply greenfield.

### 4.2 Contents API remains the one empty-repository bootstrap primitive

When no head exists, the initializer creates exactly one fixed `.parallax-greenfield` path on the canonical default branch using the existing deterministic version/provenance content, root message and server-owned actor. This is the only operation allowed while GitHub still considers the repository empty.

The returned bootstrap commit SHA and marker blob SHA are not trusted by themselves. Before cleanup construction, the initializer reads the canonical default ref and requires it to equal the bootstrap commit, then reads and verifies the bootstrap commit/tree/blob as the exact root baseline candidate: zero parents, fixed root message/actor, one fixed non-executable marker path and exact content/provenance.

### 4.3 Git Database cleanup constructs the durable empty commit

After verified bootstrap initialization:

1. create a new Git tree using the verified bootstrap tree as `base_tree` and exactly one entry for `.parallax-greenfield` with mode `100644`, type `blob`, and `sha: null`;
2. verify the returned tree SHA is non-empty and read the tree back; it must contain zero entries and must not be truncated;
3. create one cleanup commit using the fixed cleanup message/actor, the verified empty tree SHA, and exactly one parent equal to the bootstrap commit;
4. verify the returned cleanup commit identity and read it back before ref mutation; its message/actor/tree/parent must match exactly;
5. re-read the canonical default ref and require it still equals the bootstrap commit;
6. `PATCH` exactly `refs/heads/<canonical-default-branch>` to the cleanup commit with `force=false`;
7. read the default ref back and require exact equality to the cleanup commit;
8. run the existing full two-commit baseline verification before returning baseline authority.

No other tree path, ref, parent, commit message, actor or branch can be supplied by caller, model, source or provider response.

### 4.4 Concurrency remains fail closed

The bootstrap root may be created only from positive empty state. After bootstrap creation, any unexpected default-ref value before cleanup or before final PATCH is a conflict. The non-force ref update is mandatory defense in depth. A 409/422 from tree, commit or ref mutation is not converted to success unless exact final read-back proves the already-completed deterministic operation for the same expected bootstrap/baseline identity; unrelated provider movement remains failure.

The initializer never force-updates or deletes unrelated source and never rewinds a ref.

### 4.5 Exact replay remains read only

If initial inspection returns a commit-bearing default head, initialization performs no mutation. It succeeds only when the existing head and its parent/history/tree/blob/message/actor/provenance satisfy the same exact deterministic two-commit baseline. Any unrelated head or partial bootstrap state fails closed for operator resolution.

### 4.6 Existing delivery path remains unchanged after baseline

`VerifiedLineageDelivery` continues to use the verified cleanup commit as the base for the existing bounded Parallax branch. Accepted source remains committed only to the bounded branch, then existing PR create/read-back and Vercel Preview create/read-back execute. Production target, production promotion, merge and REVIEW completion remain outside autonomous authority.

## 5. Security

- Repository authority is exact and server-owned before every provider operation. The initializer cannot select another repository.
- Existing delivery credentials remain short-lived and exact-repository scoped with only `contents:write`, `metadata:read` and `pull_requests:write`; this release adds no permission.
- The one typed `repository.initialize-empty` provider action continues to own the whole initialization transaction; raw Git endpoints are implementation details behind that already-admitted action, not new model/tool capabilities.
- The only initial source path is fixed `.parallax-greenfield`; its content carries only fixed version text and a one-way provenance digest. No application source, benchmark content, credential or raw Project/run identity is written.
- Tree deletion is exact: fixed path, fixed mode/type, `sha: null`, verified bootstrap `base_tree`. No arbitrary deletion list is accepted.
- Cleanup commit parent, tree, message and actor are server-owned/verified. Caller/model input cannot author Git objects or refs.
- Default-ref update is exact canonical ref and `force=false`; force update is prohibited.
- Provider responses are untrusted until exact read-back. Returned commit/tree/ref identities do not alone establish success.
- Credentials, tokens, raw provider payloads and source bytes do not enter logs, run events, committed configuration or client responses.
- No repository mutation occurs merely because a public-source read failed; positive authenticated empty inspection remains mandatory.
- Existing human REVIEW ceiling is unchanged.

## 6. Reliability and rollback

The change has no database or environment schema migration. Existing commit-bearing repositories and source-only delivery do not enter this greenfield initializer path.

Every mutation is serial and bounded. The bootstrap root is verified before cleanup. The cleanup commit is verified before ref movement. The ref is checked immediately before a non-force update and verified afterward. A concurrent unrelated push causes failure rather than overwrite.

If the candidate release fails before production cutover, the current P2-V0.23.36 deployment remains READY. If runtime replay exposes an independent later blocker after the corrected baseline succeeds, that blocker is recorded separately without broadening this workstream.

Because production evidence disproves the old Contents-DELETE cleanup assumption, rollback to P2-V0.23.36 preserves the last-known-good API but does not restore greenfield W9-S1 publication. Forward correction is required for that path.

## 9. Risks

- Treating the Contents DELETE response as authoritative would reproduce the current failure; the corrected path must not call it for the cleanup commit.
- Creating an empty tree/commit without first initializing the repository would reproduce GitHub's documented empty-repository 409; the Contents root remains mandatory.
- Trusting the first ref read without rechecking before PATCH could overwrite concurrent movement; exact pre-update read plus `force=false` are both mandatory.
- Reusing existing generic Git commit methods without constraining paths/messages/parents/ref could accidentally widen provider authority; this work remains inside the fixed greenfield client and typed initializer action.
- A valid deterministic baseline may still expose a later PR or Preview provider blocker. That is not justification to widen this workstream.
