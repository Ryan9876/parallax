# Parallax 2.0 — Wave 2 Project Binding and Execution Identity

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.15.1
Workstream: WS-APP-PROJECT-BINDING / GitHub issue #59
Depends on: deployed Wave 1 Project/App lifecycle P2-V0.14.1
Method: additive nullable historical compatibility with fail-closed Project binding for new app-building runtime records

## 1. Objective

Make canonical `Project.id` the immutable runtime application identity for new Code conversations and Engineering Runs while preserving explicit read compatibility for historical pre-Project records.

This slice binds new app-building conversations to an authenticated owner-accessible Project, carries that identity through Work Specification ownership and Engineering Run persistence, and removes caller authority to choose an Engineering Run workspace. It does not allocate a filesystem/sandbox workspace; issue #60 owns Project-to-workspace allocation and lineage.

## 2. Fixed decisions

- `Project.id` remains the only canonical durable application identity.
- `Conversation.project_id` is nullable only so historical pre-Project conversations remain representable; new Code conversations require a non-null owner-accessible Project.
- `EngineeringRun.project_id` is nullable only so historical pre-Project runs remain representable/readable; every new protected Engineering Run must persist the exact Project ID bound to its Code conversation.
- Work Specifications remain owned by Conversation. This slice does not add a redundant mutable Project field to Work Specification rows.
- Project ownership is resolved server-side from the authenticated `AccessPrincipal.subject` and the canonical Project repository. Caller-supplied owner identity is never trusted.
- Project-bound Conversation and Engineering Run reads are owner-scoped. Historical unbound rows remain readable through the existing authenticated compatibility boundary because this workstream has no trustworthy historical owner mapping and must not fabricate one.
- Caller request contracts may not select `workspace_ref`. The existing nullable `EngineeringRun.workspace_ref` persistence seam remains for historical rows and future server-generated lineage from #60 only.
- No existing historical row is silently assigned to a Project.

## 3. Architecture requirements

Add nullable foreign-key Project identity columns to `conversations` and `engineering_runs` with indexes and forward-only production migration evidence.

Runtime service construction for protected API routes must enforce owner-aware Project resolution. New Code conversation creation fails unless `project_id` resolves for the authenticated owner. Project-bound Conversation access fails closed for a different owner while historical-unbound rows retain compatibility visibility.

Engineering Run creation/activation derives `project_id` exclusively from the durable Code conversation. It must not accept a caller-selected Project ID or workspace identity. A bound run must match its Conversation and approved Work Specification; a mismatched or historical-unbound conversation cannot create a new protected run in strict runtime mode.

Existing direct/internal test construction may explicitly use non-strict compatibility mode to exercise historical behavior, but production route dependencies must construct strict owner-scoped services.

## 4. Scope

- add nullable `Conversation.project_id` and `EngineeringRun.project_id` foreign keys to canonical `projects.id`;
- expose explicit Project binding state in read contracts;
- require owner-accessible Project binding for new Code conversation API creation;
- preserve Reason conversation creation without Project binding unless a Project is explicitly supplied and owner-resolved;
- owner-scope project-bound Conversation reads, lists, message mutation and response operations;
- keep Work Specifications project-consistent through owner-scoped Conversation resolution, without duplicating Project persistence;
- derive and persist Engineering Run Project identity from its Code conversation;
- owner-scope project-bound Engineering Run reads and protected operations;
- reject caller-supplied `workspace_ref` in new run request contracts;
- preserve historical-null read compatibility and migration safety;
- add focused persistence/API/security/mismatch tests.

## 5. Security invariants

- A caller cannot create a Code conversation for another owner's Project.
- A caller cannot read or mutate a Project-bound Conversation owned by another principal.
- A caller cannot create or activate an Engineering Run with a Project different from the Conversation's Project.
- A Work Specification from a different Conversation cannot be used to create/activate the run and therefore cannot cross Project boundaries indirectly.
- A caller cannot provide `project_id` on an Engineering Run request; the server derives it from Conversation.
- A caller cannot provide `workspace_ref` on Engineering Run create/activate requests. Unknown request fields fail validation rather than being silently ignored.
- `workspace_ref = project:<id>` is not accepted as execution authority. Project identity and future workspace allocation remain separate trust boundaries.
- Historical null Project bindings are compatibility state only and cannot be used to start new strict protected app-building execution.
- No provider, shell, Git, network, secret, sandbox-allocation or deployment authority is added.

## 6. Non-goals

- Project-to-filesystem or Project-to-Vercel-Sandbox allocation (#60);
- implementation generation/runtime wiring (#61);
- GitHub/Vercel concrete provider adapters (#62);
- patch engine changes;
- protected app-builder scoring or promotion-threshold changes;
- client Project-selection UI;
- historical Project inference/backfill guesses;
- migration application, merge or deployment by this worker.

## 7. Acceptance criteria

### AC-01 Canonical Code conversation Project binding
A new Code conversation created through the protected runtime API requires one `project_id` that resolves through the canonical Project repository for the authenticated `AccessPrincipal.subject`. The server persists that exact Project ID and rejects missing, unknown, or cross-owner Project bindings.

### AC-02 Immutable durable Conversation identity
`Conversation.project_id` persists across database sessions and is not exposed through any mutation surface in this slice. Read contracts report the persisted Project ID and explicit `PROJECT_BOUND` state; historical null rows report `HISTORICAL_UNBOUND` without synthetic assignment.

### AC-03 Owner-scoped Project-bound Conversation access
List/read/message/follow-up/response operations may expose or mutate a Project-bound Conversation only when its Project belongs to the authenticated principal. Cross-owner access is indistinguishable from missing. Historical-unbound conversations retain existing authenticated compatibility visibility.

### AC-04 Work Specification Project consistency without duplication
Work Specifications remain bound only to Conversation. Protected Work Specification read/draft/approve/resume operations resolve the owning Conversation through the same owner-scoped runtime access boundary, preventing cross-owner/cross-Project specification access without adding a mutable `project_id` column to Work Specification.

### AC-05 Canonical Engineering Run Project binding
Every new strict Engineering Run persists `project_id == conversation.project_id`. Run create/activate derives this value server-side and rejects historical-unbound Code conversations, Conversation/spec mismatches, and any existing nonterminal run whose persisted Project identity differs from the Conversation binding.

### AC-06 Owner-scoped Engineering Run access
Project-bound run read/latest/advance/autonomy/control operations validate access through the canonical Project owner boundary. Cross-owner run access fails as not found. Historical-unbound runs remain readable for compatibility but cannot be newly activated or mutated through strict runtime execution.

### AC-07 Caller workspace authority removed
`EngineeringRunCreate` and `EngineeringRunActivate` do not contain `workspace_ref` or caller-selected `project_id`, reject unknown fields, and strict runtime services reject any direct caller attempt to inject a workspace reference. New runs keep `workspace_ref` unset until #60 supplies server-generated lineage.

### AC-08 Forward-only historical-compatible migration
The committed migration adds nullable indexed Project foreign keys to Conversation and Engineering Run without assigning existing rows. Existing null rows remain valid historical state; invalid non-null Project references fail foreign-key integrity. The migration is generated/validated evidence only and is not applied by this worker.

### AC-09 Focused negative and regression evidence
Tests cover owner-accessible Code creation, missing/unknown/cross-owner Project rejection, persistence, historical-unbound compatibility, Project-bound Conversation isolation, Work Specification access inheritance, Engineering Run Project persistence, cross-Project/spec mismatch rejection, cross-owner run denial, and workspace-injection rejection. Full API regression and Python compilation must remain green.

### AC-10 Worker release boundary
The completed candidate includes this approved specification, committed compiled DSPy plan, migration, focused tests, exact validation evidence and an open PR from `ws/app-project-binding` to `main`. The worker does not merge, apply production migrations, allocate runtime workspaces, change authoritative project records, or deploy.

## 8. Risks and mitigations

- **Historical records lack reliable owner mapping.** Mitigation: preserve null as explicit historical-unbound state and retain the previous authenticated read compatibility; do not fabricate ownership.
- **Backend contract can precede Project-selection UI.** Mitigation: this worker does not deploy; Integration must coordinate client/runtime rollout before production requires Code Project selection.
- **Project identity could be confused with execution workspace.** Mitigation: remove `workspace_ref` from caller contracts and leave server allocation to #60.
- **Indirect cross-Project Work Specification use.** Mitigation: keep Work Specification conversation-owned and validate Conversation ownership plus specification/conversation equality before Engineering Run creation.
- **Nullable database columns could be misread as permission for new unbound work.** Mitigation: strict production service construction fails closed for new Code/run creation while nullable persistence exists only for history.
