Correct greenfield deterministic-baseline verification for the provider-owned commit timestamp behavior proven by the P2-V0.23.37 production replay, without relaxing any authority-bearing repository identity.

P2-V0.23.38 therefore keeps exact actor name/email verification and validates timestamp only as bounded parseable provider metadata rather than deterministic baseline identity.

## 5. Architecture requirements

### 5.1 Actor identity and timestamp metadata are separate

The server-owned Parallax actor identity remains exact name `Parallax App Builder` and exact email `parallax-app-builder@users.noreply.github.com` for both author and committer. These values continue to be supplied by the initializer and must match provider read-back exactly.

The provider read-back `date` is chronology metadata. It must exist, be a non-empty string and parse as an offset-aware ISO-8601/RFC3339 instant. Its exact value is not compared to the request preference and does not participate in deterministic baseline matching.

### 5.2 Request remains server owned

The initializer may continue to send the fixed request timestamp preference where the existing provider payload requires/allows it. That value remains a server constant; caller/model/browser input cannot set actor fields. Provider normalization or substitution of the timestamp does not invalidate the baseline if every authority-bearing invariant and timestamp shape validate.

### 5.3 Exact baseline verification remains authoritative

Existing verification remains unchanged for:

- exact repository and canonical default branch;
- exact cleanup message;
- exactly one cleanup parent;
- exact empty cleanup tree;
- exact bootstrap message and zero parents;
- exact one-entry bootstrap tree;
- exact marker path, blob mode/type and blob identity/content;
- exact version/provenance bytes;
- exact current default ref;
- read-only replay behavior for an existing baseline.

A timestamp-compatible commit that fails any of these invariants remains `GREENFIELD_BASELINE_MISMATCH`.

### 5.4 Malformed provider metadata remains fail closed

Missing author/committer object, missing name/email/date, wrong name/email, malformed date, timezone-naive date or non-string date is invalid provider baseline evidence. No raw provider data is surfaced to clients.

### 5.5 Existing lifecycle authority remains unchanged

Once the deterministic baseline verifies, verified delivery continues through the existing bounded Parallax branch, accepted-lineage commit, exact PR create/read-back and exact Vercel Preview create/read-back. Autonomous authority still stops at REVIEW.

## 6. Security

Actor timestamp carries no authority and cannot widen repository access. Exact actor name/email continue to prevent arbitrary user/provider commits from masquerading as Parallax-owned baseline history. Exact message, parent, tree, marker/provenance and default-ref checks remain stronger identity evidence than provider-controlled chronology.

Timestamp parsing must be side-effect-free and bounded. It must not consult network time, environment secrets, model output or browser input. No timestamp value may influence provider scope, mutation target, lifecycle state, approval or promotion.

## 7. Reliability and rollback

This is a verification compatibility correction with no migration. Existing commit-bearing repositories and source-only flows are unchanged. Newly created P2-V0.23.37 Git Data cleanup commits may preserve the fixed requested timestamp; legacy/real Contents-produced baseline commits may carry provider timestamps. Both are accepted only when the same exact non-temporal invariants hold.

Rollback to P2-V0.23.37 remains operationally safe but reintroduces the frozen W9-S1 `GREENFIELD_BASELINE_MISMATCH`; therefore production greenfield continuation requires the forward fix.

## 10. Risks

The main risk is over-correcting one provider timestamp discrepancy into broad historical commit acceptance. The mitigation is narrow: relax only exact timestamp equality while strengthening explicit timestamp shape/timezone validation and preserving every authority-bearing baseline invariant.

A second risk is treating provider chronology as security evidence. It is not. Name/email, exact deterministic content/history and repository/ref binding remain the relevant identity controls.
