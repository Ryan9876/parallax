## 1. Objective

Close the two remaining composition gaps in the strict repository-backed Code loop without creating a new identity, storage, authority, transport, credential, or release system.

For a newly activated Project-bound Code Engineering Run with no current source lineage, initialize the first durable lineage exactly once from the canonical owner-scoped Project `repository_ref` through the existing project-authorized GitHub read actions and #70 concrete client boundary. After protected IMPLEMENT and same-lineage BUILD/TEST/VERIFY succeed, publish only that exact accepted verified lineage through the existing bounded GitHub branch/commit/PR actions and Vercel Preview create/read actions before returning control for operator review.

The worker must preserve #68 durable immutable-object + transactional CAS semantics, #69 same-lineage execution, #45/#62 project-scoped authority, #70 scoped credential/client behavior, and the Preview-only/operator-review ceiling.

## 2. Fixed decisions

- Canonical runtime identity is only `ProjectRunIdentity(project_id=EngineeringRun.project_id, run_id=EngineeringRun.id)` from persisted server state.
- Project repository binding is resolved owner-scoped from the persisted canonical Project. Caller/model input cannot choose repository URL/ref, filesystem root, credential, source revision, branch base, Vercel target, transport, or arbitrary provider payload.
- Repository bootstrap uses only existing typed `GitHubProviderActions.resolve_repository`, `read_tree`, and `read_file` under the existing authority registry and concrete credential/client boundary.
- The root durable lineage records repository provenance through its existing `source_ref_digest`; the deterministic protected source reference is `repository_ref@provider_revision`. No new lineage schema or migration is introduced.
- A retry/process recreation with the same repository revision is idempotent through #68 `SourceLineageStore.initialize` CAS semantics. A competing/different initial source fails closed.
- IMPLEMENT continues to advance lineage through the existing expected-parent CAS path. BUILD/TEST/VERIFY continue to execute only on the exact accepted lineage through #69.
- Publication is allowed only after a successful protected VERIFY for the same accepted implementation lineage.
- Before publication, the composition walks the accepted lineage to its repository root, resolves the current repository state, recomputes the protected root provenance digest, and requires an exact match. A moved provider parent is a stale-parent failure; publication never rebases or guesses.
- GitHub delivery uses one deterministic `parallax/...` branch, exact parent revision, exact accepted lineage files, and the existing idempotent branch/commit/PR client behavior.
- Vercel delivery uses only the existing registered Preview target and exact committed source revision/branch/lineage. Production target/branch/promotion is forbidden.
- Provider credentials remain server-only and resource-scoped. They never enter model/client contracts, source lineage, run evidence, provider evidence, exceptions, or logs produced by this composition.
- Provider denial/failure is not release success. The Engineering Run remains at operator-review state and the composition returns a structurally failed delivery result; it never fabricates promotion/deployment evidence.

## 3. Architecture

Add a narrow source-delivery composition layer that consumes existing interfaces rather than modifying provider or persistence internals.

### Repository bootstrap provider

A `RepositoryBoundSourceProvider` is constructed server-side for exactly one authenticated owner-scoped Project and one `ProjectRunIdentity`. It resolves the Project by canonical ID, requires an active GitHub `repository_ref`, creates a `ProviderProjectBinding`, and uses server-owned `ProviderInvocation` values for the fixed GitHub read actions. It resolves the repository/default head, reads the bounded tree, then reads every allowed file at that exact immutable provider revision. It returns a `SourcePackage(source_kind="repository", source_ref=f"{repository_ref}@{head_revision}", files=...)`.

No URL, clone command, Git process, local source root, caller-selected SHA, or raw credential is accepted.

### Bootstrap orchestration

Extend the narrow durable allocator protocol consumed by runtime composition with only the already-implemented `initialize(identity, SourceProvider)` and `current_lineage(identity)` methods. `EngineeringRuntimeComposition` derives `ProjectRunIdentity` from the persisted run, checks whether current lineage exists, and initializes only when absent. Existing `SourceLineageStore.initialize` remains the concurrency/idempotency authority.

### Verified publication

A `VerifiedLineageDelivery` resolves the exact accepted lineage after VERIFY from durable storage, verifies Project/run identity, traverses parents to the repository root, and proves that the currently resolved provider head still hashes to the root `source_ref_digest`. It converts the accepted durable lineage files to existing `GitHubCommitFile` values by reconstructing exact immutable object content through a disposable allocator lease; the file set/content digests must match the accepted lineage manifest before any provider mutation.

It then composes existing actions only:

1. GitHub branch create from the proven bootstrap parent;
2. GitHub accepted-lineage commit using exact expected parent;
3. GitHub PR create and read-back validation;
4. Vercel Preview create from exact commit revision/branch/lineage;
5. Vercel Preview read-back validation.

The delivery result contains only bounded provider evidence/identities and safe URLs. It is not a release/promotion record.

### Runtime placement

`EngineeringRuntimeComposition.run` performs first-lineage bootstrap before protected autonomy needs source material. When the coordinator reaches `REVIEW_REQUIRED` after VERIFY, the composition confirms the successful VERIFY attempt is lineage-bound to the exact accepted implementation lineage and invokes verified delivery before returning the review result. Operator review remains the state-machine ceiling; no stage transition is added.

Production route wiring may inject only server-owned configured authority/credential/target composition. In the absence of approved live provider configuration, provider bootstrap/delivery fails closed; this worker does not provision credentials, storage, targets, or apply migrations.

## 4. Scope

This worker owns only the composition needed to bind first-run repository source into the existing durable lineage allocator and to bind post-VERIFY accepted lineage into the existing bounded provider actions. It may add one composition module, narrow runtime-composition wiring, and focused tests. It does not modify lineage persistence or migrations, Project persistence, provider action/client/credential contracts, authority policy, IMPLEMENT generation/mutation, same-lineage sandbox execution, client UI, or deployment/release workflows.

The implementation must consume already-integrated #45/#62/#68/#69/#70 contracts without widening them. Live production credential, Vercel target, storage, or migration rollout remains an Integration/Control Tower responsibility.

## 5. Security and authority invariants

- No caller/model source URL, repository selector, source SHA, filesystem root, branch base, provider token, Vercel project, arbitrary action, command, URL, HTTP method/body, or Git command enters the composition contract.
- `workspace_ref` is never source authority.
- Repository metadata selects a registered resource but never grants capability.
- Every GitHub/Vercel action passes through `ToolCapabilityRegistry` using the canonical Project ID.
- Concrete clients continue to obtain only resource-scoped credentials from their injected credential providers.
- Secret values are not serialized into lineage, run/provider evidence, errors, tests, or evaluation artifacts.
- No generic shell, subprocess, Git CLI, generic HTTP transport, arbitrary network call, provider proxy, merge, production Vercel deployment, promotion, alias/domain mutation, environment mutation, or secret mutation is introduced.

## 6. Acceptance criteria

### AC-01 Canonical owner-scoped bootstrap binding
A first-run bootstrap derives `ProjectRunIdentity` only from persisted `EngineeringRun.project_id` + `EngineeringRun.id`, resolves that Project for the authenticated owner, and requires the Project's canonical GitHub `repository_ref`. Cross-owner/missing/repository-mismatch cases fail closed.

### AC-02 Authorized repository-backed source provider
Bootstrap source is obtained only through existing project-scoped GitHub provider actions and the accepted concrete GitHub credential/client boundary. Repository resolve/tree/file reads bind one immutable provider revision and return a bounded `SourcePackage`; no URL/clone/Git/shell/generic HTTP/caller-selected revision path exists.

### AC-03 Durable first-lineage CAS and replay
When no current lineage exists, the allocator initializes exactly once through #68 durable lineage storage. Same-source retry and process recreation resolve the same accepted lineage; a different/conflicting initializer or stale identity fails closed without replacing current lineage.

### AC-04 Root provider provenance without schema expansion
The initial lineage `source_ref_digest` is the SHA-256 of the deterministic protected `repository_ref@provider_revision` reference. Publication can re-prove the expected parent revision by resolving the repository and matching this digest; no new durable lineage field or migration is required.

### AC-05 Same-lineage IMPLEMENT through VERIFY preserved
Protected IMPLEMENT advances the exact bootstrapped lineage using existing expected-parent CAS semantics. BUILD/TEST/VERIFY execute only on that accepted implementation lineage using #69. Fresh repository checkout or unrelated lineage fallback after IMPLEMENT is forbidden.

### AC-06 Verified-lineage-only publication gate
Delivery is callable only after protected VERIFY succeeds and its server-owned evidence binds the same canonical Project/run and exact accepted source lineage. Pre-IMPLEMENT, parent/root, unverified, stale, forged, or unrelated lineage publication is rejected before provider mutation.

### AC-07 Exact accepted lineage materialization
Publication reconstructs the exact accepted durable lineage into disposable server-owned materialization, verifies Project/run/lineage/content digest/file manifest, and converts only that verified content into bounded existing `GitHubCommitFile` values. Local materialization is never durable authority and is always cleaned up.

### AC-08 Bounded GitHub delivery and parent protection
Delivery uses only existing authorized GitHub branch-create, accepted-lineage commit, PR-create, and PR-read actions. Branch identity is deterministic and bounded; commit uses the re-proven bootstrap provider revision as exact expected parent. Moved/stale parent, repository mismatch, PR/head mismatch, authority denial, credential denial, or provider failure fails closed. Existing replay semantics prevent duplicate branch/commit/PR creation.

### AC-09 Preview-only Vercel delivery
After exact GitHub commit/PR validation, delivery uses only existing authorized Vercel Preview create/read actions with the exact canonical Project/repository, committed source revision, deterministic branch, accepted lineage, and registered Vercel Preview target. Production branch/target/promotion/alias/domain/environment/secret mutation remains impossible. Existing replay semantics prevent duplicate previews.

### AC-10 Secret-safe bounded delivery evidence
Success returns only bounded Project/run/repository identity digest, lineage ID/content digest, branch/commit/PR identifiers, preview deployment status/identity and safe URLs through existing provider evidence. Credential material, headers and raw provider payloads are absent. Denial/failure remains structurally distinct from success and is never recorded as release/promotion/deployment success.

### AC-11 Deterministic failure/idempotency evidence
Tests cover first bootstrap, repeated bootstrap, independent process/allocator recreation, cross-project/repository mismatch, competing initial source, stale provider parent, exact provider retry/idempotency, verified-lineage-only publication, credential/authority denial, cleanup, and Preview-only ceiling.

### AC-12 Worker release boundary
Candidate contains approved spec + authentic committed DSPy plan before implementation, only declared composition/test changes, exact-head Workstream Spec Validation/P2 CI/Bounded Autonomy success, and an open PR targeting `integration/wave2-app-builder`. Worker does not merge, deploy, apply migrations, provision production credentials/storage/targets, or edit authoritative project records.
