# Parallax 2.0 — Pre-Resume State Snapshot Correction

Status: APPROVED FOR IMPLEMENTATION — SPEC-FIRST
Spec ID: P2-V0.23.12
Date: 2026-08-30
Workstream: #474
Architecture: v3.25 (unchanged)

## 1. Objective

Correct the P2-V0.23.11 `/resume` composition so the human-authorized terminal-worker re-arm decision is based on the Engineering Run state that existed before the resume mutation, rather than on a live ORM object that may be refreshed in-place by the same SQLAlchemy session.

## 2. Triggering evidence

Production Engineering Run `2b3cd15f-c5e2-481a-8266-c92c6534b08b` was explicitly retried after the P2-V0.23.11 API deployment. Persisted event #29 recorded `RUN_CONTROL / RESUMED`, but event #30 immediately recorded `IMPLEMENT / FAILED` with `AUTONOMOUS_IMPLEMENT_FAILED`. The expected P2-V0.23.11 worker `RECOVERING` observation did not occur between those events.

The route retained `prior = svc.get(run_id)` as a live SQLAlchemy identity-mapped `EngineeringRun`, then invoked `svc.resume(...)` through the same session. The resume mutation can refresh the same Python object to `IMPLEMENT` before the route evaluates `prior.state == "FAILED"`. That causes the existing v3.25 re-arm branch to be skipped even though the request entered from durable `FAILED` state.

## 3. Fixed decisions

- The authoritative Engineering Run resume transition remains owned by `EngineeringRunService.resume`.
- The worker re-arm authorization decision uses an immutable scalar snapshot of the pre-resume run state.
- Re-arm remains permitted only when the request began from `FAILED` and the successful resume result is no longer `FAILED`.
- `WorkerRecoveryService.prepare_human_resume` and the existing `FAILED -> RECOVERING -> REASSIGNED` worker path remain unchanged.
- Ordinary `/autonomous`, reconnect, page refresh and repeated acquisition still cannot restart a terminal worker by themselves.
- The route correction creates no new model, source, repository, provider, deployment or REVIEW authority.
- A deliberately identity-aliased route regression is required so this same-session ORM behavior cannot escape again.

## 4. Scope

Owned implementation scope:

- snapshot `prior_state` as a scalar before the `/resume` mutation;
- use that scalar in the existing P2-V0.23.11 authorization predicate;
- add deterministic route-level regression for same-object identity-map mutation;
- retain existing worker recovery regressions;
- run the full protected release gates;
- reconcile current state only after exact-source deployment evidence exists.

No persistence migration, client change, worker schema change, routing-policy change, source-lineage format change or architecture revision is required.

## 5. Security and reliability

This is a fail-closed correctness correction to an already-approved authority boundary. It does not make terminal worker recovery more permissive. The authenticated user must still explicitly resume a FAILED Engineering Run before any worker re-arm can occur, and the worker must still satisfy the existing unleased terminal-state checks inside `prepare_human_resume`.

The scalar snapshot prevents authorization from depending on ORM identity-map mutation timing. The worker recovery operation remains compare-and-swap guarded, idempotent after the worker leaves `FAILED`, and unable to issue a fresh mutation lease directly; the existing `RECOVERING -> REASSIGNED` path alone increments lease generation.

Historical attempts, run events, worker checkpoints, lineage references and prior failure evidence remain immutable and visible.

## 6. Acceptance criteria

### AC-01 Pre-resume FAILED state is snapshotted
The `/resume` route captures the Engineering Run state as an immutable scalar before invoking `EngineeringRunService.resume`.

### AC-02 Identity-map alias mutation cannot suppress re-arm
When the object returned by the pre-read is the same object mutated by `resume`, a request that entered from `FAILED` still invokes `prepare_human_resume` after a successful transition to an active stage.

### AC-03 Non-failed resume does not gain terminal-worker authority
If the request begins from any state other than `FAILED`, the route does not invoke terminal-worker re-arm solely because the post-resume run is active.

### AC-04 Failed postcondition remains fail-closed
If the resume result remains `FAILED`, terminal-worker re-arm is not invoked even when the pre-resume scalar state was `FAILED`.

### AC-05 Worker recovery contract remains unchanged
Eligible recovery still uses the existing v3.25 unleased `FAILED -> RECOVERING` preparation followed by the existing protected `RECOVERING -> REASSIGNED` lease-generation path.

### AC-06 Automatic restart remains prohibited
Ordinary `/autonomous` calls, acquisition attempts, reconnects and page refreshes cannot re-arm a terminal worker without the explicit successful FAILED-run resume boundary.

### AC-07 Historical evidence is preserved
The correction does not rewrite or delete prior Engineering Run attempts/events, worker checkpoint evidence, source lineage, last-known-good lineage, current step or lease-generation history.

### AC-08 Authority ceilings remain unchanged
Candidate bounds, validator-guided repair, hosted model ordering, source mutation, Git/provider delivery, deployment and REVIEW boundaries remain unchanged.

### AC-09 Deterministic regression covers the escaped production behavior
A focused route regression deliberately mutates the same pre-read run object during `resume` and proves the recovery preparation still executes from the snapshotted scalar state.

### AC-10 Release and production proof
Focused route/worker tests, full API regression, Bounded Autonomy, client/browser/Skia, protected promotion and DSPy release gates pass. After exact-source production deployment, one explicit retry of the affected production run persists worker recovery evidence after `RUN_CONTROL / RESUMED` and progresses beyond the prior terminal-worker conflict.

## 7. Non-goals

- Automatic terminal retries.
- More than one new generation per explicit eligible human recovery boundary.
- Altering worker retry/reassignment ceilings.
- Hiding or rewriting historical failures.
- Changing the client retry UX.
- Changing model selection or candidate validation.
- New repository/provider permissions.
- Moving or bypassing REVIEW.
