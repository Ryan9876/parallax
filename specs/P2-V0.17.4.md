## 1. Objective

Build the operator-facing Live Build / Observability workspace as a faithful, inspectable projection of the protected engineering runtime. The workspace must make active and historical engineering execution understandable without granting new execution, filesystem, provider, merge, deployment or production-promotion authority.

The visible experience must follow the approved Warm Editorial mockup direction while remaining evidence-first: stage progress, run health, retries, failures, source lineage, tests, evidence, GitHub PR and Vercel Preview identity are displayed only when backed by authoritative persisted facts or protected read APIs. The UI must never infer successful progress ahead of server state, fabricate telemetry, expose hidden reasoning, or turn Parallax into a generic IDE or shell.

## 2. Scope

- Add a real Observability destination to the Warm Editorial navigation for Code conversations with an Engineering Run.
- Add a reusable Live Build workspace composed from the persisted run-event stream plus protected source/diff/evidence reads introduced by P2-V0.17.2.
- Add an observer hook that replays persisted events, resumes SSE with Last-Event-ID semantics, deduplicates by run sequence, reports transport state, and survives view pause/resume and reconnect without mutating execution.
- Render the governed engineering pipeline as SPECIFY, PLAN, IMPLEMENT, BUILD, TEST, VERIFY and REVIEW using authoritative run/event facts only.
- Render Run Event Stream controls for Follow Live, Pause View and Jump to Latest; Pause View pauses viewport following only and never pauses the Engineering Run.
- Add bounded Code, Diff, Terminal, Tests, Events and Evidence views. Source and diff content comes only from exact accepted-lineage protected read contracts; Terminal/Tests show bounded persisted evidence rather than a generic command shell.
- Derive Component Health, System Health, Active Run and Recent Alerts from persisted run facts and transport/read state. When authoritative data is unavailable, the UI renders unavailable/unknown rather than invented metrics.
- Surface current candidate lineage, parent/last-known-good lineage and correction/retry relationships when present in persisted events.
- Surface GitHub PR and Vercel Preview identities/status when present in persisted provider/evidence facts, without adding merge or production-promotion controls.
- Render explicit recoverable, failed and HUMAN_REQUIRED/REVIEW boundaries.
- Preserve existing conversation, Project, Work Specification, Engineering Run controls, authentication, mobile keyboard and reduced-graphics behavior.
- Add deterministic state/unit/browser/mobile/accessibility tests for replay, reconnect, dedupe, pause-view semantics, exact-lineage reads, responsive layout and truthfulness.

Production migration application, `PARALLAX_RUN_EVENTS_ENABLED` activation and production deployment are owned by the integrated #149 release boundary, not this worker branch.

## 3. Fixed decisions

- **Observer, not controller.** Live Build observes governed execution. Existing Engineering Run actions remain in their established protected control surface; this workspace does not add generic mutation controls.
- **Server state is authoritative.** Stage progress, health, alerts, retry/correction history and provider status must be derived from persisted events/run/evidence. No optimistic stage advancement or client-side success inference.
- **Sequence is the durable cursor.** Event ordering and reconnect resume use the server run sequence. Client timestamps are presentation only.
- **Pause View is observation-only.** It freezes auto-follow while events may continue accumulating. It never pauses execution. Pause Run remains an explicit protected Engineering Run action elsewhere.
- **Exact lineage only.** Code and Diff views may read only lineages named by the selected Engineering Run/event history through protected project/run scoped APIs. There is no unrestricted filesystem browser.
- **Bounded terminal/test evidence only.** Terminal and Tests render persisted protected attempt evidence. They are not interactive shells and cannot execute commands.
- **No hidden reasoning.** Model scratchpads, chain-of-thought, private provider payloads, credentials and unrestricted logs are not rendered or persisted into client telemetry.
- **Truthful absence.** Missing, disabled, redacted or unavailable evidence is labeled as such. Empty data never becomes green status.
- **Conversation remains primary.** Observability is a governed inspection surface accessible from the Code workflow, not a replacement coding IDE.
- **Warm Editorial stays canonical.** Forest/ivory/rust/teal/olive/charcoal tokens and responsive shell rules from P2-V0.17.3 remain the visual system.
- **Project/run scope is explicit.** Every observability request is bound to the active authenticated run and its project context; cross-Project reads must continue to fail closed server-side.
- **No production activation in #148.** The UI must tolerate Wave 4 routes being disabled and present an explicit unavailable state without breaking the core application.

## 4. Architecture requirements

### 4.1 Observer state model

Add a focused `useRunObservability` hook under `apps/client/src/hooks/**` backed by the existing `RunObservabilityClient` and `RunEventCursor`.

The hook owns only observer state:

- selected run ID;
- ordered accepted event list;
- highest accepted sequence;
- transport state `CONNECTING | LIVE | RECONNECTING | CLOSED | ERROR`;
- follow-live preference;
- view-paused state;
- selected tab and selected exact-lineage/path/attempt evidence reference;
- loading/error state for protected reads.

The hook must replay persisted events before/around stream attachment so reconnects and process recreation converge on the same ordered sequence. Duplicate or stale sequence numbers are ignored by the existing cursor contract. Switching runs resets observer-local state and cannot leak events from another run.

### 4.2 Event projection

Create pure projection helpers for UI semantics. They may translate event types/stages/outcomes into labels but cannot invent states absent from the persisted record.

The protected pipeline uses the visible stages:

1. SPECIFY — Work Specification approval / run activation evidence;
2. PLAN — engineering plan stage;
3. IMPLEMENT — source mutation / lineage candidate evidence;
4. BUILD — build attempt evidence;
5. TEST — test attempt evidence;
6. VERIFY — protected evaluation / verification evidence;
7. REVIEW — explicit human review / HUMAN_REQUIRED boundary.

A stage is complete only when persisted facts support completion. Current/failed/recoverable/human-required states are rendered separately. Future stages remain pending/unknown rather than visually complete.

### 4.3 Live Build workspace component

Create a reusable `LiveBuildWorkspace` component plus bounded child components under `apps/client/src/components/observability/**`. `App.tsx` receives only narrow composition changes: selecting the Observability destination and providing the active Engineering Run / project-bound state. Product state orchestration remains outside presentation components.

Desktop composition follows the approved mockup family:

- Warm Editorial header with run/project identity and current authoritative stage;
- horizontal/compact governed pipeline;
- central work area with Code, Diff, Terminal, Tests, Events and Evidence tabs;
- Run Event Stream with follow-live controls and sequence/time metadata;
- right contextual column for System Health, Component Health, Active Run and Recent Alerts when width permits;
- no fabricated metric cards if the runtime does not provide a defensible value.

Tablet and phone widths reflow to a single primary workspace with horizontal tabs and stacked/drawer contextual cards. Navigation and utility regions must not compress the main content below existing mobile usability requirements.

### 4.4 Event stream behavior

On opening a run:

1. request persisted replay after the local cursor;
2. append only cursor-accepted ordered events;
3. connect SSE using `Last-Event-ID` when sequence > 0;
4. append only accepted live events;
5. on network close/error, keep current events visible and offer/perform bounded reconnect rather than clearing state;
6. after reconnect, replay gaps and resume stream without duplicate UI rows.

Pause View sets `viewPaused=true` and disables automatic scroll/follow only. Accepted events continue entering the observer store. Jump to Latest clears the paused-view condition and scrolls to the newest accepted event. Follow Live controls whether the viewport continues following new events.

### 4.5 Exact-lineage Code and Diff views

The UI may select only lineage IDs observed for the active run. It retrieves file trees and text through `RunObservabilityClient.sourceTree` / `sourceFile`. Binary/too-large responses render explicit availability state without fallback guessing.

Diff compares two run-observed lineages through `sourceDiff`. Candidate defaults may be current accepted candidate vs observed parent/last-known-good only when those identities are present. The UI cannot synthesize arbitrary lineage IDs or browse the host filesystem.

### 4.6 Terminal, Tests and Evidence

Terminal and Tests are read-only evidence projections. For an observed `attempt_id`, the UI retrieves `attemptEvidence` and renders only its bounded normalized evidence payload, stage, status, attempt number, tool/model/program IDs when safe, timestamps and normalized failure code.

The UI must not expose raw provider request/response payloads or secrets. Evidence marked `UNAVAILABLE` or `REDACTED` remains visibly unavailable/redacted.

Evidence view presents durable references and safe normalized facts such as source lineage, artifact/evidence references, GitHub PR identity/status, Vercel Preview identity/status, protected evaluation outcome and human-review requirement when those facts are present in event metadata/evidence. Unknown metadata keys are not blindly dumped.

### 4.7 Health and alerts

Health projections are conservative and deterministic:

- transport health is based on current observer transport state;
- run health derives from current authoritative run state plus latest failure/recovery/human-required facts;
- component/provider health is shown only when persisted events/evidence provide a meaningful recent fact;
- recent alerts are normalized failure/retry/human-required conditions from the selected run, not a synthetic global monitoring system.

No latency, token, cost, queue or provider-SLA number is displayed unless a persisted authoritative field is explicitly available and normalized for the UI.

### 4.8 GitHub and Vercel identity

If persisted evidence exposes a GitHub PR URL/number or Vercel Preview URL/status, render it as external identity/evidence with clear Preview/PR semantics. Do not add merge, close, production promotion, environment mutation or credential controls.

### 4.9 Inactive route boundary

The runtime source is integrated but production activation is deferred. If observability routes return disabled/not-found/unavailable, the workspace renders a bounded `Live observation unavailable` state and the existing conversation/Code experience remains fully functional. App startup must not depend on event-stream availability.

## 5. Security and privacy

- All reads remain authenticated and project/run scoped by the server contracts introduced in P2-V0.17.2.
- Client code never constructs unrestricted filesystem paths, shell commands, provider API calls or production deployment actions.
- Source-file path selection comes only from the protected source tree returned for the selected exact lineage.
- Event metadata is treated as untrusted display input; only explicit allowlisted normalized fields are rendered in rich evidence cards. Generic key/value dumps are prohibited.
- Hidden reasoning, model scratchpads, raw prompts intended as private reasoning, credentials, cookies, auth headers and provider secrets remain absent.
- External PR/Preview links use only persisted normalized URLs already accepted by the runtime/provider evidence contract.
- Cross-Project reads remain a server fail-closed responsibility; client run switching must discard previous run/project data immediately.
- No generic terminal, arbitrary HTTP client, source editor, merge control or production promotion control is introduced.

## 6. Failure and recovery boundaries

- Event replay failure leaves existing Engineering Run/conversation surfaces usable and shows an explicit observer error.
- Stream disconnect retains accepted events, marks transport reconnecting/error, and can replay/resume without duplicate rows.
- A cursor mismatch or stale duplicate event is ignored rather than re-rendered.
- Missing source lineage, binary/too-large file, unavailable/redacted evidence or expired run read renders an explicit availability state.
- If a run enters FAILED but persisted facts mark it recoverable, the UI distinguishes recoverable failure from terminal/human-required state.
- HUMAN_REQUIRED/REVIEW is visually explicit and never presented as autonomous success.
- If Project/run context changes, all protected read selections are reset before the new run is observed.
- Reduced graphics/motion removes decorative transitions but preserves all evidence and controls.

## 7. Non-goals

- changing Engineering Run execution, worker leasing, retry budgets, source-lineage mutation, evaluator scoring or provider authority;
- activating `PARALLAX_RUN_EVENTS_ENABLED` or applying `20260824_0010_run_events.sql` from this worker branch;
- implementing a generic IDE, source editor, shell, terminal, arbitrary command runner or filesystem explorer;
- merging GitHub PRs, promoting Vercel Production, applying environment variables or provisioning credentials from the Live Build UI;
- displaying hidden reasoning or raw provider payloads;
- inventing global observability metrics not persisted by the runtime;
- production deployment from #148.

## 8. Acceptance criteria

### AC-01 Observer replay and SSE reconnect converge without duplicate events
For a selected Engineering Run, persisted replay plus SSE resume uses the run sequence/Last-Event-ID contract and produces one ordered UI event per accepted sequence across disconnect/reconnect, with deterministic tests covering gaps, duplicates and run switching.

### AC-02 Pipeline progress is a truthful projection of persisted facts
SPECIFY/PLAN/IMPLEMENT/BUILD/TEST/VERIFY/REVIEW states are derived only from authoritative run/event/evidence facts; the client never advances a stage optimistically or marks absent future stages successful.

### AC-03 Pause View never pauses execution
Pause View disables viewport auto-follow only while accepted events continue accumulating. Jump to Latest and Follow Live restore observation behavior. Existing protected Pause Run semantics are unchanged and visually distinct.

### AC-04 Code and Diff are exact-lineage protected reads
Source trees/files and diffs can be requested only for lineage IDs observed on the active run through protected APIs; no unrestricted filesystem browsing or arbitrary lineage/source path construction is introduced.

### AC-05 Terminal, Tests and Evidence remain bounded read-only projections
Terminal/Tests render normalized attempt evidence and Evidence renders allowlisted durable references/status only. The workspace cannot execute commands, edit source, dump raw provider payloads or expose unavailable/redacted evidence as if present.

### AC-06 Health, alerts and provider identity remain evidence-backed
System/Component Health, Active Run, Recent Alerts, GitHub PR and Vercel Preview information are rendered only when supported by persisted run/transport/evidence facts, with unavailable/unknown states instead of fabricated metrics.

### AC-07 Recoverable failure and HUMAN_REQUIRED boundaries are explicit
The UI differentiates active, recoverable failure/retry/correction, terminal failure and HUMAN_REQUIRED/REVIEW states and never presents REVIEW as autonomous completion.

### AC-08 Warm Editorial desktop and responsive mobile composition are preserved
The workspace follows the integrated forest/ivory/rust/teal/olive design system on desktop, reflows into usable mobile tabs/stacked contextual surfaces, preserves 44 pt practical targets, 16 CSS px editable text where applicable, user zoom, keyboard safety and reduced-graphics parity.

### AC-09 Inactive/unavailable observability never breaks the core application
When Wave 4 routes are disabled, unavailable or disconnected, the application continues to support authentication, conversation, Project, Work Specification and Engineering Run behavior and renders an explicit Live observation unavailable state without fake data.

### AC-10 Cross-context observer state fails closed
Switching conversation/project/run clears prior protected source/evidence selections and event state before observing the new run; server cross-Project failures remain visible and no stale data is reused.

### AC-11 Existing protected runtime and client regressions remain green
Inherited API, protected evaluation, authentication, Project, Work Specification, Engineering Run, response streaming, mobile keyboard, reduced-graphics and visual acceptance suites remain unchanged or stronger.

### AC-12 Authentic plan evidence and exact-head release gates remain mandatory
The final #148 candidate contains an authentic committed DSPy SpecCritic/SpecCompiler plan for P2-V0.17.4 and passes deterministic workstream-spec validation, Parallax P2 CI and Bounded Autonomy on the exact final head. The worker stops review-ready before merge/deploy so #149 can integrate and release it.
