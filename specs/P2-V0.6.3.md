# Parallax 2.0 v0.6.3 — Deep Violet Optical Theme

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.6.3
Depends on: P2-V0.6.2
Method: Spec-first visual refinement + release verification

## 1. Objective

Replace the current light mineral presentation with the previously selected dark purple Parallax direction while preserving the existing conversation-first product, optical-response behaviors, accessibility semantics, private-session boundary, Reason/Code flows, durable conversation state, and release integrity.

The target is a premium dark optical workspace rather than a generic neon AI interface: deep navy/black substrate, restrained indigo and violet depth, cyan optical energy, translucent dark glass, high-contrast readable copy, and a cyan → indigo → violet identity treatment.

## 2. User outcome

Parallax should immediately read as a more finished, distinctive product. The workspace should feel deeper and more intentional while keeping conversation content visually dominant and controls calm. Purple is the product atmosphere; cyan is reserved for active optical energy and focus.

## 3. Fixed visual decisions

- Primary substrate: `#080B12`.
- Raised dark surface: `#0B1019`.
- Strong surface: `#111525`.
- Primary text: `#F4F2FF`.
- Secondary text: `#B8B6CC`.
- Cyan optical accent: `#7DE7FF`.
- Indigo transition accent: `#8B9CFF`.
- Violet identity/action accent: `#D18BFF`.
- Dark translucent glass replaces light mineral glass.
- The Parallax mark uses cyan, indigo, and violet as layered optical elements rather than decorative rainbow color.
- The living workplane becomes a low-energy navy/violet field with sparse optical structure. It must remain quieter than conversation text.
- The optical typesetter retains its current behavioral contract; only its settled text and energy colors change.
- Error, warning, verified, and amendment states remain semantically distinct and must not rely on purple alone.

## 4. Scope

### 4.1 Main conversation shell

Restyle the production client shell, access surface, conversation rail, top bar, mode switch, user turns, assistant response surface, composer, metadata, and amendment/error presentation to the dark violet system.

### 4.2 Living surface

Retune the Skia shader from warm mineral paper to deep navy/violet optical material. Preserve:

- low-frequency drift;
- sparse topographic structure;
- drafting-grid restraint;
- one optical focus region;
- reduced-motion behavior;
- content-first center bias.

### 4.3 Identity and response energy

Retune the Parallax Optical Mark and LaserTypesetter so the product identity follows the cyan → indigo → violet family while keeping final response text accessible and selectable.

### 4.4 Reduced-graphics parity

The non-Skia fallback must use the same dark violet visual language and retain equivalent interaction, contrast, and semantic state communication.

### 4.5 Engineering-state surface

Code-mode engineering status must use the same dark optical material system without weakening state readability or action affordances.

## 5. Security

This release is visual-only and must preserve every existing trust boundary. It introduces no new credential storage, provider access, authentication mechanism, CORS rule, API route, persistence mutation, or execution authority.

- The production root access credential remains server-owned and absent from client persistence and bundles.
- Signed HttpOnly browser sessions, bearer compatibility, the `X-Parallax-Session` marker, and same-origin `/p2-api` routing remain unchanged.
- Theme tokens and visual state may not contain secrets or derive authorization state from color or animation.
- Reduced-graphics and reduced-motion paths retain the same authorization and content semantics as the Skia path.
- Visual changes may not weaken sanitized error handling or expose protected trace detail.

## 6. Accessibility and restraint

- Core text must target WCAG AA contrast against its rendered surface.
- 44 pt minimum mobile interaction targets remain unchanged.
- Reduced-motion behavior remains unchanged.
- Purple/violet may not become the sole carrier of status meaning.
- Ambient glow must not reduce legibility or make the interface feel visually busy.
- Conversation text remains the highest-contrast visual layer.
- The dark theme must preserve keyboard, screen-reader, selectable-text, and reduced-graphics behavior.

## 7. Acceptance criteria

### AC-01 Theme fidelity

Production-visible shell uses the approved deep navy/black, cyan, indigo, and violet family rather than the v0.6.2 light mineral palette.

### AC-02 Conversation dominance

Assistant and user content remain more visually prominent than ambient workplane effects, decorative identity treatment, or glass edges.

### AC-03 Component consistency

Access screen, rail, top bar, mode switch, messages, response glass, composer, Code status, logo, laser, and reduced-graphics fallback visibly belong to the same material system.

### AC-04 Behavior preservation

Reason, Code, session auth, SSE transport, durable conversation persistence, SPEC_AMENDMENT handling, and engineering-run controls are unchanged functionally.

### AC-05 Accessibility preservation

Reduced motion, reduced graphics, selectable response text, keyboard interaction, and semantic state communication continue to work. Core text remains readable at production contrast.

### AC-06 Release verification

Client typecheck, response-state tests, web export, browser/Skia acceptance, API tests, protected evaluation, DSPy contract checks, Vercel deployment state, and live production routing checks pass before v0.6.3 is recorded as deployment-verified.

### AC-07 Security boundary preservation

The visual release does not add or expose credentials, change authentication/session behavior, broaden CORS, alter same-origin proxy semantics, or expose protected reasoning/trace material.

### AC-08 Reduced-graphics product parity

The non-Skia fallback uses the same Deep Violet Optical identity and preserves conversation, Code status, control, accessibility, and authorization semantics without requiring CanvasKit.

## 8. Non-goals

- No new navigation architecture.
- No dashboard conversion.
- No public accounts or authentication redesign.
- No Reason/Code model or state-machine changes.
- No new animation framework.
- No broad component-library rewrite.
- No decorative high-frequency neon, particles, HUD clutter, or continuous spinning identity motion.

## 9. Risks and mitigations

- **Dark-theme contrast regression:** use explicit high-contrast text tokens and verify browser rendering.
- **Generic AI-neon appearance:** keep saturation concentrated in small focus/identity areas; surfaces remain near-black navy/violet.
- **Ambient effects competing with copy:** retain low-energy shader amplitudes and dark center bias behind conversation content.
- **Fallback drift:** restyle the reduced-graphics application in the same change and keep it in browser acceptance coverage.
- **Unrelated regression:** keep the release visual-only and preserve existing API/session/Reason/Code contracts.

## 10. Release gate

Implementation is authorized by this specification. Production promotion requires the existing exact-head release validation and live deployment evidence. `DESIGN-SYSTEM.md` and `CURRENT-STATE.md` must be updated because this release changes durable visual language and production release state.
