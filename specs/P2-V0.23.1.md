## 1. Objective

Build a governed Skill Intake Pipeline and Capability Catalog that expands Parallax's reusable engineering repertoire without allowing external skill/tool content to become executable authority.

The first accepted slice must turn bounded external-source metadata and inspected candidate content into deterministic, replay-safe **quarantined candidate records**, explain trust/admission state, and bridge an explicitly approved exact Parallax skill contract into the existing `SkillRegistry` without changing the existing deterministic `SkillSelector` or Project-scoped `ToolCapabilityRegistry` authority model.

The product outcome is a trusted capability supply chain, not an internet plugin store.

## 2. Fixed decisions

- Existing `PortableSkill`, `SkillAdmissionPolicy`, `SkillRegistry`, `SkillSelector`, `CapabilitySnapshot`, exact content-digest admission and HUMAN_REQUIRED behavior remain authoritative.
- Existing `ToolCapabilityRegistry` remains the only tool/action authorization policy in this scope. Skill intake cannot construct, enable or approve tool capabilities.
- External skill/tool material is untrusted evidence until admitted. Discovery, normalization, inspection and catalog storage grant no execution authority.
- No candidate script, command, package, binary, MCP server, prompt procedure, JavaScript, provider action or network request executes as part of intake analysis.
- A skill describes **how** to perform work. A tool/capability describes **what action** is allowed. A skill may declare required capability IDs but cannot grant them.
- Official/vendor-native authoritative sources outrank mirrors/curated indexes when equivalent upstream material exists.
- Community indexes may produce discovery leads only. A lead must resolve to an inspectable authoritative source identity before it can become admissible.
- Candidate identity is exact and immutable for an intake observation. A material source/content/version change produces a new candidate identity and requires fresh review.
- Missing/unknown provenance, license, digest or policy evidence remains unknown. Unknown required evidence blocks automatic admission.
- Runtime skill retrieval and selection operate on admitted skills only. Quarantined, blocked, rejected or superseded candidates cannot participate in runtime selection.
- No model/evaluator may override deterministic block reasons or convert unknown supply-chain evidence into trusted state.
- S2 does not add live arbitrary internet crawling. Source adapter interfaces are bounded and testable with synthetic/fixture evidence. A future live adapter that needs new network/provider authority receives a separately governed capability contract unless an existing approved provider boundary already satisfies it.

## 3. Source trust model

### Tier A — official ecosystem
Examples: official Agent Skills ecosystem (`agentskills.io` and authoritative Agent Skills repositories) and official MCP Registry metadata.

Tier A means the source is an authoritative ecosystem publisher. It does **not** mean every candidate is automatically admitted.

### Tier B — vendor-native
First-party repositories or registries maintained by the vendor that owns the capability/technology.

### Tier C — curated discovery
Community-maintained indexes/collections. Tier C can identify leads but cannot satisfy authoritative-source provenance on its own.

### Tier D — unknown/unverified
Any candidate whose authoritative upstream cannot be established deterministically.

Tier D is blocked from automatic admission.

Source tier is policy evidence only and grants no runtime/tool authority.

## 4. Candidate model

Introduce immutable bounded candidate records with at least:

- `candidate_id` — deterministic digest-derived opaque identity;
- `candidate_kind` — `skill` or `tool`;
- `source_tier`;
- authoritative source identity / repository or registry reference;
- upstream name and version/ref when available;
- observed content digest when available;
- provenance state;
- license state and normalized license identifier when deterministically known;
- objective/capability/compatibility hints as bounded metadata only;
- declared script/dependency/reference inventory as metadata only;
- policy findings/reason codes;
- duplicate/upstream relationship when deterministically established;
- intake disposition;
- safe explanation summary;
- observation/policy version digest.

Raw arbitrary upstream bodies are not part of safe catalog serialization.

### Candidate dispositions

At minimum:

- `QUARANTINED` — valid candidate metadata, not approved;
- `HUMAN_REQUIRED` — insufficient/ambiguous evidence or policy review required;
- `BLOCKED` — deterministic prohibited condition;
- `REJECTED` — explicit operator rejection;
- `APPROVED_FOR_ADMISSION` — explicit exact-candidate approval artifact exists and all deterministic policy requirements pass;
- `ADMITTED` — exact approved Parallax skill contract was successfully admitted through the existing registry;
- `SUPERSEDED` — a newer/different observation exists; old candidate remains immutable evidence.

Tool candidates cannot become `ADMITTED` in the sense of creating tool authority in S2. Their maximum S2 state is approved metadata/reference for a future separately governed tool capability process.

## 5. Intake pipeline

The accepted pipeline is:

`discover -> normalize -> inspect -> classify -> quarantine -> approve/reject -> admit`

### Discover
Receive bounded source observations from an admitted adapter/interface. Discovery records source identity and metadata only.

### Normalize
Convert source-specific metadata into the canonical candidate schema. Normalization cannot execute or fetch arbitrary secondary resources.

### Inspect
Perform deterministic static inspection over already-supplied bounded text/metadata. Inspection may identify declared commands/scripts/dependencies/references and prohibited instructions, but cannot execute them.

### Classify
Apply versioned deterministic policy. Classification emits reason codes and evidence state. It may recommend HUMAN_REQUIRED but cannot create approval.

### Quarantine
All newly discovered candidates enter a non-runtime catalog state. Quarantine content is not supplied to runtime skill selection as an executable procedure.

### Approve/reject
Approval is an explicit exact-candidate artifact bound to candidate ID, source/content identity, policy version and proposed exact Parallax contract digest. Approval cannot be inferred from source tier or model preference.

### Admit
Only skill candidates with an exact approval artifact may be converted into/admit an exact `PortableSkill`. Admission still executes the pre-existing `SkillRegistry.admit` checks. S2 may not bypass or duplicate that authority.

## 6. Deterministic policy

### Required provenance
Automatic approval eligibility requires deterministic authoritative upstream identity. Curated-only/unknown upstream is HUMAN_REQUIRED or BLOCKED according to policy.

### License state
Represent at least `ALLOWED`, `REVIEW_REQUIRED`, `PROHIBITED`, `UNKNOWN`.

The first implementation may use a small server-owned allow/review/prohibit mapping rather than attempting complete legal interpretation. Unknown is not treated as allowed.

### Prohibited authority/execution signals
The deterministic inspector must reason-code candidate material that attempts or requires unrestricted authority, including at least:

- generic shell/exec/subprocess/command execution;
- raw HTTP/arbitrary network/curl/wget style transport;
- credential/token/password extraction or persistence;
- instructions to disable/ignore approval, policy, sandbox, review or security checks;
- production merge/deploy/promotion claims outside declared Parallax authority;
- hidden download/install/execute instructions not represented in bounded declared metadata;
- destructive actions without explicit governed human approval requirements.

Policy findings are conservative evidence. A finding can block or require human review but cannot itself grant an alternative capability.

### Duplicate/upstream resolution
Exact same authoritative source/version/content maps replay-safely to the same candidate identity. Same logical upstream/version with changed content digest is a conflict requiring HUMAN_REQUIRED/BLOCKED, never silent replacement.

Curated mirrors that resolve to the same authoritative upstream are represented as discovery provenance, not distinct trusted skills unless materially different content is independently reviewed.

## 7. Approval and admission contract

Introduce an immutable `SkillCandidateApproval` or equivalent with:

- candidate identity;
- exact upstream/source content digest;
- exact proposed `PortableSkill` digest;
- policy snapshot/version digest;
- approver reference;
- optional bounded approval note/reason code.

The admission bridge must verify:

1. candidate kind is `skill`;
2. candidate disposition/policy is eligible;
3. approval matches exact candidate/source/policy identities;
4. proposed `PortableSkill.digest` exactly equals approved contract digest;
5. required capabilities are declarable under the existing `SkillAdmissionPolicy`;
6. the existing `SkillRegistry.admit` accepts the exact contract.

Any mismatch fails closed without registry mutation.

S2 approval does not create tool capability, provider credentials, Project authorization or production authority.

## 8. Catalog retrieval

Provide a bounded query/projection over catalog records for operator/product use.

### Runtime retrieval
A runtime-facing retrieval helper may expose **admitted skills only** and must delegate final choice to the existing `SkillSelector`. It may prefilter/rank by objective/repository/capability facts but cannot change selection precedence or resolve an existing ambiguity by model preference.

### Operator retrieval
Operator-facing catalog queries may include quarantined/blocked/rejected candidates with safe reason summaries so a user can understand:

- what was found;
- source/provenance;
- what it may help with;
- what capabilities it declares it needs;
- why it is trusted, blocked or needs review;
- whether enabling it would require separate tool authority.

Primary product wording should remain natural-language compatible; technical IDs/reason codes remain available as secondary detail.

## 9. Safe serialization and privacy

Safe catalog output may include bounded source identity, normalized metadata, digests, states, reason codes, declared capability/objective hints and safe summaries.

It must not include:

- credentials, tokens, cookies, authorization headers or secret values;
- unrestricted raw repository/file bodies;
- raw provider payloads;
- executable binaries/archives;
- hidden reasoning/private scratchpad;
- arbitrary command handles;
- active MCP/session handles;
- arbitrary raw URLs containing secrets/query credentials;
- cross-Project private source/evidence.

Catalog data is global only for public/repository-safe candidate metadata. Project-private candidate material cannot silently become shared global skill memory.

## 10. Scope

W9-S2 owns the first backend contract for skill/tool candidate intake, quarantine, deterministic supply-chain classification, explicit skill approval/admission bridging, safe catalog projection and admitted-only retrieval. It may add focused synthetic fixtures and tests and may minimally reuse or extend existing governed-skill exports when necessary. It does not own live arbitrary network discovery, package installation, MCP execution, provider/tool authority creation, production promotion, client marketplace UI, or benchmark/evaluation code owned by W9-S1.

The first implementation should prefer a narrow server-owned module under `services/api/parallax_api/code/`, preserve current runtime selector semantics, and prove the contract using synthetic source observations unless an already-governed provider boundary can supply equivalent bounded evidence without expanding authority.

## 11. Architecture and module boundaries

Preferred implementation shape after the DSPy gate:

- new `services/api/parallax_api/code/skill_intake.py` for canonical candidate/policy/approval/admission bridge;
- optional `services/api/parallax_api/code/skill_catalog.py` if separation materially improves maintainability;
- minimal or no changes to `governed_skills.py`; existing public contracts should be reused rather than duplicated;
- focused tests in `services/api/tests/`;
- synthetic source observations/fixtures only in S2 unless an already-authorized provider interface can supply bounded evidence without new authority;
- optional read-only API projection only if it can reuse existing authenticated route/serialization patterns without adding mutation/approval endpoints.

No database migration is required for S2 acceptance unless persistence is proven necessary. An in-memory immutable catalog is acceptable for contract validation, but a later production-operability slice must define durable persistence before claiming that discovered candidate state survives process restart.

## 12. Non-goals

- Automatic internet crawling.
- Arbitrary GitHub repository ingestion.
- Executing a `SKILL.md`, script, package lifecycle hook or MCP server during intake.
- Automatically installing packages or dependencies.
- Dynamic arbitrary plugin loading.
- Tool-capability creation/approval.
- Production merge/deploy/REVIEW authority changes.
- Replacing the current skill selector.
- Model-only trust decisions.
- Complete software-composition-analysis/SBOM platform.
- Full license legal analysis.
- Public marketplace/UI in S2.
- Cross-Project sharing of private skill material.

## 13. Security, reliability and failure behavior

- Candidate/source text is untrusted input and cannot redefine policy, authority, approval or serialization rules.
- Unknown or malformed identity fails closed.
- Oversized fields/counts are bounded and rejected before policy/admission.
- Candidate IDs, approval IDs and safe records are deterministic/replay-safe where their underlying facts are identical.
- Duplicate replay is idempotent.
- Changed material facts create changed identity or explicit conflict, never silent mutation.
- Failed admission leaves the trusted registry unchanged.
- Tool candidate processing has no path to instantiate `ToolCapabilityRegistry` entries.
- A model recommendation may be recorded as non-authoritative evidence only if later needed; it cannot change deterministic disposition.
- Supply-chain policy changes are versioned; a policy change may trigger re-evaluation but does not silently rewrite historical observation evidence.

## 14. Acceptance criteria

### AC-01 Canonical candidate identity
Candidate identity is bounded, deterministic and changes when material source/version/content facts change.

### AC-02 Quarantine by default
Every new candidate is non-runtime and non-executable until explicit approval/admission. Discovery never returns an admitted/runtime skill by side effect.

### AC-03 Source-tier/provenance semantics
Tier A/B/C/D and provenance states are deterministic. Curated-only/unknown upstream cannot satisfy automatic-admission provenance.

### AC-04 License semantics
License state is explicit. `UNKNOWN` is not treated as allowed; prohibited license state blocks admission.

### AC-05 Static prohibited-signal inspection
Focused/adversarial fixtures detect generic execution/network, credential handling, policy-bypass and unauthorized production/destructive claims without executing candidate content.

### AC-06 No candidate execution
Tests prove intake never invokes subprocess/shell/package install/MCP start/raw HTTP/browser execution from candidate instructions.

### AC-07 Replay and conflict handling
Exact replay is idempotent. Same upstream/version with changed material digest produces explicit conflict/HUMAN_REQUIRED or BLOCKED, never replacement.

### AC-08 Explicit approval identity
Approval is exact-candidate + exact-source/content + exact-policy + exact-PortableSkill-digest bound. Any mismatch fails closed.

### AC-09 Existing registry remains authoritative
Successful admission calls/uses existing `SkillRegistry.admit`; unapproved/tampered/undeclarable contracts retain existing failure semantics.

### AC-10 Tool authority separation
Tool candidates and skill-required capability declarations cannot construct, approve, enable or mutate `ToolCapability` authority in S2.

### AC-11 Admitted-only runtime retrieval
Runtime retrieval exposes admitted skills only and final deterministic choice remains the existing `SkillSelector`, including HUMAN_REQUIRED on missing capability/incompatible repository/ambiguity.

### AC-12 Safe serialization
Catalog/operator output contains bounded metadata/reason codes/digests but no raw secrets, unrestricted source bodies, executable handles, hidden reasoning or provider credentials.

### AC-13 Public/private isolation
Global catalog cannot accept Project-private source/evidence as reusable public candidate material without an explicit future protected policy.

### AC-14 Synthetic source adapter contract
Source observations can be supplied through a bounded adapter/interface and tested without granting live arbitrary network authority.

### AC-15 No regression of current skills/tools
Existing governed-skill tests, tool capability authority tests, provider/browser authority tests and full API regressions remain green.

### AC-16 Authentic DSPy gate
Authentic DSPy SpecCritic + SpecCompiler evidence for this exact spec is committed and protected `--require-dspy` validation passes before semantic implementation. Any temporary workflow/evidence-generation change is restored byte-for-byte before implementation qualification.

### AC-17 Exact-head qualification
Final implementation head passes focused tests, Workstream Spec Validation, P2 CI, Bounded Autonomy and applicable protected release gates. Changed production components are deployment-verified before recorded as deployed.

### AC-18 Durable-record reconciliation
When the S2 contract is accepted/released, `ARCHITECTURE.md` and `CURRENT-STATE.md` are updated because this introduces a durable supply-chain/capability architecture. `PROJECT-CONSTITUTION.md` changes only if existing security/human-control principles prove insufficient. `DESIGN-SYSTEM.md` changes only if a user-facing capability-management surface establishes durable new presentation rules.
