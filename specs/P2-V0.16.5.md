## 4. Architecture requirements

### 4.1 Reference-proof coordinator

A bounded coordinator composes existing service objects and returns typed evidence for each phase. It may sequence the accepted interfaces and assert invariants but cannot directly mutate source, fabricate worker leases, perform generic shell/HTTP actions, alter evaluator thresholds, create production deployments or bypass operator REVIEW.

### 4.2 Canonical identity and durable reconstruction

Every reference phase carries exact `project_id`, `run_id`, approved Work Specification ID/revision/digest, current accepted source lineage and last-known-good lineage. Delivery/browser facts additionally carry exact Preview deployment identity. Recreated contexts must reconstruct these facts from durable state; caller-supplied substitutes or cross-Project identities fail closed.

### 4.3 Process-loss recovery

The proof acquires the accepted worker lease, records a canonical checkpoint, then simulates process loss by abandoning that execution context. After lease expiry, a newly constructed worker service classifies PROCESS_LOSS, enters `STALLED -> RECOVERING`, reassigns the same durable worker execution with a strictly higher lease generation, and continues from the checkpointed accepted lineage. No manual Engineering Run resume instruction is used. Any old lease/generation checkpoint or mutation attempt after reassignment must fail.

### 4.4 Browser and visual failure ordering

Reference browser results must cover functional semantics plus accessibility, layout, console and network checks, screenshot checkpoints and multimodal review. A deterministic failure prevents visual PASS from producing protected PASS. Screenshot/visual evidence remains secondary, provenance-bound and incapable of compensating for deterministic/protected failure.

### 4.5 Autonomous correction and LKG

Normalized browser/provider/execution failures enter the existing correction controller. The reference mutation adapter returns immutable candidate lineages through the accepted mutation seam, and the validator returns fresh exact-lineage evidence. Strict quality improvement may advance LKG; equal/regressive quality cannot. Repeat/no-progress/oscillation/resource boundaries terminate without further mutation.

### 4.6 Replay-safe delivery and evaluation

Only an accepted freshly validated lineage may enter the existing bounded source-delivery route. Retrying after process recreation returns the same Git revision, pull-request identity and Preview deployment ID without repeating external mutation. Durable runtime/provider facts feed the unchanged AppBuilder protected evaluator. Passing evaluation moves only to operator REVIEW, never directly to COMPLETE or production promotion.

### 4.7 Optimization non-authority

The reference proof creates a P2-V0.16.4 dependency/impact/reuse context and deliberately attempts stale/uncertain optimization paths. Unknown impact expands validation, stale graph/lease decisions fail, uncertain cache provenance is ineligible, Project-private repair memory cannot cross Project, and speculative integration remains `authoritative=false`. No optimization artifact may become accepted source lineage or satisfy a full promotion boundary.

### 4.8 Provider and human stop classification

Reference failures distinguish provider outage, rate limit, refreshable/non-refreshable credential failure and ordinary dependency/test stalls from human approval/material-specification authority boundaries. Automatic recovery/retry may occur only where the accepted classification allows it; genuine human-required cases cannot be patched around.

### 4.9 Privacy-safe telemetry

Reference phase observations use bounded identities, phase enums, timestamps/durations, outcome classes and opaque evidence references only. Aggregation remains within one Project/run and reports validated-outcome lead time plus retry/stall/human/integration waits. Raw private source, raw logs/DOM/screenshots, prompts, credentials and hidden reasoning are forbidden.

## 5. Security and privacy

- All reference evidence remains Project/run scoped; cross-Project evidence or private reuse fails closed.
- No new general network, shell, filesystem, GitHub, Vercel or production deployment authority is introduced by the coordinator.
- Persisted/reference evidence rejects secret-bearing values, authorization headers/cookies, unrestricted URLs, raw private source/log payloads and hidden reasoning.
- Stale worker lease generations, stale optimization graph digests, mismatched Work Specification/source lineage/Preview identity and unrelated provider evidence are rejected.
- Browser network policy remains exact-Preview-host only at the protected browser seam.
- Multimodal evidence is bounded secondary judgment and may not expose hidden reasoning or override deterministic checks.
- The AppBuilder evaluator and protected thresholds are unchanged.
- The proof must not claim that deterministic adapters represent a production deployment; production remains Wave 2 until a separate authorized promotion.

## 6. Failure and recovery boundaries

Ordinary reproducible functional/visual failures may enter bounded correction. Provider outage/rate limit/dependency/test stalls may enter the accepted retry/backoff/recovery path. Refreshable credentials may request refresh under existing authority. Non-refreshable credential/authorization failure, explicit approval, material specification ambiguity, destructive/privileged work or protected-policy change stops with typed human/resource evidence.

Repeated equivalent defects, no progress, oscillation, retry/resource exhaustion, stale lease generation, stale optimization graph, uncertain impact, incompatible private reuse or absent safe cancellation boundary all fail closed. None authorize a bypass, hidden retry loop, duplicate provider mutation or production action.

## 7. Permanent reference harness

The repository must contain deterministic permanent tests that prove the integrated happy path and the deliberate negative/recovery cases. The harness must reconstruct process-scoped services between important phases, exercise the P2-V0.16.1 worker lease/checkpoint/reassignment API directly, feed P2-V0.16.2 result objects into P2-V0.16.3 correction, prove P2-V0.16.4 non-authority/isolation behavior, and reuse the existing Wave 2 delivery/evaluation/operator-REVIEW contracts.

The harness may use bounded in-memory/deterministic provider and browser adapters behind existing typed seams so CI remains reproducible. It must preserve real contract shapes and durable identities and must not create an alternate provider/evaluator/source authority.

## 8. Non-goals

- changing source mutation semantics already owned by P2-V0.16.3 and Wave 2 lineage code;
- creating another worker identity, lease table or recovery state machine;
- changing browser workflow semantics, screenshot baselines or multimodal authority from P2-V0.16.2;
- changing P2-V0.16.4 scheduler/impact/cache/model-routing acceptance policy;
- lowering or replacing AppBuilder protected scoring;
- automatic merge to `main`, production migration application, production credential/storage provisioning or production deployment;
- representing deterministic reference adapters as live production provider evidence;
- cross-Project learning from private source/log/prompt content.

## 9. Acceptance criteria

### AC-01 Full protected reference route preserves canonical identity
The permanent harness proves approved Project/Work Specification/run identity through PLAN, typed IMPLEMENT, immutable accepted lineage, exact-lineage BUILD/TEST/VERIFY, Preview delivery, browser/screenshot/multimodal validation, correction, replay-safe publication, protected evaluation and explicit operator REVIEW. Every phase rejects mismatched Project/spec/lineage/Preview evidence.

### AC-02 Functional and deterministic browser failures are corrected only through fresh exact-lineage validation
A deliberate functional browser regression fails deterministically, enters the existing bounded correction path, produces a new immutable candidate lineage and reaches PASS only after fresh validation of that exact lineage. Accessibility, layout, console and network deterministic failures are also proven to block protected PASS even when visual judgment would otherwise pass.

### AC-03 Visual and screenshot evidence cannot override higher-precedence failures
A deliberate screenshot or multimodal visual regression is detected and may be corrected, but screenshot/multimodal improvement cannot compensate for deterministic or protected acceptance failure. Visual evidence remains Preview/lineage provenance-bound and secondary.

### AC-04 Last-known-good and convergence bounds survive regressive, repeated and oscillating corrections
A correction introducing a higher-precedence regression cannot replace LKG. Equivalent repeated defects terminate at the configured repeat/no-progress bound, and an A/B/A failing-state sequence terminates at the oscillation bound without unbounded source churn or further mutation after stop.

### AC-05 Process loss recovers automatically through the accepted worker protocol without duplicate work
After a durable worker checkpoint, deliberate process loss and lease expiry are classified as PROCESS_LOSS; a recreated service performs `STALLED -> RECOVERING -> REASSIGNED`, increments the accepted lease generation and continues from durable accepted lineage without manual Engineering Run resume, duplicate IMPLEMENT mutation, duplicate Git/Preview publication, lost accepted work or corrupted LKG.

### AC-06 Stale workers and inappropriate recovery paths fail closed
The pre-loss lease/generation cannot checkpoint or mutate after reassignment. Provider outage, rate limit, dependency/test stall and credential cases remain distinct from human approval/material-specification boundaries, and only classifications permitted by P2-V0.16.1 may automatically recover/retry.

### AC-07 Delivery replay preserves exact external identities and Preview remains the autonomous ceiling
Recreated delivery of the same accepted lineage returns the original published revision, PR identity and Preview deployment ID with replay evidence and performs no duplicate provider mutation. Preview validation may continue autonomously; no reference result can claim or perform production promotion/deployment.

### AC-08 Protected AppBuilder scoring and operator REVIEW remain unchanged
Runtime/provider/browser evidence is derived from durable accepted facts and evaluated with the unchanged protected AppBuilder suite/thresholds. Deliberate forbidden production-authority or stale/unrelated evidence remains a critical failure. Autonomous success stops at REVIEW until explicit operator completion.

### AC-09 Optimization cannot advance authority or skip mandatory validation
P2-V0.16.4 speculative integration remains non-authoritative, stale graph/lease scheduling fails, uncertain impact selects the conservative/full checks, full worker/integration/release promotion suites remain mandatory, and cache/pattern/repair recommendations cannot become accepted lineage or validation evidence by themselves.

### AC-10 Project-private targets, evidence and reuse are isolated
Deliberate cross-Project provider target/evidence, cache/pattern compatibility and repair-memory queries are rejected or return no private result. A second Project cannot inherit the first Project's accepted lineage, Preview identity, private repair memory or provider authority.

### AC-11 Development-performance evidence is bounded, privacy-safe and outcome-oriented
The reference run records bounded Project/run-scoped phase telemetry covering correction/retry/recovery/integration wait and produces validated-outcome lead time plus blocked/wait metrics. Secret/private-source/raw-log/prompt/hidden-reasoning material is rejected and token/worker occupancy is not treated as success.

### AC-12 Final Wave 3 exact-head proof is reproducible and stops at production-promotion boundary
P2-V0.16.5 has authentic committed DSPy critic/compiler evidence. The final exact integration head passes Workstream Spec Validation, Parallax P2 CI and Bounded Autonomy with the permanent Wave 3 reference harness and deliberate negative cases. Authoritative records distinguish validated Wave 3 development from Wave 2 production. Completion state is READY FOR PRODUCTION PROMOTION; no production deployment, migration or credential/storage provisioning occurs automatically.
