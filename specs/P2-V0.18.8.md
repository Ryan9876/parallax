# Parallax 2.0 — Response-Stream Provider Rate-Limit Recovery

Spec ID: P2-V0.18.8
Status: APPROVED FOR IMPLEMENTATION
Date: 2026-08-26
Workstream: issue #271
Base: `6fe91a1424cf98d04ae8376a3abe972c4269d440`

## 1. Objective

Make provider-capacity failures in the protected conversation response stream truthful and recoverable. Reuse the accepted sanitized routing-failure classification from #252 so all-model `LMRateLimitError` exhaustion is presented as temporary model-capacity unavailability rather than as a protected scope or reason validation failure, while preserving conversation history, protected validation, Project/Work Specification/source-lineage authority, and existing provider/model scope.

## 2. Scope

- propagate the existing `RoutingFailureKind` through protected response coordination without exposing raw provider data;
- distinguish rate-limit exhaustion, protected-output validation exhaustion, and mixed/other provider exhaustion at both scope and reason stages;
- emit bounded SSE error codes/messages appropriate to each failure class;
- preserve an already-established protected scope decision when reason routing later fails;
- preserve the durably submitted user turn and explain that the message is saved rather than instructing the operator to resend identical text;
- retain current Luna -> Terra -> Sol routing, credentials, retries, and provider authority;
- add deterministic coordinator/API/client-state coverage and regression coverage for successful fallback;
- keep Work Specification rate-limit behavior from #252 unchanged.

## 3. Non-goals

- changing OpenAI quota, budget, billing, or rate limits;
- adding providers, models, local production fallback, credentials, or alternate routing authority;
- deleting, rewriting, or silently de-duplicating persisted conversation history;
- fabricating scope, reason, Work Specification, Engineering Run, source mutation, approval, or REVIEW state;
- changing retry counts or fan-out based on a single model failure;
- adding an invented `Retry-After` interval;
- Wave 6 agent-control-plane implementation.

## 4. Security

Failure classification is derived only from the existing sanitized `AttemptRecord` contract. Raw provider exceptions, response bodies, prompts, credentials, quota/billing details, filesystem paths, hidden reasoning, or model payloads may not cross the router boundary or enter client-visible evidence. Rate-limit recovery grants no new capability or execution authority. Protected scope/reason verification remains mandatory, and validation exhaustion must never be mislabeled as provider capacity failure.

Conversation persistence remains truthful: the user turn is already stored before response routing and is not removed merely because the provider is unavailable. Recovery copy must therefore avoid encouraging duplicate resend and must not claim that execution, approval, or source mutation occurred.

## 5. Acceptance criteria

### AC-01 Existing sanitized classifier is authoritative
Conversation response recovery reuses `RoutingFailureKind` / sanitized attempt records from the accepted router contract and does not introduce raw-provider inspection or a competing classifier.

### AC-02 Scope rate-limit exhaustion is truthful
When every configured scope attempt is `provider_failed` with sanitized `LMRateLimitError`, the SSE error uses a distinct bounded model-capacity code/message and does not emit `PROTECTED_SCOPE_FAILURE` or fabricate a scope decision.

### AC-03 Reason rate-limit exhaustion is truthful
When protected scope resolution succeeds but every reason attempt rate-limits, the SSE error uses the same model-capacity semantics while retaining the already-established safe protected scope decision in the trace; no answer is fabricated.

### AC-04 Validation exhaustion remains distinct
All-attempt protected-output validation exhaustion remains a protected scope/reason failure and is not represented as provider capacity exhaustion.

### AC-05 Mixed provider exhaustion fails closed
Mixed or unknown provider failures use generic provider-unavailable semantics and do not claim rate limiting, quota state, billing state, or a retry interval.

### AC-06 Durable conversation history is preserved
A provider-capacity failure leaves Project, conversation status, prior messages, and the submitted user turn intact and creates no Work Specification, Engineering Run, source mutation, approval, or REVIEW transition. Recovery copy says the message is saved/preserved and does not instruct the operator to resend identical content.

### AC-07 Provider and model authority is unchanged
The change adds no provider, model, credential, fallback, shell/network capability, routing order change, or deployment authority. Luna -> Terra -> Sol behavior remains intact.

### AC-08 Safe observable evidence
Client-visible errors and traces contain only bounded error codes, safe routing-attempt metadata already permitted by the current trace contract, and recovery text; no raw provider payload, secret, prompt, hidden reasoning, filesystem path, or billing/quota inference is exposed.

### AC-09 Deterministic API and coordinator coverage
Tests cover scope rate-limit, reason rate-limit after a valid scope decision, validation-only exhaustion, mixed/other provider failure, successful fallback, and preservation of conversation/status truth.

### AC-10 Client recovery presentation
Client/state acceptance proves the model-capacity message renders as a recoverable error, does not describe the event as a protected-scope defect, and does not imply that the user must duplicate the saved message.

### AC-11 Existing protected regressions remain green
Reason/Code scope classification, first-Code-objective capture, Work Specification #252 recovery, Project/repository binding, authentication, source lineage, protected evaluation, REVIEW/HUMAN_REQUIRED, mobile behavior, and successful routing remain green.

### AC-12 Governed release boundary
Before integration, this spec and authentic DSPy compiled plan pass protected validation; exact worker-head Workstream Spec Validation, Bounded Autonomy and P2 CI pass. Worker PR targets `main` as bounded production stabilization, does not self-merge/deploy, and production is not claimed fixed until governed deployment and post-cutover verification complete.
