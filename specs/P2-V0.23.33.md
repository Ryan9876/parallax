- Candidate-local challenger/repair plans remain non-authoritative server-owned producer-selection evidence. They may select only already-admitted agents and may not become a durable PLAN replacement.

- Candidate repair still consumes the existing second candidate / alternative-round slot. It adds no candidate, per-work-unit reassignment, final-validator-repair, model, provider, credential, timeout, hidden retry, or autonomy budget.
- P2-V0.23.32 repair guidance, fixed static-web reason vocabulary, immutable `static-web-v1` execution contract, SafeImplementationEngine, real disposable BUILD/TEST/VERIFY, independent evaluation/routing, and terminal second-rejection behavior remain unchanged.

## 5. Architecture requirements

### 5.1 Canonical durable PLAN versus candidate-local selection

`primary_plan` is the exact protected PLAN accepted for the Engineering Run and remains the authoritative worker-checkpoint plan for the duration of that IMPLEMENT attempt. A candidate-local alternate plan is subordinate selection evidence only: it may alter the already-admitted selected producer set for one disposable candidate, but it is not a PLAN transition and cannot replace the worker checkpoint `plan_ref`.

Proposal generation therefore carries two explicit inputs when they differ:

1. candidate-local orchestration plan — used for scheduling, task binding, assignment identity, producer identity, and candidate strategy/evaluation evidence;
2. canonical durable plan — used only for worker checkpoint PLAN identity and the protected compatibility check.

For the primary candidate both inputs are the same object/identity.

### 5.2 Compatibility guard

Before a candidate-local plan can write progress under the canonical durable PLAN checkpoint, server-owned code verifies compatibility. At minimum it must require the same Project, run, Work Specification ID/revision/digest, exact acceptance IDs, agent-protocol version, policy digest, and work-graph digest. Candidate-local roster/selected-agent identity may differ only because candidate selection already constrains it to the admitted roster/capability contract.

Mismatch fails before hosted generation or checkpoint mutation with a fixed bounded contract classification. It does not fall back to changing `plan_ref`, refreshing PLAN, or creating new authority.

### 5.3 Durable worker checkpoint behavior

Every `AGENT_DISPATCH`, candidate convergence/rejection, `AGENT_RESULT`, `AGENT_PROPOSAL`, and subsequent candidate-ready worker checkpoint created during the IMPLEMENT attempt retains the canonical `agentic-plan:{primary_plan.plan_id}` reference. Candidate-local work-unit IDs must exist in the identical canonical work graph before checkpointing.

The candidate-local assignment/task digest remains in bounded evidence references, preserving unique producer/dispatch evidence without allowing it to become PLAN authority.

### 5.4 Candidate-round identity remains unique

P2-V0.23.32's alternate candidate plan remains responsible for a distinct candidate producer and distinct assignment/operation/request/attempt identity. P2-V0.23.33 must not solve the PLAN-ref defect by reusing the primary plan's round-1 assignment identity or by replaying a previous hosted request.

Tests must prove primary and repair AgentTaskRequest/assignment identities differ while both durable worker checkpoints retain the same canonical PLAN reference.

### 5.5 Budgets and authority remain unchanged

The replacement remains candidate round 2 and terminal if it fails protected candidate validation. Existing Luna/Terra/Sol admission, 60-second hosted timeout, zero hidden provider retries, per-work-unit candidate recovery, one final validator repair, SafeImplementationEngine, deny-all validation networking, accepted source lineage, source publication/delivery controls, lifecycle state machine, Git/Preview boundaries, and human REVIEW ceiling remain unchanged.

### 5.6 Diagnostics

Any new incompatibility evidence is closed and server-owned: candidate ID/round, fixed phase/failure/reason code, and safe digests only. It must not contain source/generated content, diffs, exception text, provider payloads, filesystem paths/roots, environment values, credentials, or true canonical/source-lineage/Git/deployment/REVIEW authority claims.

## 6. Security

This release narrows identity projection rather than adding authority. The canonical PLAN remains immutable absent the already-governed explicit human replan. A candidate-local alternate cannot smuggle a changed work graph, acceptance contract, Project/run/Work Specification binding, policy identity, capability, or source-lineage authority into worker recovery merely because it is server-generated.

Candidate-local producer identity remains accurate and auditable. No model sees or controls the durable/candidate plan distinction, assignment construction, checkpoint identity, compatibility decision, candidate count, or mutation authority.

## 7. Reliability and migration

No database migration is required. Existing worker checkpoints and historical PLAN evidence remain valid. The change affects only how new candidate-round progress is projected into the existing durable worker checkpoint during the active IMPLEMENT attempt.

On rollback, candidate-repair returns to the deployment-verified P2-V0.23.32 behavior and may again stop at the known bounded proposal-assembly blocker; no persisted evidence requires reinterpretation or schema rollback.
