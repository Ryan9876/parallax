## 1. Objective

Remove the next authenticated production IMPLEMENT blocker by making disposable candidate validation use the validation profile selected from the authoritative accepted-source workspace before candidate mutation.

On exact production deployment `dpl_9Csq52Q1ihkenrw3UZW8ZfRrLdka`, the signed-in retry of Engineering Run `3a1ba66a-5649-42b6-81ee-91684fe06bbc` progressed beyond the P2-V0.23.29 source-assembly boundary. Source-lineage reads succeeded; Luna completed, then Terra completed; and the runtime emitted the bounded server-owned diagnostic `candidate=candidate-primary phase=DISPOSABLE_CANDIDATE_VALIDATION failure_kind=VALUE_CONTRACT_ERROR`. No disposable BUILD/TEST/VERIFY sandbox followed that admission failure.

The candidate validation path currently copies the authoritative workspace, safely applies the non-authoritative proposal, then asks `VercelCandidateValidationExecutor.validate_candidate()` to select a validation profile from the candidate-mutated workspace. `select_validation_profile()` intentionally infers a server-owned profile from bounded source shape, but the current call location lets model-authored candidate edits add, remove, or alter source-shape marker files before profile selection. A candidate can therefore invalidate or switch validation-profile inference even though model output has no authority to change the protected validation toolchain.

P2-V0.23.30 moves profile selection to the accepted-source side of the boundary. The exact immutable `ValidationProfile` is selected from the authoritative base workspace before the candidate proposal is applied. Disposable validation then runs the mutated candidate under that pinned profile. Candidate source still determines what is compiled and tested; it no longer determines which protected validation authority is selected.

## 2. Fixed decisions

- The authoritative accepted/base workspace is the only source used to select the validation profile for one candidate attempt.
- Profile selection occurs before applying candidate edits.
- The resulting immutable `ValidationProfile` is passed explicitly into disposable candidate validation.
- `VercelCandidateValidationExecutor` must not re-select profile authority from candidate-mutated source when an authoritative profile is supplied.
- Production `AgenticControlPlane` must always supply the authoritative profile.
- Candidate edits to `package.json`, project files, Python markers, validation tests, or other source-shape markers do not switch the validation profile for that attempt.
- A deliberate ecosystem/profile transition requires a separately governed product capability and is not inferred from candidate output.
- Existing source transfer, deny-all validation network policy, dependency preparation, BUILD/TEST/VERIFY commands, execution snapshots, SafeImplementationEngine, evaluation, source lineage, Git/deployment/lifecycle and human REVIEW authority remain unchanged.
- Existing Luna/Terra/Sol roster, hosted timeout, hidden-retry policy, bounded recovery and final validator-repair ceilings remain unchanged.
- A fixed sanitized `VALIDATION_PROFILE_ERROR` classification is added for `ValidationProfileError`/`ExecutionPolicyError` at candidate-admission boundaries; exception text is never persisted or logged.
- Architecture advances to v3.41 because validation-profile authority is durably moved from candidate-shaped inference to accepted-source pinning.

## 4. Non-goals

- Admitting generic Node or generic Python validation that is currently fail-closed.
- Adding or changing protected build/test/verify command text.
- Allowing a candidate to request or select a validation profile.
- Increasing model/provider/retry/timeout/autonomy budgets.
- Weakening SafeImplementationEngine, path, secret, symlink, extension, hierarchy, size, stale-source, dependency, execution-snapshot, source-lineage, Git/deployment/lifecycle, or REVIEW controls.
- Persisting raw source, generated content, diffs, exception messages, provider payloads, credentials, environment values, or filesystem roots.

## 5. Architecture requirements

### 5.1 Authoritative profile selection

`AgenticControlPlane._candidate_validation()` must call `select_validation_profile(base_workspace)` before creating/applying the disposable candidate. Failure to select a profile from authoritative source remains fail-closed.

The selected profile must be treated as immutable server-owned authority for the whole candidate attempt. No candidate-generated path, file content, acceptance text, model metadata, or provider output may change the selected profile.

### 5.2 Explicit candidate-validator contract

`CandidateValidationExecutor.validate_candidate()` gains an explicit authoritative validation-profile input. Production must supply it. `VercelCandidateValidationExecutor.validate_candidate()` must use the supplied profile for:

- execution-snapshot selection;
- dependency preparation policy;
- protected BUILD/TEST/VERIFY command selection;
- validation profile ID/digest evidence.

It must continue deriving candidate content digest/file count/bytes from the mutated candidate workspace.

### 5.3 Candidate marker edits

A candidate that edits or removes source-shape markers must still be validated using the profile selected from the accepted source. Such edits may cause BUILD/TEST/VERIFY to fail naturally, but they must not switch the protected toolchain or convert profile inference into a candidate-controlled authority channel.

### 5.4 Fail-closed direct usage

Any production path that cannot supply an authoritative profile must fail closed rather than infer a new profile after mutation. Test-only/deterministic adapters may preserve compatibility only where they do not participate in production authority; the production control-plane path must be explicit and covered by regression tests.

### 5.5 Sanitized diagnostics

`ValidationProfileError` and `ExecutionPolicyError` are fixed server-owned classes and may map to `VALIDATION_PROFILE_ERROR` at candidate admission. Diagnostics may contain only candidate ID, server-owned phase, fixed failure kind and existing false authority claims. Exception text and source details remain prohibited.

## 6. Security

This change contracts authority. Model-authored source can no longer influence which protected validation profile or execution snapshot is selected. Candidate source remains untrusted input to the pinned validator, not input to validator authority selection.

Dependency preparation remains bound to the pinned profile's existing package-domain allowlist and network policy. BUILD/TEST/VERIFY remains source-free at snapshot creation, receives no application environment, and retains deny-all validation networking after preparation.

## 7. Reliability

The accepted-source profile is deterministic for the run's immutable source lineage. Reusing that profile across candidate recovery prevents Luna/Terra/Sol candidates from producing different validation authorities merely because they touch different source-shape files. Candidate failures become ordinary protected BUILD/TEST/VERIFY outcomes instead of pre-sandbox profile-inference failures whenever the authoritative source profile itself is valid.

No retry or timeout increases are required.
