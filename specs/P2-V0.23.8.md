# P2-V0.23.8 — Bounded rejected-candidate recovery

## Objective
Prevent a single pre-mutation implementation proposal rejection from terminating an otherwise recoverable Engineering Run. Preserve deterministic validation as authoritative while allowing the agentic runtime to try another already-admitted implementation agent/model within a finite server-owned recovery budget.

## Problem statement
Production Engineering Run `0cb9e8c5-1381-4913-a890-7bd48bc0384f` reached IMPLEMENT. The hosted GPT-5.6 Sol call completed, but the proposal failed the protected proposal validator. The current single-agent adapter propagated `ImplementationGenerationFailure`; the live worker bridge then classified the operation as `AGENTIC_TASK_FAILED`, and autonomy persisted `AUTONOMOUS_IMPLEMENT_FAILED`. No source mutation occurred, but the runtime failed to use its admitted alternate implementations.

A rejected candidate is not equivalent to process loss, provider outage, lease loss, or canonical implementation failure. The runtime needs an explicit bounded candidate-recovery contract.

## Invariants
- Protected proposal validation and safe-source mutation checks remain unchanged and authoritative.
- Candidate rejection before canonical mutation grants no source-lineage, Git, deployment, REVIEW, or Engineering Run transition authority.
- Only agents already present in the server-owned admitted roster and eligible for the same work unit may be tried.
- Retry order is deterministic and server-owned.
- Each alternate attempt receives a fresh assignment generation/task identity.
- Recovery is finite: at most `max_reassignments_per_work_unit` alternate attempts beyond the original assignment.
- Provider errors, invalid proposal output, and proposal-validator rejection may be recoverable candidate-generation failures; actual worker process/lease-loss recovery remains governed by the existing worker recovery subsystem.
- A failed candidate is observation only and must never be committed to the canonical workspace.
- Exhaustion fails closed with bounded diagnostics and does not fabricate success.

## Design
Introduce a candidate-generation recovery helper in the agentic control plane. For each scheduled work-unit assignment:
1. Execute the original admitted assignment.
2. If generation succeeds, continue through existing S1 admission, safe proposal composition, disposable candidate validation, independent evaluation and routing unchanged.
3. If `ImplementationGenerationFailure` occurs before canonical mutation, record a bounded candidate-generation rejection observation in controller-local evidence and select the next eligible agent for the same unit.
4. Construct a deterministic reassigned `AssignmentEvidence` with incremented generation and fresh operation/request/attempt identities. Do not invoke worker-loss reassignment APIs because no worker lease/process loss occurred.
5. Repeat until one proposal is admitted or the finite alternate-agent budget/eligible set is exhausted.
6. On exhaustion, raise `CandidateAdmissionFailure` with sanitized `CANDIDATE_GENERATION_EXHAUSTED` evidence. The worker bridge may project terminal failure, but the diagnostic must distinguish candidate exhaustion from worker process loss.

The helper must not broaden the selected execution team for parallel work. It may select an alternate from `UnitPlan.eligible_agent_digests` solely for recovery of the same work unit.

## Acceptance criteria
- AC-01: A first assigned hosted implementation agent whose proposal is rejected by the protected proposal validator does not immediately terminate IMPLEMENT when another admitted eligible agent exists.
- AC-02: The alternate attempt uses a different eligible agent identity, incremented assignment generation, and fresh task/attempt identity.
- AC-03: The rejected proposal causes no canonical workspace mutation, lineage acceptance, Git mutation, deployment, REVIEW completion, or Engineering Run transition.
- AC-04: A successful alternate proposal continues through the existing exact acceptance-coverage checks and the ordinary disposable candidate validation/evaluation/routing path.
- AC-05: Recovery attempts are deterministic and bounded by `max_reassignments_per_work_unit`; no unbounded model loop is possible.
- AC-06: If every eligible alternate fails generation/validation, IMPLEMENT fails closed with bounded `candidate_generation_failure` evidence whose reason is `CANDIDATE_GENERATION_EXHAUSTED` and which contains no raw provider/model output or secrets.
- AC-07: Existing process-loss/lease-expiry worker reassignment semantics and tests remain unchanged.
- AC-08: Existing successful single-agent and multi-agent paths remain unchanged when the first assigned agent succeeds.
- AC-09: Regression tests prove first-agent rejection followed by alternate-agent success and all-alternatives-exhausted behavior.
- AC-10: Full API, Bounded Autonomy, client/browser, protected promotion, and DSPy release gates remain green before merge.

## Non-goals
- Weakening proposal validation or safe patch validation.
- Retrying canonical source mutation after a partial mutation.
- Increasing model/provider credentials or network authority.
- Adding operator-selected model controls.
- Treating provider/model rejection as worker process loss.
- Changing REVIEW or production-deployment authority.

## Rollback
Revert the release commit. Because rejected candidates remain non-mutating and this change adds only pre-mutation recovery, rollback restores the prior fail-fast behavior without data migration.
