## 1. Objective

Prevent a single pre-mutation implementation proposal rejection from terminating an otherwise recoverable Engineering Run. Preserve deterministic validation as authoritative while allowing the agentic runtime to try another already-admitted implementation agent/model within a finite server-owned recovery budget.

## 2. Triggering evidence

Production Engineering Run `0cb9e8c5-1381-4913-a890-7bd48bc0384f` reached IMPLEMENT. The hosted GPT-5.6 Sol call completed successfully, but its proposal failed the protected proposal validator. The current single-agent adapter propagated `ImplementationGenerationFailure`; the live worker bridge then classified the operation as `AGENTIC_TASK_FAILED`, and autonomy persisted `AUTONOMOUS_IMPLEMENT_FAILED`.

No source mutation occurred. The safety boundary worked, but the runtime failed to use other already-admitted eligible implementation agents. A rejected candidate is not equivalent to process loss, provider outage, lease loss, or canonical implementation failure.

## 3. Fixed decisions

- Protected proposal validation and safe-source mutation checks remain unchanged and authoritative.
- Candidate rejection before canonical mutation grants no source-lineage, Git, deployment, REVIEW, or Engineering Run transition authority.
- Only agents already present in the server-owned admitted roster and eligible for the same work unit may be tried.
- Retry order is deterministic and server-owned.
- Each alternate attempt receives a fresh assignment generation/task identity.
- Recovery is finite: at most `max_reassignments_per_work_unit` alternate attempts beyond the original assignment.
- Provider errors, invalid proposal output, and proposal-validator rejection may be recoverable candidate-generation failures; actual worker process/lease-loss recovery remains governed by the existing worker recovery subsystem.
- A failed candidate is observation only and must never be committed to the canonical workspace.
- Exhaustion fails closed with bounded diagnostics and does not fabricate success.

## 4. Architecture requirements

For each scheduled work-unit assignment:

1. Execute the original admitted assignment.
2. If generation succeeds, continue through existing S1 admission, safe proposal composition, disposable candidate validation, independent evaluation and routing unchanged.
3. If `ImplementationGenerationFailure` occurs before canonical mutation, record only bounded candidate-rejection evidence and select the next eligible agent for the same unit.
4. Construct a deterministic reassigned `AssignmentEvidence` with incremented generation and fresh operation/request/attempt identities. Do not invoke worker-loss reassignment APIs because no worker lease/process loss occurred.
5. Repeat until one proposal is admitted or the finite alternate-agent budget/eligible set is exhausted.
6. On exhaustion, raise bounded `CANDIDATE_GENERATION_EXHAUSTED` diagnostic evidence. The terminal worker projection must distinguish candidate exhaustion from process loss.

The helper may select an alternate from `UnitPlan.eligible_agent_digests` solely for recovery of the same work unit. This does not grant the alternate canonical source authority and does not change parallel work-unit coordination.

## 5. Scope

Owned semantic scope:

- bounded candidate-generation recovery helper;
- live agentic composition wiring;
- fresh candidate retry assignment identities;
- bounded candidate-rejection/exhaustion diagnostics;
- focused regression tests;
- durable architecture/state records after validation and deployment.

Existing protected proposal validation, safe source mutation, durable lineage, Git delivery, Vercel Preview delivery, REVIEW authority, worker lease recovery, provider credentials and network policy remain unchanged.

## 6. Security and reliability

Candidate/model output is untrusted. A rejected proposal receives no mutation authority. Recovery may only choose an identity already admitted by the server-owned roster and listed as eligible for the exact work unit. Retry identities are deterministic, finite and cannot be selected by browser/model text.

No raw provider/model output, credentials, environment values, hidden reasoning, filesystem roots or arbitrary exception text may be persisted in candidate-rejection diagnostics. No canonical source write occurs until a candidate has passed the existing proposal validator and later safe mutation boundary.

Actual process/lease loss remains owned by worker recovery and must not be conflated with candidate rejection. Candidate recovery must not expand provider permissions, model credentials, network authority, Git authority, deployment authority, REVIEW authority or production promotion authority.

## 7. Acceptance criteria

### AC-01 Alternate recovery
A first assigned hosted implementation agent whose proposal is rejected by the protected proposal validator does not immediately terminate IMPLEMENT when another admitted eligible agent exists.

### AC-02 Fresh bounded identity
The alternate attempt uses a different eligible agent identity, incremented assignment generation, and fresh operation/request/attempt identity.

### AC-03 No rejected-candidate mutation
The rejected proposal causes no canonical workspace mutation, lineage acceptance, Git mutation, deployment, REVIEW completion, or Engineering Run transition.

### AC-04 Existing validation path preserved
A successful alternate proposal continues through the existing exact acceptance-coverage checks and ordinary disposable candidate validation, independent evaluation, routing and competition path.

### AC-05 Finite recovery
Recovery attempts are deterministic and bounded by `max_reassignments_per_work_unit`; no unbounded model loop is possible.

### AC-06 Exhaustion diagnostic
If every eligible alternate fails generation/validation, IMPLEMENT fails closed with bounded `candidate_generation_failure` evidence whose reason is `CANDIDATE_GENERATION_EXHAUSTED`, with `worker_process_loss=false` and no raw provider/model output or secrets.

### AC-07 Worker recovery parity
Existing process-loss and lease-expiry worker reassignment semantics remain unchanged.

### AC-08 Success-path parity
Existing successful single-agent and multi-agent paths remain unchanged when the first assigned agent succeeds.

### AC-09 Regression proof
Tests prove deterministic first-agent rejection followed by alternate assignment, finite alternate exhaustion, fresh dispatch identities and no new authority claims.

### AC-10 Release gates
Protected spec/plan validation, full API regression, Bounded Autonomy, client/browser, protected promotion and DSPy release gates are green before merge.

## 8. Non-goals

- Weakening proposal validation or safe patch validation.
- Retrying canonical source mutation after a partial mutation.
- Increasing model/provider credentials or network authority.
- Adding operator-selected model controls.
- Treating provider/model rejection as worker process loss.
- Changing REVIEW or production-deployment authority.
- Reworking the accepted worker recovery state machine.

## 9. Release gate

- full API and Bounded Autonomy regression suites pass;

Only then update `CURRENT-STATE.md` and mark the release deployment-verified.

## 10. Rollback

Revert the release commit. Because rejected candidates remain non-mutating and this change adds only pre-mutation recovery, rollback restores the prior fail-fast behavior without data migration.
