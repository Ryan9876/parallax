## 1. Objective

Close the actual remaining Decision Ledger greenfield gap end to end rather than shipping only the first visible recovery step.

Production already classifies missing exact-repository GitHub App / Vercel Connect coverage as `REPOSITORY_AUTHORIZATION_REQUIRED`. That explicit consent boundary is correct, but the user currently has to discover provider installation settings manually. In addition, the canonical W9 target is a **truly empty repository**: even after consent it has no commit, tree, or source files, while Parallax durable source lineage currently requires a non-empty repository root and verified delivery currently assumes an existing parent commit.

This release therefore has two inseparable outcomes:

1. provide a first-class exact-repository authorization recovery action inside the normal Parallax experience; and
2. support a governed zero-source greenfield root that can be implemented and protected normally, then at REVIEW initialize an empty Git baseline and publish the exact accepted implementation through the existing branch → pull request → Vercel Preview path.

No reference solution, placeholder application source, manual seed commit, broad GitHub installation grant, or benchmark-only runtime path is introduced.

The canonical W9-S1 Decision Ledger benchmark remains unchanged. It still requires ordinary authenticated Project → approved Work Specification → Engineering Run → accepted source → Vercel Preview → REVIEW behavior and no out-of-band target source edits.

## 2. Triggering evidence

Finding #406 is deployment-verified through P2-V0.23.3. The canonical `Ryan9876/sickbeard` trial reaches PLAN and receives the exact production classification `REPOSITORY_AUTHORIZATION_REQUIRED` because the repository is not covered by the installed `github/parallax-runtime` authorization.

Vercel's documented Connect API exposes `POST /v1/connect/authorize/{connector}`. The request accepts `authorizationDetails` and returns a short-lived user-consent URL plus request/verifier metadata. Parallax already generates exact-repository `github_app_installation` authorization details and independently verifies successful tokens expose exactly one canonical repository.

Separate code inspection establishes the next known boundary in advance:

- `GitHubRestProviderClient.resolve_repository()` returns `SOURCE_NOT_FOUND` when the repository's default branch has no ref;
- `ProjectedRepositoryBoundSourceProvider` rejects a tree with no lineage-safe files;
- `SourceLineageStore` requires at least one root file and rejects empty materializations/manifests;
- `VerifiedLineageDelivery` requires a repository root with an existing revision, creates a branch from that revision, commits the accepted delta, opens a PR, and then creates Preview.

Therefore authorization alone would immediately expose another deterministic blocker. P2-V0.23.7 governs both boundaries now, before semantic implementation begins.

## 3. Fixed decisions

### Explicit repository consent

- Existing 422 → `REPOSITORY_AUTHORIZATION_REQUIRED` behavior remains fail-closed.
- The recovery operation is Project-scoped and authenticated. Only the canonical Project owner may request it.
- Repository identity comes exclusively from the canonical Project binding. No repository identifier is accepted from client request content.
- Connector identity is the released server-configured `github/parallax-runtime` connector. No connector identifier is accepted from the client.
- Authorization details are server-owned and derived from the existing exact-repository GitHub policy. The client cannot choose repositories, permissions, scopes, audience, installation ID, resources, webhook, prompt, return URL, or provider parameters.
- The provider operation is `POST /v1/connect/authorize/{connector}`. `/install` is not used because the connector installation already exists and the missing boundary is repository authorization within that connector.
- Authorization initiation uses request/deployment-scoped Vercel OIDC. No PAT, reusable Vercel personal token, GitHub token, password, or static provider secret is introduced.
- The first release does not persist or expose the provider `request` or `verifier`. Parallax does not trust consent-request creation or a browser redirect as proof of repository readiness.
- Final readiness remains the ordinary Connect token request followed by exact-one-repository GitHub installation read-back.

### Greenfield source lineage

- A repository is eligible for greenfield-empty handling only after exact authenticated inspection proves the canonical GitHub repository exists and has no default-branch head commit, or has an exact zero-file Git tree created by Parallax's own idempotent greenfield delivery initialization.
- `SOURCE_NOT_FOUND` by itself is never sufficient evidence of an empty repository because it can also represent missing/hidden source.
- Greenfield is a generic repository shape, not a benchmark identity. Runtime code may not inspect `decision-ledger`, benchmark IDs, DL tokens, `sickbeard`, or expected benchmark output.
- A greenfield root lineage contains **zero files**. Parallax does not create a placeholder README, `.gitkeep`, template app, hidden solution, or internal marker file in accepted source.
- Empty root lineage is admitted through an explicit lineage operation/contract, not by removing the existing non-empty validation for normal repository/template/starter source packages.
- The released lineage source kind for this root is `greenfield`. Its provenance is a bounded digest of canonical repository identity plus deterministic empty-repository state; it contains no raw provider URL or credential.
- Only a root greenfield lineage may contain zero files. An accepted implementation lineage must contain at least one valid source file; BUILD/TEST/VERIFY never execute against a zero-file implementation result.
- Empty-root materialization reconstructs an empty protected directory and verifies the canonical empty-tree digest. Existing non-empty lineage semantics stay unchanged.

### Greenfield verified delivery

- No GitHub source mutation occurs during PLAN, IMPLEMENT, BUILD, TEST, or VERIFY merely to initialize an empty repository.
- The first repository mutation occurs only inside the existing verified delivery boundary at REVIEW after accepted IMPLEMENT + VERIFY evidence is bound to the exact lineage.
- At REVIEW, Parallax re-inspects the canonical repository. It must still be empty or already contain the exact idempotent Parallax empty-baseline commit for this Project/run/root lineage. Any unrelated head fails closed as `STALE_PARENT`/equivalent.
- Add a distinct typed provider action for greenfield repository initialization. It is not represented as an ordinary branch creation or accepted-source commit because it has different parent semantics.
- The initialization action creates an **empty Git tree**, then a deterministic zero-parent baseline commit, then the canonical default-branch ref. The baseline commit contains zero source files.
- Initialization evidence is bound to canonical Project ID, Engineering Run ID, greenfield root lineage ID, repository identity and returned commit revision. Retry is idempotent only if read-back proves the existing head is exactly that baseline commit and its tree is empty.
- After the empty baseline exists, existing delivery semantics resume: create bounded Parallax branch from the baseline commit, commit the exact accepted implementation delta, open/read back the PR, create/read back Vercel Preview, and remain at REVIEW.
- The accepted implementation is never committed directly to the default branch by the greenfield initializer.
- Existing GitHub delivery permissions are reused; no additional GitHub permission is added unless exact provider evidence proves one is required, in which case this spec must be amended before release.
- Existing source-only delivery remains independent from Vercel and does not require greenfield publication. The W9 canonical `vercel-preview` path exercises the greenfield publication flow.

### Client recovery and error contract

- Autonomy errors gain a bounded structured recovery code for exact repository authorization while preserving a display-safe message. The client does not infer consent state through substring matching.
- `EngineeringRunStatus` shows `Authorize repository` only for exact `REPOSITORY_AUTHORIZATION_REQUIRED`; generic provider/runtime failures retain existing `Try again` behavior.
- The authorization action opens only the server-validated external consent URL. The same durable Engineering Run remains visible and retryable.
- After consent, `Try again` continues the same run/revision flow. No new run is created to manufacture benchmark success.
- Preview remains the autonomous publication ceiling and REVIEW remains human-required.

## 4. Architecture requirements

### 4.1 Exact repository authorization request service

Add a narrow server-owned authorization service adjacent to existing repository authority composition. Inputs are canonical Project identity, authenticated owner subject and request-scoped Vercel OIDC.

It resolves the Project's repository through existing owner-scoped authority, requires `github:owner/repository`, and constructs only:

- connector: released server-owned `github/parallax-runtime` configuration;
- subject: `{ "type": "app" }`;
- `authorizationDetails`: exact one-repository GitHub App installation authorization generated from existing policy;
- bounded server-chosen expiration;
- no client-defined return URL, webhook, prompt, installation ID, scopes/resources or additional parameters.

Provider timeout/request failure, non-2xx response, malformed body, missing URL/expiry, or unsafe URL fails closed. Raw provider payloads are not returned or durably persisted.

### 4.2 Safe consent URL

The provider URL is untrusted input. The API accepts only bounded HTTPS URLs on an explicit released origin allowlist established by the preview capability proof. It rejects userinfo, unexpected ports, fragments if not required by the provider, malformed/oversized values, non-public/foreign origins and open-redirect-like values.

The API never follows the URL. Response model contains only:

```json
{
  "status": "authorization_required",
  "authorization_url": "https://...",
  "expires_at": "..."
}
```

### 4.3 Owner-scoped API

Add:

`POST /v1/projects/{project_id}/repository-authorization`

No request body is accepted. Existing owner non-disclosure semantics apply. The endpoint obtains request-scoped Vercel OIDC through the established runtime identity path and returns the bounded consent response above.

### 4.4 Structured autonomous failure

For exact repository-consent failure, the autonomous route returns bounded structured detail while retaining existing HTTP status behavior:

```json
{
  "detail": {
    "message": "Repository authorization is required before Parallax can continue.",
    "code": "REPOSITORY_AUTHORIZATION_REQUIRED"
  }
}
```

This spec does not create an unconstrained generic error taxonomy. Other errors may retain current string detail.

### 4.5 Exact repository inspection

Add a read-only typed provider operation that distinguishes:

- repository missing/unauthorized;
- repository present with a canonical default branch and head revision;
- repository present but default branch has no head commit.

The operation uses the same exact-repository credential boundary and returns no source bytes. Existing `resolve_repository` semantics for commit-bearing source remain unchanged; normal public/Python/.NET bootstrap is not rewritten around nullable revisions.

### 4.6 Explicit greenfield lineage initialization

Extend durable lineage with a dedicated `initialize_greenfield(...)` operation rather than making ordinary `SourcePackage` empty mappings universally valid.

Required root invariants:

- source kind `greenfield`;
- parent lineage `null`;
- file count `0`;
- total bytes `0`;
- files `[]`;
- canonical empty content digest;
- non-null provenance digest bound to canonical repository empty state.

Manifest parsing, identity verification, reconstruction and materialization accept zero files **only** under these root invariants. Existing source kinds and non-empty checks remain unchanged. Implementation capture remains required to produce a non-empty changed tree.

### 4.7 Empty-repository bootstrap composition

When ordinary public source projection cannot produce a commit revision, Parallax may attempt the authenticated exact-repository path. Only an authenticated repository inspection proving the canonical repository exists and is empty may select `initialize_greenfield`.

Private repository consent and empty-state proof remain separate checks. Provider outage, repository not found, scope mismatch, hidden repo, malformed metadata, or any existing non-empty head fails closed and must not be interpreted as greenfield.

A previously created exact Parallax empty-baseline commit with an empty tree is treated as a valid empty repository shape for later recovery/new runs, but no arbitrary empty commit is silently treated as Parallax-owned initialization without exact evidence.

### 4.8 Typed greenfield baseline provider action

Add one fixed GitHub provider action, conceptually `repository.initialize-empty`, admitted only in the existing delivery capability and only at verified REVIEW delivery.

The concrete client performs bounded Git Data operations:

1. inspect canonical repository/default branch;
2. if no head exists, create an empty Git tree;
3. create a zero-parent commit with deterministic Parallax greenfield provenance message/actor;
4. create the default-branch ref to that commit;
5. read back the ref, commit, parents and tree;
6. prove the tree is empty and the commit is bound to the expected Project/run/root-lineage identity.

If the ref already exists, replay succeeds only if exact read-back proves it is the same initialization commit. Otherwise fail closed; force updates are forbidden.

### 4.9 Verified delivery integration

`VerifiedLineageDelivery` accepts repository or greenfield roots. For a repository root, current behavior is byte-for-byte equivalent. For a greenfield root:

- re-inspect empty state at REVIEW;
- initialize/replay the empty default-branch baseline;
- use returned baseline revision as the branch parent;
- compute accepted delta against the zero-file durable root;
- continue through existing branch, accepted-lineage commit, PR, Preview and read-back controls.

Durable delivery evidence records the initialization provider/audit pair in addition to the existing exact lineage, commit, PR and Preview identity. `_MAX_DELIVERY_ACTIONS` may increase only if required to retain all bounded evidence.

### 4.10 Client recovery

The existing autonomy adapter introduces a typed error carrying optional `code` plus display-safe `message`. Engineering-run failure events preserve the code. Existing retry listeners remain the continuation mechanism.

`EngineeringRunStatus` adds a compact recovery panel only for exact repository authorization failure:

- explains that the exact repository needs one-time permission;
- primary `Authorize repository` action;
- existing `Try again` remains available after consent;
- current Project/run/progress remain unchanged.

Web/mobile open the validated external URL through the platform-safe external-link mechanism. No verifier/token is stored in UI state.

## 6. Non-goals

- Automatically granting all repositories to the GitHub App installation.
- PAT/static token fallback.
- Client-provided repository, connector, permissions, scopes, provider URLs or Git ref names.
- Managing arbitrary GitHub App installations.
- Storing GitHub/Vercel provider bearer tokens in Parallax persistence.
- Treating creation of a consent request as successful authorization.
- Seeding README, `.gitkeep`, template source, a reference implementation or hidden benchmark solution.
- Writing any target repository source before accepted VERIFY/REVIEW delivery.
- Committing accepted implementation directly to the default branch.
- Force-updating an existing Git ref.
- Deleting/rewriting unrelated repository history.
- Creating a new Engineering Run after consent merely to manufacture success.
- Bypassing accepted-source lineage, protected validation, Preview or REVIEW.
- Automatic production promotion.
- Changing the frozen DL-01…DL-12 benchmark.
- Closing safe-deletion #290 or unrelated workstreams.

## 7. Security, privacy and reliability

Repository/provider/browser responses are untrusted. Project ownership and canonical repository binding are established before authorization or inspection.

Consent URL validation prevents arbitrary-link injection. Provider request/verifier values and raw provider response bodies are neither returned to the client nor logged. Repeated consent requests grant no authority themselves and do not transition the run.

Empty-repository detection requires positive authenticated evidence; absence/error never becomes empty by default. Zero-file durable lineage is a narrow root state with deterministic digest and manifest invariants, not a relaxation of source validation.

Greenfield baseline initialization is a source-control mutation and therefore remains inside the already authorized verified-delivery boundary at REVIEW. It creates zero source files, has no parent, never force-updates a ref, and is exact-replay safe. Any repository mutation between bootstrap and delivery causes fail-closed stale-parent behavior.

Accepted implementation source remains derived from protected lineage and is published only after VERIFY. Existing exact repository scope verification, tool capability/audit evidence, Preview target binding and REVIEW ceiling remain mandatory.

## 8. Acceptance criteria

### AC-01 Exact owner/Project binding
Only an authenticated owner can initiate repository authorization for a Project, and repository identity is resolved exclusively from canonical Project state.

### AC-02 Fixed connector and authorization detail
The authorization service always uses the released GitHub connector and fixed exact-repository GitHub App authorization detail. Browser input cannot alter connector, repository or authority.

### AC-03 Request-scoped server identity
Authorization initiation uses request/deployment-scoped Vercel OIDC and introduces no PAT, reusable personal token, user credential or persisted provider bearer.

### AC-04 Safe provider authorization operation
Only the fixed Connect authorization endpoint is called with bounded timeout/no redirect following. Timeout, transport error, non-2xx or malformed response fails closed.

### AC-05 Safe consent URL
Only a bounded HTTPS consent URL on the explicit provider origin allowlist is returned. Malicious scheme, userinfo, foreign host/port, malformed or oversized URL is rejected.

### AC-06 Minimal public response
The API returns only status, validated authorization URL and normalized expiry. Provider request/verifier IDs, raw payloads and tokens are not returned or durably stored.

### AC-07 Structured exact recovery signal
The autonomy client receives `REPOSITORY_AUTHORIZATION_REQUIRED` as a bounded structured code without message parsing. Generic provider failures cannot trigger repository-consent UI.

### AC-08 Authorization does not mutate work
Creating/opening a consent request does not mutate Project repository source, Engineering Run state/revision, Work Specification, lineage, deployment or REVIEW state.

### AC-09 Exact repository inspection
A typed read-only provider operation deterministically distinguishes existing commit-bearing, existing empty and missing/unauthorized repositories under exact repository scope.

### AC-10 Empty state requires positive proof
Provider outage, 404/403, credential failure, malformed response or ordinary `SOURCE_NOT_FOUND` alone cannot initialize greenfield lineage.

### AC-11 Explicit zero-file root contract
A dedicated greenfield initialization operation can create a root lineage with zero files and canonical empty digest/provenance. Ordinary repository/template/starter packages remain non-empty by contract.

### AC-12 Greenfield manifest integrity
Zero-file manifests/materialization are accepted only for a root `greenfield` lineage with exact invariants; forged empty implementation/non-greenfield lineage is rejected.

### AC-13 Non-empty implementation required
IMPLEMENT must produce at least one protected source file and a changed non-root implementation lineage before BUILD/TEST/VERIFY can pass.

### AC-14 No pre-REVIEW repository mutation
PLAN through VERIFY on an empty repository performs no GitHub commit/ref/source mutation. Tests prove the initialization write action cannot be invoked before verified REVIEW delivery.

### AC-15 Typed empty-baseline action
At REVIEW, the fixed GitHub initialization action can create an empty tree, zero-parent provenance-bound commit and default-branch ref without force, and exact read-back proves the result.

### AC-16 Initialization idempotency and stale protection
Retry reuses an existing baseline only if commit message/identity, zero parents, empty tree, Project/run/root lineage and default ref match exactly. Any unrelated head fails closed.

### AC-17 Greenfield accepted-source publication
After baseline initialization, accepted implementation is committed on the bounded Parallax branch from that baseline, not on default, and existing PR read-back semantics prove exact head/base identity.

### AC-18 Preview exactness
Vercel Preview is created from the exact accepted implementation commit and existing Preview read-back proves repository/source revision/target identity before delivery evidence is accepted.

### AC-19 Durable delivery evidence
Greenfield delivery records exact initialization, branch, accepted commit, PR and Preview provider/audit evidence without raw credentials/provider payloads and remains replay-safe.

### AC-20 Recovery UX
Web/mobile surfaces show an accessible `Authorize repository` action only for the exact consent condition and preserve same-run `Try again`, current progress and saved work.

### AC-21 Consent retry proves authority
After mocked/provider-approved consent, the same Engineering Run retries through the ordinary scoped token exchange and exact-one-repository GitHub verification before greenfield inspection/source authority is accepted.

### AC-22 Cancel/expiry stays fail-closed
Canceled, expired, wrong-repository or incomplete consent never marks Project/repository ready and does not create greenfield lineage/source mutation.

### AC-23 Existing paths do not regress
Commit-bearing public bootstrap, Python acceptance, OT Time .NET source-only acceptance, repository-root lineage, ordinary GitHub branch/commit/PR delivery, delivery-mode behavior, snapshots and REVIEW ceiling remain green.

### AC-24 No benchmark backdoor or authority expansion
Runtime/provider/client code does not inspect Decision Ledger identity or target name; change cannot grant all-repository authority, arbitrary source mutation, production promotion, work approval or REVIEW completion.

### AC-25 Provider capability proof
Before semantic release is treated as viable, a non-mutating preview/runtime diagnostic proves production-style OIDC can create the exact-repository Connect authorization request and the returned URL passes the released validator. Request/verifier values are not printed and diagnostic code is removed before merge.

### AC-26 Canonical W9 replay
After explicit exact-repository consent, the canonical Decision Ledger trial proceeds without out-of-band source edits through greenfield root, accepted source, protected BUILD/TEST/VERIFY, bounded GitHub branch/PR publication, Vercel Preview and REVIEW, with exact evidence recorded.

### AC-27 Failure remains evidence
If consent, empty initialization, implementation, provider delivery or Preview exposes another boundary, it is recorded and separately governed rather than weakening gates.

### AC-28 Authentic DSPy and exact-head release gates
This exact spec obtains authentic DSPy SpecCritic + SpecCompiler evidence before semantic implementation. Final exact head passes protected spec validation, focused/full API tests, client/browser acceptance, Bounded Autonomy, protected promotion evaluation and applicable release gates before merge/deployment.
