## 1. Objective

Close the remaining Decision Ledger greenfield repository-consent gap through a normal, explicit, least-privilege Parallax recovery path.

Today production correctly fails closed with `REPOSITORY_AUTHORIZATION_REQUIRED` when the canonical Project repository is not covered by the installed `github/parallax-runtime` GitHub App / Vercel Connect authority. The user must currently leave Parallax and discover the provider installation settings manually. That is an operational gap, not a reason to broaden repository authority.

This release will let an authenticated Project owner request a short-lived provider consent URL for **only the Project's exact canonical GitHub repository**, complete explicit authorization in the provider UI, and then retry the same durable Engineering Run. The existing Connect token exchange and exact-one-repository GitHub read-back remain the only proof that runtime repository authority is actually ready.

The canonical W9-S1 Decision Ledger benchmark remains unchanged. It still requires ordinary Project → approved Work Specification → Engineering Run → accepted source → Vercel Preview → REVIEW behavior and no out-of-band target source edits.

## 2. Triggering evidence

Finding #406 is deployment-verified through P2-V0.23.3. The canonical `Ryan9876/sickbeard` trial reaches PLAN and then receives the exact live production classification `REPOSITORY_AUTHORIZATION_REQUIRED`. Public commit-bearing repositories now use the separate credential-free read path, so this recovery path is specifically for source/delivery operations that require credentialed repository authority.

Vercel's documented Connect API exposes `POST /v1/connect/authorize/{connector}`. The request supports `authorizationDetails` and returns a short-lived authorization URL plus request/verifier metadata. The existing Parallax token exchange already uses a bounded `github_app_installation` authorization detail containing exactly one repository and the fixed delivery permissions `contents:write`, `metadata:read`, and `pull_requests:write`.

The client already preserves failed autonomous continuation as durable server truth and has a same-run retry seam. The fix therefore does not require a new Engineering Run lifecycle or benchmark-specific execution path.

## 3. Fixed decisions

- Existing 422 → `REPOSITORY_AUTHORIZATION_REQUIRED` behavior remains fail-closed.
- The recovery operation is Project-scoped and authenticated. Only the canonical Project owner may request it.
- Repository identity comes exclusively from the canonical Project binding. No repository identifier is accepted from client request content.
- Connector identity is the server-configured `github/parallax-runtime` connector already used by production repository authority. No connector identifier is accepted from the client.
- Authorization details are generated by the same server-owned exact-repository delivery policy used by the Connect token request. The client cannot choose scopes, permissions, repositories, installation ID, audience, resources, webhook, prompt, or additional provider parameters.
- The provider operation is `POST /v1/connect/authorize/{connector}`, not a generic provider-management endpoint. `/install` is not used for this release because a connector installation already exists and the missing boundary is exact repository authorization within that installed connector.
- The request uses deployment/request-scoped Vercel OIDC. No PAT, reusable Vercel personal token, GitHub token, user password, or static provider secret is introduced.
- The first release does not persist or expose the provider `request` or `verifier`. Provider consent completion is not trusted as readiness. The user returns to Parallax and retries the same Engineering Run; the ordinary token exchange plus exact-one-repository GitHub verification proves readiness.
- The API returns only bounded consent metadata: `status`, validated `authorization_url`, and normalized `expires_at`.
- Authorization URLs are accepted only when HTTPS and their origin matches an explicit server-owned allowlist derived from the documented Vercel/provider consent surface. Unexpected scheme, host, port, credentials, fragment abuse, malformed URL, or non-public origin fails closed.
- The API never follows or fetches the returned consent URL.
- Creating an authorization request does not mutate target source, create a commit/branch/PR, create a deployment, approve a Work Specification, transition an Engineering Run, or complete REVIEW.
- A client recovery action is shown only when the current request failure has the exact structured code `REPOSITORY_AUTHORIZATION_REQUIRED`. Generic 503/provider failures keep the existing retry presentation.
- Autonomy HTTP errors gain a bounded structured error code while preserving the existing human-readable error message. The client must not infer authorization state by substring matching.
- The recovery action opens the validated external consent URL using the platform's normal safe external-link mechanism. It does not embed provider credentials or tokens in Parallax UI state.
- After provider consent, the ordinary `Try again` action reuses the same Engineering Run and current server revision. No new run is created to manufacture success.
- Public-source Python and OT Time source-only behavior must not regress. W8 remains accepted.
- Preview remains the autonomous publication ceiling and REVIEW remains human-required.

## 4. Architecture

### Exact repository authorization service

Add a narrow server-owned repository authorization request service adjacent to the existing repository authority composition. Its input is canonical Project identity plus the authenticated owner subject and request-scoped Vercel OIDC. It resolves the Project's canonical repository and rejects non-GitHub bindings or invalid/missing Project repository identity.

The service constructs the fixed Connect authorization request:

- connector: existing configured `github/parallax-runtime` identifier;
- subject: `{ "type": "app" }`;
- `authorizationDetails`: exactly `VercelConnectGitHubCredentialProvider.delivery_authorization_details(canonical_repository)`;
- bounded expiration requested by the server;
- no client-defined return URL, webhook, prompt, installation ID, arbitrary scope, resource or additional parameter.

Provider timeout/request failures, non-2xx responses, malformed payloads, missing URL/expiry, or unsafe URLs fail closed with typed bounded recovery errors. Raw provider response bodies are not returned to the client or persisted as durable Project state.

### Owner-scoped API

Add an authenticated endpoint under the Project resource:

`POST /v1/projects/{project_id}/repository-authorization`

The endpoint has no request body. It resolves the Project through existing owner-scoped Project authority, obtains request-scoped Vercel OIDC through the established server path, invokes the exact authorization service, and returns a bounded response model:

```json
{
  "status": "authorization_required",
  "authorization_url": "https://...",
  "expires_at": "..."
}
```

A non-owner or inaccessible Project follows existing non-disclosure semantics. Unsupported provider/repository shape, unavailable OIDC/provider, or unsafe provider response fails closed without source/provider mutation.

### Structured autonomous failure

The autonomous route preserves HTTP status semantics but returns a bounded structured detail for recoverable repository authorization failure:

```json
{
  "detail": {
    "message": "Repository authorization is required before Parallax can continue.",
    "code": "REPOSITORY_AUTHORIZATION_REQUIRED"
  }
}
```

Other existing errors may remain string detail unless already structured. This release does not create a generic arbitrary error taxonomy. Server logs retain the existing bounded diagnostic evidence.

The client autonomy adapter introduces a typed error carrying optional `code` and display-safe `message`. Existing callers that only need an Error remain compatible.

### Client recovery

`useEngineeringRun` records the structured failure code alongside the existing conversation/run/message failure event. `EngineeringRunStatus` detects only the exact authorization-required code and presents a recovery panel near the request error:

- concise explanation that the repository needs one-time authorization;
- primary `Authorize repository` action;
- existing `Try again` remains available for post-consent retry;
- progress/run state remains visible and unchanged.

The authorization action calls the owner-scoped Project endpoint, receives the validated short-lived URL, and opens it externally. Failure to obtain/open the consent URL is recoverable and does not clear the original run failure.

Mobile and web use the same semantic action. Accessibility label/state and keyboard/touch behavior follow the existing action-button conventions. No new durable design-system primitive is introduced.

### Final readiness proof

Parallax does not persist a boolean `authorized=true` based on the consent request or provider redirect. On retry, the existing repository credential provider requests the exact scoped token and accepts it only after GitHub `/installation/repositories` proves `total_count == 1` and the one visible repository exactly matches the canonical Project repository.

This preserves least privilege if the provider consent was canceled, expired, completed for the wrong repository, or otherwise unsuccessful: the same run simply remains at the existing authorization-required boundary.

- Seeding or manually editing the Decision Ledger repository.

- Closing safe-deletion #290 or unrelated workstreams.

## 7. Security, privacy and reliability

Repository and provider responses are untrusted. Project ownership and exact repository binding are established before any authorization request. Authorization request construction is entirely server-owned.

Consent URL validation must prevent open-redirect or arbitrary-link injection. Only HTTPS is allowed; userinfo is forbidden; hostname/origin matching is exact against the released provider allowlist; malformed/oversized URLs fail closed. The raw verifier/request identifiers are not exposed or logged. Any provider error body is bounded/redacted before diagnostics.

Repeated authorization requests are safe recovery operations but must be bounded by ordinary endpoint/request controls. They do not grant authority themselves and cannot transition the run. Expired or canceled authorization simply leaves token exchange fail-closed.

The action must not expose whether another owner's Project exists. Repository identity must not be accepted from the browser. Existing exact-one-repository runtime token verification is mandatory after consent and cannot be bypassed by tests, callbacks, or UI state.

## 8. Acceptance criteria

### AC-01 Exact owner/Project binding
Only an authenticated owner can initiate repository authorization for a Project, and repository identity is resolved only from the canonical Project binding.

### AC-02 Fixed connector and authorization detail
The service always uses the released server-owned GitHub connector and the exact existing `github_app_installation` authorization detail for one canonical repository and fixed delivery permissions. Client input cannot alter these values.

### AC-03 Request-scoped server identity
Authorization initiation uses request/deployment-scoped Vercel OIDC and introduces no PAT, reusable personal token, user credential, or stored provider bearer.

### AC-04 Safe provider operation
The server calls only the fixed Connect authorization endpoint with bounded timeout and no redirect following. Provider timeout, transport error, non-2xx, malformed body or missing fields fail closed.

### AC-05 Safe consent URL
Only a bounded HTTPS authorization URL on the explicit provider allowlist is returned. Malicious schemes, credentials, unexpected origins, ports, malformed/oversized values and unsafe redirects are rejected.

### AC-06 Minimal response surface
The public API returns only status, validated authorization URL and normalized expiry. Provider request/verifier identifiers, raw payloads and tokens are neither returned nor durably stored.

### AC-07 Structured recovery classification
The autonomous client can distinguish `REPOSITORY_AUTHORIZATION_REQUIRED` through a bounded structured error code without parsing a human message. Generic provider failures do not masquerade as repository consent.

### AC-08 Existing run preserved
Authorization initiation does not change Engineering Run state/revision, approved Work Specification, source lineage, provider delivery state, or target repository contents.

### AC-09 Recovery UX
Web and mobile surfaces show an accessible `Authorize repository` action only for the exact authorization-required condition, while preserving the existing saved-progress and same-run `Try again` behavior.

### AC-10 External consent handling
The client opens only the server-validated authorization URL through the platform external-link mechanism. It does not receive provider bearer tokens or authorization verifier material.

### AC-11 Retry proves readiness
After a mocked successful provider consent, retrying the same run uses the ordinary exact-repository token request and exact-one-repository GitHub verification before source/provider authority is accepted.

### AC-12 Cancel/expiry stays fail-closed
Canceled, expired, wrong-repository or otherwise incomplete consent does not mark the Project ready; retry returns to the authorization-required boundary without source mutation.

### AC-13 Public-source and W8 regression protection
Existing credential-free public source bootstrap, Python full-experience behavior, OT Time `.NET` source-only acceptance path, validation snapshots, delivery-mode behavior and REVIEW ceiling remain green.

### AC-14 No authority expansion
The change cannot add repository installation coverage silently, select all repositories, grant arbitrary permissions, mutate source before explicit provider consent, merge, deploy production, approve work or complete REVIEW.

### AC-15 Provider capability proof
Before semantic release is treated as viable, a non-mutating preview/runtime diagnostic proves the production-style OIDC identity can create an exact-repository Connect authorization request and that the returned URL passes the released safe-origin validator. Diagnostic request/verifier values are not printed and temporary diagnostic code is removed before merge.

### AC-16 Canonical W9 replay
After release and explicit exact-repository provider consent, the existing Decision Ledger trial continues through the normal authenticated path using the same canonical Project/approved specification or a governed exact equivalent, with no out-of-band source edits, and records accepted source, protected validation, Vercel Preview and REVIEW evidence.

### AC-17 Failure remains evidence
If provider consent or the replay exposes another product boundary, it is recorded honestly and receives separate governance rather than weakening authorization or benchmark gates.

### AC-18 Authentic DSPy and exact-head release gates
This exact spec obtains authentic DSPy SpecCritic + SpecCompiler evidence before semantic implementation. Final exact head passes protected spec validation, focused/full tests, client/browser acceptance, Bounded Autonomy, protected promotion evaluation and standard release gates before merge/deployment.
