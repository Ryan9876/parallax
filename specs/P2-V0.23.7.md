## 1. Objective

Close the remaining generic empty-greenfield runtime gap without weakening Parallax's repository authority model.

Production already classifies missing exact-repository GitHub App / Vercel Connect coverage as `REPOSITORY_AUTHORIZATION_REQUIRED`. The canonical W9 target is also a truly empty repository: after repository permission is granted it still has no commit, tree, or source files, while durable source lineage and verified delivery currently assume an existing repository root commit.

P2-V0.23.7 therefore delivers two bounded outcomes:

1. preserve and expose `REPOSITORY_AUTHORIZATION_REQUIRED` as a structured, retry-safe recovery condition without inventing a new reusable provider credential or widening repository authority; and
2. support a governed zero-file greenfield root that can proceed through ordinary protected IMPLEMENT/BUILD/TEST/VERIFY, then initialize a zero-source Git baseline only inside verified REVIEW delivery before publishing the exact accepted implementation through the existing branch → pull request → Vercel Preview path.

The one-time external repository-permission action remains an explicit provider/user authorization boundary. This release does not claim that workload OIDC can initiate that consent flow.

No reference solution, placeholder source, manual seed commit, broad GitHub installation grant, benchmark-only path, reusable Vercel account token, or preview write-authority expansion is introduced.

## 2. Triggering evidence

Finding #406 is deployment-verified through P2-V0.23.3. The canonical `Ryan9876/sickbeard` trial reaches PLAN and receives `REPOSITORY_AUTHORIZATION_REQUIRED` because the repository is outside the installed `github/parallax-runtime` exact-repository authorization.

Code inspection established the next deterministic boundary:

- ordinary GitHub repository resolution requires a default-branch head revision;
- projected source rejects a repository with no lineage-safe files;
- durable lineage requires a non-empty root;
- verified delivery requires an existing parent revision before branch creation.

The first P2-V0.23.7 design proposed a first-class Parallax endpoint backed by `POST /v1/connect/authorize/{connector}` using deployment-scoped Vercel OIDC. Before semantic implementation, AC-25 required a non-mutating capability probe.

The probe produced exact counter-evidence:

- preview deployment OIDC could not request a token from the production-only `github/parallax-runtime` connector (`HTTP 403`);
- the same workload OIDC also received `HTTP 403` from the Connect authorization endpoint;
- the probe never followed a consent URL and never mutated repository or installation state;
- no provider request/verifier/token values were printed or persisted.

Vercel documentation separately confirms deployment OIDC is the normal authentication path for Connect token exchange, while Connect authorization/install REST examples are described with a general bearer/access token. There is therefore insufficient evidence to make repository-consent initiation a workload-OIDC runtime feature.

The architecture response is fail-closed: do not introduce a reusable Vercel personal/team token, do not attach the production GitHub connector to preview merely to test consent, and do not weaken exact-repository authority. The greenfield runtime path remains independently implementable once explicit provider consent exists.

## 3. Fixed decisions

### Repository authorization boundary

- Existing 422 → `REPOSITORY_AUTHORIZATION_REQUIRED` behavior remains fail-closed.
- The condition is represented as a bounded structured code, not inferred from display text.
- Parallax does not add `POST /v1/projects/{project_id}/repository-authorization` in this release.
- Parallax does not call `/v1/connect/authorize/{connector}` or `/v1/connect/install/{connector}` from production runtime without a separately governed authentication design and positive capability proof.
- No PAT, reusable Vercel personal/team token, GitHub user token, password, static provider secret, or browser-supplied provider credential is introduced.
- Production exact-repository readiness remains the ordinary Connect token request plus exact-one-repository GitHub installation verification already used by delivery composition.
- A user/provider may complete the one-time exact-repository grant out of band. That grant is never treated as successful until the next ordinary scoped token exchange and exact repository read-back succeed.
- Same-run retry remains the continuation path after permission changes; no replacement Engineering Run is created to manufacture success.

### Greenfield source lineage

- A repository is eligible for greenfield-empty handling only after exact authenticated inspection positively proves the canonical GitHub repository exists and has no default-branch head commit, or proves an exact Parallax-created empty baseline for the same repository shape.
- `SOURCE_NOT_FOUND`, 404, 403, provider outage, credential failure, malformed data, or hidden repository state alone never implies greenfield.
- Greenfield is a generic repository shape. Runtime/provider/client code may not inspect Decision Ledger identity, benchmark IDs, `sickbeard`, expected files, or expected output.
- A greenfield root lineage contains zero files. Parallax does not synthesize README, `.gitkeep`, hidden marker, template, starter code, or reference implementation.
- Empty root lineage is admitted through a dedicated contract, not by making ordinary source packages universally empty-valid.
- The released lineage source kind is `greenfield` with deterministic empty-content digest and provenance bound to canonical repository identity plus positively proven empty state.
- Only a root greenfield lineage may contain zero files. Accepted implementation lineage must be non-root, changed, and contain at least one valid source file before protected BUILD/TEST/VERIFY can pass.
- Empty-root reconstruction/materialization produces an empty protected directory and verifies canonical empty-state invariants.

### Greenfield verified delivery

- No GitHub source/ref mutation occurs during PLAN, IMPLEMENT, BUILD, TEST, or VERIFY merely to create a repository baseline.
- The first greenfield repository mutation occurs only inside existing verified delivery after accepted implementation and VERIFY evidence have reached REVIEW.
- REVIEW delivery re-inspects the canonical repository. It must still be positively empty or contain the exact idempotent Parallax empty-baseline commit for this Project/run/root lineage. Any unrelated head fails closed.
- Add one distinct typed provider action for empty-repository initialization; it is not represented as ordinary branch creation or accepted-source commit because parent semantics differ.
- Initialization creates an empty Git tree, a deterministic zero-parent provenance-bound commit, and the canonical default-branch ref without force.
- Exact read-back proves ref, commit, zero parents, empty tree, repository identity, Project/run/root-lineage binding, and default branch.
- Retry may reuse a baseline only when all exact initialization invariants match. Otherwise it fails closed as stale/conflicting source.
- After the baseline exists, existing verified-delivery semantics resume: bounded Parallax branch from baseline, accepted implementation commit, PR create/read-back, Vercel Preview create/read-back, REVIEW ceiling.
- Accepted implementation is never committed directly to the default branch by the initializer.
- Existing exact GitHub delivery permissions are reused. If provider evidence proves additional permission is required, that becomes a separately governed change rather than silent scope widening.
- Source-only delivery remains independent of Vercel application delivery.

### Recovery UX and error contract

- Autonomous failure exposes optional bounded `code` plus display-safe `message`.
- Exact repository-consent failure uses `REPOSITORY_AUTHORIZATION_REQUIRED`.
- Generic provider/runtime failures cannot trigger repository-consent-specific UI.
- Engineering Run UI explains that the exact repository requires one-time provider permission and preserves the current Project/run/progress plus existing `Try again` action.
- This release does not surface a fabricated or unverified consent URL.
- If a future provider-approved consent URL mechanism is added, it requires a new capability proof and separate governed specification amendment.

## 4. Architecture requirements

### 4.1 Structured autonomous failure

For exact repository-consent failure, retain current HTTP status semantics but return bounded structured detail:

```json
{
  "detail": {
    "message": "Repository authorization is required before Parallax can continue.",
    "code": "REPOSITORY_AUTHORIZATION_REQUIRED"
  }
}
```

Other errors may retain existing string detail unless independently typed. Client behavior must never parse display text to infer authority state.

### 4.2 Exact repository inspection

Add a read-only typed provider operation that distinguishes:

- repository missing/unauthorized;
- repository present with canonical default branch and head revision;
- repository present but default branch has no head commit.

The operation uses the existing exact-repository credential boundary and returns no source bytes. Ordinary commit-bearing public/Python/.NET bootstrap semantics remain unchanged.

The inspection result must be typed and bounded. Empty state is a positive value, not an exception-derived guess.

### 4.3 Explicit greenfield lineage initialization

Extend durable lineage with `initialize_greenfield(...)` or equivalent dedicated operation rather than making ordinary `SourcePackage` empty mappings universally valid.

Required root invariants:

- source kind `greenfield`;
- parent lineage `null`;
- file count `0`;
- total bytes `0`;
- files `[]`;
- canonical empty content digest;
- non-null provenance digest bound to canonical repository empty-state proof.

Manifest parsing, identity verification, reconstruction and materialization accept zero files only under those root invariants. Existing repository/template/starter source contracts stay non-empty by default.

### 4.4 Empty-repository bootstrap composition

When ordinary source bootstrap cannot produce a commit-bearing source root, Parallax may attempt authenticated exact-repository inspection.

Only positive `existing_empty` proof for the canonical repository may select `initialize_greenfield`. Missing authorization remains `REPOSITORY_AUTHORIZATION_REQUIRED`; missing/hidden/outage/malformed states remain bounded failures.

A previously created exact Parallax empty baseline may be recognized only through exact read-back evidence. An arbitrary empty commit is not silently promoted to Parallax-owned initialization.

### 4.5 Non-empty implementation requirement

Protected implementation runtime must reject a greenfield run that attempts to advance with zero accepted implementation files or unchanged root lineage.

At least one safe source artifact must be captured into a changed non-root lineage before BUILD/TEST/VERIFY may succeed. Existing secret/path/size/digest constraints remain unchanged.

### 4.6 Typed greenfield baseline provider action

Add fixed GitHub provider capability `repository.initialize-empty` (exact final name may follow repository conventions) admitted only within verified delivery authority.

Concrete Git operations are bounded:

1. inspect repository/default branch;
2. if no head exists, create an empty tree;
3. create zero-parent deterministic Parallax greenfield commit;
4. create default-branch ref without force;
5. read back ref, commit, parents and tree;
6. prove exact empty-tree and provenance identity.

No arbitrary ref name, parent, commit message, actor, tree content or repository is accepted from model/browser input.

### 4.7 Verified delivery integration

`VerifiedLineageDelivery` accepts ordinary repository roots and greenfield roots.

Ordinary repository-root behavior must remain byte-for-byte equivalent.

For a greenfield root:

- re-inspect exact repository at REVIEW;
- initialize/replay exact empty baseline;
- use returned baseline revision as branch parent;
- compute accepted delta against zero-file durable root;
- continue through existing branch, accepted commit, PR and Preview controls;
- preserve exact read-back, audit and replay safety.

Durable delivery evidence records initialization action evidence in addition to existing accepted commit/PR/Preview identity. Evidence budgets may increase only by the minimum required bounded count.

### 4.8 Recovery client

The existing autonomy adapter carries optional `code` and display-safe `message`. Engineering-run failure state preserves the code.

`EngineeringRunStatus` shows repository-permission guidance only for exact `REPOSITORY_AUTHORIZATION_REQUIRED` and retains existing same-run `Try again`. No provider credential, verifier or opaque authorization request is stored in UI state.

## 6. Non-goals

- Automatically granting GitHub App access to any repository.
- Requesting all-repositories GitHub scope.
- PAT/static token fallback.
- Reusable Vercel personal/team API token in runtime.
- Attaching production GitHub write authority to preview solely to enable consent initiation.
- Client-provided repository, connector, permissions, scopes, provider URLs or Git refs.
- Managing arbitrary GitHub App installations.
- Treating `SOURCE_NOT_FOUND` as proof of an empty repository.
- Seeding README, `.gitkeep`, template source, reference implementation or hidden benchmark solution.
- Writing target source before accepted VERIFY/REVIEW delivery.
- Committing accepted implementation directly to default branch.
- Force-updating existing refs.
- Deleting or rewriting unrelated repository history.
- Creating a new Engineering Run after permission changes merely to manufacture success.
- Bypassing accepted-source lineage, protected validation, Preview or REVIEW.
- Automatic production promotion.
- Changing frozen DL-01…DL-12 benchmark semantics.

## 7. Security, privacy and reliability

Repository/provider/browser responses are untrusted. Project ownership and canonical repository binding are established before credentialed inspection or mutation.

The failed authorization probe is evidence, not a reason to widen authority. Runtime gains no reusable Vercel bearer and preview gains no production GitHub connector access.

Empty-repository detection requires positive authenticated evidence; absence or error never becomes empty by default. Zero-file durable lineage is a narrow root state with deterministic digest/provenance invariants.

Greenfield baseline initialization remains inside verified REVIEW delivery. It creates zero source files, has zero parents, never force-updates a ref, and is exact-replay safe. Any intervening unrelated repository head fails closed.

Accepted implementation remains derived from protected lineage and is published only after VERIFY. Existing exact-repository scope verification, capability/audit evidence, Preview target binding and REVIEW ceiling remain mandatory.

## 8. Acceptance criteria

### AC-01 Structured exact recovery signal
Autonomy returns `REPOSITORY_AUTHORIZATION_REQUIRED` as a bounded structured code without display-message parsing.

### AC-02 No new reusable provider credential
Runtime introduces no PAT, reusable Vercel personal/team token, GitHub user token, password or static provider bearer to initiate repository consent.

### AC-03 No preview authority expansion
Preview environments are not granted production `github/parallax-runtime` mutation authority merely to make consent initiation testable.

### AC-04 Existing readiness proof remains authoritative
After external exact-repository consent, ordinary production Connect token exchange plus exact-one-repository GitHub verification remains the only readiness proof.

### AC-05 Same-run recovery
Permission changes do not alter Project/work/run identity; the same durable Engineering Run remains retryable.

### AC-06 Recovery UI is exact and non-fabricated
Repository-permission guidance appears only for exact `REPOSITORY_AUTHORIZATION_REQUIRED`; no unverified consent URL is surfaced.

### AC-07 Exact repository inspection
A typed read-only operation deterministically distinguishes commit-bearing, positively empty and missing/unauthorized repositories under exact repository scope.

### AC-08 Empty state requires positive proof
Provider outage, 404/403, credential failure, malformed response or ordinary `SOURCE_NOT_FOUND` alone cannot initialize greenfield lineage.

### AC-09 Explicit zero-file root contract
A dedicated greenfield initialization operation creates a zero-file root lineage with canonical empty digest and provenance; ordinary source packages remain non-empty by contract.

### AC-10 Greenfield manifest integrity
Zero-file manifest/materialization is accepted only for a root `greenfield` lineage with exact invariants; forged empty implementation/non-greenfield lineage is rejected.

### AC-11 Non-empty implementation required
IMPLEMENT must produce at least one safe protected source file and a changed non-root lineage before BUILD/TEST/VERIFY can pass.

### AC-12 No pre-REVIEW repository mutation
PLAN through VERIFY on an empty repository performs no GitHub commit/ref/source mutation merely to initialize baseline.

### AC-13 Typed empty-baseline action
At REVIEW, the fixed GitHub initialization action creates empty tree, zero-parent provenance-bound commit and default-branch ref without force and proves exact read-back.

### AC-14 Initialization idempotency
Retry reuses an existing baseline only if zero parents, empty tree, deterministic provenance, Project/run/root lineage and default ref all match exactly.

### AC-15 Stale/conflicting repository protection
Any unrelated head or incompatible ref state fails closed and is never overwritten.

### AC-16 Greenfield accepted-source publication
After baseline initialization, accepted source is committed on bounded Parallax branch from baseline, never directly on default.

### AC-17 Pull-request exactness
Existing PR create/read-back semantics prove exact repository, head branch/revision and base branch for greenfield delivery.

### AC-18 Preview exactness
Vercel Preview is created from exact accepted implementation commit and existing Preview read-back proves repository/source revision/target identity.

### AC-19 Durable greenfield evidence
Delivery records bounded initialization, branch, accepted commit, PR and Preview evidence without credentials/raw provider payloads and remains replay-safe.

### AC-20 Existing repository paths do not regress
Commit-bearing public bootstrap, Python acceptance, OT Time .NET source-only acceptance, ordinary repository-root lineage and GitHub delivery remain green.

### AC-21 Source-only independence
Source-only delivery does not acquire a Vercel application-delivery dependency because of greenfield support.

### AC-22 REVIEW ceiling preserved
Greenfield publication ends at REVIEW and cannot grant work approval, production promotion or REVIEW completion.

### AC-23 No benchmark backdoor
Runtime/provider/client code does not inspect Decision Ledger identity, `sickbeard`, benchmark tokens or expected solution content.

### AC-24 Failed probe is removed
Temporary authorization probe code, preview marker and temporary build invocation are removed before final PR; the negative result is retained only as governance evidence.

### AC-25 Capability conclusion is explicit
The release record states that workload-OIDC authorization initiation was not proven and is therefore not shipped; this is not represented as a deployed capability.

### AC-26 Canonical W9 replay
After explicit exact-repository consent, the canonical Decision Ledger trial proceeds without out-of-band source edits through positive empty proof, greenfield root, accepted source, protected BUILD/TEST/VERIFY, REVIEW-only baseline initialization, bounded GitHub branch/PR publication, Vercel Preview and REVIEW.

### AC-27 Failure remains evidence
If consent, empty inspection, initialization, implementation, delivery or Preview exposes another boundary, it is recorded and separately governed rather than weakening gates.

### AC-28 Authentic DSPy and exact-head release gates
This amended exact spec obtains authentic DSPy SpecCritic + SpecCompiler evidence before semantic implementation. Final exact head passes protected spec validation, focused/full API tests, applicable client/browser acceptance, Bounded Autonomy, protected promotion evaluation and release gates before merge/deployment.
