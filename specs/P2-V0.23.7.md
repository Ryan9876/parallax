## 1. Objective

Close the generic empty-greenfield runtime gap without weakening repository authority.

Production already classifies missing exact-repository GitHub App / Vercel Connect coverage as `REPOSITORY_AUTHORIZATION_REQUIRED`. After explicit repository permission is granted, a truly empty repository still has no commit, tree or source files while Parallax durable lineage and verified delivery assume a commit-bearing root.

This release therefore:

1. preserves `REPOSITORY_AUTHORIZATION_REQUIRED` as a structured, same-run recovery condition without adding reusable provider credentials or widening repository authority; and
2. supports a governed zero-file greenfield lineage that proceeds through ordinary protected IMPLEMENT/BUILD/TEST/VERIFY, then initializes a REST-compatible empty Git baseline only inside verified REVIEW delivery before existing branch → pull request → Vercel Preview publication.

The one-time repository-permission action remains an explicit provider/user authorization boundary. No reference solution, template app, benchmark-only path, PAT, reusable Vercel account token or preview write-authority expansion is introduced.

## 2. Triggering evidence and provider constraints

Finding #406 is deployment-verified. The canonical `Ryan9876/sickbeard` trial reaches PLAN and receives `REPOSITORY_AUTHORIZATION_REQUIRED` because the target is outside the installed `github/parallax-runtime` exact-repository authorization.

A required non-mutating capability probe disproved the initial in-product consent design:

- preview workload OIDC received HTTP 403 from the production-only Connect token exchange;
- the same workload OIDC received HTTP 403 from `POST /v1/connect/authorize/{connector}`;
- no consent URL was followed, no repository/installation state was mutated, and no request/verifier/provider token was printed or persisted.

Therefore Parallax will not introduce a reusable Vercel personal/team token and will not attach production GitHub authority to preview merely to initiate consent.

A second provider constraint was discovered before implementing delivery. GitHub's current REST documentation states that new Git references cannot be created in an empty repository even when the referenced commit object exists. GitHub's REST guidance for an empty repository is to initialize it through `PUT /repos/{owner}/{repo}/contents/{path}` before using Git Database endpoints. Therefore the earlier empty-tree → zero-parent commit → create-ref sequence is not implementable through the released REST surface.

The release adopts the simplest documented REST-compatible sequence while preserving the important security properties: at REVIEW only, create one deterministic non-executable bootstrap file as the initial commit, immediately delete that exact file serially, verify the resulting default-branch head tree is empty, then use that empty-tree head as the parent for the ordinary Parallax branch. The temporary bootstrap file never survives in the repository's current tree and never contains application source, benchmark content, credentials, raw Project/run IDs or provider payloads.

## 3. Fixed decisions

### Repository authorization boundary

- Existing `REPOSITORY_AUTHORIZATION_REQUIRED` behavior remains fail-closed and becomes a bounded structured code.
- No repository-authorization REST endpoint is added in this release.
- Runtime does not call Vercel Connect authorize/install without a separately governed authentication design and positive capability proof.
- No PAT, reusable Vercel personal/team token, GitHub user token, password, static provider secret or browser-supplied provider credential is introduced.
- Production readiness remains ordinary Connect token exchange followed by exact-one-repository GitHub installation verification.
- External exact-repository permission is never assumed successful until the next ordinary scoped token exchange and exact repository read-back succeed.
- Permission changes preserve the same Project, Work Specification and Engineering Run; retry continues the same durable run.

### Greenfield source lineage

- Greenfield is selected only after positive authenticated inspection proves the canonical repository exists and has no default-branch head, or proves an exact Parallax-created empty baseline shape.
- `SOURCE_NOT_FOUND`, 404, 403, provider outage, credential failure or malformed data alone never imply greenfield.
- Runtime/provider/client code may not inspect Decision Ledger identity, `sickbeard`, benchmark tokens or expected solution content.
- A greenfield root lineage contains zero files, zero bytes, canonical empty content digest, no parent and non-null provenance digest.
- Ordinary repository/template/starter packages remain non-empty by contract.
- Only a root `greenfield` lineage may contain zero files.
- Accepted implementation must be a changed non-root lineage containing at least one protected source file before BUILD/TEST/VERIFY can pass.
- Empty-root materialization is an empty protected directory; implementation capture remains subject to existing path/secret/size/digest controls.

### REST-compatible greenfield baseline

- No GitHub source/ref mutation occurs during PLAN, IMPLEMENT, BUILD, TEST or VERIFY merely to initialize the empty repository.
- The first mutation occurs only inside verified delivery after accepted implementation and VERIFY evidence have reached REVIEW.
- REVIEW delivery re-inspects the canonical repository. It must still be positively empty or contain the exact idempotent Parallax empty baseline for this Project/run/root lineage. Any unrelated head fails closed.
- One typed provider action owns the entire initialization transaction surface.
- If the repository has no head, the action uses the documented repository-contents API to create one fixed bootstrap path with fixed non-executable content carrying only version text plus a one-way provenance digest.
- The bootstrap commit is the repository's root commit. Its commit message/actor/path/content are server-owned and deterministic.
- The action then serially deletes that exact bootstrap path using its returned blob SHA and the canonical default branch.
- The resulting cleanup commit becomes the Parallax empty baseline. Exact read-back proves: expected default ref; head commit; exactly one parent equal to the deterministic bootstrap root; empty head tree; bootstrap parent tree contains only the fixed bootstrap path/content; and provenance digest matches the expected Project/run/root-lineage binding.
- The temporary bootstrap file exists only in immutable history. It is absent from the default-branch head before accepted application source is branched.
- No force update, arbitrary path, arbitrary content, arbitrary ref or arbitrary commit message is accepted from model/browser input.
- Retry reuses an existing baseline only when all exact two-commit invariants match. Otherwise fail closed.
- Concurrent unrelated repository changes are never overwritten; final non-empty or mismatched read-back fails closed.
- After the empty baseline exists, existing delivery resumes: bounded Parallax branch from baseline, accepted implementation commit, PR create/read-back, Vercel Preview create/read-back, REVIEW ceiling.
- Accepted application source is never committed directly to default by the initializer.
- Existing `contents:write`, `metadata:read`, `pull_requests:write` exact-repository permissions are reused; no additional GitHub permission is added without separate evidence/governance.
- Source-only delivery remains independent of Vercel application delivery.

### Recovery UX and error contract

- Autonomous failure exposes optional bounded `code` plus display-safe `message`.
- Exact repository-consent failure uses `REPOSITORY_AUTHORIZATION_REQUIRED`.
- Generic provider/runtime failures cannot trigger repository-consent-specific UI.
- Engineering Run UI explains that the exact repository requires one-time provider permission and preserves the current run plus existing `Try again`.
- This release does not surface a fabricated/unverified consent URL.

## 4. Architecture requirements

### 4.1 Structured autonomous failure

For exact repository-consent failure, retain current status semantics but return:

```json
{
  "detail": {
    "message": "Repository authorization is required before Parallax can continue.",
    "code": "REPOSITORY_AUTHORIZATION_REQUIRED"
  }
}
```

Other errors may retain string detail. Client behavior may not parse display text to infer authority.

### 4.2 Exact repository inspection

Add a typed read-only provider operation that returns only one of:

- missing/unauthorized failure;
- commit-bearing repository with canonical default branch and head revision;
- positively empty repository with canonical default branch and no head revision.

The operation uses existing exact-repository credential authority and returns no source bytes. Ordinary commit-bearing public/Python/.NET bootstrap remains unchanged.

### 4.3 Explicit greenfield lineage initialization

Durable lineage exposes a dedicated `initialize_greenfield(...)` operation. Required root invariants:

- `source_kind == "greenfield"`;
- `parent_lineage_id == null`;
- `file_count == 0`;
- `total_bytes == 0`;
- `files == []`;
- canonical empty content digest;
- non-null provenance digest.

Zero-file manifest parsing/reconstruction/materialization is valid only for those exact root invariants. Ordinary source packages remain non-empty.

### 4.4 Empty-repository bootstrap composition

Ordinary source bootstrap remains first. Greenfield initialization may be selected only after positive exact-repository empty inspection. Public/source errors alone never create greenfield authority.

A previously created Parallax empty baseline is recognized only through exact provider read-back; an arbitrary empty commit is not silently treated as Parallax-owned initialization.

### 4.5 Non-empty implementation requirement

A greenfield run cannot advance protected validation with zero accepted implementation files or unchanged root lineage. At least one safe source artifact must be captured into a changed non-root lineage.

### 4.6 Typed REST-compatible baseline provider action

Add fixed GitHub capability `repository.initialize-empty` admitted only in verified delivery authority.

Concrete bounded sequence:

1. inspect canonical repository/default branch;
2. when no head exists, `PUT` the fixed bootstrap path on the canonical default branch using fixed content/message/actor;
3. verify returned root commit/blob identity;
4. serially `DELETE` that exact bootstrap path using its returned blob SHA and fixed cleanup message/actor;
5. read back default ref, cleanup commit, bootstrap parent commit and both trees;
6. prove the head tree is empty and the parent tree is exactly the one allowed bootstrap file with expected digest/provenance;
7. return the cleanup commit as the empty-baseline revision.

Replay with an existing head performs read-back only. It succeeds only for the exact deterministic baseline; no write/force occurs on mismatch.

### 4.7 Verified delivery integration

`VerifiedLineageDelivery` accepts ordinary repository roots and greenfield roots. Ordinary repository behavior remains equivalent.

For greenfield:

- re-inspect exact repository at REVIEW;
- initialize/replay exact REST-compatible empty baseline;
- use returned empty-baseline revision as branch parent;
- compute accepted delta against zero-file durable root;
- continue existing branch/commit/PR/Preview controls;
- record bounded initializer plus existing provider/audit evidence.

### 4.8 Recovery client

The autonomy adapter carries optional structured `code` and display-safe `message`. Engineering-run failure state preserves the code. Repository-permission guidance appears only for exact `REPOSITORY_AUTHORIZATION_REQUIRED`; same-run `Try again` remains the continuation mechanism.

## 6. Security and reliability

Repository/provider/browser data is untrusted. Project ownership and canonical repository binding are established before credentialed inspection/mutation.

The failed Vercel authorization probe remains negative evidence and does not justify authority widening.

Empty detection requires positive exact-repository evidence. Zero-file lineage is a narrow root contract, not a relaxation of source validation.

The temporary REST bootstrap marker is fixed, non-executable, contains no source/credential/raw internal identity, and exists only in repository history. The verified default-branch head is empty before application publication. Operations are serial and no ref is force-updated. Concurrent unrelated changes cause fail-closed read-back rather than overwrite.

Accepted application source remains protected lineage and is published only after VERIFY. Existing exact repository scope, provider audit, Preview target binding and REVIEW ceiling remain mandatory.

## 7. Acceptance criteria

### AC-01 Structured exact recovery signal
Autonomy returns `REPOSITORY_AUTHORIZATION_REQUIRED` as a bounded structured code without message parsing.

### AC-02 No new reusable provider credential
Runtime introduces no PAT, reusable Vercel personal/team token, GitHub user token, password or static provider bearer to initiate repository consent.

### AC-03 No preview authority expansion
Preview is not granted production `github/parallax-runtime` mutation authority merely to make consent initiation testable.

### AC-04 Existing readiness proof remains authoritative
After external exact-repository consent, ordinary production Connect token exchange plus exact-one-repository GitHub verification remains the readiness proof.

### AC-05 Same-run recovery
Permission changes preserve Project/work/run identity and the same Engineering Run remains retryable.

### AC-06 Recovery UI is exact and non-fabricated
Permission guidance appears only for exact authorization-required code; no unverified consent URL is surfaced.

### AC-07 Exact repository inspection
Typed read-only inspection deterministically distinguishes commit-bearing, positively empty and missing/unauthorized states under exact scope.

### AC-08 Empty state requires positive proof
Outage, 404/403, credential failure, malformed response or ordinary source failure alone cannot initialize greenfield lineage.

### AC-09 Explicit zero-file root contract
Dedicated greenfield initialization creates a zero-file root with canonical empty digest/provenance; ordinary source packages remain non-empty.

### AC-10 Greenfield manifest integrity
Zero-file manifest/materialization is accepted only for exact root-greenfield invariants; forged empty implementation/non-greenfield lineage is rejected.

### AC-11 Non-empty implementation required
IMPLEMENT produces at least one safe protected file and changed non-root lineage before BUILD/TEST/VERIFY can pass.

### AC-12 No pre-REVIEW repository mutation
PLAN through VERIFY performs no GitHub source/ref mutation merely to initialize empty baseline.

### AC-13 REST-compatible empty baseline
At REVIEW, fixed initializer creates the deterministic bootstrap root commit via repository-contents API, serially deletes the exact bootstrap file, and proves the resulting default-branch head tree is empty.

### AC-14 Initialization idempotency
Replay reuses an existing baseline only when cleanup head, bootstrap parent, parent count, trees, fixed path/content/messages/actor, provenance and default ref all match exactly.

### AC-15 Stale/conflicting repository protection
Any unrelated head, extra file, modified bootstrap or incompatible ref state fails closed and is never overwritten/force-updated.

### AC-16 No persistent bootstrap source
The bootstrap path is absent from the verified default-branch head before accepted implementation publication; it exists only in immutable initialization history.

### AC-17 Greenfield accepted-source publication
Accepted application source is committed on bounded Parallax branch from the verified empty baseline, never directly to default by the initializer.

### AC-18 Pull-request exactness
Existing PR create/read-back proves exact repository, head branch/revision and base branch.

### AC-19 Preview exactness
Vercel Preview is created from exact accepted commit and read-back proves repository/source revision/target identity.

### AC-20 Durable greenfield evidence
Delivery records bounded initialization, accepted commit, PR and Preview evidence without credentials/raw provider payloads and remains replay-safe.

### AC-21 Existing paths do not regress
Commit-bearing public bootstrap, Python acceptance, OT Time .NET source-only acceptance, ordinary lineage and GitHub delivery remain green.

### AC-22 Source-only independence
Greenfield support does not add Vercel application-delivery dependency to source-only mode.

### AC-23 REVIEW ceiling preserved
Greenfield publication ends at REVIEW and cannot approve work, promote production or complete REVIEW.

### AC-24 No benchmark backdoor
Runtime/provider/client code does not inspect Decision Ledger identity, `sickbeard`, benchmark tokens or expected solution content.

### AC-25 Temporary diagnostics removed
Authorization probe/preview marker and temporary qualification/focused workflows are absent from final PR; negative capability evidence remains governance evidence only.

### AC-26 Provider constraints recorded honestly
Release record states workload-OIDC consent initiation was not proven and GitHub REST cannot create a ref in an empty repository; neither is represented as a deployed capability.

### AC-27 Canonical W9 replay
After explicit exact-repository consent, canonical Decision Ledger trial proceeds without out-of-band source edits through positive empty proof, greenfield root, accepted source, protected BUILD/TEST/VERIFY, REVIEW-only REST baseline, bounded branch/PR, Vercel Preview and REVIEW.

### AC-28 Failure remains evidence
Any newly exposed consent/inspection/initialization/delivery/Preview boundary is recorded and separately governed rather than weakening gates.

### AC-29 Authentic DSPy and exact-head release gates
This amended exact spec obtains authentic DSPy SpecCritic + SpecCompiler evidence before provider/delivery semantic implementation. Final exact head passes protected spec validation, focused/full API tests, applicable client/browser acceptance, Bounded Autonomy, protected promotion and release gates before merge/deployment.
