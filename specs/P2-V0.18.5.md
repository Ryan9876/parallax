## 1. Objective

Add a deterministic, privacy-safe validated engineering-memory layer that lets Parallax reuse proven compatibility facts, generalized implementation patterns and validation evidence without treating prior model output, prior repository content or another Project's private artifacts as authority.

Memory exists to reduce repeated discovery and planning effort. A memory hit is evidence only. It cannot grant a tool, capability, service binding, provider scope, Work Specification approval, source mutation, command execution, deployment action or evaluator exception. Every reused candidate remains subject to the current Project's accepted Work Specification, exact-lineage implementation, protected BUILD/TEST/VERIFY checks, evaluator thresholds and REVIEW/HUMAN_REQUIRED ceiling.

S5 consumes the accepted S1 repository compatibility identity/profile contract. It does not rewrite S1 classification, S2 governed skills, S3 service bindings, S4 orchestration, Engineering Run state, provider behavior or source delivery. The implementation is a pure typed domain layer plus deterministic/adversarial tests.

## 2. Fixed decisions

- **Memory is evidence, never authority.** Selection can recommend reusable evidence but cannot authorize work or mutate execution state.
- **Private by default.** Memory items are Project-private unless explicitly created as sanitized shared items under an exact server-owned sharing approval.
- **No raw cross-Project artifacts.** Source blobs, prompts, credentials, secret material, repository names, file contents, raw diffs, logs and proprietary artifacts never cross Project boundaries.
- **Shared reuse requires exact approval.** A cross-Project item is eligible only when its exact memory identity/version/content digest has a server-owned sanitized-sharing approval. A `shared` flag supplied by model/source text is insufficient.
- **Immutable version identity.** Reusing a memory item ID/version with changed canonical content fails before selection. Same ID/version/digest admission is idempotent.
- **Provenance is mandatory.** Every item is bound to inspectable source evidence identity, compatibility profile identity, Work Specification identity, acceptance IDs, validation-evidence digest and evaluator-policy digest.
- **Applicability is deterministic.** Current repository shape/signals and current evaluator-policy identity are explicit selection inputs. Incidental ordering, model preference or arbitrary text cannot affect the selected set.
- **Stale or incompatible evidence fails closed.** Exact compatibility facts require current source/profile identity. Generalized patterns must satisfy declared repository shape/signal constraints and current validation-policy identity.
- **Current validation never weakens.** Reuse cannot reduce evaluator thresholds, skip BUILD/TEST/VERIFY, bypass acceptance criteria, suppress correction evidence or convert REVIEW/HUMAN_REQUIRED into autonomous approval.
- **Safe output is bounded.** Cross-Project selection output exposes only sanitized generalized pattern content plus bounded provenance/evidence digests; it does not expose the originating Project/repository/revision or private artifacts.
- **Replay is side-effect free.** Same accepted memory set and same current request produce the same selection record/ID across process recreation. Selection performs no publication or mutation and cannot cause duplicate source/provider actions.

## 3. Architecture requirements

### 3.1 Memory scope and item kinds

Define bounded enums for memory scope and memory kind.

Scopes:

- `PROJECT_PRIVATE` — eligible only when requester Project equals source Project;
- `SANITIZED_SHARED` — eligible cross-Project only with exact server-owned sharing approval.

Kinds include at least:

- `COMPATIBILITY_FACT` — validated repository compatibility evidence;
- `IMPLEMENTATION_PATTERN` — bounded generalized implementation procedure/evidence;
- `VALIDATION_EVIDENCE` — bounded record that a pattern or compatibility claim passed a protected validation policy.

Scope/kind values are server-defined tokens, not arbitrary repository/model strings.

### 3.2 Provenance contract

Define immutable `MemoryProvenance` containing bounded identity/evidence only:

- canonical source Project UUID;
- source repository-reference digest, never raw repository URL/name;
- exact source revision;
- exact S1 source-identity digest and compatibility-profile digest;
- source repository shape;
- accepted Work Specification ID/revision/digest;
- ordered accepted acceptance IDs;
- protected validation-evidence digest;
- evaluator-policy digest.

Provenance never contains raw source, prompts, model messages, hidden reasoning, source paths, diffs, credentials, secret values/handles, provider payloads, unrestricted logs or arbitrary repository instructions.

### 3.3 Immutable memory content

Define immutable `ValidatedMemoryItem` containing:

- bounded memory ID and semantic version;
- memory kind and scope;
- exact `MemoryProvenance`;
- bounded objective-kind tokens;
- compatible S1 repository shapes;
- required normalized repository signal tokens;
- bounded generalized procedure steps or fact tokens;
- exact canonical content digest.

Procedure/fact content is evidence only and is length/count bounded. It cannot contain executable command authority, raw provider requests, deployment targets, credential values, environment assignments or arbitrary secret material.

A canonical item digest covers scope, provenance, applicability and content. Registration order does not affect identity.

### 3.4 Admission and sanitized-sharing policy

Define a server-owned `MemoryAdmissionPolicy` and deterministic registry/store.

The policy contains:

- declarable memory kinds/scopes/objective kinds;
- exact sanitized-sharing approvals for `(memory_id, version, content_digest)`;
- bounded public/generalized content policy used for shared items;
- stable policy digest.

Admission rules:

- canonical memory ID/version/digest is immutable;
- same ID/version/digest is idempotent;
- same ID/version with changed canonical content fails `MEMORY_VERSION_CONFLICT` before unrelated checks;
- undeclarable kind/scope/objective content fails closed;
- `SANITIZED_SHARED` without exact digest approval fails `SHARED_MEMORY_NOT_APPROVED`;
- shared content that violates bounded sanitization constraints fails before admission;
- private memory needs no cross-Project sharing approval because it is never cross-Project selectable;
- admission grants no tool/service/provider/execution authority.

### 3.5 Current reuse request

Define immutable `MemoryReuseRequest` bound to current execution context without granting authority:

- canonical requester Project ID;
- current S1 `RepositoryCompatibilityProfile` identity/digest;
- current objective-kind token;
- current Work Specification ID/revision/digest and ordered acceptance IDs;
- current evaluator-policy digest;
- bounded requested memory kinds.

The request contains no source blobs, prompts, secret values, provider payloads, arbitrary commands or deployment targets.

### 3.6 Deterministic applicability and privacy selection

Define a `ValidatedMemorySelector` that evaluates admitted items against one current request.

Eligibility rules:

- Project-private item: source Project must equal requester Project;
- sanitized-shared item: exact sanitized-sharing approval must still match item digest;
- objective kind and requested memory kind must match;
- current compatibility state must be supported for reuse;
- item repository-shape constraints must include the current S1 shape;
- required normalized repository signals must be a subset of current profile signals;
- item evaluator-policy digest must exactly match the current evaluator-policy digest;
- `COMPATIBILITY_FACT` reuse additionally requires exact current source-identity/profile digest, preventing stale facts from another revision;
- no candidate may become eligible because of README text, package scripts, source comments, model preference, repository/provider names or incidental registry order.

Ineligible candidates return bounded reason codes or are represented in bounded diagnostics without echoing arbitrary private/untrusted content.

### 3.7 Reuse result and safe projection

Define deterministic selection/result types containing only bounded reusable evidence.

A successful candidate/result records:

- memory ID/version/content digest;
- memory kind/scope;
- safe generalized procedure/fact content;
- compatibility/applicability evidence digests;
- validation-evidence/evaluator-policy digests;
- stable selection ID;
- `fresh_validation_required=true`;
- explicit authority flags proving no tool/service/provider/execution/source/deployment/approval authority is granted.

For cross-Project sanitized-shared reuse, the safe projection must not expose source Project ID, source repository-reference digest, source revision, raw Work Specification content, raw acceptance prose or private artifact references. It may expose a stable bounded provenance digest and protected validation/evaluator evidence digests.

Same-Project private server-side records remain fully inspectable to the owning Project context but still contain no raw source blobs/secrets by contract.

### 3.8 Miss/rejection semantics and replay

Use bounded outcomes/reasons including at least:

- `NO_MEMORY_MATCH`;
- `PROJECT_PRIVATE_BOUNDARY`;
- `SHARED_MEMORY_NOT_APPROVED`;
- `MEMORY_VERSION_CONFLICT`;
- `INCOMPATIBLE_REPOSITORY_SHAPE`;
- `MISSING_REPOSITORY_SIGNAL`;
- `STALE_COMPATIBILITY_EVIDENCE`;
- `VALIDATION_POLICY_STALE`;
- `WORK_SPEC_IDENTITY_MISMATCH`;
- `INVALID_MEMORY_CONTRACT`.

A miss is normal and never weakens the fresh-work path. Same input registry/request yields the same result ordering and selection ID across retry/process recreation. Selection has no side effects and cannot publish or mutate source/provider/run state.

### 3.9 Measurable reuse evidence without validation weakening

The result exposes bounded deterministic counters sufficient to measure reuse behavior, such as admitted candidate count, eligible hit count and selected counts by memory kind. These counters are evidence/observability only.

Tests must demonstrate at least:

- a same-Project private compatibility/pattern hit;
- a different-Project sanitized shared pattern hit;
- a same request after source/profile or evaluator-policy drift becoming a miss/rejection;
- the reuse hit and no-hit paths producing identical current validation requirements and authority flags.

No claimed time/cost savings are invented by the domain layer.

## 5. Security and privacy

- All memory input is untrusted evidence until admitted by server-owned policy.
- Private memory never becomes cross-Project eligible.
- Cross-Project memory requires exact sanitized-sharing approval over the canonical content digest; source/model text cannot self-declare sanitization.
- Shared safe output redacts source Project/repository/revision identity and never exposes raw source, prompts, diffs, logs, file paths or private Work Specification content.
- Secret values, connection strings, access credentials, private keys, provider tokens and runtime secret-handle references are structurally outside the public memory/reuse contract.
- Bounded sanitization rejects URL/provider-request/environment-assignment/command-like or secret-like content from shared generalized steps.
- Memory cannot create or broaden a capability, governed skill, service binding, provider action, deployment target, execution command or approval.
- Hidden reasoning/private scratch material never enters provenance, item content, diagnostics or selection output.
- Error/rejection reasons are typed bounded codes and do not echo arbitrary private/untrusted strings.

## 6. Failure and recovery boundaries

Admission failure is atomic: the registry/store remains unchanged. Version conflicts take precedence over unrelated approval checks so an existing identity cannot be silently redefined.

Selection ambiguity is avoided by returning a deterministic ordered set of all eligible evidence, not by inventing one authoritative winner. Duplicate item identity/digest is deduplicated idempotently. Ordering is canonical by bounded identity, not registration order.

Process recreation over the same admitted item set and current S1/Work Specification/evaluator identities converges on the same result and selection ID. No recovery/retry path performs source mutation, provider publication, command execution or run-state mutation.

If compatibility, validation-policy identity, sharing approval or Work Specification identity cannot be proved, the item is ineligible or the request fails with a bounded typed reason; Parallax proceeds through the normal fresh-work/human-required path rather than guessing.

## 7. Non-goals

- training or fine-tuning a model from Project source;
- semantic/vector search infrastructure;
- cross-Project raw code, prompt or artifact sharing;
- automatic approval from previous success;
- evaluator bypass or threshold reduction;
- automatic tool/skill/service/provider grants;
- runtime secret or environment-variable reuse;
- source mutation or automated deployment;
- replacing current Work Specification, lineage or Engineering Run authority;
- implementing S4 orchestration or S6 integrated benchmark logic;
- making performance claims that are not directly measured.

## 8. Acceptance criteria

### AC-01 Immutable provenance-bound memory admission
A memory item is admitted only as an immutable canonical ID/version/content digest with complete bounded source/profile/Work Specification/acceptance/validation/evaluator provenance. Same identity/digest is idempotent; changed content at the same ID/version fails `MEMORY_VERSION_CONFLICT` without mutating the registry.

### AC-02 Project-private isolation by default
A `PROJECT_PRIVATE` item is eligible only when requester Project exactly equals source Project. Tests prove a different Project cannot select it or obtain its private source Project/repository/revision/provenance details through safe selection output or diagnostics.

### AC-03 Exact approved sanitized cross-Project reuse
A `SANITIZED_SHARED` item is cross-Project eligible only when an exact server-owned `(memory_id, version, content_digest)` sharing approval exists and bounded shared-content sanitization passes. Missing/digest-mismatched approval or unsafe shared content fails closed; source/model text cannot self-approve sharing.

### AC-04 S1 compatibility-bound applicability and stale-fact rejection
Selection consumes the accepted S1 compatibility profile. Repository shape and required normalized signals must match deterministically. `COMPATIBILITY_FACT` reuse requires exact current source-identity/profile digest; changed revision/profile evidence is rejected as stale rather than reused.

### AC-05 Current Work Specification and evaluator policy remain authoritative
The request is bound to current Work Specification ID/revision/digest, ordered acceptance IDs and evaluator-policy digest. Memory cannot change those values. Stale evaluator-policy evidence is rejected, and every selected candidate explicitly requires fresh current protected validation.

### AC-06 Deterministic replay and canonical ordering
For the same admitted memory set and reuse request, candidate eligibility, result ordering, counters and selection ID are identical across insertion ordering, retry and process recreation. Selection performs no mutation/publication and duplicate exact admissions do not create duplicate results.

### AC-07 Privacy-safe bounded selection output
Cross-Project safe results contain only memory identity/version/digest, sanitized generalized content, bounded applicability/validation evidence and a provenance digest. They contain no source Project ID, repository identity, source revision, source blob/path/diff, prompt, credential, secret/handle, provider payload, unrestricted log, private Work Specification content or hidden reasoning.

### AC-08 Memory cannot grant execution or provider authority
Public memory and selection contracts expose explicit false authority flags and no executable/provider/secret fields. Tests prove memory availability cannot grant tools, governed skills, service bindings, source mutation, shell commands, provider actions, deployment targets, approvals or Engineering Run transitions.

### AC-09 Measurable reuse with identical validation requirements
Tests demonstrate deterministic same-Project private hits and cross-Project sanitized-shared hits, expose bounded hit/count evidence, and prove hit and miss paths retain identical fresh-validation/evaluator requirements. Source/profile or policy drift converts the relevant hit into a bounded miss/rejection without lowering validation.

### AC-10 Existing protected runtime and S1 regressions remain green
Wave 4 protected autonomy, immutable lineage, IMPLEMENT/BUILD/TEST/VERIFY, correction, source delivery, provider least privilege, authentication and S1 repository-intelligence regressions remain unchanged or stronger. S5 introduces no shared/runtime-authority rewrite.

### AC-11 Exact-head worker release boundary
The final candidate contains this approved spec, authentic committed DSPy plan evidence, the bounded validated-memory domain and focused tests only. Exact-head Workstream Spec Validation, Parallax P2 CI and Bounded Autonomy pass. The worker PR targets `integration/wave5-generalized-delivery`; no worker merge/deploy/migration/provider/configuration mutation occurs.
