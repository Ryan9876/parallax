# Parallax 2.0 v0.6.2 — Session-Safe Private Access Specification

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.6.2
Depends on: P2-V0.5.0
Method: Spec-first implementation + protected verification

## 1. Objective

Remove the production bearer credential from browser persistence while preserving Parallax's existing private single-operator access model, authenticated API contracts, conversation persistence, Reason/Code behavior, and calm conversation-first interface.

The operator may still enter the private credential to unlock Parallax, but after successful verification the credential must be discarded by client JavaScript. The API issues a short-lived, signed, HttpOnly session cookie that can authorize subsequent protected requests without placing the production credential in browser storage or the web artifact.

## 2. User outcome

An authorized operator can unlock Parallax once per browser session, refresh the application, resume durable conversations, and use Reason and Code without repeatedly handling the production credential. An invalid or expired session returns the client to the existing private-access screen. The production credential never persists in `localStorage`, `sessionStorage`, URLs, response bodies, traces, or diagnostic UI.

## 3. Fixed decisions

- P2 remains private and single-operator. Public signup, user accounts, organizations, and multi-tenant identity remain non-goals.
- `PARALLAX_ACCESS_TOKEN` remains the server-owned root access secret and keeps the existing minimum-length and constant-time bearer validation requirements.
- Existing bearer authentication remains supported for Swagger, automated verification, and non-browser clients.
- Browser unlock exchanges a valid bearer credential for a signed, short-lived HttpOnly cookie; the server does not persist session rows.
- The session cookie contains no bearer credential and is authenticated with an HMAC derived from the configured access secret.
- Production cookies are `Secure`, `HttpOnly`, host-only, and `SameSite=None` so the dedicated web and API Vercel origins can interoperate.
- Cookie-authenticated protected requests require a dedicated `X-Parallax-Session: 1` header. This forces CORS preflight and prevents ambient-cookie authorization from becoming a silent cross-site request path.
- CORS remains credential-enabled and must allow only the dedicated web origin or a narrowly scoped approved preview-host regex.
- The client does not write the production credential to browser storage. The credential exists only in the access input/in-memory unlock call and is cleared immediately after successful session establishment.
- Existing Reason, Code, persistence, evaluation, and visual contracts are unchanged.
- The durable conversation reasoning specification identity remains `P2-V0.5.0` for this release because v0.6.2 changes the access/session envelope, not the Reason/Code objective contract.

## 4. Scope

### 4.1 Server session primitive

Add a small session module that can:

- issue a signed token with an absolute expiration;
- validate signature and expiration in constant time;
- expose no configured secret in the cookie value;
- use only standard-library cryptography primitives (`hmac`, `hashlib`, `secrets`/time encoding as needed).

A valid browser session is bounded in duration and can be revoked immediately by rotating `PARALLAX_ACCESS_TOKEN`.

### 4.2 Session endpoints

Add:

- `POST /v1/session` — requires a valid bearer credential, issues the HttpOnly cookie, returns only safe session metadata;
- `GET /v1/session` — validates bearer or cookie session and returns authenticated status;
- `DELETE /v1/session` — clears the cookie without requiring durable server state.

The session endpoints never return the bearer credential, cookie signature, or other secret material.

### 4.3 Protected route authentication

Extend the existing `require_access` dependency:

1. valid bearer credential continues to authorize;
2. otherwise a valid signed session cookie plus `X-Parallax-Session: 1` authorizes;
3. missing/invalid/expired authorization returns the existing sanitized `401` contract.

Operational probes remain public.

### 4.4 Client access flow

Update the Expo API client so all protected requests use `credentials: 'include'` and the session marker header. Add explicit helpers to establish, inspect, and end a browser session.

Update the application shell so:

- initial load checks the existing HttpOnly session instead of reading `sessionStorage`;
- unlock posts the entered credential once and clears the input on success;
- no production credential is written to `sessionStorage` or `localStorage`;
- `401` clears only client authenticated state and returns to the private-access screen;
- existing conversation, SSE, Reason, Code, Skia, reduced-motion, and draft behavior remains intact.

### 4.5 Verification

Add protected tests covering:

- bearer access still succeeds;
- missing/invalid bearer still returns sanitized `401`;
- valid bearer can establish a session;
- issued cookie is HttpOnly and production-secure;
- cookie alone is insufficient without the session marker header;
- signed cookie + marker authorizes protected routes;
- tampered and expired cookies fail;
- logout clears the cookie;
- no response contains the configured bearer credential.

Client typecheck/export must continue to pass after removing persistent-token logic.

## 5. Architecture review findings

A focused architecture review against production-agent concerns found that Parallax already has strong durable state, protected evaluation, human-control, explicit failure-state, and observable-trace boundaries. This change should therefore remain narrow.

Material findings addressed here:

- **State contract:** authentication state should be explicit and recoverable rather than inferred from a JavaScript-stored credential.
- **Tool/credential trust:** the root bearer credential should not become general client state once identity has been established.
- **Human control:** session establishment remains an explicit operator action; no background privilege elevation is introduced.
- **Observability:** session failures retain the same sanitized `401` contract and must not add secret-bearing logs.
- **Safety:** ambient cookies require a preflight-forcing marker header and strict CORS rather than relying on cookie flags alone.

No multi-agent rewrite, new identity provider, new database table, or autonomous security policy is justified for this single-operator release.

## 6. Acceptance criteria

### AC-01 No browser-persisted root credential

Production access credential is absent from localStorage, sessionStorage, URLs, bundles, response bodies, and diagnostic UI after unlock.

### AC-02 Bearer compatibility

Existing bearer-authenticated API and Swagger use remains functional.

### AC-03 Session establishment

A valid bearer credential can establish a signed HttpOnly browser session without server-side session persistence.

### AC-04 Session authorization

A valid signed session cookie plus the required session marker header authorizes protected routes.

### AC-05 CSRF-resistant cookie path

Cookie-only protected requests without `X-Parallax-Session: 1` fail with sanitized `401`.

### AC-06 Tamper and expiry resistance

Tampered, malformed, and expired session values are rejected without revealing validation details.

### AC-07 Clean recovery

Expired/invalid browser sessions return the client to the private-access screen without destroying durable conversations.

### AC-08 Existing product behavior preserved

Reason, Code, conversation persistence, SSE transport, response state machine, Skia/reduced-graphics behavior, and visual design remain unchanged except for the access boundary.

### AC-09 Verification evidence

Backend auth/session tests, client typecheck/export, Vercel preview build, and live `/health` + `/ready` evidence must pass before the release can be called deployment-verified.

## 7. Non-goals

- OAuth/OIDC, social login, password reset, user administration, RBAC, multi-tenant identity, or billing.
- Changing model routing, Reason/Code protected policies, benchmark thresholds, persistence schema, visual language, or product terminology.
- Server-side durable session tables or refresh-token infrastructure.
- Exposing the access secret to the frontend through `EXPO_PUBLIC_*` configuration.
- Broad CORS wildcards.

## 8. Risks and mitigations

- **Cross-site cookie misuse:** require the custom session marker header and strict credentialed CORS.
- **Cookie theft:** use `HttpOnly`, `Secure`, host-only cookies with bounded lifetime; root-secret rotation revokes all sessions.
- **Session forgery:** sign expiration-bound tokens with HMAC-SHA256 and compare signatures in constant time.
- **Client regression:** retain bearer support and existing private-access UI while replacing only the persistence mechanism.
- **Deployment mismatch:** validate on `p2/v0.6.2` preview before production promotion; do not call production deployed until Vercel evidence proves it.

## 9. Release gate

Implementation is authorized by this approved specification. Production promotion requires exact-head validation and live deployment evidence. `CURRENT-STATE.md` must distinguish generated, validated, preview-deployed, production-deployed, and deployment-verified states.
