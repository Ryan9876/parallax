# Parallax 2.0 v0.9.1 — Editorial Optical Amplification

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.9.1
Depends on: P2-V0.9.0
Method: visual refinement + hosted-web reliability correction + release verification

## 1. Objective

Make the deployed Editorial Optical direction visibly unmistakable in the normal conversation shell while preserving Parallax's calm, high-end character. Correct the production-web API fallback condition that can leave the shell displaying sample fallback content even when the same-origin production API is healthy.

## 2. Scope

- Increase the visual presence of the existing violet/indigo ink fields, irregular contour ribbons, cyan focus, and restrained warm editorial accents without turning the product into a neon HUD.
- Strengthen editorial hierarchy in the shell: brand block, top title, conversation reading field, user/assistant framing, composer, and selected controls.
- Keep cream/peach/sage accents selective but actually perceptible in the resting UI.
- Preserve and strengthen Work Specification and Engineering Run editorial surfaces.
- On hosted HTTPS web builds, use the deployed same-origin `/p2-api` route even when `EXPO_PUBLIC_PARALLAX_API_URL` is absent at bundle time.
- Preserve local web development behavior and native direct-API behavior.
- Update release metadata and visual acceptance expectations.

## 3. Non-goals

- No navigation rewrite.
- No authentication redesign.
- No Reason, Code, Work Specification, execution-binding, persistence, database, or deployment-authority changes.
- No new animation framework.
- No external brand copying.
- No high-frequency particles, scanner HUD clutter, or continuous decorative motion.

## 4. Security

- Hosted web requests remain same-origin through `/p2-api`.
- Signed HttpOnly browser sessions and bearer compatibility remain unchanged.
- No credential is placed in public environment variables, local storage, or persistent browser storage.
- The hosted-web route correction may only change transport selection; it may not bypass authentication or weaken the `X-Parallax-Session` contract.
- Local/mock HTTP browser tests must remain able to run without secure production-session assumptions.

## 5. Acceptance criteria

### AC-01 Editorial direction is obvious at rest
A desktop production screenshot must read as Editorial Optical without requiring an active response animation: asymmetric violet/indigo fields, restrained warm accent, authored hierarchy, and non-generic framing are perceptible while copy remains dominant.

### AC-02 Background gains presence without competing with copy
The Skia workplane is materially more visible than v0.9.0, but center reading contrast remains sufficient for narrative text and the field does not become a full-screen saturated gradient.

### AC-03 Shell hierarchy is stronger
Brand, top title, active mode, assistant identity, response surface, and composer have clearly differentiated visual hierarchy rather than a uniformly small utility-interface treatment.

### AC-04 Warm accents are perceptible and restrained
Cream, dusty peach, and sage appear in stable editorial roles but do not displace violet/indigo/cyan as the Parallax identity family or become status-only color semantics.

### AC-05 Work Specification and Code surfaces remain coherent
Existing Work Specification and Engineering Run surfaces keep their governed semantics, Skia editorial traces, approval/binding information, actions, and reduced-graphics parity.

### AC-06 Hosted production web uses same-origin API routing
On an HTTPS hosted web origin, API requests use `/p2-api` even when the compile-time public API base is absent. The production app must not silently fall back to `http://localhost:8010` in this case.

### AC-07 Local and native transports remain intact
Local web development over HTTP may continue using the configured/local API base, and native clients continue using the configured direct API base.

### AC-08 Authentication remains enforced
An unauthenticated hosted-web protected request through `/p2-api` still returns the protected authentication boundary rather than being treated as an offline transport failure or bypassed.

### AC-09 Accessibility remains intact
Selectable final text, keyboard semantics, reduced motion, reduced graphics, and minimum interaction targets remain intact; editorial amplification does not reduce core copy contrast below the established production standard.

### AC-10 Release verification passes
Specification validation, API tests, client typecheck, response-state tests, web export, browser/Skia acceptance, protected Engineering/Reason/Code evaluation, DSPy release compilation, production deployment state, same-origin health/readiness, and runtime-error checks pass before v0.9.1 is recorded as deployment-verified.

## 6. Implementation constraints

- Prefer targeted visual/token/layout changes over component-library replacement.
- Preserve existing component and state architecture.
- Do not add new database migrations.
- Do not change server API contracts.
- Keep visual changes reversible and isolated to the client/design layer except for test/release metadata.

## 7. Risks

- **Visual overcorrection:** stronger Skia amplitudes can compete with text; mitigate with a dark center reading bias and capped saturation.
- **Generic neon appearance:** warm accents and asymmetry must provide editorial character while cyan remains a small active-energy accent.
- **Transport regression:** hosted-web detection could affect local tests; gate same-origin routing specifically on HTTPS hosted web and preserve local HTTP behavior.
- **Fallback masking:** sample fallback content can hide real product surfaces; hosted production should prefer explicit authentication state over accidental offline fallback when the proxy is healthy.

## 8. Release gate

Production promotion requires exact-head full release validation, a READY production web deployment, HTTP 200 from the production root, `/p2-api/health`, and `/p2-api/ready`, the expected unauthenticated protected-route response through the same-origin gateway, and no material runtime error cluster. `CURRENT-STATE.md` must be updated after verified promotion. `DESIGN-SYSTEM.md` should only change if the durable design rules themselves change; this release primarily increases fidelity to the already-authoritative Editorial Optical direction.
