# Parallax 2.0 — Durable Source-Lineage Persistence

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.15.5
Workstream: WS-APP-DURABLE-LINEAGE / GitHub issue #68
Integration base: integration/wave2-app-builder
Depends on: accepted #59 canonical Project/run identity and #60 protected source-lineage semantics
Method: private immutable object persistence plus transactional durable metadata/current-head CAS; local filesystem only for disposable materialization

## 1. Objective

Replace #60's function-local filesystem durability assumption with production-safe durable source-lineage persistence suitable for separate Vercel Function invocations and instances without changing the accepted lineage contract.

Canonical Project/run identity, immutable content addressing, exact reconstruction, stale-parent denial, no-change denial, idempotent retry, bounded evidence and disposable server-owned materialization remain mandatory. `/tmp`, a function-local directory, `workspace_ref`, caller input, model output or provider state must never become authoritative durable lineage state.

## 2. Fixed decisions

- `ProjectRunIdentity` remains the canonical UUID-only Project/run identity contract; `Project.id` and `EngineeringRun.id` are the only integration inputs.
- `workspace_ref` remains opaque metadata and never becomes a storage path, object key or caller-selectable authority.
- Immutable source bytes are persisted behind a narrow content-addressed durable object protocol. The production adapter uses the supported public Vercel Python SDK with private Blob access and server-derived SHA-256 object paths.
- Immutable lineage manifests and the mutable current-lineage head are persisted transactionally through the existing SQLAlchemy/Postgres persistence boundary.
- Current-lineage advancement is governed by persistent expected-current compare-and-swap semantics, not a process-local lock.
- Local filesystem state exists only as a generated disposable materialization lease for source mutation/build/test/verify work. Deleting it cannot delete accepted durable lineage.
- Object writes complete and verify before a lineage manifest/head may become accepted. A partial object write may leave unreferenced immutable content but cannot advance accepted metadata.
- Production storage resources and migrations are not provisioned/applied from this worker.

## 3. Architecture requirements

`SourceLineageStore` must depend on two explicit persistence protocols rather than a filesystem state root:

1. **Immutable object storage** — write-if-absent and read operations addressed only by lowercase SHA-256 content digest. Writes and reads verify the digest. The production Vercel Blob adapter uses private access, deterministic non-random paths, no overwrite, and no model/caller-provided URL or pathname.
2. **Transactional lineage metadata** — immutable canonical manifest bytes keyed by lineage ID plus one durable current-lineage head per canonical Project/run. The production SQLAlchemy/Postgres adapter commits a manifest and advances the head in one transaction with expected-current CAS semantics.

The #60 `SourceLineage` identity calculation and manifest validation remain authoritative. Durable storage adapters do not redefine Project/run identity, source policy, content digests, lineage IDs or protected stage authority.

## 4. Scope

- Add narrow immutable-object and lineage-metadata protocols beneath `SourceLineageStore`.
- Add deterministic in-memory adapters for focused tests/local development that are explicitly injected and independent of local materialization paths.
- Add a private Vercel Blob object adapter using the official `vercel.blob` public API and `BLOB_READ_WRITE_TOKEN`/explicit server token behavior without exposing credentials.
- Add SQLAlchemy metadata tables/adapters for immutable manifests and current-lineage heads plus a forward-only SQL migration.
- Store source bytes only in durable object storage; relational metadata contains bounded manifest JSON/checksum and current-head identity/revision, not source bytes.
- Refactor `SourceLineageStore` so it accepts explicit object/metadata stores and contains no authoritative filesystem state root.
- Refactor `ProjectWorkspaceAllocator` so it requires an explicit `SourceLineageStore`; it may not silently create a local durable store.
- Preserve #60 initialization, mutation, current, resolve, reconstruct/materialize and cleanup behavior at the protected contract boundary.
- Preserve path normalization, secret-sensitive path denial, symlink/special-file denial and resource bounds.
- Verify every object on read and every manifest through checksum, canonical shape, lineage-ID recomputation, identity binding and content digest before use.
- Treat partial object writes as non-accepted orphan content; metadata/head advancement occurs only after all objects are durably verified.
- Preserve exact idempotent replay after process/store recreation while rejecting stale different children.
- Keep evaluation/audit/workspace evidence bounded and free of source bytes, filesystem roots, raw Blob results and credentials.

## 5. Transaction and concurrency rules

For initialization, the durable head advances from absent to the deterministic initial lineage only. Repeating the same initialization is idempotent; a different initialized lineage conflicts.

For implementation mutation, the durable head advances from exactly `expected_parent_lineage_id` to the deterministic child lineage through a conditional persistent update. Two separate API instances using the same expected parent cannot both advance to different children. An exact already-accepted child replay is idempotent even after process recreation; a different child observes the durable winner and fails stale.

The immutable manifest insert and mutable head CAS occur in the same database transaction. A losing CAS rolls back its candidate manifest metadata. Immutable content objects written before a losing/failed transaction may remain unreferenced but do not constitute accepted lineage.

## 6. Security and privacy

- Private Blob access is mandatory for production source objects; public object access is not an accepted implementation.
- Blob object paths are generated from a fixed server prefix and validated SHA-256 digest only; caller/model/provider URLs and arbitrary object names are not accepted.
- Blob reads bypass mutable cache assumptions for integrity checks and verify downloaded bytes against their content address.
- Provider tokens are server-owned configuration and never emitted in lineage, evaluation, audit or UI evidence.
- Postgres manifest rows contain bounded canonical lineage metadata only; no raw source contents, credentials, filesystem roots or provider-private state are persisted there.
- The current-head key is canonical Project ID + Engineering Run ID, never `workspace_ref`.
- Local materialization paths remain generated beneath a protected allocator root and are omitted from returned evidence.
- No shell, Git history mutation, arbitrary HTTP contract, dependency-install authority, provider secret handling by models, Work Specification self-approval, protected-stage success override, production promotion or deployment authority is added.

## 7. Non-goals

- Provisioning a Vercel Blob store, Postgres database/table migration in production, environment secrets or other provider resources.
- Applying the committed migration from this worker.
- Replacing #59 canonical Project/run identity or changing Project/conversation/Engineering Run persistence.
- Weakening or redefining #60 lineage IDs, stale-parent semantics, idempotency, integrity validation, path/resource policy or evidence shape.
- Changing #61 implementation-generation/stage authority semantics.
- Giving #62 provider publication authority to mutate accepted lineage.
- Using `/tmp` or any local directory as authoritative lineage persistence.
- Garbage collection of unreferenced immutable objects; that requires a separate retention design.
- Merge, production deployment or authoritative project-record updates from this worker.

## 8. Acceptance criteria

### AC-01 Canonical identity and authority preservation
Durable lineage accepts the same canonical lowercase UUID Project/run identity as #60. `Project.id` + `EngineeringRun.id` remain the only integration inputs; `project:<id>`, `workspace_ref`, paths, URLs, caller/model storage keys and malformed identity cannot become durable storage authority.

### AC-02 No function-local authoritative durability
`SourceLineageStore` requires explicit durable object and metadata adapters and exposes no filesystem state-root parameter. `ProjectWorkspaceAllocator` requires an explicit lineage store and uses its local protected root only for generated disposable leases; no `/tmp` or other local path is considered accepted durable lineage state.

### AC-03 Private immutable content-addressed objects
Every source file is persisted by SHA-256 through an immutable write-if-absent object contract. The Vercel production adapter uses the public Python SDK with `access="private"`, deterministic digest-derived paths, no random suffix, no overwrite and read-after-write/read-time digest verification. Missing, corrupt or conflicting content fails closed.

### AC-04 Transactional persistent manifest and head CAS
Canonical lineage manifests and the current Project/run lineage head persist in the relational boundary. Manifest insertion and head advancement are transactional. Advancement succeeds only when the durable current lineage exactly equals the expected parent (or is absent for initialization), so separate API invocations/instances cannot accept different children from one parent.

### AC-05 Stale-parent, no-change and replay semantics survive recreation
A different stale child is rejected without changing the accepted head; unchanged source cannot create a lineage; and retrying the exact already-accepted initialization or implementation child returns the existing lineage idempotently after `SourceLineageStore`/allocator process recreation.

### AC-06 Exact reconstruction and integrity remain fail-closed
Any accepted historical/current lineage can be resolved and reconstructed into a fresh disposable workspace using durable manifest metadata and immutable objects. Manifest checksum/shape/identity tampering, identity mismatch, missing/corrupt objects, object size mismatch or reconstructed content-digest mismatch fails before the lineage is used.

### AC-07 Failure atomicity across object and metadata boundaries
A failed or partial durable object write cannot create or advance accepted lineage metadata. A failed/losing metadata CAS cannot advance the durable head and rolls back its unaccepted manifest metadata. Unreferenced immutable objects may remain but are never reported as accepted lineage.

### AC-08 Disposable materialization and cleanup safety
Materialized workspaces remain generated server-owned leases beneath a configured local root, never durable state. Cleanup is idempotent and deletes only the lease; a separate allocator/function instance with a different local root can reconstruct the same accepted lineage from durable storage afterward.

### AC-09 Bounded evidence and no authority expansion
Existing source count/per-file/aggregate/path/provenance bounds remain enforced. Lineage/workspace evidence contains bounded canonical IDs, lineage/content/provenance digests, counts/sizes and generated lease identity only; it contains no source bytes, filesystem roots, provider tokens/raw state, generic shell/Git/HTTP authority, protected-stage self-approval, production-promotion or deployment authority.

### AC-10 Integration-ready production persistence seam
The worker delivers the forward migration, official Vercel Python SDK dependency, durable adapters, refactored #60 store/allocator and focused durability tests without provisioning resources or applying the migration. The exact candidate passes the deterministic workstream-spec gate, full API regression, Parallax P2 CI and Bounded Autonomy Pilot and targets `integration/wave2-app-builder` READY FOR INTEGRATION without merge/deploy.
