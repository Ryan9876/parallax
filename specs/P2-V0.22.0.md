## 1. Objective

Make Parallax answer **“What should I do next?”** explicitly and consistently across desktop and mobile without creating a parallel client lifecycle or changing any server-owned Project, Work Specification, Engineering Run, source, provider, validation, delivery or REVIEW authority.

Wave 8 already established readable mobile progress and plain-language ordinary product copy. The remaining product gap is orientation on desktop: Build plan, Progress, conversation and utility-rail information can all be correct while still requiring the user to infer the next meaningful action. W8-S4 introduces one shared deterministic presentation mapping over existing canonical state and renders it as primary workflow guidance.

## 2. Fixed decisions

- The guidance layer is **presentation only**. It does not own or persist lifecycle state.
- Guidance is derived from freshly available conversation, Work Specification and Engineering Run values already used by the client.
- The mapping is pure and deterministic. Equal canonical inputs produce equal ordinary guidance on desktop and mobile.
- Guidance may expose an action intent only when the caller already has an existing authenticated callback for that action.
- Guidance never performs network requests, transitions lifecycle state, constructs run revisions, invents idempotency keys or bypasses existing hooks.
- Existing Build plan and Progress components remain authoritative detailed surfaces. The new guidance card summarizes rather than replacing their server-bound controls.
- REVIEW remains a human review boundary, not completion, merge or production deployment.
- Failure, pause, cancellation and amendment states outrank generic active-work messaging.
- Raw Project IDs, Work Specification IDs, Engineering Run IDs, provider identities, internal stage names and failure codes remain outside ordinary guidance.
- Technical details, Activity / Live Build and existing canonical inspection surfaces remain available for technical truth.
- Ask mode stays lightweight. It must not fabricate a Build lifecycle merely because the shared mapper exists.

## 3. Canonical inputs and precedence

The mapper may consume only bounded presentation inputs already available to the client:

- mode: Ask (`reason`) or Build (`code`);
- conversation status / response phase where already available;
- current Work Specification, if any;
- current Engineering Run, if any;
- whether a Build plan may be created from the current conversation;
- whether an approved Work Specification exists for amendment recovery;
- whether the existing Engineering Run hook has a recoverable request failure.

Guidance precedence is deterministic:

1. approved-goal amendment / `SPEC_AMENDMENT`;
2. recoverable Engineering Run request failure or canonical `FAILED`;
3. canonical `PAUSED`;
4. canonical `CANCELLED`;
5. canonical `REVIEW`;
6. canonical `COMPLETE`;
7. active Engineering Run stages already accepted by the server;
8. approved Build plan while the run is being activated/loaded;
9. draft Build plan ready for user review;
10. captured Build request for which a Build plan can be created;
11. fresh Build conversation requiring an outcome description;
12. Ask mode ready for conversation.

The mapper may use a run `resume_stage` only to describe what work would resume after a canonical paused/failed state; it may not represent that resume stage as the current canonical state.

## 4. Guidance output contract

The shared mapper returns bounded presentation data such as:

- `kind`: stable presentation category;
- `eyebrow`: short orientation label (`NEXT STEP`, `RIGHT NOW`, `READY FOR YOU`, `NEEDS ATTENTION`);
- `title`: plain-language current/next-action headline;
- `description`: concise explanation of what the state means;
- optional existing action intent;
- optional action label;
- tone metadata for presentation only.

Allowed action intents are presentation references to existing callbacks, not new runtime commands. They may include:

- create/update Build plan through the existing Work Specification hook;
- review Build plan through existing detail/disclosure behavior;
- continue/retry/pause/stop through existing Engineering Run hook callbacks;
- open existing Progress / Activity detail;
- continue approved scope through the existing amendment recovery endpoint/callback;
- start a new conversation/goal through the existing conversation action.

If the current surface does not possess the existing callback needed for a mapped action intent, it renders informative guidance without inventing a substitute action.

## 5. Desktop presentation

Desktop Build conversations render one visually primary guided-workflow card before the detailed Build plan and Progress cards.

The card communicates:

- where the Build is now;
- what that means in ordinary language;
- the next meaningful user action, if one exists.

It must not duplicate technical evidence or pretend to be a second Progress state machine. Detailed Build plan and Progress controls remain below it. At widths where the utility rail is visible, the rail may show a secondary compact `Next` summary derived from the same mapper.

The card is absent or intentionally lightweight in Ask mode so conversational use remains uncluttered.

## 6. Mobile presentation

The existing mobile context card must use the same shared mapper for its ordinary guidance categories/copy rather than maintaining a separate hand-authored lifecycle decision tree.

Mobile keeps its existing stable `Chat · Progress · Project` navigation, full-screen Build plan review, amendment recovery, Progress workspace and technical-detail disclosure behavior.

W8-S4 does not add a second mobile navigation model or another persistent bottom action surface.

## 7. Failure, amendment and review behavior

- Amendment guidance explains that the newer request differs from the approved plan and never implies that Parallax may silently change approved scope.
- Recoverable run failure explains that saved work remains and points only to the existing retry/continue path when allowed.
- Paused work is presented as paused, even when a resume stage exists.
- Cancelled work is presented as stopped and does not offer autonomous continuation unless an existing server-approved control explicitly does so.
- REVIEW is `Ready for your review`; it does not say complete/deployed/shipped.
- COMPLETE may say the protected work is complete while still avoiding any production-deployment implication.
- A generic request/stream error must not overwrite a more consequential canonical amendment/failure/pause/review state.

## 8. Accessibility and responsive requirements

- Primary guidance text is readable at existing Wave 8 typography floors.
- Any guidance CTA has at least 44 CSS px / logical px minimum touch height.
- Controls are keyboard reachable and have explicit accessibility labels.
- State meaning is not color-only.
- Dynamic consequential guidance uses restrained live-region behavior and must not repeatedly announce unchanged state.
- Desktop card reflows without horizontal overflow at supported tablet/desktop widths.
- Mobile retains composer and bottom-navigation clearance.
- Reduced-graphics fallback remains functional and understandable; the shared mapper must not depend on Skia/CanvasKit.

## 9. Security and authority boundaries

The mapper is prohibited from:

- calling APIs directly;
- creating Project, Work Specification or Engineering Run identities;
- deriving or mutating canonical run revision/state;
- accepting source or validation evidence;
- changing provider/model selection;
- creating provider credentials or target identity;
- creating Preview/production deployments;
- merging source;
- approving or completing REVIEW;
- exposing credentials, hidden reasoning, raw provider payloads, raw source/patches or unrestricted logs.

All user-controlled text is untrusted display data and cannot alter guidance precedence or create action authority beyond typed canonical fields.

## 11. Non-goals

- New lifecycle or client state machine.
- New server endpoint or action vocabulary.
- Automatic production deployment, merge or REVIEW approval.
- Reworking Development Studio / Activity technical evidence.

## 12. Acceptance criteria

### AC-01 Shared deterministic mapper
A focused unit/state test proves canonical fixtures map deterministically to one ordinary guidance object and that desktop/mobile consume the shared mapper rather than independent lifecycle decision trees.

### AC-02 Desktop primary orientation
At supported desktop/tablet width, a Build conversation presents one primary guidance card before detailed Build plan and Progress surfaces. The user can identify current position and next meaningful action without using the utility rail.

### AC-03 Fresh Build and plan guidance
Fixtures prove a fresh Build asks for an outcome, a captured request permits `Create build plan`, and a draft Build plan is `Ready for your review` without implying approval.

### AC-04 Active run truthfulness
PLAN/IMPLEMENT/BUILD/TEST/VERIFY server states map to truthful current-work guidance without fabricated percentages, completed steps or client-authored lifecycle transitions.

### AC-05 Failure and pause precedence
Recoverable hook error, canonical FAILED and PAUSED fixtures outrank generic active-stage guidance. Saved work remains explicit and only the existing retry/continue control may be referenced.

### AC-06 Amendment authority preserved
`SPEC_AMENDMENT` guidance outranks plan/run generic states, explains the approved-scope boundary and points only to the existing `Continue approved work` / `Start a new goal` flows.

### AC-07 REVIEW and COMPLETE boundaries
REVIEW is visibly `Ready for your review` and never represented as deployed/finished production work. COMPLETE is distinguishable from REVIEW and grants no deploy/merge shortcut.

### AC-08 Mobile/desktop parity
The same canonical fixtures at desktop and 390px mobile widths produce semantically equivalent guidance category/title/next-action meaning, while retaining platform-appropriate layout.

### AC-09 Utility rail is secondary
When present, the desktop utility rail may summarize `Next` from the shared mapper but absence of the rail at narrower desktop/tablet widths does not remove primary guidance.

### AC-10 Accessibility and reduced-graphics integrity
Focused browser acceptance proves >=44px guidance CTAs, keyboard/accessibility labels, no horizontal overflow and continued understandable behavior when reduced-graphics fallback is active.

### AC-11 Existing authority/regression gates remain green
Existing auth/session, Project binding, Work Specification approval, Engineering Run continuation/amendment, browser/Skia, Live Build, protected promotion/regression rejection and API contract suites pass unchanged in authority semantics.

### AC-12 No authority expansion
Changed-file review confirms no API/database/provider/source-lineage/model/deployment/merge/REVIEW authority is added. Ordinary guidance contains no raw IDs, internal stages, provider names or failure codes.
