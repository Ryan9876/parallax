# Parallax 2.0 — App Project Lifecycle Foundation

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.14.1
Workstream: WS-APP-PROJECT-LIFECYCLE / GitHub issue #43
Depends on: P2-V0.14.0 parallel-development foundation and the app-builder program contract in issue #32
Method: additive spec-first durable Project/App identity with owner-scoped persistence

## 1. Objective

Give Parallax a durable first-class Project/App boundary so it can create, identify, list, read, and later resume multiple isolated application workspaces instead of implicitly treating the Parallax repository itself as the only engineering workspace.

The first slice establishes the canonical Project identity and persistence contract that later Work Specification, Engineering Run, safe implementation, tool authority, evaluation, UX, and deployment work must consume rather than inventing competing durable project identifiers.

## 2. Fixed decisions

- A Project is the canonical durable identity for one application-building workspace.
- The Project primary key is a server-generated UUID string and never derives from a filesystem path, repository URL, conversation ID, or user-supplied identifier.
- Every Project is owned by the authenticated `AccessPrincipal.subject`; owner scope is part of every repository read/list/create operation.
- `workspace_ref` is an immutable server-generated opaque reference in the form `project:<project-id>`. It is an identity seam only, not a filesystem path and not execution authority.
- `repository_ref` is optional and provider-neutral. When present it is normalized as `provider:owner/name`; it contains no URL, credential, branch, token, command, or network authority.
- Project creation accepts a bounded name, optional slug, optional description, and optional repository reference. Slugs are stable within an owner and are not used as authorization authority.
- This slice exposes protected create/list/read API operations only. Mutation, deletion, repository discovery, source implementation, tools, deployment, and frontend project management remain separate work.

## 3. Architecture requirements

Implement the lifecycle as an additive `parallax_api.projects` package containing its SQLAlchemy model, Pydantic request/read contracts, owner-scoped repository, service, and FastAPI router. Keep the canonical Project model outside the existing shared `models.py` so the worker does not create unnecessary collision pressure; importing the projects router must register the model with the existing SQLAlchemy `Base` before optional development/test schema creation runs.

Persist Projects in a dedicated `projects` table with owner-scoped uniqueness for slug and non-null repository reference. The repository must fail closed on owner scope: a Project owned by another principal is indistinguishable from a missing Project through the public read operation. The API must use the existing access principal and global protected-router boundary; it must not create a second authentication system.

Add a forward SQL migration for production integration, while focused tests use the existing SQLite test pattern and `Base.metadata.create_all` to prove durable behavior without requiring provider mutation.

## 4. Scope

- Add canonical Project/App persistence with stable UUID identity, owner subject, slug, optional description, optional repository reference, opaque workspace reference, lifecycle status, and timestamps.
- Add strict normalization and validation for project slugs and provider-neutral repository references.
- Add an owner-scoped repository with deterministic create, list, and read behavior.
- Add a lifecycle service that maps duplicate owner-scoped identities to explicit conflicts and missing/cross-owner reads to not-found behavior.
- Add protected API endpoints: `POST /v1/projects`, `GET /v1/projects`, and `GET /v1/projects/{project_id}`.
- Register only the new projects router in the shared API composition root.
- Add a forward project-table migration with owner-scoped uniqueness and query indexes.
- Add focused persistence, isolation, validation, conflict, and API tests.
- Add integration notes through the workstream issue/PR for later binding of Work Specifications, Engineering Runs, safe implementation, project-scoped tools, evaluation, UX, and deployment.

## 5. Security

Project identity is an authorization boundary precursor, not a convenience label.

- Every create/list/read operation receives the server-resolved `AccessPrincipal.subject`; callers cannot supply or override `owner_subject`.
- Cross-owner reads return not found so the API does not disclose another principal's Project existence or metadata.
- Project IDs and workspace references are server generated. User/model input cannot supply an absolute path, relative path, shell fragment, Git command, URL credential, access token, secret, or deployment target through these fields.
- Repository references are metadata only and use a bounded provider/owner/name identity. This release performs no repository lookup, clone, fetch, push, merge, HTTP request, provider call, or secret resolution.
- `workspace_ref` is deliberately opaque and must not be interpreted as a local path until a later protected workspace allocator binds it under an isolated execution boundary.
- Database uniqueness reinforces owner isolation, but application queries must still include owner scope; uniqueness is not a substitute for authorization.
- This workstream adds no new production credential, privileged database operation, tool authority, arbitrary shell/network capability, Git mutation, or deployment authority.

## 7. Acceptance criteria

### AC-01 Canonical durable Project identity
Creating a Project persists a server-generated UUID Project ID and immutable opaque `workspace_ref` equal to `project:<project-id>`. Neither value is derived from user-supplied paths, repository metadata, conversations, or model output, and both remain stable when the Project is read from a later database session.

### AC-02 Owner-scoped isolation
Every Project repository operation is scoped by the server-resolved owner subject. Listing returns only the caller's Projects, the same slug may exist for different owners, and reading another owner's Project through the public contract returns not found without disclosing its metadata.

### AC-03 Stable repository identity metadata
A Project may persist one optional normalized `repository_ref` in bounded `provider:owner/name` form. The field stores identity metadata only, rejects URLs/credentials/path traversal, and grants no repository lookup, network, Git, secret, implementation, or deployment authority.

### AC-04 Deterministic create/list/read API
Protected API routes expose `POST /v1/projects`, `GET /v1/projects`, and `GET /v1/projects/{project_id}` with typed request/read contracts. Creation returns the persisted Project, listing uses deterministic creation/id ordering, and reads preserve the same canonical identity and metadata.

### AC-05 Durable persistence and schema contract
The additive SQLAlchemy Project model and forward migration define the same durable fields and owner-scoped uniqueness constraints. Focused SQLite tests prove records survive session boundaries, while the migration is committed as integration evidence and is not claimed applied or deployed by this worker.

### AC-06 Validation and conflict semantics
Project names, slugs, descriptions, and repository references are explicitly bounded and normalized before persistence. Invalid request shapes fail validation, duplicate owner/slug or duplicate non-null owner/repository identity fails as conflict, and a missing Project fails as not found without partial state mutation.

### AC-07 Opaque workspace boundary without authority expansion
`workspace_ref` is a stable opaque identity seam only. No code in this slice interprets it as a filesystem path, creates directories, executes commands, invokes Vercel Sandbox, mutates Git, calls provider APIs, grants protected stage authority, or performs deployment.

### AC-08 Integration-safe canonical contract
The first slice remains additive except for protected router registration and does not modify shared `models.py`/`schemas.py`, Work Specification or Engineering Run persistence, Code/autonomy internals, tool-authority contracts, app-builder evaluation contracts, client UI, deployment workflows, or authoritative product-state records. Later integration must consume this accepted Project ID rather than invent a competing durable identifier.

### AC-09 Focused regression and isolation evidence
Focused tests cover create/list/read behavior, persistence across sessions, stable workspace identity, same-owner conflicts, cross-owner slug independence, cross-owner read/list isolation, repository-reference validation, and protected API behavior. The full API regression and Python compile checks must also pass on the worker candidate.

### AC-10 Worker release boundary
The completed candidate includes the approved `P2-V0.14.1` specification, committed compiled-plan evidence, exact validation results, and a pull request from `ws/app-project-lifecycle` to `main`. The worker does not merge, apply the production migration, promote a Vercel deployment, or mark the implementation deployed/deployment-verified; final integration remains serialized through the Control Tower.

## 8. Risks

- **Principal identity evolution:** development, break-glass, and Google-backed principals have different subject sources. Mitigation: treat `AccessPrincipal.subject` as the existing opaque ownership contract and defer membership/identity migration until a dedicated authorization design requires it.
- **Repository rename or transfer:** a stored provider/owner/name reference can become stale. Mitigation: treat it as optional metadata, never as the Project primary key; later provider synchronization may update repository metadata without replacing canonical Project identity.
- **Workspace reference misuse:** later code could mistake `project:<id>` for a filesystem path. Mitigation: name and test it as an opaque reference and require a later protected workspace allocator to map Project identity to an isolated execution resource.
- **Migration/integration sequencing:** the model can be validated locally before the production table exists. Mitigation: commit the forward migration but state clearly that it is generated/validated only; Integration applies deployment changes only after serialized acceptance.
- **Premature coupling pressure:** other Wave 1 workstreams need a Project seam. Mitigation: keep this contract small and stable, publish integration notes, and let #44/#45/#46 reconcile to the accepted ID during Control Tower integration rather than expanding this worker's scope.
