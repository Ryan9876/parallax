## 1. Objective

Introduce first-class governed, versioned skill contracts that let Parallax reuse engineering procedures without turning skill text, repository content, model preference or prior output into tool authority.

A skill may describe a bounded reusable procedure, typed input/output fields, repository compatibility requirements, evidence requirements and capability prerequisites. Portable skill content is non-authoritative until admitted by a server-owned registry against an exact approved content digest and a server-owned capability policy. Admission does not itself grant tools or credentials. Selection may prove that prerequisites are already available under current policy, but cannot create or broaden them.

The runtime added here is a deterministic domain contract, not a generic plugin executor. It records exact skill identity/version/digest, Project/run identity, compatibility profile identity, capability-policy identity and bounded outcome evidence. Existing Work Specification acceptance, immutable lineage, protected execution, evaluator thresholds, provider scope and REVIEW/HUMAN_REQUIRED remain authoritative.

## 2. Fixed decisions

- **Exact-digest admission.** A portable skill enters the registry only when its canonical content digest is explicitly approved by server-owned admission policy for that exact skill ID/version.
- **Skills never grant authority.** Required capabilities are prerequisites checked against an already-authorized server-owned capability snapshot. A skill cannot create capability handles, commands, provider actions, credentials, filesystem/network access, service bindings, deployment scope or approvals.
- **No generic executable plugin surface.** Skill procedures are bounded guidance/schema metadata only. This workstream adds no dynamic code loading, shell execution, package installation, arbitrary tool calls or arbitrary provider invocation.
- **S1 compatibility is authoritative repository evidence.** Skill selection consumes only accepted `RepositoryCompatibilityProfile` facts. It may not rescan raw repository content or infer authority from package scripts/README/source text.
- **Deterministic selection.** Objective, compatibility facts, registered skill metadata and capability snapshot determine eligibility. Model preference cannot break ties. Material top-rank ambiguity fails closed to a typed human-required outcome.
- **Immutable version identity.** One skill ID/version maps to one canonical digest. Re-admitting the same digest is idempotent; a different digest for the same ID/version is rejected.
- **Bounded portable content.** IDs, versions, procedure steps, fields, evidence requirements and capability IDs have strict count/byte/format limits before hashing/admission.
- **Bounded invocation evidence only.** Invocation records contain digests, typed status/codes and bounded opaque references—not raw source, prompts, credentials, logs, chain-of-thought or unrestricted model output.
- **Project privacy remains strict.** Portable skills cannot embed Project/run identity or private source as reusable state; invocation records are Project/run-bound and cannot be replayed under another Project/run.
- **Existing protected runtime remains unchanged.** Engineering Run, Work Specification, lineage, execution, validation/evaluation, provider delivery and REVIEW/HUMAN_REQUIRED remain the single execution truth.

## 3. Architecture requirements

### 3.1 Portable skill contract

Add a pure domain module under `services/api/parallax_api/code/` defining a canonical portable skill contract with bounded fields including:

- stable `skill_id` using a server-safe identifier format;
- semantic version;
- bounded ordered procedure steps;
- typed ordered input/output field descriptors;
- one or more objective kinds the skill can serve;
- optional accepted repository shapes and required S1 signal pairs;
- ordered required capability IDs;
- ordered evidence-requirement IDs;
- deterministic canonical digest.

The portable contract contains no executable code, provider request, secret value, environment mutation, command line, network target or approval token. Procedure text is metadata/guidance only and becomes registry-visible only after exact-digest admission.

### 3.2 Server-owned admission policy and registry

Define a server-owned admission policy containing:

- exact approved `(skill_id, version) -> content_digest` mappings;
- the capability IDs skills are permitted to declare as prerequisites;
- a deterministic policy digest.

`SkillRegistry.admit()` validates the complete portable contract, recomputes its canonical digest and requires exact match to the approved mapping. Required capability IDs must be a subset of the admission policy's declarable capability set.

The registry stores immutable `RegisteredSkill` records only. Exact same skill/version/digest admission is idempotent. Same skill/version with another digest fails closed. Unapproved content, malformed contracts, undeclared capabilities and oversized content fail closed with typed errors.

Admission means only “this reusable skill contract is approved for selection.” It does not authorize or execute its prerequisites.

### 3.3 Capability snapshot

Define a narrow immutable `CapabilitySnapshot` representing capability IDs already available to the current protected orchestration context plus a server-owned policy digest.

Skill selection may check `required_capabilities ⊆ capability_snapshot.capability_ids`. It must not mutate the snapshot or return credential/tool/provider handles. Missing prerequisites produce a typed no-selection/human-required reason.

Capability IDs are opaque server-owned identifiers. Skills cannot create new IDs from procedure text or repository data.

### 3.4 Deterministic skill selection

Define a deterministic selector consuming:

- one accepted registered-skill registry;
- one accepted S1 `RepositoryCompatibilityProfile`;
- one objective kind;
- one server-owned capability snapshot.

Eligibility requires:

- repository compatibility state is supported for normal autonomous selection;
- objective kind matches;
- declared repository shapes include the current shape or are explicitly shape-agnostic;
- every required S1 signal pair is present;
- every required capability is already available.

Selection ordering must be deterministic and server-owned. Use bounded contract specificity/priority metadata only if explicitly represented in the skill contract. Model output, registration order and dictionary iteration order cannot decide ties.

If no candidate matches, return a typed `NO_MATCHING_SKILL`/human-required result. If otherwise-equivalent top candidates remain, return `AMBIGUOUS_SKILL_SELECTION` rather than guessing.

### 3.5 Invocation record

This workstream does not execute skills. It defines a replay-safe bounded record for a skill invocation performed by later protected orchestration/execution layers.

A `SkillInvocationRecord` must bind:

- canonical Project/run UUIDs;
- registered skill ID/version/digest;
- S1 compatibility profile digest and exact source revision;
- capability policy digest and declared prerequisite capability IDs;
- bounded input digest rather than raw input payload;
- bounded ordered outcome evidence items containing typed kind/status plus content digest and optional safe opaque reference;
- final invocation status `SUCCEEDED`, `FAILED` or `HUMAN_REQUIRED`;
- deterministic invocation ID.

Same exact invocation facts reproduce the same invocation ID across retry/process recreation. Different Project/run, skill digest, source/profile, capability policy, input or evidence produce a different identity. No record may contain raw skill procedure text, source content, prompt text, credentials, unrestricted logs or chain-of-thought.

### 3.6 Failure taxonomy

Use typed bounded failure/review reasons including at least:

- `SKILL_NOT_APPROVED`;
- `SKILL_VERSION_CONFLICT`;
- `INVALID_SKILL_CONTRACT`;
- `CAPABILITY_NOT_DECLARABLE`;
- `MISSING_CAPABILITY`;
- `INCOMPATIBLE_REPOSITORY`;
- `NO_MATCHING_SKILL`;
- `AMBIGUOUS_SKILL_SELECTION`;
- `INVOCATION_IDENTITY_MISMATCH`;
- `EVIDENCE_LIMIT_EXCEEDED`.

Errors and selection outcomes must not echo arbitrary procedure/source/model content.

## 5. Security and privacy

- Portable skill content is untrusted until exact-digest admission.
- Skill procedure text cannot create execution authority and is never interpreted by this module as commands/tool calls/provider requests.
- Capability prerequisites are checked against immutable server-owned capability facts only.
- Registry records are digest/version bound and cannot be mutated in place.
- Skill contracts cannot carry Project/run UUIDs, repository source blobs, credentials or provider secrets as typed fields.
- Invocation output evidence is digest/reference based and bounded; raw output/prompt/source content is excluded.
- Cross-Project private source cannot be embedded in reusable skill records; invocation identity is Project/run scoped.
- Hidden reasoning/chain-of-thought is neither requested nor stored.

## 6. Failure and recovery boundaries

- Invalid or oversized skill contracts fail before digest admission.
- Unapproved digest or undeclarable capability fails before registry mutation.
- Same ID/version/digest replay is idempotent; same ID/version/different digest is a hard conflict.
- Unsupported/ambiguous S1 compatibility cannot be bypassed by a skill.
- Missing capability cannot be satisfied by the skill itself; selection returns typed human-required/no-selection evidence.
- Ambiguous top selection cannot be resolved by model preference.
- Invocation record creation rejects Project/run, skill/profile/source/capability identity mismatch.
- Retry/process recreation over the same invocation facts yields the same record identity.
- Existing S1 and Wave 4 protected runtime regressions remain green.

## 7. Non-goals

- executable plugins or arbitrary Python/JavaScript modules;
- skill marketplaces, remote downloads or package installation;
- model-generated skill auto-admission;
- runtime credential/tool provisioning;
- dynamic provider/API invocation;
- secret/environment management;
- application service bindings;
- objective-to-application orchestration;
- cross-Project memory/reuse;
- changing acceptance/evaluation/REVIEW authority.

## 8. Acceptance criteria

### AC-01 Exact server-owned skill admission
A portable skill is registered only when its recomputed canonical digest exactly matches the server-owned approved `(skill_id, version)` mapping. Unapproved or tampered content fails closed before registry mutation.

### AC-02 Immutable versioned registry and idempotent replay
One skill ID/version maps to exactly one digest. Re-admitting the same exact contract is idempotent and deterministic across process recreation; a different digest for the same ID/version fails with `SKILL_VERSION_CONFLICT`.

### AC-03 Bounded safe skill contract
Skill IDs/versions, ordered procedure steps, typed input/output fields, objective kinds, repository requirements, evidence requirements and capability IDs are format/count/byte bounded. Malformed/oversized contracts fail with bounded typed errors and cannot smuggle Project/source/credential/provider authority through typed fields.

### AC-04 Skills declare prerequisites but never grant authority
Required capability IDs must be allowed by admission policy and already present in the immutable server-owned capability snapshot for selection. Missing/undeclarable capabilities fail closed. Registry/selection outputs contain no credential, command, filesystem/network/provider/deployment handle or approval authority.

### AC-05 Deterministic S1 compatibility-based selection
Selection consumes the accepted P2-V0.18.1 compatibility profile only, not raw repository content. Objective, repository shape/signals, registered contract metadata and capability snapshot deterministically determine eligibility and selection independent of model preference, registration order or map iteration.

### AC-06 No-match, incompatible and ambiguous cases fail closed
Unsupported/ambiguous repository compatibility, no matching skill, missing capability and equivalent top-skill ambiguity produce explicit typed no-selection/HUMAN_REQUIRED outcomes rather than guessed skill execution.

### AC-07 Replay-safe bounded invocation identity and evidence
Invocation records bind canonical Project/run identity, exact registered skill version/digest, S1 profile/source identity, capability policy/prerequisites, input digest, final status and bounded digest/reference evidence. Same facts replay to the same invocation ID; changed protected facts change identity or fail mismatch validation.

### AC-08 Privacy-safe reusable skill and invocation records
Registry and invocation outputs exclude raw repository/source content, Project-private reusable artifacts, raw inputs/outputs, prompts, credentials, environment values, unrestricted logs and hidden reasoning. Deliberate secret/policy/deployment instructions in unapproved skill text cannot enter the registry or invocation record.

### AC-09 Existing S1 and protected runtime regressions remain green
Accepted P2-V0.18.1 repository intelligence plus Wave 4 source bootstrap, immutable lineage, protected execution, provider least privilege, authentication, bounded delivery and protected evaluation tests remain unchanged or stronger.

### AC-10 Exact-head worker release boundary
The candidate contains this approved spec plus authentic committed DSPy plan evidence and only declared bounded implementation/tests. Exact-head Workstream Spec Validation, Parallax P2 CI and Bounded Autonomy pass. The worker opens a PR targeting `integration/wave5-generalized-delivery`, does not merge/deploy/apply migrations/change production configuration, and stops READY FOR INTEGRATION.
