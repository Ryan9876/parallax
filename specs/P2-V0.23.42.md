## 1. Objective

Correct one repository-state classification defect exposed only after P2-V0.23.41 had already completed its production REVIEW correction cycle.

The frozen W9-S1 Engineering Run `a64d56b7-ad42-42ad-9562-891783363f4a` successfully reworked `AC-03` and `AC-05`, accepted replacement source lineage `src:001736ab731e243956cf78ede7a0087d2b81595f1008568850eac1e9acc3e809`, passed BUILD/TEST/VERIFY, and returned to human REVIEW revision 12. Its subsequent source-publication step failed with `repository.initialize-empty -> GREENFIELD_BASELINE_MISMATCH`.

The target `Ryan9876/parallax-qa1` is not truly empty: its authenticated default ref exists and points to user-authored cleanup commit `b24c029be916f8b1f0ab07347a988f814cc8d567`. That commit's tree is the universal canonical Git empty tree `4b825dc642cb6eb9a060e54bf8d69288fbee4904`. Current delivery code routes every accepted lineage descending from a `greenfield` root through `initialize_empty_baseline()`, and that function interprets any existing default-branch head as a claim that the head is the exact Parallax two-commit baseline. A valid commit-bearing empty branch therefore fails strict Parallax-baseline verification even though it can safely serve as an ordinary immutable branch base.

P2-V0.23.42 must distinguish this state from both a truly empty repository and the exact Parallax canonical baseline. The correction may use a commit-bearing empty head only as a read-only verified base for the existing feature-branch/commit/PR/Preview delivery path. It must not rewrite the default branch, weaken canonical-baseline proof, or broaden provider authority.

## 2. Verified findings and fixed decisions

- `GreenfieldVerifiedLineageDelivery.deliver()` calls `initialize_empty_baseline()` for every accepted lineage whose durable root has `source_kind=greenfield`.
- `GreenfieldGitHubClient.initialize_empty_baseline()` currently behaves as follows:
  - `head_revision is None`: initialize the deterministic two-commit Parallax baseline;
  - `head_revision is not None`: require that head to verify as the exact Parallax two-commit baseline.
- Existing strict replay verifies Parallax cleanup message/actor/parent, canonical empty cleanup tree, bootstrap message/actor/root shape, marker path/type/mode/blob/content/provenance, provider-owned timestamp shape, and exact default-ref stability.
- Existing test coverage intentionally rejects an unrelated user commit even when its tree is empty. That assertion described the old two-state model and is the exact behavior this release must refine without weakening the canonical-baseline branch.
- The current QA target head `b24c029...` has an authenticated default ref and canonical empty tree but is not a Parallax baseline commit.
- An empty-tree commit contains no repository source to inherit. Using its exact immutable commit SHA as the base of a new bounded feature branch does not grant source authority beyond the already authenticated repository/ref identity.
- The safest classification is three-state rather than fallback-on-error:
  1. no usable default-branch head — truly empty, existing initializer required;
  2. exact Parallax cleanup baseline head — strict canonical replay required;
  3. other commit-bearing head — independently prove exact empty tree and stable ref, then use that exact head as an ordinary delivery base.
- A failed Parallax-baseline verification must never be silently downgraded to generic commit-bearing-empty when the head identifies itself as the Parallax cleanup baseline. Tampered or provenance-mismatched canonical-baseline claims remain fail-closed.

## 5. Architecture requirements

### 5.1 Repository state is classified before mutation

For greenfield-root source delivery, the GitHub boundary must resolve exactly one of three states from authenticated provider evidence:

- `TRUE_EMPTY`: exact repository metadata is valid and the canonical default ref has GitHub's narrowly recognized empty-repository response, yielding no head revision;
- `PARALLAX_BASELINE`: the default ref exists and the head claims the exact Parallax cleanup-baseline identity, which must pass the complete existing strict baseline/provenance verification;
- `COMMIT_BEARING_EMPTY`: the default ref exists, the head does not claim the Parallax cleanup-baseline identity, and the exact head commit/tree is independently proven empty and stable.

No exception-catching fallback may convert a failed `PARALLAX_BASELINE` proof into `COMMIT_BEARING_EMPTY`.

### 5.2 Truly empty behavior is unchanged

`TRUE_EMPTY` continues to use the existing fixed `.parallax-greenfield` Contents bootstrap, exact bootstrap read-back, Git Data empty-tree cleanup commit, and exact non-force default-ref update. The result must still verify as the canonical two-commit baseline before delivery continues.

No mutation may occur before positive exact repository identity and true-empty proof.

### 5.3 Canonical baseline replay remains strict

A head whose commit message is the exact Parallax cleanup message remains a canonical-baseline claim. It must pass all existing baseline invariants, including:

- exact cleanup actor name/email and valid offset-aware provider timestamps;
- exact cleanup message;
- exactly one bootstrap parent;
- canonical cleanup empty-tree identity;
- exact bootstrap actor/message and zero parents;
- exact one-entry bootstrap tree;
- fixed `.parallax-greenfield` path/type/mode;
- exact marker version and provenance digest;
- exact current default ref.

Any mismatch remains `GREENFIELD_BASELINE_MISMATCH`; it cannot be treated as an ordinary user empty commit.

### 5.4 Commit-bearing empty is read-only proof

For a non-Parallax existing head, the client must:

1. fetch the exact commit by the head SHA;
2. require a valid tree SHA;
3. require that tree SHA equals universal canonical Git empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`;
4. fetch that exact tree and require `truncated` is not true and `tree == []`;
5. re-read the canonical default ref and require it still equals the originally inspected head SHA.

The proof performs GET operations only. It does not care about user commit author/message/parents except that the response is structurally valid and does not claim the protected Parallax cleanup identity.

If the ref moves, the tree is non-empty/truncated, the commit/tree response is malformed, or source identity cannot be proven, fail closed before branch creation.

### 5.5 Delivery base identity is explicit

The typed result returned to `GreenfieldVerifiedLineageDelivery` must expose:

- exact repository ref;
- exact default branch;
- exact immutable delivery-base revision;
- bounded classification (`TRUE_EMPTY_INITIALIZED`, `PARALLAX_BASELINE`, or `COMMIT_BEARING_EMPTY` or equivalent stable names);
- whether Parallax initialized the baseline.

Parallax-specific bootstrap/provenance fields must remain present and exact for Parallax baseline classifications, but must not be fabricated for a generic commit-bearing-empty base.

### 5.6 Durable greenfield lineage identity remains unchanged

The Engineering Run's durable source root remains the previously admitted `greenfield_source_ref(repository_ref, default_branch)`. P2-V0.23.42 does not rewrite or migrate source lineage.

Before delivery continues, `greenfield_source_ref(binding.repository_ref, resolved.default_branch)` must still hash to the durable root `source_ref_digest`. A repository/default-branch identity mismatch fails closed.

### 5.7 Existing publication authority remains unchanged

After the base is resolved, delivery uses the existing bounded operations only:

- create deterministic `parallax/{project-prefix}-{run-prefix}` feature branch from the exact resolved base revision;
- commit only the exact accepted same-run immutable lineage to that branch;
- create/read back the exact PR against the resolved default branch;
- create/read back the exact Vercel Preview from the exact committed revision;
- persist the ordinary delivery record;
- stop at human REVIEW.

No default-branch application mutation, force update, merge, or production promotion is authorized.

### 5.8 Concurrency is fail-closed

The commit-bearing-empty proof must re-read the default ref after commit/tree inspection. Branch creation remains bound to the exact resolved head SHA. Existing provider branch-creation conflict semantics remain authoritative if any later race occurs.

No clock tolerance, retry loop, force ref update, or last-write-wins behavior is introduced.

## 6. Security and authority

This release reduces unnecessary mutation; it does not add provider authority. The existing `repository.initialize-empty` capability remains the only greenfield default-branch mutation authority and is used only for `TRUE_EMPTY`.

`COMMIT_BEARING_EMPTY` is a read-only classification followed by existing feature-branch publication authority. The caller cannot select the base revision, default branch, tree, or classification. All are derived from exact authenticated GitHub responses and revalidated server-side.

An ordinary non-empty repository cannot enter this path because its exact head tree must equal the universal empty-tree identity and decode to an empty tree. A tampered Parallax baseline cannot enter this path because the Parallax cleanup identity forces strict canonical verification.

## 7. Reliability, compatibility, and rollback

No database migration is expected. Existing truly-empty initialization and canonical-baseline replay remain compatible. Existing non-greenfield repository delivery remains untouched.

Rollback removes the commit-bearing-empty classification and returns to the previous conservative mismatch behavior. It does not require data rollback, source-lineage rollback, Git history repair, or deletion of accepted application lineage.

Provider-read failures remain bounded provider failures. Source-delivery failure still cannot move a run beyond human REVIEW or alter the accepted lineage.

## 8. Acceptance criteria

### AC-01 Three repository states are distinct
Provider-realistic tests prove true-empty/no-head, exact Parallax canonical baseline, and non-Parallax commit-bearing empty-head states are classified separately and deterministically.

### AC-02 Truly empty initialization is unchanged
The existing Contents bootstrap + Git Data cleanup + non-force ref update sequence and all positive/negative tests remain green without added mutation or relaxed proof.

### AC-03 Canonical baseline strictness is unchanged
Exact Parallax baseline replay remains GET-only and requires every existing actor/message/parent/tree/marker/blob/provenance/default-ref invariant. A tampered or provenance-mismatched Parallax cleanup claim still fails `GREENFIELD_BASELINE_MISMATCH` and cannot downgrade to generic commit-bearing empty.

### AC-04 Commit-bearing empty proof is exact and read-only
A non-Parallax existing head is accepted only when its exact commit points to canonical empty-tree SHA, the exact tree payload is non-truncated and empty, and a final default-ref read returns the same head SHA. Provider calls for this proof are GET-only.

### AC-05 Non-empty or malformed heads fail closed
Non-empty tree SHA/payload, truncated tree, malformed commit/tree/ref payload, missing repository identity, missing default branch/head identity, or unrelated provider errors fail before branch/commit/PR/Preview mutation.

### AC-06 Ref movement fails closed
If the default ref changes between initial inspection and final stability read, commit-bearing-empty resolution fails and no delivery mutation occurs.

### AC-07 No fabricated Parallax provenance
Typed delivery-base evidence for `COMMIT_BEARING_EMPTY` does not invent a bootstrap revision, provenance digest, Parallax actor, or Parallax baseline identity. Those fields remain exact only for the two Parallax baseline classifications.

### AC-08 Greenfield durable identity remains exact
The resolved repository/default-branch identity must still match the existing durable greenfield root digest. P2-V0.23.42 introduces no root migration or cross-run lineage substitution.

### AC-09 Existing delivery path uses exact resolved base
Composition tests prove feature-branch creation receives the exact commit-bearing-empty head SHA as `base_revision`, accepted-lineage commit uses that same expected parent, PR targets the exact default branch, and Preview binds the exact committed source revision.

### AC-10 No authority expansion
Diff and protected tests prove no new default-branch application mutation, force update, arbitrary Git object/ref authority, repository scope, credentials, providers, network, command, lifecycle, automatic REVIEW, merge, or production authority.

### AC-11 Existing paths do not regress

### AC-13 Protected release gates pass
