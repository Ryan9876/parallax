## 1. Objective

Close the complete source-publication compatibility gap exposed after P2-V0.23.41 successfully completed a same-run human REVIEW correction cycle.

The frozen W9-S1 Engineering Run `a64d56b7-ad42-42ad-9562-891783363f4a` reworked only `AC-03` and `AC-05`, accepted replacement source lineage `src:001736ab731e243956cf78ede7a0087d2b81595f1008568850eac1e9acc3e809`, passed BUILD/TEST/VERIFY, and returned to human REVIEW revision 12. Its subsequent source-publication step exposed three coupled assumptions that were valid before same-run REVIEW rework existed but are no longer sufficient:

1. every existing default-branch head for a durable `greenfield` root is assumed to be the exact Parallax two-commit baseline;
2. the deterministic publication branch is keyed only by Project + Engineering Run, so a corrected lineage in the same run collides with the prior rejected lineage branch;
3. durable source-delivery records use a lineage-specific operation key but explicitly reject a second `SOURCE_DELIVERY` record for the same Engineering Run and hardcode attempt number 1.

The target `Ryan9876/parallax-qa1` currently has an authenticated default ref at user-authored cleanup commit `b24c029be916f8b1f0ab07347a988f814cc8d567`, whose tree is the universal canonical Git empty tree `4b825dc642cb6eb9a060e54bf8d69288fbee4904`. P2-V0.23.42 must make publication identity consistently source-lineage-aware while preserving all existing authority ceilings. The corrected lineage must receive a distinct deterministic feature branch and a distinct immutable durable delivery record. The old branch, old PR/Preview evidence, and old delivery record remain historical evidence and are never overwritten.

## 2. Verified findings and fixed decisions

- `GreenfieldVerifiedLineageDelivery.deliver()` routes every accepted lineage whose durable root has `source_kind=greenfield` through `initialize_empty_baseline()`.
- `GreenfieldGitHubClient.initialize_empty_baseline()` currently has a two-state model:
  - no head: initialize the deterministic Parallax baseline;
  - existing head: require the head to be the exact deterministic Parallax baseline.
- The current QA default head is commit-bearing and empty but is not a Parallax baseline claim.
- A commit-bearing empty head contains no repository source content. Its exact immutable commit SHA can safely serve as a feature-branch base after exact read-only commit/tree/ref proof.
- Canonical Parallax baseline proof must remain strict. A head that claims the exact Parallax cleanup identity cannot fall back to generic commit-bearing-empty if any protected baseline invariant fails.
- `GitHubRestProviderClient.create_branch()` correctly refuses to reuse an existing branch when its head differs from the requested base; it must remain non-force and fail-closed.
- The old W9 branch `parallax/0e20392b-a64d56b7` already exists at old accepted lineage `src:da5d0fb62d34a3228bb56e7a7d82971c8023a536d11944ba71bcaa51a407b871`. Reusing that branch for the corrected lineage would require an unauthorized non-fast-forward reset.
- Publication branch identity must therefore include immutable accepted-lineage identity. The branch name is server-derived and deterministic; candidate/user input cannot select it.
- `EngineeringAttemptDeliveryRecordStore.operation_key()` is already lineage-keyed as `source-delivery:{lineage_id}` and the database permits multiple attempts for one stage if `attempt_number` differs. The store itself currently blocks any second delivery record for the run and hardcodes `attempt_number=1`; those two restrictions must be aligned with the lineage-keyed operation identity.
- A same-run correction requires multiple immutable delivery records, one per accepted lineage. It does not require replacing, mutating, or deleting a prior delivery record.
- No database schema migration is required: existing uniqueness constraints `(run_id, operation_key)` and `(run_id, stage, attempt_number)` are compatible with distinct lineage operation keys and monotonically allocated stage attempt numbers.

## 5. Architecture requirements

### 5.1 Greenfield publication base uses three explicit repository states

For delivery from a durable `greenfield` root, authenticated GitHub evidence must resolve exactly one state:

- `TRUE_EMPTY`: exact repository metadata is valid and the canonical default ref yields GitHub's narrowly recognized empty-repository condition with no head revision;
- `PARALLAX_BASELINE`: the default ref exists and its head claims the exact Parallax cleanup-baseline identity, requiring the complete strict baseline/provenance verification;
- `COMMIT_BEARING_EMPTY`: the default ref exists, the head does not claim the protected Parallax cleanup identity, and the exact head commit/tree is proven empty and stable.

No catch-all/fallback may convert failed `PARALLAX_BASELINE` proof into `COMMIT_BEARING_EMPTY`.

### 5.2 Truly empty initialization is unchanged

`TRUE_EMPTY` continues to use the fixed `.parallax-greenfield` Contents bootstrap, exact bootstrap read-back, Git Data empty cleanup commit, and exact non-force default-ref update. The result must verify as the canonical Parallax baseline before publication continues.

No mutation occurs before exact repository identity and true-empty proof.

### 5.3 Canonical baseline replay remains strict

A head whose commit message is the exact Parallax cleanup message is a protected canonical-baseline claim and must pass all existing invariants:

- exact cleanup actor name/email and valid offset-aware provider timestamps;
- exact cleanup message;
- exactly one bootstrap parent;
- canonical cleanup empty-tree identity;
- exact bootstrap actor/message and zero parents;
- exact one-entry bootstrap tree;
- fixed `.parallax-greenfield` path/type/mode;
- exact marker version and provenance digest;
- exact current default ref.

Any mismatch remains `GREENFIELD_BASELINE_MISMATCH`.

### 5.4 Commit-bearing empty proof is exact and read-only

For a non-Parallax existing head, the GitHub client must:

1. fetch the exact head commit by its inspected SHA;
2. require a valid tree SHA;
3. require the tree SHA equals `4b825dc642cb6eb9a060e54bf8d69288fbee4904`;
4. fetch that exact tree and require `truncated` is not true and `tree == []`;
5. re-read the canonical default ref and require the same original head SHA.

The proof is GET-only. User commit actor/message/parents are not source authority and need not match Parallax-owned values, except an exact Parallax cleanup message triggers strict protected baseline verification instead.

### 5.5 Greenfield publication-base evidence is typed without fabricated provenance

The result used by `GreenfieldVerifiedLineageDelivery` must expose exact repository ref, exact default branch, exact immutable publication-base revision, bounded classification, and whether Parallax initialized the base.

Parallax bootstrap revision/provenance identity may be present only for Parallax baseline classifications. A generic commit-bearing-empty base must not fabricate Parallax provenance or bootstrap identity.

### 5.6 Durable greenfield source-root identity remains unchanged

The Engineering Run's admitted durable source root remains `greenfield_source_ref(repository_ref, default_branch)`. P2-V0.23.42 introduces no source-root migration.

`greenfield_source_ref(binding.repository_ref, resolved.default_branch)` must continue to hash to the durable root `source_ref_digest` before publication.

### 5.7 Publication identity is Project + Run + accepted lineage

A source publication is an immutable artifact of one exact accepted source lineage. Its deterministic server-owned branch identity must include:

- bounded Project identity component;
- bounded Engineering Run identity component;
- a stable bounded suffix derived from the exact accepted `src:` lineage identity.

Equivalent implementations may use a protected hash of the lineage rather than raw lineage text, but collision resistance and deterministic replay must be sufficient for the existing provider bounds.

The same lineage always resolves the same branch identity. A different accepted lineage in the same run resolves a different branch identity. Candidate input cannot select or influence the branch name except through the already-protected accepted lineage identity.

### 5.8 Historical branches remain immutable

If a prior lineage branch exists, a corrected lineage must not reset, patch, delete, rename, or reuse it. The corrected lineage creates its own deterministic branch from the exact current resolved publication base.

Existing `create_branch` fail-closed semantics remain unchanged for an unexpected collision on the new deterministic name. No force branch operation is introduced.

### 5.9 Durable delivery records are lineage-scoped and append-only

`SOURCE_DELIVERY` evidence is durable per accepted lineage, not singleton per run.

- operation identity remains `source-delivery:{lineage_id}` or equivalent exact lineage identity;
- same-lineage replay returns the exact previously persisted record;
- conflicting evidence for the same lineage fails closed;
- a distinct accepted lineage in the same run may append a distinct delivery record;
- the record receives the next available positive `attempt_number` for `SOURCE_DELIVERY` under the existing `(run, stage, attempt_number)` uniqueness contract;
- concurrent inserts must either persist one exact record or replay that same record; they cannot overwrite a different lineage or silently reorder authority.

Historical delivery records remain queryable and immutable.

### 5.10 Existing PR/Preview authority remains unchanged

After resolving the publication base and lineage-specific branch name, the existing bounded path remains:

- create the deterministic lineage-specific feature branch from exact resolved base revision;
- commit only exact accepted same-run immutable lineage files with exact expected parent;
- create/read exact PR against resolved default branch;
- create/read exact Vercel Preview against exact committed revision;
- append exact lineage delivery record;
- remain at human REVIEW.

No default-branch application mutation, force update, merge, or production promotion is authorized.

### 5.11 Concurrency is fail-closed

Commit-bearing-empty resolution re-reads the default ref after commit/tree proof. Branch creation is bound to the exact resolved SHA. Delivery record persistence respects existing database uniqueness and exact lineage operation identity.

No clock tolerance, provider retry loop, force update, last-write-wins, record overwrite, or history repair is added.

## 6. Security and authority

This release primarily removes invalid singleton assumptions; it does not add execution or provider power.

`repository.initialize-empty` remains the only greenfield default-branch mutation authority and is used only for `TRUE_EMPTY`. `COMMIT_BEARING_EMPTY` adds no provider action; it is a stricter read-only proof followed by already-authorized feature-branch publication.

Lineage-scoped branch naming reduces collision pressure without authorizing branch reset. Allowing multiple immutable delivery records does not authorize multiple accepted lineages at once: the current run's latest accepted IMPLEMENT+VERIFY evidence remains the sole source of publishable lineage identity. Historical records are evidence only.

An ordinary non-empty repository cannot enter the commit-bearing-empty path because its exact head tree must be the universal empty tree and decode as empty. A tampered Parallax baseline cannot enter because the protected cleanup identity forces strict baseline verification.

## 7. Reliability, compatibility, and rollback

No database migration is expected. Existing uniqueness constraints already support distinct lineage operation keys and distinct `SOURCE_DELIVERY` attempt numbers.

Existing delivery records and old publication branches remain valid historical artifacts. Replays of already-recorded lineages must resolve their persisted records before any new provider mutation, so branch naming changes do not invalidate prior delivery evidence.

Rollback removes commit-bearing-empty support and lineage-scoped publication for new deliveries, returning to conservative failure. It requires no source-lineage rollback, Git history repair, database migration rollback, or deletion of historical delivery records.

Provider/read/publication failure still cannot advance a run beyond human REVIEW or mutate the accepted lineage.

## 8. Acceptance criteria

### AC-01 Three repository states are distinct
Provider-realistic tests prove true-empty/no-head, exact Parallax baseline, and non-Parallax commit-bearing empty-head states classify separately and deterministically.

### AC-02 Truly empty initialization is unchanged

### AC-04 Commit-bearing empty proof is exact and read-only
A non-Parallax existing head is accepted only when exact commit points to canonical empty-tree SHA, exact tree payload is non-truncated and empty, and final default-ref read returns the same SHA. The proof uses GET operations only.

### AC-05 Invalid commit-bearing states fail closed
Non-empty tree, truncated tree, malformed commit/tree/ref payload, missing identity, unrelated provider error, or default-ref movement fails before delivery mutation.

### AC-06 No fabricated Parallax provenance
Commit-bearing-empty evidence does not invent bootstrap revision, provenance digest, Parallax actor, or baseline identity.

### AC-07 Greenfield durable identity remains exact
Resolved repository/default-branch identity still matches the existing durable greenfield root digest; no root migration or cross-run substitution occurs.

### AC-08 Branch identity is lineage-scoped
Two accepted lineage IDs under the same Project/run produce two distinct deterministic bounded branch names; replay of the same lineage produces the same name.

### AC-09 Prior rejected branch is never rewritten
Provider/composition tests prove corrected lineage publication does not reset/reuse the existing old-lineage branch. Existing branch/ref mutation semantics remain non-force.

### AC-10 Exact resolved base flows through publication
For commit-bearing-empty, branch creation receives exact verified head SHA as `base_revision`; accepted-lineage commit uses the same expected parent; PR targets exact default branch; Preview binds exact committed revision.

### AC-11 Multiple immutable delivery records coexist

Each record has a distinct operation key and non-colliding stage attempt number. Same-lineage replay remains exact and conflicting same-lineage evidence fails closed.
