## 1. Objective

Add the smallest governed correction loop for a Project-bound Engineering Run that has reached the human `REVIEW` boundary with a defective generated application while the requested corrections remain inside the already-approved Work Specification.

The first W9-S1 Decision Ledger candidate proved the missing product capability. P2-V0.23.40 correctly stopped static-web structural TEST/VERIFY from claiming behavioral acceptance, exposing two real REVIEW findings: malformed imported records can corrupt persisted browser state and later break rendering, and the delivered repository contains no automated tests despite the frozen acceptance requirement. Parallax can currently record a failed REVIEW or start/amend work, but it cannot revise the exact REVIEW candidate through the ordinary protected workflow. A new Engineering Run is not an equivalent substitute because durable source lineage is intentionally scoped to Project + Run and therefore does not inherit the prior run's accepted candidate.

P2-V0.23.41 must permit an authenticated operator to submit bounded in-scope REVIEW findings against the exact current run, preserve that run's accepted source lineage, re-enter protected PLAN, invalidate stale selected-candidate replay state, regenerate through the unchanged protected IMPLEMENT path, rerun BUILD/TEST/VERIFY, and stop again at REVIEW. Human findings are context and evidence only; they never become direct patch, source, lifecycle, provider, Git, Preview, merge or production authority.

- Existing PLAN and IMPLEMENT logic already use the latest successful PLAN and latest accepted IMPLEMENT lineage. Rework must preserve this ordering rather than adding a parallel correction engine.

## 5. Architecture requirements

### 5.1 REVIEW rework is explicit human control

The new endpoint is an operator control operation, not an autonomy stage. It is admitted only for the exact authenticated Project-bound Engineering Run currently in `REVIEW`, with optimistic `expected_revision` and idempotent `operation_key` semantics identical in spirit to existing control operations.

The server rejects calls from PLAN/IMPLEMENT/BUILD/TEST/VERIFY, PAUSED/FAILED, COMPLETE, CANCELLED, SPEC_AMENDMENT or any unknown state. Rework does not reuse `resume()` because ordinary resume semantics must remain limited to protected recovery from PAUSED/FAILED.

### 5.2 Findings are bounded acceptance-linked evidence

Each request contains one or more findings with:

- one acceptance ID;
- one trimmed non-empty plain-text finding;
- bounded count and bounded per-finding length.

Every acceptance ID must belong to the run's immutable protected acceptance map. Duplicate acceptance-ID/finding pairs, unknown IDs, empty text, hidden-reasoning fields or arbitrary nested payloads are rejected before mutation.

The server canonicalizes the ordered finding envelope and computes a deterministic SHA-256 rework-context digest. The observable context may contain only acceptance IDs and bounded finding text. It may not contain source bytes, diffs, provider payloads, credentials, environment values or hidden reasoning.

### 5.3 Same-run accepted lineage is the correction base

Before mutation, the service locates the latest successful IMPLEMENT attempt for the current REVIEW run and requires exact bounded evidence containing the same Project/run identity, a valid accepted `source_lineage_ref`, and a valid `workspace_digest`.

That accepted source lineage is recorded in the rework control evidence as the required correction base. The rework transition does not create or copy lineage. After transition to PLAN, existing runtime composition resolves the same run's current durable lineage and must observe that exact accepted source lineage. Any lineage mismatch fails closed before replacement IMPLEMENT mutation.

### 5.4 Rework returns to PLAN, not directly to IMPLEMENT

The state policy admits exactly `REVIEW -> PLAN`. The prior Work Specification remains immutable and bound to the run.

A fresh PLAN must therefore execute against the current accepted candidate lineage before replacement IMPLEMENT. The latest bounded rework-context digest and affected acceptance IDs are included in PLAN evidence. PLAN verification independently recomputes the current rework context and rejects stale/missing/drifted rework identity.

This preserves the existing execution-contract binding order and ensures the correction cannot reuse a PLAN created for the pre-review base lineage.

### 5.5 Human findings guide generation but do not author source

When the run reaches IMPLEMENT after a rework PLAN, `ProtectedImplementationRuntime` obtains the current bounded rework context from `EngineeringRunService` and appends server-generated correction guidance to the implementation-generation request.

The model still receives only:

- immutable approved Work Specification contract;
- exact acceptance map;
- bounded protected source context selected from the accepted candidate lineage;
- bounded server-owned correction findings.

Generation still returns typed semantic file-content intent. Canonical patch rendering, proposal safety, disposable candidate validation, independent evaluation, SafeImplementationEngine commit-time validation and source-lineage acceptance remain unchanged and authoritative.

### 5.6 Prior selected-candidate replay must be invalidated explicitly

The prior live worker may be unleased in `READY_FOR_INTEGRATION` with an old selected-candidate artifact and plan checkpoint. REVIEW rework must not permit `selected_candidate_artifact()` to replay that rejected proposal.

The worker preparation operation is allowed only after a valid same-run REVIEW-rework transition and only for a worker associated with that run. For an unleased `READY_FOR_INTEGRATION` worker it:

- moves to existing `RECOVERING`;
- clears the old checkpoint payload/plan reference/current step and progress fingerprints;
- resets retry/no-progress/oscillation counters;
- binds current and last-known-good lineage fields to the exact reviewed accepted lineage;
- sets existing `REASSIGN` recovery intent;
- increments durable worker revision;
- retains no mutation lease.

The operation is idempotent when the worker is already in the exact REVIEW-rework recovery state for the same accepted lineage. It must fail closed for active leases, unrelated terminal states, lineage mismatch or competing state changes.

Existing `DurableAgentWorkerBridge.acquire()` may then use the already-governed `RECOVERING -> REASSIGNED` path. No ordinary acquisition or autonomous call gains terminal-worker restart authority.

### 5.7 Interrupted route handling is replay-safe

The run transition and worker reset use separate existing persistence boundaries. A request may therefore be interrupted after the run reaches PLAN but before worker preparation completes.

Retrying the same `operation_key` must resolve the existing REVIEW-rework attempt idempotently and then retry only the worker preparation. The route must never create a second run transition for the same operation and must never require an out-of-band database repair for this bounded interruption.

### 5.8 REVIEW remains the completion ceiling

After rework, autonomous execution follows the unchanged PLAN -> IMPLEMENT -> BUILD -> TEST -> VERIFY path and stops again at REVIEW. P2-V0.23.40 structural-only TEST/VERIFY semantics remain unchanged for static web.

The replacement candidate cannot complete REVIEW, merge, or enter production autonomously. A later operator decision remains required.

## 6. Security and authority

This release adds only authenticated bounded correction control within an already-approved Work Specification. It does not make human findings executable authority and does not let findings select files, patches, commands, tools, providers, credentials, network policy, execution profiles, source lineage, Git refs, Preview targets or deployment destinations.

The exact protected acceptance map and latest accepted same-run lineage are independently resolved server-side. Caller-supplied acceptance IDs are references that must match that map; caller text cannot create a new acceptance criterion or material objective.

The worker reset is a narrow terminal-state exception tied to an already-authorized REVIEW-rework operation. It cannot be reached by ordinary autonomy, reconnect, page refresh, acquisition or generic recovery classification.

## 7. Reliability, compatibility and rollback

No schema migration is expected. Existing runs without REVIEW rework remain byte/behavior compatible. Existing PAUSED/FAILED resume, PLAN refresh, worker process-loss recovery, candidate replay, source delivery and REVIEW PASS behavior remain unchanged.

Rework creates additional attempts on the same run. Consumers must continue to use latest successful PLAN/IMPLEMENT evidence where existing code already does so; tests must prove old earlier attempts cannot outrank the refreshed cycle.

Rollback removes the REVIEW-rework endpoint/transition but leaves any already-produced accepted source lineage and ordinary run attempts durable. No automatic destructive rollback of generated application source is introduced.

## 8. Acceptance criteria

### AC-01 Exact REVIEW-only transition
An authenticated request with the exact current revision can transition a Project-bound run from REVIEW to PLAN. The same request is rejected from every other state and ordinary `resume()` behavior is unchanged.

### AC-02 Findings are bounded and acceptance-linked
The request rejects empty findings, unknown acceptance IDs, malformed nested data, duplicate exact findings, over-limit counts/text and any acceptance reference outside the immutable run acceptance map.

### AC-03 Same-run source continuity is exact
The transition requires the latest successful IMPLEMENT evidence and records its exact accepted source-lineage/workspace identity. The new PLAN resolves that same lineage as its base; no cross-run/default-branch source substitution is admitted.

### AC-04 Rework context has deterministic identity
Equivalent canonical findings produce the same bounded SHA-256 rework-context digest; changed finding text or affected acceptance IDs changes the digest. The latest PLAN persists and independently verifies the exact current digest.

### AC-05 Findings reach implementation generation safely
The rework IMPLEMENT request includes bounded server-owned correction guidance plus the unchanged approved contract and protected source context. Findings do not bypass typed generation, proposal safety, disposable validation, independent evaluation, SafeImplementationEngine or lineage acceptance.

### AC-06 Old selected candidate cannot replay
A prior `READY_FOR_INTEGRATION` worker/candidate artifact is reset through the explicit rework preparation path. The old plan/candidate checkpoint cannot satisfy `selected_candidate_artifact()` for replacement IMPLEMENT.

### AC-07 Worker re-arm is narrow and idempotent
The reset requires an unleased exact-run worker and exact reviewed accepted lineage, uses the existing RECOVERING/REASSIGNED lifecycle, is idempotent for an already-prepared matching rework, and rejects active leases, unrelated terminal states or lineage drift.

### AC-08 Interrupted rework request is replay-safe
If the run transition commits before worker preparation, repeating the same operation does not create another transition and successfully completes only the pending worker preparation when safe.

### AC-09 Fresh correction cycle uses latest evidence
After rework, PLAN/IMPLEMENT/BUILD/TEST/VERIFY use the new cycle's latest successful PLAN and accepted implementation lineage. Earlier passing attempts cannot authorize stale execution or REVIEW completion.

### AC-10 Static-web evidence truthfulness remains unchanged
Reworked static-web TEST/VERIFY still use P2-V0.23.40 `STRUCTURAL_ONLY` evidence with empty verified acceptance IDs and return to REVIEW rather than COMPLETE.

### AC-11 No material-scope bypass
The endpoint cannot amend the Work Specification or add acceptance criteria. Material objective changes continue to require the existing `SPEC_AMENDMENT`/draft/approval path.

### AC-12 No authority expansion
Diff and protected tests prove no new model/provider/credential/network/command/execution-profile/Git/Preview/merge/production/automatic-REVIEW authority and no cross-run source-lineage authority.

### AC-13 Protected release gates pass
Spec validation, authentic DSPy SpecCritic/SpecCompiler, strict compiled-plan validation, focused tests, full API regression, Bounded Autonomy, Workstream Spec Validation and P2 CI pass on exact reviewed heads.

### AC-14 Production runtime remains healthy
Exact merged API source reaches production READY; normal production preflights, `/health`, `/ready` and exact-deployment runtime scans pass.

### AC-15 W9-S1 real correction is proven
After deployment, the frozen Decision Ledger run accepts bounded REVIEW findings for the observed import-safety and automated-test defects, regenerates from its existing accepted candidate lineage through the protected path, reruns normal validation, and returns to human REVIEW. Any subsequent independent application defect is recorded separately rather than hidden.

## 10. Risks

The largest risk is accidentally converting REVIEW into a generic model-controlled retry loop. The mitigation is an explicit authenticated operator endpoint, exact REVIEW state/revision, bounded acceptance-linked findings and no autonomous invocation path.

A second risk is replaying the old selected candidate after transition. The mitigation is a dedicated exact-lineage worker reset that clears the old plan/candidate checkpoint and forces the existing RECOVERING/REASSIGNED path before generation.

A third risk is allowing stale PLAN evidence to authorize execution on a different source base. The mitigation is re-entry through PLAN, same-run current-lineage resolution, existing execution-contract identity checks and an added rework-context digest bound to the latest PLAN.

A fourth risk is turning finding text into source authority. The mitigation is to treat it only as bounded generation context; all existing typed generation, patch canonicalization, candidate validation, independent evaluation, safe mutation and lineage authority remain unchanged.

A fifth risk is non-atomic run/worker persistence creating a stranded rework. The mitigation is idempotent run transition plus independently retryable exact worker preparation under the same operation identity.
