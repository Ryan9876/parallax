## 1. Objective

Define one bounded operator-facing Agent Run projection/control contract that explains the existing Wave 6 agentic runtime without creating a second orchestrator or moving agent/source/provider authority into the client.

The projection is derived from existing authoritative Project, Work Specification, Engineering Run, worker checkpoint/recovery, source-lineage, validation, independent evaluation, routing/competition, provider delivery and run-event facts. It is a read model plus typed requests for only those controls whose server-side authority already exists.

## 2. Fixed decisions

- Projection is evidence, not authority.
- Canonical Project/run/spec/source identities always come from server-owned persisted facts.
- Client-supplied agent/task/source/provider identities are never accepted as authority.
- No hidden reasoning, raw prompts, credentials, raw provider payloads or unrestricted logs are projected.
- Controls are allowlisted typed operations only. The projection cannot create a generic command surface.
- Unsupported controls are omitted or denied; the API may not advertise a button merely because the UI wants one.
- Existing Engineering Run/worker/source/tool/provider state machines remain authoritative and unchanged.
- Replay/reconnect of the same exact run produces an equivalent projection identity.
- Projection may report observed/estimated/unknown economics only according to accepted evidence provenance; it cannot fabricate cost/time.
- REVIEW/HUMAN_REQUIRED remains explicit and cannot be auto-completed by the projection/control layer.

## 3. Architecture requirements

### 3.1 Immutable projection identity

Define a bounded `AgentRunProjection`-equivalent record binding exact Project ID, Engineering Run ID, Work Specification ID/revision/digest, stable acceptance IDs, current run revision/stage, accepted source lineage where present and a projection fingerprint/digest.

### 3.2 Team/task projection

Normalize accepted Wave 6 team/assignment evidence into bounded operator-safe task nodes including stable task/assignment identity, dependencies, status, producer/agent display identity, attempt/generation, bounded progress state and reason codes. Agent private reasoning is never included.

### 3.3 Recovery projection

Expose durable worker/reassignment facts such as checkpointed/stalled/recovering/reassigned/ready-for-integration states, generation changes and bounded recovery reasons. Process-local transient memory is not authoritative.

### 3.4 Validation/evaluation projection

Expose protected BUILD/TEST/VERIFY and deterministic browser/visual result summaries plus independent-evaluation disposition/identity for the exact candidate. Deterministic failures remain visually and semantically authoritative over qualitative support.

### 3.5 Routing/competition projection

Expose bounded routing/competition disposition, selected strategy/candidate identity and known-state economic evidence without revealing raw provider payloads or letting selection evidence imply canonical source acceptance.

### 3.6 Delivery/REVIEW projection

Expose exact accepted source lineage, publication/PR/Preview references when authorized and persisted, Preview readiness/status, final protected run state and REVIEW/HUMAN_REQUIRED handoff. Production deployment is not an ordinary Agent Run control.

### 3.7 Typed control capability advertisement

Define a server-derived list of currently admissible operator controls. A control is advertised only when an existing server-owned action and current run state permit it. Initial candidate controls may include cancel or existing resume/review-related boundaries only where repository inspection proves accepted server semantics.

No generic pause/resume/retry control may be invented if the underlying state machine lacks that authority.

### 3.8 Typed control request

Each control request binds Project/run identity, expected run revision/state, exact control kind and idempotency/request identity. Stale, cross-Project, unsupported, duplicate-conflicting or unauthorized requests fail closed.

### 3.9 Privacy-safe serialization

Projection payloads are bounded and exclude secrets, credentials, headers/cookies/environment, raw provider responses, prompts, hidden reasoning, source bytes/patches and unrestricted logs. Safe evidence references/digests and bounded excerpts may be included only under existing privacy policy.

### 3.10 Reconnect/replay

A reconnect/reload may reconstruct projection from durable facts without mutating the run, duplicating provider action or changing worker ownership. Projection-local UI state is never durable run authority.

## 4. Scope

Specification-only work is authorized before S1 acceptance. Semantic scope after dependency acceptance may include a narrow API projection service/model/route, safe serialization and focused tests. S3 owns the visual canvas and interaction presentation.

## 5. Non-goals

- client-managed agent roster/team planning;
- new Engineering Run lifecycle or worker recovery semantics;
- arbitrary command/shell/network/filesystem actions;
- source mutation/acceptance;
- provider/model administration;
- browser tool implementation;
- merge/deploy or REVIEW completion;
- hidden reasoning display.

## 6. Acceptance criteria

### AC-01 Exact canonical projection binding
Projection binds server-owned Project/run/spec/acceptance/source identity and rejects cross-context substitution.

### AC-02 Derived-only team/task state
Team/task nodes derive only from accepted persisted/runtime evidence; client input cannot create or change task/agent authority.

### AC-03 Durable recovery truth
Recovery/reassignment projection reflects durable worker generation/checkpoint state and cannot be synthesized from transient UI/model text.

### AC-04 Deterministic validation precedence
Protected deterministic failure remains explicit and cannot be hidden or overridden by qualitative evaluation/routing/competition output.

### AC-05 Safe economic known-state
Time/cost/usage/intervention evidence preserves observed/estimated/unknown state and provenance; unknown is never converted to zero.

### AC-06 Exact delivery/Preview identity
Published PR/Preview evidence binds the exact accepted source/candidate/run identity and does not imply production authority.

### AC-07 Server-derived control advertisement
Only controls backed by an accepted server authority contract and valid current run state are advertised.

### AC-08 Stale/unauthorized control rejection
Typed control requests bind expected identity/revision/state and fail closed on stale, unauthorized, cross-Project or unsupported requests.

### AC-09 Replay/idempotency safety
Projection reconstruction and exact control replay cannot duplicate canonical mutation, worker ownership change or provider publication.

### AC-10 Safe serialization
No secrets, credentials, raw provider payloads, prompts, hidden reasoning, source bytes/patches or unrestricted logs are exposed.

### AC-11 No authority expansion
Projection/control code has no direct source acceptance, new lifecycle transition, provider administration, arbitrary command, merge/deploy or REVIEW completion authority.
