## 1. Objective

Add a server-owned optimization control plane that reduces time-to-validated-outcome across concurrent Parallax development work without weakening any protected correctness or authority boundary. The controller maintains a dependency graph, ranks critical work, proposes bounded work stealing and cancellation only at safe boundaries, selects fast-lane validation only from proven impact, reuses only provenance-complete secret-free environments/patterns/repair memory, routes models within approved capability classes, and records bounded development-performance telemetry.

The optimization plane is advisory with respect to source mutation, worker ownership, protected evaluation and production promotion. Existing P2-V0.16.1 worker execution/lease/checkpoint identity remains authoritative for who may work; existing protected validation remains authoritative for what passes; P2-V0.16.3 remains authoritative for correction mutation and stop boundaries.

## 2. Scope

- Represent workstreams, protected contracts, validation gates and release gates as a deterministic dependency DAG with stable canonical identities and restart-safe serialization.
- Compute critical-path priority from explicit dependencies, remaining bounded cost estimates, readiness, blocking impact and integration capacity without granting new mutation authority.
- Produce bounded work-steal proposals only for READY work whose current worker lease/path ownership permits reassignment under the accepted P2-V0.16.1 protocol.
- Apply integration-capacity backpressure so runnable work does not overwhelm the serialized integration bottleneck.
- Support safe-boundary cancellation/supersession decisions that never interrupt an in-flight protected mutation, provider side effect, commit publication or accepted-lineage transition.
- Maintain a machine-readable change-impact graph from repository paths/configuration to components, protected contracts, platforms and validation suites.
- Select fast-lane validation only when impact provenance is complete and include mandatory global invariants; uncertainty always expands validation rather than skipping checks.
- Require full protected promotion suites at worker READY FOR INTEGRATION, integration acceptance and release/promotion boundaries regardless of fast-lane eligibility.
- Define immutable digest-addressed warm-environment/cache identity over secret-free toolchain, dependency, platform and source inputs; uncertain or stale provenance invalidates reuse.
- Define a Project-safe reusable pattern/component/config registry with validation provenance and compatibility constraints.
- Define privacy-safe failure fingerprints and repair-memory records that contain bounded structural facts rather than raw private source, logs, secrets or hidden reasoning.
- Route approved model classes according to task capability, evidence confidence and bounded policy while keeping protected acceptance thresholds and evaluator policy immutable.
- Perform deterministic specification preflight for contradiction, missing dependency, untestable acceptance, authority conflict and architecture conflict before implementation work is scheduled.
- Represent speculative integration as disposable candidates that cannot advance accepted lineage, satisfy protected merge/release gates or acquire production authority.
- Recommend workstream sizing/rebalancing while preserving single ownership of each acceptance criterion and dependency edge.
- Record bounded phase telemetry for queue, planning, generation, environment, build, test, browser, visual, provider, retry, integration, stall and human-wait intervals.
- Optimize validated outcome time and blocked critical-path time, not worker occupancy, token volume or raw task throughput.

## 3. Fixed decisions

- Correctness and protected authority dominate optimization. A slower fully proven path is preferred to a faster path with uncertain impact, provenance, ownership or validation coverage.
- P2-V0.16.1 worker execution identity, lease generation and checkpoint CAS remain the sole worker lifecycle authority.
- Scheduling decisions are recommendations until applied through the existing worker protocol; a scheduler cannot fabricate leases, generations or source ownership.
- Critical-path priority is deterministic for equal graph state; ties use stable canonical node identity rather than timing/randomness.
- Uncertain change impact means include the potentially affected check. Unknown impact can never justify skipping validation.
- Fast-lane validation is development acceleration only; full protected suites remain mandatory at worker/integration/release boundaries.
- Warm cache/environment reuse requires exact digest identity and complete provenance. Any ambiguous input, missing digest or secret-bearing identity invalidates reuse.
- Reusable patterns and repair memory are Project-scoped by default. Cross-Project reuse is allowed only for explicitly public/non-private validated artifacts that contain no Project data.
- Model routing cannot alter protected prompts/contracts/thresholds merely to obtain a pass and cannot grant tools or network/provider authority absent from the caller's approved capability set.
- Speculative integration is non-authoritative and disposable.
- Telemetry is bounded operational evidence, not private reasoning and not an acceptance metric by itself.

## 4. Architecture requirements

### 4.1 Canonical optimization graph

A graph contains canonical `project_id`, graph revision/digest and stable nodes for workstreams, contracts, validation gates and release gates. Each node carries bounded status, explicit dependencies, estimated remaining effort, optional integration cost and immutable acceptance ownership references. Cycles and dangling dependencies fail preflight. Serialized graph state must round-trip deterministically across process recreation.

### 4.2 Critical-path scheduler

The scheduler derives ready nodes from satisfied dependencies, computes deterministic downstream blocking cost and emits ranked `SchedulingDecision` data. It may account for bounded cost estimates, queue age and integration congestion but cannot treat occupancy or token use as success. Equal-priority ties are stable. Scheduling output contains no shell, repository mutation, lease mutation, provider call or deployment action.

### 4.3 Work stealing and worker identity

A `WorkStealProposal` names the existing worker execution, expected lease generation, source/path ownership set, reason and target worker capability class. A proposal is eligible only when dependency state is ready, no conflicting path owner exists, no protected mutation/provider side effect is in flight, and accepted P2-V0.16.1 lease semantics permit reassignment. Application of a proposal must occur through the existing worker recovery/lease service with CAS; stale generations fail closed.

### 4.4 Integration backpressure and safe cancellation

Server policy defines bounded integration capacity. When the number or estimated cost of READY-FOR-INTEGRATION items exceeds capacity, lower-criticality upstream work may be deferred. Cancellation/supersession is allowed only at checkpoints explicitly marked safe: before a new mutation starts, after a mutation is durably accepted and validated, or after a side effect's idempotent result is durably recorded. Unsafe cancellation returns a wait decision rather than forcing interruption.

### 4.5 Change-impact graph and validation selection

A machine-readable `ChangeImpactGraph` maps normalized repository path patterns/configuration identities to components, contracts, platforms and validation suites. `ValidationSelection` contains changed paths, proven impacted scopes, mandatory global invariants, selected checks, excluded checks with explicit evidence, graph digest and confidence. Missing mapping, conflicting mapping, changed impact configuration or confidence below server threshold expands to the conservative/full relevant set.

Full promotion suites cannot be excluded by impact selection at worker READY FOR INTEGRATION, integration acceptance or release boundaries.

### 4.6 Warm environment/cache identity

A reusable environment identity is a SHA-256 digest over canonical, secret-free values such as runtime/OS/architecture, toolchain versions, lockfile/dependency digests, build configuration digest, source lineage/materialization digest and cache schema version. Secret values, credentials, arbitrary environment values and mutable timestamps are excluded from identity and forbidden from persisted cache metadata. Missing/uncertain provenance makes the cache ineligible.

### 4.7 Reusable pattern registry

A pattern record contains canonical pattern ID/version/digest, type, bounded compatibility predicates, validation evidence refs, provenance scope and optional Project/public scope. Only previously validated patterns may be recommended. Recommendation never mutates source and does not bypass fresh validation after use.

### 4.8 Privacy-safe failure fingerprint and repair memory

A failure fingerprint is derived from normalized failure class/code, component/contract identity, bounded structural locator and normalized tool/test identity. Raw private source, raw logs, DOM, screenshot bytes, provider payloads, credentials, user content and hidden reasoning are excluded. Repair-memory records contain fingerprint, bounded repair class, outcome quality, compatibility constraints and provenance; Project-private records cannot be used across Projects.

### 4.9 Adaptive model routing

A routing policy maps task class, required capability, confidence/evidence quality and bounded cost/latency preference to an already-approved model class. Low confidence or protected/high-risk work may route upward; routine bounded work may route to a cheaper/faster approved class. Routing cannot change Work Specification acceptance, evaluator thresholds, tool/provider/network authority, production permissions or protected evidence precedence.

### 4.10 Specification preflight

Before implementation scheduling, preflight deterministically checks: graph cycles/dangling dependencies; contradictory requirements; acceptance criteria without deterministic validation coverage; requested authority exceeding the workstream/tool/provider contract; conflicts with Project Constitution or Architecture records; missing upstream protocol binding; and ambiguous ownership of acceptance criteria. Material failures block scheduling with typed findings.

### 4.11 Speculative integration

A speculative candidate may compose immutable source lineages and run development validation to reveal likely conflicts. It has a canonical digest and provenance but is explicitly `authoritative=false`; it cannot replace accepted lineage, satisfy merge/promotion gates, publish production artifacts, change worker ownership or mutate provider state.

### 4.12 Workstream sizing and acceptance ownership

Sizing may propose split/merge/rebalance operations based on dependency density, estimated validation cost and critical-path impact. Every acceptance criterion must remain assigned to exactly one owning workstream after a proposed transformation, with explicit dependency edges for shared prerequisites. A proposal with orphaned or duplicated acceptance ownership is invalid.

### 4.13 Development-performance telemetry

Telemetry records bounded phase observations with Project/run/workstream identity, phase enum, started/ended timestamps or duration, attempt/retry count, outcome class and bounded evidence references. It excludes prompt contents, hidden reasoning, raw source/logs, credentials and unrelated Project data. Aggregation reports validated-outcome lead time, critical-path blocked time, retry/stall/human wait and integration wait without turning token consumption or worker occupancy into primary success metrics.

## 5. Security and privacy

- Optimization data is Project-scoped unless an artifact is explicitly public/non-private and validated for cross-Project reuse.
- No persisted optimization contract accepts raw secrets, authorization headers, cookies, credential values, arbitrary environment variables, unrestricted URLs, raw private source contents, raw logs, DOM/screenshot payloads or hidden reasoning.
- Scheduler, impact selector, cache registry, repair memory, model router and telemetry components expose typed data only and grant no direct source/provider/deployment authority.
- Existing path ownership, worker lease/generation, Work Specification, source-lineage, Preview identity, evaluator and promotion bindings are immutable inputs to optimization decisions.
- Stale graph revisions, stale lease generations, mismatched Project/run identity, unknown cache provenance or incompatible pattern/repair memory fail closed.
- Optimization cannot weaken rate limits, credential controls, provider target registration, browser baselines/workflows, protected metrics or production-promotion approval.
- Development telemetry is bounded and must be safe to persist without exposing private prompts or chain-of-thought.

## 6. Failure and stop boundaries

Optimization returns typed blocked/conservative decisions rather than guessing when dependencies are unresolved, graph state is cyclic/incomplete, impact is uncertain, cache provenance is incomplete, work ownership conflicts, lease generation is stale, integration capacity is saturated, safe cancellation boundary is absent, reusable-pattern compatibility is uncertain, repair-memory scope is incompatible, model capability is insufficient, or preflight finds a material specification/authority/architecture conflict.

A blocked optimization decision never authorizes a source mutation, validation omission, lease takeover, provider side effect, production promotion or acceptance-policy change.

## 7. Reference harness

Permanent deterministic tests must prove DAG validation and restart-safe serialization; stable critical-path ordering; no work stealing across active lease/path ownership/single-writer boundaries; stale-generation rejection; integration backpressure; safe-boundary cancellation; conservative impact expansion; mandatory global invariants/full promotion suites; exact cache digest reuse and invalidation; secret rejection; validated pattern compatibility; Project isolation for repair memory; adaptive routing without authority/threshold changes; specification preflight findings; non-authoritative speculative integration; acceptance-preserving workstream rebalance; and bounded telemetry/validated-outcome metrics.

## 8. Non-goals

- implementing browser execution, screenshot capture or multimodal semantics;
- implementing source-repair mutation policy already owned by P2-V0.16.3;
- creating a second worker execution/lease/checkpoint/reassignment state machine;
- replacing protected evaluation, Work Specification approval or source-lineage acceptance;
- automatic GitHub merge, production deployment or provider production promotion;
- cross-Project learning from private source/log/prompt content;
- optimizing solely for utilization, token volume or number of simultaneous workers;
- provisioning production caches, credentials, storage or migrations in this workstream.

## 9. Acceptance criteria

### AC-01 Dependency graph is deterministic, durable and validatable
Workstreams, contracts, validation gates and release gates form a canonical restart-safe DAG with stable identities, deterministic serialization/digesting, cycle detection and dangling-dependency rejection. Process recreation yields the same graph and scheduling inputs.

### AC-02 Critical-path scheduling is deterministic and correctness-subordinate
Ready work is ranked by deterministic downstream blocking/remaining-cost signals with stable tie-breaking. Optimization targets validated outcome time and cannot grant mutation, lease, provider or deployment authority.

### AC-03 Work stealing preserves accepted worker lease, path ownership and single-writer guarantees
Steal/reassignment proposals reference the existing worker execution and expected lease generation, require conflict-free path ownership and safe state, and are applied only through accepted P2-V0.16.1 CAS semantics. Stale generations or in-flight protected mutations/side effects fail closed.

### AC-04 Integration backpressure and cancellation operate only at safe boundaries
Server-owned integration capacity can defer lower-criticality work. Cancellation/supersession cannot interrupt an in-flight mutation, accepted-lineage transition or unrecorded side effect; absent a safe checkpoint the controller returns WAIT rather than forcing cancellation.

### AC-05 Change-impact validation never omits uncertain or globally mandatory checks
Impact selection is bound to a versioned graph digest and exact changed paths. Unknown/conflicting/low-confidence impact expands validation, mandatory global invariants are always included, and full protected suites remain mandatory at worker READY FOR INTEGRATION, integration and release boundaries.

### AC-06 Warm environment/cache reuse is immutable, secret-free and provenance-complete
Reusable environments/caches are addressed by deterministic digest over approved secret-free toolchain/dependency/platform/config/source inputs. Missing or uncertain provenance invalidates reuse; secret-bearing material is rejected from identity and persisted metadata.

### AC-07 Reusable patterns are validated, compatible and cannot bypass fresh validation
Pattern/component/config recommendations require immutable digest/version, validation provenance and compatibility predicates. Project/private scope is respected and use of a pattern never advances accepted lineage or satisfies validation without fresh evidence.

### AC-08 Failure fingerprint and repair memory are privacy-safe and Project-isolated
Failure/repair memory stores bounded structural fingerprints, repair class and outcome/provenance only. Raw private source/log/DOM/image/provider/prompt/credential/hidden-reasoning content is rejected, and Project-private memory cannot influence another Project.

### AC-09 Adaptive model routing remains inside approved capability and protected-evaluation boundaries
Routing chooses only from approved model classes based on task capability/confidence and bounded cost/latency policy. It cannot alter Work Specification acceptance, evaluator thresholds, protected evidence precedence, tool/network/provider capabilities or production authority.

### AC-10 Specification preflight blocks contradictory, untestable or authority-conflicting work
Preflight deterministically identifies cycles/missing dependencies, contradictory requirements, acceptance criteria without validation coverage, architecture/constitution conflicts, excess authority requests and ambiguous acceptance ownership. Material findings block implementation scheduling with typed evidence.

### AC-11 Speculative integration and workstream rebalancing remain non-authoritative and acceptance-safe
Speculative candidates are immutable/disposable and explicitly cannot advance accepted lineage, merge/promotion gates or provider state. Sizing/rebalancing proposals preserve exactly one owner for every acceptance criterion and explicit dependency edges; orphaned/duplicate ownership is rejected.

### AC-12 Telemetry is bounded, privacy-safe and measures validated outcome time
Phase telemetry covers queue/planning/generation/environment/build/test/browser/visual/provider/retry/integration/stall/human wait with bounded Project/run/workstream identity and evidence. It excludes private reasoning/raw content/secrets and supports lead-time, critical-path-blocked, retry/stall/human/integration-wait measures rather than treating occupancy/token throughput as the objective.
