# Parallax 2.0 v0.8.0 — Approved-Spec Execution Binding

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.8.0
Depends on: P2-V0.7.0
Method: Spec-first protected execution contract + migration-backed binding + release verification

## 1. Objective

Make an explicitly approved user Work Specification the authoritative contract for every new Code engineering run. Code must not begin substantive execution against an unapproved, superseded, missing, or silently changed work specification.

The durable audit chain becomes:

`conversation → WorkSpecification revision → operator approval → EngineeringRun binding → stage evidence → protected verification`.

This release strengthens execution integrity only. It does not enable an unrestricted live shell, autonomous Git mutation, autonomous merge, or autonomous production deployment.

## 2. User outcome

When the operator enters Code mode, Parallax clearly shows whether the conversation is ready for implementation. Once a Work Specification is approved, starting Code creates or reuses a run bound to that exact approved specification revision. The run continues against that immutable binding even if a later draft is created. A materially changed objective requires a new approved revision and a new run rather than silently retargeting existing work.

## 3. Product/spec identity separation

Parallax continues to maintain two distinct specification identities:

- `Conversation.spec_id` is the product/policy/release specification governing Parallax itself.
- `WorkSpecification.id` + `revision` is the user's implementation contract for the current objective.

Engineering runs retain the product `spec_id` and additionally bind to one exact approved Work Specification.

## 4. Scope

### 4.1 Durable EngineeringRun binding

Every new v0.8 engineering run stores:

- `work_specification_id`;
- `work_specification_revision`;
- `work_specification_digest`.

The digest is computed server-side from the bounded, product-visible specification contract: ID, revision, title, objective, constraints, acceptance criteria, risks, and open questions. Approval timestamps/status are not part of the content digest so normal approval bookkeeping does not alter the contract identity.

The database fields are nullable only for compatibility with historical pre-v0.8 runs. The v0.8 service refuses to create a new unbound run.

### 4.2 Approval gate

Creating or activating a Code run requires:

- an existing Code conversation;
- conversation not in `SPEC_AMENDMENT`;
- an existing Work Specification explicitly requested by ID or resolved as the latest approved revision;
- Work Specification belongs to the same conversation;
- Work Specification status is `APPROVED`;
- stored revision is positive;
- product `spec_id` still matches the durable conversation product spec.

A `DRAFT` or `SUPERSEDED` Work Specification cannot start a new run.

### 4.3 Immutable run target

Once created, a run's Work Specification binding cannot be changed through activation, resume, stage advance, or client state refresh.

A later Work Specification draft or approval does not mutate the existing run. Starting implementation against the newly approved revision creates/reuses a separate run bound to that newer revision.

Historical runs created before v0.8 may remain readable but cannot be treated as approved-spec-bound evidence.

### 4.4 Server-owned acceptance map

The server derives stable acceptance IDs from the bound Work Specification in list order:

- first criterion → `AC-01`;
- second criterion → `AC-02`;
- and so on.

Clients, models, and tools may report evidence against these IDs, but they do not define the required set.

The run read contract exposes the immutable binding and acceptance map so the operator can see exactly what Code is executing against.

### 4.5 Protected stage gates

Protected validation uses the bound Work Specification acceptance map rather than trusting an evidence-supplied `required_acceptance_ids` list.

- `SPECIFY` proves the exact approved Work Specification binding and automatically advances a newly activated run to `PLAN`.
- `PLAN` must exactly cover the server-owned acceptance map.
- `BUILD` must declare the complete acceptance set targeted by the built candidate.
- `TEST` must report the complete acceptance set exercised by protected test evidence.
- `VERIFY` must report the complete acceptance set verified by protected verification evidence.
- `REVIEW` must verify the complete acceptance set and match independently persisted implementation workspace identity.

A mismatched, missing, duplicated, or extra acceptance ID fails the protected gate.

### 4.6 Activation API

Add a protected activation endpoint:

`POST /v1/engineering-runs/activate`

Request:

- `conversation_id`;
- optional `work_specification_id`;
- optional bounded `workspace_ref`.

Behavior:

- if `work_specification_id` is omitted, resolve the latest approved Work Specification for the conversation;
- if no approved specification exists, return a sanitized 422 explaining that operator approval is required;
- reuse the latest nonterminal run only when it is already bound to the exact same Work Specification;
- otherwise create a new run;
- automatically record the protected `SPECIFY` binding evidence and advance a new run to `PLAN`;
- repeated activation for the same run/spec is idempotent and does not duplicate stage evidence.

The existing low-level create/advance/control endpoints remain protected for internal/test compatibility, but `POST /activate` is the product path used by the client.

### 4.7 Conversation-native client behavior

In Code mode:

- if there is no approved Work Specification, show a concise blocked state: approval required before Code can start;
- an approved Work Specification exposes a `START CODE RUN` action;
- activating Code shows the bound Work Specification revision and acceptance count in the engineering status surface;
- if the latest Work Specification is a newer draft while a run is active, the run remains visibly bound to its older approved revision;
- the operator can still inspect/approve a newer draft, but the active run is never silently retargeted;
- reduced-graphics mode preserves the same semantic state and activation control.

The interface remains conversation-first and does not become a project-management dashboard.

## 5. Security and trust boundaries

- All activation/run/specification routes remain behind the existing private server authentication boundary.
- The client cannot mark a Work Specification approved.
- The client cannot choose or overwrite the server-owned required acceptance set.
- Work Specification digesting uses only bounded product-visible fields; no hidden reasoning, provider diagnostics, credentials, or environment values are included.
- Engineering evidence remains bounded and rejects forbidden secret/reasoning keys.
- Activation does not grant shell, Git, merge, Vercel, database-DDL, or production-deployment authority.
- Existing same-origin session, bearer compatibility, CORS, and secret-storage boundaries remain unchanged.

## 6. Persistence migration

Add an ordered production migration that adds nullable compatibility fields to `engineering_runs`:

- `work_specification_id` referencing `work_specifications(id)`;
- `work_specification_revision` integer;
- `work_specification_digest` bounded string;
- index on `work_specification_id`.

The migration does not fabricate bindings for historical rows. Production startup continues to perform no implicit DDL.

## 7. Acceptance criteria

### AC-01 Approved spec required

A new Code run cannot activate without an explicitly approved Work Specification belonging to the same conversation.

### AC-02 Immutable exact binding

A new run persists exact Work Specification ID, revision, and digest. Later drafts/approvals do not change that binding.

### AC-03 New approved revision creates new execution target

After a newer Work Specification revision is explicitly approved, activation against that revision does not reuse or retarget a run bound to an older revision.

### AC-04 Server-owned acceptance map

Acceptance IDs are deterministically derived from the bound Work Specification and exposed in run reads. Evidence cannot redefine the required set.

### AC-05 Protected PLAN coverage

PLAN passes only when its acceptance coverage exactly matches the server-owned acceptance set.

### AC-06 Protected BUILD coverage

BUILD passes only when the candidate evidence targets the complete server-owned acceptance set and existing execution-success requirements pass.

### AC-07 Protected TEST coverage

TEST passes only when protected test evidence exercises the complete server-owned acceptance set and execution-success requirements pass.

### AC-08 Protected VERIFY coverage

VERIFY passes only when protected verification evidence verifies the complete server-owned acceptance set and execution-success requirements pass.

### AC-09 Protected REVIEW coverage

REVIEW passes only when it verifies the complete server-owned acceptance set, recommends PASS, and matches independently persisted implementation workspace identity.

### AC-10 Activation idempotency

Repeated activation of the same conversation and exact approved Work Specification reuses the same eligible run and does not duplicate `SPECIFY` evidence.

### AC-11 Amendment containment

A conversation in `SPEC_AMENDMENT` cannot activate a Code run. Existing durable conversation/spec/run evidence remains preserved.

### AC-12 Historical compatibility

Pre-v0.8 engineering runs without Work Specification bindings remain readable and are clearly distinguishable from approved-spec-bound runs.

### AC-13 Client clarity

Code mode clearly communicates approval-required, ready-to-start, and bound-running states without hiding the Work Specification revision used by an active run.

### AC-14 Reduced-graphics parity

Reduced-graphics mode preserves the same approved-spec requirement, start action, and bound-run identity without CanvasKit.

### AC-15 Release integrity

Database migration, specification validation, API compile/tests, client typecheck/state/export, browser/Skia acceptance, protected Engineering/Reason/Code evaluation, DSPy release compilation, Vercel preview state, and production verification pass before v0.8.0 is recorded as deployment-verified.

## 8. Non-goals

- unrestricted live shell execution;
- arbitrary command execution;
- automatic Git commit/push/merge;
- automatic Vercel promotion;
- autonomous production deployment;
- automatic model approval of Work Specifications;
- editing an approved Work Specification in place;
- rewriting historical engineering-run bindings;
- replacing `Conversation.spec_id` with the user Work Specification identity.

## 9. Risks and mitigations

- **Old run ambiguity:** expose nullable binding for historical runs and require binding for every new v0.8 run.
- **Client-defined acceptance cheating:** derive acceptance IDs server-side and ignore evidence-supplied required sets as authority.
- **Silent retargeting:** persist immutable ID/revision/digest and reuse only exact-bound runs.
- **Spec lifecycle race:** resolve/validate approval inside the service immediately before run creation; persist exact revision/digest.
- **UI clutter:** extend the existing compact specification and engineering status surfaces rather than adding a dashboard.
- **Migration risk:** additive nullable columns only; no destructive rewrite or fabricated historical data.

## 10. Release gate

Implementation is authorized by this specification. Production promotion requires the additive migration to be applied before the new API deployment receives traffic, the existing full release-grade gates to pass on the exact candidate tree, and production evidence to confirm route/database/readiness integrity. `ARCHITECTURE.md` and `CURRENT-STATE.md` must be updated because the durable execution trust boundary changes. `DESIGN-SYSTEM.md` changes only if implementation introduces a new durable visual rule.
