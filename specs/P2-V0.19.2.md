## 1. Objective

Enable Parallax to determine whether an approved engineering objective should use one agent or a bounded multi-agent development team, choose only compatible admitted agents, schedule dependency-safe work, and recover or reassign failed labor without requiring the operator to manually manage agents and without creating a second worker, source-lineage, validation or release authority path.

S2 composes the accepted S1 agent protocol with the existing Parallax durable worker lease/checkpoint/recovery and single-writer source-lineage architecture. It produces deterministic orchestration decisions and bounded evidence. It does not make agent self-reported capability authoritative, accept source lineage, judge candidate quality, weaken protected validation, grant tools/provider scope, merge, deploy or cross REVIEW/HUMAN_REQUIRED.

The simplest adequate team is preferred. Multi-agent execution is justified only when the approved objective contains independently schedulable work whose admitted requirements can be satisfied safely in parallel or when bounded recovery requires reassignment. A task that gains no material dependency-safe benefit from parallelism remains a one-agent task.

## 2. Fixed decisions

- **S1 is the immutable agent boundary.** S2 consumes accepted `AgentIdentity`, task/result/checkpoint and admission contracts from `agent_protocol.py`; it does not fork or redesign them.
- **Parallax forms the team.** Agent/provider content cannot choose its own role, expand its capability set, add teammates, rewrite dependencies, claim canonical mutation authority or select itself by provider preference.
- **Server-owned admission outranks declarations.** S1-declared work kinds/capabilities are descriptive evidence. S2 additionally requires a server-owned orchestration policy/snapshot that explicitly admits an exact agent identity digest for bounded work kinds/capabilities before that evidence can satisfy a team requirement.
- **Use the smallest adequate team.** One compatible agent is the default when the work is serial, overlapping, too small to justify coordination, or cannot be proven dependency-safe. Multi-agent execution is bounded and only used when independent work can make meaningful progress without violating shared-path/single-writer constraints.
- **Dependency graph is explicit and deterministic.** Work units have stable IDs, bounded acceptance ownership, dependencies, required work kinds/capabilities and coordination/mutation classification. Cycles, duplicate ownership or ambiguous dependency relationships fail closed.
- **Parallel labor never means parallel canonical mutation.** S2 may schedule independent evidence/proposal work concurrently, but canonical source acceptance remains single-writer under the existing protected runtime. Any work that may affect the same canonical mutation domain is serialized or blocked.
- **Existing durable worker authority remains canonical.** Worker leases, generations, checkpoints, stall classification, recovery and reassignment remain owned by the existing worker-recovery layer. S2 consumes those facts and emits team-level scheduling/reassignment evidence; it does not create a competing durable worker state machine.
- **Recovery uses trustworthy evidence.** Reassignment requires exact current task identity plus S1-admitted result/checkpoint evidence and/or authoritative worker health/stall evidence. Agent self-report alone cannot declare itself stalled, healthy, complete or eligible for replacement.
- **Replay is deterministic.** The same bound objective, work graph, admitted roster and orchestration policy produce the same team-plan identity and dispatch identities. Replaying an already-issued work assignment does not create duplicate work or a second canonical authority action.
- **Quality judgment is not S2.** S2 may record completion/failure/latency/usage facts supplied by admitted evidence, but it cannot declare an implementation good, accepted or preferred. S3 owns independent quality judgment.
- **Economics are not S2 routing authority.** S2 emits provenance-bound team/dispatch timing, retry and usage evidence that S4 may later consume. S2 does not optimize by cost/quality/time history or fabricate performance claims.
- **Human boundaries remain explicit.** Missing compatible agents, irreducible dependency ambiguity, conflicting mutation ownership, exhausted bounded recovery, unsupported capability or authority requirements produce deterministic `HUMAN_REQUIRED`/blocked evidence rather than guessed orchestration.

## 3. Architecture requirements

### 3.1 Exact orchestration identity

Define an immutable S2 orchestration identity bound to at least:

- exact Project ID;
- exact Engineering Run ID;
- exact Work Specification ID, revision and digest;
- exact stable acceptance IDs;
- accepted S1 protocol version;
- server-owned orchestration policy digest;
- bounded objective/work-graph digest;
- admitted roster snapshot digest.

Identity construction rejects malformed canonical IDs, invalid Work Specification digests, empty/duplicate acceptance IDs, unsupported protocol versions and mismatched Project/run/spec evidence.

### 3.2 Server-owned admitted roster

Define bounded immutable roster/policy evidence that distinguishes:

- S1 agent identity/declaration evidence; from
- server-owned admission of an exact `AgentIdentity.digest` for specific work kinds/capabilities.

A roster entry must not contain credentials, arbitrary commands, provider endpoints, raw provider payloads, user/model-defined capability grants or deployment authority. Duplicate agent identity, conflicting admission, unknown identity digest and over-limit roster size fail closed.

Selection requires both:

1. the agent's S1 identity declares the required work kind/capability evidence; and
2. the server-owned policy admits that exact identity digest for the requirement.

Neither condition alone is sufficient.

### 3.3 Bounded work graph

Define an immutable work graph containing stable bounded work-unit IDs. Each work unit contains at minimum:

- bounded work kind;
- exact acceptance-ID subset it contributes evidence toward;
- explicit dependency IDs;
- required admitted capability identifiers;
- shared/mutation domain identifiers used only for coordination;
- whether the work is evidence/proposal-only or requires later serialized protected canonical mutation;
- bounded context/evidence references, never raw secrets/provider payloads.

Graph validation rejects:

- cycles or self-dependencies;
- missing dependency IDs;
- duplicate work-unit IDs;
- acceptance IDs not present in the approved specification;
- ambiguous or duplicate authoritative acceptance ownership where the Work Specification requires one owner;
- incompatible shared/mutation domains represented as parallel-safe;
- unbounded graph size/depth/fan-out.

### 3.4 One-agent versus multi-agent formation

The team planner deterministically computes the smallest adequate plan.

A one-agent plan is selected when:

- one admitted agent can satisfy all currently schedulable requirements; and
- the graph is serial, materially overlapping, or has no proven parallel benefit; or
- parallelism would violate a shared/mutation domain or protected dependency.

A multi-agent plan may be selected only when:

- at least two graph nodes are dependency-ready at the same time;
- each ready node has a compatible admitted agent;
- their shared/mutation domains are proven non-conflicting for the planned concurrent phase;
- team size and parallelism remain within server-owned hard bounds; and
- no additional capability/authority is created by forming the team.

The planner must not use provider name/order as an implicit preference. Deterministic tie-breaking uses server-owned stable identifiers/policy only.

### 3.5 Deterministic assignment and dispatch

For each assignment, generate stable bounded orchestration evidence containing:

- team-plan ID;
- work-unit ID;
- exact selected S1 agent identity digest;
- exact S1 `AgentTaskBinding`/request identity or deterministic inputs required to create it;
- dependency snapshot/digest;
- assignment generation/attempt identity;
- scheduling disposition (`READY`, `WAITING_DEPENDENCY`, `SERIALIZED_MUTATION`, `BLOCKED`, or equivalent);
- no authority-bearing executable command, URL, credential or source writer.

An assignment is not Engineering Run authority and cannot advance a protected stage merely because it is dispatched or completed.

### 3.6 Parallel-safety and single-writer preservation

S2 must explicitly prevent unsafe parallelism.

- Work units sharing a protected mutation domain are never admitted as concurrent canonical writers.
- Evidence/proposal work may execute concurrently only when its declared coordination domains do not conflict.
- Candidate/proposal output from parallel agents remains isolated evidence until the existing protected source-mutation/lineage path serially admits any canonical change.
- S2 cannot create or advance source-lineage heads, bypass compare-and-swap, write to a canonical workspace, merge source, or reinterpret isolated candidate output as accepted lineage.
- Unknown overlap is treated conservatively as conflict/serialization rather than parallel-safe.

### 3.7 Durable worker/recovery composition

S2 must consume existing durable worker facts rather than replace them.

Team recovery decisions may inspect bounded authoritative evidence equivalent to:

- current worker execution identity;
- lease generation/status;
- current durable checkpoint revision;
- current step;
- stall classification and next protected recovery action;
- last meaningful progress timestamp/counters;
- exact S1 admitted checkpoint/result evidence for the current assignment.

Recovery/reassignment may be proposed or scheduled only when current authoritative worker evidence permits it. Stale lease generations, stale assignment attempts, late results from revoked assignments and mismatched checkpoints are rejected.

A reassignment preserves canonical Project/run/Work Specification/work-unit identity while creating an explicit new assignment/attempt generation. The prior agent's late completion cannot displace the newer assignment.

### 3.8 Bounded recovery policy

Define server-owned hard bounds for at least:

- maximum team size;
- maximum simultaneous ready assignments;
- maximum reassignments per work unit;
- maximum orchestration attempts/replans;
- maximum no-progress/repeated-failure state before bounded stop or `HUMAN_REQUIRED`.

Exhaustion returns deterministic bounded status. It does not recursively create more agents, weaken acceptance, expand authority or retry indefinitely.

### 3.9 Replay and idempotency

A deterministic team-plan digest/ID is derived from the exact orchestration identity, validated work graph, admitted roster snapshot and policy.

Replay behavior must distinguish:

- exact same plan replay;
- same work unit/assignment replay;
- new assignment generation after authoritative reassignment;
- stale result/checkpoint from an older generation;
- graph/policy/roster/spec drift requiring a distinct plan or fail-closed decision.

Exact replay returns the same immutable identities/evidence and does not duplicate dispatch authority or canonical mutation.

### 3.10 Orchestration evidence for S3/S4/operator visibility

Expose bounded deterministic team/orchestration evidence including, where available:

- plan/team identity and disposition;
- selected admitted agents by bounded identity only;
- work-unit dependency/assignment state;
- assignment/reassignment count;
- admitted result/checkpoint references;
- observed elapsed/usage evidence from S1 with explicit missingness/provenance;
- blocked/HUMAN_REQUIRED reason codes.

S2 evidence must not include raw prompts, hidden reasoning, provider payloads, credentials, unbounded logs, source blobs, cross-Project private evidence or fabricated quality/cost/time conclusions.

### 3.11 Process recreation

A deterministic orchestration snapshot can be reconstructed from immutable plan/assignment evidence plus current authoritative worker/S1 facts. Process recreation must not rely on in-memory agent objects, provider-native sessions or local filesystem state as canonical truth.

Reconstruction of the same current facts yields the same ready/waiting/blocked assignment state. Changed worker generation, admitted checkpoint, roster/policy version or exact Work Specification identity is explicitly detected rather than silently reused.

## 6. Security

All agent/source/provider content remains untrusted evidence. S2 orchestration authority is limited to selecting from server-admitted S1 identities, producing bounded assignment/scheduling evidence and coordinating with existing protected worker recovery.

Agent declarations cannot satisfy a work requirement unless a server-owned policy independently admits that exact identity digest for the required work/capability. Repository or model text cannot add a roster entry, capability, dependency override, provider endpoint, credential, command or deployment permission.

Cross-Project identity is exact. No plan, work unit, assignment, result, checkpoint or usage evidence can be reused across Projects/runs/Work Specifications merely because objective/source content is similar.

Unknown dependency or shared-path/mutation overlap is unsafe by default. S2 serializes or blocks it rather than assuming parallel safety.

Late success from a revoked/stale assignment cannot restore authority after durable worker reassignment. Existing worker lease generation/checkpoint authority and S1 admission checks must be current before recovery evidence can influence scheduling.

S2 never treats agent completion, confidence, claimed acceptance coverage or self-reported quality as protected validation/acceptance. Deterministic/protected validators and later S3 independent judgment remain structurally separate.

## 7. Acceptance criteria

### AC-01 Exact team-orchestration identity is canonical and fail-closed
Every orchestration plan binds exact Project, run, Work Specification ID/revision/digest, stable acceptance IDs, accepted S1 protocol version, server-owned policy digest, work-graph digest and admitted-roster digest. Malformed/mismatched identity or drift produces a bounded non-ready decision.

### AC-02 Agent eligibility requires both S1 declaration and server-owned admission
Tests prove an agent is eligible only when its exact S1 identity declares the required work/capability and a server-owned policy admits that exact identity digest for it. Agent/provider/repository content cannot self-expand eligibility, tools, network/provider scope or credentials.

### AC-03 Planner chooses the smallest adequate one-agent or multi-agent team
Deterministic fixtures prove serial/overlapping work stays single-agent while materially independent dependency-ready work can form a bounded multi-agent team. Team size is capped, tie-breaking is deterministic and provider name/order is not implicit preference.

### AC-04 Dependency graph validation prevents unsafe or ambiguous parallelism
Cycles, missing dependencies, duplicate work-unit IDs, acceptance IDs outside the approved contract, conflicting ownership and unknown/shared mutation overlap fail closed or serialize. Only proven dependency-ready non-conflicting work can be concurrent.

### AC-05 Canonical single-writer/source-lineage authority is preserved
Parallel assignments may produce isolated evidence/proposals but cannot create/advance source-lineage heads, bypass compare-and-swap, write canonical source, merge candidate fragments or represent agent output as accepted lineage. Work sharing a protected mutation domain is serialized.

### AC-06 Dispatch identities are deterministic, exact-bound and replay-safe
Each assignment binds plan/work-unit/agent/task/dependency/generation identity. Exact replay returns the same bounded assignment evidence without duplicate dispatch/canonical action; spec/graph/policy/roster drift is detected rather than silently replayed.

### AC-07 Recovery and reassignment compose with existing durable worker authority
S2 consumes authoritative worker lease/checkpoint/stall evidence plus S1-admitted evidence. It does not create a competing worker state machine. Failed/stalled labor can be reassigned while preserving canonical Project/run/spec/work-unit identity and incrementing an explicit assignment generation.

### AC-08 Stale lease/result/checkpoint and late completion fail closed
Tests cover stale worker generation, stale assignment attempt, late result after reassignment, duplicate result, mismatched checkpoint and revoked assignment. None can displace the current assignment, resurrect old work, advance canonical source or create a second protected action.

### AC-09 Bounded recovery terminates no-progress and repeated failure
Server-owned limits cap team size, concurrency, per-work-unit reassignment and orchestration retry/no-progress behavior. Exhaustion deterministically stops or returns `HUMAN_REQUIRED`; S2 cannot recursively add agents, retry forever or weaken protected acceptance.

### AC-10 S2 evidence is provenance-bound and safe for S3/S4 without inventing quality
Team/assignment/reassignment/dependency and S1 usage observations retain exact provenance and explicit missingness. S2 emits no fabricated quality/cost/time claims, implementer self-evaluation as acceptance, raw provider payloads, prompts, hidden reasoning, credentials, unbounded logs or cross-Project evidence.

### AC-11 Process recreation preserves deterministic orchestration state
Given the same immutable plan/assignment evidence and current authoritative S1/worker facts, process recreation yields the same ready/waiting/blocked/reassigned state without provider-native session, local filesystem or in-memory agent state as authority. Changed generation/policy/roster/spec facts are explicitly detected.

### AC-12 Existing protected runtime and human/release ceilings remain authoritative
S1, Engineering Run, durable worker recovery, source lineage, governed skills/tools/service bindings, protected validation/evaluation, Preview delivery and REVIEW/HUMAN_REQUIRED semantics remain unchanged. Relevant API/protected-autonomy regression suites stay green.

### AC-13 Exact-head worker boundary and dependency handoff
`P2-V0.19.2` validates with authentic DSPy metadata before semantic implementation. Final S2 diff remains within #265 ownership; exact-head Workstream Spec Validation, P2 CI and Bounded Autonomy pass; PR targets `integration/wave6-agentic-control-plane`; worker stops `READY FOR INTEGRATION` with no worker merge/deploy. S4/S5/S6 dependencies are not bypassed.
