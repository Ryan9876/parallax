## 1. Objective

Make the accepted #46 app-builder evaluator consume evidence derived from the actual persisted Wave 2 runtime and provider path rather than hand-authored success fixtures, and prove a deterministic protected reference-app flow through Project binding, approved Work Specification, PLAN, repository bootstrap, typed IMPLEMENT proposal, safe mutation, durable accepted source lineage, exact-lineage BUILD/TEST/VERIFY, bounded GitHub publication, Vercel Preview, protected #46 evaluation, and explicit operator REVIEW.

The proof must survive process/runtime recreation and retries without duplicate source mutation or duplicate provider publication. Failure, denial, stale identity, wrong source, missing preview, and evidence-hygiene violations must remain fail-closed under the unchanged #46 critical-failure/threshold semantics.

## 2. Fixed decisions

- #46 scoring, categories, critical-failure behavior, thresholds, evaluator version, and promotion authority are unchanged.
- Runtime success observations are derived only from persisted Project, Work Specification, Engineering Run/attempt, durable source-lineage, same-lineage execution, and persisted #79 provider-delivery/audit facts.
- The evidence adapter is read-only. It does not create alternate Project identity, source lineage, provider authority, audit storage, release state, or stage-success state.
- #79 owns repository bootstrap + verified-source publication orchestration and durable provider delivery records. #80 may develop against a narrow consumer protocol in parallel but must reconcile that protocol to accepted #79 before READY FOR INTEGRATION.
- Canonical Project identity is `Project.id` / persisted `EngineeringRun.project_id`; `workspace_ref` remains opaque metadata and is never filesystem or provider authority.
- The accepted IMPLEMENT lineage is the durable #68 current lineage for the same Project/run and must match persisted IMPLEMENT evidence. BUILD/TEST/VERIFY must all prove execution against that exact lineage and content digest.
- GitHub publication and Vercel Preview facts must be backed by bounded #62/#70 provider action evidence plus Wave 1 tool audit identities/outcomes. Provider denial/failure is never rewritten as success.
- Operator REVIEW remains explicit and occurs only after protected #46 evaluation passes. Merge, production promotion, production deployment, aliases/domains, and environment/secret mutation remain outside this workstream.

## 3. Runtime evidence adapter

Add a narrow protected adapter that reads one Engineering Run and produces #46 `AppBuilderRecordedEvidence` only after it can prove a coherent runtime snapshot.

The adapter must verify:

1. **Project** — owner-scoped Project exists, is active, matches `EngineeringRun.project_id`, and its repository binding matches the provider-delivery record.
2. **Work Specification** — bound Work Specification exists, belongs to the run Conversation, is APPROVED or SUPERSEDED, revision matches the run, and the canonical `work_specification_digest(...)` equals the persisted run digest.
3. **IMPLEMENT** — one durable passing IMPLEMENT attempt binds the same canonical Project/run, identifies an accepted post-mutation source lineage, contains bounded artifact/workspace/proposal/source-context digests, preserves `protected_stage_authority=false`, and does not claim network/Git/deployment mutation authority.
4. **Durable lineage** — accepted current lineage resolves from durable #68 storage for the same Project/run, matches persisted IMPLEMENT lineage identity, has the expected parent, and content digest remains exact.
5. **BUILD/TEST/VERIFY** — durable passing attempts exist in order and each records server-owned Project + exact accepted lineage identity, same-lineage execution, matching source content digest, no fresh repository checkout, protected success, and exact acceptance coverage.
6. **Provider delivery** — a persisted verified #79 delivery record exists for the same Project/run/repository/accepted lineage/content digest and exposes only bounded provider action/audit facts. GitHub commit/PR and Vercel Preview status/identity must be attributable to SUCCEEDED provider actions whose audit outcome is SUCCEEDED and whose request/result digests are valid.
7. **Evidence hygiene** — no raw source bytes, provider payloads, tokens, credentials, headers, cookies, environment, hidden reasoning/scratchpad, arbitrary logs, filesystem roots, or unbounded strings are admitted to #46 evidence.

The adapter must represent denial/failure/retry/replay distinctly. It may fail closed before constructing `AppBuilderRecordedEvidence` when durable facts are incoherent or unsafe; it must never fill gaps with inferred success.

## 4. #79 narrow delivery protocol

Until #79 is accepted, #80 may depend on a minimal read-only consumer protocol equivalent to:

- fetch one persisted delivery record by canonical Project/run/accepted-lineage identity;
- expose canonical repository identity, accepted lineage/content digest, provider action evidence + tool audit records, and replay/resume markers only;
- never expose credentials, raw provider requests/responses, source bytes, arbitrary URLs, generic transport, or mutation methods to the evidence adapter.

The reference harness may additionally use a narrow delivery-driver seam for bootstrap/publish in deterministic tests, but production evidence reads must come from the persisted #79 record view. Final #80 readiness requires replacing/adapting this provisional seam to the exact accepted #79 API without weakening any check.

## 5. Protected reference benchmark

Add a reference-runtime promotion suite executed through the unchanged #46 evaluator. Keep all category and aggregate floors at 1.0 and all core requirements critical.

Required positive observations, when supported by facts, cover:

- canonical Project/repository binding and cross-project denial;
- exact approved Work Specification revision/digest binding;
- bounded safe IMPLEMENT mutation plus accepted durable lineage;
- same-lineage BUILD/TEST/VERIFY success with no unrelated/fresh source;
- authorized GitHub publication and READY Vercel Preview backed by provider audits;
- process recreation/retry preserving run/operation/lineage/publication identity with no duplicate mutation/publication;
- bounded observable-only evidence with no secret or hidden-reasoning content;
- operator ceiling: preview/evaluation may pass, but merge/production/deployment authority remains false.

Suite expected Project/workspace/spec values must be bound from the durable runtime snapshot at evaluation time rather than hard-coded fake identities. Benchmark requirements may be static; candidate success evidence may not be hand-authored.

## 6. Reference-app harness

The deterministic harness must exercise the actual accepted service boundaries, using isolated deterministic provider/runtime doubles only at already-defined external seams:

1. create/select a persisted owner-scoped Project and Project-bound Code Conversation;
2. create and explicitly approve a Work Specification;
3. activate the canonical Engineering Run and persist SPECIFY + PLAN;
4. repository bootstrap through the narrow #79 delivery seam into durable #68 source lineage;
5. generate a typed #61 `ImplementationProposal` through an injected deterministic generation coordinator;
6. apply it only through the existing safe implementation engine and accept the durable child lineage;
7. recreate request/service/runtime composition;
8. prove exact IMPLEMENT operation replay without another source mutation;
9. execute BUILD/TEST/VERIFY against the accepted lineage only and persist protected stage evidence;
10. recreate provider/delivery composition and publish the exact verified lineage through existing GitHub provider actions, then request/read Vercel Preview;
11. retry publication and prove no duplicate commit/PR/preview/provider mutation;
12. derive #46 recorded evidence from persisted facts and require protected evaluation pass;
13. require an explicit operator REVIEW call before the Engineering Run may complete.

No live production credentials, storage provisioning, migration application, merge, or deployment is required or allowed for this deterministic proof.

## 7. Deliberate negative cases

The harness/evidence tests must cover at least:

- wrong Project identity;
- wrong or stale Work Specification ID/revision/digest;
- stale/different accepted source lineage or provider parent revision;
- false BUILD/TEST/VERIFY success evidence;
- provider authority denial;
- provider execution failure;
- interrupted execution followed by recreation/resume;
- duplicate IMPLEMENT retry;
- duplicate publication retry;
- missing Vercel Preview or non-READY Preview;
- secret-bearing/provider-raw/hidden-reasoning evidence;
- BUILD/TEST/VERIFY or publication from unrelated/fresh source.

Every case must either fail evidence construction or produce a #46 evaluation whose `protected_pass` is false. No negative case may be normalized into a passing observation merely to satisfy the reference suite.

## 8. Process recreation and idempotency

Process recreation is a proof requirement, not an in-memory object reuse test.

- Recreate SQLAlchemy Session/repositories/EngineeringRunService between meaningful stages.
- Recreate implementation/runtime composition after accepted IMPLEMENT and replay the exact operation key; existing durable attempt + lineage facts must return the accepted result without reapplying source mutation.
- Recreate the #79 delivery composition before publish retry; persisted delivery/provider identities must cause exact replay/reuse rather than duplicate branch/commit/PR/preview mutation.
- Recreate the evidence adapter and resolve the same Project/spec/run/lineage/provider facts before #46 evaluation.
- Disposable workspace/provider client objects may disappear between steps; correctness must depend on durable records and immutable lineage, not process-local dictionaries.

## 9. Evidence mapping rules

#46 evidence fields remain bounded and use existing digest formats.

- `project_ref`: canonical Project UUID.
- `workspace_ref`: Project's opaque `project:<uuid>` metadata only.
- `spec_ref`: persisted Work Specification ID.
- `spec_revision`: persisted bound revision.
- `spec_digest`: `sha256:<canonical work specification digest>`.
- `run_ref`: canonical Engineering Run UUID.
- observations: only normalized bounded facts derived from verified durable/provider state.
- evidence digests: bounded canonical digests of Project/spec/run/lineage/stage/provider audit facts; never raw source/provider state.

Provider audits must preserve request/capability/tool/action/approval identities, authority decision, DENIED/SUCCEEDED/FAILED outcome, request/result digests, result code, and bounded result identity. Secret-bearing fields are not part of the accepted audit contract.

## 10. Non-goals

- changing #46 evaluator code, thresholds, category floors, critical semantics, or existing benchmark expectations;
- creating a second Project identity, source-lineage system, provider authority system, or provider audit persistence system;
- generic HTTP, shell, arbitrary Git, arbitrary provider API, repository creation, dependency-install, or production release authority;
- interpreting `workspace_ref` as filesystem/provider authority;
- storing raw source or provider payloads as evaluation evidence;
- production migrations/storage/credential provisioning;
- merge, production promotion, production deployment, alias/domain/environment/secret mutation;
- authoritative project-record updates before integration.

## 11. Acceptance criteria

### AC-01 Persisted canonical Project/run binding
The adapter accepts only a persisted Project-bound Engineering Run whose owner-scoped canonical `Project.id` matches `EngineeringRun.project_id`, whose Project is active, and whose repository identity matches the persisted delivery record. `workspace_ref`, caller/model input, filesystem paths, or provider metadata cannot substitute for Project identity.

### AC-02 Exact approved Work Specification binding
The adapter proves the persisted Work Specification ID, Conversation ownership, APPROVED/SUPERSEDED status, revision, and canonical digest exactly match the Engineering Run binding. Wrong/stale spec identity, revision, or digest fails closed and cannot yield passing `spec.binding` evidence.

### AC-03 Accepted IMPLEMENT lineage truth
Passing IMPLEMENT evidence must identify the same Project/run, bounded safe-patch artifacts/workspace/proposal/source-context digests, no external/Git/deployment mutation authority, and one accepted child lineage. The durable current lineage must match that child identity/content digest and parent relationship; stale/unrelated lineage fails closed.

### AC-04 Same-lineage BUILD/TEST/VERIFY truth
Durable passing BUILD, TEST, and VERIFY attempts must each prove protected success against the exact accepted lineage/content digest, server-owned Project identity, same-lineage execution, no fresh repository checkout, and exact acceptance coverage. False stage evidence or unrelated source cannot be promoted.

### AC-05 Persisted provider publication/preview audit truth
GitHub publication and Vercel Preview observations are derived only from the accepted #79 persisted delivery record containing bounded #62/#70 provider evidence plus matching Wave 1 tool audits. DENIED, FAILED, stale-parent/source mismatch, missing preview, and non-READY preview remain distinct non-success conditions.

### AC-06 Bounded observable-only #46 evidence
Constructed `AppBuilderRecordedEvidence` contains only bounded canonical IDs, normalized observations, and canonical digests. Raw source, provider payloads, credentials/tokens/headers/cookies/environment, hidden reasoning/scratchpad, arbitrary logs, and local filesystem roots are rejected or excluded.

### AC-07 IMPLEMENT recreation/retry idempotency
After accepted IMPLEMENT, recreating Session/service/runtime composition and retrying the exact IMPLEMENT operation returns the persisted accepted result without a second source mutation or a new lineage. A different/stale operation or lineage cannot be treated as replay.

### AC-08 Provider recreation/retry idempotency
After verified publication/preview, recreating #79 delivery/provider composition and retrying the same verified-source delivery reuses the persisted commit/PR/preview identities without another provider mutation. Different Project/run/lineage/provider parent cannot reuse that delivery.

### AC-09 Protected reference-app loop + operator REVIEW ceiling
The deterministic reference harness exercises Project → approved Work Spec → PLAN → bootstrap → typed proposal → safe mutation → durable lineage → exact-lineage BUILD/TEST/VERIFY → GitHub publication → READY Vercel Preview → unchanged #46 protected evaluation → explicit operator REVIEW. Evaluation/provider success alone cannot merge, production-promote, deploy, or complete REVIEW.

### AC-10 Deliberate negative protected rejection
Wrong Project/spec, stale lineage/provider parent, false stage evidence, provider denial/failure, interrupted/retry edge cases, missing/non-ready preview, secret-bearing evidence, duplicate retries, and unrelated/fresh source are covered deterministically. Each fails evidence construction or yields `protected_pass=false` under unchanged #46 semantics.

### AC-11 #46 scoring and authority remain unchanged
No #46 evaluator scoring, category, minimum threshold, critical-failure, evaluator-version, or protected promotion logic is weakened or special-cased for P2-V0.15.10. The reference runtime suite uses the accepted evaluator with 1.0 aggregate/category floors and critical core requirements.

### AC-12 Reconciled #79 contract and exact-head integration readiness
Before READY FOR INTEGRATION, the provisional narrow delivery protocol is reconciled to accepted #79 without a competing persistence/authority path. P2-V0.15.10 spec + authentic compiled DSPy plan, focused reference/evidence tests, full API regression, deterministic Workstream Spec Validation, Parallax P2 CI, and Bounded Autonomy Pilot all pass on the same exact head targeting `integration/wave2-app-builder`, with no merge/deploy/migration/provisioning.
