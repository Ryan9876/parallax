## 1. Objective

Implement concrete server-owned GitHub and Vercel preview clients underneath the exact accepted `GitHubProviderClient` and `VercelProviderClient` Protocols from #62 without broadening the accepted #45/#62 authority model.

The client layer translates one already-authorized typed provider action into one bounded authenticated provider API operation. It must preserve canonical Project, repository, source revision, and accepted source-lineage binding; normalize failures into bounded secret-safe provider errors; support safe idempotent retry; and keep Vercel preview as the autonomous deployment ceiling.

## 2. Scope

This workstream owns additive concrete client modules, a server-only scoped credential lease/provider abstraction, focused deterministic client tests, and this workstream specification/compiled plan.

GitHub client scope is exactly the existing `GitHubProviderClient` methods:

- resolve one configured `github:owner/repository`, default branch, and exact head revision;
- read one bounded recursive tree at an exact source revision;
- read one bounded UTF-8 source file at an exact source revision;
- create one bounded `parallax/...` branch at an exact base revision;
- write bounded accepted-lineage files to that branch with exact expected-parent protection;
- create one pull request bound to the exact repository, head branch, and expected head revision;
- read one pull request into the existing bounded typed result.

Vercel client scope is exactly the existing `VercelProviderClient` methods:

- request one preview deployment for a server-registered Vercel Project from an exact GitHub repository/source revision and accepted lineage;
- read one preview deployment into the existing bounded typed status/identity/URL result.

The existing #62 action layer remains responsible for canonical Project/action authorization and post-client result binding. This workstream does not edit or redefine #62 `common.py`, `github.py`, or `vercel.py`, and does not edit the #45 registry/contracts.

## 3. Fixed decisions and interfaces

- The concrete clients implement the exact #62 Protocol signatures. No provider action or user/model-visible request field is added.
- `httpx` may be used only as an internal server implementation detail. No generic URL/method/body/header transport object is accepted from model/user request data or exposed as a provider action.
- Provider credentials are acquired through an injected server-side credential-provider interface returning a redacted scoped credential lease bound to the provider resource. Credential material never appears in #62 request/result/evidence contracts.
- GitHub architecture prefers GitHub App installation credentials or equivalently fine-grained repository-scoped short-lived credentials. A broad long-lived PAT is not the default credential source and no PAT/environment loader is introduced by this workstream.
- Vercel architecture prefers short-lived/scoped server credentials such as OIDC-derived or equivalent scoped credentials when supported. No production credential is provisioned here.
- Credential leases validate provider/resource binding and expiration before use. Their repr/string form never reveals the bearer token.
- Provider response bodies and provider exception text are not propagated into `ProviderClientError`, audit records, evaluation evidence, or logs intended for models/UI.
- All provider HTTP status/transport failures map to bounded normalized codes such as credential unavailable/expired, auth denied, not found, rate limited, conflict/stale source, timeout, invalid provider response, or provider unavailable.
- GitHub reference updates are never forced. Exact current head is checked before branch publication, commit publication, and pull-request creation.
- Idempotent retries recognize an already-created exact branch, exact accepted-lineage commit, or exact matching pull request instead of creating uncontrolled duplicates.
- Vercel preview creation sends an explicit preview target and rejects any provider result that does not remain preview-scoped. No production promotion, alias/domain mutation, environment/secret mutation, or arbitrary deployment configuration method exists.

## 4. Credential model

A scoped credential lease contains only server-internal bearer material plus bounded provider/resource identity, credential kind, and optional expiration metadata. It must:

- be issued for exactly one provider and one registered resource identity;
- reject empty or expired credentials before network use;
- redact secret material from repr/string/equality diagnostics;
- expose no serialization helper intended for model/UI/evaluation payloads; and
- remain injectable so CI can use deterministic fake credentials without source-controlled secrets.

Concrete clients receive a provider-specific credential provider, not a raw token parameter on individual action methods. Integration / Control Tower owns binding that provider to GitHub App installation token issuance, Vercel OIDC/scoped token issuance, or another approved server secret mechanism.

## 5. GitHub client architecture

The GitHub client uses only documented REST endpoints needed by the exact #62 Protocol.

Repository/source reads:

- repository metadata resolves `default_branch`;
- the default branch ref resolves the exact head revision;
- recursive tree read is bounded and fails closed on provider truncation, unsupported symlink/submodule modes, malformed entries, or more than the caller-provided maximum entries;
- file read accepts only the exact requested source revision/path, bounded base64 UTF-8 file content, and fails closed on directories, non-base64/raw download substitution, binary/invalid UTF-8 content, malformed digests, or oversized content.

Branch creation:

- first read the target branch ref;
- if it already exists at the exact requested base revision, return the existing branch as an idempotent success;
- if it exists at another revision, fail with a normalized branch conflict;
- otherwise create `refs/heads/<branch>` at the exact base revision and re-read on ambiguous/racing provider responses before deciding success/failure.

Accepted-lineage commit:

- read the branch ref and require exact equality with `expected_parent_revision`;
- if the branch already points at a commit whose exact parent and deterministic Parallax lineage marker match the requested accepted lineage, return it as an idempotent replay;
- otherwise create a bounded tree on the expected parent tree, create a commit with a deterministic secret-safe lineage marker, and update the branch ref with `force=false`;
- re-read the ref after ambiguous update failures; success is returned only if the branch points to the exact created/replayed accepted-lineage commit;
- stale/non-fast-forward races fail closed and never become forced writes.

Pull request creation:

- require the current head branch revision to equal `expected_head_revision` before creation;
- search only for an existing matching open PR for that same repository/head/base and return it only when its exact head revision matches;
- otherwise create the PR and re-query on an ambiguous duplicate/rate response before deciding failure;
- no merge, review approval, branch deletion, force push, release, repository settings, workflow mutation, or generic Git operation exists.

## 6. Vercel preview client architecture

The Vercel client receives immutable server-owned target configuration mapping the registered #62 `vercel_project_ref` to an actual Vercel project identity/scope and expected `github:owner/repository` identity.

Before preview creation it must:

- require the registered Vercel target to exist in server configuration;
- require the exact repository identity to match that target;
- acquire a valid scoped credential for that Vercel target;
- fetch bounded Vercel project metadata and confirm the project identity/scope;
- reject attempts to preview the configured production branch;
- submit only a GitHub-backed deployment request for the exact branch/source revision with an explicit `target: preview` and no aliases, environment mutation, secret values, domains, custom production target, or arbitrary build configuration.

After creation/read it must:

- normalize only bounded deployment ID, exact source revision, status, and safe `*.vercel.app` URL into the existing `VercelPreviewResult`;
- require the deployment to resolve to Preview rather than Production before returning success;
- reject repository/source/target mismatch and malformed/missing provider metadata;
- recognize an already-existing exact preview for the same registered Project/source revision where the provider exposes one, avoiding uncontrolled replay creation.

Because preview-vs-production behavior is safety-critical, provider ambiguity or a response that reports Production is a failure. This worker performs no live Vercel deployment; Integration / Control Tower must validate the provider behavior with approved disposable/preview resources before production credential binding.

## 7. Failure normalization and secret hygiene

No provider response text is surfaced. Normalized failure codes are derived only from transport category, HTTP status, and bounded typed validation results.

Required mappings include:

- missing credential -> `CREDENTIAL_UNAVAILABLE`;
- expired credential -> `CREDENTIAL_EXPIRED`;
- timeout/connect failure -> `PROVIDER_TIMEOUT` or `PROVIDER_UNAVAILABLE`;
- 401/403 -> `PROVIDER_AUTH_DENIED`;
- 404 -> bounded resource-specific not-found code where needed;
- 409/422 -> bounded conflict/stale/invalid request code after idempotency re-check;
- 429 -> `PROVIDER_RATE_LIMITED`;
- 5xx -> `PROVIDER_UNAVAILABLE`;
- malformed/unexpected success payload -> `PROVIDER_INVALID_RESPONSE`.

Secrets from credential values, provider error bodies, authorization headers, cookies, environment values, or raw provider payloads must never appear in typed results, normalized errors, repr output, tests, or protected evidence.

## 8. Non-goals

- Editing #45 authority contracts/registry or #62 typed action contracts.
- Generic HTTP, generic GitHub/Vercel API proxying, arbitrary URLs, arbitrary methods/bodies/headers, shell, subprocess, or Git command execution.
- GitHub repository creation, merge, review approval, branch deletion, force push, release publication, workflow/settings mutation, or destructive administration.
- Vercel production deployment/promotion, production aliases, domains, environment/secret mutation, environment inspection, or arbitrary build/deployment configuration.
- Provisioning GitHub App keys/installations, Vercel production tokens, or any live provider credential.
- Project persistence, workspace/source-lineage implementation, IMPLEMENT generation/runtime, client UX, merge, or deployment.

## 9. Acceptance criteria

### AC-01 Spec-first concrete-client authorization
This approved `P2-V0.15.7` specification exists on `ws/app-provider-clients` before substantive client implementation and passes the protected workstream specification gate.

### AC-02 Exact #62 Protocol preservation
The workstream implements the existing `GitHubProviderClient` and `VercelProviderClient` method signatures without modifying #62 `common.py`, `github.py`, or `vercel.py`, and without adding a generic provider action surface.

### AC-03 Least-privilege credential architecture
Concrete clients obtain provider credentials only through injected server-owned scoped credential providers. Credential leases are resource-bound, expiry-aware, redacted, absent from source control/evidence, and architecturally favor GitHub App/fine-grained and Vercel short-lived/scoped credentials rather than broad long-lived PATs.

### AC-04 Bounded GitHub source reads
Repository/default-head, recursive tree, and UTF-8 file reads return only exact bounded #62 result types and reject provider truncation, unsupported source modes, oversized/binary/malformed content, wrong repository/source identity, and malformed provider payloads.

### AC-05 Exact GitHub write/CAS semantics
Branch creation and accepted-lineage commit require exact base/parent revisions, never force-update refs, fail closed on stale/non-fast-forward state, and return deterministic bounded #62 result identities.

### AC-06 GitHub publication idempotency and review safety
Exact branch/lineage-commit/PR retries reuse an already-created exact result when provable. Pull-request creation requires exact current head revision and no merge, approval, deletion, release, workflow/settings, or generic Git authority is introduced.

### AC-07 Preview-only Vercel client
The Vercel client implements only preview create/read, uses immutable server-registered Vercel Project/repository binding, sends an explicit Preview target, rejects production-branch or Production-resolved deployments, and exposes no production promotion/alias/domain/environment/secret/configuration mutation method.

### AC-08 Exact Project/repository/source-lineage preservation
Concrete clients preserve the repository/source identities supplied by the #62 action layer and accept `AcceptedSourceLineage` only through the exact existing Protocol. Client results are independently checked so provider-returned repository/source/target mismatch cannot become success.

### AC-09 Normalized secret-safe failure evidence
Missing/expired credentials, timeout/connect errors, 401/403, 404, 409/422, 429, 5xx, malformed success payloads, and secret-bearing provider error bodies produce only bounded normalized `ProviderClientError` codes with no raw provider text, token, header, cookie, or environment value leakage.

### AC-10 Deterministic isolated tests
`httpx.MockTransport` or equivalent bounded fakes prove authorized concrete GitHub read/write/PR and Vercel preview behavior plus stale parent/head, wrong repository/target, missing/expired credentials, timeout, rate limit, auth failure, 5xx, malformed/raw/secret-bearing responses, idempotent replay, and the absence of production Vercel methods.

### AC-11 No live credential or production side effects
The worker provisions no production GitHub/Vercel credential, performs no live provider mutation/deployment, and relies on isolated deterministic provider boundaries for CI. Live preview verification remains Control Tower/Integration responsibility.

### AC-12 Exact-head integration readiness
The branch carries the authentic committed DSPy plan, is current with `integration/wave2-app-builder`, passes focused tests, full API regression, deterministic Workstream Spec Validation, Parallax P2 CI, and Bounded Autonomy Pilot on the exact final head, and has a review-ready PR targeting `integration/wave2-app-builder`. The worker does not merge or deploy.

## 10. Risks and mitigations

- **Credential overreach:** require server-injected resource-bound credential leases and provide no built-in broad PAT loader. Integration binds approved issuers later. AC-03.
- **Provider API drift:** validate every successful response into strict #62 result records; malformed provider data fails closed. AC-04, AC-07, AC-09.
- **Git write races:** exact ref checks plus non-force ref updates and post-failure re-reads provide bounded CAS-like protection without force push. AC-05.
- **Retry duplication:** exact existing branch/commit/PR/preview reconciliation precedes or follows ambiguous provider responses. AC-06, AC-07.
- **Vercel production escalation:** reject the production branch, explicitly request Preview, verify returned deployment target, and keep all production/alias/environment APIs absent. Live behavior must be separately verified before credential binding. AC-07, AC-11.
- **Secret leakage from provider errors:** ignore raw provider bodies/messages when mapping failures. AC-09.
- **Authority confusion:** concrete clients are only invoked by the already-authorized #62 action layer and cannot choose Project/capability/action identities themselves. AC-02, AC-08.
