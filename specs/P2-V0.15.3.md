## 1. Objective

Turn the protected Code `IMPLEMENT` stage from a deliberate hard stop into a bounded app-building runtime that can author source-change proposals from one immutable approved Work Specification plus deterministic bounded project source context, apply only validated proposals through the accepted Wave 1 safe implementation engine, and advance the durable Engineering Run only after Project/run/source-lineage identity is proven.

The model/program may propose source changes. It never receives filesystem mutation authority, caller-selected workspace authority, shell/command authority, Git/network/provider authority, protected stage authority, review authority, merge authority, or production deployment authority.

## 2. Scope

This workstream owns the protected IMPLEMENT orchestration boundary and typed implementation-generation semantics.

The first slice includes:

- a provider-independent typed implementation proposal containing exact protected acceptance coverage and one bounded set of source patches compatible with Wave 1 `SourcePatch`;
- Luna -> Terra -> Sol generation routing through a DSPy implementation program, with protected structural validation after every candidate;
- a deterministic bounded source-context selector that sends only supported UTF-8 source files, excludes repository internals and secret-sensitive files/content, and enforces file/count/byte limits;
- an injected canonical Project-binding protocol that #59 can satisfy without this workstream owning Project persistence;
- an injected workspace/source-lineage protocol that #60 can satisfy without this workstream allocating a Project workspace or interpreting opaque `workspace_ref` as a path;
- an IMPLEMENT runtime that validates Project/run/base-lineage identity, generates a proposal, converts it to a Wave 1 implementation request, invokes the unchanged safe implementation engine, asks the lineage adapter to accept the resulting source identity, verifies the returned lineage receipt, constructs bounded observable IMPLEMENT evidence, and only then calls the existing protected `EngineeringRunService.complete_stage` validator/policy boundary;
- autonomy wiring that attempts IMPLEMENT only when the protected implementation runtime is explicitly configured and otherwise preserves a fail-closed stop;
- focused positive/negative/idempotency tests and exact integration notes for #59/#60.

The first worker slice may use fakes for #59/#60 integration tests because those workstreams are parallel. Final serialized integration must bind the protocols to their accepted implementations before end-to-end app-building can be claimed.

## 3. Fixed decisions and interfaces

- Canonical Project identity comes from #59 and ultimately resolves to server-owned `Project.id`. No model/user value, `workspace_ref`, repository metadata, or filesystem path may substitute for that identity.
- Workspace/source-lineage allocation comes from #60 through an injected protocol. This slice accepts a protected workspace handle; it does not construct one from opaque Project metadata.
- A workspace handle must bind exact `project_ref`, `run_id`, immutable/base `source_lineage_ref`, `base_revision`, and an already-protected local workspace root.
- After patch application the lineage adapter returns a receipt binding the same Project/run/base lineage to a new accepted lineage plus the resulting workspace digest. A mismatch fails before durable IMPLEMENT success is recorded.
- Source selection is deterministic for the same workspace and implementation contract. It must not silently use the entire repository or silently truncate an over-limit material file into misleading context.
- The generation input contains bounded approved-spec facts, the protected acceptance map, and selected source content only. It contains no credentials, environment values, arbitrary provider payloads, hidden reasoning, filesystem-root authority, executable commands, or release-state authority.
- The generation output contract allows only exact acceptance IDs plus patch objects with `path`, `expected_base_sha256`, and `unified_diff`. Unknown/extra fields are forbidden.
- Candidate acceptance coverage must exactly equal the protected acceptance map. Duplicate, missing, extra, malformed, or model-invented acceptance IDs fail validation.
- Proposal validation is separate from mutation. Passing proposal validation does not imply patch success or stage success.
- The Wave 1 `SafeImplementationEngine` / `TextPatchEngine` remain authoritative for filesystem confinement, target allowlisting, pre-image binding, diff format, secret-content rejection, aggregate limits, atomic preparation/commit, rollback, and mutation evidence. This workstream must not weaken those constraints.
- `applied: true` remains mutation evidence only. The existing protected IMPLEMENT validator and state-machine policy remain required for the durable stage transition.
- The runtime records only observable bounded facts/digests. It never stores model chain-of-thought, scratchpad, private reasoning, provider credentials, raw environment values, or unrestricted raw provider responses.
- BUILD/TEST/VERIFY same-lineage execution is a required integration invariant. This slice exposes the accepted post-IMPLEMENT lineage identity for #60/integration; it must not claim later stages used that lineage until the integrated executor proves it.

## 5. Architecture and failure semantics

Required execution order:

```text
current IMPLEMENT Engineering Run
      ↓
#59 canonical Project binding adapter
      ↓
#60 protected workspace/base-lineage handle
      ↓
approved Work Specification + exact protected acceptance map
      ↓
deterministic bounded source-context selection
      ↓
Luna → Terra → Sol typed proposal generation
      ↓
protected proposal validation
      ↓
Wave 1 SafeImplementationEngine
      ↓
#60 post-mutation lineage acceptance receipt
      ↓
exact Project/run/base-lineage/workspace-digest receipt verification
      ↓
bounded IMPLEMENT evidence
      ↓
existing validate_implementation + protected stage policy
      ↓
BUILD state + accepted source-lineage identity for later integration
```

The runtime must fail closed and preserve a non-success durable stage when any of the following cannot be proven:

- current run is not exactly at IMPLEMENT;
- canonical Project identity is missing or mismatched;
- protected workspace handle is missing, stale, wrong-Project, wrong-run, or has invalid lineage/base identity;
- selected source context exceeds policy, contains unsupported/secret-sensitive material, or cannot be read deterministically;
- every routed model fails or produces structurally invalid proposal output;
- acceptance coverage is missing, duplicated, extra, or changed;
- proposal contains extra authority fields, unsafe path, unsupported patch content, hidden-reasoning fields, secret material, or exceeds configured proposal limits;
- Wave 1 patch preparation/application fails, including stale pre-image or concurrent duplicate mutation;
- lineage acceptance fails or returns a receipt that does not exactly match the Project/run/base lineage/resulting workspace digest;
- existing protected IMPLEMENT validation or state policy rejects the evidence;
- an idempotent/retry operation cannot prove whether the mutation already succeeded.

A failed generation/validation/workspace-resolution path must not mutate files. Patch-engine failures use existing atomic prepare/commit/rollback behavior. A durable IMPLEMENT failure must remain distinguishable from successful mutation and from a recoverable fail-closed stop.

## 6. Security

- Treat model output and source files as untrusted input.
- Pydantic/typed proposal models use `extra="forbid"`; fields such as root/path authority, commands, environment, headers, URLs, shell, Git/provider actions, `chain_of_thought`, `reasoning`, or `scratchpad` are not valid proposal fields.
- The source-context selector excludes secret-sensitive names/directories and probable credential/private-key content before model invocation.
- Source-context, proposal, diff, and evidence byte/count limits are server-owned constants/configuration, not model-controlled values.
- Never pass the protected local workspace root into the model prompt or persist it as model-visible evidence.
- Never expose provider keys, application secrets, Vercel credentials, root access credentials, session cookies, or raw secret environment values.
- Acceptance IDs and Work Specification binding facts are server-derived. Model output cannot redefine their required set.
- No generation candidate can call the patch engine directly; only the protected runtime may convert a validated proposal into an implementation request.
- No patch result can call stage transition directly; only the protected runtime may construct evidence and invoke the existing service/policy boundary.
- Observable generation metadata is limited to selected model identity, normalized proposal digest/counts, bounded source-context digest/counts, acceptance IDs, source/lineage identifiers, patch/artifact evidence, and explicit negative-authority flags.

## 7. Acceptance criteria

### AC-01 Spec-first and compiled-plan authorization
`P2-V0.15.3` exists and passes the repository specification validator. Before substantive runtime implementation is treated as authorized, the mandatory DSPy SpecCritic + SpecCompiler development path executes for this specification, the generated plan is committed at `specs/compiled/P2-V0.15.3.plan.json`, and `scripts/validate_spec.py --require-dspy specs/P2-V0.15.3.md` passes.

### AC-02 Strict typed implementation proposal
The implementation-generation boundary exposes strict typed contracts whose candidate output contains only exact protected acceptance coverage plus bounded source-patch objects (`path`, `expected_base_sha256`, `unified_diff`). Unknown fields, malformed digests, empty/duplicate targets, oversized patch sets, extra authority fields, hidden-reasoning/scratchpad fields, and invalid proposal shapes are rejected before mutation.

### AC-03 Protected acceptance-map ownership
Generation receives the immutable server-derived acceptance map for the bound approved Work Specification. A candidate passes only when its acceptance IDs exactly equal the required set with no duplicate, missing, extra, reordered-authority or model-invented requirement. Model text cannot change the Work Specification ID/revision/digest or protected stage policy.

### AC-04 Deterministic bounded secret-safe source context
For the same implementation contract/workspace state the selector returns the same ordered bounded source context and digest. It enforces file/count/aggregate-byte limits, supported UTF-8 source policy, skips repository/credential-sensitive names and probable secret-bearing content, never exposes the workspace root, and fails rather than silently truncating an included material file.

### AC-05 Provider-independent generation with protected routing
A provider-independent `ImplementationGenerationProgram` protocol is implemented by a DSPy program and coordinator using the existing Luna -> Terra -> Sol router. Provider exceptions and invalid candidates are sanitized/escalated; all-model failure yields a bounded generation failure and no mutation. Generation artifacts expose proposal data/model identity, not hidden reasoning.

### AC-06 Wave 1 mutation authority preserved
Only a validated proposal is converted into a Wave 1 `ImplementationRequest`. `SafeImplementationEngine` / `TextPatchEngine` remain unchanged and authoritative for path confinement, stale-base checks, diff format, secret rejection, atomicity, rollback and size limits. Automated tests prove malformed, path-escaping, secret-bearing, stale and duplicate-target proposals cannot become successful mutation evidence.

### AC-07 Exact Project/run/base-lineage binding
The runtime consumes #59/#60-compatible injected protocols. Before mutation it requires a non-empty canonical Project reference and a protected workspace handle whose Project and run IDs match exactly. After mutation it requires a lineage receipt matching the same Project/run/base-lineage identity plus the exact resulting workspace digest. Any mismatch fails closed and cannot produce durable IMPLEMENT success.

### AC-08 Protected IMPLEMENT evidence and stage authority
A successful patch result is transformed into bounded evidence containing the existing required `artifacts`, `base_revision`, and `workspace_digest` plus Project/run/source-lineage/proposal/context identities and explicit negative-authority facts. The runtime must then call the existing `EngineeringRunService.complete_stage(IMPLEMENT, ...)`; `applied: true` or a valid lineage receipt alone cannot bypass `validate_implementation` or the protected state machine.

### AC-09 Idempotent retry and duplicate-mutation safety
The IMPLEMENT operation key is deterministic from the autonomy operation/stage/revision. Durable replay is recognized before a second mutation where possible, and Wave 1 pre-image/commit checks remain the concurrency backstop. Tests prove retrying the same accepted operation does not apply the same mutation twice and stale/concurrent base content cannot be silently overwritten.

### AC-10 Fail-closed autonomy integration
`AutonomyCoordinator` attempts IMPLEMENT only when an explicit protected implementation runtime is configured. Missing runtime, project binding, workspace resolution, generation/validation, patch application or lineage verification stops without fabricated success. A configured positive path advances PLAN -> IMPLEMENT -> BUILD while preserving REVIEW as an operator boundary and preserving no generic shell/Git/network/deployment authority.

### AC-11 Same-lineage integration seam
The accepted IMPLEMENT result exposes one immutable post-mutation source-lineage identity suitable for #60. This worker slice does not claim BUILD/TEST/VERIFY same-lineage success by itself; integration notes require later execution to resolve the exact accepted lineage and require cumulative tests to reject unrelated fresh source.

### AC-12 Workstream isolation and integration readiness
Final worker changes remain within the declared #61 ownership plus the declared temporary validation workflow, which is absent from the final candidate. No #59 schema/persistence, #60 allocator internals, #62 provider adapters, #46 protected scoring, client UI, or authoritative project records are changed. The final branch is current with relevant `main`, the deterministic Workstream Spec Validation, Parallax P2 CI and Bounded Autonomy Pilot pass on the exact final head, and the PR is ready for serialized Integration without merge/deployment by the worker.

## 8. Risks and mitigations

- **Parallel #59/#60 contract drift:** use narrow injected protocols and reconcile only at those adapter seams during serialized integration; do not import unmerged worker branches as shared truth.
- **Model emits plausible but unsafe patches:** strict typed proposal validation plus unchanged Wave 1 patch safety and protected stage validation remain independent gates.
- **Source context omits a material file:** deterministic limits must stop or route for narrower work rather than silently claiming successful complete context when policy says the source is too large.
- **Duplicate/autonomy retry mutates twice:** durable operation replay plus exact base digests and commit-time pre-image checks fail closed on repeated/stale mutation.
- **Mutation succeeds but lineage recording fails:** do not record durable IMPLEMENT success; expose bounded failure so Integration can add recovery/reconciliation. The runtime must never fabricate accepted lineage.
- **False end-to-end confidence:** worker evidence proves the #61 boundary only. Same-lineage later stages, provider preview actions and app-builder protected promotion require cumulative Integration evidence.
