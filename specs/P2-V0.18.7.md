# Parallax 2.0 — P2-V0.18.7 Mobile Interaction Model & Guided Build Flow

Status: APPROVED
Date: 2026-08-26
Workstream: Mobile Interaction Model & Guided Build Flow
Base: `7b65aff9ed62ddc94b1a29eb22c5ab81048888bf`

## Objective

Make Parallax materially easier to understand and operate on phone-sized screens before any Wave 6 capability work begins. Preserve conversation as the primary surface while replacing compact desktop composition with a mobile-specific interaction model centered on three destinations: Chat, Build, and Project.

The mobile experience must keep canonical server-owned Project, Work Specification, Engineering Run, source-lineage, validation, provider, and human-review truth unchanged. This work changes presentation and interaction hierarchy only.

## User problem

The current compact layout technically fits below 760px, but it exposes too many desktop-oriented surfaces and actions at once. Work Specification controls, Engineering Run state, Observability/Live Build content, project context, and conversation compete for limited vertical space. Nested scroll regions and wrapped action rows make the experience difficult to follow.

A mobile operator should always be able to answer three questions without understanding Parallax internals:

1. What project am I in?
2. What is Parallax doing now?
3. What should I do next?

## Scope

### Mobile navigation

For compact widths (`<760px`):

- replace desktop-style primary navigation with a persistent bottom navigation containing exactly `Chat`, `Build`, and `Project`;
- keep desktop/tablet navigation behavior unchanged at non-compact widths;
- entering `Build` must show the current engineering lifecycle and relevant evidence for the current conversation/run;
- entering `Project` must expose project/conversation switching and project context without requiring Observability or engineering-internal terminology;
- `Observability` is not a top-level mobile destination; its useful run evidence is incorporated under `Build`.

### Chat surface

- conversation remains the dominant mobile surface;
- current Project identity is visible in the mobile header;
- current mode is presented in user-facing language (`Ask` for internal `reason`, `Build` for internal `code`), without changing API/state-machine mode values;
- engineering status is reduced to a compact contextual summary that links to `Build` rather than rendering full engineering panels in the conversation flow;
- the composer remains reachable above the keyboard and bottom navigation;
- mobile must avoid card expansion that pushes the composer out of practical reach.

### Work Specification interaction

- the compact Chat surface must not render the full expandable Work Specification body inline;
- when specification action is needed, render one clear contextual card/action (for example `Review specification`, `Approve and continue`, or `Continue current build`);
- detailed specification content opens in one dedicated mobile detail surface/sheet/page with one primary vertical scroll container;
- the detail surface retains objective, acceptance criteria, constraints, open questions, risks, revision/status, and approval controls;
- internal durable Work Specification status and approval semantics remain unchanged.

### Guided Build lifecycle

- represent the authoritative lifecycle as an understandable ordered mobile flow: `Specification`, `Plan`, `Implementation`, `Build`, `Test`, `Verify`, `Review`;
- derive completed/current/pending/failed presentation only from authoritative server state;
- show current activity/status first and keep detailed evidence behind progressive disclosure;
- expose run events, tests, code/diff/terminal/evidence only as secondary detail views within Build;
- no client-only simulated stage transitions or fabricated progress are permitted.

### Contextual action hierarchy

- when protected state requires operator action, present one visually dominant primary action whenever the state admits a single next step;
- secondary actions move behind quieter secondary controls or an overflow menu/sheet;
- `SPEC_AMENDMENT` must be described in plain language as a scope change while preserving the existing protected boundary and `Start new objective` semantics;
- human-review, retry, preview, approval, resume-current-scope, and similar actions must be named by user outcome rather than internal state-machine jargon where possible.

### Project surface

- provide a mobile Project destination that makes current Project identity obvious;
- allow switching among existing conversations/projects using existing APIs and canonical Project bindings;
- do not create a competing client-side Project identity;
- less-frequent account/access/system controls may remain secondary.

### Scrolling and touch behavior

- use one primary vertical scroll container per mobile screen/detail surface;
- remove nested scrolling from the compact Work Specification experience;
- preserve approximately 44pt minimum practical touch targets;
- preserve reduced-motion/reduced-graphics capability;
- preserve iOS/mobile-web keyboard viewport compensation and zoom accessibility requirements.

## Acceptance criteria

- AC-01: At `<760px`, the primary mobile navigation exposes exactly Chat, Build, and Project, with the current destination unambiguous; desktop/tablet behavior remains unchanged.
- AC-02: Mobile Chat keeps conversation and composer primary, displays current Project context and user-facing Ask/Build mode language, and does not inline the full Work Specification or full Engineering Run/Observability workspace.
- AC-03: A mobile user can review the complete current Work Specification in a dedicated detail surface and approve a DRAFT specification without nested scroll containers or loss of specification content.
- AC-04: `SPEC_AMENDMENT` is presented in plain language with a clear `Start new objective` primary action and an available path back to the current approved scope when that protected action is permitted; server guard/semantics are unchanged.
- AC-05: Mobile Build shows Specification→Plan→Implementation→Build→Test→Verify→Review from authoritative Engineering Run/Work Specification state and never fabricates progress.
- AC-06: Mobile Build provides progressive-disclosure access to available events/evidence/Live Build details without promoting Observability to a fourth primary mobile destination.
- AC-07: Mobile Project clearly identifies the active Project/conversation and supports existing switching/creation behavior without creating client-owned Project authority.
- AC-08: States requiring operator input present one dominant primary next action when one is available; secondary actions are visually subordinate.
- AC-09: Mobile interaction surfaces use one primary vertical scroll container each; compact Work Specification no longer creates a nested scroll region.
- AC-10: Existing protected authentication, Work Specification approval, Project identity/binding, Engineering Run lifecycle, source lineage, provider authority, REVIEW/HUMAN_REQUIRED ceiling, and desktop UX contracts remain unchanged.
- AC-11: Client typecheck and existing state/browser visual acceptance suites pass, with added deterministic mobile coverage for navigation, specification review, guided build state, project switching, and amendment recovery.
- AC-12: Phone viewport acceptance verifies no control overlap, no hidden primary action/composer, and practical touch targets at representative narrow widths.

## Non-goals

- Wave 6 production application lifecycle capabilities.
- server state-machine changes.
- new Project/Work Specification/Engineering Run authority.
- redesigning desktop/tablet information architecture.
- adding a fourth mobile dashboard/observability destination.
- arbitrary source editing or shell access.
- changing authentication/session lifetime/provider credentials.
- introducing multi-user collaboration behavior beyond existing Access UI.
