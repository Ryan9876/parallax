# Parallax 2.0 — Mobile Interaction Model & Guided Build Flow

Spec ID: P2-V0.18.7
Status: APPROVED FOR IMPLEMENTATION
Date: 2026-08-26
Workstream: `WS-MOBILE-GUIDED-BUILD` / issue #261
Base: `7b65aff9ed62ddc94b1a29eb22c5ab81048888bf`

## 1. Objective

Make Parallax materially easier to understand and operate on phone-sized screens before Wave 6. Replace the current compact adaptation of desktop surfaces with a mobile-specific interaction model centered on `Chat`, `Build`, and `Project`, while preserving conversation as the primary creation surface and preserving all server-owned Project, Work Specification, Engineering Run, source-lineage, validation, provider, authentication, and human-review authority.

The mobile operator should be able to answer three questions immediately: what Project am I in, what is Parallax doing now, and what should I do next.

## 2. Scope

For compact widths below 760px:

- introduce persistent primary navigation with exactly `Chat`, `Build`, and `Project`;
- keep desktop/tablet navigation and information architecture unchanged at non-compact widths;
- keep Chat conversation-first, with current Project identity and user-facing `Ask`/`Build` mode language visible without changing internal `reason`/`code` values;
- replace inline full Work Specification presentation with a compact contextual summary and a dedicated mobile specification detail surface;
- represent the authoritative lifecycle as `Specification`, `Plan`, `Implementation`, `Build`, `Test`, `Verify`, `Review` in a guided Build screen;
- move run events, Live Build/code/diff/test/evidence inspection behind progressive disclosure within Build rather than making Observability a fourth mobile destination;
- provide a Project destination for active Project/conversation context and existing switching/creation behavior;
- present one dominant contextual next action when protected state admits one obvious operator action;
- describe `SPEC_AMENDMENT` in plain user language while retaining the existing protected `Start new objective` and approved-scope recovery semantics;
- use one primary vertical scroll container per mobile screen/detail surface, eliminating nested compact Work Specification scrolling;
- preserve practical approximately 44pt touch targets, keyboard/composer reachability, reduced-motion, reduced-graphics, and mobile-web viewport accessibility behavior.

Owned implementation paths are limited to the declared client/mobile paths in issue #261. API/runtime behavior is out of scope unless separately authorized as a dependency.

## 3. Non-goals

- Wave 6 production application lifecycle capabilities.
- Server state-machine or persistence changes.
- New Project, Work Specification, Engineering Run, source-lineage, provider, approval, merge, or deployment authority.
- Redesigning desktop/tablet navigation or desktop Observability/Live Build behavior.
- Adding a fourth primary mobile dashboard destination.
- Arbitrary source editing, shell access, or provider controls.
- Authentication/session-lifetime or credential changes.
- New multi-user collaboration semantics.

## 4. Security

This is a presentation and interaction-hierarchy change only. Canonical Project resolution, Work Specification approval, Engineering Run stage truth, source lineage, repository/provider target identity, credentials, protected validation/evaluation, authentication/session behavior, and `REVIEW` / `HUMAN_REQUIRED` authority remain server-owned and unchanged.

The client must not infer or fabricate completion, approval, Project identity, source state, provider success, or deployment state. Mobile labels may translate internal terminology into clearer user language but may not change the underlying state or grant an action that the existing protected API does not permit. No secret-bearing diagnostics, raw credentials, or hidden reasoning may be added to the mobile surfaces.

## 5. Acceptance criteria

### AC-01 Mobile primary navigation
At widths below 760px, Parallax exposes exactly three primary destinations named `Chat`, `Build`, and `Project`, with the current destination visually and accessibly unambiguous. Non-compact desktop/tablet navigation remains unchanged.

### AC-02 Conversation-first mobile Chat
Mobile Chat keeps the conversation and composer as the dominant surface, shows current Project context and user-facing `Ask`/`Build` mode language, and does not inline the complete Work Specification, Engineering Run panel, or Observability workspace.

### AC-03 Dedicated Work Specification review
A mobile user can open a dedicated specification detail surface that contains the complete current objective, acceptance criteria, constraints, open questions, risks, revision/status, and permitted approval action. The detail surface uses one primary vertical scroll container and the compact Chat surface does not create a nested Work Specification scroller.

### AC-04 Plain-language specification amendment recovery
When the protected conversation state is `SPEC_AMENDMENT`, mobile explains that the new request changes the approved build, makes `Start new objective` the dominant action, and retains an available path back to the current approved scope when the existing protected API permits it. Server guard and inheritance semantics remain unchanged.

### AC-05 Authoritative guided Build lifecycle
Mobile Build presents `Specification`, `Plan`, `Implementation`, `Build`, `Test`, `Verify`, and `Review` in order, deriving completed/current/pending/failed presentation only from the current Work Specification and Engineering Run server state. No client-only simulated stage progress is permitted.

### AC-06 Progressive engineering evidence
Mobile Build provides access to available run events, tests, code/diff/terminal/evidence or Live Build details through progressive disclosure without promoting Observability to a fourth primary mobile destination and without changing desktop Observability behavior.

### AC-07 Clear Project context and switching
Mobile Project clearly identifies the active Project/conversation and supports existing conversation/project switching and creation behavior through existing canonical APIs. It creates no competing client-owned Project identity or repository binding.

### AC-08 One dominant contextual action
When protected state requires operator input and one clear next action exists, the mobile presentation gives that action visual priority. Secondary actions remain available but visually subordinate; action availability continues to come from existing protected state and APIs.

### AC-09 Single-scroll mobile interaction
Each mobile primary screen and dedicated detail surface uses one primary vertical scroll container. Compact Work Specification content no longer introduces a nested vertical ScrollView inside Chat, and the composer remains practically reachable above the keyboard and bottom navigation.

### AC-10 Protected contracts and desktop regression safety
Existing authentication, session expiry handling, Project identity/binding, Work Specification approval, Engineering Run lifecycle, source lineage, provider authority, protected evaluation, `REVIEW` / `HUMAN_REQUIRED` ceiling, reduced-motion/reduced-graphics behavior, and desktop/tablet UX contracts remain unchanged.

### AC-11 Deterministic mobile acceptance coverage
Client typecheck/state/export and existing browser/Skia acceptance pass, and deterministic mobile coverage verifies navigation, specification review, guided Build state, Project switching, and amendment recovery at representative phone widths.

### AC-12 Phone viewport usability
Representative narrow-phone acceptance verifies no overlapping primary controls, no hidden primary action or composer, accessible labels for the three destinations and critical actions, and practical touch targets for primary mobile controls.
