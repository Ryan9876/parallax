## 1. Objective

Create the permanent Wave 5 generalization benchmark and integrated reference proof showing that Parallax can accept materially different unfamiliar application/repository shapes, understand them through accepted repository intelligence, choose only approved skills and Project-scoped service bindings, use validated memory only as non-authoritative evidence, execute through the existing protected Engineering Run and immutable source-lineage path, correct bounded failures on fresh lineage, publish a governed replay-safe Preview, and stop at REVIEW or HUMAN_REQUIRED without creating new authority.

S6 is a proof and benchmark layer, not a new application runtime. The benchmark must make the complete protected story inspectable and repeatable while preserving the existing sources of truth for Project/run/Work Specification identity, source mutation, BUILD/TEST/VERIFY execution, correction, evaluator thresholds, provider actions, source delivery, replay, and operator review.

A successful benchmark result means the accepted components compose correctly. It does not make benchmark fixture text authoritative, approve a new command, bypass a capability, weaken a Work Specification, create credentials, or authorize production deployment.

## 2. Fixed decisions

- **One execution truth.** Existing Engineering Run, attempt, Work Specification, source-lineage, protected execution, validation, correction, source-delivery, evaluator and REVIEW contracts remain authoritative. S6 must not implement a parallel state machine or mutation/provider path.
- **Fixtures are evidence, never authority.** Repository fixture files, manifests, package scripts, READMEs and malicious text are untrusted evidence. Their strings may not become shell, package-manager, credential, provider, deployment or approval authority.
- **Accepted S1-S5 are required admission layers.** Supported cases must be classified by S1, select only accepted S2 skills and S3 Project bindings, produce an S4 READY decision bound to the exact Project/run/Work Specification/profile, and treat S5 HIT/MISS as evidence only.
- **Material diversity is required.** The permanent manifest must contain at least a client/static-web case, a Python API/service case, and a workspace/monorepo or mixed/full-stack case, plus negative ambiguous/malicious cases. Cosmetic variants of the Parallax repository cannot satisfy the benchmark.
- **HUMAN_REQUIRED is a valid protected outcome.** Ambiguous/unsupported repositories, missing skills/bindings/capabilities, or other genuine authority gaps must fail closed rather than be converted into a false benchmark success.
- **Current validation is never weakened by reuse.** S5 memory hits may reduce repeated discovery evidence only. They must retain `fresh_validation_required=true`; current Work Specification and evaluator-policy identity remain unchanged.
- **Correction must advance immutable lineage.** The deliberate repair case starts from a reproducible validation failure, uses the accepted bounded correction interfaces, produces a new source lineage, and passes only after fresh validation. It may not mutate protected policy/evaluator/workflow paths or relax acceptance.
- **Preview is the autonomous delivery ceiling.** Successful delivery evidence must come through the existing governed GitHub/Vercel source-delivery contracts and be bound to the exact accepted lineage. Production delivery is out of scope.
- **Replay is observable.** Recreated implementation and delivery operations must replay the existing durable result. A proof that performs a second source mutation, commit, pull request or Preview for the same exact operation fails.
- **Operator REVIEW remains explicit.** Autonomous proof may reach REVIEW and prove Preview/evaluation evidence. Only an explicit operator review operation may complete a protected run.
- **Evidence is privacy-safe.** S6 reports contain bounded identities, digests, statuses, counters and approved safe evidence only. They contain no private source blobs, cross-Project private memory metadata, prompts, credentials, secret values/handles, unrestricted logs, provider request payloads, hidden reasoning or executable command authority.
- **No release authority.** S6 may create deterministic test/provider doubles inside tests to exercise accepted contracts, but it may not deploy production, alter provider credentials, change production configuration, merge to `main`, or claim production readiness without Control Tower deployment proof.

## 3. Architecture requirements

### 3.1 Permanent benchmark manifest

Add a versioned JSON manifest under `benchmarks/wave5-generalization/reference-v0.1.json` describing bounded benchmark metadata, not executable source authority.

Each case records only:

- stable case ID and case version;
- expected repository/application shape or expected HUMAN_REQUIRED outcome;
- objective kind;
- required normalized S1 signals;
- required governed capability IDs;
- logical service requirements where applicable;
- requested memory kinds;
- expected protected checks/outcome flags;
- whether actual protected runtime/reference-loop proof is required;
- whether correction proof is required;
- whether governed Preview/replay proof is required.

The manifest may not contain raw provider credentials, arbitrary shell commands, environment values, production targets, secret material or free-form authority instructions. The loader validates bounded IDs, expected case diversity, unique identities and required negative/correction/replay coverage before the suite may execute.

### 3.2 Repository evidence fixtures and S1 profiles

The S6 harness/test suite constructs deterministic bounded `RepositoryEvidenceSnapshot` fixtures through the accepted S1 interface.

Minimum supported shapes:

1. static/client web evidence such as `index.html` and bounded web assets/configuration;
2. Python service evidence such as `pyproject.toml`/Python service signals;
3. workspace/monorepo evidence such as root package/workspace markers plus bounded package roots.

Negative fixtures include:

- an ambiguous/unfamiliar layout that S1 classifies AMBIGUOUS/UNSUPPORTED or otherwise not safely supported;
- malicious manifest/README/script text requesting secrets, arbitrary commands, policy override or production deployment.

S6 records only S1 normalized compatibility/profile evidence. Repository-defined command strings never become an execution specification or capability.

### 3.3 Governed admission composition

For supported cases, the harness composes the accepted S2/S3/S4 contracts with server-owned test policy:

- exact-digest approved `PortableSkill` contracts appropriate to each benchmark shape;
- bounded `CapabilitySnapshot` with only the capabilities required by the selected skill;
- exact Project-scoped S3 service-binding policies when the case declares a logical service need;
- an `OrchestrationIdentity` bound to exact Project/run/Work Specification/revision/digest, exact acceptance IDs, source revision and S1 profile digest;
- an `ApplicationObjective` containing bounded objective kind, acceptance IDs, service requirements and feature tokens;
- an exact correction-policy digest/reference.

The only autonomous supported result is an accepted S4 `READY` decision. Missing capability, ambiguous skill, missing service binding, unsupported/ambiguous repository, identity mismatch or conflict remains HUMAN_REQUIRED/fail-closed according to the accepted module semantics.

### 3.4 Validated memory proof

The harness may admit deterministic S5 memory entries for benchmark purposes only through the accepted `MemoryAdmissionPolicy` and `ValidatedMemoryRegistry`.

It must demonstrate:

- same-Project private memory can produce an eligible HIT when exact applicability and current evaluator policy match;
- a HIT retains fresh current validation and grants no authority;
- a MISS produces the same protected validation requirement;
- foreign Project-private memory is absent from caller-visible counts/fingerprints/selection identities;
- stale compatibility/evaluator evidence is rejected;
- any cross-Project shared pattern is eligible only after an exact sanitized-sharing approval.

S6 may record memory selection IDs/counts/digests in the benchmark report, but it may not copy private provenance/source into a cross-Project result.

### 3.5 Existing protected runtime/reference-loop proof

Actual mutation/execution/delivery proof must delegate to the existing protected runtime/reference seams rather than being reimplemented in S6.

A successful runtime-backed case proves, using durable evidence:

- approved Work Specification and canonical Project/run identity;
- repository bootstrap to immutable root lineage;
- exactly one accepted IMPLEMENT mutation producing new immutable lineage;
- recreated IMPLEMENT replay without another mutation;
- exact-lineage BUILD, TEST and VERIFY;
- deterministic/browser/visual or protected evaluator evidence as applicable;
- autonomy stops at REVIEW rather than completing itself;
- verified source delivery produces governed GitHub branch/commit/PR and Vercel Preview evidence on the exact accepted lineage;
- repeated delivery returns the durable publication instead of creating another publication;
- explicit operator REVIEW remains the only path to completion.

The existing `ProtectedReferenceAppHarness`, runtime/evidence adapters and source-delivery/provider contracts remain read-only and authoritative.

### 3.6 Deliberate bounded correction proof

At least one permanent benchmark case begins with a deterministic failed `CandidateValidation` on a known immutable lineage.

S6 uses the accepted correction interfaces (`CorrectionContext`, `AutonomousCorrectionController`, planner, mutation-runtime and validator protocols) with deterministic test adapters to prove the controller semantics rather than duplicating them.

The repair case must demonstrate:

- the first validation failure is Project/run/Work Specification/lineage bound and reproducible;
- the bounded plan targets only current defect IDs and a non-protected source path;
- mutation receives the exact base lineage and deterministic operation key;
- the mutation returns a different immutable lineage;
- fresh validation is run against that new lineage;
- Work Specification digest, acceptance authority, evaluator policy and protected path policy are unchanged;
- correction reaches PASSED only when the fresh quality vector passes;
- process recreation/replay cannot substitute a different pending plan or duplicate the accepted correction mutation.

No S6 correction adapter may alter `.github/workflows`, `specs/`, protected metrics, tool registry, browser policy, credentials, provider scope or other accepted protected paths.

### 3.7 Deterministic proof report

Define a bounded immutable Wave 5 generalization result/report containing, per case, only safe proof facts such as:

- case ID/version and manifest digest;
- Project/run/Work Specification identity digests;
- S1 compatibility state/shape/profile digest;
- S4 orchestration status/ID/reason and selected safe skill/binding identities;
- S5 memory selection status/ID/counts and fresh-validation flag;
- protected lineage/replay status when a runtime-backed case executes;
- correction status and before/after lineage identities for the deliberate correction case;
- protected evaluation/visual status;
- Preview delivery ID/status and publication replay flag where applicable;
- final autonomous stop (`REVIEW` or `HUMAN_REQUIRED`);
- pass/fail reason codes derived from protected expectations.

The report itself grants no authority and performs no mutation/provider call. Same manifest + same accepted evidence produces the same evidence digest/report identity independent of input ordering.

### 3.8 Negative authority/privacy proof

Permanent negative cases/tests must prove at least:

- malicious repository strings such as shell/curl/provider/deploy/secret requests do not appear as executable/provider authority in S1-S6 safe evidence;
- missing capability or missing/ambiguous binding cannot be converted to READY;
- foreign Project-private memory remains non-observable;
- stale Work Specification/profile/evaluator/lineage evidence fails closed;
- out-of-order protected stage/replay evidence is rejected;
- provider/delivery evidence for the wrong Project or lineage is rejected by the existing runtime evidence path;
- benchmark fixtures cannot change evaluator thresholds, acceptance IDs, correction protected paths or operator REVIEW requirements.

## 5. Security and privacy

- Repository/manifests/README/source fixture content is untrusted evidence only.
- No fixture field or benchmark manifest field may supply a shell command, raw provider URL/request body, credential, secret, environment assignment, production target, arbitrary capability ID, approval or runtime transition.
- Skill and service authority must originate exclusively from accepted exact-digest server-owned admission policies.
- Cross-Project private memory must remain non-observable through result candidates, counts, rejection summaries, visible registry digests or proof IDs.
- Shared memory requires exact server-owned sanitized-sharing approval and retains `grants_authority=false` / `fresh_validation_required=true`.
- S6 reports may expose safe Preview deployment identity/status when already provided by accepted delivery evidence, but not provider credentials or unrestricted payloads.
- Source contents, diffs, prompts, hidden reasoning, access tokens, cookies, API keys, secret handles, connection strings and unrestricted logs must not enter the public proof report.
- Deliberate malicious inputs must be asserted absent from all authority-bearing contracts and safe report serialization.
- Production deployment remains outside the autonomous S6 boundary.

## 6. Failure and recovery boundaries

Use bounded typed proof outcomes/reasons for at least:

- invalid benchmark manifest/case contract;
- benchmark diversity/coverage failure;
- repository HUMAN_REQUIRED/unsupported/ambiguous outcome;
- governed skill/capability HUMAN_REQUIRED;
- service-binding HUMAN_REQUIRED;
- orchestration identity/acceptance mismatch;
- memory privacy/applicability/policy-staleness failure;
- protected runtime/evaluation mismatch;
- correction identity/policy/replay failure;
- source-delivery Project/lineage/replay mismatch;
- autonomous REVIEW ceiling violation;
- safe-report privacy/authority violation.

A negative case passes only when the expected protected rejection occurs. It must never be normalized into a successful supported case. Process recreation may resume from durable evidence but cannot create a second source mutation or provider publication for the same exact operation identity.

## 7. Non-goals

- creating a new generic app-generation runtime;
- replacing Engineering Run or Work Specification state;
- teaching repository text to execute its own package scripts;
- creating arbitrary shell/package-manager/network/provider execution;
- changing capability, skill or service-binding approval policy;
- persisting a new production memory database;
- modifying evaluator thresholds to make the benchmark pass;
- replacing protected browser/visual validation;
- creating production provider credentials or targets;
- deploying benchmark applications to production;
- merging Wave 5 to `main`;
- claiming Wave 5 production readiness before Control Tower integration/release/deployment verification.

Permanent tests prove at least static/client web, Python API/service, and workspace/monorepo or mixed/full-stack fixtures are deterministically classified through accepted S1 evidence and can reach governed S4 READY only when an exact accepted S2 skill, required capability snapshot and required S3 Project binding are present.

### AC-03 Ambiguous/unsupported repositories require human action
An unfamiliar/ambiguous or unsupported repository fixture produces the accepted S1/S4 fail-closed outcome and never proceeds as a supported runtime case. HUMAN_REQUIRED is recorded as the correct benchmark result without guessed root, command, skill, service or provider authority.

### AC-04 Malicious repository instructions cannot escalate authority
Deliberate repository content requesting arbitrary shell/network commands, secrets, policy override or production deployment cannot create capabilities, skills, service bindings, provider scope, correction authority or approval. Safe S1-S6 evidence/report serialization contains no secret/provider payload or executable command authority derived from the malicious text.

Supported cases select only exact-digest approved S2 skills whose declared capabilities are present and resolve logical service needs only through exact Project-scoped S3 bindings. Missing capability, no binding, incompatible binding or ambiguous binding remains HUMAN_REQUIRED/fail-closed and cannot be bypassed by benchmark configuration.

The benchmark demonstrates same-Project private memory HIT and MISS behavior through accepted S5. Foreign Project-private memory is non-observable, stale compatibility/evaluator evidence is rejected, and any shared cross-Project candidate requires exact sanitized-sharing approval.

### AC-07 Existing protected runtime proves exact-lineage objective-to-Preview flow
At least one supported runtime-backed case delegates to the existing protected reference/runtime seams and proves approved Work Specification identity, exactly one accepted IMPLEMENT lineage advance, exact-lineage BUILD/TEST/VERIFY, protected evaluator/browser/visual evidence as applicable, governed GitHub/Vercel Preview delivery on that lineage, and autonomous stop at REVIEW. ### AC-08 Deliberate validation failure is corrected on fresh immutable lineage

The repair produces a different immutable lineage, receives fresh validation, preserves Work Specification/acceptance/evaluator policy and protected path restrictions, and reaches PASSED only after the new lineage satisfies protected quality.

### AC-09 Process recreation and delivery replay are duplicate-safe
Permanent proof recreates runtime/process context and retries exact implementation/delivery identities. IMPLEMENT replay returns the accepted lineage without a second mutation. Delivery replay returns the same published revision, PR and Preview identity and proves only one branch/commit/PR/Preview mutation set occurred for the exact operation.

Memory hits, benchmark expectations, provider/evaluator success, correction success or Preview readiness cannot independently complete or approve the Engineering Run.

For the same manifest and accepted evidence, case ordering, case/result identities and aggregate proof digest are stable across input ordering/retry. The public report exposes only bounded safe identities/digests/status/counters and explicitly grants no tool, execution, source-mutation, service-binding, provider, deployment or approval authority; it contains no cross-Project private metadata, raw source, prompts, secrets/handles, provider payloads or hidden reasoning.
