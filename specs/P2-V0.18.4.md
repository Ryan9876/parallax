## 1. Objective

Add a deterministic server-owned objective-to-application orchestration contract that composes the accepted Wave 5 repository-intelligence, governed-skill and application-service-binding interfaces into the existing protected Engineering Run lifecycle without creating a second execution state machine or a new authority surface.

S4 answers one bounded question before protected mutation proceeds: given the exact canonical Project/run/approved Work Specification identity, exact repository compatibility profile, server-owned capability snapshot, admitted skill registry and Project-scoped service-binding registry, is there one deterministic governed route through the existing IMPLEMENT -> BUILD -> TEST -> VERIFY -> REVIEW path for this objective? If yes, S4 emits an immutable orchestration decision containing only bounded identities, acceptance ownership, selected skill identity, service-resolution evidence and fixed protected-stage intent. If the objective, repository, capability selection or required service configuration is materially ambiguous or unsupported, S4 returns HUMAN_REQUIRED with a typed bounded reason before it can be treated as execution authority.

S4 does not replace `EngineeringRunService`, `AutonomyCoordinator`, protected IMPLEMENT mutation, accepted source lineage, BUILD/TEST/VERIFY execution, autonomous correction, provider publication, evaluation or REVIEW. Those existing systems remain the only authorities for state transitions, mutation, validation, correction and Preview delivery. The orchestration decision is deterministic admission/evidence for those systems, not an alternate runner.

## 2. Fixed decisions

- **One execution truth remains authoritative.** The existing Engineering Run, attempts, accepted source lineage, worker/checkpoint records, provider action/audit evidence and protected evaluation remain the sole execution state. S4 creates no competing run/stage/checkpoint/persistence state machine.
- **Structured objective, not executable prose.** The orchestrator consumes a bounded `ApplicationObjective` contract containing an objective kind, exact acceptance IDs and logical service requirements. It carries no shell command, package script, provider endpoint, environment assignment, filesystem path, credential, deployment target, arbitrary HTTP request, source blob, raw conversation, README instruction or hidden reasoning.
- **Approved Work Specification is the acceptance authority.** Every orchestration request binds to canonical Project ID, Engineering Run ID, Work Specification ID/revision/digest and the exact ordered protected acceptance IDs already derived from that approved specification. Objective acceptance IDs must exactly equal that protected set; S4 cannot add, remove, rename or weaken acceptance criteria.
- **Repository evidence is prerequisite, never authority.** S4 accepts only an S1 `RepositoryCompatibilityProfile` bound to the same canonical Project and exact repository revision. `SUPPORTED` is required for autonomous admission. PARTIAL, UNSUPPORTED or AMBIGUOUS profiles stop HUMAN_REQUIRED; command candidates, manifest strings and repository text never become executable authority.
- **Skills remain governed procedures, not tool grants.** S4 delegates deterministic skill choice to the accepted S2 `SkillSelector` against an admitted registry and server-owned `CapabilitySnapshot`. A missing capability, no matching skill or ambiguous selection stops HUMAN_REQUIRED. The selected skill identity/digest is evidence only and cannot grant tools or providers.
- **Service intent remains separate from provider authority.** Logical `ServiceRequirement` values are resolved only through the accepted S3 Project-scoped registry/resolver. Every required service must resolve deterministically to one exact approved binding. Missing, incompatible or ambiguous bindings stop HUMAN_REQUIRED; S4 never invents a provider or uses repository/framework/model hints as a fallback.
- **Fixed protected route.** A ready orchestration decision references the existing protected application route `IMPLEMENT -> BUILD -> TEST -> VERIFY -> REVIEW`. It does not introduce alternative stage ordering, skip required protected stages, redefine stage success, or permit COMPLETE without the existing operator-controlled REVIEW boundary.
- **Correction remains subordinate to validation.** S4 may carry an opaque server-owned correction-policy digest/evidence reference proving which existing protected correction policy applies. It cannot set evaluator thresholds, reduce acceptance coverage, skip deterministic/browser/visual checks, select a weaker validation lane for promotion, or convert a failed protected check into success.
- **Preview remains the autonomous delivery ceiling.** S4 may declare that accepted REVIEW-bound delivery uses the existing governed Preview path, but it contains no project ID from a provider, target name, token, URL, production environment or provider request. Existing source-delivery composition remains responsible for exact-lineage GitHub/Vercel Preview actions and replay protection.
- **Replay is identity-based.** The same exact bounded inputs produce the same orchestration decision ID independent of registry/input ordering and process recreation. Existing accepted mutation, validation or delivery evidence is represented only by bounded identity references; S4 cannot replay those actions itself. Contradictory identity/evidence fails closed rather than scheduling duplicate mutation/publication.
- **No persistence/route/UI/provider mutation in S4.** Prefer a pure typed orchestration domain module and deterministic tests. Runtime persistence/wiring, if later required, must be separately governed and cannot be inferred from this pure decision contract.

## 3. Architecture requirements

### 3.1 Canonical orchestration identity

Define an immutable `OrchestrationIdentity` containing only:

- canonical Project UUID;
- canonical Engineering Run UUID;
- canonical Work Specification UUID;
- positive Work Specification revision;
- exact 64-hex Work Specification digest;
- exact ordered protected acceptance IDs;
- exact S1 repository/profile source revision and compatibility-profile digest.

Identity construction must fail closed for malformed/non-canonical UUIDs, empty/duplicate/invalid acceptance IDs, invalid digests, non-positive revisions or mismatch with the supplied compatibility profile.

The Work Specification digest and acceptance set are immutable inputs. S4 has no API that edits specification text, changes approval, synthesizes acceptance IDs or treats model output as acceptance authority.

### 3.2 Bounded application objective

Define an immutable `ApplicationObjective` containing:

- bounded `objective_kind` token used only for governed S2 skill matching;
- exact protected acceptance IDs, which must match `OrchestrationIdentity.acceptance_ids` exactly;
- a bounded ordered tuple of logical S3 `ServiceRequirement` objects;
- optional bounded objective-feature tokens only when they are non-executable selection/evidence facts.

Canonicalization must make semantically identical service/feature ordering deterministic while rejecting duplicates and unbounded input.

There is deliberately no free-form objective text in the orchestration record. Raw user/model conversation can inform the approved Work Specification upstream, but S4 receives the resulting bounded contract only.

### 3.3 S1 repository compatibility admission

The orchestrator accepts one exact `RepositoryCompatibilityProfile` and requires:

- `profile.project_id` equals the canonical Project ID;
- profile source revision/profile digest equal the `OrchestrationIdentity` values;
- compatibility state is `SUPPORTED`;
- repository shape is neither unsupported nor ambiguous.

Any identity mismatch is a hard fail-closed contract error. A correctly bound profile that is PARTIAL, UNSUPPORTED or AMBIGUOUS produces HUMAN_REQUIRED with a typed repository reason. S4 does not reinterpret blockers or infer executability from S1 command candidates.

Representative success tests must include materially different accepted S1 shapes such as static/web, Python service and workspace/monorepo. Shape differences affect governed skill compatibility only; they do not create new commands or provider authority.

### 3.4 S2 governed skill composition

The orchestrator consumes an accepted S2 `SkillRegistry`, `SkillSelector` and server-owned `CapabilitySnapshot`.

For the objective kind/profile/capability tuple:

- call the accepted deterministic selector rather than reimplementing skill matching;
- require exactly one `SELECTED` skill;
- bind the selected skill ID/version/content digest and capability-policy digest into the orchestration decision;
- preserve required-capability IDs as evidence, not grants;
- reject any selected identity that cannot be resolved back to exactly one admitted registry entry with the same digest.

S2 HUMAN_REQUIRED reasons remain visible as bounded orchestration reasons. S4 must not choose a lower-priority or incompatible skill to avoid HUMAN_REQUIRED.

Procedure steps remain untrusted/non-executable content at this layer. They are never converted to shell commands, provider calls or acceptance changes by S4.

### 3.5 S3 application service composition

For every objective `ServiceRequirement`, S4 uses the accepted S3 `ServiceBindingResolver` against one `ProjectServiceBindingRegistry` whose canonical Project equals the orchestration Project.

Rules:

- requirements are resolved in deterministic requirement-digest order;
- every selected resolution is recorded through the accepted S3 `record_service_binding_resolution` path using the exact Project/run identity and exact registered binding;
- every record must bind to the same Project/run and policy digest;
- if any requirement returns HUMAN_REQUIRED, overall orchestration returns HUMAN_REQUIRED and no partial set is represented as ready;
- S4 preserves each S3 reason (`NO_BINDING_AVAILABLE`, `INCOMPATIBLE_BINDING`, `AMBIGUOUS_BINDING_SELECTION`, etc.) as bounded evidence;
- duplicate logical requirements with the same canonical digest collapse deterministically only if they are exactly identical; contradictory requirements for the same logical service/interface fail HUMAN_REQUIRED rather than guessing;
- secret values/handles, provider payloads and adapter execution remain structurally absent.

A selected service binding is eligibility evidence only and does not satisfy S2 capability prerequisites or create tool/provider authority.

### 3.6 Immutable orchestration decision

Define an immutable `ObjectiveOrchestrationDecision` with status `READY` or `HUMAN_REQUIRED` and a deterministic `orchestration_id` derived from canonical bounded fields.

A READY decision contains only:

- canonical orchestration identity digest/fields;
- objective kind and objective digest;
- S1 profile digest/source revision/repository shape;
- exact S2 selected skill ID/version/digest and capability-policy digest;
- deterministic safe S3 resolution records/IDs;
- exact acceptance IDs;
- fixed protected route `IMPLEMENT`, `BUILD`, `TEST`, `VERIFY`, `REVIEW`;
- server-owned correction-policy digest/reference if supplied;
- explicit booleans/facts that acceptance cannot be weakened, provider authority is not granted, source mutation is not performed here, validation is required on exact accepted lineage, Preview delivery remains governed externally, and REVIEW is the autonomous ceiling.

A HUMAN_REQUIRED decision contains the same safe canonical context available before the stop plus one typed bounded reason and optional bounded dependency identifiers. It contains no guessed skill/binding/provider or fabricated success evidence.

Same exact inputs across ordering/retry/process recreation must yield byte-stable safe metadata and the same orchestration ID.

### 3.7 Existing protected execution boundary

S4 must model the route to application delivery without performing it.

The READY decision explicitly delegates:

- source mutation to the existing protected IMPLEMENT runtime;
- accepted lineage to the existing transactional lineage authority;
- BUILD/TEST/VERIFY to existing registered exact-lineage execution;
- deterministic/browser/accessibility/visual checks to existing protected validators where applicable;
- correction to the existing bounded correction controller on fresh candidate lineage;
- GitHub/Vercel Preview delivery to existing source-delivery composition;
- final advancement beyond REVIEW to existing operator-controlled authority.

No S4 function may call a shell, provider, filesystem, network, database, source-delivery adapter or Engineering Run mutation method.

### 3.8 Replay/idempotency evidence guard

Define a bounded `OrchestrationProgressEvidence` (or equivalent validation helper) that can be used only to verify whether already-persisted downstream facts correspond to this exact orchestration identity. It may contain opaque/digest references for:

- accepted source-lineage ID/content digest;
- completed protected stage names and evidence digests;
- correction-policy/candidate evidence IDs;
- source-delivery action/delivery identity;
- current authoritative Engineering Run stage/revision.

The helper must never create or mutate those facts. It validates identity/order consistency and derives only a deterministic disposition such as `START`, `CONTINUE`, `ALREADY_AT_REVIEW`, or `HUMAN_REQUIRED`.

Required replay rules:

- completed stages must form a valid prefix of the fixed protected route; out-of-order/duplicate/unknown stages fail closed;
- evidence bound to another Project/run/spec/profile/orchestration identity fails closed;
- a recorded implementation/accepted-lineage identity must not be represented as permission to run IMPLEMENT again;
- a recorded source-delivery identity at REVIEW must not be represented as permission to publish again;
- process recreation over identical evidence returns the same disposition;
- absence of evidence is not fabricated as success.

This evidence guard is advisory to future wiring; existing runtime/source-delivery replay controls remain authoritative.

### 3.9 Human-required taxonomy

Use typed bounded orchestration reasons that preserve upstream cause without echoing untrusted payloads. Include at least:

- `INVALID_ORCHESTRATION_CONTRACT`;
- `ORCHESTRATION_IDENTITY_MISMATCH`;
- `ACCEPTANCE_CONTRACT_MISMATCH`;
- `REPOSITORY_HUMAN_REQUIRED`;
- `SKILL_HUMAN_REQUIRED`;
- `SERVICE_BINDING_HUMAN_REQUIRED`;
- `CONFLICTING_SERVICE_REQUIREMENTS`;
- `CORRECTION_POLICY_MISMATCH`;
- `REPLAY_EVIDENCE_MISMATCH`;
- `PROTECTED_STAGE_SEQUENCE_INVALID`.

Material ambiguity is never normalized into READY merely to continue autonomously.

## 5. Security and privacy

- Repository/source/model text is evidence or upstream drafting input, never orchestration authority.
- Objective contracts contain bounded semantic tokens and approved acceptance identities only; raw prompts/conversation/source are not retained.
- No secret values, credential handles, provider tokens, connection strings, headers/cookies, environment values, arbitrary URLs, raw HTTP requests, arbitrary commands, filesystem paths, source blobs or provider payloads enter safe orchestration metadata.
- S4 cannot register a skill, capability, service binding, command or provider target.
- S4 cannot convert S1 command candidates or S2 procedure text into executable actions.
- Cross-Project skill/service/replay evidence fails closed before a READY decision is produced.
- Error reasons are typed bounded codes and do not echo arbitrary untrusted values.
- Hidden chain-of-thought/scratchpad is never stored, hashed as an identity input, scored or exposed.
- Safe metadata explicitly states that it grants no authority and performs no mutation/provider action.

## 6. Failure and recovery boundaries

Contract/identity corruption raises a typed fail-closed `ObjectiveOrchestrationError`; ordinary supported-input ambiguity returns a HUMAN_REQUIRED decision with a typed bounded reason.

The orchestrator must distinguish:

- malformed/cross-identity evidence — hard fail closed;
- valid but unsupported/ambiguous repository — HUMAN_REQUIRED;
- valid repository but unavailable/ambiguous governed skill — HUMAN_REQUIRED;
- valid skill but missing/incompatible/ambiguous service binding — HUMAN_REQUIRED;
- conflicting logical service requirements — HUMAN_REQUIRED;
- invalid correction-policy digest/reference — hard fail closed;
- invalid replay stage ordering or identity — hard fail closed/HUMAN_REQUIRED according to whether the evidence is malformed versus materially ambiguous.

Retry/process recreation over identical accepted inputs returns the same orchestration ID/status/reason and must not invoke source mutation, validation commands or provider publication. S4 does not implement a retry loop; existing protected runtime controls retain retry/recovery authority.

## 8. Acceptance criteria

### AC-01 Exact Project/run/spec/profile binding
A READY or HUMAN_REQUIRED orchestration decision is bound to one canonical Project, Engineering Run, approved Work Specification revision/digest/acceptance set and exact S1 compatibility profile/source revision. Cross-Project, cross-run, cross-spec, stale profile or malformed identity fails closed before a READY decision can exist.

### AC-02 Deterministic multi-shape repository and skill composition
For materially different supported S1 repository shapes (including static/web, Python service and workspace/monorepo fixtures), S4 delegates to the accepted S2 selector and deterministically binds exactly one admitted compatible skill using only the server-owned capability snapshot. Registration/input ordering and process recreation do not change the selected identity or orchestration ID.

### AC-03 Exact Project-scoped service composition
Every logical service requirement is resolved through the accepted S3 Project registry/resolver and recorded with exact Project/run/binding/policy identity. All required services must resolve before READY; missing, incompatible, ambiguous or conflicting requirements produce HUMAN_REQUIRED and never trigger provider fallback or guessed configuration.

### AC-04 One protected execution route and no new authority
READY records only the existing `IMPLEMENT -> BUILD -> TEST -> VERIFY -> REVIEW` route, exact acceptance IDs and bounded S1/S2/S3 evidence. Tests prove S4 exposes no shell/filesystem/network/provider/database/credential/deployment execution surface, performs no Engineering Run/source mutation and cannot turn repository commands, skill text or service adapter IDs into authority.

### AC-05 Acceptance and correction policy cannot weaken
Objective acceptance IDs must exactly match the approved Work Specification-derived set. Correction-policy identity is server-owned and immutable in the decision. Attempts to omit/add acceptance criteria, lower validation/evaluation requirements, skip protected stages or substitute a different correction-policy identity fail closed; S4 cannot convert failed protected validation into success.

### AC-06 Replay and process recreation are duplicate-safe
Same exact inputs and bounded downstream progress evidence reproduce the same orchestration ID/disposition. Valid completed stages must be an ordered prefix of the protected route; accepted-lineage/IMPLEMENT evidence prevents representing IMPLEMENT as fresh work, and existing REVIEW/source-delivery evidence prevents representing publication as fresh work. Mismatched, duplicate, out-of-order or foreign evidence fails closed rather than authorizing duplicate mutation/provider action.

### AC-07 Material ambiguity stops HUMAN_REQUIRED
Supported-input ambiguity or unavailable authority from S1/S2/S3 produces explicit HUMAN_REQUIRED with bounded typed reason. Unsupported/ambiguous repository, no/ambiguous skill, missing capability, missing/incompatible/ambiguous service binding and conflicting service requirements never silently select a fallback. Operator REVIEW remains the autonomous ceiling.

### AC-08 Privacy-safe deterministic evidence
Safe orchestration metadata contains only bounded canonical identities, digests, semantic tokens, acceptance IDs, admitted skill identity, safe service-resolution identity and protected-route/correction references. It contains no raw objective/conversation/source, hidden reasoning, arbitrary logs, commands, filesystem paths, secret values/handles, environment data, arbitrary URLs, provider payloads or credentials; safe metadata explicitly grants no authority.

### AC-09 Existing protected runtime and accepted S1-S3 regressions remain green
Wave 4 canonical Project/Work Specification/Engineering Run, protected implementation, exact-lineage BUILD/TEST/VERIFY, correction, provider/source-delivery, evaluation/auth/observability/mobile suites plus accepted S1 repository-intelligence, S2 governed-skill and S3 service-binding tests remain unchanged or stronger. S4 does not modify those accepted semantics.

### AC-10 Exact-head worker release boundary
The final worker candidate contains this approved spec, authentic committed DSPy plan evidence, the bounded orchestration domain and focused tests only, with any temporary DSPy workflow harness restored to canonical bytes. Exact-head Workstream Spec Validation, Parallax P2 CI and Bounded Autonomy pass; the PR targets `integration/wave5-generalized-delivery`; no worker merge/deploy/migration/provider/configuration mutation occurs.
