## 1. Objective

Add a provider-neutral, configuration-driven model routing capability that can prefer an admitted local model endpoint for eligible Parallax inference work and then fall back through the existing hosted GPT-5.6 Luna -> Terra -> Sol chain. Protected validation, canonical model identity, provider credentials, Project/source authority, REVIEW and release governance remain unchanged.

Local-first routing is opt-in and server-owned. With no local-first configuration, the accepted hosted production behavior remains unchanged. This workstream is developed in isolation while Wave 6 S6/release work proceeds and has no merge or deployment authority.

## 2. Fixed decisions

- The existing `MODEL_ORDER` hosted chain remains the compatibility default.
- Local-first routing is enabled only by validated server-owned configuration; callers cannot supply arbitrary endpoints, credentials or route order.
- Each route resolves its own provider transport. A local endpoint must never globally redirect hosted GPT-5.6 traffic away from the Vercel AI Gateway.
- Existing explicit `DSPY_API_BASE` / `DSPY_API_KEY` remains a deliberate operator override and is not repurposed as the provider registry.
- Protected validators remain authoritative. Local success stops escalation only when the existing validator accepts the result.
- Local provider failure, unavailability or protected-validation failure may advance to the next admitted route without changing acceptance requirements.
- Request-scoped Vercel OIDC remains the only automatic hosted-production GPT-5.6 credential path.
- Local model/provider content is labor/evidence only and grants no shell, network, source mutation, provider-spending, GitHub/Vercel, approval, REVIEW or release authority.
- Production-hosted Parallax must not assume `localhost` reaches an operator machine. Any future remote private-inference transport requires separate deployment design/authorization.

## 3. Architecture requirements

### 3.1 Server-owned route definition

Introduce a bounded immutable route definition containing at minimum model identity, provider kind and optional server-owned endpoint/key-slot references needed by that provider. Route definitions must reject empty or duplicate model identities, unsupported provider kinds, malformed endpoints, inline secret material where a key-slot identity is required, and unbounded configuration.

### 3.2 Configuration-driven route order

Resolve the effective model route order from server-owned configuration. When local-first configuration is absent, return the exact existing hosted order. When present, admitted local routes may precede the existing hosted chain. Configuration parsing is deterministic and fails closed.

### 3.3 Per-route transport isolation

Model construction must resolve transport from the selected route rather than applying one global local endpoint to every model. Local routes may use an explicit OpenAI-compatible/Ollama-compatible endpoint. Hosted `openai/gpt-5.6-*` routes retain the current Vercel AI Gateway request-scoped OIDC logic and canonical model identities.

### 3.4 Protected fallback semantics

The existing sequential router remains authoritative for attempts. Provider failures are sanitized to bounded error class evidence. Protected-validation rejection is distinct from provider failure. Either may advance to the next admitted route; neither may weaken the validator or acceptance contract.

### 3.5 Bounded diagnostics

Attempt evidence and logs may include model identity, provider kind, bounded status, duration and sanitized error class. They must exclude credentials, endpoint authorization headers, raw provider payloads, prompts, generated source, hidden reasoning and unrestricted exception text.

### 3.6 Compatibility and rollback

Default runtime behavior remains the accepted hosted route unless local-first configuration is explicitly enabled. Rollback is removal of local-first configuration plus code rollback to the accepted parent/reconciled integration baseline. No database migration is required by this capability.

## 6. Security and privacy

Local inference endpoints are untrusted model transports, not authority. Server-owned configuration determines which provider/model/endpoint combinations are admissible. Caller/model/repository content cannot create routes, change endpoints, supply credentials or expand provider/network authority.

Credentials remain outside prompts, source packages, route evidence and logs. Hosted production GPT-5.6 traffic continues to use admitted request-scoped Vercel OIDC. Local endpoint credentials, if later required, must be resolved from server-owned secret slots rather than embedded in route configuration.

A local route does not grant the model filesystem, shell, source mutation, external HTTP, deployment or approval capabilities. Those remain governed by existing Parallax boundaries. Cross-Project privacy and exact Project/Work Specification/source-lineage contracts are unchanged.

## 7. Acceptance criteria

### AC-01 Default hosted compatibility
With no local-first configuration, effective runtime order remains exactly `openai/gpt-5.6-luna`, `openai/gpt-5.6-terra`, `openai/gpt-5.6-sol`, and existing hosted transport tests remain green.

### AC-02 Validated local-first configuration
A bounded server-owned configuration can place one admitted local model before the hosted chain. Empty, duplicate, malformed, unsupported, caller-controlled or secret-bearing route configuration fails closed before model execution.

### AC-03 Per-provider transport isolation
A configured local endpoint applies only to its admitted local route. Hosted GPT-5.6 routes continue to use the fixed Vercel AI Gateway endpoint with canonical model IDs and are not redirected to the local endpoint.

### AC-04 Local success stops escalation
When the local route returns a result accepted by the existing protected validator, routing returns that result and does not attempt a hosted model. Bounded attempt evidence identifies the local model/provider without exposing endpoint credentials or payloads.

### AC-05 Local provider failure falls back
When the local route is unavailable or raises a provider failure, routing records only sanitized bounded failure evidence and advances to the next admitted hosted route without changing the acceptance contract.

### AC-06 Local protected-validation failure falls back
When the local route returns output rejected by the existing protected validator, routing records `validation_failed`, advances to the next admitted route and cannot lower or bypass the validator.

### AC-07 Hosted credential boundary preserved
Request-scoped Vercel OIDC remains the only automatic hosted-production GPT-5.6 credential path. Process `VERCEL_OIDC_TOKEN` remains non-authoritative and local configuration cannot substitute a credential for hosted production routing.

### AC-08 Explicit DSPy override compatibility
Existing explicit `DSPY_API_BASE` / `DSPY_API_KEY` behavior remains an intentional operator override. Local-first provider configuration is not silently combined with or substituted for this compatibility path.

### AC-09 Bounded diagnostics and secret safety
Logs and attempt evidence contain only admitted model/provider identity, status, duration and sanitized error class. Tests prove endpoint credentials, authorization values, raw provider errors/results and generated content are not logged.

### AC-10 No authority expansion
Tests and code inspection prove local-first routing grants no shell/network capability, source acceptance, Project/spec mutation, provider spending authority, GitHub/Vercel authority, approval, REVIEW completion or production deployment authority.

### AC-11 Isolated exact-head validation
The worker branch passes authentic DSPy spec compilation, protected `--require-dspy` plan validation and applicable exact-head Workstream Spec Validation, Bounded Autonomy Pilot and P2 CI. The PR remains draft/DO NOT MERGE and no deployment occurs.

### AC-12 Post-Wave-6 reconciliation gate
Before integration, Wave 6 is deployment-verified and `CURRENT-STATE.md` reconciled; this branch is rebased/reconciled to that exact production SHA, architecture drift is resolved, required authentic evidence and exact-head gates are rerun, and Control Tower explicitly authorizes integration.
