## 1. Objective

Activate the accepted Wave 6 agentic development control plane inside the ordinary protected Parallax Engineering Run path. An approved objective must be able to reach one server-owned decision path that determines whether one or more admitted engineering agents are appropriate, coordinates bounded agent work, recovers or reassigns recoverable agent failure, independently evaluates exact candidate evidence, uses trustworthy routing/economic evidence, invokes bounded competition only when policy justifies it, and hands only the selected exact candidate into the existing protected source-mutation, source-lineage, BUILD, TEST, VERIFY, Preview and REVIEW path.

This work closes the gap between validated Wave 6 control-plane primitives/reference proof and live Engineering Run composition. It must not create a second Engineering Run, source-lineage, validation, provider, deployment or approval authority path.

## 2. Fixed decisions

- **Existing protected runtime remains authoritative.** `EngineeringRunService`, approved Work Specification binding, `ProtectedImplementationRuntime`, the safe implementation engine, durable source-lineage allocator, exact-lineage BUILD/TEST/VERIFY, `SourceDeliveryComposition` and REVIEW remain the only canonical mutation/progression boundaries.
- **Agentic control is orchestration, not authority.** S1-S5 may choose labor/strategy and emit evidence, but they cannot accept canonical source, waive protected validation, transition REVIEW, merge or production-deploy.
- **One canonical writer remains.** Multiple agents may produce bounded candidate/proposal evidence. Only one Parallax-selected exact candidate may enter the existing protected mutation/lineage acceptance operation for a canonical IMPLEMENT transition.
- **No silent legacy bypass.** When the agentic runtime is enabled for an eligible run, failure to admit a compatible bounded strategy must stop with explicit bounded failure/HUMAN_REQUIRED evidence rather than silently invoking an ungoverned second implementation path.
- **Deterministic validation precedes judgment.** S3/S4/S5 cannot support or economically prefer a candidate that has failed required protected deterministic validation.
- **Existing provider policy remains.** Runtime activation does not add provider/model registrations, credentials, arbitrary endpoints or autonomous spending authority. Hosted model traffic continues through the existing server-owned transport/routing policy.
- **Replay and process recreation are first-class.** Repeated PLAN/agent dispatch/candidate selection/IMPLEMENT/delivery operations resolve durable accepted evidence rather than duplicating source mutation or provider publication.
- **Preview remains the autonomous publication ceiling.** Production merge/promotion and REVIEW completion remain governed release/operator boundaries.
- **Operator does not manage agents.** The normal build surface does not require manual agent selection, task assignment, recovery, competition or candidate choice.

## 3. Architecture requirements

### 3.1 Runtime admission boundary

Introduce one narrow server-owned agentic runtime composition seam attached to the existing Engineering Run composition. The seam receives only canonical Project/run/approved Work Specification/acceptance/source-context identity and server-owned agent/policy registries.

It may emit bounded planning/agent/evaluation/routing/competition evidence but cannot mutate Engineering Run state directly except through the existing protected service operations already authorized for PLAN/IMPLEMENT/BUILD/TEST/VERIFY.

Activation must be explicit and server-owned. Historical/pre-Wave-6 compatibility must remain deterministic; unsupported or disabled activation must not reinterpret old evidence as agentic evidence.

### 3.2 PLAN integration

At PLAN, derive a bounded work graph from server-owned acceptance IDs and protected repository/source context. Admit only exact S1-compatible agent identities from a server-owned registry and use accepted S2 planning to choose the smallest adequate team and dependency/coordination schedule.

PLAN evidence must record, in bounded form:

- exact Project/run/spec revision/digest/acceptance identity;
- S1 protocol and admitted agent identity digests;
- S2 team-plan/schedule identity;
- one-agent versus multi-agent decision;
- bounded work-unit/dependency/coordination summaries;
- no credential/provider/source acceptance authority.

Malformed graphs, impossible coverage, ambiguous unsafe overlap or no eligible agent strategy fail closed.

### 3.3 Production-capable agent adapters

Provide a narrow production adapter around the existing protected implementation-generation/model transport rather than inventing a new model credential path. Each admitted agent identity must bind exact adapter/version/model-class evidence and return only canonical S1 `AgentResult`/checkpoint/evidence semantics.

Provider/model output remains untrusted candidate labor. Raw provider payloads, prompts, credentials, hidden reasoning, unrestricted URLs/commands and arbitrary authority are not canonical agent evidence.

Reference adapters remain test fixtures and must not be silently selected as production labor.

### 3.4 Bounded agent execution and recovery

Dispatch S2 assignments through exact S1 `AgentTaskRequest` bindings. Verify result/checkpoint admission before any candidate is considered. Recoverable failure uses accepted durable worker/lease/checkpoint evidence and S2 reassignment/generation limits; stale/revoked/competing terminal evidence fails closed.

Parallel execution is allowed only when the accepted S2 dependency/coordination plan allows it. Overlapping work is serialized or returned for replanning; it is never race-applied to canonical source.

### 3.5 Candidate construction without duplicate source authority

Agent labor produces bounded implementation-candidate/proposal evidence. Candidate construction must not accept canonical lineage.

For multiple outputs, candidate identity must bind:

- exact Project/run/spec/acceptance identity;
- exact producer/team identities;
- exact base source-lineage/source-context identity;
- exact proposal digest and attempt identity;
- bounded cost/time/retry evidence state.

Only a selected candidate may be handed to the existing `ProtectedImplementationRuntime` mutation boundary. The safe implementation engine and existing lineage gateway revalidate the proposal against the current protected workspace immediately before canonical mutation. Stale-base or conflicting candidate patches fail closed.

If minimal safe integration requires extending `ProtectedImplementationRuntime`, the extension must be an injected pre-generated-candidate seam that preserves all existing validation, safe mutation, lineage receipt and durable stage semantics. It must not bypass proposal validation or accept caller-provided workspace roots.

### 3.6 Validation and S3 evaluation

After an exact candidate has protected deterministic evidence available, construct accepted S3 evaluation input from that exact candidate and protected evidence. Producer self-evaluation cannot satisfy independent quality policy.

A deterministically failed, missing, stale or cross-candidate validation cannot be converted to support by evaluator/model text.

### 3.7 S4 routing and S5 competition

S4 consumes only admitted strategy/outcome facts with explicit provenance/known state. Quality/confidence floors and protected failures remain non-tradeable. Unknown cost/time is never treated as zero.

S5 competition is optional and policy-triggered. Multiple agents or candidates alone do not force competition. Only exact eligible candidates may compete. Synthesis, when policy requests it, is a new attempt/candidate requiring fresh protected validation and independent evaluation before comparison.

### 3.8 Selected candidate to protected runtime

Exactly one selected candidate may be committed through the protected IMPLEMENT path. The resulting accepted lineage is the only lineage allowed into BUILD/TEST/VERIFY and source delivery.

The agentic controller cannot directly call lineage metadata/object stores to advance a head. It cannot mark IMPLEMENT passed without the existing safe mutation + lineage receipt + `EngineeringRunService.complete_stage` sequence.

### 3.9 Preview and REVIEW

When the existing runtime reaches REVIEW_REQUIRED, existing `SourceDeliveryComposition` publishes the exact accepted lineage to GitHub/Vercel Preview under current provider authorization/idempotency rules.

Agentic evidence may be included in bounded operator-review evidence, but cannot complete REVIEW. Exact replay cannot duplicate branch/commit/PR/Preview publication.

### 3.10 Persistence and replay

Persist or derive sufficient canonical evidence so request/process recreation can reproduce the accepted agentic PLAN/team/assignment/candidate decision without relying on transient in-memory agent state. Repeated identical operation identity is duplicate-safe. Drift creates a distinguishable operation/fingerprint or fails closed; it must never silently overwrite accepted evidence.

Prefer existing Engineering Run attempt/evidence and durable worker/checkpoint stores. Add new persistence only if existing bounded durable records cannot represent the required identity safely; any new schema requires a separate migration gate and must not be activated merely by source integration.

### 3.11 Observability

Expose bounded non-secret telemetry adequate to prove runtime behavior:

- selected team/strategy class and digests;
- assignment/recovery counts;
- S3/S4/S5 dispositions and reason codes;
- explicit observed/estimated/unknown economic state;
- selected candidate/lineage identity;
- replay/idempotency state;
- terminal REVIEW/HUMAN_REQUIRED reason.

Do not log prompts, hidden reasoning, source bytes, raw provider payloads or credentials.

### 3.12 Failure behavior

At minimum fail closed on:

- Project/run/spec/acceptance/source-context drift;
- no eligible production agent;
- malformed/unsafe work graph;
- stale/revoked/competing S1 result;
- exhausted S2 recovery/reassignment/no-progress bounds;
- producer self-evaluation or mismatched S3 evidence;
- failed/missing protected validation;
- stale/invalid/cross-Project S4 evidence;
- S5 out-of-policy competition or unvalidated synthesis;
- stale candidate base or safe-patch rejection;
- lineage CAS conflict;
- provider delivery failure;
- attempted merge/production deploy/REVIEW completion by agentic code.

## 5. Non-goals

- New agent marketplace or arbitrary user-authored adapters.
- New model/provider credential path.
- Generic shell, arbitrary HTTP/network, unrestricted package-manager or filesystem authority.
- Replacement of Engineering Run/service/source-lineage state machines.
- Multiple canonical writers.
- Autonomous production deployment, merge, approval or REVIEW completion.
- Client UI redesign unless a server-visible state cannot be represented by the existing Build/Live Build surfaces.
- Billing, enterprise RBAC or constitutional redesign.

## 6. Security and reliability

Agent/model/repository/evaluator content is evidence only. Server-owned registries/policies decide admissibility. Every candidate must remain exact-identity bound and revalidated by the existing protected mutation/validation boundaries. Cross-Project evidence is structurally rejected.

No raw credential, OIDC token, provider payload, prompt or hidden reasoning may enter agent evidence, durable run evidence, client payloads or logs. Production provider access remains request-scoped and project-scoped under existing authority.

Bounded retries, reassignment, competition, synthesis and runtime steps are mandatory. Exhaustion resolves to explicit bounded failure/HUMAN_REQUIRED rather than unbounded compute.

## 7. Acceptance criteria

### AC-01 Ordinary runtime uses one agentic admission path
An approved eligible Engineering Run reaches a server-owned agentic runtime seam during normal PLAN/IMPLEMENT execution, bound to exact Project/run/spec/acceptance identity. The operator does not select agents manually, and no parallel ungoverned implementation path is invoked.

### AC-02 Smallest adequate one-agent and multi-agent team behavior
Permanent runtime tests prove the same composition selects one compatible agent when sufficient and a bounded multi-agent team when decomposition/capability evidence requires it, with dependency-safe parallelism and conservative serialization of overlapping coordination domains.

### AC-03 Production-capable S1 adapter and result admission
At least one production-capable adapter wraps the existing protected model/implementation-generation transport into exact S1 identity/task/result/checkpoint evidence. Stale, revoked, mismatched and competing results are rejected before candidate admission; reference adapters are never silently used as production labor.

### AC-04 Durable recovery and replay
A recoverable agent failure is resumed or reassigned only from accepted durable worker/checkpoint evidence, advances generation/attempt identity correctly, remains within bounds and survives request/process recreation without duplicate canonical source mutation.

### AC-05 Single-writer candidate handoff preserves safe IMPLEMENT authority
Agent outputs cannot mutate or accept canonical lineage directly. Exactly one selected candidate is revalidated and applied through the existing safe implementation engine, existing lineage acceptance/CAS boundary and existing durable IMPLEMENT stage transition. Stale/conflicting proposals mutate nothing.

### AC-06 Protected validation and independent evaluation precedence
Failed/missing/stale deterministic BUILD/TEST/VERIFY evidence blocks S3 support; producer self-evaluation cannot satisfy independence; evaluation remains exact-candidate and exact-policy bound.

### AC-07 Trustworthy routing, selective competition and synthesis
S4 only scores already-admissible strategies using provenance-bound evidence with explicit unknown state. S5 cannot select failed/unvalidated candidates, multiple candidates alone do not force competition, and synthesis creates a fresh candidate requiring fresh validation/evaluation.

### AC-08 Exact selected lineage reaches replay-safe Preview
Only the selected accepted lineage reaches BUILD/TEST/VERIFY and existing GitHub/Vercel Preview delivery. Process recreation/replay does not substitute lineage or duplicate branch/commit/PR/Preview mutation.

### AC-09 REVIEW/HUMAN_REQUIRED and authority boundaries remain intact
Runtime activation stops at REVIEW/HUMAN_REQUIRED. Agentic code cannot complete REVIEW, merge, production-deploy, create provider credentials, widen capabilities or bypass Project/tool/provider policy. Adversarial tests prove fail-closed behavior.

### AC-10 Whole-product regression and release evidence
Focused W6-R1 tests plus accepted S1-S6, worker recovery, source-lineage, safe implementation, BUILD/TEST/VERIFY, provider delivery, production preflight and client regressions pass. Exact-head Workstream Spec Validation, Bounded Autonomy Pilot and P2 CI pass. The final integration checkpoint records generated/validated/integrated/deployed states distinctly; no production claim occurs before a separate governed release and post-cutover verification.
