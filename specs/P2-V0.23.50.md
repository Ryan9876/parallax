## 1. Objective

Make a verified REVIEW result recoverable when Preview publication fails, without rerunning protected implementation or verification, and make the desktop Run observability workspace vertically reachable.

Production Engineering Run `89f6db3f-7a56-4e18-8307-22e377b2766a` proved both defects:

- IMPLEMENT, BUILD, TEST and VERIFY succeeded on one immutable accepted lineage;
- the run reached REVIEW revision 6 with `last_failure_code=null`;
- Vercel Preview delivery failed and emitted `SOURCE_DELIVERY_FAILED`;
- no delivery-only retry action exists;
- desktop observability uses a fixed-height root with only nested-pane scrolling, so lower content can be inaccessible.

P2-V0.23.50 adds an explicit REVIEW-only delivery recovery surface and correct desktop scroll containment.

## 2. Scope

Included:

- read-only REVIEW delivery status for the exact current accepted lineage;
- REVIEW-only Vercel Preview retry from the already verified lineage;
- reuse of existing server-owned source-delivery readiness and provider idempotency contracts;
- no protected lifecycle stage rerun during retry;
- safe Preview/PR result projection;
- explicit retry UI inside the existing delivery panel;
- desktop observability root vertical scrolling while retaining inner pane scrolling;
- API/client/browser regressions;
- Architecture v3.59 after semantic validation.

## 3. Non-goals

This release does not:

- rerun PLAN, IMPLEMENT, BUILD, TEST or VERIFY during delivery retry;
- alter accepted source lineage;
- merge a pull request;
- deploy to production;
- complete REVIEW automatically;
- convert Preview success into acceptance evidence;
- change Work Specification or Behavioral Verification Plan semantics;
- broaden GitHub/Vercel provider authority;
- auto-retry the user's production run without an explicit operator action;
- redesign the observability workspace.

## 4. Security

Delivery retry is allowed only when:

- the Engineering Run is owner-scoped and Project-bound;
- the run state is exactly REVIEW;
- the canonical Project delivery mode is exactly `vercel-preview`;
- durable lineage exists;
- accepted IMPLEMENT evidence identifies a source lineage;
- passed VERIFY evidence proves protected success on that exact lineage;
- the durable current lineage still equals the verified lineage.

The endpoint accepts no repository, branch, commit, pull-request, Vercel Project, deployment or lineage identity from the client. Those identities remain server-derived.

Existing GitHub branch/commit/PR and Vercel Preview clients remain authoritative and replay-safe. Retry grants no production target or merge authority.

A retry failure must not mutate Engineering Run state, revision, attempts, accepted lineage or REVIEW authority.

## 5. Acceptance criteria

### AC-01 REVIEW delivery status is read-only and exact
A read endpoint returns `NOT_PUBLISHED` or `PUBLISHED` for the exact current REVIEW run and canonical Project delivery mode. Published status may expose only bounded safe PR/Preview URLs and provider identifiers from a durable verified delivery record.

### AC-02 Retry is REVIEW-only
Delivery retry rejects non-REVIEW runs and historical/unbound runs before any provider mutation.

### AC-03 Retry never reruns protected lifecycle stages
A delivery retry must not invoke AutonomyCoordinator and must not create PLAN/IMPLEMENT/BUILD/TEST/VERIFY attempts.

### AC-04 Exact verified lineage remains authoritative
Retry must reuse existing VerifiedLineageDelivery checks proving accepted IMPLEMENT and passed VERIFY refer to the same exact current lineage.

### AC-05 Provider publication is replay-safe
Retry reuses the existing canonical publication branch, exact lineage commit, matching open PR and exact Preview when already present. It may create only missing bounded publication artifacts.

### AC-06 Run authority remains unchanged
Success or failure leaves Engineering Run state REVIEW, run revision unchanged, protected lifecycle attempt identities unchanged, and `last_failure_code` unchanged. A successful publication may add/replay only the existing durable `SOURCE_DELIVERY` record used by the accepted delivery contract.

### AC-07 Delivery events remain truthful
Successful retry records/replays one SOURCE_DELIVERY success fact for the exact lineage. Failed retry may record bounded delivery failure evidence but cannot be presented as a run-stage failure.

### AC-08 Client exposes explicit delivery recovery
At REVIEW with `vercel-preview`, the delivery panel shows current delivery status. When not published it exposes `Retry Vercel Preview`; on success it exposes safe `Open Vercel Preview` and `Open GitHub PR` links/actions without saying merged or deployed.

### AC-09 Retry UI does not reuse generic build continuation
The delivery action calls only the delivery retry API. It does not call resume/autonomous continuation.

### AC-10 Desktop observability vertically scrolls
At desktop widths, the Live Build workspace root is vertically scrollable so header, pipeline, tabs, primary content and contextual content are reachable without browser zoom or layout clipping.

### AC-11 Nested observability panes remain usable
Event stream, code, diff, evidence and horizontal technical panes preserve their existing bounded inner scrolling and Follow Live behavior.

### AC-12 Mobile behavior does not regress
The existing compact/mobile root scroll and mobile Build/Review flows remain unchanged.

## 7. API design

### 7.1 GET /v1/engineering-runs/{run_id}/delivery

Returns a bounded object:

- `run_id`;
- `delivery_mode`;
- `status: NOT_PUBLISHED | PUBLISHED`;
- `preview_status` when durable;
- `preview_url` when safe and durable;
- `pull_request_url` when safe and durable;
- `preview_deployment_id` when durable;
- `pull_request_number` when durable.

The read path never provisions a Vercel Project and never mutates provider state.

### 7.2 POST /v1/engineering-runs/{run_id}/delivery/retry

Input is only an `EngineeringOperation` containing server-bound operation identity and expected run revision. The route:

1. reads canonical run and Project;
2. checks REVIEW and `vercel-preview`;
3. checks expected revision without transitioning the run;
4. composes the existing lazy source-delivery stack;
5. invokes only `delivery.deliver(...)`;
6. re-reads the run and proves state/revision and protected lifecycle attempt identities unchanged; the existing durable SOURCE_DELIVERY record may be added/replayed;
7. emits bounded delivery success/failure observation;
8. returns delivery status.

## 8. Client design

The existing REVIEW Delivery card becomes the operator recovery surface. It reads delivery status when the run is REVIEW and delivery mode is Vercel Preview.

- NOT_PUBLISHED → `Retry Vercel Preview`;
- retry busy → `Publishing preview…`;
- PUBLISHED → safe Preview/PR actions.

No generic Try again/resume action is used for this condition.

## 9. Desktop scrolling design

LiveBuildWorkspace uses an outer vertical ScrollView on non-compact widths. The content container grows to at least the available workspace height but can exceed it. Existing event/code/evidence ScrollViews remain nested.

This fixes reachability without changing the surrounding desktop navigation rail or conversation scroll behavior.
