# Parallax 2.0 — Human-Authorized Worker PLAN Rebinding After PLAN Refresh

Status: APPROVED FOR IMPLEMENTATION — SPEC-FIRST
Spec ID: P2-V0.23.14
Date: 2026-08-30
Workstream: #476
Architecture target: v3.27

## 1. Objective

Complete the P2-V0.23.13 failed-IMPLEMENT retry path by allowing the recovered durable worker to checkpoint against the newly persisted protected PLAN, without weakening the ordinary rule that an accepted worker checkpoint cannot arbitrarily change its PLAN reference.

## 2. Triggering production evidence

Authenticated production replay on Engineering Run `03bb96e1-5f42-483f-bca3-5b8d6d3bf4cb` proved the P2-V0.23.13 boundaries through worker reassignment:

- explicit `/resume` returned HTTP 200 and moved `FAILED / resume_stage=IMPLEMENT / revision 3` to `PLAN / revision 4`;
- the control attempt persisted `plan_refresh_authorized=true`;
- a new protected PLAN passed at revision 5 under current orchestration policy, with a new `team_plan_id`, roster digest and selected-agent identity;
- worker recovery persisted `STALLED -> RECOVERING -> REASSIGNED` and incremented lease generation from 1 to 2;
- immediately after reassignment, before any hosted model/provider invocation, the worker stopped bounded with `AGENTIC_TASK_FAILED` at `AGENT_PROPOSAL`, and `/autonomous` returned HTTP 422.

The protected worker checkpoint validator currently rejects any `plan_ref` change once a checkpoint has accepted a prior PLAN reference. That invariant is correct for ordinary execution, but it is incomplete for the explicit human-authorized PLAN-refresh transition added by P2-V0.23.13: the historical worker checkpoint still names the old PLAN while the new IMPLEMENT dispatch correctly names the freshly persisted PLAN.

## 3. Fixed decision

Retain PLAN-reference immutability by default. Permit exactly one effective PLAN-reference replacement only when the Engineering Run itself proves a valid human-authorized refresh cycle:

1. a persisted PLAN control attempt has status `RESUMED` and bounded evidence `plan_refresh_authorized=true`;
2. a later protected PLAN attempt has status `PASSED`;
3. that passed PLAN contains a valid server-owned `team_plan_id`;
4. the incoming worker checkpoint `plan_ref` equals exactly `agentic-plan:<that team_plan_id>`.

No caller-supplied flag, model text, repository content, exception text or worker-local state may manufacture this authority.

After the first accepted checkpoint under the refreshed PLAN, the ordinary existing-plan-reference equality rule applies again because the worker's current checkpoint now carries the refreshed PLAN reference.

## 4. Boundaries

- Historical PLAN attempts, failed IMPLEMENT attempts, run events and prior worker event/checkpoint history remain preserved.
- Work Specification identity and accepted source lineage remain unchanged.
- A normal worker checkpoint cannot change `plan_ref`.
- A process-loss reassignment without a preceding human-authorized PLAN refresh cannot change `plan_ref`.
- A `RESUMED` PLAN control without `plan_refresh_authorized=true` grants no rebinding authority.
- A refresh control without a later successful protected PLAN grants no rebinding authority.
- The replacement reference must exactly match the latest valid refreshed protected PLAN; arbitrary or historical PLAN references fail closed.
- PLAN rebinding grants no source mutation, lineage acceptance, Git/provider, deployment, approval or REVIEW authority.
- Worker lease-generation, retry, no-progress, oscillation and reassignment bounds remain unchanged.
- No database migration and no public API change are introduced.

## 5. Scope

- Add one deterministic helper in the protected worker checkpoint domain that derives the currently authorized refreshed PLAN reference from persisted Engineering Run attempt evidence.
- Extend checkpoint validation so a changed `plan_ref` is accepted only when it exactly equals that derived protected reference.
- Preserve all existing checkpoint identity, Work Specification, source-lineage, secret-safety and bounded-payload validation.
- Add focused regressions for authorized replacement and all relevant denial cases.
- Re-run the P2-V0.23.13 production retry path on a fresh QA-owned failed IMPLEMENT fixture after deployment.

## 6. Acceptance criteria

### AC-01 Default PLAN immutability remains intact
Without a valid human-authorized PLAN-refresh cycle, changing an accepted worker checkpoint `plan_ref` continues to raise `WorkerCheckpointError`.

### AC-02 Explicit refresh authorizes only the fresh protected PLAN
A persisted `PLAN / RESUMED` attempt with `plan_refresh_authorized=true` followed by a later `PLAN / PASSED` attempt authorizes only `agentic-plan:<team_plan_id>` from that successful refreshed PLAN.

### AC-03 Malformed or incomplete refresh evidence fails closed
Missing, false or malformed refresh evidence, missing/malformed `team_plan_id`, or a refresh control without a later PASSED PLAN does not authorize rebinding.

### AC-04 Historical or arbitrary PLAN references remain denied
Even after a valid refresh cycle, a checkpoint cannot select any PLAN reference other than the exact refreshed PLAN reference.

### AC-05 Worker/source authority is unchanged
The change does not alter lease acquisition/reassignment limits, Work Specification binding, source-lineage equality, canonical mutation, provider/Git/deployment authority or REVIEW boundaries.

### AC-06 Refresh authority comes only from protected persisted attempts
Browser input, public request payloads, model output, repository content, exception strings and worker-local flags cannot create or select the authorized replacement PLAN reference.

### AC-07 Newer incomplete refresh fails closed
If a later human-authorized PLAN-refresh control exists but no later protected PLAN has passed, any prior replacement authority is invalidated until the new PLAN succeeds.

### AC-08 Post-rebind immutability resumes immediately
Once the refreshed PLAN reference is accepted into the current worker checkpoint, subsequent checkpoints remain bound to that exact reference under the ordinary equality rule unless another complete explicit human-authorized refresh cycle occurs.

### AC-09 Persistence and public API remain compatible
No database migration, persistence column, browser request field or response schema is added. Rollback is application revert only.

### AC-10 Production retry progresses beyond checkpoint rebinding
After exact-source deployment, an authenticated user-equivalent retry of a QA-owned failed IMPLEMENT run must persist the fresh PLAN, worker reassignment and at least the first post-reassignment worker checkpoint under the refreshed PLAN, then reach hosted implementation dispatch or expose a later bounded failure beyond PLAN-reference validation.

## 7. Security and reliability

Authorization is reconstructed solely from immutable persisted Engineering Run attempts already written by the protected state machine. The validator does not trust browser parameters, worker-local flags or exception strings. The exact refreshed PLAN ID is cryptographically bounded and must match the incoming checkpoint reference. This keeps ordinary PLAN immutability fail-closed while making explicit human-authorized replanning internally coherent.

## 8. Non-goals

- General mutable worker PLAN references.
- Automatic failed-run retries.
- Rewriting or deleting historical checkpoints or attempts.
- New worker state-machine states or persistence columns.
- Model-routing, candidate-recovery or validator changes.
- Client UX changes.
- Transaction redesign for non-authoritative run-event emission.
