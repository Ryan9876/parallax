# Parallax 2.0 — Human-Authorized Worker PLAN Rebind After Refreshed PLAN

Status: APPROVED FOR IMPLEMENTATION — SPEC-FIRST
Spec ID: P2-V0.23.14
Date: 2026-08-30
Workstream: #483
Architecture: v3.27

## 1. Objective

Allow a recovered durable agentic worker to bind its fresh mutation generation to the exact new protected PLAN created by P2-V0.23.13 after an explicit human retry, while preserving ordinary worker PLAN-reference immutability and keeping Engineering Run state consistent when protected worker checkpoint validation fails.

## 2. Triggering production evidence

Authenticated production QA run `33333765067` acted through the same resume and autonomous endpoints used by the client on Engineering Run `03bb96e1-5f42-483f-bca3-5b8d6d3bf4cb`.

The retry correctly produced:

- `/resume` HTTP 200;
- durable `FAILED + resume_stage=IMPLEMENT -> PLAN`;
- a `RESUMED` PLAN control attempt with `plan_refresh_authorized=true`;
- a new successful protected PLAN under current orchestration policy;
- worker `PROCESS_LOSS -> STALLED -> RECOVERING -> REASSIGNED`;
- a fresh worker lease generation.

The first protected worker checkpoint under the refreshed PLAN then failed before hosted model dispatch. The prior durable checkpoint still carried the historical `agentic-plan:<old-team-plan-id>` reference, while the new checkpoint correctly carried `agentic-plan:<fresh-team-plan-id>`. Existing worker validation rejects every PLAN-reference change after initial acceptance, so the refreshed PLAN could not become the active worker PLAN contract. The worker stopped as `AGENTIC_TASK_FAILED`, `/autonomous` returned HTTP 422, and the Engineering Run remained active at IMPLEMENT.

## 3. Fixed decisions

- Worker PLAN-reference immutability remains the default and must not be globally relaxed.
- One changed worker PLAN reference is admissible only when server-held durable run history proves the exact P2-V0.23.13 human PLAN-refresh sequence and the requested reference matches the latest successful protected agentic PLAN.
- The accepted rebind is not a new PLAN. It binds the newly recovered worker generation to the already-persisted fresh PLAN.
- Historical worker checkpoint payloads, PLAN attempts, failures, lineage evidence and lease generations are not rewritten.
- After the new PLAN reference is persisted in the next worker checkpoint, ordinary equality-based PLAN immutability resumes automatically.
- A protected worker checkpoint contract failure during agentic generation is a bounded pre-mutation implementation failure. It must reach the existing `ImplementationContractError -> AUTONOMOUS_IMPLEMENT_FAILED` path rather than leaving an active IMPLEMENT run paired with a terminal worker.

## 4. Protected rebind authorization

A changed worker `plan_ref` may be accepted only when all of the following are true:

1. the Engineering Run is currently `IMPLEMENT`;
2. an existing durable checkpoint already has a different PLAN reference;
3. the requested reference has canonical form `agentic-plan:<lowercase-sha256>`;
4. the latest two PLAN attempts form the exact protected refresh boundary: the newest PLAN attempt is `PASSED`, and the immediately preceding PLAN attempt is `RESUMED` with bounded evidence `plan_refresh_authorized=true`;
5. the newest PASSED PLAN evidence contains `team_plan_id`, and the requested worker reference is exactly `agentic-plan:<team_plan_id>`;
6. the rebind is exercised only at the first protected dispatch checkpoint for the refreshed implementation generation.

No browser request field, model output, repository content, provider response or arbitrary checkpoint text may create this authorization. If any condition is absent, malformed or ambiguous, the existing PLAN-reference mismatch rejection remains authoritative.

## 5. Worker and run consistency

`WorkerCheckpointError` remains a worker-recovery error but is also a typed protected value/contract error at the implementation generation boundary. When such an error occurs before canonical mutation, `ProtectedImplementationRuntime` must convert it through its existing bounded generation-failure handling so `AutonomyCoordinator` records a durable failed IMPLEMENT attempt with `AUTONOMOUS_IMPLEMENT_FAILED`.

The fix must not convert unknown exceptions, source-mutation failures after mutation, revision conflicts or unrelated infrastructure faults into fabricated implementation failures.

## 6. Scope

- Narrow worker checkpoint PLAN-reference authorization for the human-refreshed PLAN sequence.
- Preserve the existing generic `validate_checkpoint` fail-closed contract for all other PLAN changes.
- Keep worker recovery, lease ownership, source-lineage and checkpoint bounds unchanged.
- Make typed checkpoint contract errors participate in the existing pre-mutation implementation failure boundary.
- Add focused regressions for authorized and unauthorized rebinds and the production-shaped expired-worker recovery sequence.
- Update Architecture to v3.27.

## 7. Acceptance criteria

### AC-01 Ordinary PLAN-reference immutability remains
A worker checkpoint with a changed `plan_ref` is rejected exactly as before when no protected human PLAN-refresh sequence authorizes the new reference.

### AC-02 Exact human-refresh history is required
A changed reference is not admitted merely because the worker has recovered, the run is at IMPLEMENT, or a later PLAN exists. The latest PLAN history must contain the exact `RESUMED(plan_refresh_authorized=true) -> PASSED` sequence.

### AC-03 Fresh protected PLAN identity is exact
The only admissible changed reference is `agentic-plan:<team_plan_id>` from the newest PASSED PLAN attempt in that exact refresh sequence. A stale, arbitrary or malformed PLAN identity fails closed.

### AC-04 Rebind occurs only at refreshed dispatch
The exceptional changed-reference admission is limited to the first protected agent-dispatch checkpoint that follows the human-refreshed PLAN. It does not create a generic checkpoint API for changing PLAN identity.

### AC-05 One rebind then immutability resumes
After the first accepted checkpoint persists the fresh PLAN reference, subsequent checkpoints use ordinary equality validation. A second unrelated PLAN change is rejected unless a later independently authorized human PLAN refresh creates another exact protected sequence.

### AC-06 Production-shaped expired worker recovers
A durable worker carrying an old PLAN checkpoint and expired old lease can traverse protected process-loss recovery to a fresh lease generation and persist its first checkpoint under the human-refreshed PLAN without `AGENTIC_TASK_FAILED` at PLAN-reference validation.

### AC-07 Historical evidence and lineage are preserved
Worker identity, prior checkpoint history, checkpoint revision progression, accepted/last-known-good lineage, lease-generation history, prior PLAN/IMPLEMENT attempts and run events remain intact.

### AC-08 Typed checkpoint failures keep run and worker state coherent
A protected worker checkpoint contract failure during pre-mutation agentic generation is converted into the existing bounded implementation failure path, causing a durable FAILED IMPLEMENT attempt rather than HTTP 422 with an active IMPLEMENT run and terminal worker.

### AC-09 No authority expansion
The change grants no new source mutation, lineage acceptance, Git/provider credentials, arbitrary network/tool use, deployment, production promotion or REVIEW-completion authority.

### AC-10 Exact-head and production proof
Focused worker/agentic/runtime tests and the full protected release gates pass. After exact-source production deployment, authenticated user-equivalent QA on a fresh failed IMPLEMENT fixture must show `resume -> fresh PLAN PASSED -> worker fresh generation -> first refreshed dispatch checkpoint` and hosted implementation dispatch, or capture the next later bounded failure with preserved diagnostic evidence.

## 8. Security and reliability

PLAN identity remains server-derived and digest-bound. The exceptional rebind does not trust the checkpoint merely because it claims a new PLAN; durable Engineering Run history independently proves the fresh PLAN identity and the explicit human authorization that caused it. Any missing or malformed evidence fails closed.

Checkpoint failure classification remains bounded. Raw exception messages, prompts, model output, credentials and hidden reasoning are not persisted as diagnostics.

## 9. Non-goals

- Global worker PLAN mutability.
- Automatic PLAN refresh without explicit human retry.
- Rewriting historical checkpoints or PLAN attempts.
- A second worker state machine or lease path.
- Same-model retry loops or changes to Luna -> Terra -> Sol policy.
- Relaxing proposal/candidate validation.
- Changing client retry UX.
- New repository/provider/deployment permissions.
- Moving or bypassing REVIEW.
