## 1. Objective

Modernize the existing Parallax platform in place so persistence and Engineering Run transitions are materially faster, execution boundaries are easier to reason about, DSPy development remains protected and reproducible, observability can stream safely, and the existing Warm Editorial Observatory workspace becomes a more responsive live engineering surface.

This release is an in-place platform overhaul, not a greenfield rewrite. It preserves the current FastAPI/SQLAlchemy service, Expo/React/Skia client, existing Project and Engineering Run contracts, exact source-lineage authority, replay-safe worker semantics, preview-only delivery ceiling, and human REVIEW completion boundary.

The work is implemented in six ordered phases:

1. persistence and schema organization;
2. execution, transition and cache boundaries;
3. DSPy program/compiler hardening and deterministic offline intelligence;
4. delivery isolation;
5. authenticated replayable observability streaming;
6. client streaming/workspace integration plus integrated validation.

## 2. Scope

Included:

- split the monolithic SQLAlchemy model surface into focused model modules while preserving compatibility imports;
- preserve one canonical metadata graph and identical clean schema semantics across SQLite and PostgreSQL;
- improve database/session/repository hot paths used by Engineering Run transitions, run events, worker leases and checkpoints;
- add the indexes and query-shape changes required by measured transition performance;
- preserve exact same-lineage, lease, retry, recovery and rollback behavior;
- clarify the boundaries among autonomy coordination, candidate implementation, execution/cache helpers and durable mutation;
- ensure cache layers accelerate reads/computation only and never become lifecycle or lineage authority;
- keep DSPy programs/compiler modules optimizable while protected evaluators, thresholds and promotion rules remain outside optimizer control;
- provide a deterministic offline intelligence path for development and regression tests;
- isolate source delivery from engineering lifecycle execution and retain the existing Preview/REVIEW ceiling;
- add owner-scoped authenticated observability streaming with replay/cursor semantics and bounded reconnect behavior;
- retain canonical read endpoints as reconciliation authority;
- migrate the existing client observability hook toward streaming while preserving safe fallback/reconciliation behavior;
- refine the existing Live Build workspace and theme without replacing the current Expo/Skia architecture or Warm Editorial Observatory design language;
- responsive, scrolling, keyboard and screen-reader verification;
- focused and full regression coverage, including SQLite/PostgreSQL schema checks and performance evidence;
- update authoritative records only when durable validated subject matter changes.

## 3. Non-goals

This release does not:

- replace Parallax with Next.js or another greenfield application stack;
- remove Expo, React Native Web or Skia;
- change conversation from the primary creation surface;
- weaken Project ownership, Work Specification approval, Engineering Run state/revision checks, exact source-lineage authority or worker-lease ownership;
- allow cache state to authorize mutation;
- expose protected evaluator implementations, protected thresholds, promotion-suite expected contracts or hidden reasoning to DSPy optimizers;
- allow candidate source to choose execution, credentials, provider identities, Git/Vercel targets, lifecycle transitions or release authority;
- merge generated application pull requests automatically;
- promote generated applications or Parallax itself to production automatically;
- make Vercel Preview success equivalent to behavioral acceptance;
- complete human REVIEW automatically;
- silently delete or purge an existing database during clean-initialization or migration work;
- claim historical-data cutover is complete merely because new schema/code is generated;
- redesign the product into an IDE, log console or generic dashboard.

## 4. Fixed decisions

- Current `main@7b503876d3e2d9d42261235ff466f89432f37d5f` is the implementation base.
- P2-V0.23.50 lineage, worker single-flight, REVIEW delivery retry and desktop scroll corrections remain foundations and must not regress.
- `apps/client` remains the production client architecture.
- `services/api` remains the production API architecture.
- SQLite remains a supported development/test database and PostgreSQL remains the production-class database contract.
- Existing database contents are preserved unless a separately authorized migration/cutover explicitly transforms them.
- Protected evaluators and release thresholds remain deterministic code outside optimizer-controlled DSPy programs.
- Vercel delivery remains Preview-only for generated applications under this release.
- Human REVIEW remains the terminal engineering authority boundary.
- Streaming is additive transport; canonical durable state and read APIs remain authoritative.
- The release is not complete until measured transition latency improves by at least 40% against the P2-V0.23.50 baseline on the defined benchmark path without protected semantic regression.

## 5. Architecture requirements

### 5.1 Persistence

The model refactor must produce one SQLAlchemy metadata graph. Focused modules may define domain groups, but imports through the historical `parallax_api.models` surface remain compatible until callers are deliberately migrated.

Schema creation must be deterministic and equivalent on clean SQLite and PostgreSQL databases for the supported model set. New indexes must target demonstrated hot predicates/orderings rather than speculative duplication.

Database initialization may create missing schema on a clean database. It must never silently drop, truncate or recreate an existing database merely to match the new code. Historical data conversion is a separately observable migration concern.

### 5.2 Repository and transition hot paths

Engineering Run transition, run-event append/read, worker lease/checkpoint and source-lineage operations must minimize avoidable round trips while retaining atomicity, optimistic revision protection, monotonic event sequence semantics and replay safety.

The performance benchmark must compare the same transition scenario against P2-V0.23.50 and report median/representative latency under controlled local conditions. Admission requires at least 40% improvement and no correctness regression.

### 5.3 Execution and cache boundaries

`code/autonomy.py`, `code/implementation.py` and cache helpers must expose narrower responsibilities. Durable state transitions remain repository/service authority. Candidate generation and execution helpers return bounded results rather than mutating unrelated lifecycle state.

Caches may store deterministic derived/read data with explicit keys and invalidation/TTL policy. Cache hits cannot bypass owner checks, expected revision, lease checks, lineage validation, protected evidence requirements or provider authority.

### 5.4 DSPy and intelligence

DSPy program/signature/compiler code may be optimized using development-suite evidence. Protected metrics/evaluators, protected thresholds, promotion rules and promotion-suite expected outputs remain outside optimizer input and mutation.

Development and CI require a deterministic offline intelligence path that can exercise compiler/program contracts without external provider availability. Provider-backed compilation remains supported and produces explicit provenance when used.

No hidden chain-of-thought or scratchpad is stored, scored or exposed.

### 5.5 Delivery isolation

Source delivery is downstream of exact accepted lineage plus passed VERIFY evidence and is not an Engineering Run lifecycle stage. Delivery failure cannot retroactively turn a verified REVIEW run into IMPLEMENT/BUILD/TEST/VERIFY failure.

Generated-application authority remains bounded to the configured delivery mode. For `vercel-preview`, PR merge, default-branch mutation and production promotion remain forbidden.

### 5.6 Observability streaming

Add an authenticated owner-scoped streaming route for Engineering Run observability. The stream replays durable events after an explicit cursor, then follows new durable events in monotonic sequence order.

The server validates cursor shape and run ownership, bounds replay and heartbeat behavior, and allows reconnect without inventing events. A client cursor is observation state only and never grants mutation authority.

Canonical event/read APIs remain available for initial load, reconciliation and recovery when the stream is unavailable.

### 5.7 Client workspace

The client uses the existing design system and Live Build information architecture. Streaming reduces polling pressure and improves perceived liveness but does not make local client state authoritative.

Desktop and compact/mobile layouts must remain reachable and scrollable. Dense technical panes retain nested scrolling where appropriate. Keyboard focus, readable text sizing, visible state text, reduced-motion behavior and screen-reader semantics remain protected.

## 6. Acceptance criteria

### AC-01 Existing architecture is preserved
P2-V0.24.0 is implemented inside the existing FastAPI/SQLAlchemy API and Expo/React/Skia client. No greenfield Next.js replacement or competing application shell is introduced.

### AC-02 Model modularization preserves one schema contract
Focused model modules share one canonical SQLAlchemy metadata graph, historical `parallax_api.models` imports remain compatible, and clean SQLite/PostgreSQL schema checks pass for the supported tables, constraints and indexes.

### AC-03 Database initialization is non-destructive
Clean initialization creates required schema, while an existing database is never silently dropped, truncated or rebuilt. Any historical data cutover is explicit, separately validated and not inferred from code generation.

### AC-04 Repository hot paths retain protected semantics
Engineering Run transitions, run events and worker execution persistence preserve owner scope, expected revision, atomicity, monotonic sequence, exact lease ownership, replay safety and rollback/recovery semantics while reducing avoidable database round trips.

### AC-05 Transition latency improves by at least 40 percent
A controlled benchmark against the exact P2-V0.23.50 baseline demonstrates at least 40% improvement for the defined Engineering Run transition/event persistence path with the same correctness assertions.

### AC-06 Same-lineage, lease and rollback regressions remain green
Focused tests prove exact accepted-lineage checks, active-lease single-flight, expired-lease recovery, stale revision rejection and rollback/retry behavior are unchanged or stricter.

### AC-07 Cache cannot become authority
Any new/refined cache uses deterministic keys plus bounded invalidation/TTL behavior and cannot bypass authentication, revision, lease, lineage, protected evidence, lifecycle or provider checks.

### AC-08 Execution responsibilities are narrower
Autonomy coordination, implementation/candidate execution and durable mutation responsibilities are separated enough that candidate/execution helpers cannot mutate unrelated Engineering Run lifecycle state or provider authority implicitly.

### AC-09 DSPy optimization stays outside protected evaluation
DSPy programs/compiler code may be optimized, but protected evaluator implementations, thresholds, promotion rules and promotion-suite expected contracts are neither optimizer inputs nor optimizer-controlled outputs. Protected promotion gates remain deterministic.

### AC-10 Offline intelligence is deterministic
A provider-independent development/test intelligence path produces deterministic contract-valid outputs for covered compiler/program regression cases and records that it is an offline development path rather than provider-backed production intelligence.

### AC-11 Delivery remains isolated and Preview-bounded
Source delivery consumes only exact verified accepted lineage under the canonical Project delivery mode. Delivery failure does not rewrite protected lifecycle success, and `vercel-preview` grants no merge, default-branch or production-promotion authority.

### AC-12 Observability streaming is authenticated and replayable
The stream requires the same owner-scoped authentication as canonical reads, validates run ownership and cursor, replays durable events after the cursor in monotonic order, follows new durable events, and bounds replay/heartbeat behavior.

### AC-13 Streaming reconnect reconciles with canonical state
Client reconnect preserves only an observation cursor, resumes without duplicate-authority assumptions, and reconciles through canonical read APIs after gaps/errors. Poll/read fallback remains safe when streaming is unavailable.

### AC-14 Workspace behavior and accessibility do not regress
The existing Warm Editorial Observatory visual language, conversation-primary hierarchy, desktop/mobile reachability, nested technical scrolling, keyboard operation, readable text, reduced motion and screen-reader state semantics pass client/browser validation.

### AC-15 Release evidence stays truthful
The candidate passes changed-spec validation, authentic DSPy compiled-plan validation, focused API/client tests, cross-database schema checks, performance gate, full relevant API/client/protected release gates and records generated, validated, deployed and deployment-verified states distinctly.

## 9. Security and failure containment

- All mutating APIs retain owner authentication and expected-revision protection.
- Streaming is read-only observation and cannot reuse a cursor as an operation identity.
- Database and cache optimizations cannot weaken transaction or authorization boundaries.
- Provider credentials remain server-side and repository/project scoped.
- Candidate source cannot introduce arbitrary execution commands or delivery targets through this overhaul.
- Replay/reconnect must prefer duplicate observation over missing canonical durable facts; clients deduplicate by durable identity/sequence and reconcile through reads.
- A performance optimization that changes protected semantics is rejected even if it meets the latency target.
- A schema optimization that requires destructive historical transformation is blocked until the transformation is separately specified and validated.
