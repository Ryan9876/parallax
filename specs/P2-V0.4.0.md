# Parallax 2.0 v0.4.0 — Code 2.0 Execution Kernel Specification

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.4.0
Depends on: P2-V0.3.0
Method: Spec-first + mandatory DSPy-governed development + protected evaluation

## 1. Objective

Build Code 2.0 as a durable, observable engineering execution kernel on top of validated Reason 2.0 and the protected evaluation spine.

Code 2.0 must turn an approved software specification into a durable engineering run with an explicit lifecycle, typed planning, bounded execution/evidence contracts, resumable state, truthful build/test/verification status, and protected review before completion. The release must establish the execution architecture that later closed-loop repair and optimizer-driven improvement can safely use.

The kernel must not equate model output with implementation success. A run advances only when protected transition rules and required observable evidence permit the transition.

## 2. User outcome

A user can enter Code mode from a durable conversation governed by an approved specification and create or resume an engineering run without losing context after refresh or process interruption.

The user can see what stage the run is actually in, what evidence exists, why a run stopped, and whether work is generated, built, tested, verified, reviewed, or complete. Parallax must not claim implementation, validation, merge, deployment, or deployment verification merely because a model generated code or prose.

The primary interaction remains conversational. Code state may appear as concise run/step status inside the existing interface; this release does not turn Parallax into a conventional IDE or dashboard.

## 3. Fixed decisions

- An engineering run is a durable server-side entity separate from but linked to a durable conversation.
- Every run is bound to exactly one approved `spec_id` at creation. A run cannot silently switch to a later specification.
- Code 2.0 uses the protected workflow: `SPECIFY → PLAN → IMPLEMENT → BUILD → TEST → VERIFY → REVIEW → COMPLETE`.
- `SPECIFY` in Code 2.0 validates/binds an already approved specification; it does not permit Code mode to invent or self-approve a replacement specification.
- Protected transition policy, not model output or client state, owns run-stage mutation.
- Failed work remains observable. A failed build/test/verify/review does not advance to the next success state.
- v0.4.0 establishes a single-pass execution kernel. Autonomous multi-cycle repair is a later release and may not be smuggled into this release as an unbounded loop.
- A run may enter `PAUSED`, `FAILED`, `SPEC_AMENDMENT`, or `CANCELLED` terminal/holding states as defined by protected policy.
- Step attempts are append-only evidence. Retrying a step creates another attempt; it does not overwrite the prior attempt.
- Tool/command execution is behind an executor interface. API routes do not execute arbitrary shell commands directly.
- The initial live executor must be disabled by default. CI uses a deterministic recorded/fake executor. Any later live executor requires an explicit bounded workspace root and protected command policy.
- Command/tool evidence stores observable metadata and digests; secrets, environment values, hidden reasoning, and unrestricted raw execution transcripts are not public trace fields.
- Generated files/artifacts are identified by path plus SHA-256 digest and size before they can be used as evidence.
- Runtime model ordering remains Luna → Terra → Sol for Code planning/review programs that use the model router.
- Protected Code promotion contracts and thresholds remain outside DSPy/optimizer-controlled code.
- Passing a Code benchmark does not authorize merge or deployment.
- Code 2.0 must preserve the P2 visual system, live Reason behavior, and no-Skia degradation behavior.

## 4. Scope

### 4.1 Durable engineering-run model

Add durable server-side entities sufficient to represent an engineering run and its evidence.

At minimum a run records:

- opaque run ID;
- conversation ID;
- immutable bound spec ID;
- mode/program version metadata;
- current protected stage/state;
- optimistic concurrency/revision value;
- created/updated/completed timestamps;
- optional workspace identity/reference;
- latest failure code when not successful.

At minimum a step attempt records:

- opaque attempt ID;
- run ID;
- workflow stage;
- attempt number;
- status;
- started/completed timestamps;
- program/model identity when applicable;
- observable evidence references/digests;
- sanitized failure code when applicable.

Attempts are append-only. Historical evidence must remain queryable after retries and process restarts.

### 4.2 Protected workflow state machine

Create a deterministic protected transition policy for:

```text
SPECIFY
  ↓
PLAN
  ↓
IMPLEMENT
  ↓
BUILD
  ↓
TEST
  ↓
VERIFY
  ↓
REVIEW
  ↓
COMPLETE
```

Additional protected states:

- `PAUSED` — recoverable stop with durable state and an allowed resume target;
- `FAILED` — run cannot continue automatically under the current attempt/result;
- `SPEC_AMENDMENT` — requested/observed change is materially outside the bound approved spec;
- `CANCELLED` — explicit user/operator cancellation.

Requirements:

- transitions are explicit and validated server-side;
- success-stage skipping is rejected;
- a failed BUILD/TEST/VERIFY/REVIEW cannot be recorded as success without new passing evidence;
- `COMPLETE` requires all protected predecessor gates to have passing evidence;
- retries append attempts and preserve prior failure evidence;
- transition requests are idempotent under a client-supplied/derived operation key so network retry cannot double-advance a run;
- a stale revision must be rejected rather than silently overwriting newer run state.

### 4.3 Specification binding

`SPECIFY` validates that the requested spec:

- exists under the approved spec contract;
- has `Status: APPROVED FOR IMPLEMENTATION`;
- matches the durable conversation/run `spec_id`;
- passes the protected spec contract gate;
- has not been superseded for this run by an unapproved client/model mutation.

If a material objective change is detected, the run enters or remains `SPEC_AMENDMENT` instead of modifying its bound spec in place.

### 4.4 DSPy Code planner

Create a typed DSPy-compatible Code planner whose observable result contains bounded structured planning data, for example:

- `summary`;
- `work_items`;
- `files_or_boundaries`;
- `validation_commands_or_checks`;
- `risks`;
- `acceptance_ids_covered`;
- `program_version`.

The planner receives the approved spec contract plus bounded repository/workspace context supplied through an interface. It does not receive protected promotion-suite answers or promotion thresholds.

Protected planner validation must ensure every approved acceptance criterion is mapped before PLAN may pass. Protected code, not model obedience, derives the authoritative acceptance-ID set from the approved spec.

### 4.5 Workspace and repository context boundary

Define a provider-neutral workspace/repository interface. Code 2.0 must not couple core workflow state to a specific Git hosting provider or local filesystem implementation.

The interface may expose bounded observable context such as:

- repository/workspace identity;
- base revision/commit identity;
- permitted root path;
- bounded file manifest/path metadata;
- selected file content through explicit reads;
- working-tree/change digest;
- artifact references.

Path traversal outside the configured workspace root is rejected. Provider credentials are never returned through this interface to model programs or public traces.

### 4.6 Implementation evidence contract

The IMPLEMENT stage must not be satisfied by prose stating that code was written.

Protected implementation evidence must include at least one observable code-change artifact/reference, including:

- changed file path(s) within the allowed workspace;
- resulting content or patch digest(s);
- base revision identity or pre-change digest;
- resulting workspace/change-set digest;
- tool/program identity that produced the change.

The evidence layer may store bounded patch text where explicitly safe, but protected release evidence must always include stable digests so artifact identity can be verified without trusting prose.

### 4.7 Execution broker and command policy

Introduce an executor/broker interface for build/test/verification commands.

The core API must not invoke unrestricted shell strings supplied by the client or model. A request is expressed as a typed execution specification with at minimum:

- tool/command identifier;
- argument list;
- bounded working directory relative to the approved workspace root;
- timeout;
- environment-variable allowlist/reference policy;
- stage (`BUILD`, `TEST`, or `VERIFY`);
- operation key.

Protected execution policy rejects:

- absolute/out-of-root working directories;
- shell metacharacter injection when a direct argv execution contract is required;
- undeclared environment access;
- commands marked destructive/privileged/deployment-capable in this release;
- network/deployment actions not explicitly allowed by an approved later capability;
- execution after cancellation or material specification amendment.

v0.4.0 CI uses a deterministic recorded executor. A live executor may exist only behind an explicit disabled-by-default configuration and must not be required for validation of the Code kernel architecture.

### 4.8 Build, test, and verify evidence

Each execution attempt produces a bounded observable result containing at minimum:

- command/tool identity;
- argument/working-directory digest;
- exit code or typed execution outcome;
- duration;
- stdout digest and bounded sanitized excerpt where useful;
- stderr digest and bounded sanitized excerpt where useful;
- timeout indicator;
- redaction indicator;
- produced artifact references/digests where applicable.

Rules:

- BUILD passes only on protected-success execution evidence.
- TEST passes only on protected-success test evidence.
- VERIFY passes only when required acceptance checks and evidence contracts are satisfied.
- absence of evidence is not success.
- non-zero/timeout execution is not silently converted to success by a model summary.

### 4.9 DSPy engineering reviewer

Create a typed DSPy engineering reviewer that can summarize observable implementation/build/test/verify evidence and identify gaps.

The reviewer may recommend `PASS`, `NEEDS_WORK`, or `SPEC_AMENDMENT`, but protected review policy owns the actual transition.

Protected review requires:

- all required prior gates passed;
- all approved acceptance IDs represented by verification evidence;
- no unresolved critical protected failure;
- no false deployment/merge status;
- no secret/hidden-reasoning leakage;
- evidence digests tied to the same run/workspace revision being reviewed.

`COMPLETE` may be entered only after protected review passes.

### 4.10 Failure, pause, resume, and idempotency

A process crash, request retry, provider failure, or user refresh must not erase run history.

Requirements:

- the latest durable run/step state is reloadable independently of in-memory state;
- resuming a run returns to a protected allowed stage rather than restarting from SPECIFY without evidence;
- operation keys prevent duplicate step creation/advancement from request retries;
- stale revision writes are rejected with a typed conflict;
- failure codes are sanitized and durable;
- candidate model output/hidden reasoning is not required to resume;
- `CANCELLED` and `SPEC_AMENDMENT` block further execution until a new authorized action/run is created.

### 4.11 API contract

Add Code API/service boundaries that keep orchestration outside the client.

At minimum support:

- create engineering run from an existing Code conversation and approved spec;
- get run including ordered step/attempt summaries;
- request/execute the next protected stage through an orchestration service;
- pause/resume/cancel where permitted;
- retrieve safe evidence/artifact metadata;
- stream or poll observable run-state updates without exposing executor secrets.

The API must reject attempts to bind a run to a different spec than the durable conversation without an approved amendment/new run.

### 4.12 Client integration

Code mode remains part of the conversation-first P2 interface.

Add a concise engineering-run presentation showing at minimum:

- bound spec ID;
- current stage/state;
- completed stages;
- current/last failure state when applicable;
- whether evidence exists for build/test/verify/review;
- resume/retry action only when protected server policy allows it.

Do not expose a raw terminal by default and do not turn the interface into an IDE/dashboard. Ordinary assistant text remains selectable/accessibility-first. Skia may augment stage motion but may not become the semantic source of truth.

Reduced-graphics mode must preserve Code run semantics and status honesty.

### 4.13 Code development and promotion benchmarks

Add separate repository-safe Code `development` and `promotion` suites using the protected v0.2 evaluation subsystem.

The initial Code benchmark must cover at least:

1. approved-spec fidelity and immutable spec binding;
2. complete acceptance mapping in plan output;
3. valid workflow ordering/no stage skipping;
4. implementation evidence rather than prose-only completion;
5. build/test failure status honesty;
6. verify/review evidence completeness;
7. safe command/workspace boundary handling;
8. resume/idempotency behavior;
9. secret/hidden-reasoning non-disclosure;
10. generated/validated/merged/deployed status honesty.

Development contracts may guide DSPy improvement. Promotion expected contracts/thresholds remain protected from optimizer input.

### 4.14 Recorded baseline and regressions

Create provider-credential-free recorded fixtures sufficient to prove the Code evaluation mechanism.

At minimum include:

- known-good Code baseline;
- equivalent/non-regressing challenger;
- stage-skipping regression;
- false build/test success regression;
- spec-drift regression;
- unsafe execution-boundary regression.

The protected promotion gate must reject each regression for machine-readable reasons even if aggregate score elsewhere is high.

### 4.15 CI and mandatory DSPy development gate

Extend CI so Code 2.0 architecture is validated without commercial model credentials or a live arbitrary-code executor.

The gate must:

1. validate `P2-V0.4.0` before Code implementation authorization;
2. execute mandatory DSPy SpecCritic + SpecCompiler for v0.4.0;
3. verify the compiled plan against the exact protected v0.4 acceptance map;
4. run engineering-run/state-machine/persistence/idempotency tests;
5. run planner/reviewer protected-validation tests;
6. run execution-policy/evidence tests using deterministic executor fixtures;
7. validate Code development and promotion suites;
8. prove the equivalent challenger passes;
9. prove stage/status/spec-drift/unsafe-execution regressions are rejected;
10. run inherited v0.1/v0.2/v0.3 backend/evaluation/client/Skia gates;
11. retain Code evaluation and DSPy development evidence artifacts.

A provider-backed Code optimizer and a live sandbox executor are not prerequisites for validating the v0.4.0 kernel architecture.

## 5. Non-goals

- Autonomous unbounded closed-loop code repair.
- Automatic merging to GitHub or any other source-control provider.
- Production deployment or deployment verification.
- Allowing model/client input to execute unrestricted shell commands.
- Remote infrastructure provisioning.
- Production authentication/authorization.
- Replacing SQLAlchemy schema bootstrap with the final migration framework in this release.
- Semantic/vector repository retrieval.
- Full IDE/editor/terminal UX.
- Multi-repository distributed workspace orchestration.
- Provider-backed MIPROv2 optimization as a prerequisite for validating the execution kernel.
- Model-as-judge as sole completion/promotion authority.
- Exposing chain-of-thought, DSPy rationale, executor secrets, environment secrets, or unrestricted process transcripts.

## 6. Architecture requirements

Recommended durable additions:

```text
services/api/parallax_api/code/
  ├─ models.py / domain.py
  ├─ state_machine.py
  ├─ planner.py
  ├─ workspace.py
  ├─ executor.py
  ├─ evidence.py
  ├─ reviewer.py
  └─ coordinator.py

services/api/parallax_api/repositories/
  └─ engineering_runs.py

services/api/parallax_api/routes/
  └─ engineering_runs.py

benchmarks/parallax-engineering/
  ├─ code-development-v0.1.json
  ├─ code-promotion-v0.1.json
  └─ fixtures/code-*.json
```

Exact filenames may differ if the same dependency direction is preserved.

Dependency rules:

- workflow state/transition policy is deterministic and independent of DSPy;
- persistence repositories do not contain model logic;
- planner/reviewer depend on typed DSPy/model interfaces but not promotion authority;
- executor is an interface behind protected execution policy;
- protected evidence verification does not trust model summaries as execution truth;
- API routes call services/coordinators rather than embedding shell/model logic;
- client displays durable server state and does not own stage transitions;
- Code development/promotion suites remain under the protected evaluation spine.

## 7. Code quality contract

Code 2.0 quality is judged from observable specification/evidence behavior.

Protected priority order:

1. approved-spec fidelity;
2. safe workflow ordering and immutable run/spec identity;
3. concrete implementation/change evidence;
4. truthful build/test/verify/review evidence;
5. safe workspace/tool boundary behavior;
6. resumability/idempotency and failure preservation;
7. security/secret/hidden-reasoning non-disclosure;
8. concise useful user-facing status.

DSPy optimization may improve planning/review prompts, demonstrations, context selection, bounded program strategies, and routing heuristics. It may not change the protected workflow transition policy, acceptance criteria, command safety policy, promotion suite, protected evaluator implementation, release-state definitions, or evidence requirements in the same optimization loop.

## 8. Security and privacy

- Client/model input cannot execute unrestricted shell strings directly through the API.
- Workspace paths are normalized and constrained beneath an approved root/reference.
- Destructive, privileged, deployment, and undeclared network execution are denied by default in v0.4.0.
- Provider/executor/repository credentials remain server-side and are never model output fields or public trace fields.
- Execution evidence is bounded and sanitized; stable digests identify raw outputs/artifacts without requiring unrestricted transcript exposure.
- Environment access is allowlisted/referenced, not inherited wholesale by model-proposed commands.
- Hidden chain-of-thought, scratchpads, DSPy rationale, and executor internals are not persisted as release evidence.
- Run/conversation/spec IDs are validated before orchestration actions.
- Stale revision/idempotency conflicts fail closed rather than overwriting durable state.
- Promotion policy remains isolated from planner/reviewer/optimizer code.

## 9. Observability

Every material Code state claim must be explainable from durable observable evidence.

Run/step traces include only what is necessary to explain execution:

- run/conversation/spec identity;
- workflow stage/state/revision;
- attempt identity/number;
- program/model/tool identity;
- execution outcome and timing;
- evidence/artifact digests;
- protected validation result;
- sanitized failure code;
- final transition.

Do not persist hidden reasoning or unrestricted environment/process content for observability.

A UI label such as `built`, `tested`, `verified`, `reviewed`, or `complete` must correspond to the durable protected stage evidence rather than model prose.

## 10. Failure handling

- Invalid/unapproved/mismatched spec: stop in SPECIFY and do not create successful PLAN evidence.
- Planner provider/validation failure: escalate Luna → Terra → Sol; preserve failed attempt evidence.
- Planner cannot map all protected acceptance IDs: PLAN does not pass.
- Workspace path escapes root: reject execution request before invoking executor.
- Duplicate operation key: return/reuse the already-recorded operation result; do not double-advance.
- Stale revision: return typed conflict and require refresh/resume from current durable state.
- Implementation lacks change artifact evidence: IMPLEMENT does not pass.
- BUILD command non-zero/timeout: BUILD fails and TEST is not advanced automatically.
- TEST command non-zero/timeout: TEST fails and VERIFY is not advanced automatically.
- VERIFY missing acceptance evidence: VERIFY fails.
- REVIEW recommends pass but protected prerequisites fail: REVIEW remains failed/needs work.
- Material objective/spec change: stop in `SPEC_AMENDMENT`; do not mutate the bound run spec.
- User cancellation: transition to `CANCELLED`; no further execution.
- Service/process interruption: reload durable run/attempt state and resume only from a protected allowed state.
- Skia unavailable: use inherited reduced-graphics UI while preserving Code semantics.

## 11. Acceptance criteria

### AC-01 Spec-first Code authorization
`P2-V0.4.0` is committed as the first Code-specific branch change, passes the protected spec-only gate, and receives mandatory DSPy SpecCritic + SpecCompiler evidence before substantive Code 2.0 implementation is treated as authorized.

### AC-02 Durable immutable engineering run
Automated tests prove an engineering run persists across service/session instances, is linked to one conversation and one immutable approved spec ID, exposes revision/state timestamps, and cannot silently rebind to another spec.

### AC-03 Protected workflow ordering
Automated tests prove only allowed stage transitions occur; stage skipping is rejected; failed BUILD/TEST/VERIFY/REVIEW cannot advance as success; COMPLETE requires protected passing evidence for every predecessor stage.

### AC-04 Append-only attempts and idempotency
Retries create new ordered attempts without overwriting prior evidence; duplicate operation keys do not duplicate side effects or stage advancement; stale revision writes are rejected.

### AC-05 Typed DSPy planner with protected acceptance mapping
The Code planner executes behind a typed program interface. Protected validation derives the approved acceptance-ID set independently and rejects PLAN completion until all acceptance IDs are mapped by observable planning output.

### AC-06 Workspace/repository boundary safety
Tests prove workspace paths cannot escape the approved root/reference, repository/provider credentials are not exposed to model/public trace data, and Code workflow logic remains provider-neutral.

### AC-07 Implementation change evidence
IMPLEMENT cannot pass on prose alone. Tests prove passing implementation evidence contains bounded in-workspace changed-file/artifact references and stable pre/post/change digests tied to the run revision.

### AC-08 Protected execution broker
BUILD/TEST/VERIFY execution goes through a typed executor plus protected command/workspace policy. Tests prove unsafe/out-of-root/destructive/privileged/deployment-capable execution is rejected before invocation and deterministic safe fixture execution is observable.

### AC-09 Truthful build/test/verify evidence
Tests prove non-zero exits/timeouts/missing evidence remain failures, stdout/stderr/artifact evidence is bounded/sanitized/digested, and model summaries cannot convert failed or absent execution evidence into success.

### AC-10 Protected engineering review
A typed reviewer can recommend PASS/NEEDS_WORK/SPEC_AMENDMENT, but protected review owns the transition. COMPLETE is impossible unless prior gates and acceptance evidence pass and the reviewed evidence belongs to the same run/workspace revision.

### AC-11 Pause/resume/failure durability
Tests prove PAUSED/FAILED/SPEC_AMENDMENT/CANCELLED semantics are durable, conversation/run history survives process/service reload, and resume starts from a protected allowed stage without discarding prior attempts.

### AC-12 Code API contract
API tests prove a user can create/get/advance/resume/cancel a Code run through service boundaries, retrieve safe step/evidence metadata, and cannot request a run spec that conflicts with the durable conversation without an authorized amendment/new run.

### AC-13 Conversation-first Code client
The client displays the bound spec, current/completed stage, evidence/failure status, and allowed resume/retry state without becoming a raw terminal/IDE. Reduced-motion and reduced-graphics paths preserve the same semantic Code state.

### AC-14 Dedicated Code protected evaluation
Separate Code development and held-out promotion suites cover spec fidelity, acceptance mapping, workflow ordering, implementation evidence, build/test honesty, verification/review completeness, execution safety, resumability/idempotency, security, and release-status honesty.

### AC-15 Recorded regression rejection
Offline CI proves the equivalent Code challenger passes and deliberate stage-skipping, false-success, spec-drift, and unsafe-execution regressions are rejected for protected machine-readable reasons.

### AC-16 Security and no hidden reasoning
Tests/evidence prove secrets, environment credentials, chain-of-thought, scratchpads, DSPy rationale traces, and unrestricted raw executor transcripts do not enter public Code traces or promotion artifacts.

### AC-17 Inherited Reason/evaluation/visual regression safety
The complete inherited v0.1/v0.2/v0.3 backend, Reason, protected-evaluation, TypeScript, Expo export, browser/Skia, live optical inscription, amendment, and no-Skia degradation gates remain green after Code 2.0 changes.

### AC-18 Status honesty
No Code API/UI/evidence may label work merged, deployed, deployment-verified, or production-ready without corresponding explicit external evidence. Code COMPLETE means only that the protected Code 2.0 run gates passed.

## 12. Release gate

v0.4.0 may be called **VALIDATED CODE 2.0 EXECUTION KERNEL** only when:

- AC-01 through AC-18 pass on one exact implementation head;
- the v0.4 mandatory DSPy development artifact proves SpecCritic + SpecCompiler execution and protected acceptance-map validation;
- Code development/promotion evidence artifacts are retained;
- every deliberate Code regression is rejected by protected policy;
- full inherited Reason/evaluation/client/Skia regression validation passes;
- authoritative records are updated to distinguish generated, validated, deployed, and deployment-verified states.

Validation of v0.4.0 does **not** mean autonomous repair, live arbitrary-code execution, source-control merge, deployment, provider-backed optimization, or deployment verification occurred.
