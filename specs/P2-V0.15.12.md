# Parallax 2.0 — Wave 2 Per-Target Production Provider Credentials

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.15.12
Workstream: WS-APP-PRODUCTION-TARGET-CREDENTIALS / GitHub issue #88
Base: integration/wave2-app-builder@66ec68652c8a80d0a0ca449d89d8e1c505deb8ca

Method: close the multi-Project least-privilege gap discovered during final production preflight without broadening provider authority

## 1. Objective

Make the P2-V0.15.11 production provider composition genuinely multi-Project while preserving exact provider-side least privilege. The existing server-owned repository→Vercel Preview target registry remains the only runtime selection boundary, but each registered repository target must carry its own GitHub Connect connector reference and its own dedicated Vercel credential environment-variable reference. Secrets themselves remain outside source and outside the registry.

The runtime must first resolve the authenticated canonical Project repository to exactly one registered target, then resolve only that target's credential references. A credential for one repository/Preview target must never be treated as valid for another registered target.

## 2. Scope

- Extend the existing bounded server-owned Preview target registry with a per-target GitHub Connect connector identifier and a per-target Vercel credential environment-variable name.
- Store only secret references in the registry; never store bearer material in JSON, source, database rows, evidence, logs, API responses, or model-visible data.
- Require Vercel credential environment-variable names to use a bounded Parallax-owned prefix so registry configuration cannot become a generic environment-secret reader.
- Resolve the exact registered target from canonical `Project.repository_ref` before reading connector or Vercel credential configuration.
- Instantiate the Vercel credential provider with exactly one allowed `vercel_project_ref`, never all registered targets.
- Preserve P2-V0.15.11 GitHub Connect app-token exchange and GitHub-side `/installation/repositories` verification that the minted installation token can access exactly the canonical repository.
- Add deterministic tests for two distinct registered repository targets, per-target connector/token references, cross-target credential denial, malformed secret references, and the existing single-target path.
- Preserve all prior source-lineage, delivery replay, provider action, evaluation, and operator-review contracts.

## 3. Security

- Canonical `Project.id`, authenticated owner scope, and persisted `Project.repository_ref` remain authoritative.
- Target registry entries are server-owned deployment configuration. Callers/models cannot select connector IDs, secret variable names, Vercel project IDs, team IDs, GitHub repository IDs, production branches, URLs, headers, or provider payloads.
- GitHub Connect connector identifiers are bounded and tied to the selected repository target. The resulting app credential is accepted only after GitHub confirms exact single-repository installation scope.
- Vercel credential environment-variable names must match `PARALLAX_VERCEL_TOKEN_[A-Z0-9_]+` within a bounded length. No arbitrary environment variable name is accepted.
- The selected Vercel bearer material is wrapped as a `ScopedBearerCredential` whose resource is exactly the selected target's `vercel_project_ref`; the provider is configured with a singleton allowed-target set.
- Missing, duplicate, malformed, stale, or mismatched target/credential configuration fails closed before provider mutation.
- No provider secret is persisted or exposed. Existing redaction and bounded error normalization remain authoritative.

## 4. Target registry contract

Each registered production delivery target must include:

- `vercel_project_ref`
- `project_id`
- `project_name`
- optional `team_id`
- canonical `repository_ref`
- `github_repo_id`
- `production_branch`
- `github_connector`
- `vercel_token_env`

The registry may contain multiple targets, but repository identity and Vercel target identity must remain unique. `github_connector` may differ between repositories. `vercel_token_env` may differ between targets and contains only an environment-variable name, never the secret value.

The registry must expose an exact registered-target lookup for one canonical `ProviderProjectBinding`. `resolve()` continues to return the accepted `VercelPreviewTarget`; production composition may additionally retrieve the selected target's credential references through an internal server-only method.

## 5. Production composition

For one authenticated Project-bound request:

1. load the bounded server-owned registry;
2. resolve the exact canonical Project repository to one registered target;
3. read only that target's GitHub connector identifier;
4. read only that target's dedicated Vercel credential environment variable;
5. construct the P2-V0.15.11 GitHub Connect credential provider and exact repository-scope verification path;
6. construct `EnvironmentVercelCredentialProvider` with a singleton allowed-target set containing only the selected `vercel_project_ref`;
7. construct the unchanged #70 typed provider clients and #79 source-delivery composition;
8. preserve existing durable action/evidence replay semantics.

A registry containing a second Project must not cause the first Project's credential object to authorize or expose that second target.

## 6. Non-goals

- changing canonical Project identity or repository binding;
- adding a generic secret manager, environment reader, provider registry, generic HTTP transport, shell, Git CLI, merge, production deployment, alias/domain, or environment mutation authority;
- changing #46 evaluation scoring or #79/#80 evidence semantics;
- provisioning production Blob stores, Connect installations, access tokens, or environment values inside this workstream;
- supporting user/model-selected provider targets or credentials;
- weakening P2-V0.15.11's exact GitHub installation repository-scope verification.

## 7. Acceptance criteria

### AC-01 Per-target credential references
The server-owned target registry accepts bounded `github_connector` and `vercel_token_env` fields for each registered repository/Preview target, and exposes the exact selected target only after canonical Project/repository binding succeeds.

### AC-02 No generic secret lookup
`vercel_token_env` accepts only bounded names under the protected `PARALLAX_VERCEL_TOKEN_` prefix. Arbitrary environment names, secret values embedded in the registry, malformed connector identifiers, and missing target credentials fail closed before provider construction.

### AC-03 Exact GitHub connector selection
For two registered repositories with distinct GitHub connectors, production composition selects only the connector associated with the canonical Project repository. P2-V0.15.11's GitHub-side exact single-repository scope verification remains unchanged and required before credential caching/use.

### AC-04 Exact Vercel target credential selection
For two registered Vercel targets with distinct credential environment variables, production composition reads only the selected target's secret and constructs `EnvironmentVercelCredentialProvider` with exactly one allowed `vercel_project_ref`. A target-A credential cannot satisfy target B.

### AC-05 Existing single-target reference path preserved
The protected Parallax reference target `github:Ryan9876/parallax` → `vercel:preview:parallax` continues to construct the same accepted #70/#79 provider and delivery path when supplied with its per-target credential references.

### AC-06 Failure evidence remains bounded and secret-safe
Missing or invalid per-target configuration returns bounded normalized configuration/provider failures without secret values, raw environment contents, raw provider payloads, or credential material in evidence, logs, API responses, or representations.

### AC-07 Prior authority/evidence contracts unchanged
The accepted GitHub source/read/branch/commit/PR action set, Vercel Preview create/read ceiling, Engineering Attempt replay persistence, durable lineage binding, #46 evaluation scoring, and operator REVIEW/production authority boundaries remain unchanged.

### AC-08 Exact-head validation
P2-V0.15.12 has authentic committed DSPy critic/compiler evidence. The exact workstream head passes Workstream Spec Validation, Parallax P2 CI, Bounded Autonomy Pilot, and Vercel Preview checks before integration. The cumulative integration head must rerun the same release gates after serialization.

## 8. Release gate

Before this workstream is integrated:

- AC-01 through AC-08 are implemented and deterministically tested;
- no secret value is present in the target registry or committed artifacts;
- multi-target tests prove connectors and Vercel credentials cannot cross target boundaries;
- the existing single-target protected reference path remains green;
- authentic DSPy plan evidence is committed;
- exact-head Workstream Spec Validation, P2 CI, Bounded Autonomy, and Vercel Preview checks are green.

Production migration/merge/deployment remains separately blocked until the actual private Blob store, Vercel Connect GitHub connector(s), project-scoped Vercel access token(s), target registry, and OIDC configuration are provisioned and verified.
