# Parallax 2.0 — Wave 2 Production Release Composition

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.15.11
Workstream: REL-WAVE2-PRODUCTION-COMPOSITION / GitHub issue #84
Base: integration/wave2-app-builder@d4ca9c95527198c7884f87056afab8bbcc85ab39
Depends on: accepted P2-V0.15.1 through P2-V0.15.10 contracts
Method: close only production dependency-graph/configuration/security gaps discovered during promotion preflight without broadening runtime authority

## 1. Objective

Make the already-validated Wave 2 protected app-builder path actually reachable through the production FastAPI autonomous endpoint and preserve the existing production database security posture. Production composition must construct the accepted #79 repository-bootstrap and verified-source delivery stack from server-owned configuration, use only the accepted #45/#62/#68/#70 provider and lineage contracts, and fail closed when required delivery configuration or credentials are unavailable.

This release correction must not introduce a new identity system, generic provider transport, merge authority, production-promotion authority, or a weaker evaluation path. Preview remains the autonomous provider ceiling and operator authority remains required for merge and production deployment.

## 2. Scope

- Add a narrow production source-delivery factory that composes existing Project binding, tool registry, concrete GitHub/Vercel Preview clients, provider credential adapters, preview-target registry, durable lineage allocator, and Engineering Attempt delivery store.
- Inject the resulting `SourceDeliveryComposition` into the real `/v1/engineering-runs/{run_id}/autonomous` dependency path whenever Wave 2 durable runtime composition is active.
- Add server-only configuration parsing for exact Project-to-Vercel Preview target bindings and provider credential acquisition; caller/model request bodies cannot supply these values.
- Support short-lived app-scoped GitHub credentials from Vercel Connect/OIDC when configured. Support Vercel REST Preview credentials only from explicit server-side scoped credential configuration accepted by the existing client contract.
- Fail closed with bounded configuration errors when an active Project lacks an exact registered Preview target or required provider credential configuration.
- Harden migration `20260823_0008_durable_source_lineage.sql` by enabling RLS and revoking all `anon`/`authenticated` table privileges on both internal lineage tables.
- Add route-level and composition tests proving the actual FastAPI dependency graph carries bootstrap and verified delivery, plus negative tests for missing/mismatched configuration.
- Preserve all P2-V0.15.1–P2-V0.15.10 behavior and exact #46 scoring/evidence semantics.

## 3. Security

- Canonical `Project.id`, persisted Engineering Run identity, and owner-scoped Project repository binding remain the only Project/repository authority.
- Project-to-Vercel target mappings are server-owned exact registrations. Caller/model data cannot select Vercel project IDs, team IDs, repository IDs, production branches, credentials, URLs, headers, or generic provider payloads.
- GitHub runtime credentials must be short-lived/scoped when obtained via Vercel Connect and are never persisted in Engineering Attempts, lineage metadata, evaluation evidence, logs, or API responses.
- Vercel REST credentials are server-only and must satisfy the existing `ScopedBearerCredential` resource binding before any provider call. No broad credential is exposed to the model/client.
- Missing credential/target configuration fails closed before provider mutation. The runtime must not silently omit bootstrap/delivery and still report the complete Wave 2 path.
- Private source contents remain in private durable object storage; local materialization remains disposable only.
- `source_lineage_manifests` and `source_lineage_heads` are internal runtime tables: RLS is enabled and all table privileges are revoked from Supabase `anon` and `authenticated` roles.
- Existing Preview-only provider ceiling remains unchanged. No merge, production deployment, alias/domain mutation, environment/secret mutation, arbitrary HTTP, shell, or generic Git authority is added.

## 4. Runtime composition

Production composition must be deterministic from persisted Project/run state plus server configuration.

For a Project-bound autonomous run, the production route must:

1. construct the production durable lineage allocator;
2. construct a `SourceDeliveryComposition` bound to the authenticated owner scope and same database Session/repository boundary;
3. use `OwnerScopedProjectBindingResolver` for canonical repository identity;
4. use a project-scoped `ToolCapabilityRegistry` whose actions are exactly the already accepted GitHub source/read/write/PR and Vercel Preview create/read actions required by #79;
5. use concrete #70 clients beneath those typed actions;
6. use `EngineeringAttemptDeliveryRecordStore` for durable delivery replay evidence;
7. inject the source-delivery object into `EngineeringRuntimeComposition`;
8. allow repository bootstrap before IMPLEMENT and verified-source delivery only after exact-lineage VERIFY reaches operator REVIEW.

If the durable allocator is active but the production source-delivery stack cannot be constructed for the Project, the route must return a bounded failure and must not fall back to `EngineeringRuntimeComposition(..., source_delivery=None)` or the legacy fresh-source path.

## 5. Provider configuration

Provider configuration is an operator/deployment concern, not user input.

- GitHub Connect configuration consists of a server-owned connector identifier plus deployment OIDC. The adapter exchanges OIDC for an app-scoped GitHub provider token and emits an expiring `ScopedBearerCredential` bound to the exact `github:owner/repository` resource.
- Vercel Preview REST configuration consists of server-owned scoped bearer material plus exact registered Preview target data. The token is bound to the target's `vercel_project_ref` through `ScopedBearerCredential` before use.
- Preview targets are loaded from bounded server configuration and converted to exact `VercelApiTarget` + `VercelPreviewTarget` records. Duplicate Project registrations, mismatched repository identities, unsupported production branches, malformed IDs, or unknown Projects fail closed.
- Configuration parsers must never echo secret values in exceptions or representations.

## 6. Database hardening

Before migration 0008 is production-applied, the committed migration must preserve the production Supabase policy used by existing internal tables:

- `ALTER TABLE source_lineage_manifests ENABLE ROW LEVEL SECURITY;`
- `ALTER TABLE source_lineage_heads ENABLE ROW LEVEL SECURITY;`
- `REVOKE ALL ON TABLE source_lineage_manifests, source_lineage_heads FROM anon, authenticated;`

No permissive RLS policy is added. Server database access continues through the existing protected database role/path.

## 7. Non-goals

- redesigning Project persistence or adding a project dashboard;
- replacing #79 source-delivery orchestration or #70 provider clients;
- changing #46 evaluator scoring, thresholds, critical semantics, or evidence schema;
- creating a second tool-authority or provider-audit system;
- granting arbitrary shell, network, HTTP, Git, repository, Vercel, merge, production-deploy, alias/domain, environment, or secret-mutation capability;
- persisting provider bearer credentials or raw provider responses;
- deploying without exact-head gates and verified production prerequisites;
- treating Vercel Preview success as production deployment verification.

## 8. Acceptance criteria

### AC-01 Live autonomous route injects source delivery
The actual FastAPI autonomous endpoint constructs `EngineeringRuntimeComposition` with a non-null accepted `SourceDeliveryComposition` whenever the Wave 2 durable allocator is active. A route-level test proves bootstrap occurs before autonomous execution and verified delivery occurs only when the run reaches `REVIEW_REQUIRED`.

### AC-02 Missing release configuration fails closed
If a Project lacks required server-owned provider credential configuration or an exact registered Vercel Preview target, production composition fails with a bounded configuration error before provider mutation. It cannot silently run with `source_delivery=None`, fabricate delivery evidence, or fall back to unrelated fresh repository source.

### AC-03 Canonical Project/repository/target binding
Production delivery resolves repository identity from the authenticated owner-scoped canonical Project and accepts only an exact server-registered Project→Vercel target whose repository identity matches. Caller/model project target fields, arbitrary URLs, workspace paths, and provider-selected identities cannot override the binding.

### AC-04 Scoped provider credential adapters
GitHub credentials are obtained through the configured short-lived app-scoped Vercel Connect/OIDC path and returned only as exact-resource `ScopedBearerCredential` values. Vercel REST credentials come only from explicit server configuration and are exact-resource scoped. Secrets are not logged, persisted, serialized, or exposed to model/client/evaluation surfaces.

### AC-05 Accepted authority ceiling preserved
The production registry exposes only the already accepted GitHub repository/source/branch/commit/PR operations and Vercel Preview create/read operations needed by #79. Preview remains the autonomous provider ceiling; no merge, production promotion/deployment, alias/domain, arbitrary HTTP/Git/shell/network, environment, or secret mutation authority is added.

### AC-06 Durable delivery replay remains authoritative
The live production composition uses `EngineeringAttemptDeliveryRecordStore` and existing #79 replay semantics. Process/request recreation resolves the exact accepted Project/run/lineage delivery and retries without duplicate commit, PR, or Preview mutation; no competing provider-audit persistence is introduced.

### AC-07 Lineage tables preserve Supabase security posture
Migration `20260823_0008_durable_source_lineage.sql` enables RLS on `source_lineage_manifests` and `source_lineage_heads` and revokes all table privileges from `anon` and `authenticated`. Production verification proves both tables have RLS enabled and those roles have no read/write privileges.

### AC-08 Exact-head release validation and deployment boundary
P2-V0.15.11 has authentic committed DSPy plan evidence and the corrected cumulative head passes Workstream Spec Validation, Parallax P2 CI, Bounded Autonomy Pilot, and Vercel Preview checks. Production migrations/merge/deploy occur only after server credential/target configuration is proven available; post-deploy health, readiness, auth, runtime/provider behavior, logs, and rollback evidence are then verified before recording Wave 2 as deployment-verified.

## 9. Release gate

Before production promotion resumes:

- AC-01 through AC-08 are implemented and covered by deterministic tests;
- the actual route dependency graph is exercised, not only the reference harness;
- migration 0008 security posture is validated against the existing production pattern;
- P2-V0.15.11 and authentic compiled DSPy plan pass protected validation;
- full API/client/browser regression and bounded-autonomy suites are green on one exact head;
- Vercel Preview checks for web/API are green on that exact head;
- production provider credential and target configuration is verified without exposing secret material;
- only then may migrations be applied, PR #67 advanced, main merged, and production deployments verified.
