# Parallax 2.0 v0.5.0 — Private Production Release Specification

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.5.0
Depends on: P2-V0.4.0
Method: Spec-first + mandatory DSPy-governed development + protected release verification

## 1. Objective

Release the validated Parallax 2.0 Code candidate as an isolated, private production service without changing the existing Parallax 1.x production project. Replace implicit schema bootstrap with a versioned migration, protect durable application data and model-backed routes with application-level authentication, deploy dedicated web and API projects, and collect end-to-end production evidence before recording the release as deployment-verified.

## 2. User outcome

An authorized operator can open the P2 web application, supply the private production access credential, create and resume durable conversations, use Reason and Code workflows, and recover the same state across requests. An unauthenticated caller cannot read or mutate conversations or engineering runs. Operational probes remain suitable for hosting health checks without exposing application data.

## 3. Fixed decisions

- Production is a private single-operator release. A user/account system and public self-service registration are non-goals.
- Application access uses a high-entropy bearer credential supplied by the operator at runtime. The credential is never embedded in the web bundle, persisted by the server, logged, returned by an API response, or written to repository files.
- The browser may retain the credential only in session-scoped storage; closing the browser session clears it.
- `/health` and `/ready` remain unauthenticated operational probes. All conversation, Reason, and Code routes require authentication.
- Authentication failures return the same concise `401` contract without revealing whether a candidate credential was close or which internal check failed.
- Schema evolution uses an explicit ordered SQL migration committed under `services/api/migrations`. Production startup does not call `Base.metadata.create_all()`.
- The production migration is applied to the dedicated P2 Supabase project before API traffic is enabled.
- P2 uses dedicated Vercel projects for `apps/client` and `services/api`. The existing `parallax` project is never linked, modified, promoted, or used for verification.
- Production secrets belong only to the API project. The web project receives only the API base URL.
- Production is not deployment-verified until the protected end-to-end checks in this specification pass against the live URLs.

## 4. Scope

### 4.1 Protected API access

Add a server-owned authentication dependency that validates `Authorization: Bearer <credential>` using constant-time comparison against `PARALLAX_ACCESS_TOKEN`. Missing configuration must fail closed outside test/development. Protected routers apply the dependency at the router boundary so a newly added endpoint cannot accidentally omit the check.

The application must not log request authorization headers or expose configured credentials through traces, errors, readiness output, or OpenAPI examples.

### 4.2 Private web entry

Add a minimal, accessible access screen before the conversation shell. The operator enters the credential manually. On successful authenticated API access, the existing conversation-first interface loads. On `401`, the client returns to the access screen with concise recovery copy.

The credential is held in memory and session storage only. It is attached to protected API and SSE requests through the bearer header and is never placed in a URL or rendered into diagnostic UI.

### 4.3 Versioned database migration

Add an explicit idempotent initial production migration that creates the durable conversation, message, engineering-run, and engineering-attempt schema represented by the validated SQLAlchemy models, including primary keys, foreign keys, uniqueness constraints, and query indexes.

Application startup in production verifies connectivity but does not mutate schema. Development/test may retain an explicit opt-in bootstrap path for isolated local databases.

### 4.4 Production configuration and topology

Provide deployment configuration for the FastAPI service and retain the validated static Expo web export. Required API configuration includes the transaction-pooler `DATABASE_URL`, `PARALLAX_ENV=production`, `PARALLAX_ACTIVE_SPEC_ID=P2-V0.5.0`, the private access credential, model configuration/credentials, strict CORS origin, and disabled scope override.

The web project points to the dedicated API production URL. No API secret is exposed through `EXPO_PUBLIC_*` variables.

### 4.5 Verification, rollback, and evidence

Before promotion, validate specification structure, run the mandatory DSPy SpecCritic + SpecCompiler gate, compile the API, run the complete backend suite, run the client typecheck/state tests/export, and rerun inherited Engineering, Reason, and Code protected evaluation gates.

Production verification must prove:

- web loads at mobile, tablet, and desktop sizes;
- reduced-graphics behavior remains usable;
- API `/health` and database-backed `/ready` succeed;
- unauthenticated protected requests return `401` without sensitive detail;
- authenticated conversation creation, separate-request retrieval, and stored `P2-V0.5.0` identity succeed;
- authenticated Reason SSE emits live state/chunk/completion behavior;
- authenticated Code run creation and retrieval succeed;
- the existing P1 Vercel project was not changed;
- production logs contain no credential, provider secret, or database URL.

Rollback retains the last known-good Vercel deployments and uses provider promotion/rollback rather than changing P1. Database rollback is forward-fix only after the initial additive migration; no destructive down migration is executed against production data.

## 5. Security

The bearer credential is a private operator secret. Production requires at least 32 characters, compares it in constant time, accepts it only in the Authorization header over TLS, and fails closed if configuration is missing. It is excluded from repository content, web bundles, URLs, response bodies, traces, and logs. CORS is restricted to the dedicated web origin. Protected router-level dependencies and route-family tests prevent accidental unauthenticated additions.

## 6. Acceptance criteria

### AC-01 Protected route denial

Every application-data and AI/Code endpoint rejects a missing or invalid bearer credential with sanitized `401` output.

### AC-02 Safe operational probes

`/health` and `/ready` remain usable without credentials and reveal no secrets or application records.

### AC-03 Fail-closed production configuration

Production fails closed when `PARALLAX_ACCESS_TOKEN` is absent or unacceptably short.

### AC-04 No credential in the web artifact

The web bundle contains no production access credential and the client never sends it in a URL.

### AC-05 Authorized private client

An authorized operator can unlock the client, use the existing conversation experience, and recover cleanly from an expired or invalid credential.

### AC-06 Explicit durable migration

A committed migration creates the complete validated durable schema and required constraints and indexes on an empty PostgreSQL database.

### AC-07 No production startup DDL

Production startup performs no implicit DDL.

### AC-08 Isolated P2 infrastructure

Dedicated P2 web, API, and Supabase targets are used; the existing P1 `parallax` project remains unchanged.

### AC-09 Exact-head release validation

Exact-head backend, client, DSPy, and protected evaluation gates pass before production promotion.

### AC-10 Live production verification

Live production verification covers health, readiness, authentication denial, authenticated persistence, Reason SSE, Code lifecycle access, responsive rendering, and reduced-graphics behavior.

### AC-11 Evidence-based release status

Release evidence distinguishes generated, validated, deployed, and deployment-verified states and records live deployment identities without recording secrets.

### AC-12 Secret-safe observability

Production logs and public traces contain no bearer credential, provider secret, database URL, hidden reasoning, or unrestricted execution transcript.

## 7. Non-goals

- Public signup, multi-user tenancy, password recovery, social login, billing, or organization administration.
- Changing the Reason/Code protected policies, model ordering, benchmark thresholds, visual system, or product terminology.
- Deploying, rebinding, or modifying Parallax 1.x.
- Enabling an unrestricted live Code executor or deployment-capable command registry.
- Claiming provider-backed DSPy optimization quality that has not been measured.

## 8. Risks and mitigations

- Shared-credential exposure: require high entropy, keep it out of the bundle and URLs, use TLS, constant-time comparison, session-only client retention, and secret redaction.
- Accidental public data access: enforce authentication at protected router boundaries and test every route family.
- Schema drift: apply the committed migration before traffic and remove production `create_all` behavior.
- Cross-project deployment error: verify project IDs/names before promotion and record that P1 was untouched.
- False deployment claims: require live behavioral evidence, not only provider `READY` state.
- Provider outage or model failure: preserve the existing durable/recoverable error contract and inspect production logs after verification.

## 9. Release gate

This specification authorizes implementation and private-production deployment only after its protected development and validation gates pass. Deployment status may be recorded only from hosting/database evidence; deployment-verified status requires all live acceptance checks. Any failed critical security, persistence, or P1-isolation check blocks promotion.
