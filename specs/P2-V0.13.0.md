# Parallax 2.0 v0.13.0 — Bounded Autonomy Pilot

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.13.0
Depends on: P2-V0.12.0
Method: bounded remote execution + protected autonomous progression + preview-first verification

## 1. Objective

Add the first live autonomous engineering capability to Parallax without crossing the existing human-control and release-authority boundaries. A Code run bound to an operator-approved Work Specification must be able to execute a bounded engineering validation loop in an isolated remote sandbox, collect protected evidence, advance itself through authorized stages, stop safely on failure or an unsupported stage, and clearly report why it stopped.

## 2. User outcome

The operator can approve a Work Specification, activate the bound Code run, and start an autonomous execution cycle without manually advancing each safe validation stage. Parallax performs the work it is currently authorized to perform, persists evidence for every transition, and returns control whenever implementation authority, an approval boundary, or a failure prevents safe continuation.

This release intentionally proves trustworthy autonomy before granting repository-write, Git merge, or production-deployment authority.

## 3. Scope

- Introduce a bounded autonomy coordinator for approved-spec Engineering Runs.
- Introduce a live remote execution provider backed by Vercel Sandbox, with a provider interface that remains testable without external infrastructure.
- Execute commands only from a server-owned registry; callers and models may not submit shell command strings.
- Default live sandbox networking to deny-all.
- Use the immutable EngineeringRun Work Specification binding and server-owned acceptance map as the execution contract.
- Allow one operator action to advance through every currently safe autonomous stage.
- Persist command identity, exit status, timeout state, output digests/excerpts, and stop reason as protected observable evidence.
- Preserve pause, resume, cancel, revision, idempotency, and existing protected stage-order behavior.
- Add a compact conversation-native control to start the bounded autonomous cycle and show the resulting stop state.
- Preserve Reason, Work Specification, authentication, authorization, persistence, and current Editorial Optical interaction hierarchy.

## 4. Autonomy boundary

v0.13.0 authorizes autonomous execution only inside the bounded executor contract.

Parallax may autonomously:

- derive a deterministic PLAN from the approved Work Specification acceptance map when the run is at PLAN;
- run registered build/test/verification commands inside an isolated sandbox when the run is at BUILD, TEST, or VERIFY;
- retry only through the existing explicit FAILED → resume-stage mechanism when the operator requests resume;
- persist protected evidence and advance a stage when the corresponding protected validator passes;
- stop and report a durable reason whenever it reaches a stage for which this release does not have safe authority.

Parallax may not autonomously:

- approve or amend a Work Specification;
- invent or alter the server-owned acceptance map;
- modify the production API host filesystem;
- execute arbitrary shell strings or model-supplied commands;
- access arbitrary environment variables or secrets;
- enable sandbox network access by default;
- commit, push, merge, or rewrite Git history;
- promote or deploy to Vercel production;
- claim a release is deployed or deployment-verified.

IMPLEMENT and REVIEW remain explicit stop boundaries in this pilot unless independently valid implementation/review evidence already exists. This prevents the system from fabricating implementation work merely to complete the lifecycle.

## 5. Sandbox execution contract

The live provider must:

- execute outside the FastAPI host in an isolated Vercel Sandbox session;
- use the deployment-scoped Vercel identity/token available only to the server runtime;
- bind sandbox creation to the current Vercel project identity;
- use deny-all networking for the execution session;
- use a bounded timeout and non-persistent session;
- run only structured command + argument arrays selected by a server-owned registry;
- never invoke a shell interpreter to concatenate untrusted values;
- sanitize and bound observable stdout/stderr excerpts while retaining digests;
- stop or discard the sandbox after the cycle;
- return a sanitized unavailable state when sandbox credentials or project identity are absent.

The test provider may use deterministic recorded results but must pass through the same protected command policy.

## 6. Autonomous progression contract

A request to run autonomously is idempotent by operator-supplied operation key and current run revision.

For each cycle:

1. Re-read the durable EngineeringRun and its immutable approved Work Specification binding.
2. Refuse stale expected revisions.
3. If state is PLAN, produce a deterministic protected plan that exactly covers the server-owned acceptance IDs and advance to IMPLEMENT.
4. If state is IMPLEMENT, stop with `IMPLEMENTATION_REQUIRED`; do not fabricate code-artifact evidence.
5. If state is BUILD, TEST, or VERIFY, select the stage-specific registered command, execute it in the bounded provider, map successful execution evidence to the exact server-owned acceptance IDs, and advance only through the existing protected stage validator.
6. If state is REVIEW, stop with `REVIEW_REQUIRED` unless a later release explicitly authorizes independent review automation.
7. If state is PAUSED, FAILED, COMPLETE, CANCELLED, or SPEC_AMENDMENT, do not silently change state; return the corresponding stop reason.
8. Abort the cycle immediately when a command fails, times out, protected validation rejects evidence, or the run revision changes unexpectedly.

No autonomous cycle may skip IMPLEMENT or REVIEW by manufacturing passing evidence.

## 7. Registered pilot commands

The initial live registry is intentionally narrow and repository-specific:

- BUILD: Python compilation of the API package and Parallax scripts.
- TEST: the protected API code/execution test subset.
- VERIFY: the protected Code boundary and kernel test subset.

Commands are versioned server policy, not API inputs. The registry may be expanded only through a future approved specification.

## 8. Security and reliability

- Existing Google/Supabase identity and Parallax authorization remain authoritative for starting an autonomous run.
- No Vercel OIDC token, root bearer, provider credential, or environment value is returned to the client or persisted as run evidence.
- The sandbox session receives no application secrets.
- Network is deny-all by default.
- Output excerpts are bounded and secrets/hidden reasoning remain forbidden evidence.
- Stage transitions continue to use optimistic revision checks and idempotent operation records.
- A provider outage results in a durable failed stage or sanitized blocked response, never a fabricated success.
- Existing operator pause/cancel controls remain available.

## 9. Acceptance criteria

### AC-01 Isolated live executor
Production-capable code provides a Vercel Sandbox execution provider and never runs registered autonomous commands through an unrestricted subprocess on the FastAPI host.

### AC-02 Deny-by-default sandbox
The live provider creates non-persistent bounded sessions with deny-all network policy and passes no application secrets into the sandbox.

### AC-03 Server-owned command registry
BUILD, TEST, and VERIFY map to fixed structured command definitions owned by the server. API callers cannot provide executable command strings, environment names, shell metacharacters, or arbitrary working-directory escapes.

### AC-04 Protected autonomous progression
One autonomous-run request may advance PLAN deterministically and may execute/advance BUILD, TEST, and VERIFY through existing protected stage validators, while preserving exact acceptance coverage, revision checks, and idempotency.

### AC-05 Honest stop boundaries
At IMPLEMENT and REVIEW the pilot stops with an explicit reason rather than manufacturing implementation/review evidence. PAUSED, FAILED, COMPLETE, CANCELLED, and SPEC_AMENDMENT likewise stop without unauthorized state mutation.

### AC-06 Durable execution evidence
Successful or failed live/recorded commands expose only bounded observable evidence: tool identity, invocation/output digests, bounded excerpts, duration, exit code, timeout state, redaction state, and exact protected acceptance coverage where required.

### AC-07 Failure safety
Command failure, timeout, provider unavailability, stale revision, or protected-validation failure cannot be recorded as a passing stage and cannot cause the run to skip ahead.

### AC-08 Conversation-native operator control
The Code run surface provides an accessible `Run autonomously` action when the current state is eligible and reports the latest autonomy stop reason without turning the product into an IDE/dashboard. Reduced-graphics parity is preserved.

### AC-09 Release-authority boundary
No v0.13.0 runtime path performs Git commit/push/merge, autonomous Vercel promotion/production deployment, Work Specification self-approval, or unsupported release-state claims.

### AC-10 Regression and preview verification
Specification validation, API compilation/tests, client typecheck/state tests, web export, protected evaluation, existing browser acceptance, and a preview-hosted autonomy readiness/blocked-path verification pass before this release is described as validated. Production promotion remains a separate operator decision.

## 10. Non-goals

- General arbitrary shell access.
- Autonomous source-code editing.
- AI-generated patch application.
- Autonomous GitHub commit/push/merge.
- Autonomous production deployment.
- Autonomous Work Specification approval.
- Removing operator pause/cancel or release gates.
- Expanding the interface into an IDE or agent dashboard.

## 11. Risks and mitigations

- **Remote execution could become an escape hatch:** keep registry-only structured commands, deny-all networking, no secrets, bounded timeouts, and an isolated provider.
- **Autonomy could falsely imply implementation:** stop at IMPLEMENT until real implementation evidence exists; make the stop reason visible.
- **Evidence could drift from the approved objective:** derive acceptance coverage only from the immutable bound Work Specification.
- **Provider availability could make runs flaky:** separate provider readiness from stage success and persist sanitized failure state without claiming completion.
- **A single request could run too long:** bound the cycle length and individual command timeouts; stop after the current authorized sequence.
- **Future autonomy could accidentally inherit release authority:** keep Git and deployment operations outside the executor interface entirely.

## 12. Release gate

Implementation is authorized by this specification. The first delivery target is a validated GitHub feature branch and Vercel preview so the operator can test the bounded autonomy behavior before any production merge. `ARCHITECTURE.md` must be updated because the durable execution topology changes from recorded-only evidence to a live isolated executor. `CURRENT-STATE.md` must record the validated preview state once evidence exists. `DESIGN-SYSTEM.md` and `PROJECT-CONSTITUTION.md` remain unchanged unless implementation reveals a durable visual or governance change.
