## 1. Objective

Prevent bounded candidate recovery from repeating the same safe-patch mistake blindly after a syntactically valid implementation proposal is rejected by the server-owned proposal validator. Preserve the existing fail-closed validation and mutation boundaries while supplying later already-admitted candidate generators with bounded server-owned repair guidance.

## 2. Triggering evidence

Production Engineering Run `2b3cd15f-c5e2-481a-8266-c92c6534b08b` reached IMPLEMENT against `github:Ryan9876/ot-time`. All three admitted hosted model calls completed, and each was logged as `validation_failed` by the model router. The run then exhausted bounded candidate recovery and persisted `AGENTIC_CANDIDATE_EXHAUSTED` / `AUTONOMOUS_IMPLEMENT_FAILED`.

No source-lineage acceptance, Git mutation, deployment mutation, REVIEW completion, or canonical source mutation occurred. The safety boundary worked. The defect is recovery quality: alternate candidates receive no bounded indication that the previous parsed proposal failed strict safe-source validation.

## 3. Fixed decisions

- `SafeImplementationEngine` and `TextPatchEngine` remain authoritative and unchanged.
- A rejected candidate remains non-authoritative and non-mutating.
- Only router-classified `VALIDATION_EXHAUSTED` failures may trigger safe-patch repair guidance. Provider failures do not masquerade as validation failures.
- Repair guidance is server-owned static text. It contains no raw model output, raw provider payload, filesystem roots, credentials, environment values, secret source, or arbitrary exception text.
- Repair guidance may be appended only to a later already-admitted candidate generation request for the same work unit.
- Candidate count and alternate-agent budget remain unchanged; this release does not add an unbounded or hidden same-model loop.
- Exact acceptance ownership, candidate admission, disposable validation, independent evaluation, routing, canonical mutation, Git delivery, Preview delivery, REVIEW, and production authority remain unchanged.

## 4. Architecture requirements

1. Preserve the model router’s existing bounded attempt records and failure classification.
2. When implementation generation exhausts a route, project only a bounded `routing_failure` diagnostic containing the server-owned failure kind and sanitized attempt metadata.
3. In candidate recovery, inspect only that bounded diagnostic. If the kind is `VALIDATION_EXHAUSTED`, mark the rejection as validator-rejected and attach static repair guidance to the next admitted candidate’s immutable generation request.
4. Repair guidance must explicitly reinforce the strict safe-patch contract: exact selected source path/digest for existing files, empty-content digest for new files, one target per patch, matching single-file unified-diff headers, exact hunk coordinates/counts/context, bounded supported text targets, and exact acceptance coverage.
5. Provider exhaustion/rate-limit failures continue to alternate without validator-specific guidance.
6. Exhaustion diagnostics may record only bounded rejection kind values; they must not persist raw candidate text or arbitrary exception messages.

## 5. Acceptance criteria

### AC-01 Failure classification survives generation boundary
`ImplementationGenerationFailure` exposes bounded router failure classification without raw provider/model output.

### AC-02 Validation-only repair guidance
A parsed proposal rejected by the protected proposal validator causes the next admitted candidate for the same work unit to receive static server-owned safe-patch repair guidance.

### AC-03 Provider-failure separation
Provider/rate-limit failures do not receive validator-specific repair guidance and remain governed by existing candidate/provider recovery semantics.

### AC-04 Strict contract reinforcement
Repair guidance states the exact safe-patch requirements needed by the unchanged server validator, including exact path/digest binding and strict single-file unified-diff form.

### AC-05 Finite recovery preserved
The existing `max_reassignments_per_work_unit` bound and eligible-agent set remain authoritative. No additional unbounded retry loop is introduced.

### AC-06 No authority expansion
Repair guidance grants no canonical source, lineage, Git, deployment, REVIEW, Engineering Run transition, credential, or network authority.

### AC-07 Bounded exhaustion evidence
If all admitted candidates still fail, exhaustion evidence records only bounded server-owned rejection kind values and preserves `worker_process_loss=false` with all mutation claims false.

### AC-08 Success-path parity
A first candidate that passes the protected proposal validator follows the existing path with no repair guidance or semantic change.

### AC-09 Regression proof
Tests prove validation classification, validation-guided next-candidate repair, provider-failure separation, finite recovery, and bounded diagnostics.

### AC-10 Release gates
Protected spec/plan validation, focused tests, full API regression, Bounded Autonomy, client/browser, protected promotion, and DSPy release gates are green before merge.

## 6. Non-goals

- Weakening or bypassing safe patch validation.
- Logging or persisting rejected source proposals.
- Automatically editing malformed model output server-side.
- Increasing candidate count, reassignments, provider credentials, network access, or mutation authority.
- Changing worker-loss recovery, REVIEW, Git delivery, Preview delivery, or production promotion.

## 7. Production verification

After exact-source deployment, verify `/health` and `/ready`, scan runtime error/fatal logs, then exercise a bounded authenticated production implementation run. Acceptance requires either (a) a previously validator-rejected shape reaches an admitted proposal through repair-guided alternate recovery and continues through protected validation, or (b) deterministic production evidence proves the repair guidance was supplied and the run still failed closed for a different bounded reason. Do not fabricate a validator rejection or mutate canonical source merely to force the test.

## 8. Rollback

Revert the release commit. The change is pre-mutation generation guidance plus bounded diagnostics only; rollback restores P2-V0.23.8 blind alternate generation without data migration.
