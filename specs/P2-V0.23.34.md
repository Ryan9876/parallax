Eliminate the legacy post-IMPLEMENT source-shape re-inference that can contradict already-authoritative PLAN execution identity, while preserving exact accepted-lineage verification, closed-catalog execution profiles, source-free execution snapshots, dependency-preparation/network controls, command authority, mutation authority, provider/model/retry limits, Git/deployment/lifecycle authority, and the human REVIEW ceiling.

This reintroduces source-shape execution authority after PLAN and is inconsistent with the immutable execution-contract architecture established by P2-V0.23.31.

## 2. Fixed decisions

- Protected PLAN remains the sole authority that selects the Engineering Run execution contract. Post-IMPLEMENT source shape cannot select, upgrade, downgrade, or replace that authority.
- Same-lineage BUILD/TEST/VERIFY resolves the exact closed-catalog contract identity persisted by the latest authoritative successful PLAN associated with the accepted IMPLEMENT lineage.
- The required persisted identity includes at minimum execution-contract ID, binding reason, optional target, execution-contract digest, validation-profile ID, and validation-profile digest. Every supplied identity must match the server-resolved closed-catalog contract exactly.
- Invalid, missing, malformed, contradictory, stale, or drifted contract identity fails closed as bounded protected stage failure. It must not fall back to source-shape inference, generic Node/Python discovery, or caller-selected commands.
- Exact accepted-lineage Project/run identity, file set, byte size, per-file SHA-256, aggregate lineage evidence, sandbox source transfer, snapshot restoration, and cleanup verification remain mandatory.
- The same-lineage executor uses the validation profile from the resolved PLAN-bound contract. It does not call `select_validation_profile()` to choose authority after IMPLEMENT.
- `static-web-v1` remains the narrow server-owned static-web validator contract. Generated `package.json`, Python markers, .NET files, or other source-shape changes cannot switch it to generic Node, Python, or .NET execution.
- Existing governed Python and .NET execution contracts retain their current command profiles, preparation rules, execution snapshots, network policies, timeouts, and evidence semantics.
- No new execution contract, validation ecosystem, command, provider/model, credential, candidate, retry, hidden retry, timeout, mutation, lineage, Git/deployment, lifecycle, or REVIEW authority is added.
- Candidate validation and same-lineage validation must derive execution from the same immutable contract identity, preventing divergent execution authority between IMPLEMENT candidate acceptance and subsequent BUILD/TEST/VERIFY.

## 5. Architecture requirements

### 5.1 One execution authority from PLAN through VERIFY

Protected PLAN already materializes the exact current accepted source lineage, binds one closed-catalog `ExecutionContract`, and persists its server-owned identity. That binding remains authoritative for the Engineering Run until an already-governed human-authorized PLAN refresh creates a new authoritative PLAN. Successful IMPLEMENT may create a new accepted source lineage, but it does not create a new execution contract or authorize source-shape reclassification.

For an Engineering Run with accepted IMPLEMENT lineage, BUILD/TEST/VERIFY therefore require two independent authoritative references:

1. accepted source-lineage identity — determines exactly which source bytes execute;
2. PLAN-bound execution-contract identity — determines exactly how those bytes execute.

Neither may be inferred from the other after IMPLEMENT.

### 5.2 Authoritative contract extraction

The coordinator must use the latest successful protected PLAN applicable to the accepted IMPLEMENT lineage, not model output, caller input, generated source, or generic defaults. It extracts only the bounded contract fields already persisted by protected PLAN: contract ID, binding reason, target, contract digest, validation-profile ID, and validation-profile digest.

The extraction path must reject missing or wrong-typed fields, invalid digest forms, unknown closed-catalog identities, and conflicting target/binding combinations before those values can become execution authority. Human PLAN refresh remains the only mechanism that can replace the authoritative PLAN contract.

### 5.3 Closed-catalog resolution and exact verification

Server-owned code resolves the persisted contract through the existing `resolve_execution_contract()` catalog. The resolved contract must match all persisted identity fields exactly:

- `contract_id`;
- `binding_reason`;
- `target` including exact `None`/string semantics;
- execution-contract digest;
- validation-profile ID;
- validation-profile digest.

Mismatch fails closed. It does not call `select_validation_profile()`, inspect generated source markers to choose another profile, or silently repair persisted evidence.

### 5.4 Same-lineage execution remains byte-exact

Contract resolution changes only execution-authority selection. `SameLineageVercelSandboxExecutor` must still reconstruct the exact accepted lineage for the same Project/run, verify lineage ID, root containment/type, symlink exclusion, exact manifest path set, file size/SHA-256, aggregate file count/bytes, and source transfer into a disposable sandbox. The contract cannot authorize different source bytes.

### 5.5 Snapshot, preparation, network, and command authority remain fixed

After exact contract verification, the executor derives the existing validation profile, snapshot identity, working directory, protected command, timeout, and dependency-preparation policy from the resolved contract profile. Source-free execution snapshots remain server configured. Existing preparation allowlists remain bounded. Validation networking must still be proven locked to deny-all before protected command execution. Caller `ExecutionSpec` remains limited to identifying the registered stage/operation and cannot override the contract command.

### 5.6 Static-web cannot self-upgrade

A run bound to `static-web-v1` remains static-web for same-lineage BUILD/TEST/VERIFY even if accepted generated source contains a `package.json`, Python marker, `.csproj`, or other ecosystem marker. Such source may still fail the server-owned static-web validator according to its existing contract, but it cannot switch execution authority to Node package scripts, Python, or .NET.

Conversely, absence of generic ecosystem markers cannot invalidate an already-bound static-web contract. The protected validator itself determines static-web BUILD/TEST/VERIFY success.

### 5.7 Existing Python and .NET behavior

For a PLAN-bound established Parallax Python contract or bounded .NET contract, contract resolution must produce the same validation profile, target, execution snapshot family, dependency-preparation behavior, commands, and stage evidence as before this release. Tests must prove the authority source changes from re-inference to persisted binding without changing those governed behaviors.

### 5.8 Bounded diagnostics

Execution-contract extraction/resolution failure evidence is server-owned and sanitized. It may contain only fixed reason/classification identity and safe digests/boolean state already allowed by run-event evidence. It must not persist raw exception text, source/generated content, command output beyond existing bounded execution evidence, provider payloads, filesystem roots, credentials, environment values, or invented mutation/lineage/Git/deployment/REVIEW claims.

## 6. Security

This release removes a second execution-authority decision rather than adding one. The model cannot influence execution classification by writing manifests or markers after PLAN. The server resolves only a finite previously bound catalog identity and independently verifies its digest/profile identity before use.

Exact accepted-lineage reconstruction remains independent of execution-contract resolution, preserving separation between "what source" and "how to validate it." Caller command drift remains rejected before protected sandbox execution. No application environment or credentials are injected into validation sandboxes.

## 7. Reliability and migration

No database migration is required because protected PLAN already persists the required execution-contract identity in attempt evidence. Existing historical runs without sufficient PLAN-bound contract evidence remain fail-closed on the tightened same-lineage path; no speculative source-shape fallback is introduced for them.

Rollback restores P2-V0.23.33 behavior, including its known bounded marker-free same-lineage BUILD failure. Accepted source lineage and historical PLAN/IMPLEMENT attempt evidence require no reinterpretation or schema rollback.
