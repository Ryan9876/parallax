## 1. Objective

Wire the already-accepted Wave 2 application-building boundaries into the real engineering-run runtime so a Project-bound Code run can execute protected IMPLEMENT and, after that mutation is accepted into durable source lineage, BUILD, TEST, and VERIFY operate only on the exact accepted lineage inside an ephemeral deny-all Vercel Sandbox.

This workstream composes authority; it does not broaden it. Model output and API callers never receive filesystem-root, command, shell, Git, network, provider, publication, review, merge, or production-deployment authority.

## 2. Scope

This workstream owns only the production composition/adapters required to connect:

- #59 canonical `EngineeringRun.project_id` / `Project.id` identity;
- #60 `ProjectRunIdentity`, materialized workspace lease, immutable `SourceLineage`, stale-parent protection, reconstruction, and cleanup semantics;
- #68's production-safe durable persistence implementation beneath that same narrow lineage/materialization contract;
- #61 `RunProjectBinding`, `WorkspaceLineageGateway`, `ProtectedImplementationRuntime`, and `LineageAwareAutonomousExecutor` seams;
- the existing `VercelSandboxExecutor` security posture, `ProtectedCommandPolicy`, and server-owned `ProtectedCommandRegistry`;
- the actual `/v1/engineering-runs/{run_id}/autonomous` route composition.

The workstream may add concrete runtime-composition and lineage-aware sandbox modules, focused tests, and the minimum route dependency wiring. It must not change durable lineage storage internals, implementation-generation semantics, patch-engine safety, protected command definitions, provider publication, client UX, or deployment authority.

## 3. Fixed decisions

- Canonical runtime identity is `ProjectRunIdentity(project_id=EngineeringRun.project_id, run_id=EngineeringRun.id)`. `workspace_ref`, repository metadata, URLs, caller/model text, and filesystem paths are never identity or authority inputs.
- #69 depends on a narrow `DurableLineageAllocator` protocol rather than `SourceLineageStore` or any persistence implementation. The protocol must remain reconcilable with #68's accepted production-safe allocator/materialization boundary before this workstream may be called ready for integration.
- The implementation gateway resolves the exact current lineage into a generated disposable materialized lease, binds the resulting #61 handle to that lineage, and accepts mutation only against that exact expected parent.
- The implementation adapter records/validates the safe implementation `workspace_digest` against the accepted lineage `content_digest`; a mismatch is a post-mutation non-success.
- Materialized lease roots are server-owned implementation details. They are never returned to model prompts, API evidence, or provider-visible metadata.
- The lineage-aware executor reconstructs the exact accepted `source_lineage_ref` for the exact canonical Project/run before creating a sandbox.
- Post-IMPLEMENT BUILD/TEST/VERIFY must never call `GitSource`, clone/fetch a repository, use a fresh checkout, or fall back to the legacy executor.
- The sandbox is ephemeral and empty at creation: `persistent=False`, `NetworkPolicy.deny_all()`, `env={}`, `destroy=True`. Source enters only by transferring the reconstructed accepted lineage through the Sandbox filesystem API.
- Executable command text remains server-owned by `ProtectedCommandRegistry`. The lineage-aware executor validates the incoming `ExecutionSpec` with `ProtectedCommandPolicy`, proves it exactly equals the registry-generated spec for the stage/operation key, and resolves command/args only from the registry.
- No application environment values, Vercel credentials, provider tokens, repository credentials, or arbitrary headers are copied into the sandbox environment.
- Sandbox evidence remains bounded and sanitized. Server-owned `project_ref`, `run_id`, and `source_lineage_ref` are written by `AutonomyCoordinator`; executor-provided identity cannot override them.
- Lease cleanup runs after successful or failed source transfer/execution and may delete only disposable materialization. Cleanup must never delete or advance durable lineage.
- Historical/pre-lineage Wave 1 runs retain the accepted legacy executor behavior only when no successful IMPLEMENT lineage evidence exists. Once accepted lineage exists, same-lineage execution is mandatory.
- A production composition that cannot construct the durable allocator, resolve canonical Project identity, reconstruct lineage, transfer exact source, or establish sandbox readiness fails closed rather than silently substituting local or fresh-repository state.

## 4. Non-goals

- Replacing #68's durable object/metadata persistence architecture.
- Treating `/tmp`, function-local disk, or `Project.workspace_ref` as authoritative lineage storage.
- Changing #61 typed generation, source-context selection, `SafeImplementationEngine`, `TextPatchEngine`, or IMPLEMENT protected validator semantics.
- Adding or editing protected BUILD/TEST/VERIFY commands.
- Arbitrary shell, command, subprocess, HTTP, network, Git, GitHub, Vercel-provider, database, or filesystem APIs exposed to caller/model input.
- Provider publication, preview mutation, deployment promotion, alias mutation, Git commit/push/merge, or pull-request approval.
- Autonomous REVIEW.
- Client UI changes.
- Authoritative project-record edits in this worker slice.

## 5. Architecture requirements

Required composed path:

```text
authenticated Project-bound Engineering Run
      ↓
EngineeringRunService (owner-scoped #59 contract)
      ↓
RuntimeComposition
      ├─ RunProjectBinding -> EngineeringRun.project_id
      ├─ DurableLineageGateway -> #60/#68 allocator protocol
      ├─ ProtectedImplementationRuntime (#61)
      └─ SameLineageVercelSandboxExecutor
              ↓
AutonomyCoordinator
      ↓ PLAN
IMPLEMENT: current durable lineage -> disposable lease -> typed proposal -> Wave 1 safe patch -> expected-parent lineage acceptance -> protected stage write
      ↓
accepted source_lineage_ref
      ↓
BUILD / TEST / VERIFY:
exact lineage reconstruct -> disposable lease -> empty ephemeral deny-all Vercel Sandbox -> exact file transfer -> existing protected registered command -> bounded evidence -> cleanup
      ↓
REVIEW operator boundary
```

`DurableLineageAllocator` must expose only the semantics required by composition: resolve/materialize current or requested lineage, accept an implementation against an expected parent, reconstruct an exact lineage, and cleanup a disposable materialized workspace. #69 must not inspect storage roots, blob keys, Postgres rows, provider credentials, or local-store internals.

The implementation gateway must retain the materialized lease associated with the exact #61 handle without placing the local path in observable evidence. Acceptance must fail if the handle is unknown, already consumed, Project/run identity changed, expected parent changed, or the accepted lineage content digest does not equal the safe implementation workspace digest. Cleanup follows acceptance/failure without mutating durable lineage.

The same-lineage sandbox executor must independently reconstruct the requested lineage through the allocator for every execution attempt/process instance. It must verify the reconstructed lineage's Project/run/lineage IDs, enumerate only regular protected source files under the lease, transfer the exact file bytes to `/vercel/sandbox` through the SDK filesystem API, and execute only the protected registry command with the registry working directory and timeout. It must destroy the sandbox and clean the lease in `finally` behavior.

## 6. Security

Fail closed without fabricated success when any of the following cannot be proven:

- `EngineeringRun.project_id` is missing, non-canonical, or inconsistent with the requested lineage;
- run identity or lineage belongs to another Project/run;
- current or requested lineage is missing, corrupt, stale, or cannot be reconstructed;
- expected-parent acceptance fails, including stale parent or idempotency conflict;
- safe implementation workspace digest differs from the accepted lineage content digest;
- materialized lease is unavailable, escaped, symlinked, or contains unexpected file state;
- sandbox SDK/provider identity is unavailable;
- sandbox creation does not use deny-all network / ephemeral / empty-env settings;
- source transfer fails or transfers a different byte set than the reconstructed accepted lineage;
- execution spec differs from the protected registry-generated spec;
- protected command execution fails or times out;
- cleanup encounters a failure after execution; cleanup failure is observable but never converts command failure into success;
- durable IMPLEMENT stage write fails after mutation/lineage acceptance; `mutation_applied=true` remains observable and no stage success is fabricated;
- #68's final durable allocator cannot satisfy the protocol used here.

Security invariants:

- no generic shell/network/Git/provider authority is added;
- no repository URL is used in same-lineage sandbox creation;
- no application secrets or environment values are copied into the sandbox;
- no source contents, local roots, credentials, or unrestricted provider responses are stored in durable stage evidence;
- Sandbox stdout/stderr remain bounded/redacted by the existing evidence boundary;
- source transfer uses only reconstructed lineage bytes already accepted by the protected lineage system;
- the model cannot select lineage ID, Project ID, run ID, command, working directory, timeout, sandbox network policy, or environment.

### AC-02 Canonical Project/run identity composition
Production composition derives `ProjectRunIdentity` exclusively from persisted `EngineeringRun.project_id` and `EngineeringRun.id`. Missing/non-canonical/mismatched Project or run identity fails closed. Tests prove `workspace_ref`, repository metadata, URL/path text, and executor/model values cannot substitute for canonical identity.

### AC-03 Narrow durable-lineage adapter and #68 reconciliation
A concrete #61 `WorkspaceLineageGateway` depends only on a narrow allocator/materialization protocol matching #60 semantics and not on filesystem store internals. It resolves the current exact parent lineage, accepts implementation with expected-parent protection, verifies returned Project/run/parent/content identity, and cleans only the disposable lease. Final readiness requires explicit evidence that this protocol is reconcilable with #68's accepted durable-lineage implementation.

### AC-04 Protected IMPLEMENT wired into the actual runtime
The actual owner-scoped engineering-run autonomous route composes and injects `ProtectedImplementationRuntime` with `RunProjectBinding` and the durable-lineage gateway. A production Project-bound IMPLEMENT can therefore execute through #61 without bypassing Work Specification binding, Wave 1 safe mutation, lineage receipt validation, revision/idempotency semantics, or the existing protected stage validator.

### AC-05 Exact same-lineage reconstruction for later stages
After successful IMPLEMENT, BUILD/TEST/VERIFY use a lineage-aware executor that reconstructs the exact accepted `source_lineage_ref` for the exact canonical Project/run on every attempt. Missing/corrupt/wrong-Project/wrong-run lineage fails closed. Tests prove a different process/composition instance can resume from durable lineage and no fresh repository checkout is used.

### AC-06 Ephemeral deny-all sandbox with exact source transfer
Same-lineage execution creates an empty ephemeral Vercel Sandbox with deny-all network, `persistent=False`, `env={}`, and destroy-on-exit semantics, then transfers only the reconstructed lineage source through the Sandbox filesystem API. No `GitSource`, repository clone/fetch, application environment forwarding, or provider credential copying occurs. Transfer failure yields non-success and both sandbox/lease cleanup are attempted.

### AC-07 Existing protected command registry remains authoritative
The lineage-aware executor validates the `ExecutionSpec` with existing `ProtectedCommandPolicy`, requires exact equality with `ProtectedCommandRegistry.spec_for(stage, operation_key)`, and resolves executable command/args only through `ProtectedCommandRegistry.invocation_for(stage)`. Caller/model text cannot introduce shell, command, working-directory, timeout, environment, Git, network, or provider actions.

### AC-08 Server-owned lineage execution evidence
BUILD/TEST/VERIFY evidence remains bounded and includes same-lineage execution facts, while canonical `project_ref`, `run_id`, and `source_lineage_ref` are server-owned and cannot be spoofed by executor output. Tests inject conflicting executor identity and prove the protected evidence still binds the accepted lineage. No local workspace root, raw source, credential, or unrestricted provider response is persisted.

### AC-09 Cleanup, interruption, and failure truthfulness
Disposable lineage leases and ephemeral sandboxes are cleaned after success and failure without deleting durable lineage. Materialization failure, source-transfer failure, protected command failure/timeout, cleanup failure, revision conflict, stale expected parent, and accepted mutation followed by durable-stage-write failure remain distinguishable non-success conditions. No failure path fabricates IMPLEMENT or later-stage success.

### AC-10 Retry and cross-process durability behavior
Runtime retry/replay preserves #61 operation-key and Wave 1 pre-image semantics. A fresh runtime-composition instance can reconstruct the accepted lineage and continue BUILD/TEST/VERIFY without relying on prior process memory or local authoritative lineage state. Tests prove successful IMPLEMENT is not applied twice and same-lineage execution remains stable across composition instances.

### AC-11 Deterministic end-to-end same-lineage fixture
A deterministic local/integration fixture proves PLAN -> IMPLEMENT -> BUILD -> TEST -> VERIFY -> REVIEW uses one canonical Project/run and one accepted post-IMPLEMENT lineage identity for all later execution stages. The fixture also proves later stages cannot run against unrelated source and that the legacy fresh-repository executor is never called once accepted IMPLEMENT lineage exists.

### AC-12 Worker isolation and exact-head validation
Final changes stay inside #69's declared owned paths; the temporary DSPy workflow is absent. The branch is current with `integration/wave2-app-builder`, the #68 adapter contract is reconcilable, focused adapter/API/executor tests and full API regression pass, and exact-head Workstream Spec Validation, Parallax P2 CI, and Bounded Autonomy Pilot are green. PR targets the integration branch and remains unmerged/undeployed.

## 8. Risks and mitigations

- **#68 contract drift while parallel:** isolate #69 behind the narrow allocator/materialization protocol and refuse final readiness until the accepted #68 implementation is checked against it.
- **Accidental fresh-checkout fallback:** the same-lineage executor never constructs Git source and tests assert the legacy executor is not called after accepted IMPLEMENT lineage.
- **Source-transfer corruption:** transfer only reconstructed accepted files and verify bounded file/digest identity before execution; provider/transfer failures remain non-success.
- **Local-function durability regression:** composition never constructs `SourceLineageStore` or treats local roots as authoritative; process-memory/local leases are disposable only.
- **Command-authority expansion:** reuse `ProtectedCommandPolicy` and `ProtectedCommandRegistry` unchanged, require exact registered specs, and prohibit command text from API/model inputs.
- **Cleanup hides execution truth:** cleanup runs in bounded finalization and cannot turn failure into success or delete durable lineage.
- **Post-mutation durable-write failure:** preserve #61 `mutation_applied=true` semantics and never replay a mutation without protected pre-image/idempotency proof.
