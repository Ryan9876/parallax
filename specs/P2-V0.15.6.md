## 1. Objective

Wire the accepted Wave 2 application-building boundaries into the actual engineering-run runtime. A Project-bound Code run must be able to execute protected IMPLEMENT and then run BUILD, TEST, and VERIFY only against the exact immutable source lineage accepted from that IMPLEMENT operation.

This workstream composes existing authority; it does not broaden authority. Model output and API callers never receive filesystem-root, shell/command, Git, network, provider, publication, review, merge, or production-deployment authority.

## 2. Scope

This workstream may add only the production composition/adapters required to connect:

- #59 canonical `EngineeringRun.project_id` / `Project.id` identity;
- #60 Project/run source-lineage materialization, expected-parent acceptance, reconstruction, and cleanup semantics;
- #68 production-safe durable persistence beneath that same narrow allocator/materialization interface;
- #61 `RunProjectBinding`, `WorkspaceLineageGateway`, `ProtectedImplementationRuntime`, and lineage-aware autonomy seam;
- the existing `ProtectedCommandPolicy`, server-owned `ProtectedCommandRegistry`, and Vercel Sandbox security posture;
- the actual `/v1/engineering-runs/{run_id}/autonomous` runtime composition.

The worker may add `runtime_composition.py`, `lineage_sandbox_execution.py`, focused tests, the minimum route dependency wiring, this specification, and its compiled plan. It must not change #68 persistence internals, #61 generation or safe-mutation semantics, the protected command registry, provider publication, client UX, deployment workflows, or authoritative project records.

## 3. Fixed decisions

- Canonical runtime identity is `ProjectRunIdentity(project_id=EngineeringRun.project_id, run_id=EngineeringRun.id)`. `workspace_ref`, repository metadata, URL/path text, caller/model text, and executor output cannot substitute for identity or authority.
- #69 depends on a narrow `DurableLineageAllocator` protocol, not `SourceLineageStore`, filesystem roots, blob keys, database rows, or another persistence implementation. Final readiness requires this protocol to reconcile with #68's accepted production-safe implementation.
- IMPLEMENT resolves the exact current lineage into a generated disposable lease and accepts mutation only against that exact expected parent.
- Wave 1 `SafeImplementationEngine.workspace_digest` and #60 `SourceLineage.content_digest` have different meanings. The safe mutation digest hashes the changed-artifact projection; the lineage content digest identifies the complete accepted tree. They must never be compared as if identical.
- After lineage acceptance, the adapter must prove every safe-mutation artifact path, SHA-256, and size is represented exactly in the accepted lineage. The #61 receipt separately echoes the original safe-mutation `workspace_digest` while `source_lineage_ref` identifies the immutable accepted tree.
- Materialized lease roots are server-owned disposable implementation details and are never model-visible or durable evidence.
- BUILD/TEST/VERIFY after accepted IMPLEMENT must reconstruct the exact accepted `source_lineage_ref` for the canonical Project/run. They must never call `GitSource`, clone/fetch a repository, use a fresh checkout, or fall back to the legacy executor.
- Same-lineage execution creates an empty ephemeral Vercel Sandbox with `persistent=False`, `NetworkPolicy.deny_all()`, `env={}`, and destroy-on-exit behavior. Source enters only through the Sandbox filesystem API from the reconstructed accepted lineage.
- Executable command text remains server-owned by `ProtectedCommandRegistry`. The executor validates the incoming `ExecutionSpec` with `ProtectedCommandPolicy`, requires exact equality with the registry-generated spec for stage/operation key, and resolves command/args only from the registry.
- No application environment values, Vercel credentials, repository credentials, provider tokens, or arbitrary headers are copied into the sandbox environment.
- Server-owned Project/run/lineage evidence overrides any conflicting executor-provided values.
- Lease and sandbox cleanup runs after success or failure and may delete only disposable materialization. It never deletes or advances durable lineage.
- Historical/pre-lineage Wave 1 behavior remains only when no successful IMPLEMENT lineage exists. Once accepted lineage exists, same-lineage execution is mandatory.
- If durable allocation, canonical identity, exact reconstruction, source transfer, protected execution, or #68 compatibility cannot be proven, the runtime fails closed rather than substituting local or fresh-repository state.

## 4. Non-goals

- Replacing #68 durable object/metadata persistence architecture.
- Treating `/tmp`, function-local disk, or `Project.workspace_ref` as authoritative lineage state.
- Changing #61 typed generation, source-context selection, `SafeImplementationEngine`, `TextPatchEngine`, or protected IMPLEMENT validation.
- Adding/editing protected BUILD/TEST/VERIFY commands.
- Generic shell, command, subprocess, HTTP/network, Git/GitHub, provider, database, or filesystem APIs exposed to caller/model input.
- Provider publication, preview mutation, deployment promotion, alias mutation, Git commit/push/merge, or pull-request approval.
- Autonomous REVIEW.
- Client UI changes.
- Authoritative project-record edits by this worker.

## 5. Architecture requirements

Required composition:

```text
authenticated owner-scoped Project-bound Engineering Run
      ↓
EngineeringRunService (#59)
      ↓
RuntimeComposition
      ├─ RunProjectBinding -> EngineeringRun.project_id
      ├─ DurableLineageGateway -> #60/#68 allocator protocol
      ├─ ProtectedImplementationRuntime (#61)
      └─ SameLineageVercelSandboxExecutor
              ↓
AutonomyCoordinator
      ↓ PLAN
IMPLEMENT:
current lineage -> disposable lease -> typed proposal -> Wave 1 safe patch
-> exact expected-parent lineage acceptance -> artifact-to-lineage verification
-> protected IMPLEMENT stage write
      ↓
accepted source_lineage_ref
      ↓
BUILD / TEST / VERIFY:
exact lineage reconstruct -> disposable lease -> empty deny-all Vercel Sandbox
-> exact source transfer -> existing registered protected command -> bounded evidence
-> cleanup
      ↓
REVIEW operator boundary
```

`DurableLineageAllocator` exposes only the semantics needed by composition: resolve/materialize current or requested lineage, accept implementation against an expected parent, reconstruct an exact lineage, and cleanup a disposable materialized workspace. #69 does not inspect or own persistence internals.

The concrete #61 gateway retains only in-flight lease ownership required to connect a returned `ImplementationWorkspaceHandle` to later `accept_implementation`. That in-process mapping is not durable authority. A composition-level finalizer cleans unresolved leases when generation, validation, or mutation stops before lineage acceptance.

On acceptance the gateway verifies exact Project/run identity, exact parent lineage, a newly accepted lineage, and exact representation of every changed artifact in the accepted lineage. It returns `ImplementationLineageReceipt.workspace_digest` from the safe mutation evidence without conflating it with whole-tree `SourceLineage.content_digest`.

The same-lineage sandbox executor independently reconstructs the requested lineage on every execution attempt, including a new process/composition instance. It verifies the materialized file set against the immutable lineage manifest, transfers those exact bytes into an otherwise empty sandbox, executes only the protected registry command, then destroys the sandbox and cleans the lease.

## 6. Security

Fail closed without fabricated success when any of the following cannot be proven:

- canonical `EngineeringRun.project_id` and run ID are valid and match the lineage;
- current/requested lineage exists, is intact, and reconstructs for the exact Project/run;
- expected-parent acceptance succeeds without stale-parent/CAS conflict;
- every safe mutation artifact exists in the accepted lineage with identical digest and size;
- materialized lease is server-owned, available, non-symlinked, and contains exactly the accepted lineage files;
- sandbox provider identity/SDK is available;
- sandbox creation uses deny-all network, empty environment, non-persistence, and destroy-on-exit;
- exact source transfer succeeds;
- `ExecutionSpec` exactly matches the protected command registry;
- registered command execution succeeds without timeout;
- cleanup completes or its failure is surfaced as non-success;
- durable IMPLEMENT stage write succeeds after mutation/lineage acceptance;
- #68's final durable allocator satisfies the protocol consumed here.

Security invariants:

- no generic shell/network/Git/provider authority is added;
- no repository URL or `GitSource` is used after accepted IMPLEMENT lineage;
- no application secrets/environment values are forwarded into the sandbox;
- no source contents, local roots, credentials, or unrestricted provider responses are persisted as stage evidence;
- stdout/stderr remain bounded/sanitized by the existing evidence posture;
- the model cannot choose Project ID, run ID, lineage ID, command, working directory, timeout, sandbox network policy, or environment;
- safe mutation success, lineage acceptance, sandbox execution, and durable stage transition remain separate authorities.

### AC-02 Canonical Project/run identity composition
Production composition derives `ProjectRunIdentity` exclusively from persisted `EngineeringRun.project_id` and `EngineeringRun.id`. Missing/non-canonical/mismatched identity fails closed. Tests prove workspace metadata, repository metadata, URLs/paths, model text, and executor values cannot substitute for canonical identity.

### AC-03 Narrow durable-lineage adapter and #68 reconciliation
A concrete #61 `WorkspaceLineageGateway` depends only on the narrow allocator/materialization protocol. It resolves the exact current parent, accepts with expected-parent protection, verifies Project/run/parent/new-lineage identity and exact changed-artifact membership, and cleans only disposable leases. Final readiness requires evidence that the protocol is reconcilable with #68's accepted durable implementation.

### AC-04 Protected IMPLEMENT wired into the actual runtime
The real owner-scoped autonomous engineering-run route injects `ProtectedImplementationRuntime` with `RunProjectBinding` and the durable-lineage gateway. A Project-bound IMPLEMENT executes through #61 without bypassing approved Work Specification binding, Wave 1 safe mutation, lineage verification, revision/idempotency, or protected stage validation.

### AC-05 Exact same-lineage reconstruction for later stages
After successful IMPLEMENT, BUILD/TEST/VERIFY reconstruct the exact accepted `source_lineage_ref` for the exact canonical Project/run on every attempt. Missing/corrupt/wrong-Project/wrong-run lineage fails closed. A fresh runtime-composition instance can resume from durable lineage without relying on prior process memory.

### AC-06 Ephemeral deny-all sandbox with exact source transfer
Same-lineage execution creates an empty ephemeral Vercel Sandbox with deny-all network, `persistent=False`, `env={}`, and destroy-on-exit behavior, then transfers only reconstructed accepted source through the Sandbox filesystem API. No `GitSource`, repository clone/fetch, application environment forwarding, or credential copying occurs. Transfer failure yields non-success and cleanup is attempted.

### AC-07 Existing protected command registry remains authoritative
The executor validates `ExecutionSpec` with existing `ProtectedCommandPolicy`, requires exact equality with `ProtectedCommandRegistry.spec_for(stage, operation_key)`, and resolves command/args only via `ProtectedCommandRegistry.invocation_for(stage)`. Caller/model input cannot create commands, working directories, timeouts, environment, Git/network actions, or provider actions.

### AC-08 Server-owned lineage execution evidence
BUILD/TEST/VERIFY evidence is bounded and same-lineage. Canonical `project_ref`, `run_id`, and `source_lineage_ref` are server-owned and cannot be spoofed by executor output. No local workspace root, raw source, credential, or unrestricted provider response is persisted.

### AC-09 Cleanup, interruption, and failure truthfulness
Disposable leases and ephemeral sandboxes are cleaned after success/failure without deleting durable lineage. Materialization failure, source-transfer failure, protected command failure/timeout, cleanup failure, revision conflict, stale parent, and mutation followed by durable-stage-write failure remain distinguishable non-success conditions. No failure path fabricates stage success.

### AC-10 Retry and cross-process durability behavior
Runtime retry preserves #61 operation-key replay and Wave 1 pre-image semantics. A new composition/process instance reconstructs accepted lineage for later stages from the durable allocator contract. Successful IMPLEMENT is not applied twice and later execution does not depend on process-local authoritative lineage state.

### AC-11 Deterministic end-to-end same-lineage fixture
A deterministic fixture proves PLAN -> IMPLEMENT -> BUILD -> TEST -> VERIFY -> REVIEW uses one canonical Project/run and one accepted post-IMPLEMENT lineage for all later stages. It proves unrelated/fresh source cannot execute and the legacy fresh-repository executor is never called once accepted IMPLEMENT lineage exists.

### AC-12 Worker isolation and exact-head validation
Final changes remain inside #69-owned paths and the temporary DSPy workflow is absent. The branch is current with `integration/wave2-app-builder`, #68 compatibility is proven, focused/full regression tests pass, and exact-head Workstream Spec Validation, Parallax P2 CI, and Bounded Autonomy Pilot are green. PR targets the integration branch and remains unmerged/undeployed.

## 8. Risks and mitigations

- **#68 contract drift:** isolate behind the narrow allocator protocol and refuse final readiness until accepted #68 code is checked.
- **Fresh-checkout fallback:** same-lineage executor never constructs Git source; tests assert the legacy executor is not called after accepted lineage.
- **Digest semantic confusion:** mutation digest and whole-tree lineage digest remain separate; artifact membership proves the mutation is contained in the accepted tree.
- **Source-transfer corruption:** verify reconstructed materialization against immutable lineage file digests before transfer; transfer/provider failures remain non-success.
- **Local durability regression:** composition never creates/owns `SourceLineageStore` or treats disposable local lease state as durable.
- **Command-authority expansion:** reuse existing policy/registry unchanged and require exact registered specs.
- **Cleanup hides truth:** cleanup cannot turn failure into success or delete durable lineage.
- **Post-mutation durable-write failure:** preserve #61 `mutation_applied=true` semantics and do not fabricate/replay mutation without protected idempotency proof.
