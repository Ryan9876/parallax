# Parallax 2.0 — Wave 3 Durable Worker Lifecycle and Recovery

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.16.1
Workstream: WS-W3-WORKER-RECOVERY / GitHub issue #95
Base: main@ec65c00eec5bdd1b1b66afdfb0c287834cfc1aa9
Depends on: deployed P2-V0.15.1 through P2-V0.15.12 Project/run/spec/source-lineage/runtime/evidence contracts
Method: extend the existing Engineering Run kernel with one server-owned durable worker-execution authority rather than encoding recovery state in immutable stage attempts or inventing a competing run identity

## 1. Objective

Make ordinary worker/process loss, hangs and recoverable execution stalls resumable without requiring the operator to issue a manual `resume` instruction. The server must durably know who currently owns one Engineering Run's worker mutation lease, what meaningful progress has been accepted, which exact checkpoint/source lineage can be resumed, why a run is stalled, and whether the correct next action is retry, recovery, reassignment or genuine human intervention.

Recovery must preserve the deployed Wave 2 authority chain: authenticated canonical Project, approved Work Specification, Engineering Run, accepted source lineage, protected mutation, exact-lineage validation, provider replay and protected evaluation remain authoritative. Worker recovery coordinates those capabilities; it cannot replace or weaken them.

## 2. Scope

- Add one durable worker-execution record associated one-to-one with an Engineering Run. Existing `EngineeringAttempt` rows remain immutable stage/evidence history and are not repurposed as lease state.
- Represent protected worker lifecycle states including `RUNNING`, `PROGRESSING`, `CHECKPOINTED`, `STALLED`, `RECOVERING`, `REASSIGNED`, `HUMAN_REQUIRED`, `READY_FOR_INTEGRATION`, `SUCCEEDED` and `FAILED`.
- Add a renewable bounded lease with an opaque owner identity, monotonically increasing lease generation, explicit expiry and atomic stale-writer rejection.
- Define meaningful progress as an accepted durable state advancement such as checkpoint revision, accepted source-lineage advancement, protected stage/evaluation result or explicit bounded blocker classification. Status text, token activity and repeated heartbeats without durable advancement do not reset no-progress state.
- Persist a bounded resumable checkpoint binding canonical Project/run identity, approved Work Specification revision/digest, compiled-plan reference, accepted source-lineage identity, current bounded step, attempt/retry/no-progress counters, last-known-good lineage, bounded normalized evidence references and outstanding dependencies/blocker state.
- Classify stalls from bounded evidence into at least process loss, test/CI hang, provider outage, dependency wait, rate limit, authorization/credential failure, contention/deadlock, repeated implementation failure and genuine human-required authority/specification boundary.
- Support bounded retry/backoff, lease recovery and reassignment from the last durable checkpoint. Independent work remains outside this workstream; this contract only guarantees safe ownership/recovery for one worker execution.
- Expose an operator-readable health snapshot containing lifecycle state, current lease status, last meaningful progress, checkpoint/source-lineage identity, retry/no-progress counters, stall classification, dependency/blocker and next recovery action.
- Add deterministic process-loss, lease-expiry, stale-writer, no-progress, oscillation and reassignment tests proving recovery without duplicate mutation or corruption of accepted lineage.
- Add a forward migration for the worker-execution persistence boundary with RLS enabled and direct `anon`/`authenticated` privileges revoked in hosted production posture.

## 3. Security

- `EngineeringRun.id`, canonical `Project.id`, approved Work Specification revision/digest and accepted source lineage remain authoritative. A caller/model cannot supply a replacement Project/run/spec/lineage identity through a checkpoint.
- Lease owner IDs and lease generations are server-issued coordination values, not user identities and not authorization credentials for provider, filesystem, shell, network or production actions.
- A mutation-capable worker operation must prove the exact current lease owner and generation. Expired, replaced, stale or mismatched lease generations fail closed before mutation authority is used.
- Reassignment increments the lease generation before a replacement owner can progress. A stale process that wakes afterward cannot renew, checkpoint or mutate under the abandoned generation.
- Checkpoint payloads are bounded and normalized. They may contain identifiers, counters, enums, digests and bounded evidence references; they must not persist source bytes, provider responses, credentials/tokens/headers/cookies/environment, hidden reasoning/scratchpad, arbitrary commands, arbitrary URLs or unbounded logs.
- Worker recovery cannot redefine Work Specification acceptance criteria, protected evaluator thresholds, tool capabilities, registered provider targets, source-lineage parentage or production authority.
- `HUMAN_REQUIRED` is reserved for genuine specification/authority/credential boundaries after classification; ordinary process failure, recoverable timeout, provider transient and worker crash must not be escalated merely because the original process disappeared.
- Hosted worker-execution tables follow the server-owned posture: RLS enabled, no permissive direct-client policies, and direct `anon`/`authenticated` table privileges revoked.

## 4. Durable worker execution contract

Each Engineering Run may have at most one durable worker-execution authority record. The record contains bounded fields equivalent to:

- worker execution ID and `run_id`;
- lifecycle state;
- opaque current `lease_owner_id` when leased;
- monotonic `lease_generation`;
- `lease_expires_at`;
- `last_meaningful_progress_at`;
- checkpoint revision and bounded checkpoint JSON;
- current step;
- accepted `source_lineage_ref` and optional `last_known_good_lineage_ref`;
- retry, no-progress and oscillation counters;
- optional stall classification / blocker code / next recovery action;
- row revision plus created/updated timestamps.

The durable row is coordination authority only. It references the canonical Engineering Run and accepted lineage; it does not duplicate Work Specification, source bytes, provider audit or evaluation authority.

## 5. Lease and progress semantics

Lease acquisition/renewal/reassignment must be atomic under concurrent callers.

- Initial acquisition creates or claims the worker record, issues an opaque owner ID and current generation, and sets a bounded expiry.
- Renewal succeeds only for the exact active owner + generation and extends expiry by a server-bounded duration.
- Meaningful progress may update checkpoint state and renew the active lease in one protected transaction when identity/generation/revision checks pass.
- Expired leases may be recovered only through a protected recovery transition. Reassignment increments generation before assigning a replacement owner.
- A stale owner/generation cannot renew, checkpoint, transition lifecycle, reset no-progress counters or claim mutation authority.
- Mere renewal without accepted progress does not update `last_meaningful_progress_at` and cannot indefinitely hide a stalled worker.

## 6. Checkpoint and recovery semantics

A checkpoint is resumable only when all canonical bindings still match the Engineering Run and durable source-lineage state. At minimum it binds:

- `project_id` and `run_id`;
- Work Specification ID/revision/digest;
- compiled-plan/spec reference;
- current bounded lifecycle/step;
- accepted source-lineage reference;
- optional last-known-good lineage reference;
- attempt/retry/no-progress/oscillation counters;
- bounded normalized evidence references;
- bounded dependency/blocker state.

Recovery never replays a source mutation merely because a process vanished. It resumes from the checkpoint and asks the existing Wave 2 runtime/provider replay boundaries to resolve accepted mutation/stage/delivery facts. If the checkpoint and current authoritative lineage disagree, recovery fails closed rather than guessing.

## 7. Stall classification and recovery policy

The watchdog consumes timestamps, lease state and normalized failure/dependency evidence and returns a deterministic bounded classification plus next action.

Recoverable examples:

- process/worker loss -> expire/recover/reassign from checkpoint;
- test or CI hang -> bounded cancel/timeout then retry from checkpoint;
- transient provider outage/rate limit -> bounded backoff and retry;
- dependency wait -> remain checkpointed/waiting while independent scheduler work may continue;
- contention/deadlock -> bounded backoff/reassignment when safe;
- repeated implementation failure -> correction/retry only until configured no-progress/attempt bounds.

Human-required examples are limited to missing/expired authorization that cannot be refreshed automatically, destructive/privileged approval, material Work Specification ambiguity/conflict, or another explicit protected authority boundary.

No-progress/oscillation counters are monotonically derived from accepted attempts/checkpoints; workers cannot reset them by emitting activity.

## 8. Operator health evidence

A health snapshot must be reconstructable after process recreation and include only bounded observable facts:

- Project/run and worker-execution identifiers;
- lifecycle state;
- active/expired/unowned lease status and generation, but no secret lease material;
- current step;
- accepted and last-known-good lineage references;
- checkpoint revision;
- last meaningful progress time;
- retry/no-progress/oscillation counters;
- current stall/blocker classification;
- bounded dependency state;
- next recovery action and whether human intervention is actually required.

The health surface does not expose hidden reasoning, raw checkpoint internals, source, credentials or unbounded provider/test logs.

## 9. Non-goals

- browser/DOM/accessibility/screenshot/multimodal validation implementation;
- autonomous correction/model repair policy;
- critical-path scheduling or work stealing across multiple workstreams;
- changing the deployed Engineering Run stage lifecycle or replacing `EngineeringAttempt` evidence history;
- introducing a second Project, Work Specification, source-lineage, provider-audit or protected-evaluation identity;
- generic shell, process control, raw HTTP, arbitrary provider calls or production deployment authority;
- automatically merging or deploying Wave 3 to production.

## 10. Acceptance criteria

### AC-01 One durable worker authority per Engineering Run
A server-owned worker-execution record is durably associated with exactly one canonical Engineering Run, and concurrent creation/acquisition cannot produce competing active worker authorities for the same run. Existing Engineering Attempt history remains separate and unchanged.

### AC-02 Lease generation enforces single-writer ownership
Initial acquisition, renewal, expiry recovery and reassignment use an opaque owner plus monotonically increasing generation. Only the exact active unexpired owner/generation may perform protected worker-state progress. A stale or replaced worker fails closed before checkpoint or mutation-capable progression.

### AC-03 Meaningful progress cannot be faked by activity
Lease renewal/status activity without accepted durable advancement does not update `last_meaningful_progress_at` or reset no-progress counters. Accepted checkpoint/source-lineage/stage/evaluation/blocker advancement updates meaningful-progress evidence deterministically.

### AC-04 Checkpoints bind canonical execution identity
A resumable checkpoint binds exact Project/run identity, approved Work Specification ID/revision/digest, compiled-plan/spec reference, current step, accepted source lineage, counters, optional last-known-good lineage and bounded evidence/dependency state. Wrong Project/run/spec/digest/lineage or malformed checkpoint data is rejected rather than repaired by inference.

### AC-05 Checkpoint evidence is bounded and secret-safe
Checkpoint persistence and operator health evidence reject source bytes, credentials/tokens/headers/cookies/environment, hidden reasoning/scratchpad, arbitrary command/URL payloads and over-bound logs/evidence. Stored JSON and string/list cardinalities have deterministic upper bounds.

### AC-06 Stall classification distinguishes recovery from human authority
The watchdog deterministically distinguishes process loss, test/CI hang, provider outage, dependency wait, rate limit, credential/authorization failure, contention/deadlock, repeated implementation failure and genuine human-required authority/specification boundaries, returning a bounded next recovery action. Ordinary worker loss is not labeled `HUMAN_REQUIRED`.

### AC-07 Recovery and reassignment preserve accepted work
After lease expiry/process loss, a replacement execution resumes from the durable checkpoint/accepted lineage, increments generation before becoming mutation-capable, and uses existing Wave 2 replay semantics so accepted implementation/provider work is not duplicated. A waking stale process cannot race the replacement.

### AC-08 No-progress and oscillation terminate boundedly
Repeated retries without measurable durable state improvement and alternating equivalent failing checkpoints increment protected counters and stop at configured bounds with actionable failure evidence rather than consuming unlimited compute or resetting through fresh worker identities.

### AC-09 Operator health survives process recreation
A newly composed request/process can reconstruct worker lifecycle, lease status/generation, checkpoint revision, current and last-known-good lineage, last meaningful progress, counters, blocker/stall classification, dependencies, next recovery action and human-required status without relying on worker-local memory.

### AC-10 Hosted persistence remains fail-closed
The worker-execution migration creates the required unique/FK/check/index constraints, enables RLS and revokes direct `anon`/`authenticated` privileges. SQLite development compatibility is preserved without runtime implicit production DDL.

### AC-11 Exact-head protected validation and kill proof
The exact P2-V0.16.1 workstream head has authentic committed DSPy critic/compiler evidence and passes Workstream Spec Validation, P2 CI and Bounded Autonomy. Deterministic tests deliberately expire/kill an owner, resume under a replacement generation, reject the stale owner, preserve checkpoint/lineage identity and prove no duplicate accepted mutation/provider publication is introduced by recovery.
