## 1. Objective

Restore the accepted P2-V0.23.3 separation between explicit multi-repository GitHub App installation coverage and exact-one-repository derived runtime credentials across every production build preflight and runtime-readiness check. A production redeploy of P2-V0.23.34 currently fails before application build because `production_provider_preflight.py` requests an installation-wide Vercel Connect token and then correctly rejects that now-two-repository token after the owner explicitly added `Ryan9876/parallax-qa1` to the `github/parallax-runtime` installation. The same unscoped exchange remains in projected-source preflight and `/ready` credential verification.

The correction must request the exact registered repository through Vercel Connect `authorizationDetails`, independently verify that the derived GitHub credential sees exactly that repository, and preserve every existing provider, source, storage, deployment, lifecycle, and human REVIEW boundary. It must not contract the owner-approved installation back to one repository, accept a broad runtime token, introduce a PAT or reusable installation credential, or weaken production preflight.

## 2. Verified root cause and fixed decisions

- Owner-approved installation coverage now includes both `Ryan9876/parallax` and `Ryan9876/parallax-qa1`; this is explicitly permitted by P2-V0.23.3 AC-04.
- Failed production redeploys `dpl_H4W1x1rWFeUQTh129PNbzqTbJijt` and `dpl_Br8NEPp5QiMXVyAXFLjfCUpcRi83` used exact application source `e5504d9e6c78fd8bbbc71609df66c810e2da2707` and failed with `GitHub installation scope is not exactly one repository` before application publication.
- The active P2-V0.23.34 deployment remains READY, so the failed redeploys caused no production cutover or outage.
- Installation coverage and derived-token scope are separate authority layers. Installation coverage may include multiple explicitly approved repositories; each production operation still receives only one exact-repository credential.
- Every Vercel Connect exchange followed by exact-one-repository verification must request the exact canonical registered repository in `authorizationDetails` before accepting the returned token.
- Source-only provider preflight and projected-source preflight request only `contents:read` and `metadata:read` for the exact repository.
- Delivery-permission preflight retains its existing exact repository and minimum `contents:write`, `metadata:read`, and `pull_requests:write` request.
- Runtime `/ready` verification uses the same exact read-scoped credential contract as production source bootstrap; it does not request an installation-wide token or a write-scoped delivery token.
- Exact token scope remains independently verified through GitHub `/installation/repositories` with `total_count == 1`, one returned repository, case-insensitive full-name match, and existing numeric identity checks where already required.
- No new repository coverage, provider, connector, credential, permission, source mutation, Preview, promotion, lifecycle, Git merge, production deployment, or REVIEW-completion authority is added.

## 5. Security and architecture requirements

### 5.1 Installation coverage is not runtime token scope

The explicitly approved GitHub App installation may cover multiple repositories. That standing installation coverage is only the outer consent boundary. Each production preflight/readiness operation must request a short-lived token for exactly one canonical registered repository and the minimum permissions required by that operation.

### 5.2 Exact read-scoped authorization details

Provider/source preflight, projected-source preflight, and runtime credential readiness use one canonical payload:

```json
{
  "subject": {"type": "app"},
  "authorizationDetails": [
    {
      "type": "github_app_installation",
      "repositories": ["<owner>/<repository>"],
      "permissions": ["contents:read", "metadata:read"]
    }
  ]
}
```

Repository identity comes only from the bounded server-owned target registry or canonical Project binding. Caller, model, source, branch content, provider response, and environment values cannot substitute another repository.

### 5.3 Independent scope verification remains mandatory

Connect success alone is insufficient. Before branch, tree, file, or repository reads, GitHub `/installation/repositories?per_page=2` must prove the returned credential sees exactly one repository and that repository matches the requested canonical identity. Broad, empty, mismatched, malformed, unavailable, or unverifiable scope fails closed.

### 5.4 Numeric and source verification remain unchanged

Provider preflight continues to verify the exact registered numeric repository ID, production branch commit identity, recursive source tree, entry modes, paths, file sizes, and protected bounds. Projected-source preflight retains its secret-path exclusions, UTF-8/base64 verification, exact sizes, counts, and aggregate byte bounds. Exact credential scope cannot bypass any source or storage control.

### 5.5 Runtime readiness matches source bootstrap

`verify_registered_runtime_github_credentials()` uses the same read-scoped credential construction as production source bootstrap. Readiness remains read-only and may not gain delivery mutation permissions merely to satisfy exact scope verification. OIDC token validation and result-code sanitization remain unchanged.

### 5.6 Secrets and evidence

OIDC and GitHub bearer values remain transient and never enter logs, errors, committed configuration, Project/run records, client responses, URLs, or authoritative records. Diagnostics may identify the fixed preflight/readiness stage and sanitized provider failure only.

## 6. Reliability and rollback

No database or configuration schema migration is required. The existing server-owned target registry and Vercel/GitHub connector remain authoritative. A failed candidate cannot replace the current READY production deployment.

Rollback returns to exact source `cf18e7ba698f213303d27b2e0c9c819bd17edca0`, which remains operational but cannot be redeployed or pass `/ready` after multi-repository installation coverage because its legacy exchanges request an installation-wide token. Rollback therefore remains viable only as last-known-good runtime preservation; forward correction is required for a fresh qualified production build.

## 7. Acceptance criteria

### AC-01 Production failure evidence is preserved accurately

The workstream records both failed exact-source redeploy identities and the precise fail-closed installation-wide token mismatch without claiming an outage, successful redeploy, or W9-S1 completion.

### AC-02 Provider preflight requests exact read scope

Tests prove `production_provider_preflight.py` sends the exact registered repository and only `contents:read` plus `metadata:read` in Vercel Connect `authorizationDetails` before GitHub reads.

### AC-03 Provider preflight still rejects broad or mismatched tokens

Tests prove a returned credential seeing two repositories, zero repositories, or the wrong repository fails before numeric repository, branch, tree, or Blob verification.

### AC-04 Projected-source preflight requests and verifies exact read scope

Tests prove projected-source Connect exchange uses the same exact read-scoped request and independently rejects broad/mismatched derived credentials before branch/tree/content reads.

### AC-05 Runtime readiness reuses exact read-scoped bootstrap authority

Tests prove `verify_registered_runtime_github_credentials()` requests each registered repository separately with read-only authorization details and accepts only an independently verified exact-one-repository credential.

### AC-06 Multi-repository installation remains compatible and least privileged

Deterministic provider fixtures model an installation covering multiple repositories while returning an exact scoped token per request. Provider preflight, projected-source preflight, and readiness succeed only for the requested target; no credential can read or mutate another covered repository.

### AC-07 Existing delivery mutation scope is unchanged

The exact delivery-permission preflight continues to request only `contents:write`, `metadata:read`, and `pull_requests:write` for one registered repository, with no repository administration, merge, production promotion, domain, environment-variable, or deletion permission.

### AC-08 Existing source/storage and credential boundaries remain green

Focused and full regressions prove numeric repository identity, source path/tree/file/byte bounds, private Blob verification, OIDC validation, secret exclusion, fail-closed provider classification, and no secret persistence remain unchanged.

### AC-09 Exact production deployment becomes READY

After exact-head gates and expected-head merge, the corrected API source reaches production READY with all provider, delivery-permission, projected-source, Blob, lineage, runtime, snapshot, and schema preflights green; `/health` and `/ready` return HTTP 200 and exact-deployment warning/error/fatal scans are clean.

## 9. Risks

- A superficially simple removal of the exact-one-repository check would make the build pass while violating P2-V0.23.3 and expanding runtime authority; this is explicitly prohibited.
- Updating only the first failing preflight would allow publication to reach a later unscoped projected-source or `/ready` failure; all three parity points must be corrected together.
- Reusing write-scoped delivery credentials for readiness would unnecessarily expand read-only health checks; readiness must use the read-scoped bootstrap contract.
- Provider response or GitHub App installation behavior may change independently; exact derived-token verification remains fail-closed and production deployment remains last-known-good until all gates pass.
