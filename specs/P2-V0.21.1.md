## 1. Objective

Remove the hidden manual Vercel-target-registration prerequisite from ordinary Parallax Project builds. A valid active Project bound to an admitted GitHub repository must be able to advance from an approved Build plan through protected source bootstrap, implementation, validation and the existing bounded Preview/REVIEW boundary without an operator separately pre-registering that repository in `PARALLAX_VERCEL_PREVIEW_TARGETS_JSON`.

The production defect motivating this specification is observable on Engineering Run `af617b0b-5297-427c-a40d-90d58f59a20a` for Project `OT Time` / `github:ryan9876/ot-time`: the client correctly requests protected continuation, but the API returns HTTP 503 at delivery composition before PLAN can proceed because the repository has no pre-registered Vercel Preview target. This specification fixes that product/runtime mismatch without weakening Project, source-lineage, provider, validation, Preview or REVIEW authority.

## 2. Fixed decisions

- **PLAN is not a delivery-provisioning gate.** PLAN may depend on protected executor/model/source-context evidence required by its accepted runtime, but it must not fail merely because a Vercel Preview Project has not yet been discovered or provisioned.
- **Canonical Project identity remains authoritative.** Provider readiness starts only from the server-owned active Project and its persisted `repository_ref`. Client input may not nominate a Vercel Project, team, GitHub repository ID, connector, credential, production branch or provider scope.
- **Existing target registrations remain valid.** A repository already represented by the accepted static registry continues to use that exact verified registration. This slice is additive for otherwise-valid Project repositories.
- **Provisioning is exact and minimal.** When no verified target exists, Parallax may discover or create exactly one Vercel Project linked to the canonical GitHub repository under one server-owned admitted provisioning profile. This authority exists only to make the existing Preview-only delivery path usable.
- **Project creation is not deployment authority.** Ensuring a Vercel Project must not create or request a production deployment, promote a deployment, merge source, alter REVIEW, or broaden the existing autonomous Preview ceiling.
- **Existing credentials are reused, not invented.** This slice may reuse the already admitted server-owned Vercel credential reference and request-scoped Vercel Connect/GitHub credential path. It does not create credentials, accept client tokens or add an arbitrary provider endpoint.
- **GitHub identity is independently verified.** Repository full name, numeric repository ID and default production branch are resolved from the exact repository-scoped GitHub credential before a dynamic Vercel target is admitted.
- **Provider discovery/provisioning is replay-safe.** Repeated requests, retries and process recreation converge on one exact Vercel Project for the canonical repository or fail closed on ambiguity. They must not create duplicate Projects.
- **Static configuration cannot silently broaden scope.** A dynamic provisioning profile is server-owned and bounded. If production configuration exposes zero or multiple conflicting provisioning profiles, readiness fails closed rather than guessing.
- **No database migration by default.** Prefer provider-verified discovery and deterministic reconstruction from canonical Project plus server-owned provider configuration. Add persistence only if exact idempotent provider reconciliation cannot be proven without it; any schema change requires a separate migration gate.
- **Plain-language failure is required.** A user who cannot continue because delivery readiness is unavailable receives an actionable nontechnical explanation while bounded technical evidence remains inspectable. The UI must not imply progress that the server did not record.

## 3. Architecture requirements

### 3.1 Lazy delivery-readiness boundary

Move delivery-target readiness out of the unconditional pre-PLAN path. Source-delivery composition and repository bootstrap must be resolved only when canonical execution first requires repository-backed source material, and again when Preview delivery is required after protected validation.

The runtime may introduce one narrow lazy readiness seam or implementation-preparation hook. It must preserve the existing `EngineeringRunService` transition authority and must not create a second lifecycle or client-side state machine.

A PLAN result that passes must be durable even if later repository/Preview readiness fails. A later readiness failure must stop at the appropriate protected boundary with explicit evidence rather than retroactively erasing or fabricating PLAN state.

### 3.2 Server-owned provisioning profile

Dynamic target readiness may use only a server-owned provisioning profile derived from explicit production configuration. The profile must bind:

- one exact Vercel team/account scope;
- one admitted Vercel credential environment reference;
- one admitted Vercel Connect GitHub connector;
- the existing Preview-only provider policy.

If the currently accepted static target registry is used to derive this profile, every registration contributing to the profile must agree on these values. Multiple conflicting profiles are configuration ambiguity and fail closed.

### 3.3 Exact GitHub repository identity

Before dynamic Vercel discovery or creation, Parallax must obtain a repository-scoped GitHub credential through the existing request-scoped Vercel Connect path and verify:

- canonical full repository name equals the Project `repository_ref`, provider-semantically normalized only for comparison;
- GitHub numeric repository ID is positive and exact;
- default branch is a bounded valid branch identity;
- repository installation scope is exactly the canonical repository.

Repository access mismatch, missing source or scope ambiguity fails closed before any Vercel mutation.

### 3.4 Vercel Project discovery

Search only the admitted Vercel team/account and use bounded pagination/result limits. A reusable Project is admitted only when provider read-back proves its Git link resolves to the exact canonical GitHub numeric repository ID and repository identity.

Outcomes are:

- exactly one verified matching Vercel Project — reuse it;
- none — the bounded provisioning operation may create one;
- more than one exact matching Project or any unresolved identity ambiguity — fail closed for operator resolution.

Name matching alone is never sufficient authority.

### 3.5 Bounded Vercel Project creation

When no target exists, a dedicated typed provider action may create one Vercel Project linked to the exact verified GitHub repository. The request must:

- execute only under the admitted server-owned team/account;
- use a deterministic bounded project name derived from canonical Project/repository identity with collision-safe reconciliation;
- link only the exact verified GitHub repository;
- omit any production deployment request;
- avoid arbitrary framework/build/environment configuration unless exact source inspection later proves it is required by the existing Preview delivery contract;
- avoid user-controlled project settings, domains, environment variables, credentials or production target selection.

After creation, Parallax must perform authenticated read-back and verify exact Vercel Project ID/name/team and exact GitHub link identity before admitting it as a delivery target.

### 3.6 No implicit production deployment

Dynamic readiness may create provider Project metadata but cannot create a production deployment. Permanent tests must assert no production-deployment action is invoked. Production qualification must additionally observe that the provisioned test/real Project does not gain a production deployment as a side effect of readiness.

If provider behavior changes such that creating a linked Project automatically creates a production deployment and Parallax cannot suppress or prove absence of that effect, provisioning must fail closed until a separately governed authority decision is made.

### 3.7 Dynamic target construction

A verified discovered/provisioned Project may be converted in memory into the existing `RegisteredProductionDeliveryTarget`/`VercelApiTarget` contract using only server/provider-verified values:

- dynamic target reference derived from exact Vercel Project identity;
- Vercel Project ID/name/team;
- canonical repository ref;
- verified GitHub repository ID;
- verified default production branch;
- server-owned GitHub connector;
- server-owned Vercel credential environment reference.

The existing `RepositoryPreviewTargetResolver`, scoped provider registry, GitHub delivery, Vercel Preview creation/read-back and REVIEW ceiling remain authoritative after target resolution.

### 3.8 Idempotency and concurrency

Readiness must be replay-safe across duplicate requests and process recreation. Before creation, discover by exact repository identity. On provider conflict/race, reconcile by re-reading the admitted team and accepting only one exact verified match.

A retry after successful creation must reuse the same Vercel Project. Concurrent requests must not leave multiple admissible targets; if multiple exact matches become visible, stop with bounded ambiguity rather than choosing one nondeterministically.

No caller-generated idempotency token may redefine canonical Project/provider identity.

### 3.9 Failure evidence and user experience

Provider/configuration failures remain fail-closed and emit bounded non-secret evidence such as normalized error class/result code, Project/run identity, and readiness phase. Never log credentials, OIDC tokens or raw provider responses.

Ordinary product copy should explain outcomes such as “Parallax couldn’t prepare this project for building yet. Your plan and work are still saved. Try again.” Technical details may expose normalized provider/configuration evidence for diagnosis.

A failed readiness attempt must not leave the UI indefinitely implying that work is progressing.

### 3.10 Existing provider and review ceilings

This slice does not authorize:

- production Vercel deployment or promotion;
- GitHub merge, branch protection changes or repository administration;
- Vercel Project deletion, domain management, environment-variable management or arbitrary settings mutation;
- creation/rotation of provider credentials;
- access to repositories outside the canonical Project;
- acceptance of source lineage except through the existing protected lineage gateway;
- bypass of BUILD/TEST/VERIFY;
- autonomous REVIEW completion.

Preview remains the autonomous publication ceiling and REVIEW/HUMAN_REQUIRED remains the human-control ceiling.

### 3.11 Production readiness verification

Production preflight must exercise or deterministically verify both paths:

1. already-registered/discovered target reuse;
2. newly eligible repository target discovery/provisioning and exact read-back without production deployment.

The release must also retry the reported OT Time run or an exact equivalent canonical production fixture and observe durable progression beyond PLAN without `ProductionDeliveryConfigurationError` caused by missing static target registration.

## 6. Security and reliability

All repository/provider identifiers are untrusted until matched against canonical Project and authenticated provider read-back. The provisioning action is a narrow external mutation with explicit audit evidence and exact scope; it cannot be represented as an ordinary read.

The existing request-scoped Vercel OIDC -> Vercel Connect -> repository-scoped GitHub credential path remains the only admitted GitHub credential path for production delivery. The existing server-owned Vercel credential reference remains the only admitted Vercel credential path. Credentials never enter durable evidence or client payloads.

Discovery and creation have strict time/result/page bounds. Provider failures, ambiguous matches, stale identities, scope mismatch, inability to prove no production deployment, or configuration ambiguity stop safely with retryable/actionable evidence. Exact Project/run/spec/source state remains durable and recoverable.

## 7. Acceptance criteria

### AC-01 PLAN no longer depends on Preview target registration
A permanent runtime test proves an approved Project-bound run with no static Preview target can complete protected PLAN without invoking Vercel target discovery/creation or failing on Preview configuration. The resulting PLAN attempt and next canonical state are durable.

### AC-02 Existing registered targets preserve exact behavior
Permanent provider/runtime tests prove repositories already present in the accepted static target registry continue to resolve to the same exact verified target and do not invoke dynamic project creation.

### AC-03 Exact GitHub repository identity and scope are verified
Tests prove dynamic readiness accepts only the canonical Project repository after exact repository-scoped credential verification, numeric GitHub repository ID resolution and default-branch validation. Cross-repository, broader installation scope, stale/missing repository and identity mismatch all fail before Vercel mutation.

### AC-04 Existing Vercel target discovery is exact and bounded
Tests prove bounded discovery reuses exactly one Vercel Project whose authenticated Git link matches the canonical numeric GitHub repository ID. Name-only matches, wrong-team targets and duplicate exact matches are rejected.

### AC-05 Missing target is provisioned exactly once and replay safely
Tests prove zero matching target permits one bounded Vercel Project creation linked to the exact canonical repository; authenticated read-back verifies the created identity; replay/process recreation reuses it; simulated concurrent conflict reconciles to one exact target without duplicate admissible Projects.

### AC-06 Provisioning cannot create or promote production deployment
Provider-contract tests prove readiness invokes no production-deployment/promotion operation, includes no production target in project-creation authority, and cannot call existing production promotion surfaces. Production qualification observes no production deployment side effect for the newly readied Project.

### AC-07 Existing protected source and Preview delivery remain authoritative
After readiness, repository bootstrap, safe implementation, accepted source lineage, BUILD/TEST/VERIFY, GitHub branch/commit/PR and Vercel Preview use the existing protected contracts and exact identities. The dynamically resolved target cannot bypass lineage acceptance or alter the Preview-only deployment ceiling.

### AC-08 Configuration and provider ambiguity fail closed without losing work
Tests cover missing/ambiguous provisioning profile, provider auth denial, unavailable provider, repository mismatch, Vercel duplicate match and read-back mismatch. Each failure preserves canonical Project/spec/run truth, does not fabricate stage progress, and remains retryable where safe.

### AC-09 User-facing failure is actionable and technical evidence is secondary
When readiness cannot complete, the ordinary client explains in plain language that Parallax could not prepare the Project and that saved work remains intact, exposes an appropriate retry/continue action when server state permits, and keeps normalized technical evidence behind the technical-detail surface. Mobile touch/accessibility rules remain satisfied.

### AC-10 Production defect is proven fixed with full regression evidence
The exact release candidate passes focused W8-S2 tests, provider/source-lineage/agentic-runtime regressions, API contract tests, client state/type/export and applicable browser/Skia acceptance, protected promotion/regression rejection, authentic DSPy validation and Bounded Autonomy Pilot. Production verification proves the reported OT Time path or an exact equivalent new repository-bound Project advances beyond PLAN without the missing-static-target `ProductionDeliveryConfigurationError`, while production deployment/merge/REVIEW authority remains unchanged.
