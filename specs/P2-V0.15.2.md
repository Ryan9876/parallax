# Parallax 2.0 — Protected Project Workspace Lineage

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.15.2
Workstream: WS-APP-WORKSPACE-LINEAGE / GitHub issue #60
Depends on: canonical Project/run identity from Wave 2 project binding #59 during serialized integration
Method: additive protected source-lineage contract with content-addressed snapshots and server-owned materialization

## 1. Objective

Create a protected source-workspace lineage boundary that lets Parallax carry the exact accepted source tree from initialization through IMPLEMENT, BUILD, TEST and VERIFY without ever treating `Project.workspace_ref`, model output, caller input, repository URLs, or other user-controlled values as filesystem authority.

The accepted source tree must remain reconstructable after retries, resumes, live-workspace cleanup, or process restarts. Every accepted initialization and implementation result is represented by immutable bounded lineage evidence derived from the exact source content.

## 2. Fixed decisions

- Canonical Project and Engineering Run identities are opaque UUID identities supplied by protected runtime integration; they are not filesystem paths.
- Filesystem roots are generated only beneath a server-configured protected allocator root.
- Accepted source versions are represented by immutable content-addressed snapshots, not by the continued existence of a mutable working directory.
- Repository or starter initialization is mediated only by an injected trusted `SourceProvider` seam that receives canonical protected identity and returns bounded source bytes plus bounded provenance metadata. It does not accept caller URLs, commands, credentials, generic HTTP requests, or arbitrary bootstrap scripts.
- This workstream adds no shared database fields and does not edit #59 persistence/schema ownership.

## 3. Architecture requirements

Separate immutable lineage storage from live-workspace allocation. The lineage store validates canonical identity, normalizes and bounds source paths, stores content-addressed blobs, records immutable manifests, tracks one protected current lineage per Project/run pair, detects stale lineage, and reconstructs exact source content. The allocator materializes a requested accepted lineage only under its server-owned root, returns an internal workspace lease, validates that lease before accepting source mutation, and deletes only materialized workspaces during cleanup.

Lineage identity must bind canonical Project ID, run ID, parent lineage, exact content digest, bounded source kind/provenance digest, file count and total bytes. A different source tree, different Project/run identity, modified manifest, or modified blob must not validate as the accepted lineage.

## 4. Scope

- Add canonical `ProjectRunIdentity` validation for protected UUID Project/run identifiers while explicitly rejecting `project:<id>` and other opaque references as execution paths.
- Add a bounded trusted `SourceProvider` protocol and immutable source-package contract for repository/template/starter initialization.
- Add a content-addressed lineage store using immutable manifests and SHA-256-addressed source blobs under a server-owned state root.
- Normalize relative POSIX source paths and reject traversal, absolute paths, backslashes, NULs, `.git`, secret-sensitive paths, duplicate normalized paths, symlinks, special files and over-bound source trees.
- Support binary and text source bytes so later BUILD/TEST/VERIFY can reconstruct the exact accepted tree rather than only patchable text files.
- Compute deterministic content digests from sorted file path/digest/size evidence.
- Compute immutable lineage IDs from canonical Project/run identity, parent lineage, content digest, bounded provenance digest, source kind, file count and total bytes.
- Persist a protected current-lineage pointer per canonical Project/run identity outside the shared relational schema.
- Initialize a run idempotently when the same trusted source is retried; reject reinitialization with different source after lineage exists.
- Record an accepted implementation result only when its expected parent is current and content actually changed.
- Make retry of an already-recorded identical implementation result idempotent while rejecting stale or mismatched source content.
- Resolve and verify historical accepted lineage independently of the current pointer.
- Materialize any verified accepted lineage into a fresh isolated server-owned workspace for later BUILD/TEST/VERIFY.
- Cleanup a materialized workspace without deleting immutable lineage manifests, source blobs or current-lineage evidence.
- Emit bounded lineage evidence containing canonical IDs, lineage/content digests, file counts/sizes, source kind and provenance digest only; raw provider state, credentials and source contents are not emitted as evidence.

## 5. Security

The allocator root and lineage store root are server configuration, not request parameters.

- Caller/model content cannot choose an absolute or relative filesystem root.
- `Project.workspace_ref = project:<id>` remains opaque identity metadata and is rejected by canonical Project/run identity parsing.
- Project/run identifiers must be canonical UUID strings; filesystem storage uses derived server-side hashes rather than raw identity text.
- Source paths reject absolute paths, traversal, empty or dot components, backslashes, NULs, Git internals and secret-sensitive targets.
- Provider packages and scanned workspaces are bounded by file count, per-file bytes, aggregate bytes and bounded provenance metadata.
- Symlinks and non-regular filesystem objects fail closed during source capture.
- Blob contents are SHA-256 verified before use; manifest identity is recomputed before resolution; reconstructed content is rescanned and must match the recorded content digest.
- Stale parent lineage fails closed unless the request is an exact idempotent retry of the already-accepted child lineage.
- A source tree that does not change cannot manufacture a new implementation lineage.
- No shell, Git command, arbitrary HTTP, provider credential, generic tool, protected-stage self-approval, Vercel mutation or production deployment authority is added.

## 6. Non-goals

- Project/conversation/Engineering Run schema changes owned by #59.
- Interpreting `workspace_ref` as a path or adding filesystem authority to Project records.
- Model-generated patch proposals or changes to the safe patch engine.
- Wiring protected IMPLEMENT stage orchestration; #61 owns runtime orchestration.
- Concrete GitHub/Vercel/provider authority adapters; #62 owns those integrations.
- Arbitrary bootstrap commands, package installation, shell execution or repository mutation.
- Long-lived mutable directories as the durable source identity.
- Production deployment or authoritative record updates before integration.

## 7. Acceptance criteria

### AC-01 Canonical identity confinement
The lineage boundary accepts only canonical UUID Project and Engineering Run identifiers. `project:<id>`, paths, URLs, blank values and malformed UUIDs are rejected, and filesystem storage locations are derived server-side rather than from raw Project/run text.

### AC-02 Server-owned workspace allocation
All live source workspaces are created beneath one server-configured allocator root using server-generated lease identities. The initialization, resolve/reconstruct and implementation-acceptance interfaces expose no caller-controlled filesystem-root parameter, and forged/out-of-root workspace leases fail closed.

### AC-03 Immutable content-addressed lineage
Initialization and each accepted implementation mutation produce immutable lineage evidence derived from the exact sorted source tree, canonical Project/run identity, parent lineage and bounded provenance. Equivalent accepted inputs are deterministic, while a different tree or different identity produces a different content/lineage identity and cannot be mislabeled as the accepted lineage.

### AC-04 Trusted source-provider seam
Repository/template/starter initialization occurs only through an injected trusted source provider that receives canonical Project/run identity. The public lineage contract accepts no raw repository URL, generic HTTP request, provider credential, shell command, Git command or arbitrary bootstrap command; provider source paths/content are normalized and bounded before persistence.

### AC-05 Stale-lineage denial and idempotent retry
A new implementation lineage may advance only from the current expected parent and must contain an actual source change. Repeating an already-recorded identical implementation result with the same expected parent returns the accepted child lineage idempotently, while a different tree, wrong parent, wrong Project/run identity or stale lineage is rejected without changing the protected current pointer.

### AC-06 Exact historical reconstruction and integrity
Any accepted lineage can be resolved after later mutations and reconstructed into a fresh isolated workspace whose rescanned content digest exactly matches the recorded snapshot. Manifest tampering, blob tampering, missing blobs, identity mismatch or attempts to substitute different content fail integrity validation.

### AC-07 Cleanup and expiry safety
Deleting or expiring a materialized live workspace removes only that server-owned lease. Immutable manifests, content-addressed blobs and protected current-lineage evidence remain available so BUILD/TEST/VERIFY, retry or resume can reconstruct and prove the accepted source version after cleanup.

### AC-08 Bounded evidence and resource behavior
Source capture enforces explicit maximum file count, per-file bytes and aggregate bytes. Lineage evidence contains bounded canonical identifiers, lineage/content digests, file counts/sizes, source kind and a digest of bounded provenance; it does not expose raw source contents, provider credentials, repository state, secret files or unbounded metadata.

### AC-09 No execution or release authority expansion
The new modules expose no user/model-supplied shell, arbitrary HTTP/network, Git history mutation, dependency installation, provider secret handling, Work Specification self-approval, protected-stage success override, Vercel promotion or production deployment operation.

### AC-10 Integration-ready Wave 2 contract
The worker candidate remains additive to `code/`, tests and `P2-V0.15.2` artifacts, does not edit #59 shared schema/persistence or #61 orchestration paths, and provides a protected source-lineage interface that serialized integration can bind to #59 canonical `project_id`/run identity and #61 IMPLEMENT→BUILD→TEST→VERIFY orchestration without reinterpreting `workspace_ref` as a path.

## 8. Risks

- **Filesystem tampering:** immutable snapshot files could be modified outside the process. Mitigation: recompute manifest identity and blob digests whenever lineage is resolved/materialized and rescan reconstructed source.
- **Concurrent run advancement:** two workers could attempt to advance the same run lineage. Mitigation: this worker uses atomic pointer replacement and exact expected-parent checks; serialized runtime integration must retain one protected run owner or add stronger cross-process locking if concurrent mutation is introduced.
- **Snapshot storage growth:** immutable source versions consume durable storage. Mitigation: enforce strict per-snapshot resource limits and keep cleanup policy for live workspaces separate from later garbage-collection policy for snapshots; accepted lineage must never be garbage-collected while still referenced by protected evidence.
- **Provider trust boundary:** a source adapter could return unsafe paths or oversized content. Mitigation: treat provider output as untrusted bytes and fully normalize/bound it before storage; concrete provider authority remains #62.
- **Wave 2 identity drift:** #59 may refine how canonical Project/run identity reaches orchestration. Mitigation: use only canonical UUID-shaped identity in this standalone contract and leave persistence binding to serialized integration.
