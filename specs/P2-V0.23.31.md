## 1. Objective

Stop serial production fault discovery in the Engineering Run CREATE path by replacing repeated source-shape validation inference with an explicit server-owned execution contract bound during protected PLAN, and by adding a deterministic end-to-end acceptance replay that must prove real disposable candidate BUILD/TEST/VERIFY on the exact production release before another signed-in retry is requested.

On exact P2-V0.23.30 production deployment `dpl_Gygn6JBjVdPhbSkLvSKvuXrh7SGm`, the signed-in retry of Engineering Run `3a1ba66a-5649-42b6-81ee-91684fe06bbc` resumed successfully. Source-lineage reads succeeded; a real Vercel sandbox was created and executed on the refreshed PLAN path; Luna and Terra completed during IMPLEMENT; and candidate admission then failed at `DISPOSABLE_CANDIDATE_VALIDATION` with bounded server diagnostic `VALIDATION_PROFILE_ERROR`. P2-V0.23.30 correctly prevented candidate-mutated source from switching validation authority, but the pinned profile was still inferred from accepted repository shape at candidate time. The current greenfield accepted workspace has no admitted source marker from which that legacy inference can select a profile.

The underlying product contract is therefore incomplete: Parallax knows the intended application before generating source, but the runtime does not persist a protected statement of how that application is to be built and verified. P2-V0.23.31 makes that statement explicit and makes release validation exercise the same real sandbox boundary before involving the user.

## 2. Fixed decisions

- Protected PLAN binds one immutable server-owned execution contract to the exact work specification and accepted source lineage before IMPLEMENT generation.
- The execution contract references only a closed server-owned catalog of validation profiles and commands. User text, model output and repository scripts never become executable command text.
- The contract is persisted in successful agentic PLAN evidence and is verified against exact Project/run/work-specification/source-lineage identity before IMPLEMENT uses it.
- Existing recognized Parallax Python and bounded root .NET repositories may be classified once during PLAN and then bound. Candidate validation must not re-infer the profile from source thereafter.
- A greenfield workspace with no ecosystem markers binds to a dedicated `static-web-v1` execution contract. This is a narrow greenfield capability, not generic Node package-script admission.
- `static-web-v1` runs a server-owned validator from outside candidate source using the already released common Python/Node execution snapshot. Candidate source cannot edit the validator or command text.
- The static-web validator requires a root `index.html`, validates local HTML references, and performs JavaScript syntax checks without executing repository package scripts or arbitrary shell.
- Ambiguous or unsupported existing-source shapes remain fail-closed with fixed sanitized reason codes.
- Candidate admission diagnostics may expose only fixed server-owned reason codes and existing bounded false-authority claims; exception text, source content and filesystem roots remain excluded.
- Production Vercel build promotion gains a deterministic static-web candidate-validation canary that invokes the same `VercelCandidateValidationExecutor` and real disposable sandbox BUILD/TEST/VERIFY path used by production candidate admission.
- The canary is non-mutating with respect to Projects, Engineering Runs and canonical source lineage. It validates an immutable repository QA fixture only.
- A production release must fail closed if the exact release cannot complete all three canary stages. Do not request another signed-in user retry until this release canary is green.
- Existing SafeImplementationEngine, dependency preparation, deny-all validation networking, execution-snapshot identity, independent evaluation, source lineage, Git/deployment/lifecycle authority, model roster, retry/timeout ceilings and human REVIEW boundary remain unchanged.
- Architecture advances to v3.42 because execution-policy binding and production acceptance gating become durable runtime contracts.

## 5. Architecture requirements

### 5.1 Closed execution-contract catalog

An immutable `ExecutionContract` is server-owned and identifies a closed catalog entry plus its exact immutable `ValidationProfile`. Its digest covers contract ID/version, profile ID/digest and binding mode. Resolving a persisted contract ID must never consult candidate source or arbitrary strings to construct commands.

The initial catalog contains:

- the established Parallax Python profile;
- the established bounded .NET profile with a target path selected from accepted source during PLAN;
- `static-web-v1`, backed by the existing common execution snapshot and a server-owned static validator.

Node package scripts are not admitted by this release.

### 5.2 PLAN-time binding

Protected agentic PLAN materializes the exact current accepted source lineage, selects one execution contract and records at minimum:

- `execution_contract_id`;
- `execution_contract_digest`;
- `validation_profile_id`;
- `validation_profile_digest`;
- a fixed binding reason code.

The materialized workspace is cleaned up through the durable allocator after binding. PLAN evidence remains tied to the already persisted source-lineage ID/content digest and work-specification identity.

For an accepted workspace with no recognized ecosystem markers, bind `static-web-v1`. This is the greenfield default because there is no pre-existing runtime ecosystem to preserve. If accepted source contains ambiguous or unsupported ecosystem markers, fail closed rather than silently treating it as greenfield.

### 5.3 IMPLEMENT verification

Before source generation/candidate validation, IMPLEMENT verifies the successful PLAN evidence including execution-contract fields. It resolves the contract only from the closed server catalog plus any already-bound safe target metadata and confirms the recomputed contract/profile digests. Candidate source cannot influence this resolution.

`AgenticControlPlane._candidate_validation()` receives the verified `ExecutionContract`/`ValidationProfile`; it must not call source-shape selection.

### 5.4 Static-web protected validator

The static-web profile uses server-owned BUILD/TEST/VERIFY commands whose executable/arguments are constants released with Parallax. The validator itself is copied into the sandbox outside `/vercel/sandbox` and therefore outside candidate bytes/digests.

The validator must:

- require a regular root `index.html`;
- reject symlinks/special files/path traversal within the validated source walk;
- parse HTML with the Python standard library;
- treat external/fragment/data/mail/tel references as non-local and never fetch them;
- require local referenced files to resolve within source root and exist;
- syntax-check local `.js`, `.mjs` and `.cjs` files through direct `node --check` subprocess invocation with no shell;
- perform no network calls;
- execute no repository package scripts;
- return deterministic non-zero exit status on validation failure.

BUILD establishes root structure and JavaScript syntax. TEST establishes local reference integrity and syntax. VERIFY repeats the complete deterministic contract.

### 5.5 Fixed diagnostics

`ValidationProfileError` carries a closed server-owned reason code rather than relying on exception text. Candidate-admission diagnostics may expose `failure_kind=VALIDATION_PROFILE_ERROR` and a fixed `reason_code` selected from the closed vocabulary, including at least:

- `UNSUPPORTED_VALIDATION_ECOSYSTEM`;
- `AMBIGUOUS_VALIDATION_ECOSYSTEM`;
- `AMBIGUOUS_DOTNET_TARGET`;
- `PYTHON_FIXED_VALIDATION_UNAVAILABLE`;
- `NODE_FIXED_VALIDATION_UNAVAILABLE`;
- `EXECUTION_CONTRACT_DRIFT`;
- `EXECUTION_CONTRACT_UNAVAILABLE`;
- `EXECUTION_SNAPSHOT_UNAVAILABLE`.

Raw exception text remains excluded from durable and operational diagnostics.

### 5.6 End-to-end production canary

An immutable static-web fixture is stored under API test fixtures. The production build canary constructs the catalog `static-web-v1` contract, invokes the same production `VercelCandidateValidationExecutor.validate_candidate()` with the fixture, and requires BUILD, TEST and VERIFY evidence to all report `protected_success=true`.

The canary must use the exact production Vercel project identity, released execution snapshot and sandbox SDK/session. It must not create or mutate application database rows, canonical source lineage, Git state, delivery state or REVIEW state.

The production `vercel_build.py` must execute this canary after execution-snapshot preflight and before publication can succeed. Preview/non-production builds may skip it explicitly.

## 6. Security

This release contracts execution authority. The AI may produce source, but it cannot choose executable command text, package scripts, execution snapshots, network policy or validation profile after PLAN binding. The static-web validator is server-owned code outside the candidate source root, so candidate changes cannot replace their own judge.

The canary uses the same deny-all sandbox and no application environment. It proves released infrastructure and protected commands work together without granting the fixture or user any production mutation authority.

## 7. Reliability and migration

No database migration is required. The execution contract is run-scoped and belongs in successful PLAN evidence, which is already authoritative for IMPLEMENT orchestration and already bound to the exact work specification and source lineage. This avoids creating a second project-level execution-policy state machine.

Existing successful in-flight PLAN evidence from an older agentic runtime is not silently upgraded. The existing failed-IMPLEMENT plan-refresh path re-runs protected PLAN and binds the new execution contract before another IMPLEMENT attempt. New runs bind the contract on their first protected PLAN.

Existing recognized Python/.NET projects retain their released toolchains. Greenfield runs stop depending on source markers that cannot exist before generation. Unsupported/ambiguous existing-source projects fail earlier in PLAN with a fixed reason instead of failing after model generation.

### AC-02 Execution contract is bound before IMPLEMENT

### AC-03 Greenfield binds static web without source markers

### AC-04 Existing-source compatibility remains fail-closed
Established Parallax Python and bounded .NET source bind their existing profiles; ambiguous/unsupported/generic unadmitted shapes fail with fixed reason codes rather than falling back to static web.

### AC-05 IMPLEMENT consumes only verified bound contract
Candidate validation receives the PLAN-bound profile and performs no candidate-time or accepted-source re-inference after PLAN. Contract ID/digest/profile drift fails closed before model-authored candidate authority can affect validation.

### AC-06 Static-web validator is source-independent and bounded
Focused tests prove root index requirement, local-reference integrity, JavaScript syntax checks, traversal/symlink rejection and absence of repository package-script execution or network fetching.

### AC-07 Diagnostics are fixed and sanitized
Profile/contract/snapshot failures project fixed `reason_code` values without exception text, source content, generated content, filesystem roots, provider payloads or credentials.

### AC-08 Real disposable canary reaches BUILD/TEST/VERIFY
The exact production release runs the immutable QA fixture through `VercelCandidateValidationExecutor` in a real Vercel sandbox and records BUILD, TEST and VERIFY as protected successes. Production publication fails if this canary fails.

### AC-09 Canary cannot claim production mutation authority
Tests and implementation inspection prove the canary does not create/mutate Projects, Engineering Runs, source lineage, Git/delivery/lifecycle or REVIEW state and cannot be used as authenticated real-path acceptance.

### AC-10 Existing authority ceilings remain unchanged
SafeImplementationEngine, dependency preparation, deny-all validation network, execution snapshots, independent evaluation, source lineage, Git/deployment/lifecycle authority, Luna/Terra/Sol order, 60-second hosted timeout, zero hidden retries, recovery ceilings and human REVIEW are unchanged.

### AC-11 Protected release gates pass
Spec/DSPy evidence, focused regressions, full API regression, applicable client checks, protected promotion evaluation, Bounded Autonomy, Workstream Spec Validation and exact-head PR gates are green.

### AC-12 Exact production deployment is healthy and canary-proven
The exact merged application source reaches READY only after the real candidate canary passes; `/health` and `/ready` return HTTP 200 and exact-deployment runtime verification is clean.
