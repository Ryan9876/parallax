## 1. Objective

Add the bounded autonomous correction controller that turns reproducible implementation, BUILD/TEST/VERIFY, browser, screenshot, visual and provider failure evidence into typed repair attempts. The controller repeatedly diagnoses, proposes a bounded correction, re-enters the existing protected source-mutation and validation path, and converges toward acceptance while preserving last-known-good lineage and explicit human/resource boundaries.

The controller must make ordinary defects self-correcting without creating a second source authority, evaluator, worker identity or provider path. It may decide what defect to address and propose source changes, but it cannot directly mutate source, alter protected acceptance/evaluator policy, expand tool/provider/network authority or promote to production.

## 2. Scope

- Normalize bounded failure evidence from IMPLEMENT generation/mutation, BUILD/TEST/VERIFY, protected browser validation, screenshot regression, multimodal review and bounded provider operations into one deterministic defect contract.
- Preserve evidence source/provenance, Project/run/Work-Spec/source-lineage/Preview identity, severity, reproducibility, protected precedence and bounded evidence references without copying raw logs, DOM, screenshots, provider responses, secrets or hidden reasoning.
- Add a protected correction-planning protocol that consumes only the bounded defect set, approved Work Specification identity, source-lineage identity and bounded source context. It returns typed source patch proposals and explicit target defect IDs but receives no filesystem, shell, HTTP, provider, evaluator or deployment authority.
- Route every accepted correction proposal through an injected protected mutation runtime that must return a new accepted source-lineage receipt or fail closed. The controller cannot write source directly.
- Re-run protected validation after every accepted correction lineage. The correction loop must never reuse stale validation evidence as proof for a new source lineage.
- Preserve one explicit last-known-good (LKG) source-lineage identity. A candidate only replaces LKG when its protected quality vector strictly improves under the precedence defined below and the candidate introduces no higher-precedence regression.
- Enforce bounded attempt, cumulative source churn, runtime/elapsed, compute-unit, repeated-defect, no-progress and oscillation budgets.
- Detect repeated identical defect sets, alternating equivalent failing states and candidate/defect fingerprints already observed in the bounded session history.
- Return explicit stop reasons for human authority/specification boundaries, missing non-refreshable credential/authorization, privileged/destructive work, unrecoverable bounded failure, resource exhaustion, repeated defect, no progress and oscillation.
- Produce a bounded failure-dispatch record for reproducible integration failures that another workstream can consume. Dispatch records bind canonical evidence/dependencies but do not autonomously create GitHub issues, broaden ownership or grant implementation authority.
- Integrate with P2-V0.16.1 worker checkpoints so process recreation retains current source lineage, LKG identity, bounded evidence references, blocker code and convergence counters without creating a competing worker execution identity.
- Consume P2-V0.16.2 `ProtectedBrowserValidationResult` directly as the browser/visual evidence boundary; do not rerun or reinterpret browser internals inside this workstream.

## 3. Fixed decisions

- Deterministic failures outrank protected acceptance failures; protected acceptance outranks screenshot-regression failure; screenshot regression outranks multimodal visual judgment. Lower-precedence improvement cannot compensate for a new higher-precedence regression.
- The controller uses a lexicographic protected quality vector. A correction is progress only when that vector strictly improves compared with the current accepted candidate.
- A candidate with a new deterministic failure is rejected even if screenshots or multimodal output improve.
- Multimodal `PASS` never converts deterministic, protected-acceptance or screenshot-regression failure into success.
- LKG means the best accepted source lineage observed by this bounded correction session under the protected quality vector. It is source identity, not a mutable workspace path.
- Every source change must return through the existing safe mutation and immutable source-lineage acceptance boundary. The controller never gains direct filesystem or Git/provider mutation access.
- Evaluation thresholds, acceptance criteria, Work Specification content, provider targets, browser workflows/baselines, tool capabilities and production authority are immutable inputs for one correction session.
- A human/resource boundary ends the autonomous loop; it is never represented as ordinary failure that can be patched around.
- Failure dispatch is data, not authority. The receiving scheduler/integration layer decides whether and where to create future work.

## 4. Architecture requirements

### 4.1 Canonical correction session identity

A correction session is bound to:

- canonical `project_id`;
- Engineering `run_id`;
- approved `work_specification_id`, revision and digest;
- immutable compiled-plan reference;
- initial accepted source-lineage identity;
- optional initial LKG lineage identity;
- server-owned correction budget policy.

Caller/model input cannot replace those identities after session construction.

### 4.2 Normalized defect evidence

Each normalized defect contains only bounded typed data:

- stable defect ID/fingerprint;
- source category (`IMPLEMENT`, `BUILD`, `TEST`, `VERIFY`, `BROWSER_DETERMINISTIC`, `SCREENSHOT_REGRESSION`, `VISUAL`, `PROVIDER`);
- protected precedence class;
- normalized failure code;
- severity and reproducibility flag;
- current source-lineage identity and optional Preview identity;
- bounded source/evidence reference(s) and optional source path/semantic locator where already protected;
- whether the defect itself represents a human/resource boundary.

Raw stdout/stderr streams, raw DOM, screenshot bytes, provider payloads, headers/cookies/environment, credentials, arbitrary URLs, hidden reasoning and unrelated Project data are forbidden.

### 4.3 Protected quality vector

A candidate validation result projects to a deterministic vector in this exact order:

1. deterministic failure count;
2. protected acceptance failure count;
3. screenshot-regression failure count;
4. multimodal FAIL count;
5. multimodal REVIEW count.

`(0,0,0,0,0)` is protected success. Candidate B is an improvement over candidate A only when B's vector is lexicographically lower. Equal vectors are no progress. The controller may use bounded tie-break metadata for diagnosis but may not redefine this protected ordering.

### 4.4 Correction planning and mutation separation

The correction planner receives the canonical session context, current candidate lineage, normalized defect evidence and bounded source context. It returns a typed plan containing:

- plan ID/digest;
- exact target defect IDs;
- one or more bounded source patch proposals with relative path, expected base digest and supported unified diff;
- bounded expected churn/compute estimates;
- optional explicit stop boundary when correction requires authority unavailable to the planner.

The planner cannot supply commands, shell, arbitrary executable code, generic HTTP requests, provider targets, credentials, environment values, evaluator thresholds, baseline mutations or acceptance changes.

The controller passes a valid plan to a separate `CorrectionMutationRuntime` interface. Only that protected runtime may accept source mutation and return a new immutable lineage identity. Replaying the same correction operation key must not create duplicate mutation.

### 4.5 LKG and regression handling

The controller tracks current candidate lineage and LKG independently.

- Initial LKG may be absent if no candidate has passed any protected validation yet.
- A new candidate becomes LKG only after fresh validation proves a strictly better quality vector than the current LKG.
- A candidate that is equal or worse is rejected as progress and cannot replace LKG.
- A higher-precedence regression forces rollback preference to the retained LKG for the next correction decision.
- LKG identity is recorded in the P2-V0.16.1 worker checkpoint and survives process recreation.

### 4.6 Convergence budgets

Server-owned policy bounds at least:

- maximum correction attempts;
- maximum cumulative changed bytes/churn;
- maximum cumulative compute units;
- maximum elapsed correction runtime;
- maximum consecutive no-progress attempts;
- maximum repeats of the same normalized defect fingerprint;
- maximum oscillations between previously observed equivalent failing states.

Exceeding any bound stops autonomously with an explicit normalized stop reason. The controller never increases its own budget.

### 4.7 Failure dispatch

A bounded dispatch record contains:

- canonical Project/run/Work-Spec identity;
- source and LKG lineage identities;
- failure/defect fingerprint;
- bounded evidence refs;
- bounded dependency refs;
- proposed receiving capability/workstream class;
- stop reason and reproducibility classification.

Dispatch cannot contain secrets, hidden reasoning, raw logs/provider payloads or mutable ownership assertions. Dispatch does not create/merge/deploy anything by itself.

### 4.8 Worker recovery integration

Correction uses the existing P2-V0.16.1 worker lease/checkpoint execution identity. It may record current correction step, accepted source lineage, LKG lineage, evidence refs, dependencies and blocker/stop code through the worker checkpoint API. It must not create a second worker table, lease owner or recovery state machine.

Worker-level retry/no-progress/oscillation controls remain authoritative outer bounds. Correction-specific counters may be stricter but cannot weaken worker recovery limits.

## 5. Stop boundaries

The controller stops with a typed reason rather than attempting a patch when evidence proves any of the following:

- explicit human approval is required;
- destructive or privileged action is required;
- material Work Specification ambiguity prevents a bounded repair;
- credential/authorization is missing and cannot be refreshed within existing authority;
- evaluator/acceptance/baseline/provider-target change would be required to pass;
- the failure is unrecoverable within supported safe mutation semantics;
- a correction budget is exhausted;
- the same defect exceeds the repeat bound;
- no protected quality progress exceeds the configured bound;
- an equivalent failing-state oscillation exceeds the configured bound.

Refreshable transient credentials, rate limits and provider outages remain recoverable worker/runtime concerns and do not authorize source changes solely to bypass the external failure.

## 6. Reference harness

Permanent deterministic tests must prove at least:

- normalization of IMPLEMENT/BUILD/TEST/VERIFY/browser/screenshot/visual/provider defects;
- deterministic failure precedence over all lower evidence;
- protected acceptance precedence over screenshot/multimodal evidence;
- screenshot-regression precedence over multimodal evidence;
- successful multi-attempt convergence from failing source to protected PASS;
- LKG retention when a repair regresses;
- rejection of an equal-quality/no-progress candidate;
- repeated-defect stop;
- A/B/A or equivalent oscillation stop;
- cumulative churn, compute and attempt budget exhaustion;
- human/spec/privilege/credential boundary stop;
- process recreation from durable checkpoint/ledger state without duplicate mutation;
- failure dispatch with exact canonical evidence/dependency binding;
- inability of planner output to alter acceptance, evaluator, baseline, provider, network or production authority.

## 7. Non-goals

- browser execution, accessibility engine, screenshot capture or multimodal model implementation;
- worker lease persistence or reassignment state-machine implementation;
- critical-path scheduling/work stealing or global worker allocation;
- direct GitHub issue/workstream mutation from correction output;
- automatic baseline updates;
- Work Specification amendment/approval;
- production merge/deployment/promotion autonomy;
- generic shell, HTTP, filesystem or provider authority for the planner/controller.

## 8. Acceptance criteria

### AC-01 Failure evidence is normalized, bounded and provenance-safe
IMPLEMENT, BUILD/TEST/VERIFY, browser deterministic, screenshot, visual and provider failures normalize into stable bounded defect evidence tied to the exact Project/run/Work-Spec/source-lineage/Preview facts where applicable. Raw unbounded logs/DOM/images/provider payloads, secrets, hidden reasoning and unrelated Project data are rejected.

### AC-02 Protected evidence precedence cannot be weakened
The controller uses deterministic failure > protected acceptance > screenshot regression > multimodal judgment precedence. Lower-precedence improvement cannot compensate for a new higher-precedence failure, and multimodal PASS cannot override deterministic/protected/screenshot failure.

### AC-03 Correction planning is typed and has no mutation or policy authority
Planner output identifies exact target defects and bounded source patch proposals but exposes no direct filesystem/shell/HTTP/provider/deployment capability and cannot change Work Specification acceptance, evaluator thresholds, browser baselines/workflows, tool authority or provider targets.

### AC-04 Every correction re-enters protected source mutation and fresh validation
The controller can only advance through a protected mutation runtime that returns a new immutable accepted lineage. Every new lineage receives fresh protected validation; stale evidence from a prior lineage cannot satisfy the candidate.

### AC-05 Last-known-good lineage is preserved and only advances on strict protected improvement
LKG survives failed/regressive repair attempts and process recreation. A candidate replaces LKG only when its protected quality vector is lexicographically better. Equal/worse candidates cannot overwrite LKG.

### AC-06 Bounded convergence budgets stop runaway correction
Attempt, cumulative churn, compute, elapsed runtime, repeated-defect, no-progress and oscillation limits are server-owned, finite and enforced. The model/controller cannot increase them, and exhaustion returns a typed stop reason without further mutation.

### AC-07 Repeated defects and oscillation are detected deterministically
Repeated equivalent defect fingerprints and alternating previously observed failing states are identified from bounded canonical fingerprints. The reference harness proves same-defect repetition and A/B/A-style oscillation stop before unbounded repair churn.

### AC-08 Human, privileged, specification and credential boundaries fail closed
Explicit approval, destructive/privileged work, material specification ambiguity and non-refreshable missing credential/authorization stop with typed human/resource reasons. The controller does not patch around these boundaries or misrepresent them as passing validation.

### AC-09 Failure dispatch is canonical data without autonomous ownership expansion
Reproducible bounded failures can produce a dispatch record with exact Project/run/spec/lineage/LKG/evidence/dependency binding and receiving workstream class. Dispatch itself creates no GitHub issue, source mutation, provider mutation, ownership grant or production action.

### AC-10 P2-V0.16.1 worker recovery identity remains authoritative
Correction checkpoints reuse the accepted worker execution/lease/checkpoint contract, retain current and LKG lineage plus bounded evidence/stop metadata, and do not create a competing recovery identity. Existing worker retry/no-progress/oscillation bounds remain outer authority.

### AC-11 Replay/process recreation does not duplicate mutation or lose convergence state
Reconstructing the controller from durable run/checkpoint/correction evidence resumes the same bounded session, retains LKG/budget/fingerprint state and replays accepted operation keys without creating duplicate source mutation or provider publication.

### AC-12 Exact-head protected validation and integration reconciliation
P2-V0.16.3 has authentic committed DSPy critic/compiler evidence. The exact worker head passes Workstream Spec Validation, P2 CI, Bounded Autonomy and the correction/convergence reference harness after reconciliation to accepted P2-V0.16.1 and P2-V0.16.2 contracts. Final Wave 3 integration reruns cumulative protected gates.
