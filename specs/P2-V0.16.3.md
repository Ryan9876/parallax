## 1. Objective

Add a bounded autonomous correction controller that converts reproducible implementation, BUILD/TEST/VERIFY, browser, screenshot, visual and provider failure evidence into typed repair attempts. It repeatedly diagnoses, proposes a bounded source correction, re-enters the existing protected mutation and validation path, and converges toward acceptance while preserving last-known-good lineage and explicit human/resource boundaries.

The controller must not create a second source authority, evaluator, worker identity or provider path. It may decide what defect to address and propose source changes, but it cannot directly mutate source, alter protected acceptance/evaluator policy, expand tool/provider/network authority or promote to production.

## 2. Scope

- Normalize bounded failure evidence from IMPLEMENT generation/mutation, BUILD/TEST/VERIFY, P2-V0.16.2 browser validation, screenshot regression, multimodal review and bounded provider operations into one deterministic defect contract.
- Preserve exact Project/run/Work-Spec/source-lineage/Preview provenance, severity, reproducibility, precedence and bounded evidence references without retaining raw logs, DOM, images, provider payloads, credentials or private reasoning.
- Add a correction-planning protocol that receives only canonical session identity, bounded defects and bounded source context, and returns exact target defect IDs plus typed source patch proposals.
- Route every source change through a separate protected mutation runtime that returns a new immutable accepted lineage or fails closed. The controller never writes source directly.
- Require fresh protected validation for every new accepted lineage; stale evidence from a previous lineage cannot satisfy a new candidate.
- Preserve one explicit last-known-good (LKG) source lineage and advance it only on strict protected improvement.
- Enforce finite server-owned attempt, cumulative churn, compute, elapsed-runtime, repeated-defect, no-progress and oscillation budgets.
- Detect repeated equivalent defect sets and alternating previously observed failing states.
- Return typed stop reasons for human approval, privileged/destructive work, material specification ambiguity, missing non-refreshable credential/authorization, unsupported bounded repair and resource exhaustion.
- Produce a bounded data-only failure-dispatch record for reproducible integration failures.
- Reuse the P2-V0.16.1 worker checkpoint/lease identity to retain current lineage, LKG, evidence refs, dependencies and stop metadata across process recreation.
- Consume P2-V0.16.2 `ProtectedBrowserValidationResult` as the browser/visual evidence boundary without reimplementing browser execution internals.

## 3. Fixed decisions

- Evidence precedence is deterministic failure > protected acceptance > screenshot regression > multimodal judgment.
- Candidate quality is the lexicographic vector `(deterministic_failures, acceptance_failures, screenshot_failures, visual_failures, visual_reviews)`; `(0,0,0,0,0)` is protected success.
- Lower-precedence improvement cannot compensate for a new higher-precedence regression.
- Equal quality is no progress.
- LKG is immutable source-lineage identity, not a workspace path.
- Every repair returns through the existing safe mutation and immutable source-lineage acceptance boundary.
- Work Specification content, acceptance criteria, evaluator thresholds, browser workflows/baselines, provider targets, tool capabilities and production authority are immutable inputs for a correction session.
- Human/resource boundaries terminate autonomous correction rather than being patched around.
- Failure dispatch is evidence data, not authority to create work, mutate source, publish or deploy.

## 4. Architecture requirements

### 4.1 Canonical correction session

A session binds canonical `project_id`, Engineering `run_id`, approved Work Specification ID/revision/digest, immutable compiled-plan reference, initial accepted lineage, optional initial LKG lineage, and a server-owned correction budget. These identities cannot be replaced by caller/model input after construction.

### 4.2 Normalized defects

Each defect retains a stable fingerprint, source category (`IMPLEMENT`, `BUILD`, `TEST`, `VERIFY`, `BROWSER_DETERMINISTIC`, `SCREENSHOT_REGRESSION`, `VISUAL`, `PROVIDER`), precedence class, normalized failure code, severity, reproducibility, exact lineage and optional Preview identity, bounded evidence refs and optional already-protected path/locator. Raw unbounded evidence is forbidden.

### 4.3 Protected quality vector

Candidate B is progress over candidate A only when B's quality vector is lexicographically lower. A candidate with a new higher-precedence failure is rejected even if lower-precedence evidence improves. Multimodal PASS cannot override deterministic, acceptance or screenshot-regression failure.

### 4.4 Planning and mutation separation

A correction plan contains a bounded plan identity, exact target defect IDs, one or more relative-path source patches with expected base digest and supported unified diff, bounded estimated changed bytes/compute units, and optionally an explicit stop boundary. It contains no command, shell, arbitrary HTTP, provider target, credential, environment value, evaluator threshold, baseline mutation, Work Specification mutation or production action.

Only an injected `CorrectionMutationRuntime` may accept a plan and return a new immutable accepted source lineage. Operation keys are deterministic and replay-safe so process recreation cannot duplicate mutation.

### 4.5 LKG and regression handling

The controller tracks current candidate and LKG separately. A freshly validated candidate replaces LKG only when its quality vector strictly improves on the current LKG. Equal or worse candidates never overwrite LKG. Higher-precedence regression causes the retained LKG to remain the preferred base for subsequent correction.

### 4.6 Convergence budgets

Server policy bounds maximum correction attempts, cumulative changed bytes, cumulative compute units, elapsed runtime, consecutive no-progress attempts, repeat count for an equivalent defect fingerprint, and oscillations across previously seen failing-state fingerprints. The controller cannot raise its own limits.

### 4.7 Failure dispatch

A dispatch record contains canonical Project/run/Work-Spec identity, current and LKG lineage, normalized failure fingerprint, bounded evidence/dependency refs, receiving capability/workstream class, stop reason and reproducibility. It creates no GitHub issue, ownership grant, source/provider mutation or deployment by itself.

### 4.8 Worker recovery integration

Correction reuses the accepted P2-V0.16.1 worker execution identity. Checkpoints may retain current correction step, current lineage, LKG, evidence refs, dependencies and blocker/stop code. Existing worker retry/no-progress/oscillation bounds remain authoritative outer limits; correction-specific limits may be stricter but never weaker.

## 5. Security

- Correction code receives no raw provider credential, authorization header, cookie, environment secret, arbitrary URL or unrestricted network capability.
- Planner/controller interfaces expose typed data and source-patch proposals only; no shell, generic command, raw HTTP, filesystem root, Git credential, Vercel credential or production-promotion capability is present.
- Defect, state, checkpoint and dispatch evidence is bounded and secret-safe. Raw stdout/stderr streams, full DOM, screenshot bytes, request/response bodies, provider payloads and unrelated Project data are not persisted by this controller.
- Private chain-of-thought or scratchpad content is never required, stored, scored or emitted as correction evidence.
- Project/run/Work-Spec/lineage/Preview mismatches fail closed before planning, mutation, validation-state acceptance or dispatch.
- Source patches cannot change evaluator thresholds, acceptance criteria, browser baseline/workflow policy, capability registry, provider target registration or production authority as a means to pass validation.
- Replay identities are server-derived; a caller cannot select an operation key to alias another Project/run/lineage correction.
- LKG and correction state are Project/run scoped and cannot be reused as cross-Project repair memory.
- Missing or non-refreshable authorization is a stop boundary, not permission to weaken credential, network or provider controls.
- Production merge/deployment remains outside this workstream.

## 6. Stop boundaries

Autonomous correction stops with a typed reason when explicit human approval is required; destructive/privileged action is required; material Work Specification ambiguity prevents a bounded repair; credential/authorization is unavailable and non-refreshable; protected policy/baseline/provider-target change would be required to pass; supported safe mutation cannot repair the failure; or any finite attempt/churn/compute/runtime/repeated-defect/no-progress/oscillation budget is exhausted.

Transient provider outage, rate limiting or refreshable credential failure remains a worker/runtime recovery concern and does not authorize a source change merely to bypass the external failure.

## 7. Reference harness

Permanent tests must prove normalization across all supported failure sources; protected precedence; successful multi-attempt convergence; LKG retention on regression; equal-quality no-progress rejection; repeated-defect stop; A/B/A-style oscillation stop; attempt/churn/compute/runtime exhaustion; human/spec/privilege/credential boundaries; process recreation without duplicate mutation; canonical failure dispatch; checkpoint reuse; and inability of planner/controller output to mutate policy, authority or provider/deployment boundaries.

## 8. Non-goals

- browser execution, accessibility engine, screenshot capture or multimodal model implementation;
- a second worker lease/checkpoint/reassignment state machine;
- critical-path scheduling, work stealing or global worker allocation;
- direct GitHub issue creation from correction output;
- automatic browser-baseline acceptance/update;
- Work Specification amendment or approval;
- production merge/deployment/promotion autonomy;
- generic shell, HTTP, filesystem or provider authority for the planner/controller.

## 9. Acceptance criteria

### AC-01 Failure evidence is normalized, bounded and provenance-safe
IMPLEMENT, BUILD/TEST/VERIFY, browser deterministic, screenshot, visual and provider failures normalize into stable bounded defect evidence tied to the exact Project/run/Work-Spec/source-lineage/Preview facts where applicable. Raw unbounded logs/DOM/images/provider payloads, secrets, private reasoning and unrelated Project data are rejected.

### AC-02 Protected evidence precedence cannot be weakened
The controller uses deterministic failure > protected acceptance > screenshot regression > multimodal judgment precedence. Lower-precedence improvement cannot compensate for a new higher-precedence failure, and multimodal PASS cannot override deterministic/protected/screenshot failure.

### AC-03 Correction planning is typed and has no mutation or policy authority
Planner output identifies exact target defects and bounded source patch proposals but exposes no direct filesystem/shell/HTTP/provider/deployment capability and cannot change Work Specification acceptance, evaluator thresholds, browser baselines/workflows, tool authority or provider targets.

### AC-04 Every correction re-enters protected source mutation and fresh validation
The controller can only advance through a protected mutation runtime that returns a new immutable accepted lineage. Every new lineage receives fresh protected validation; stale evidence from a prior lineage cannot satisfy the candidate.

### AC-05 Last-known-good lineage is preserved and only advances on strict protected improvement
LKG survives failed/regressive repair attempts and process recreation. A candidate replaces LKG only when its protected quality vector is lexicographically better. Equal/worse candidates cannot overwrite LKG.

### AC-06 Bounded convergence budgets stop runaway correction
Attempt, cumulative churn, compute, elapsed runtime, repeated-defect, no-progress and oscillation limits are server-owned, finite and enforced. The model/controller cannot increase them, and exhaustion returns a typed stop reason without further mutation.

### AC-07 Repeated defects and oscillation are detected deterministically
Repeated equivalent defect fingerprints and alternating previously observed failing states are identified from bounded canonical fingerprints. The reference harness proves same-defect repetition and A/B/A-style oscillation stop before unbounded repair churn.

### AC-08 Human, privileged, specification and credential boundaries fail closed
Explicit approval, destructive/privileged work, material specification ambiguity and non-refreshable missing credential/authorization stop with typed human/resource reasons. The controller does not patch around these boundaries or misrepresent them as passing validation.

### AC-09 Failure dispatch is canonical data without autonomous ownership expansion
Reproducible bounded failures can produce a dispatch record with exact Project/run/spec/lineage/LKG/evidence/dependency binding and receiving workstream class. Dispatch itself creates no GitHub issue, source mutation, provider mutation, ownership grant or production action.

### AC-10 P2-V0.16.1 worker recovery identity remains authoritative
Correction checkpoints reuse the accepted worker execution/lease/checkpoint contract, retain current and LKG lineage plus bounded evidence/stop metadata, and do not create a competing recovery identity. Existing worker retry/no-progress/oscillation bounds remain outer authority.

### AC-11 Replay/process recreation does not duplicate mutation or lose convergence state
Reconstructing the controller from durable run/checkpoint/correction evidence resumes the same bounded session, retains LKG/budget/fingerprint state and replays accepted operation keys without creating duplicate source mutation or provider publication.

### AC-12 Exact-head protected validation and integration reconciliation
P2-V0.16.3 has authentic committed DSPy critic/compiler evidence. The exact worker head passes Workstream Spec Validation, P2 CI, Bounded Autonomy and the correction/convergence reference harness after reconciliation to accepted P2-V0.16.1 and P2-V0.16.2 contracts. Final Wave 3 integration reruns cumulative protected gates.
