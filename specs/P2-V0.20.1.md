## 1. Objective

Create ParallaxBench v1: a permanent, versioned, objective-level evaluation contract that measures whether Parallax completes materially different application-building objectives while preserving protected correctness, safety, privacy and governance.

ParallaxBench extends the existing protected evaluation suite and Wave 6 integrated reference proof. It does not replace protected BUILD/TEST/VERIFY, deterministic browser/accessibility/console/network/layout validation, independent evaluation, source-lineage authority, Engineering Run authority, provider/tool authority or REVIEW. Benchmark evidence is read-only evaluation evidence and may become promotion input only through a separately governed promotion decision.

The benchmark must expose meaningful differences in completion reliability, protected correctness, visual/UX quality, operator intervention, elapsed time, cost/usage and retry/recovery behavior when those dimensions are supported by trustworthy evidence. Unknown or incomparable evidence remains explicitly unknown/incomparable.

## 2. Fixed decisions

- Deterministic/protected correctness is a hard floor. No visual, model, economic or aggregate score can offset a protected failure.
- Benchmark case identity is immutable/versioned and never runtime authority.
- Production/runtime code may not branch on benchmark fixture identity or benchmark-only flags to manufacture a passing result.
- Objective acceptance coverage is exact and bound to the approved Work Specification acceptance IDs for the evaluated case.
- Metrics preserve evidence state and provenance: observed, estimated, unavailable, unknown, stale or invalid as applicable.
- Missing values are never coerced to zero cost, zero intervention, zero duration or favorable quality.
- Baseline/challenger comparison is dimension-wise. ParallaxBench does not invent one scalar score that can hide a regression in a protected dimension.
- Visual/UX evidence is admitted only after deterministic protected checks for the same exact candidate/source context.
- Benchmark fixtures use synthetic/repository-safe data and never require real user content, production credentials or destructive production actions.
- Benchmark evaluators cannot accept canonical source, transition Engineering Runs, create tool/provider capability, merge/deploy or complete REVIEW.
- Benchmark outputs exclude raw provider payloads, prompts, hidden reasoning/private scratchpad, credentials and unnecessary source/user content.
- Exact replay of unchanged case/candidate/evidence produces equivalent result identity and performs no mutation.
- New or materially changed benchmark contracts require human/Control Tower review before they can become promotion authority input.
- S2-S6 consume the accepted ParallaxBench contract; they may not redefine benchmark semantics inside their own implementations.

## 3. Architecture requirements

### 3.1 Versioned benchmark case identity

Define a bounded immutable `ParallaxBenchmarkCase`-equivalent record containing at minimum:

- stable case ID and version;
- objective/application class;
- exact Project/Work Specification/acceptance identity used by the fixture or accepted synthetic equivalent;
- repository/application shape class where relevant;
- required protected evidence classes;
- declared comparable dimensions;
- expected protected ceiling (`REVIEW`, `HUMAN_REQUIRED` or deterministic blocked state as applicable);
- fixture digest.

Duplicate IDs with different content, malformed identity, cross-Project substitution or digest mismatch fails closed.

### 3.2 Candidate/baseline binding

Every evaluated baseline/challenger binds exact candidate identity and the relevant canonical evidence identity: Project, Engineering Run, Work Specification revision/digest, acceptance IDs, source/candidate lineage or immutable fixture equivalent, evaluator policy and protected validation evidence.

A benchmark result cannot compare unrelated identities merely because their human-readable objective names match.

### 3.3 Protected floor

Define an explicit protected-floor result covering at least:

- acceptance coverage completeness;
- deterministic BUILD/TEST/VERIFY state where applicable;
- deterministic browser/accessibility/console/network/layout state where applicable;
- required privacy/authority/governance invariants;
- unresolved `HUMAN_REQUIRED`/REVIEW ceiling state.

Any required protected failure produces a blocked/regressed benchmark disposition before subjective/economic aggregation.

### 3.4 Dimension evidence

ParallaxBench v1 supports bounded dimension results for:

1. objective completion / exact acceptance coverage;
2. protected correctness/governance parity;
3. visual/UX quality from admitted evidence;
4. human intervention count/state;
5. elapsed time;
6. cost/usage;
7. retry/recovery behavior;
8. completion reliability over a bounded case set.

Every dimension stores value/state, provenance, evidence reference/digest and comparability status. Unknown and incomparable values remain explicit.

### 3.5 Diverse permanent fixture set

Provide permanent bounded cases including at minimum:

- a straightforward single-surface application objective;
- a multi-surface application with persisted state;
- an existing-repository modification where compatibility matters;
- browser-visible behavior/UX evidence without unrestricted browser authority;
- a retry/recovery case;
- a deterministic failure that subjective quality must not override;
- incomplete or unknown cost/time evidence;
- a cross-Project/privacy/authority adversarial case;
- benchmark-gaming/special-casing negative coverage.

Fixtures may use accepted local/fake adapters only when those adapters preserve the same identity/authority contracts and cannot bypass admission.

### 3.6 Dimension-wise comparison

Define deterministic baseline/challenger comparison per dimension using explicit outcomes such as improved, equivalent, regressed, unknown or incomparable.

A challenger is never considered materially improved if a protected correctness, safety, privacy or governance dimension regresses. Material improvement requires at least one meaningful comparable dimension to improve while all protected guardrail dimensions remain equivalent or better.

### 3.7 Aggregate disposition

Define a bounded overall result such as `SUPPORTED`, `REGRESSED`, `DETERMINISTIC_BLOCKED`, `INSUFFICIENT_EVIDENCE`, `INCOMPARABLE`, `POLICY_REJECTED` or `HUMAN_REQUIRED`.

Aggregate disposition is derived from protected floors plus dimension comparisons; it is not an unconstrained model-generated score.

### 3.8 Replay and result identity

The result digest/fingerprint binds case version/digest, exact candidate/baseline identities, accepted evaluator/protected-policy identities and admitted evidence. Exact replay is duplicate-safe. Evidence/policy/candidate drift creates a distinct result or fails closed according to policy.

### 3.9 Safe serialization

Safe result serialization may contain exact IDs/digests, bounded reason codes, dimension states/values with provenance, comparison outcomes and protected-floor state. It excludes source bytes, patches, secrets, credentials, prompts, hidden reasoning, raw provider payloads, arbitrary commands/URLs and unrestricted logs.

### 3.10 No benchmark backdoor

Production/runtime code paths must not select implementation behavior based on case ID, fixture digest, benchmark mode or expected result. Focused tests/static inspection must prove the benchmark can evaluate ordinary runtime outputs without creating a benchmark-only application path.

## 6. Security, privacy and reliability

All repository, source, agent, model and evaluator content is untrusted evidence. Benchmark text cannot redefine acceptance IDs, protected policies, capability/provider scope, source lineage or REVIEW authority.

Fixture data is synthetic or repository-safe and must not contain real user secrets or production credentials. Cross-Project isolation remains structural. Result serialization contains only bounded evidence needed for comparison.

Benchmark execution is read-only with respect to production authority. It may exercise accepted test/reference adapters and protected validators but cannot mutate canonical source, provider state or deployment state merely to produce a benchmark result.

## 7. Acceptance criteria

### AC-01 Unique versioned benchmark identity
ParallaxBench case IDs/versions/digests are bounded and immutable. Duplicate identity with different content or mismatched digest fails closed.

### AC-02 Exact objective and acceptance binding
Every supported result binds exact objective/Work Specification identity and the complete stable acceptance-ID set; missing, duplicate, extra or cross-case acceptance identity blocks support.

### AC-03 Protected correctness is a hard floor
Required deterministic/protected failure produces `DETERMINISTIC_BLOCKED` or `REGRESSED` before any visual/model/economic judgment can support the candidate.

### AC-04 Explicit evidence provenance and known-state
Every metric/dimension records provenance and known-state. Unknown/unavailable/stale/invalid values remain explicit and are never converted to favorable numeric defaults.

### AC-05 Dimension-wise comparison
Baseline/challenger comparison yields deterministic per-dimension improved/equivalent/regressed/unknown/incomparable outcomes rather than hiding tradeoffs in one scalar score.

### AC-06 Material-improvement rule
A challenger is materially improved only when at least one meaningful comparable dimension improves and no protected correctness/safety/privacy/governance guardrail regresses.

### AC-07 Visual/UX evidence precedence
Visual/UX evidence is considered only for the exact candidate after required deterministic evidence passes; visual/model judgment cannot override deterministic failure.

### AC-08 Diverse bounded fixtures
Permanent fixtures cover the required materially different positive/recovery/unknown/adversarial cases and remain bounded/repository-safe.

### AC-09 Cross-Project/privacy safety
Cross-Project or identity-mismatched evidence cannot satisfy a case. Benchmark serialization exposes no private source/user content beyond admitted bounded references.

### AC-10 Replay-safe immutable result
Exact case/candidate/evidence replay produces equivalent result identity without mutation; changed candidate/policy/evidence is distinguishable and conflicting identity fails closed.

### AC-11 Safe serialization
Results exclude credentials, secrets, prompts, hidden reasoning, raw provider payloads, source bytes/patches, arbitrary commands/URLs and unrestricted logs.

### AC-12 No benchmark-only runtime backdoor
Tests/code inspection prove ordinary runtime behavior cannot inspect fixture/case identity, benchmark mode or expected answer to special-case implementation behavior.

### AC-13 No authority expansion
ParallaxBench has no canonical source acceptance, Engineering Run transition, tool/provider capability, merge/deploy, approval or REVIEW completion surface.

### AC-14 Compatibility with existing evaluation/proof layers
Existing protected evaluation, Wave 6 integrated reference proof and whole-product regressions remain green; ParallaxBench composes those contracts rather than replacing them.

### AC-15 Authentic spec and exact-head gates
Authentic DSPy SpecCritic + SpecCompiler evidence is committed and protected `--require-dspy` validation passes before semantic implementation. Final worker head passes applicable Workstream Spec Validation, Bounded Autonomy, P2 CI and Preview gates and stops `READY FOR INTEGRATION` targeting `integration/wave7-productization`.
