## 1. Objective

Establish the foundational Wave 6 protocol that lets Parallax invoke interchangeable engineering agents as bounded labor without transferring any canonical authority to an agent or provider adapter.

The protocol must make an agent task and every result attributable to the exact canonical Project, Engineering Run, approved Work Specification revision/digest, acceptance IDs, source context, operation identity, adapter identity and attempt. Provider-specific outputs are normalized into bounded evidence that existing Parallax worker/runtime logic may inspect; they never become accepted source lineage, validation truth, approval, merge/deployment authority or REVIEW completion merely because an agent returned them.

S1 is intentionally narrower than orchestration. It defines the trust boundary and evidence vocabulary required by S2–S6. It does not decide which agent should work, whether a candidate is good enough, which candidate should win, or whether more spending is justified.

## 2. Fixed decisions

- **Agents are labor, never authority.** A task may request bounded work; an agent result may provide evidence. Only existing Parallax server-owned contracts can approve Work Specifications, mutate canonical source through registered protected paths, validate acceptance, accept lineage, transition protected run state, publish governed delivery or cross REVIEW/HUMAN_REQUIRED.
- **Provider-neutral canonical envelope.** Provider payloads are translated at the adapter edge. Raw provider request/response objects, prompts, hidden reasoning and credentials are not canonical protocol fields and are not persisted as safe evidence.
- **Exact identity binding is mandatory.** Task/result/checkpoint/error evidence is invalid unless bound to exact Project ID, run ID, Work Specification ID/revision/digest, stable acceptance IDs, operation ID and agent/adapter identity. When source context is supplied, its exact immutable lineage/revision identity is also bound.
- **Capability declarations are evidence only.** An adapter or agent can declare supported work kinds/capabilities, but declarations cannot create Project capability grants, tools, shell/network/provider scope, service bindings or credential access.
- **No acceptance rewriting.** The task may carry the stable acceptance IDs it is expected to address. An adapter/agent may report claimed coverage but cannot add, remove, replace or reinterpret the protected acceptance contract.
- **Replay is explicit and fail-closed.** Stable operation/request IDs and attempt identities distinguish exact replay from a new task. Duplicate/stale/mismatched results cannot replace newer accepted worker evidence or cause a second authority-bearing action.
- **Cancellation and timeouts are normalized outcomes.** They produce bounded terminal/non-terminal evidence as appropriate; they do not silently become success or grant the adapter freedom to continue after Parallax revoked the task.
- **Usage economics never fabricate certainty.** Duration, token, request or cost observations include source/provenance and explicit `UNAVAILABLE`/`UNKNOWN` semantics. Missing provider usage is not estimated as observed fact.
- **Two reference adapters prove interchangeability.** S1 uses deterministic in-process reference/fake adapters to prove the canonical contract and failure normalization. Real external-agent provider onboarding is not required to establish S1 and must not introduce new provider authority by implication.
- **Existing protected execution remains authoritative.** S1 does not replace Engineering Run, durable worker lease/checkpoint/recovery, implementation runtime, immutable lineage, correction, validation/evaluation, source delivery or provider authorization paths.

## 3. Architecture requirements

### 3.1 Canonical agent identity

Define immutable bounded identity structures for at least:

- agent ID;
- agent version;
- adapter ID/version;
- provider kind as a descriptive enum/string owned by Parallax configuration;
- declared work/capability evidence as bounded normalized identifiers;
- optional model/runtime label as non-authoritative evidence.

Identity fields must be validated for bounded length/format and deterministic serialization. Agent identity cannot contain credentials, provider tokens, arbitrary executable commands or authority grants.

### 3.2 Immutable task request envelope

Define an immutable `AgentTaskRequest`-equivalent contract containing at minimum:

- exact Project ID;
- exact Engineering Run ID;
- exact Work Specification ID, revision and digest;
- exact stable acceptance IDs, preserving order deterministically;
- stable operation/task ID and explicit attempt number/ID;
- bounded task/work kind;
- source lineage/revision identity when source evidence is part of the task;
- bounded context/evidence references rather than unrestricted blobs;
- explicit requested capability/work evidence, which is descriptive and cannot create authorization;
- creation/deadline/cancellation metadata where required for timeout handling.

Construction rejects empty or duplicate acceptance IDs, malformed identity, negative attempts, inconsistent deadline data and unsafe/unbounded context fields. Task serialization contains no raw credentials or hidden reasoning.

### 3.3 Normalized lifecycle and result evidence

Define normalized immutable evidence for lifecycle/result states sufficient to express at least:

- accepted/started/running/checkpointed;
- completed with bounded result summary/evidence references;
- recoverable failure;
- terminal failure;
- timeout;
- cancellation/cancelled;
- rejected/stale/duplicate/mismatched evidence.

Every result carries the exact immutable task identity projection and agent/adapter identity. Result evidence may include claimed acceptance coverage, changed-path/source references, diagnostics or test observations only as bounded evidence. It grants no source acceptance or protected validation status.

### 3.4 Checkpoint and recovery evidence

A checkpoint is a bounded evidence object bound to the exact task/attempt and agent identity. It can be passed back to a conforming adapter only when the current Parallax task identity still matches. Checkpoint contents cannot contain raw credentials, hidden reasoning, unrestricted logs or a provider-native opaque object that is required to determine canonical authority.

S1 does not replace durable worker checkpoint persistence. It provides normalized evidence the existing worker/recovery layer can safely associate with an attempt.

### 3.5 Usage, duration and cost evidence

Define typed observations for time/tokens/requests/cost where:

- each metric records availability state (`OBSERVED`, `UNAVAILABLE`, or `UNKNOWN` or equivalent);
- observed values carry a normalized source/provenance identifier and units/currency when applicable;
- numeric values are finite and non-negative;
- cost cannot be inferred from token counts and represented as provider-observed cost unless provenance explicitly says it is an estimate, and S1 should prefer `UNAVAILABLE` over invented estimates;
- missing provider telemetry survives normalization as missing rather than zero;
- evidence is task/attempt/agent bound.

### 3.6 Adapter protocol

Define a provider-neutral async/sync protocol or abstract interface with bounded operations equivalent to:

- describe identity/capability evidence;
- invoke a canonical task;
- request cancellation when supported;
- optionally resume from a canonical checkpoint when supported.

The protocol must not expose a generic shell, arbitrary URL/request function, raw credential access, direct canonical source writer, merge/deploy function, approval function, evaluator override or run-state mutator.

Adapters normalize provider-specific failures into the canonical failure taxonomy. Unknown provider failures fail closed as a bounded non-success result.

### 3.7 Result admission/identity verification

Provide deterministic server-owned verification helpers that compare a result/checkpoint against the expected task and reject at least:

- different Project;
- different run;
- different Work Specification ID/revision/digest;
- changed, missing or reordered acceptance identity where the canonical projection must match;
- different operation/task ID;
- invalid/stale attempt;
- different adapter/agent identity when the task bound an expected identity;
- source-lineage mismatch when source context is bound;
- duplicate terminal result admission for the same exact operation/attempt when a durable accepted result is already known.

The verifier returns bounded reason codes/evidence. It does not accept source lineage or transition Engineering Run state.

### 3.8 Deterministic reference adapters

Implement at least two deterministic in-process conforming reference/fake adapters with materially different internal behavior or response shapes behind the same protocol. Tests prove the caller receives equivalent normalized task/result evidence and failure categories independent of adapter implementation.

At least one adapter supports deterministic checkpoint/resume or recoverable failure. At least one demonstrates timeout/cancellation normalization. Neither adapter receives or invents real provider credentials, network/shell authority or production mutation ability.

### 3.9 Safe serialization and observability boundary

Canonical evidence serialization must be deterministic and privacy-safe. Safe serialized evidence may expose bounded IDs, statuses, reason codes, metric availability/provenance, safe summaries and approved evidence references. It must not expose:

- raw source blobs/diffs unless already represented by an existing protected bounded reference;
- prompts or hidden reasoning;
- provider request/response payloads;
- access tokens, cookies, API keys, secret values/handles or connection strings;
- unrestricted logs;
- cross-Project private context;
- executable commands or arbitrary URLs supplied by agent output as authority.

## 6. Security

All agent/provider output is untrusted evidence. The adapter boundary is specifically a trust-reduction boundary, not a trust-transfer boundary.

The implementation must fail closed on identity mismatch, malformed evidence, unknown failure states, duplicate/stale results and unsupported recovery. Agent declarations cannot be converted into capability grants. No API key, provider token, credential handle/value, cookie, connection string, hidden reasoning, raw provider payload or unrestricted log may enter the canonical task/result structures or safe serialization.

Cross-Project identity must be exact and cannot be inferred from agent content. A result for one Project/run/Work Specification must never be admissible for another even if objective text or source content appears identical.

Acceptance IDs come from the approved Work Specification and are immutable task bindings. Claimed acceptance coverage from an agent remains evidence and cannot satisfy protected evaluation by itself.

S1 may describe requested work/capability evidence but cannot construct or expand capability snapshots, provider scopes, shell/network access, service bindings, source writer authority, evaluator thresholds, merge/deploy permissions or review authority.

Cancellation/revocation wins over late provider success. A result arriving from a stale/revoked attempt is rejected as stale evidence rather than reinstating work.

## 7. Acceptance criteria

### AC-01 Exact canonical task identity binding
Every canonical agent task includes exact Project ID, Engineering Run ID, Work Specification ID/revision/digest, stable acceptance IDs, operation/task ID, attempt identity and, when applicable, immutable source-lineage/revision identity. Construction rejects malformed identity, duplicate/empty acceptance IDs and invalid attempt/deadline metadata.

### AC-02 Agent and adapter identity is bounded evidence only
Agent ID/version, adapter ID/version, provider kind, model/runtime label and declared capabilities/work kinds are deterministically serialized bounded evidence. None of these fields can create a Project capability grant, credential, tool, shell/network/provider scope, service binding, source acceptance, merge/deploy authority or REVIEW permission.

### AC-03 Provider-specific payloads cannot become canonical truth
At least two deterministic conforming reference adapters with materially different internal response shapes normalize into the same canonical request/result/failure evidence. Raw provider payloads, prompts, hidden reasoning and credential material are absent from canonical evidence and safe serialization.

### AC-04 Exact acceptance contract cannot be redefined by an agent
The task binds the stable acceptance IDs from the approved Work Specification. Agent claimed coverage is represented only as bounded evidence. Missing, added, replaced or mismatched acceptance identity causes admission failure and no agent result can alter evaluator thresholds or satisfy protected acceptance without existing validation/evaluation.

### AC-05 Result admission fails closed on identity mismatch or staleness
Deterministic admission tests reject results/checkpoints with mismatched Project, run, Work Specification identity/revision/digest, acceptance projection, operation ID, source lineage, agent/adapter identity where bound, stale attempt or revoked/cancelled task. Rejection returns bounded reason codes and cannot transition Engineering Run state or accept source lineage.

### AC-06 Replay and duplicate result handling is idempotent
Stable task/operation and attempt identities distinguish exact replay from a new attempt. Re-admitting the same terminal evidence is duplicate-safe; stale or competing duplicates cannot replace the durable accepted worker evidence for the operation, trigger a second authority-bearing action or silently become a new task.

### AC-07 Recoverable failure and checkpoint evidence preserves worker authority
A conforming reference adapter demonstrates recoverable failure plus bounded checkpoint/resume. Checkpoints are exact task/attempt/agent bound, contain no authority/credential/private-reasoning payload, and are resumable only when current canonical identity still matches. Existing durable worker lease/checkpoint/recovery remains authoritative.

### AC-08 Timeout and cancellation normalize without false success
A conforming reference adapter demonstrates deterministic timeout/cancellation behavior. Cancellation/revocation wins over late completion, unsupported cancellation is represented explicitly, and unknown provider errors normalize to bounded non-success rather than success or autonomous retry authority.

### AC-09 Usage, duration and cost observations preserve provenance and missingness
Time/token/request/cost evidence uses explicit availability state and provenance. Observed numeric values are finite/non-negative and carry required units/currency where applicable. Missing provider telemetry remains `UNAVAILABLE`/`UNKNOWN`, not zero or fabricated observed cost, and all observations remain task/attempt/agent bound.

### AC-10 Safe evidence serialization preserves privacy and authority boundaries
Deterministic serialization exposes only bounded safe identities, status/reason codes, safe summaries/references and metric provenance/availability. Tests prove it contains no raw credentials/secrets, provider request/response payloads, prompts, hidden reasoning, unrestricted logs, cross-Project private context or agent-supplied executable/network authority.

### AC-11 Existing protected runtime contracts remain authoritative and green
S1 does not replace or weaken Engineering Run state, durable worker recovery, immutable accepted lineage, implementation/correction runtime, governed skills/service bindings, protected validation/evaluation, source delivery, authentication/session handling or REVIEW/HUMAN_REQUIRED. Relevant existing API/protected-autonomy regression suites remain green.

### AC-12 Exact-head worker boundary and dependency gate
`P2-V0.19.1` validates with authentic DSPy metadata before semantic implementation. Final S1 diff remains within issue #264 ownership; exact-head Workstream Spec Validation, P2 CI and Bounded Autonomy pass; PR targets `integration/wave6-agentic-control-plane`; worker stops `READY FOR INTEGRATION` with no worker merge/deploy. S2/S3 semantic implementation remains blocked until Control Tower accepts S1.
