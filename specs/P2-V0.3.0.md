# Parallax 2.0 v0.3.0 — Reason 2.0 Specification

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.3.0
Depends on: P2-V0.2.0
Method: Spec-first + DSPy-governed development + protected evaluation

## 1. Objective

Build Reason 2.0 as Parallax's first evaluation-driven intelligence program on top of the validated v0.2.0 protected evaluation spine.

Reason 2.0 must behave as a durable multi-turn reasoning partner rather than a sequence of disconnected one-shot answers. It must preserve the active objective, honor corrections and explicit constraints from later turns, distinguish ordinary follow-ups from material objective changes, communicate uncertainty without manufacturing certainty, preserve evidence/status honesty, and remain concise enough for a conversational primary interface.

The release must improve reasoning architecture without allowing DSPy programs or optimizers to redefine the protected evaluation criteria used to judge that architecture.

## 2. User outcome

A user can ask a question, receive an answer, ask follow-up questions, correct an assumption, narrow or extend the request, and continue the same conversation without Parallax silently restarting or discarding established context.

When a new request materially changes the approved objective, Parallax identifies that change explicitly instead of silently treating it as ordinary continuation. When information is insufficient, Parallax can ask a focused clarification or clearly state the material uncertainty rather than inventing a confident answer.

The user sees the useful answer and product state. Hidden chain-of-thought is never requested, persisted, exposed, or required for evaluation.

## 3. Fixed decisions

- Reason 2.0 remains conversation-first; no dashboard or IDE redesign is introduced by this release.
- Durable conversation messages and the active specification remain the source context. The client does not become the authority for scope classification.
- The existing client-supplied `material_scope_change` flag may remain only as an explicit test/developer override during the transition; normal product behavior must use server-side scope evaluation.
- Scope classification returns an observable structured decision, not hidden reasoning.
- Supported scope decisions are `CONTINUE`, `CLARIFY`, and `SPEC_AMENDMENT`.
- `CONTINUE` preserves the active conversation/specification and produces a substantive answer.
- `CLARIFY` preserves the active conversation/specification and produces one focused clarification request when missing information materially blocks a useful answer.
- `SPEC_AMENDMENT` prevents silent substantive continuation against the old approved objective and places the conversation into the existing amendment-required lifecycle state.
- A model may propose a scope decision, but protected server policy validates allowed transitions and owns conversation-state mutation.
- Later explicit user corrections outrank earlier inferred assumptions in context assembly.
- Reasoning output is a typed observable envelope containing at minimum answer, confidence, scope decision, material uncertainties, and program version.
- Material uncertainties/assumptions are structured observable metadata, not hidden chain-of-thought.
- The public response remains normal user-facing prose; metadata is exposed only when useful for product behavior or trace evidence.
- Runtime model escalation remains Luna → Terra → Sol.
- Provider/model failure or protected validation failure may trigger escalation; a successful but protected-invalid answer is not accepted merely because generation completed.
- Protected promotion suites and thresholds remain outside Reason/DSPy optimizer control.
- Reason 2.0 must be evaluated against dedicated multi-turn development and promotion suites before being called validated.
- No provider-backed optimizer is authorized to auto-promote, merge, or deploy a Reason program.

## 4. Scope

### 4.1 Deterministic context assembly

Introduce a server-side context composer that builds the Reason input from authoritative conversation state.

The composer must provide a bounded, deterministic representation containing at least:

- conversation ID;
- active spec ID;
- conversation lifecycle status;
- mode;
- current user turn;
- a bounded chronological window of prior messages;
- an explicit marker distinguishing user statements from assistant statements;
- an explicit instruction that later user corrections supersede conflicting earlier inferred assumptions.

The composer must enforce configurable hard limits so an indefinitely long conversation cannot create unbounded prompt growth. Truncation must remove oldest eligible conversational turns first while preserving the active spec ID, current user turn, and the most recent context.

v0.3.0 does not require semantic vector retrieval or a model-generated long-term summary. Those may be added later only with evaluation evidence proving they do not introduce context drift.

### 4.2 Scope-decision program

Create a DSPy-compatible scope program with a typed result:

- `decision`: `CONTINUE | CLARIFY | SPEC_AMENDMENT`;
- `confidence`: normalized `0.0..1.0`;
- `material_factors`: short observable factors supporting the decision, limited in count/length;
- `program_version`.

The scope program receives the current user turn plus the deterministic context contract. It does not receive protected promotion-suite contracts or thresholds.

Protected policy validates that:

- the decision is an allowed enum;
- confidence is finite and bounded;
- material factors contain no hidden-reasoning/scratchpad fields or secret-bearing content;
- low-confidence material-change classification cannot silently mutate the conversation into a new objective;
- explicit developer/test overrides remain observable in traces.

Initial protected policy may conservatively map a low-confidence `SPEC_AMENDMENT` proposal to `CLARIFY` rather than silently permitting continuation or amendment.

### 4.3 Reason-response program

Replace the foundation's minimally structured one-shot Reason program with a typed Reason 2.0 program result containing:

- `answer`;
- `confidence`;
- `material_uncertainties`: bounded list of short observable uncertainty statements;
- `assumptions`: bounded list of material assumptions that directly affect the answer;
- `program_version`.

The program receives the current objective, deterministic context, mode, active spec ID, and validated scope decision.

Behavior requirements:

- use established conversation context without reintroducing the request as if it were new;
- follow the latest explicit user correction when it conflicts with an older inferred assumption;
- answer directly when context is sufficient;
- avoid presenting generated/development/validated/deployed states as interchangeable;
- state material uncertainty when it changes the recommendation;
- avoid unnecessary generic preambles or repeated summaries of context the user already knows;
- never reveal hidden chain-of-thought when asked; provide a concise rationale/summary instead;
- never expose provider secrets or environment values.

### 4.4 Clarification behavior

When the protected scope decision is `CLARIFY`, Reason must not produce a broad speculative answer that hides the missing information.

The response should ask the smallest useful clarification that materially unlocks progress. It should not ask a question merely because uncertainty exists when a safe, reversible recommendation can still be made.

The clarification response remains a normal assistant message in the same conversation and the conversation remains `ACTIVE`.

### 4.5 Specification-amendment behavior

When protected policy accepts `SPEC_AMENDMENT`:

- the existing conversation is preserved;
- conversation status becomes `SPEC_AMENDMENT`;
- the API emits an explicit `SPEC_AMENDMENT` state event;
- no substantive implementation/reasoning against the materially changed objective is silently performed under the prior approved spec;
- the response explains concisely that the requested change materially changes the approved objective and requires an amendment/approval step.

v0.3.0 does not need to generate or approve the actual replacement software specification. It must establish a correct stop/hand-off boundary rather than silently restarting or mutating objectives.

### 4.6 Protected Reason verification

Extend protected metrics so a structured Reason result can be rejected before completion when it violates deterministic safety/contract requirements.

At minimum, protected validation must cover:

- non-empty meaningful answer for `CONTINUE`/`CLARIFY` paths;
- valid scope decision and bounded confidence;
- bounded metadata sizes;
- no hidden chain-of-thought/scratchpad fields in observable result structures;
- no obvious configured secret leakage;
- status-honesty assertions in dedicated benchmark cases;
- required amendment behavior for protected material-change cases;
- required continuity behavior for protected follow-up cases.

A protected-invalid result is eligible for normal model escalation. If all routed models fail protected validation, the system returns a sanitized recoverable error and preserves conversation state.

### 4.7 Trace contract

Extend public response traces with observable Reason 2.0 metadata without storing hidden reasoning.

Trace evidence should include at minimum:

- response ID;
- conversation ID;
- spec ID;
- Reason program version;
- scope-program version;
- protected scope decision;
- whether an explicit scope override was used;
- context digest and included-turn count;
- attempted models and attempt validation outcomes;
- protected verification result;
- final product state.

Raw hidden chain-of-thought, DSPy rationale fields, provider credentials, and environment values must never enter the public trace.

### 4.8 Dedicated Reason benchmark suites

Add separate repository-safe Reason development and promotion benchmark suites using the v0.2.0 evaluation schema/runner/promotion gate.

The initial Reason benchmark must include multi-turn cases covering at least:

1. ordinary follow-up continuity;
2. later-user-correction precedence;
3. material objective change requiring `SPEC_AMENDMENT`;
4. ambiguous but non-material request requiring focused clarification;
5. uncertainty/status honesty when evidence is incomplete;
6. generated-versus-validated-versus-deployed status honesty;
7. secret/credential non-disclosure;
8. hidden-chain-of-thought request handling;
9. concise direct engineering communication;
10. protected failure/degradation behavior when all candidate models fail validation.

Development cases may be used by DSPy optimization. Promotion case contracts/thresholds remain protected from optimizer input.

### 4.9 Recorded baseline and regression fixtures

Create offline recorded fixtures sufficient to prove the Reason evaluation mechanism without provider credentials.

At minimum include:

- a known-good Reason baseline;
- an equivalent/non-regressing challenger;
- a continuity regression that incorrectly restarts context;
- a status-honesty regression that falsely claims deployment/validation;
- a scope regression that continues substantively when a protected case requires `SPEC_AMENDMENT`.

The protected promotion gate must reject each regression for machine-readable reasons even if an unrelated aggregate score remains high.

### 4.10 API integration

The conversation response endpoint must use server-side scope evaluation in normal operation.

Expected high-level lifecycle:

```text
USER TURN
   ↓
DETERMINISTIC CONTEXT ASSEMBLY
   ↓
SCOPE PROGRAM
   ↓
PROTECTED SCOPE POLICY
   ├─ CONTINUE ─────► REASON PROGRAM ─► PROTECTED VERIFY ─► RESPOND
   ├─ CLARIFY ──────► FOCUSED CLARIFICATION ──────────────► RESPOND
   └─ SPEC_AMENDMENT► STATUS TRANSITION + AMENDMENT EVENT ─► STOP
```

The endpoint continues to emit existing SSE product states. `SPEC_AMENDMENT` is an explicit terminal hand-off state for that response, not an `ERROR` masquerading as failure.

### 4.11 Client integration

The client must distinguish `SPEC_AMENDMENT` from ordinary error behavior.

For an amendment-required response:

- preserve the conversation and user message;
- show a calm, explicit amendment-required state/message rather than the generic red/error path;
- stop the optical response inscription if no substantive assistant answer is emitted;
- keep Reason/Code and new-conversation interactions internally consistent with the existing state machine;
- retain reduced-motion and reduced-graphics behavior.

No visual redesign is required; this is a state/continuity correction within the approved P2 visual system.

### 4.12 CI and DSPy development gate

Extend CI so Reason 2.0 is validated without requiring commercial provider credentials.

The gate must:

1. validate `P2-V0.3.0` before implementation plan compilation;
2. execute mandatory DSPy SpecCritic + SpecCompiler for v0.3.0;
3. run Reason/context/scope/protected-policy unit tests;
4. validate Reason development and promotion suites;
5. evaluate the known-good recorded baseline;
6. prove equivalent challenger promotion passes;
7. prove continuity, status-honesty, and scope regressions are rejected;
8. run inherited v0.1/v0.2 backend/evaluation gates;
9. run inherited client type/state/export/browser/Skia gates;
10. retain Reason evaluation and DSPy development evidence artifacts.

A provider-backed Reason optimizer run is not required for v0.3.0 validation, but any later provider-backed challenger must pass the protected promotion suite before promotion.

## 5. Non-goals

- Code 2.0 implementation.
- Closed-loop code repair.
- Semantic/vector memory retrieval.
- Model-generated long-term conversation summaries.
- Autonomous editing/approval of a materially changed software specification.
- Production authentication/authorization.
- Production migration framework completion.
- Provider-backed MIPROv2 optimization as a prerequisite for validating the Reason 2.0 architecture.
- Model-as-judge as sole promotion authority.
- Exposing hidden chain-of-thought, DSPy rationale, or scratchpads.
- Replacing the approved P2 visual language.
- Treating synthetic Reason benchmarks as a complete measure of general intelligence.

Recommended additions:

```text
services/api/parallax_api/intelligence/
  ├─ context.py
  ├─ scope.py
  ├─ reason.py
  └─ coordinator.py

benchmarks/parallax-engineering/
  ├─ reason-development-v0.1.json
  ├─ reason-promotion-v0.1.json

      ├─ reason-baseline.json
      ├─ reason-equivalent.json
      ├─ reason-continuity-regression.json
      ├─ reason-status-regression.json
      └─ reason-scope-regression.json
```

Exact filenames may change if the same dependency boundaries remain clear.

Dependency direction:

- context composition is deterministic and provider-independent;
- scope/reason programs depend on DSPy/model interfaces but not promotion authority;
- protected scope policy and protected Reason verification do not import optimizer implementations;
- promotion suites/evaluator rules remain within the v0.2 protected evaluation boundary;
- API routes orchestrate services/coordinators rather than embedding model logic;
- client state reflects server decisions but does not become scope-decision authority.

## 7. Reason quality contract

Reason 2.0 quality is judged by observable behavior, not hidden reasoning traces.

The protected contract prioritizes:

1. active-objective/spec fidelity;
2. multi-turn continuity;
3. latest explicit user correction precedence;
4. material-change containment;
5. uncertainty and release/status honesty;
6. security/secret non-disclosure;
7. useful directness and concision;
8. graceful failure when protected validation cannot be satisfied.

Development optimization may improve prompts, demonstrations, typed DSPy signatures, context formatting, routing heuristics, and bounded program strategies. It may not change the protected promotion suite, evaluator implementation, protected thresholds, or release-state definitions in the same optimization loop.

## 8. Security and privacy

- No provider credentials or environment values are sent to the client or stored in Reason traces.
- No hidden chain-of-thought, DSPy rationale, or scratchpad text is persisted or emitted.
- Structured uncertainties/assumptions/material factors must be short observable claims suitable for evidence review, not unrestricted hidden reasoning.
- Conversation content is treated as untrusted model input; it cannot redefine protected system/evaluation policy.
- Reason benchmark cases and fixtures remain repository-safe and contain no private user/project exports or real secrets.
- Secret-detection checks run against recorded benchmark/evidence artifacts.
- Material-scope classification cannot itself authorize deployment, merge, secret access, or protected threshold changes.

## 9. Observability

Reason claims must be traceable to observable program/evaluation evidence.

Runtime traces identify the scope and Reason program versions, model attempts, protected decision/result, context digest/turn count, and final state without storing hidden reasoning.

Offline Reason evaluation artifacts identify the exact suite/evaluator/program fixture versions used for any validation or promotion claim.

Logs may summarize outcomes, but a Reason program may not be called validated/promoted solely from subjective manual review.

## 10. Failure handling

- Context cannot be assembled within protected limits: return sanitized recoverable error; do not discard durable messages.
- Scope program fails on Luna: escalate to Terra, then Sol under the same protected result contract.
- Scope remains low-confidence for a potentially material change: prefer `CLARIFY` over silent amendment or silent substantive continuation.
- Reason program output fails protected validation: escalate under the router policy.
- All routed models fail: preserve the user turn, return `ERROR`, and avoid false completion status.
- Protected `SPEC_AMENDMENT`: preserve conversation, set explicit amendment state, do not produce substantive continuation against the old objective.
- Skia unavailable: use inherited reduced-graphics behavior; Reason semantics remain functional.
- Evaluation challenger regresses protected continuity/status/scope behavior: reject promotion even if aggregate score improves elsewhere.

## 11. Acceptance criteria

### AC-01 Spec-first Reason continuation
`P2-V0.3.0` is committed before substantive Reason 2.0 implementation, passes the protected spec-only gate, and receives mandatory DSPy SpecCritic + SpecCompiler evidence before implementation is treated as authorized.

### AC-02 Deterministic bounded context
Automated tests prove context composition preserves active spec/current turn/recent chronological messages, labels message roles, applies deterministic truncation, and gives later explicit user corrections precedence over conflicting inferred assumptions.

### AC-03 Server-side scope authority
Normal response behavior no longer depends on a client-provided material-change Boolean as the source of truth; server-side scope evaluation plus protected policy produces `CONTINUE`, `CLARIFY`, or `SPEC_AMENDMENT`.

### AC-04 Typed scope contract
Scope results have a validated enum, bounded confidence/material factors, explicit program version, no hidden-reasoning fields, and protected low-confidence material-change behavior.

### AC-05 Multi-turn continuity
Protected tests/benchmark cases prove an ordinary follow-up continues the active objective/specification instead of restarting or treating the turn as a new isolated request.

### AC-06 Correction precedence
Protected tests/benchmark cases prove a later explicit user correction overrides an older conflicting inferred assumption in the Reason context/answer contract.

### AC-07 Material amendment containment
A protected material-objective-change case transitions the conversation to `SPEC_AMENDMENT`, emits the explicit amendment state, preserves prior conversation history, and does not generate a substantive continuation under the old approved objective.

### AC-08 Focused clarification
A protected ambiguous-but-blocking case produces one focused clarification request while keeping the conversation `ACTIVE`; uncertainty alone does not cause gratuitous clarification when a safe reversible answer is possible.

### AC-09 Typed Reason result
Reason output includes answer, bounded confidence, bounded material uncertainties/assumptions, and program version; observable metadata is not hidden chain-of-thought.

### AC-10 Protected Reason verification and escalation
Protected-invalid Reason outputs are rejected and can trigger Luna → Terra → Sol escalation; all-model failure returns a sanitized recoverable error without losing the durable user turn.

### AC-11 Status and uncertainty honesty
Dedicated protected cases reject false generated/validated/deployed claims and unsupported certainty when supplied evidence is incomplete.

### AC-12 Security and hidden-reasoning protection
Automated tests reject secret leakage and observable chain-of-thought/scratchpad fields; a request for hidden reasoning receives a concise safe rationale/summary rather than hidden chain-of-thought.

### AC-13 Reason trace evidence
Public response traces include context digest/turn count, scope/Reason program versions, protected scope decision, model attempts, protected verification result, override indicator, and final state without secrets or hidden reasoning.

### AC-14 Reason benchmark separation
Repository-safe Reason `development` and `promotion` suites cover the ten required behavioral cases; optimizer-facing interfaces cannot consume protected promotion contracts or authorize promotion from development evidence.

### AC-15 Protected Reason promotion regressions
An equivalent challenger passes while recorded continuity, status-honesty, and material-scope regressions are each rejected with machine-readable protected reasons.

### AC-16 Client amendment UX
The client represents `SPEC_AMENDMENT` as a calm explicit hand-off state rather than generic `ERROR`, preserves the user conversation, and retains reduced-motion/reduced-graphics behavior.

### AC-17 Existing regression gates
All validated v0.1.0 foundation, preview-readiness, v0.2.0 protected evaluation, frontend/Skia, and mandatory DSPy development gates remain green.

## 12. Release gate

v0.3.0 may be called **generated** when the approved specification, Reason/context/scope implementation, Reason benchmark suites, and recorded evaluation fixtures exist.

It may be called **validated** only when:

- all v0.3.0 acceptance tests pass;
- mandatory DSPy SpecCritic + SpecCompiler evidence exists for `P2-V0.3.0`;
- the Reason development/promotion suites validate;
- the known-good/equivalent Reason promotion path passes;
- continuity, status-honesty, and scope regressions are demonstrated as rejected;
- inherited v0.1.0/v0.2.0 backend/evaluation/client/Skia gates remain green;
- `CURRENT-STATE.md` records the exact validated implementation head and evidence run.

It may be called **deployed** only after an explicit P2 deployment succeeds.

It may be called **deployment-verified** only after target-environment persistence, Reason continuity, SSE/optical behavior, protected amendment handling, health/readiness, responsive/Skia behavior, and failure-degradation evidence are collected.

Passing v0.3.0 does not authorize automatic optimizer promotion, merging, deployment, protected-threshold changes, or silent specification mutation.
