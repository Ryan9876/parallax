## 1. Objective

Prevent an overlapping autonomous continuation request from converting a legitimate in-flight protected worker into a durable Engineering Run failure.

Production evidence from Engineering Run `3a1ba66a-5649-42b6-81ee-91684fe06bbc` proved that two requests can enter the same IMPLEMENT revision before the first request commits a stage transition. The second request encounters the first request's valid active worker lease. The current bridge converts that expected concurrency conflict into `AgenticRuntimeError`, which is then classified as candidate admission failure and persisted as `AUTONOMOUS_IMPLEMENT_FAILED` even while the original lease owner continues making protected progress.

P2-V0.23.49 makes active worker ownership a non-failure single-flight boundary. It does not weaken lease exclusivity or recovery rules.

## 2. Scope

Included:

- preserve active worker lease conflicts as bounded concurrency rather than implementation/candidate failure;
- map the protected worker contention condition to structured HTTP 409 `AUTONOMY_IN_PROGRESS`;
- ensure the conflicting request does not mutate Engineering Run, attempt, worker, source-lineage or acceptance state;
- preserve expired-lease PROCESS_LOSS classification and bounded reassignment;
- add same-hook client single-flight protection before network dispatch;
- reconcile `AUTONOMY_IN_PROGRESS` read-only in the client instead of publishing a Needs Attention failure;
- focused server and client concurrency regression tests;
- full inherited regression and exact-source deployment verification;
- Architecture v3.58 after semantic validation.

## 3. Non-goals

This release does not:

- allow two workers to share or steal one mutation lease;
- extend worker lease duration or retry budgets;
- change PROCESS_LOSS, stale-lease, checkpoint, candidate-repair or worker-reassignment authority;
- auto-complete a failed Engineering Run;
- mutate the user's currently failed QA Test run as part of implementation;
- change Work Specification acceptance semantics;
- add browser-verification evidence;
- widen source, provider, GitHub, Vercel, REVIEW, merge or production authority.

## 4. Security

The active worker lease remains the sole mutation owner. A competing autonomous request may observe that protected ownership but cannot acquire, replace, renew, checkpoint, stall or fail it.

Only an unexpired active lease conflict is classified as `AUTONOMY_IN_PROGRESS`. Expired leases continue through the existing server-owned PROCESS_LOSS classification and bounded recovery path. STALLED, RECOVERING, READY_FOR_INTEGRATION, FAILED, HUMAN_REQUIRED and other worker states retain their existing closed transitions.

The conflict response contains a fixed server-owned code/message only. It exposes no lease owner identifier, provider payload, model output, checkpoint body, credential or hidden runtime detail.

Client suppression is defense in depth only. Server-side worker ownership remains authoritative across refreshes, multiple tabs, duplicate network delivery and multiple client instances.

## 5. Acceptance criteria

### AC-01 Active worker contention is not an implementation failure
When an autonomous IMPLEMENT request encounters a valid unexpired worker lease owned by another request, the conflict must escape candidate-admission and implementation-failure classification. No `AUTONOMOUS_IMPLEMENT_FAILED` attempt may be persisted by the competing request.

### AC-02 Concurrency response is fixed and structured
The API returns HTTP 409 with fixed code `AUTONOMY_IN_PROGRESS` and bounded ordinary-language guidance. The response contains no worker owner ID, checkpoint payload, model/provider detail or raw exception text.

### AC-03 Engineering Run and worker state remain unchanged by the loser
The competing request must not change run state/revision/resume stage/failure code, worker state/revision/checkpoint/lease, source lineage, acceptance evidence or durable stage attempts.

### AC-04 Existing expired-lease recovery remains intact
An expired worker lease continues to classify PROCESS_LOSS and may enter the existing STALLED → RECOVERING → REASSIGNED path only when current protected recovery policy admits it.

### AC-05 Terminal and protected worker states remain fail-closed
Non-active lease conflicts that represent terminal, human-required, ready-for-integration or otherwise incompatible worker state remain governed by their existing protected rules and are not mislabeled as ordinary in-flight contention.

### AC-06 Same-hook client continuation is single-flight
Within one `useEngineeringRun` instance, synchronous duplicate continuation entry cannot issue a second autonomy request while the first continuation promise is active.

### AC-07 Client treats AUTONOMY_IN_PROGRESS as read-only reconciliation
A structured 409 `AUTONOMY_IN_PROGRESS` causes the client to read the latest canonical Engineering Run and keep it visible without publishing a Needs Attention failure. It does not invent progress or start another request in the same call.

### AC-08 Other API failures retain current handling
409s without `AUTONOMY_IN_PROGRESS`, provider failures, validation failures and ordinary protected stage failures continue through existing error/recovery behavior.

### AC-09 Operation/revision authority remains unchanged
Automatic operation keys and expected Engineering Run revisions remain server-bound exactly as before. Single-flight handling grants no stage transition or replay authority.

### AC-10 Regression proves the observed race cannot recur
Automated tests model one request holding an active worker lease while a second request enters the same IMPLEMENT revision and prove the second request cannot mark the run failed while the first owner remains valid.

## 7. Server design

### 7.1 Worker bridge

`DurableAgentWorkerBridge.acquire` retains existing recovery handling for expired, STALLED and RECOVERING workers. When repository acquisition reports a lease conflict and protected health proves an unexpired active mutation lease, the bridge preserves `WorkerLeaseConflict` as concurrency state instead of translating it to `AgenticRuntimeError`.

### 7.2 Candidate boundary

Because `WorkerLeaseConflict` is not an `AgenticRuntimeError`, the existing candidate-admission wrapper must not reinterpret it as candidate failure. It propagates without invoking candidate failure persistence.

### 7.3 API boundary

The route invocation boundary catches `WorkerLeaseConflict` before the broader `WorkerRecoveryError` mapping and returns structured HTTP 409 `AUTONOMY_IN_PROGRESS`.

## 8. Client design

A synchronous ref guards the continuation promise because React state updates are not a mutual-exclusion primitive. If another caller enters the same hook while continuation is active, it returns the currently supplied canonical run without another POST.

If the server returns `AUTONOMY_IN_PROGRESS`, the client performs one read-only latest-run reconciliation. It clears no server state, starts no new autonomy request and does not publish failure UI.
