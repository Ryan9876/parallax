# Parallax 2.0 v0.1.0 — Foundation Specification

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.1.0
Method: Spec-first + DSPy-governed optimization

## 1. Objective

Build the first real Parallax 2.0 foundation as a new product track. The release must prove that Parallax can preserve the calm, conversation-first strengths of P1 while introducing a purpose-built architecture for persistent context, DSPy-optimizable AI programs, protected evaluation, and a distinctive Skia-driven visual language.

Parallax 2.0 must not merely *contain* spec-first and DSPy features. Its own development workflow must be organized around an explicit specification, measurable evaluation, DSPy-compatible program boundaries, and traceable implementation evidence.

## 2. User outcome

A user can open Parallax 2.0, start or resume a durable conversation, submit a message, see a calm animated Parallax identity and living surface, and receive a response that is visually inscribed with the optical laser-typesetter effect. The conversation model must be capable of being driven by a DSPy program and a model-routing policy without coupling the UI directly to a provider.

## 3. Fixed product decisions

- Product name: Parallax 2.0.
- Product surface: conversation-first, not a dashboard or IDE.
- Frontend: Expo + React Native + React Native Skia, targeting web first while preserving a universal/native path.
- Intelligence service: Python + FastAPI + DSPy.
- Model routing order: `openai/gpt-5.6-luna` → `openai/gpt-5.6-terra` → `openai/gpt-5.6-sol`.
- Persistence: conversations and messages must be server-side durable. Browser storage may cache drafts but is not the source of truth.
- Optimization boundary: DSPy may optimize AI-program behavior but may not modify protected acceptance criteria or release gates.
- Visual baseline: evolve the calmer P1 visual language rather than replacing it with an experimental dashboard composition.
- Signature response behavior: optical laser print head sweeps the active response and reveals text behind it.
- Signature ambient behavior: a Skia living surface that remains calm at idle and becomes moderately more energetic only while Parallax is working.
- Logo: a representative Parallax mark with calm, non-spinner motion; reduced-motion users see a stable static mark.

## 4. Scope for v0.1.0

### 4.1 Frontend

Build a single primary conversation screen with:

- Parallax 2.0 animated logo.
- Reason / Code mode selector.
- Recent-conversation rail on wider screens and compact mobile behavior.
- User message presentation.
- Assistant response presentation.
- Skia `LivingSurface` background.
- Skia-enhanced `LaserTypesetter` response renderer.
- Composer with draft retention.
- Clear state presentation: idle, thinking, responding, verifying, complete, error.
- Reduced-motion fallback that keeps all text readable and removes continuous animation.

### 4.2 Backend

Build a FastAPI service with:

- health endpoint;
- conversation creation/list/get;
- message append;
- streaming response endpoint contract;
- SQLite development persistence through SQLAlchemy, configurable to PostgreSQL with `DATABASE_URL`;
- DSPy reasoning program boundary;
- model router with Luna → Terra → Sol escalation;
- protected evaluation contract;
- structured trace object for model attempts and validation outcomes.

### 4.3 DSPy development system

Build repository tooling that treats specifications as program inputs:

- `SpecCompiler` DSPy program converts an approved specification into a structured implementation plan;
- `SpecCritic` DSPy program searches for missing acceptance criteria, contradictions, hidden dependencies, and unsafe optimization boundaries;
- deterministic protected metrics validate required sections and acceptance criteria before any optimizer result can be promoted;
- an optimizer entrypoint supports MIPROv2 for improvement against a development set when provider credentials are available;
- compiled plans are persisted as reviewable artifacts under `specs/compiled/`;
- CI validates that implementation changes reference an existing spec ID.

The bootstrap repository may contain an initial human-reviewed compiled plan because this execution environment cannot access package registries or model-provider credentials. The repository must make this limitation explicit and must not represent an unexecuted optimizer run as completed.

## 5. Non-goals for v0.1.0

- Full P1 feature parity.
- Autonomous production deployment.
- Multi-user authentication/authorization.
- Plugin marketplace.
- Voice mode.
- Full autonomous code-generation loop.
- Production-grade vector memory.
- Skottie dependency unless a concrete logo/motion requirement cannot be satisfied more simply with Skia.

## 6. Architecture requirements

### Frontend boundaries

- Visual effects must not own message text state.
- Assistant text remains normal accessible/selectable React Native text.
- Skia supplies background material, glow, beam, masks, and motion accents.
- Animation state derives from the same explicit response-state machine used by product logic.
- UI must continue to function if Skia fails to load; web shows a static fallback surface.

### Backend boundaries

- API routes depend on service interfaces, not provider SDKs directly.
- Provider routing is isolated in an intelligence adapter.
- Persistence is isolated behind repositories.
- DSPy programs are isolated behind a `ReasoningProgram` interface so evaluation and compiled program versions can change without changing route contracts.
- Protected metrics live outside optimizer-controlled modules.

## 7. State model

Conversation lifecycle:

`NEW → SPEC_DRAFT → AWAITING_APPROVAL → ACTIVE`

During `ACTIVE`:

- ordinary follow-ups remain ACTIVE;
- a material objective/scope change creates `SPEC_AMENDMENT`;
- approval returns the conversation to ACTIVE;
- only explicit New Chat creates a new conversation.

Response lifecycle:

`IDLE → THINKING → RESPONDING → VERIFYING → COMPLETE`

Error may be entered from THINKING, RESPONDING, or VERIFYING and must preserve recoverable context.

## 8. Visual / motion specification

### Living surface

The surface should feel like calm optical material rather than a generic gradient:

- warm mineral white foundation;
- smoky transparent gray;
- restrained teal-blue;
- very soft peach and yellow-green undertones;
- slow broad interference waves;
- bright but sparse caustic highlights;
- idle amplitude low;
- thinking/responding amplitude moderately elevated;
- no distracting high-frequency movement behind readable text.

### Optical typesetter

- One precise print head advances through the active response.
- Text is revealed at the head position, not before it.
- Fresh text receives a brief cool-blue energized edge and then cools to standard typography.
- The head may reset to the beginning of a wrapped line without a theatrical travel animation.
- Text selection/accessibility must not depend on Skia-rendered glyphs.
- Reduced motion reveals text normally with no beam.

### Animated logo

The mark represents parallax as two gently displaced optical planes that slowly drift into and out of near-alignment around a stable center point.

- movement is subtle and periodic, not continuous rotation;
- 6–10 second calm cycle;
- a restrained glint may pass through the center when planes approach alignment;
- reduced motion shows the centered static mark.

## 9. Security requirements

- No provider secret in client code or repository.
- Backend reads provider/API secrets from environment variables.
- API returns sanitized errors.
- Conversation IDs are opaque UUIDs.
- SQL is parameterized via ORM.
- CORS defaults to configured origins, not wildcard in production configuration.
- Optimizer artifacts must never contain secrets.

## 10. Observability requirements

Every response trace records at minimum:

- conversation ID;
- response ID;
- spec ID;
- mode;
- program version;
- attempted model IDs in order;
- per-attempt status and duration;
- validation result;
- final state.

Do not store chain-of-thought. Traces record observable execution metadata and concise model output/evaluation artifacts only.

## 11. Acceptance criteria

### AC-01 Spec-first gate
A build validation command fails when a material implementation plan does not reference an existing approved spec ID.

### AC-02 DSPy boundary
The Python service contains DSPy signatures/modules for specification compilation and conversation reasoning, plus an optimizer entrypoint with protected metrics outside optimizer-controlled code.

### AC-03 Persistence
A created conversation and appended messages can be read back after constructing a new application/service instance against the same development database.

### AC-04 Multi-turn contract
A follow-up message can be appended to an ACTIVE conversation without creating a new spec unless a material-scope-change flag is explicitly raised.

### AC-05 Routing
The configured router attempts Luna, then Terra, then Sol when preceding attempts fail a provider or validation contract.

### AC-06 Visual state linkage
The same response state machine that controls product status also controls living-surface energy and optical-typesetter activity.

### AC-07 Selectable text
Assistant message content is rendered as normal accessible text, not Skia glyphs.

### AC-08 Reduced motion
With reduced motion enabled, the living surface becomes static, the logo stops animating, and responses appear without the laser beam.

### AC-09 Responsive layout
The primary conversation screen remains usable at 390×844 mobile, 768×1024 tablet, and 1440×900 desktop sizes without clipped message text or controls.

### AC-10 Failure degradation
If Skia cannot initialize on web, the chat remains usable with a static material background and normal text rendering.

### AC-11 Backend tests
Automated tests cover health, conversation persistence, multi-turn append, routing fallback, and protected metric behavior.

### AC-12 Frontend tests
Automated tests cover reducer/state transitions and deterministic motion-state mapping.

### AC-13 Build
Frontend type-check and web export succeed; backend Python compile/tests succeed in a network-enabled environment with declared dependencies installed.

## 12. Release gate

v0.1.0 may be called **generated** when implementation artifacts exist.
It may be called **validated** only after the declared automated checks pass.
It may be called **deployed** only after a deployment action succeeds.
It may be called **deployment-verified** only after target-environment health and UI evidence are collected.
