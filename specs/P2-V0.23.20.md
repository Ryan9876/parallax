## 1. Objective

Close the provider-compatibility defect exposed by the canonical W9-S1 Decision Ledger acceptance attempt against the explicitly approved fresh repository `Ryan9876/parallax-qa1` without weakening positive empty-repository proof.

The production attempt used deployed API source `ea00a943d4bc5f00f0f5416881d482c0f799be63`, positively verified the target as empty before execution, created the canonical Project / Work Specification / Engineering Run, and then stopped before mutation during source bootstrap. GitHub's real REST behavior for `GET /repos/Ryan9876/parallax-qa1/git/ref/heads/main` on the empty repository is HTTP 409 with exact message `Git Repository is empty.`. The existing protected greenfield inspector delegates that ref read to the ordinary GitHub ref helper, which accepts 404 as no head but treats 409 as conflict. The surrounding greenfield fallback then conservatively rethrows the prior public-source error, producing the observed `PROVIDER_INVALID_RESPONSE` bootstrap failure.

This release recognizes only GitHub's exact empty-repository ref response as positive no-head evidence inside the already-authenticated greenfield inspection boundary. Ordinary ref behavior and unrelated conflicts remain unchanged.

## 2. Fixed decisions

- Positive repository identity remains mandatory before empty classification: the authenticated repository metadata response must be successful, structured, and match the exact canonical owner/repository plus a valid default branch.
- Only the greenfield inspection adapter may normalize an absent head for this compatibility case. The shared `GitHubRestProviderClient._get_ref()` behavior remains unchanged.
- Within greenfield inspection, HTTP 404 for the exact default-branch ref continues to mean no head.
- Within greenfield inspection, HTTP 409 means no head only when the response is valid JSON object evidence whose exact `message` is `Git Repository is empty.`.
- Any other HTTP 409, 422, malformed response, missing/altered message, authorization failure, rate limit, timeout, provider outage, repository mismatch, or ambiguous response remains fail-closed.
- The exact 409 compatibility rule is read-only. It creates no source, Git ref, commit, branch, pull request, deployment, or durable provider mutation during PLAN/bootstrap.
- The existing zero-file `greenfield` lineage contract, non-empty accepted implementation requirement, REVIEW-only `repository.initialize-empty` action, deterministic bootstrap/cleanup baseline, bounded branch/commit/PR flow, exact Vercel Preview read-back, and human REVIEW ceiling remain authoritative.
- The approved target `Ryan9876/parallax-qa1` must remain empty until an exact-source deployment containing this correction is READY and the canonical W9-S1 replay reaches the REVIEW delivery boundary.
- No benchmark identity, repository name, target repository ID, Decision Ledger token, or expected application solution may be inspected by runtime code to trigger this behavior.

- Completing REVIEW automatically.

## 5. Security and reliability

An empty repository is a privileged classification because it authorizes creation of a zero-file durable root and later enables a REVIEW-only Git initialization transaction. Therefore the compatibility fix cannot infer emptiness from status code alone.

The allowed 409 is evaluated only after the authenticated repository metadata read has proved the canonical repository identity and default branch. The ref response must be exactly the documented/observed empty-repository signal. Any deviation falls back to the ordinary strict provider status handling. This keeps permission failures, repository conflicts, provider errors, malformed payloads and concurrent source creation fail-closed.

The production target is preserved unchanged after the failed attempt. The original run stopped at PLAN and performed zero out-of-band or provider source mutations. The next canonical replay must re-prove the target state before execution.

## 6. Acceptance criteria

### AC-01 Real GitHub empty-ref response is accepted narrowly
After exact repository metadata verification, an HTTP 409 response from the canonical default-branch ref endpoint with JSON `{"message":"Git Repository is empty."}` yields `head_revision=None` and positive `is_empty=true`.

### AC-02 Existing 404 no-head behavior remains equivalent
The existing HTTP 404 default-ref response still yields `head_revision=None` only inside positive greenfield inspection.

### AC-03 Arbitrary 409 remains rejected
A 409 with any other message or invalid/missing JSON is not normalized to empty and remains a provider failure.

### AC-04 Shared Git ref semantics remain unchanged
`GitHubRestProviderClient._get_ref()` is not relaxed; ordinary branch/source paths continue to treat non-404 conflicts according to existing strict behavior.

### AC-05 Repository identity remains positive and exact
Missing repository metadata, wrong `full_name`, invalid/missing default branch, authorization failure, or provider error cannot create a greenfield root.

### AC-06 No pre-REVIEW mutation
The corrected inspection and greenfield root bootstrap perform no GitHub mutation. Repository initialization remains isolated to verified REVIEW delivery.

### AC-07 Greenfield authority remains bounded
Zero-file root, non-empty implementation, accepted lineage, deterministic REST-compatible baseline, exact branch/PR/Preview binding, and REVIEW ceiling remain unchanged.

### AC-08 Existing repository paths do not regress
Focused greenfield tests plus the full API regression suite keep commit-bearing source bootstrap and existing GitHub provider behavior green.

### AC-09 Governed release gates remain green
The exact release head passes spec validation, committed DSPy plan validation, API/contracts, Bounded Autonomy, protected promotion and all other applicable release gates before merge; main promotion performs fresh DSPy SpecCritic/SpecCompiler compilation and verification.
