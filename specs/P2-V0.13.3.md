# Parallax 2.0 — P2-V0.13.3

Status: Approved implementation specification
Date: 2026-08-22

## Objective

Correct the Work Specification amendment lifecycle so that explicitly approving the current replacement specification releases a conversation from `SPEC_AMENDMENT` and allows governed Code execution to proceed again.

## Problem

A material scope change correctly moves a conversation to `SPEC_AMENDMENT`, but approving the newly drafted replacement Work Specification currently changes only the specification record. The conversation remains stuck in `SPEC_AMENDMENT`, which leaves the UI showing a stale stop state and can block Engineering Run activation even though the operator has explicitly approved the amended contract.

## Requirements

1. Keep `SPEC_AMENDMENT` fail-closed until an operator explicitly approves a new current Work Specification draft.
2. Approval may clear the conversation stop state only when the approved item was the latest `DRAFT` for that same conversation at the time approval began.
3. On that valid amendment approval path, transition the conversation from `SPEC_AMENDMENT` to `ACTIVE` after specification approval succeeds.
4. Approving or re-reading an older/superseded/already-approved specification must not independently clear a newer amendment stop.
5. Preserve existing approval semantics, revision history, Code binding, autonomy authority boundaries, authentication, and persistence.
6. Add deterministic API/service coverage proving both the resume path and the negative safety cases.

## Acceptance criteria

- A conversation in `SPEC_AMENDMENT` with a current draft becomes `ACTIVE` after that draft is approved.
- The draft becomes `APPROVED` and remains the durable latest approved revision.
- A conversation not in `SPEC_AMENDMENT` is not otherwise mutated by approval.
- A non-current or non-draft specification cannot be used as a shortcut to clear an amendment stop.
- Existing Work Specification, Reason, Engineering Run, bounded-autonomy, and full API regression tests remain green.
- No database migration is required.

## Risks

- Clearing the stop too broadly could let stale approval bypass a material-scope gate. Mitigation: require the pre-approval record to be the current draft and the conversation to already be in `SPEC_AMENDMENT`.
- Two repository commits make the approval/status update a short two-step operation. Existing repository architecture already owns commits internally; this patch preserves that architecture rather than introducing a larger transaction refactor. A future unit-of-work refactor may make these changes atomic across repositories.

## Non-goals

- Changing how scope changes are detected.
- Automatically approving specifications.
- Expanding autonomous implementation, Git, or deployment authority.
- Redesigning the Work Specification UI.
