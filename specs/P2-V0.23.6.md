## 1. Objective

Close the remaining W8-S2 .NET protected-validation readiness gap by binding admitted validation profiles to server-owned, prequalified, source-free execution snapshots rather than assuming one existing snapshot is suitable for every ecosystem.

Production Python source-only acceptance has already proven the general protected engineering lifecycle through PLAN, IMPLEMENT, BUILD, TEST, VERIFY, REVIEW, and authenticated exact-lineage ZIP handoff. The separate public `github:Ryan9876/ot-time` replay now reaches deterministic `dotnet-v1` selection but fails closed in PREPARE because the current pinned execution snapshot does not provide the admitted .NET toolchain. This slice fixes that execution-substrate qualification defect without changing validation commands, source authority, delivery semantics, or lifecycle authority.

## 2. Fixed decisions

- Validation profile selection remains deterministic from exact server-materialized source and remains separate from execution-snapshot selection.
- Snapshot identity is server-owned configuration keyed only by the finite released validation profile identity; repository text, user text, model output, benchmark identity, Project metadata, and runtime tool output cannot select or alter a snapshot.
- The established `python-v1` path retains the existing `PARALLAX_EXECUTION_SNAPSHOT_ID` compatibility contract and current default snapshot unless an explicitly released common-snapshot override is configured.
- `node-v1` remains a reserved finite profile identity mapped to the same common snapshot for compatibility, but generic Node source remains fail-closed under the existing `NODE_FIXED_VALIDATION_UNAVAILABLE` selector contract. This slice does not admit Node source or add Node validation commands.
- `dotnet-v1` requires an explicit .NET-qualified snapshot identity through a dedicated server-owned environment contract. Missing or invalid .NET snapshot configuration fails closed before sandbox creation; it never falls back to the existing common snapshot.
- Future profile-specific snapshots or new source admissions may be added only by released server policy. No arbitrary ecosystem name may become an environment-variable lookup or snapshot identifier.
- Candidate validation and accepted-lineage BUILD/TEST/VERIFY select the same snapshot from the same admitted profile identity.
- Snapshot selection does not change the existing fixed profile commands. For .NET, PREPARE remains `dotnet restore <target> --nologo` under the exact NuGet-domain allowlist; BUILD/TEST/VERIFY remain fixed offline `dotnet` commands after verified deny-all lock-down.
- Toolchain provisioning is a separate server-owned release operation. User runs do not install operating-system runtimes, SDKs, or arbitrary packages to compensate for an unqualified snapshot.
- Every production-configured snapshot must pass a release/build preflight that restores the exact snapshot with deny-all network, verifies exact snapshot identity, proves the required fixed toolchain probes, and proves that the protected source root contains no repository source.
- A snapshot may contain server-owned runtime/toolchain dependencies but must contain no Project repository source, user source, application environment, provider credential, Git credential, deployment credential, or reusable secret.
- Source-only delivery remains independent from Vercel application deployment. Vercel Sandbox remains an isolated execution provider only.
- REVIEW remains the autonomous ceiling.

## 3. Server-owned snapshot policy

The execution environment exposes a finite released mapping from validation profile identity to snapshot configuration.

Initial policy:

- `python-v1` → existing compatible common execution snapshot contract;
- reserved `node-v1` → the same common execution snapshot contract without changing the existing fail-closed Node source-admission contract;
- `dotnet-v1` → dedicated .NET execution snapshot contract with no common-snapshot fallback.

Snapshot identifiers must satisfy the existing bounded `snap_...` identity validation. Unknown profile IDs, missing required .NET configuration, malformed values, whitespace variants, or caller-supplied snapshot identities fail closed.

The policy must not derive environment variable names dynamically from untrusted profile text. The admitted mapping is a finite code-owned registry or equivalent immutable released policy.

## 4. Candidate and accepted-lineage execution

For both disposable candidate validation and accepted-lineage execution:

1. Select the exact validation profile from canonical materialized source using the existing P2-V0.23.5 rules.
2. Resolve the server-owned snapshot identity for that admitted profile.
3. Restore only that exact snapshot and verify the sandbox reports the same snapshot identity before source transfer or protected execution.
4. Transfer the exact candidate or accepted-lineage source after snapshot restoration.
5. Run the existing profile-owned PREPARE contract, if required.
6. Verify the active sandbox network transitions to `deny-all` before BUILD/TEST/VERIFY.
7. Record the selected profile ID/digest and exact execution snapshot ID in bounded evidence.

Candidate and canonical execution may not select different snapshots for the same profile/configuration during one release. The snapshot is infrastructure/toolchain state only and does not replace source-lineage identity.

## 5. Production snapshot readiness preflight

Production deployment must fail closed if a required configured execution snapshot is not qualified.

The preflight must at minimum verify:

### Existing common snapshot

- exact snapshot restore succeeds;
- effective sandbox network is deny-all;
- established Python offline dependencies required by the existing protected Parallax validation remain available;
- fixed `node --version` readiness probe succeeds so the reserved finite Node profile mapping does not lose its common-image executable compatibility; this probe does not admit Node source or create Node command authority;
- protected source root contains no repository source.

### .NET snapshot

When `dotnet-v1` support is production-enabled:

- the dedicated .NET snapshot identity is present and valid;
- exact snapshot restore succeeds;
- effective sandbox network is deny-all;
- fixed `dotnet --info` probe succeeds without network or application environment;
- protected source root contains no repository source.

The release preflight must not run `dotnet restore`, access NuGet, inject credentials, or inspect user repositories. Its job is to prove the server-owned execution image has the required toolchain before production traffic can select it.

## 6. Snapshot provisioning boundary

Provisioning or refreshing a profile snapshot is a release/operations action, not an Engineering Run action.

A governed provisioning mechanism may build a Vercel Sandbox snapshot or a Vercel Container Registry-backed image/snapshot, but it must:

- use a fixed server-owned toolchain recipe and pinned/controlled dependency sources;
- contain no application or Project source;
- contain no persistent secrets or credentials;
- verify the intended toolchain before snapshot publication;
- produce an immutable non-expiring snapshot/image identity suitable for exact production configuration;
- be separately evidenced before production configuration changes.

The runtime must not auto-provision, mutate, upgrade, or repair snapshots in response to user requests. Failure to provision is an operations/readiness failure, not permission to broaden PREPARE.

## 7. Security and authority requirements

- Snapshot selection authority is finite, released, server-owned, and profile-bound.
- No generic environment-variable lookup from user/model/repository values.
- No repository-defined scripts, MSBuild command text, package sources, shell fragments, or toolchain installers become executable authority.
- No application environment or secrets enter candidate or accepted-lineage sandboxes.
- PREPARE retains its exact package-domain allowlist and is the only validation-time network window for profiles that require dependency restore.
- BUILD/TEST/VERIFY retain verified `deny-all` networking.
- Snapshot contents cannot establish source authority, accepted lineage, Project identity, source admission, deployment authority, or REVIEW completion.
- Missing/invalid/unqualified profile snapshots produce bounded non-success and no fabricated lifecycle progress.
- Existing tenant/auth, single-writer source acceptance, immutable lineage, evaluator precedence, source-only handoff, Vercel Preview, merge, deployment, and REVIEW ceilings do not change.

## 8. Acceptance criteria

### AC-01 Deterministic profile-to-snapshot mapping
`python-v1`, reserved `node-v1`, and `dotnet-v1` resolve only through a finite server-owned mapping. Python and the reserved Node identity use the existing common snapshot; .NET requires its dedicated snapshot. Unknown profiles, malformed IDs, and missing required .NET configuration fail closed. User/model/repository values cannot select snapshot identity, and snapshot mapping alone cannot admit Node source.

### AC-02 Existing Python execution and Node fail-closed behavior do not regress
Candidate and accepted-lineage Python validation continue to restore the existing compatible common snapshot, preserve the established fixed commands/evidence, and pass inherited protected execution tests. Generic Node source continues to fail closed with `NODE_FIXED_VALIDATION_UNAVAILABLE`; the production common-snapshot `node --version` readiness probe preserves executable compatibility for the reserved identity without creating Node source admission or command authority.

### AC-03 .NET requires a qualified snapshot
`dotnet-v1` candidate and accepted-lineage execution use only the configured dedicated .NET snapshot. They never silently reuse the common snapshot when the .NET snapshot is absent or invalid.

### AC-04 Candidate and canonical snapshot agreement
For identical admitted profile/configuration, disposable candidate validation and accepted-lineage BUILD/TEST/VERIFY record the same exact snapshot ID alongside the same validation profile ID/digest.

### AC-05 Production preflight proves toolchain readiness
Production build preflight restores every production-enabled snapshot with deny-all network, verifies exact snapshot identity, verifies the fixed readiness probes required by released mapping (`python` dependency probe plus compatibility-only `node --version` for the common snapshot and `dotnet --info` for the .NET snapshot), and rejects any snapshot containing repository source.

### AC-06 Existing PREPARE and authority boundaries remain intact
The change does not add per-run SDK installation, generic shell commands, broader package domains, application credentials, source mutation authority, provider/deployment authority, source-admission bypass, or REVIEW bypass. .NET restore remains the existing fixed bounded PREPARE followed by verified deny-all BUILD/TEST/VERIFY.

### AC-07 OT Time authenticated production proof
After a .NET-qualified snapshot is provisioned, configured, exact release source is deployed READY, and production preflight passes, the QA-owned source-only Project bound to `github:Ryan9876/ot-time` progresses through PLAN, IMPLEMENT, BUILD, TEST, VERIFY to REVIEW and its authenticated exact-lineage ZIP handoff verifies with no Vercel application deployment, repository-provider authorization dependency, out-of-band source edit, owner impersonation, or DB mutation.

### AC-08 Snapshot provisioning remains a source-free release operation
The governed provisioning mechanism produces an immutable non-expiring .NET-qualified execution artifact from a fixed server-owned recipe with pinned and checksum-verified dependencies, verifies the intended toolchain before publication, persists no Project/application source or reusable credentials, and cannot be invoked as part of a user Engineering Run or used to widen runtime command/network authority.

## 10. Non-goals

- Installing .NET or other operating-system toolchains during user Engineering Runs.
- Admitting generic Node source or adding Node validation commands.
- Arbitrary repository script execution or generic shell authority.
- Broadening NuGet/package network domains beyond the existing profile contract.
- Private package-feed credentials.
- Replacing Vercel Sandbox as the isolated execution provider in this slice.
- Making Vercel an application-delivery dependency for source-only Projects.
- Supporting every language/toolchain.
- Benchmark-specific or OT-Time-specific runtime branches.
- Changing source bootstrap, Project delivery mode, source-lineage acceptance, merge, deployment, or REVIEW semantics.
