## 1. Objective

Close the remaining P2-V0.23.5 OT Time acceptance gap by separating the server-owned validation command profile from the server-owned execution-environment capability that must satisfy it.

Authenticated production replay of the QA-owned source-only `github:Ryan9876/ot-time` Project selected `dotnet-v1` correctly and reached its bounded dependency PREPARE contract. The replay then failed closed with `DEPENDENCY_PREPARATION_FAILED`; both the toolchain-probe and restore exit codes were absent, both dependency output digests were the empty-string digest, and the sandbox was successfully returned to deny-all. Production execution-snapshot preflight currently proves only the existing Parallax/Python offline dependencies and does not prove the .NET SDK exists. The remaining defect is therefore execution-environment readiness, not repository authority, delivery mode, profile selection, command ownership, NuGet restore behavior, or lifecycle authority.

This slice introduces immutable profile-to-environment binding while preserving the existing execution provider, dependency PREPARE boundary, and REVIEW ceiling.

## 2. Fixed decisions

- Validation command policy and execution-environment policy are separate server-owned contracts.
- The existing Parallax/Python validation profile continues to use its currently pinned, deployment-verified execution snapshot without behavior broadening.
- `dotnet-v1` uses a separate server-owned execution environment containing a pinned .NET 8 SDK.
- The current implementation remains Vercel Sandbox snapshot-backed. This slice does not replace Vercel Sandbox as the isolated execution provider.
- Validation profile identity deterministically selects exactly one execution-environment identity from immutable released policy. Repository text, model output, user input, benchmark identity, Project metadata, or runtime request data cannot select or override a snapshot/image/runtime.
- Candidate validation and accepted-lineage BUILD/TEST/VERIFY for one validation profile use the same environment policy identity and environment digest.
- A missing, malformed, unavailable, or capability-mismatched environment fails closed with typed `EXECUTION_PROFILE_UNAVAILABLE` readiness evidence before source acceptance or lifecycle success.
- The .NET environment must prove the admitted .NET SDK capability under deny-all networking before release and before being treated as production-ready.
- Runtime dependency PREPARE remains unchanged in authority: only the profile-owned fixed command and exact NuGet-domain allowlist may use temporary package egress; BUILD/TEST/VERIFY remain deny-all and no-secret.
- Source-only Projects still require no Vercel application Project/Preview deployment target. Vercel Sandbox is Parallax control-plane execution infrastructure, not target-application deployment authority.
- REVIEW remains the autonomous ceiling.

## 3. Execution-environment policy

A protected execution environment is immutable server policy containing only server-owned values:

- environment policy ID/version;
- validation profile IDs admitted to use it;
- exact snapshot identity;
- required toolchain executable path;
- required bounded capability probe;
- required toolchain version constraint;
- policy digest.

The environment registry is finite and released with the server. Unknown validation profiles or unknown environment IDs fail closed.

### Existing Parallax/Python environment

The established Parallax/Python environment keeps the current production snapshot identity and Python dependency preflight semantics. This slice must not alter its protected BUILD/TEST/VERIFY commands, package/runtime assumptions, or previously verified source-free snapshot behavior.

### .NET environment

The initial .NET environment is a separately provisioned source-free snapshot containing the pinned .NET 8 SDK required by `dotnet-v1`.

The .NET executable lives at a server-owned absolute path under a protected toolchain directory rather than depending on a user/repository-controlled `PATH`. `dotnet-v1` invocations and its toolchain probe use that server-owned executable identity.

The exact SDK version is fixed by released policy. A future SDK update requires a new verified environment identity/policy revision rather than silently changing an existing snapshot contract.

## 4. Controlled environment provisioning

Provisioning a protected execution environment is a release-engineering operation, not an Engineering Run stage and not runtime application authority.

For the .NET environment:

1. Provisioning starts a disposable, source-free sandbox under the Parallax API project.
2. The sandbox receives no repository source, application environment, user secret, Git/provider credential, deployment credential, or model/user content.
3. Network access is restricted to the fixed server-owned Microsoft distribution domains required to obtain the exact pinned .NET SDK artifact/installer. No repository or NuGet package egress is authorized during environment provisioning.
4. Provisioning installs the SDK only into a server-owned protected toolchain directory and verifies the exact executable/version using fixed commands.
5. `/vercel/sandbox` must remain empty of repository/application source.
6. The sandbox is snapshotted. The resulting snapshot ID is recorded as non-secret server policy and the temporary provisioning mechanism is removed or disabled before release.
7. Production release preflight restores the exact .NET snapshot with deny-all networking and independently verifies snapshot identity, exact toolchain version/capability, and absence of repository source.

Provisioning failure does not change runtime policy and cannot promote a partially prepared environment.

## 5. Runtime environment selection

After exact source materialization selects one validation profile, Parallax resolves the profile's environment policy from the immutable server registry.

Candidate validation:

- select the validation profile from canonical candidate source;
- resolve the exact environment policy from the profile ID;
- restore that environment snapshot;
- require restored snapshot identity to equal the policy identity;
- run the existing bounded profile PREPARE and then BUILD/TEST/VERIFY using that same environment.

Accepted-lineage execution:

- preserve the existing pre-materialization caller command-envelope rejection;
- reconstruct exact accepted lineage;
- select the same validation profile deterministically;
- resolve the same environment policy identity/digest;
- restore and verify that environment before PREPARE/stage execution.

Environment identity and digest become bounded evidence. They do not confer source acceptance, Git/provider mutation, deployment, approval, or REVIEW authority.

## 6. Security and authority requirements

- Environment policy is server-owned immutable data; no caller, repository, model, benchmark, Project field, or manifest content may provide snapshot/image/runtime IDs.
- Snapshot IDs and toolchain paths are validated bounded identifiers before use.
- The .NET toolchain executable path is absolute and server-owned; no PATH search or repository executable shadowing may substitute it.
- Environment provisioning is source-free and no-secret.
- Provisioning domains are fixed server policy and are unavailable to normal Engineering Run BUILD/TEST/VERIFY.
- Runtime .NET dependency PREPARE keeps only the existing exact NuGet allowlist and no application/provider credentials.
- BUILD/TEST/VERIFY remain deny-all network with an empty application environment.
- Candidate validation remains disposable and cannot accept source lineage.
- Accepted-lineage execution remains exact Project/run/lineage bound.
- Missing/mismatched environment capability cannot fall back to another profile, image, host shell, generic subprocess, or ungoverned network install.
- No generic shell command, repository script, manifest target, arbitrary container image, or model/user command is introduced.
- No target-app Vercel deployment requirement is reintroduced for source-only delivery.
- No owner impersonation, tenant bypass, DB mutation, promotion bypass, or authority widening.

## 7. Acceptance criteria

### AC-01 Immutable profile-to-environment registry
A finite server-owned registry binds each admitted validation profile to exactly one protected execution environment identity/digest. Repository/model/user/request values cannot override environment selection.

### AC-02 Existing Python environment does not regress
The established Parallax/Python profile continues to resolve its current verified execution snapshot and all inherited protected execution behavior remains green.

### AC-03 Pinned .NET 8 environment
`dotnet-v1` resolves a separately pinned source-free execution environment whose server-owned absolute `dotnet` executable proves the released .NET 8 SDK version under deny-all networking.

### AC-04 Controlled source-free provisioning
The one-time .NET environment provisioning path uses only fixed server-owned SDK identity/install commands and fixed Microsoft distribution domains, receives no repository/application/provider secrets or source, verifies the exact toolchain, snapshots it, and is absent/disabled from normal runtime after provisioning.

### AC-05 Production environment preflight
Production deployment fails closed unless every runtime-admitted environment restores its exact snapshot and passes its fixed capability/version/source-free checks under deny-all networking.

### AC-06 Candidate environment binding
An OT Time-like candidate selecting `dotnet-v1` restores the .NET environment, records bounded environment identity/digest, performs bounded dependency PREPARE, and never uses the Python snapshot.

### AC-07 Accepted-lineage environment agreement
BUILD/TEST/VERIFY against accepted lineage deterministically resolve the same validation-profile/environment policy identity as candidate validation; no lifecycle request can switch environments.

### AC-08 Environment readiness fails closed
Missing snapshot, snapshot mismatch, missing executable, wrong SDK version, or provider inability returns typed non-success evidence and performs no source-lineage acceptance, Git/provider mutation, deployment mutation, or fabricated lifecycle progress.

### AC-09 Existing authority/delivery contracts remain intact
Source-only and Vercel Preview delivery semantics, tenant/auth boundaries, provider scopes, single-writer source acceptance, immutable lineage, PREPARE package-domain authority, deny-all validation, and REVIEW ceiling do not regress.

### AC-10 OT Time authenticated production acceptance
After exact production deployment, the QA-owned source-only Project bound to `github:Ryan9876/ot-time` progresses PLAN → IMPLEMENT → BUILD → TEST → VERIFY → REVIEW and the authenticated exact-lineage ZIP handoff verifies, without Vercel target deployment, Vercel repository-provider authorization, out-of-band source edit, owner impersonation, DB mutation, or authority widening.

## 9. Non-goals

- Replacing Vercel Sandbox as the current isolated execution provider.
- Installing SDKs dynamically during BUILD/TEST/VERIFY.
- Allowing user/model/repository-selected images, snapshots, runtimes, PATH entries, commands, or package domains.
- Private package-feed credentials.
- General container orchestration.
- Supporting every language/toolchain in one release.
- IIS/Azure/AWS/local deployment adapters.
- Changing P2-V0.23.4 delivery-mode semantics.
- Benchmark- or OT-Time-specific runtime branches.
