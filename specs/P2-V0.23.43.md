## 1. Objective

Correct the source-publication identity defect exposed after P2-V0.23.42 successfully admitted an ordinary commit-bearing empty repository. Distinct accepted source lineages in the same Engineering Run must receive distinct deterministic feature branches so bounded REVIEW rework can publish a replacement candidate without rewriting, deleting, or reusing the branch that represents an earlier reviewed lineage.

The change must be shared by ordinary and greenfield accepted-source delivery, preserve exact durable delivery replay for an already-published lineage, and leave every prior branch, pull request, Preview, default branch, merge boundary, and human REVIEW decision untouched.

## 2. Production finding and confirmed root cause

P2-V0.23.42 is merged as exact source `9e169ac707126c078195c75403e2d7c58bae1dec`; post-merge Workstream Spec Validation `33707913803` and P2 CI `33707913909` passed, and exact production API deployment `dpl_64w1FdF7jGbfCKYbuxJQamoNqSz5` is READY.

Frozen W9-S1 Engineering Run `a64d56b7-ad42-42ad-9562-891783363f4a` remains at human REVIEW revision 12 after P2-V0.23.41 produced replacement accepted lineage `src:001736ab731e243956cf78ede7a0087d2b81595f1008568850eac1e9acc3e809` from reviewed base lineage `src:da5d0fb62d34a3228bb56e7a7d82971c8023a536d11944ba71bcaa51a407b871`.

Authenticated P2-V0.23.42 production retry `33747854471` proved commit-bearing-empty repository classification now succeeds. Exact deployment logs show read-only inspection of `Ryan9876/parallax-qa1`, stable `main@b24c029be916f8b1f0ab07347a988f814cc8d567`, exact head commit/tree inspection, and no recurrence of `GREENFIELD_BASELINE_MISMATCH`. Publication then failed independently as `BRANCH_CONFLICT` after GitHub returned the existing branch `parallax/0e20392b-a64d56b7`.

That branch belongs to the earlier reviewed lineage. The root cause is confirmed in both `VerifiedLineageDelivery.deliver()` and `GreenfieldVerifiedLineageDelivery.deliver()`: branch identity is currently only `parallax/{project_id[:8]}-{run_id[:8]}`. P2-V0.23.41 intentionally preserves the same Engineering Run across REVIEW correction, so a replacement lineage in that run collides with the original lineage's publication branch.

## 3. Fixed publication-branch identity

For every new accepted-lineage publication with no durable delivery record, Parallax must derive the feature branch from exact authenticated Project identity, exact Engineering Run identity, and exact accepted lineage identity.

The canonical branch format is:

`parallax/{project8}-{run8}-{lineage64}`

where:

- `project8` is the existing first eight characters of canonical Project UUID identity;
- `run8` is the existing first eight characters of canonical Engineering Run UUID identity;
- `lineage64` is the complete 64 lowercase hexadecimal characters after the required `src:` prefix of the exact accepted source-lineage ID.

The full lineage digest is retained rather than truncated. The resulting branch remains well inside the existing provider policy `^parallax/[A-Za-z0-9][A-Za-z0-9._/-]{0,110}$`, removes avoidable collision handling, and makes the exact accepted lineage visible in deterministic publication identity without granting caller-selected ref authority.

No caller, model, candidate source, REVIEW text, repository content, or provider response may choose or alter this branch name.

## 4. Shared branch helper contract

One server-owned helper must own canonical publication branch derivation and be used by both ordinary `VerifiedLineageDelivery` and `GreenfieldVerifiedLineageDelivery`.

The helper must:

1. accept a canonical `ProjectRunIdentity` and exact accepted `src:<64hex>` lineage ID;
2. fail closed on malformed Project/run/lineage identity;
3. return exactly the canonical format above;
4. remain deterministic across process/retry boundaries;
5. remain within the existing provider branch policy;
6. contain no repository, benchmark, Work Specification, acceptance, provider, or environment special case.

The helper changes ref identity only. Existing delivery operation-key and durable record identity already bind full Project+Run+Lineage and remain unchanged.

## 5. Replay and conflict semantics

Existing durable delivery replay remains the first publication authority boundary:

- `resolve_record(run, accepted_lineage_id=...)` remains before branch mutation;
- an existing exact durable delivery record for the accepted lineage returns that record and performs no new provider mutation;
- a different accepted lineage in the same run has a different delivery-record key and a different canonical branch name.

If the canonical lineage-scoped branch already exists but there is no exact durable delivery record proving that lineage's publication, existing provider branch creation/read-back conflict behavior remains fail-closed. P2-V0.23.43 must not silently adopt, reset, force-update, delete, rename, or reuse that branch.

Prior run-scoped branches created by releases before P2-V0.23.43 remain valid historical artifacts. This release does not migrate or rename them. Existing durable records continue to replay their stored branch name unchanged.

## 8. Reliability and compatibility

### Existing delivered lineage
An exact lineage with a durable delivery record continues to replay that record, including its historical run-scoped branch name if created before P2-V0.23.43. No branch provider call occurs.

### First publication after P2-V0.23.43
A lineage without a durable delivery record uses its canonical lineage-scoped branch.

### Same-run replacement lineage
A different accepted lineage in the same run derives a different branch because the full lineage digest differs. The prior branch remains untouched.

### Unexpected existing canonical branch
If the new computed branch already exists without exact durable record authority, provider branch creation remains fail-closed. No heuristic branch suffix, random token, retry rename, or force update is allowed.

### Retry after partial provider failure
Existing lineage-scoped operation keys and provider action idempotency remain unchanged. This slice must not add timing sleeps or eventually-consistent branch probing outside existing provider contracts.

## 9. Acceptance criteria

### AC-01 Canonical branch derivation is exact
For canonical Project/run identity and accepted lineage `src:<64hex>`, the helper returns exactly `parallax/{project8}-{run8}-{lineage64}` using all 64 lineage hexadecimal characters.

### AC-02 Malformed identity fails closed
Malformed Project identity, run identity, missing/invalid `src:` lineage prefix, non-hex lineage data, or wrong lineage length cannot produce a publication branch.

### AC-03 Ordinary delivery uses shared lineage branch
`VerifiedLineageDelivery` publishes an accepted lineage on the shared canonical lineage-scoped branch and preserves all existing repository/commit/PR/Preview verification.

### AC-04 Greenfield delivery uses the same shared lineage branch
`GreenfieldVerifiedLineageDelivery` uses the identical helper and format after its existing P2-V0.23.42 delivery-base classification. No greenfield-specific branch naming remains.

### AC-05 Same-run replacement receives a distinct branch
Two valid accepted lineages for the same Project/run deterministically derive distinct branch names while retaining identical Project/run prefixes.

### AC-06 Prior branch is untouched
Publishing the replacement lineage performs no mutation/delete/force update against the earlier lineage's existing branch, PR or Preview.

### AC-07 Durable replay is unchanged
If the exact accepted lineage already has a durable delivery record, delivery returns that record before branch creation and preserves the stored historical branch identity.

### AC-08 Unexpected computed branch conflict remains fail-closed
If the canonical lineage-scoped branch exists unexpectedly without exact durable delivery-record authority, provider conflict remains a hard failure. No automatic reuse or alternate branch is attempted.

### AC-09 Delivery records remain exact lineage authority
Record keys, accepted lineage/content digests, exact Git commit/PR/Preview read-back and replay semantics remain lineage-bound and unchanged except that a newly persisted result records the canonical lineage-scoped branch.

### AC-10 No authority expansion
Diff/tests prove no provider/model/credential/network/command/execution-profile/retry/source-lineage/force-ref/default-branch/merge/production/automatic-REVIEW authority expansion.

### AC-11 Protected release gates pass
The exact spec passes validation plus authentic DSPy SpecCritic/SpecCompiler and strict compiled-plan validation before semantic implementation. Focused tests, full API regression, Bounded Autonomy, Workstream Spec Validation and P2 CI pass on exact reviewed heads.

### AC-12 Production acceptance
The exact merged API source reaches production READY with normal preflights, `/health` and `/ready` HTTP 200 and reviewed exact-deployment runtime scans. Frozen W9-S1 run `a64d56b7-ad42-42ad-9562-891783363f4a` at REVIEW revision 12 retries publication of replacement lineage `src:001736ab731e243956cf78ede7a0087d2b81595f1008568850eac1e9acc3e809`. The retry must:

- not recur `GREENFIELD_BASELINE_MISMATCH`;
- not recur `BRANCH_CONFLICT` against prior branch `parallax/0e20392b-a64d56b7`;
- create/read a new canonical lineage-scoped feature branch for the replacement lineage;
- create/read the exact replacement-lineage commit and a new GitHub PR;
- create/read a READY Vercel Preview or existing bounded READY-equivalent result under normal delivery semantics;
- preserve the original branch and QA PR #1 unchanged;
- leave the Engineering Run at human REVIEW revision 12 with `last_failure_code=null`.

Any genuinely later independent blocker is recorded separately rather than weakening this boundary.
