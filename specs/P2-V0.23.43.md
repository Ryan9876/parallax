## 1. Objective

Correct the source-publication branch identity exposed by the production W9-S1 retry after P2-V0.23.42. A single Engineering Run may legitimately accept a replacement immutable lineage after bounded human REVIEW rework. Publication identity must therefore distinguish accepted lineages within the same Project/run instead of reusing the earlier run-scoped feature branch.

The change must preserve exact durable delivery replay for an already-published lineage, leave prior reviewed branches/PRs/Previews untouched, and fail closed if a computed lineage-scoped branch exists without the exact durable delivery record/read-back identity.

## 2. Production finding and confirmed root cause

P2-V0.23.42 is merged at `9e169ac707126c078195c75403e2d7c58bae1dec` and exact production API deployment `dpl_64w1FdF7jGbfCKYbuxJQamoNqSz5` is READY from that source. Authenticated frozen W9-S1 publication retry `33747854471` on Engineering Run `a64d56b7-ad42-42ad-9562-891783363f4a` at `REVIEW` revision 12 proved the P2-V0.23.42 repository-state boundary: production inspected `Ryan9876/parallax-qa1`, read stable `main@b24c029be916f8b1f0ab07347a988f814cc8d567` and its canonical empty tree, and did not fail the prior greenfield initializer path.

The next bounded provider failure is `BRANCH_CONFLICT` on existing branch `parallax/0e20392b-a64d56b7`.

That branch belongs to the earlier reviewed lineage `src:da5d0fb62d34a3228bb56e7a7d82971c8023a536d11944ba71bcaa51a407b871`. P2-V0.23.41 legitimately accepted replacement lineage `src:001736ab731e243956cf78ede7a0087d2b81595f1008568850eac1e9acc3e809` in the same Engineering Run. Both ordinary `VerifiedLineageDelivery` and `GreenfieldVerifiedLineageDelivery` currently derive branch identity only from Project+Run using `parallax/{project8}-{run8}`. Distinct accepted lineages therefore collide even though the durable delivery record key is already lineage-scoped.

## 3. Fixed publication identity contract

Introduce one server-owned helper used by both ordinary and greenfield delivery paths:

`publication_branch_name(identity: ProjectRunIdentity, lineage: SourceLineage) -> str`

The helper must:

1. require the exact authenticated Project/run identity already bound to delivery;
2. require the exact accepted `src:<sha256>` lineage identity already admitted by the existing same-run lineage checks;
3. derive a deterministic bounded branch under the existing `parallax/` namespace;
4. include Project and Run tokens plus a lineage token derived only from the exact accepted lineage identity;
5. reject malformed/non-`src:` lineage identities rather than normalizing arbitrary caller input;
6. remain independent of repository name, benchmark identity, issue number, provider response, user/model text, timestamps, retries, or random values.

The fixed initial branch format is:

`parallax/{project8}-{run8}-{lineage16}`

where `lineage16` is the first 16 lowercase hexadecimal characters of the exact `src:<sha256>` lineage digest after the `src:` prefix. The full lineage identity remains authoritative in the existing lineage-scoped delivery operation/record key and delivery payload. The short branch token is only a bounded provider-safe locator.

A short-token collision or unexpected pre-existing branch is not silently reused: existing provider branch-create/read-back conflict behavior must fail closed unless an exact durable delivery record for that full lineage was already loaded before mutation.

## 4. Replay and prior-artifact preservation

Existing durable delivery records remain authoritative and are checked before provider mutation exactly as today.

For an already-published accepted lineage:

- replay returns the exact persisted branch/commit/PR/Preview record;
- no new branch, commit, PR, or Preview mutation occurs;
- branch-name recomputation must not replace or reinterpret the persisted record.

For a replacement accepted lineage in the same Engineering Run:

- a distinct deterministic lineage-scoped branch is created;
- the earlier branch/commit/PR/Preview remains untouched;
- no branch deletion, force update, PR close/replacement, or default-branch rewrite occurs.

## 6. Security and authority requirements

- canonical Project/run/repository binding remains server-resolved;
- exact accepted application source remains the immutable same-run lineage already admitted by existing lifecycle checks;
- branch identity is derived only from server-authenticated Project/run/lineage identity;
- candidate source, user/model/browser input, benchmark identity, repository name, provider metadata, or external content cannot select branch identity;
- no new provider action, permission, credential, repository scope, network capability, generic Git ref capability, force update, delete, merge, default-branch application publication, production deployment/promotion, or REVIEW-completion authority is added;
- Preview remains the autonomous publication ceiling;
- human `REVIEW` remains the completion boundary.

## 7. Reliability and collision behavior

The helper must be pure and deterministic for the same exact Project/run/lineage tuple.

The existing provider branch-create path remains the collision authority:

- if the lineage-scoped branch does not exist, create it from the exact verified base revision;
- if it exists unexpectedly and there is no exact durable delivery record for the full lineage, fail closed through the existing conflict/read-back contract;
- never infer branch ownership from the short lineage token alone;
- never silently retarget, delete, reuse, or force-update an unexpected branch.

No clock heuristic, retry suffix, random branch name, provider enumeration, or branch cleanup sweep is introduced.

## 8. Acceptance criteria

### AC-01 Deterministic lineage-scoped branch identity
For a valid Project/run and exact `src:<sha256>` lineage, the helper returns exactly `parallax/{project8}-{run8}-{lineage16}` and returns the same value on replay.

### AC-02 Distinct same-run accepted lineages receive distinct branches
Two different exact accepted `src:<sha256>` lineages in the same Project/run produce different deterministic branch names while retaining the same Project/run prefix.

### AC-03 Malformed lineage identity fails closed
Missing, non-string, non-`src:` or non-64-hex accepted lineage identity is rejected before provider branch mutation.

### AC-04 Ordinary and greenfield delivery use one shared contract
`VerifiedLineageDelivery` and `GreenfieldVerifiedLineageDelivery` both call the same server-owned branch helper; no duplicate greenfield-only or benchmark-specific branch derivation exists.

### AC-05 Exact durable replay remains authoritative
If an exact durable delivery record exists for the full accepted lineage, delivery returns that record before provider mutation and does not require branch recreation.

### AC-06 Unexpected pre-existing lineage branch fails closed
If the computed lineage-scoped branch already exists without the exact durable delivery record/read-back identity, provider conflict remains a hard failure; no reuse, suffixing, force update, deletion, or history rewrite occurs.

### AC-07 Prior reviewed publication remains untouched
Publishing a replacement lineage in the same Engineering Run creates a new branch/commit/PR/Preview and does not mutate or close the earlier lineage branch, commit, PR, or Preview.

### AC-08 Repository/base-selection semantics remain unchanged
P2-V0.23.42 true-empty, canonical-baseline, commit-bearing-empty, non-empty-drift and concurrent-ref protections are unchanged; only post-verification feature-branch identity changes.

### AC-09 No authority expansion
Tests and diff prove no new provider permission, credential, repository scope, network, command, model, execution profile, source authority, force-ref, delete, merge, production, or automatic REVIEW authority.

### AC-10 Protected release gates pass
The exact spec passes deterministic validation plus authentic DSPy SpecCritic/SpecCompiler and strict committed-plan validation before semantic implementation. Focused regressions, full applicable API regression, Bounded Autonomy, Workstream Spec Validation and P2 CI pass on the exact reviewed head.

### AC-11 Production acceptance
The exact merged API source reaches Vercel production READY with normal preflights, `/health` and `/ready` HTTP 200, and reviewed exact-deployment runtime scans. Frozen W9-S1 run `a64d56b7-ad42-42ad-9562-891783363f4a` remains at human `REVIEW` revision 12 and republishes replacement lineage `src:001736ab731e243956cf78ede7a0087d2b81595f1008568850eac1e9acc3e809` without `GREENFIELD_BASELINE_MISMATCH` or `BRANCH_CONFLICT`.

### AC-12 Replacement delivery artifacts are distinct and exact
Production acceptance proves the replacement lineage receives a distinct bounded branch, exact lineage commit, GitHub PR and READY Vercel Preview while the earlier W9-S1 branch/PR #1 remain unchanged and the Engineering Run remains at human REVIEW revision 12.
