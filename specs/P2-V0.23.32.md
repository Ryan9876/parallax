# P2-V0.23.32 — Bounded Candidate Validation Repair and Profile-Matched Canaries

Status: APPROVED FOR SPEC-FIRST VALIDATION
Workstream: #543
Architecture target: v3.43

## Objective

Make protected disposable candidate BUILD/TEST/VERIFY rejection a recoverable, bounded candidate-quality signal rather than an immediate terminal IMPLEMENT failure when the failure is caused by a repairable server-classified candidate defect. Reuse the existing alternative-candidate ceiling and preserve all existing model, timeout, source-lineage, mutation, deployment, lifecycle, evaluation, and human REVIEW authority limits. Expand the production candidate canary so marker-free `static-web-v1` is proven through the same real disposable BUILD/TEST/VERIFY substrate before another authenticated user retry.

## Triggering production evidence

P2-V0.23.31 deployment `dpl_FDuJ3JKRHnvHf14mzJX59cVGasAY`, exact application source `27bb6b2af73dbae1809cbb168dc760cf81c977ba`, was healthy and deployment-verified. The signed-in retry of Engineering Run `3a1ba66a-5649-42b6-81ee-91684fe06bbc` resumed successfully, restored authoritative source lineage, and exercised a real Vercel sandbox. The explicit execution-contract boundary no longer emitted `VALIDATION_PROFILE_ERROR`. Instead, protected candidate validation was reached and production emitted `parallax_candidate_validation_failed candidate=candidate-primary stage=BUILD timed_out=False` before durable IMPLEMENT failure sequence #89.

This satisfies P2-V0.23.31's later-boundary acceptance condition. The remaining failure is candidate-quality recovery after a real protected build rejection.

## Problem statement

`ResilientLiveAgenticControlPlane.generate_protected()` currently obtains a complete safe proposal and then performs disposable candidate validation. A `CandidateValidationFailure` is converted to `ImplementationGenerationFailure`, so the IMPLEMENT stage terminates even when the failure is a candidate-authored defect that another already-admitted bounded candidate could repair.

The `static-web-v1` validator already emits a server-owned closed vocabulary such as `STATIC_WEB_INDEX_REQUIRED`, `STATIC_WEB_JS_SYNTAX_INVALID`, and local-reference failures. Candidate validation currently persists only protected stage identity, exit/timing flags, and output digests; it does not admit the fixed validator reason code to bounded repair guidance. Production's P2-V0.23.31 candidate canary also proved the real `node-v1` path but did not separately gate `static-web-v1`, the contract selected for marker-free greenfield work.

## Fixed decisions

1. The execution contract remains selected and bound by protected PLAN. Candidate validation repair cannot change its contract ID, validation profile, command policy, working directory, network policy, or execution snapshot.
2. Candidate validation remains non-authoritative. A rejected candidate never mutates accepted source lineage, Project, Engineering Run, Git, delivery, deployment, lifecycle, or REVIEW state.
3. No raw stdout, stderr, source text, generated content, provider payload, exception text, filesystem root, credential, or environment value may be forwarded to models or durable failure evidence.
4. A server-owned validator may expose a repair reason only when the runtime can prove it is an exact member of a closed fixed vocabulary. P2-V0.23.32 initially admits only the `static-web-v1` validator's exact reason vocabulary.
5. Candidate-repairable static-web reasons are content/structure defects that candidate source can change. Infrastructure/policy reasons remain terminal and do not authorize model repair.
6. A repairable protected BUILD/TEST/VERIFY rejection consumes the already-existing alternative-candidate slot. It does not add a third candidate, add a model, increase the Luna/Terra/Sol roster, increase the one final validator-repair ceiling, increase the hosted 60-second model timeout, or enable hidden provider retries.
7. The repair request is a complete replacement candidate under the same Work Specification, accepted source lineage, and immutable execution contract. It receives only: protected stage, closed reason code, execution contract/profile ID, and a fixed instruction to produce a complete replacement compatible with that contract. It never receives rejected candidate source or raw validator output.
8. The replacement candidate must pass the unchanged proposal schema, exact acceptance coverage, SafeImplementationEngine preflight, and real disposable BUILD/TEST/VERIFY from scratch before independent evaluation and routing.
9. If the replacement candidate fails protected validation, or if the first failure is non-repairable/infrastructure-classified, IMPLEMENT fails closed with existing bounded durable diagnostics plus the admitted reason code where allowed.
10. Successful repair consumes the alternative candidate slot; no additional competitive challenger is generated afterward for that attempt. This preserves the existing maximum candidate-round ceiling.
11. Production release gating must run real disposable candidate BUILD/TEST/VERIFY canaries for both `node-v1` and `static-web-v1`. The canaries are immutable, source-lineage/project/run non-mutating, use the released server-owned validator/toolchain, and fail the Vercel production build if either admitted profile cannot complete its protected stages.
12. Existing Python and .NET execution-snapshot/build preflights remain unchanged. This release does not admit generic Node, generic Python, frameworks, package-script authority, repository-selected commands, or arbitrary shell execution.

## Model-visible repair guidance

The only dynamic fields permitted in candidate-validation repair guidance are values already admitted from closed server-owned sets:

- failed stage: `BUILD`, `TEST`, or `VERIFY`;
- reason code from the repairable static-web set above;
- execution contract ID `static-web-v1`;
- validation profile ID `static-web-v1`.

The instruction is otherwise fixed and must state that the prior candidate is discarded, the new proposal must be complete, root `index.html` and local assets must satisfy the fixed static-web contract, package managers/bundlers/network fetches are unavailable, and all acceptance IDs must remain exactly covered.

## Durable diagnostic contract

The existing `candidate_validation_failure` envelope may add only:

- `validation_reason_code` from the fixed static-web vocabulary;
- `validation_profile_id` / digest already bounded by existing diagnostics;
- existing stage, exit/timing, invocation/output digests, dependency-preparation flags, candidate digest, and false authority claims.

Unknown reason codes, multi-line/raw stderr, arbitrary strings, true authority claims, invalid digests, and oversized evidence must be dropped fail-closed by the existing sanitizer.

## Production canary contract

The Vercel production build gate must execute two source-free-snapshot candidate validation canaries through `VercelCandidateValidationExecutor`:

1. `node-v1` — preserve the existing immutable Node fixture and require protected BUILD, TEST, VERIFY success.
2. `static-web-v1` — use an immutable self-contained root `index.html` plus local CSS/JavaScript fixture, the server-owned static-web validator outside candidate source, deny-all validation networking, and require protected BUILD, TEST, VERIFY success.

Both canaries must prove no Project, Engineering Run, accepted source lineage, Git, delivery, deployment, lifecycle, or REVIEW mutation authority. The build log may emit only profile ID, protected stage list, and immutable candidate digest.

## Security

- Candidate validation remains deny-all networked and receives no application environment.
- Candidate source cannot alter server-owned validator code, execution contract, validation profile, command list, snapshot identity, or network policy.
- Only exact fixed validator reason codes may cross from protected validation evidence into model repair guidance or durable diagnostics.
- No raw command output, source, generated content, exception/provider payload, credential, environment material, or filesystem root is persisted or forwarded.
- Rejected candidates are disposable and never gain canonical mutation/source-lineage authority.
- Git, deployment, lifecycle, and REVIEW authorities remain unchanged.

## Risks and mitigations

- Risk: repair guidance becomes an output-exfiltration path. Mitigation: only exact fixed reason codes and fixed server-authored text are admitted.
- Risk: validation repair silently increases model cost/retry authority. Mitigation: repair consumes the existing alternative-candidate slot; no new candidate/model/timeout/retry ceiling is introduced.
- Risk: infrastructure failures waste model calls. Mitigation: only the explicitly repairable content-code subset authorizes repair.
- Risk: release canary proves the wrong profile again. Mitigation: production build must independently prove node-v1 and static-web-v1.
- Risk: successful repair bypasses protected evaluation. Mitigation: replacement candidate follows the unchanged candidate validation -> independent evaluation -> routing path.

## Non-goals

- Generic Node/Python ecosystem admission.
- Framework/package-manager/bundler command admission for marker-free greenfield work.
- Arbitrary command generation or repository-selected validation commands.
- Retry/timeout/model/provider/credential expansion.
- New source-lineage, Git, deployment, lifecycle, or REVIEW authority.
- Persisting raw build/test/verify logs.
- UI redesign.
