## 1. Objective

Make protected disposable candidate BUILD/TEST/VERIFY rejection a recoverable, bounded candidate-quality signal rather than an immediate terminal IMPLEMENT failure when the failure is caused by a repairable server-classified candidate defect. Reuse the existing alternative-candidate ceiling and preserve all existing model, timeout, source-lineage, mutation, deployment, lifecycle, evaluation, and human REVIEW authority limits. Expand production candidate canaries so marker-free `static-web-v1` is proven through the same real disposable BUILD/TEST/VERIFY substrate before another authenticated user retry.

On exact P2-V0.23.31 deployment `dpl_FDuJ3JKRHnvHf14mzJX59cVGasAY`, application source `27bb6b2af73dbae1809cbb168dc760cf81c977ba`, signed-in Engineering Run `3a1ba66a-5649-42b6-81ee-91684fe06bbc` resumed successfully. Source-lineage reads and a real Vercel sandbox lifecycle succeeded. The explicit execution-contract boundary no longer emitted `VALIDATION_PROFILE_ERROR`; protected candidate validation was reached and production emitted `parallax_candidate_validation_failed candidate=candidate-primary stage=BUILD timed_out=False` before durable IMPLEMENT failure sequence #89.

P2-V0.23.31 therefore satisfied its later-boundary completion condition. The remaining product defect is candidate-quality recovery after a real protected build rejection. `generate_protected()` currently converts `CandidateValidationFailure` to terminal `ImplementationGenerationFailure`, even when the protected validator emitted a fixed candidate-repairable reason and an already-bounded alternative candidate could be used.

## 2. Fixed decisions

- The execution contract remains selected and bound by protected PLAN. Candidate validation repair cannot change contract ID, validation profile, commands, working directory, network policy, or execution snapshot.
- Candidate validation remains non-authoritative. A rejected candidate never mutates accepted source lineage, Project, Engineering Run, Git, delivery, deployment, lifecycle, or REVIEW state.
- No raw stdout, stderr, source text, generated content, provider payload, exception text, filesystem root, credential, or environment value may be forwarded to models or durable failure evidence.
- A server-owned validator may expose a repair reason only when the runtime proves it is one exact member of a closed fixed vocabulary. P2-V0.23.32 initially admits only the `static-web-v1` validator vocabulary.
- Candidate-repairable static-web reasons are content/structure defects that candidate source can change. Infrastructure/policy reasons remain terminal and do not authorize model repair.
- A repairable protected BUILD/TEST/VERIFY rejection consumes the already-existing alternative-candidate slot. It does not add a third candidate, add a model, increase the Luna/Terra/Sol roster, increase the one final validator-repair ceiling, increase the hosted 60-second model timeout, or enable hidden provider retries.
- The repair request is a complete replacement candidate under the same Work Specification, accepted source lineage, and immutable execution contract. It receives only protected stage, closed reason code, execution contract/profile ID, and fixed server-authored replacement guidance. It never receives rejected candidate source or raw validator output.
- The replacement candidate must pass the unchanged proposal schema, exact acceptance coverage, SafeImplementationEngine preflight, and real disposable BUILD/TEST/VERIFY from scratch before independent evaluation and routing.
- A second candidate validation rejection, or a first non-repairable/infrastructure failure, remains fail-closed with bounded diagnostics.
- Successful validation-guided repair consumes the alternative-candidate slot; no additional competitive challenger is generated afterward for that attempt. The existing candidate-round ceiling is preserved.
- Production release gating runs real disposable candidate BUILD/TEST/VERIFY canaries for both `node-v1` and `static-web-v1` before publication can succeed.
- Existing Python and .NET execution-snapshot/build preflights remain unchanged. This release does not admit generic Node, generic Python, frameworks, package-script authority, repository-selected commands, or arbitrary shell execution.
- Architecture advances to v3.43 only after focused behavior validation proves the repair and profile-matched canary contracts.

## 5. Architecture requirements

### 5.1 Closed static-web validation reason contract

The server-owned static-web validator emits only these fixed codes:

- `STATIC_WEB_ARGUMENTS_INVALID`
- `STATIC_WEB_ROOT_INVALID`
- `STATIC_WEB_SYMLINK_REJECTED`
- `STATIC_WEB_SPECIAL_FILE_REJECTED`
- `STATIC_WEB_PATH_ESCAPE`
- `STATIC_WEB_INDEX_REQUIRED`
- `STATIC_WEB_INDEX_ESCAPE`
- `STATIC_WEB_JS_CHECK_UNAVAILABLE`
- `STATIC_WEB_JS_SYNTAX_INVALID`
- `STATIC_WEB_REFERENCE_SCHEME_UNSUPPORTED`
- `STATIC_WEB_REFERENCE_PATH_INVALID`
- `STATIC_WEB_INDEX_NOT_UTF8`
- `STATIC_WEB_HTML_INVALID`
- `STATIC_WEB_LOCAL_REFERENCE_MISSING`
- `STATIC_WEB_REFERENCE_PATH_ESCAPE`
- `STATIC_WEB_STAGE_INVALID`

Protected candidate evidence may project one `validation_reason_code` only when stderr is exactly one trimmed line equal to a member of that set and the active profile is exactly `static-web-v1`. Unknown text, extra lines, prefixes/suffixes, arbitrary strings, or output from other profiles does not become a reason code.

Candidate-repairable codes are limited to:

- `STATIC_WEB_INDEX_REQUIRED`
- `STATIC_WEB_JS_SYNTAX_INVALID`
- `STATIC_WEB_REFERENCE_SCHEME_UNSUPPORTED`
- `STATIC_WEB_REFERENCE_PATH_INVALID`
- `STATIC_WEB_INDEX_NOT_UTF8`
- `STATIC_WEB_HTML_INVALID`
- `STATIC_WEB_LOCAL_REFERENCE_MISSING`

All other static-web codes remain policy/infrastructure/non-repairable for this release.

### 5.2 Bounded candidate validation repair

A primary candidate still runs unchanged disposable candidate validation. If it fails BUILD, TEST, or VERIFY with a repairable admitted reason code, the control plane may consume the existing `candidate-challenger` / alternative-round slot as a validation-guided repair candidate.

The repair candidate:

- uses the same Work Specification and exact required acceptance IDs;
- uses the same accepted source context and base source lineage;
- uses the same persisted execution contract and validation profile;
- starts from authoritative base workspace, not the rejected candidate workspace;
- receives no rejected source bytes or raw validator output;
- receives only server-owned fixed repair guidance with dynamic fields limited to failed stage and admitted reason code plus fixed contract/profile identifiers;
- must produce a complete replacement proposal;
- passes unchanged proposal validation and SafeImplementationEngine preflight;
- runs real disposable BUILD/TEST/VERIFY from scratch;
- passes independent evaluation/routing before selected proposal can reach canonical commit-time validation.

A repair candidate failure is terminal for this candidate attempt. No third candidate is generated. If a repair candidate succeeds, it consumes the alternative slot and the ordinary competition/challenger path is skipped so the existing maximum candidate-round ceiling is unchanged.

### 5.3 Repair guidance contract

The repair request may add only fixed server-authored constraints equivalent to:

- the previous disposable candidate was rejected and is discarded;
- the replacement must be complete and independently satisfy all acceptance IDs;
- the immutable contract is `static-web-v1` / profile `static-web-v1`;
- root `index.html` and local HTML/CSS/JavaScript assets must satisfy the server-owned static-web validator;
- package managers, bundlers, package scripts, arbitrary shell and network fetches are unavailable;
- the protected validator rejected the prior candidate at one of BUILD/TEST/VERIFY with one admitted repairable reason code.

No arbitrary validator output or exception text is interpolated.

### 5.4 Durable diagnostics

The existing `candidate_validation_failure` durable envelope may add `validation_reason_code` only from the fixed static-web vocabulary. Existing bounded stage, exit/timing, invocation/output digests, dependency-preparation fields, candidate digest, validation profile ID/digest, and false authority claims remain unchanged.

The durable sanitizer must reject unknown reason codes, arbitrary extra fields, true authority claims, malformed digests/counts, and oversized evidence exactly as before.

### 5.5 Profile-matched production canaries

The production Vercel build gate must invoke the same `VercelCandidateValidationExecutor` against two immutable fixtures:

1. `node-v1` — preserve the existing Node fixture and require protected BUILD, TEST, VERIFY success.
2. `static-web-v1` — immutable self-contained root `index.html` plus local CSS/JavaScript assets, validated by the released server-owned static-web validator outside candidate source, with deny-all validation networking, requiring protected BUILD, TEST, VERIFY success.

The canaries must not create/mutate Projects, Engineering Runs, source lineage, Git, delivery, lifecycle, deployment, or REVIEW state. Build logging is limited to profile ID, protected stage list, and immutable candidate digest.

### 5.6 Existing ceilings remain unchanged

SafeImplementationEngine, dependency preparation, source-lineage authority, protected evaluation, delivery, lifecycle, Git/deployment authority, Luna/Terra/Sol roster/order, hosted timeout, hidden provider retry policy, one final validator-repair ceiling, autonomous request depth, and human REVIEW ceiling remain unchanged.

## 6. Security

Only exact fixed validator reason codes may cross from protected candidate validation into model repair guidance or durable diagnostics. No raw stdout/stderr, source, generated content, exception/provider payload, filesystem root, credential, or environment material is forwarded or persisted.

Candidate validation remains deny-all networked and receives no application environment. Candidate source cannot alter the server-owned execution contract, validation profile, validator code, command list, execution snapshot, or network policy. Rejected candidates remain disposable and cannot mutate or accept canonical source lineage. Git, deployment, lifecycle, and REVIEW authorities are unchanged.

## 7. Reliability and migration

No database migration is required. Candidate validation repair is request-local and uses existing PLAN-bound execution-contract evidence plus the existing alternative candidate identity. Older successful PLAN evidence must still satisfy the current execution-contract version checks; failed IMPLEMENT retries continue through the existing protected refresh/rebind path.

A repairable content failure is corrected in the same bounded IMPLEMENT operation rather than requiring a user-driven deploy/retry cycle. Infrastructure/policy failures fail early and do not waste model calls. The static-web production canary closes the profile mismatch left by the P2-V0.23.31 node-only canary while preserving the existing Python/.NET execution-snapshot preflights.
