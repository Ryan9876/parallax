## 1. Objective

Convert a repairable protected disposable candidate BUILD/TEST/VERIFY rejection from a terminal IMPLEMENT failure into one bounded validation-guided replacement candidate, using the already-existing alternative-candidate ceiling. Preserve every existing execution-contract, model, timeout, source-lineage, mutation, evaluation, deployment, lifecycle, and human REVIEW authority limit.

On exact P2-V0.23.31 production deployment `dpl_FDuJ3JKRHnvHf14mzJX59cVGasAY`, application source `27bb6b2af73dbae1809cbb168dc760cf81c977ba`, signed-in Engineering Run `3a1ba66a-5649-42b6-81ee-91684fe06bbc` resumed successfully. Source-lineage reads and a real Vercel sandbox lifecycle succeeded. The explicit execution-contract boundary no longer emitted `VALIDATION_PROFILE_ERROR`; protected candidate validation was reached and production emitted `parallax_candidate_validation_failed candidate=candidate-primary stage=BUILD timed_out=False` before durable IMPLEMENT failure sequence #89.

Inspection of the exact P2-V0.23.31 release corrects one diagnostic ambiguity: its production canary already resolves `ExecutionContractCode.STATIC_WEB` with `GREENFIELD_STATIC_WEB` and validates the immutable `static_web_canary` fixture through `VercelCandidateValidationExecutor`. The build log printed `profile=node-v1` because the `static-web-v1` contract deliberately reuses the common Node-capable execution snapshot/profile identifier while its execution ecosystem remains `static-web`. P2-V0.23.32 therefore does not add a second static-web canary. It preserves that real static-web canary and makes its safe contract identity explicit in release evidence.

## 2. Fixed decisions

- Protected PLAN remains the sole execution-contract binding authority. Candidate validation repair cannot change contract ID, binding reason, validation ecosystem/profile, commands, network policy, working directory, or execution snapshot.
- A rejected candidate remains non-authoritative and disposable. It cannot mutate accepted source lineage, Project, Engineering Run, Git, delivery, deployment, lifecycle, or REVIEW state.
- No raw stdout/stderr, source text, generated content, exception/provider payload, filesystem root, credential, or environment value may reach model repair guidance or durable evidence.
- The runtime may project a validation reason only when the active execution ecosystem is exactly `static-web` and protected stderr is exactly one trimmed line from the server-owned fixed reason vocabulary.
- Only candidate-authored content/structure reason codes authorize repair. Infrastructure/policy reason codes remain terminal and do not consume a model call.
- A repairable protected BUILD/TEST/VERIFY rejection consumes the existing second candidate / alternative-round slot. It adds no third candidate, model, hidden retry, validator-repair allowance, timeout, or autonomy depth.
- The replacement is a complete independent proposal under the same Work Specification, accepted source lineage, source context, and immutable execution contract. Rejected candidate bytes are not retained or supplied.
- The replacement re-runs unchanged proposal validation, SafeImplementationEngine preflight, and real disposable BUILD/TEST/VERIFY from authoritative base source before independent evaluation/routing.
- A replacement validation failure is terminal for the attempt. No further candidate is generated.
- If validation-guided replacement consumes the second candidate slot, ordinary competitive challenger creation is skipped. Existing maximum candidate count remains two.
- The existing production `static-web-v1` canary remains the release gate. Its output is clarified to include the execution contract ID, binding reason, ecosystem/profile ID, stages, and immutable candidate digest so profile reuse cannot be mistaken for a generic Node/package-script canary.
- Existing Python/.NET execution-snapshot preflights, deny-all validation networking, SafeImplementationEngine, independent evaluation, source lineage, Git/deployment/lifecycle authority, Luna/Terra/Sol roster, 60-second hosted timeout, zero hidden provider retries, and human REVIEW ceiling remain unchanged.

## 5. Architecture requirements

### 5.1 Closed static-web validation reason contract

The server-owned static-web validator emits this fixed vocabulary:

`STATIC_WEB_ARGUMENTS_INVALID`, `STATIC_WEB_ROOT_INVALID`, `STATIC_WEB_SYMLINK_REJECTED`, `STATIC_WEB_SPECIAL_FILE_REJECTED`, `STATIC_WEB_PATH_ESCAPE`, `STATIC_WEB_INDEX_REQUIRED`, `STATIC_WEB_INDEX_ESCAPE`, `STATIC_WEB_JS_CHECK_UNAVAILABLE`, `STATIC_WEB_JS_SYNTAX_INVALID`, `STATIC_WEB_REFERENCE_SCHEME_UNSUPPORTED`, `STATIC_WEB_REFERENCE_PATH_INVALID`, `STATIC_WEB_INDEX_NOT_UTF8`, `STATIC_WEB_HTML_INVALID`, `STATIC_WEB_LOCAL_REFERENCE_MISSING`, `STATIC_WEB_REFERENCE_PATH_ESCAPE`, `STATIC_WEB_STAGE_INVALID`.

Protected candidate evidence may set `validation_reason_code` only if the active profile ecosystem is `static-web` and stderr is exactly one trimmed line equal to one fixed code. Unknown text, multiline output, prefixes/suffixes, or output under any other ecosystem cannot become a reason code.

Repairable reasons are limited to:

`STATIC_WEB_INDEX_REQUIRED`, `STATIC_WEB_JS_SYNTAX_INVALID`, `STATIC_WEB_REFERENCE_SCHEME_UNSUPPORTED`, `STATIC_WEB_REFERENCE_PATH_INVALID`, `STATIC_WEB_INDEX_NOT_UTF8`, `STATIC_WEB_HTML_INVALID`, `STATIC_WEB_LOCAL_REFERENCE_MISSING`.

All other fixed codes remain non-repairable policy/infrastructure failures in this release.

### 5.2 Bounded validation-guided replacement

A primary candidate runs the existing candidate-validation path. When BUILD, TEST, or VERIFY fails with one repairable reason, the control plane may consume the existing alternative candidate round as `candidate-repair` or equivalent server-owned identity.

The replacement request carries the original authoritative ImplementationGenerationRequest plus fixed constraints stating that the prior candidate is discarded, all acceptance IDs must be covered by a complete replacement, the immutable contract is `static-web-v1`, root `index.html` plus local HTML/CSS/JavaScript assets must satisfy the static-web validator, package managers/bundlers/package scripts/arbitrary shell/network fetches are unavailable, and the prior candidate failed one protected stage with one admitted fixed reason code.

Only failed stage, admitted reason code, fixed contract ID, fixed binding reason, and fixed ecosystem/profile ID may vary in this guidance. Rejected source and raw validator output are never included.

The replacement starts again from authoritative base workspace, passes unchanged proposal schema/exact acceptance validation and SafeImplementationEngine preflight, then executes real disposable BUILD/TEST/VERIFY from scratch. A successful replacement proceeds through existing independent evaluation/routing. A failed replacement terminates with bounded diagnostics and no third candidate.

### 5.3 Existing candidate ceiling

The current competition policy already permits at most two candidates / two rounds. Validation-guided replacement reuses that finite capacity. If replacement is used, no ordinary competitive challenger is subsequently created. This release does not increase candidate count, reassignments, final validator-repair count, model roster, timeout, or provider retries.

### 5.4 Durable diagnostics

The existing `candidate_validation_failure` envelope may add only `validation_reason_code` from the fixed static-web vocabulary. Existing bounded stage, exit/timing, invocation/output digests, dependency-preparation fields, candidate digest, validation profile ID/digest, and false authority claims remain unchanged. Unknown reason codes, arbitrary extra fields, raw output, true authority claims, malformed digests, or oversized evidence fail closed through the existing sanitizer.

### 5.5 Explicit production canary identity

The existing production candidate canary already exercises the `static-web-v1` execution contract through the real `VercelCandidateValidationExecutor` and immutable `static_web_canary` fixture. It remains mandatory before production publication and must continue to require BUILD, TEST, and VERIFY `protected_success=true` with false canonical/source-lineage authority claims.

Safe canary output is changed from ambiguous profile-only identity to explicitly include:

- `contract=static-web-v1`;
- `binding=GREENFIELD_STATIC_WEB`;
- `ecosystem=static-web`;
- `profile=node-v1` (the reused common execution profile identity);
- `stages=BUILD,TEST,VERIFY`;
- immutable candidate digest.

This is evidence clarification, not a new execution contract or additional canary path.

## 6. Security

Only exact fixed validator reason codes may cross from protected validation into repair guidance or durable diagnostics. Raw validator output, candidate/source content, exception/provider payloads, filesystem roots, credentials, and environment values remain excluded.

Candidate validation remains deny-all networked and receives no application environment. Candidate source cannot alter the server-owned execution contract, validation ecosystem/profile, validator code, command list, snapshot identity, or network policy. Rejected candidates never gain mutation or source-lineage acceptance authority. Git, deployment, lifecycle, and REVIEW authority remain unchanged.

## 7. Reliability and migration

No database migration is required. Candidate validation repair is request-local and consumes existing PLAN-bound execution-contract evidence and existing finite candidate capacity. Older successful PLAN evidence still must satisfy current execution-contract version checks; failed IMPLEMENT retry continues through the existing protected PLAN refresh/rebind path.

Repairable content failure is corrected inside the same bounded IMPLEMENT attempt rather than becoming another deploy/user-retry cycle. Infrastructure/policy failure fails early without wasting a model call. Explicit canary contract identity prevents future release diagnosis from confusing the reused `node-v1` profile identifier with generic Node execution authority.
