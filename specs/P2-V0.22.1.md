## 1. Objective

Allow the existing dedicated Google-linked and Parallax-authorized QA account to establish a normal authenticated Parallax session when a managed testing browser cannot reach Google OAuth. The fallback must let the owner create or reset the QA password privately through Supabase's email recovery flow and then sign in through a deliberately hidden QA form, without sharing the password in chat, weakening the ordinary Google-only login screen, or bypassing the existing Parallax access allowlist and server-issued session cookie.

## 2. Fixed decisions

- The ordinary production login at `/` remains Google-only.
- QA password controls render only when the operator deliberately opens `?qa=1` or returns from a Supabase password-recovery link.
- The client may use only the existing public Supabase URL and publishable key. No service-role key, database password, static Parallax access token, or new provider secret is introduced.
- Password values remain browser-local form values. They are sent only over HTTPS to Supabase Auth, are never logged, persisted by Parallax, stored in local/session storage, or included in URLs.
- Password recovery uses the existing confirmed email account and Supabase's generic recovery response. The client does not disclose whether another supplied email exists.
- A password-authenticated Supabase access token is passed through the existing `/v1/session/google` boundary. The server's current Google-provider membership check, `authorized_users` allowlist, identity binding, active/revoked status check, signed HttpOnly session cookie, and expiry behavior remain authoritative.
- No public sign-up path is added. The fallback cannot create a new Supabase or Parallax user.
- Supabase access and refresh tokens are transient. Only the access token needed for the existing session exchange is returned in memory; the refresh token is not persisted.
- Recovery fragments are removed from browser history immediately after capture. A recovery access token is held only in component memory until password update succeeds or the flow is abandoned.
- Existing Google OAuth, sign-out, session-expiry handling, owner/member access management, Project binding, Engineering Run authority, and all protected runtime boundaries remain unchanged.

## 3. Scope

Owned implementation paths:

- `apps/client/src/lib/qaPasswordAuth.ts` for bounded Supabase password sign-in, recovery request, recovery-fragment capture, and password update;
- `apps/client/src/WebAuthRoot.tsx` for the hidden QA login and recovery presentation;
- focused deterministic acceptance under `apps/client/scripts/`;
- this specification.

No package dependency is added. The client uses bounded HTTPS `fetch` calls against Supabase Auth's documented REST endpoints because the current client intentionally has no Supabase SDK dependency.

## 4. Non-goals

- Replacing Google as the normal production identity provider.
- General public email/password registration or account creation.
- Changing API authentication/session semantics or accepting an email-only identity.
- Adding, rotating, retrieving, or exposing a service-role key, Parallax break-glass token, database password, OAuth secret, or recovery token.
- Database migrations or direct mutation of `auth.users` password hashes.
- Changes to W8-S4-owned workflow guidance, `App.tsx`, mobile navigation, utility rail, or package scripts.
- Claiming W8-S2 complete before the authenticated OT Time replay actually advances and is verified.

## 5. Security and reliability requirements

- All Supabase calls require hosted HTTPS and the configured publishable key.
- Email and password inputs are trimmed/validated locally only enough to prevent empty requests; server responses remain generic where account enumeration is possible.
- The UI uses an email field and a secure password field with appropriate browser autocomplete semantics.
- The password form must never echo a real password in an error, telemetry, console output, committed fixture, or serialized state. Deterministic tests may use clearly synthetic non-secret values only to verify transport and non-persistence behavior.
- The recovery callback accepts only a fragment with `type=recovery` and a non-empty access token. Query-string tokens are not accepted.
- Captured recovery fragments are cleared before any subsequent network action.
- Supabase failures are converted to bounded plain-language messages; raw response bodies and tokens are not displayed.
- Failed QA sign-in does not create a Parallax session. Existing server denial for non-Google, non-allowlisted, revoked, mismatched, or invalid identities remains fail-closed.
- The fallback can be removed or disabled by reverting the client release; no schema rollback is required.

## 6. Acceptance criteria

### AC-01 Ordinary login remains Google-only
At `/` without `qa=1` and without a recovery fragment, the existing Parallax gate exposes only `Continue with Google`; no email, password, recovery, or sign-up control is rendered.

### AC-02 QA entry is deliberate and bounded
At `/?qa=1`, the gate exposes a clearly secondary `QA test account` path while retaining Google as the primary sign-in method. No public sign-up action is present.

### AC-03 Password sign-in uses Supabase safely
Submitting QA email/password sends them only to the configured Supabase `/auth/v1/token?grant_type=password` endpoint over HTTPS with the publishable key. The password is absent from URLs, storage, logs, errors, and Parallax API requests.

### AC-04 Existing Parallax authorization remains authoritative
The resulting transient Supabase access token is exchanged only through existing `api.establishGoogleSession`. Current server verification must still require a Google-linked Supabase identity and an active matching `authorized_users` row before issuing the normal signed HttpOnly Parallax session cookie.

### AC-05 Recovery can enroll the existing QA password privately
The QA form can request a Supabase password-recovery email without disclosing account existence. A valid recovery redirect returns to the QA gate and presents a secure new-password form.

### AC-06 Recovery material is transient
The recovery access token is accepted only from a `type=recovery` URL fragment, immediately removed from browser history, retained only in component memory, and discarded after success, cancellation, or page exit. Refresh tokens are never stored.

### AC-07 Password update is bounded
The new password is sent only to Supabase `/auth/v1/user` with the transient recovery access token. Success returns the user to the QA sign-in form rather than fabricating a Parallax session.

### AC-08 Failure behavior is safe and understandable
Invalid credentials, expired recovery, Supabase unavailability, Parallax authorization denial, and session failure preserve the login gate and show bounded natural-language guidance without revealing raw tokens, passwords, provider payloads, or whether an arbitrary email exists.

### AC-09 Existing authentication regressions remain green
Client typecheck, web export, Google-auth smoke, session-expiry smoke, normal visual acceptance, and focused QA-auth acceptance pass. No server, database, provider configuration, package dependency, or W8-S4-owned path changes.

### AC-10 Production verification is evidence-based
The exact client release is Preview-validated and production-deployed under the existing serialized release process. Deployment verification proves normal Google-only root behavior, hidden QA form availability, private recovery/password enrollment, authenticated managed-browser session establishment, and clean runtime errors before `CURRENT-STATE.md` records the fallback as deployment-verified or the W8-S2 authenticated replay proceeds.
