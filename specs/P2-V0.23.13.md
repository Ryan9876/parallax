# Parallax 2.0 — Human-Authorized PLAN Refresh on Failed IMPLEMENT Retry

Status: APPROVED FOR IMPLEMENTATION — SPEC-FIRST
Spec ID: P2-V0.23.13
Date: 2026-08-30
Workstream: #476
Architecture: v3.26

## 1. Objective

Make explicit human retry of a FAILED agentic IMPLEMENT run resume through a fresh protected PLAN before IMPLEMENT dispatch, so long-lived runs cannot be trapped by stale persisted agentic PLAN evidence after server-owned orchestration or routing policy changes.

## 2. Triggering evidence

Production Engineering Run `2b3cd15f-c5e2-481a-8266-c92c6534b08b` was explicitly retried on API source `997d46a9759206fe37b5092c98b4e39c757da2ca`. Persisted events proved P2-V0.23.12 executed correctly: `#31 RUN_CONTROL / RESUMED`, `#32 WORKER_STATE / RECOVERING`, then `#33 IMPLEMENT / FAILED / AUTONOMOUS_IMPLEMENT_FAILED`.

Exact production runtime logs showed `/resume` and `/autonomous` both returned HTTP 200, protected source-lineage objects were resolved, but no hosted implementation-agent invocation occurred and no worker `REASSIGNED` event was persisted. The current live agentic runtime verifies persisted PLAN identity against current source, orchestration, routing and competition policy before worker dispatch. A historical successful PLAN can therefore correctly fail closed after those server-owned policies change.

## 3. Fixed decisions

For a modern Project-bound run using the enabled agentic runtime, an explicit human resume that begins from durable `FAILED` with `resume_stage=IMPLEMENT` will refresh PLAN unconditionally rather than attempting to infer whether the old PLAN is stale.

This is deliberately more conservative than exception-driven stale-plan recovery:

- the human retry remains the authority boundary;
- the run resumes to `PLAN`, not directly to `IMPLEMENT`;
- the ordinary protected PLAN runtime recomputes current work graph, admitted agents, routing policy and competition policy against the current accepted source lineage;
- the new PLAN attempt is persisted as historical evidence and advances through the existing protected `PLAN -> IMPLEMENT` success transition;
- the terminal worker is re-armed only through the already-approved `FAILED -> RECOVERING` preparation and receives a fresh lease only through the existing `RECOVERING -> REASSIGNED` path when IMPLEMENT dispatch begins.

No model output decides whether PLAN refresh occurs. No exception-string matching is used.

## 4. Fixed boundaries

- The Work Specification binding remains unchanged and authoritative.
- Existing successful PLAN/IMPLEMENT attempts and all run events remain immutable.
- Only explicit human resume from `FAILED` may request the PLAN-refresh resume target.
- PLAN refresh is permitted only when the stored protected `resume_stage` is `IMPLEMENT`.
- PAUSED resumes retain their existing direct resume-stage behavior.
- FAILED BUILD/TEST/VERIFY retries retain their existing direct resume-stage behavior.
- Ordinary `/autonomous`, reconnect, refresh, background execution and worker acquisition cannot trigger PLAN refresh.
- The refreshed PLAN must pass the same protected PLAN validator before IMPLEMENT can run.
- Worker recovery ceilings, source mutation authority, source-lineage acceptance, repository/provider delivery, production deployment and REVIEW authority are unchanged.
- The client contract is unchanged; the existing active-stage continuation already treats PLAN as autonomously continuable after a successful resume.

## 5. Scope

- Add a server-only protected resume mode that allows `FAILED + resume_stage=IMPLEMENT` to target `PLAN`.
- Keep the public request schema unchanged; the route derives this mode only from durable pre-resume state plus server-owned agentic-runtime configuration.
- Snapshot pre-resume state, resume stage and Project binding as immutable scalars before mutation.
- Persist bounded control evidence identifying the human-authorized PLAN refresh.
- Re-arm the existing terminal worker after the successful resume exactly as in P2-V0.23.12.
- Add policy, service and route regressions proving the authority boundary and non-agentic/non-IMPLEMENT exclusions.
- Add an end-to-end runtime regression proving `FAILED IMPLEMENT -> RESUMED PLAN -> PLAN PASSED -> IMPLEMENT -> worker REASSIGNED` before hosted generation.

## 6. Acceptance criteria

### AC-01 Explicit failed IMPLEMENT retry resumes to PLAN
When the request begins from durable `FAILED`, `resume_stage=IMPLEMENT`, the run is Project-bound, and the agentic runtime is enabled, the successful resume target is `PLAN`.

### AC-02 Human authority is required
Ordinary autonomous execution cannot move a FAILED run to PLAN or refresh prior PLAN evidence.

### AC-03 Non-IMPLEMENT failures are unchanged
FAILED runs whose protected resume stage is BUILD, TEST, VERIFY, PLAN or SPECIFY resume through the existing policy and do not gain PLAN-refresh behavior solely because agentic runtime is enabled.

### AC-04 PAUSED behavior is unchanged
A PAUSED run resumes to its protected resume stage and cannot use the failed-run PLAN-refresh mode.

### AC-05 Current PLAN evidence is persisted before IMPLEMENT
After a PLAN-refresh resume, autonomous continuation executes the existing protected PLAN runtime and persists a new successful PLAN attempt before IMPLEMENT dispatch.

### AC-06 Worker recovery remains bounded
The explicit failed-run retry prepares the prior terminal worker as `RECOVERING`; PLAN execution does not mint a worker lease. IMPLEMENT dispatch alone may move the worker through the existing `RECOVERING -> REASSIGNED` path and increment lease generation.

### AC-07 Historical evidence is preserved
Prior PLAN attempts, implementation failures, worker checkpoints, accepted lineage and run events remain unchanged and visible.

### AC-08 Current routing policy is authoritative
The refreshed PLAN is generated from current server-owned orchestration/routing policy. Historical selected-agent ordering is never replayed merely to satisfy the retry.

### AC-09 Public API remains compatible
The client sends the same `/resume` payload as before. PLAN refresh is derived server-side; no browser/model/repository text can request it directly.

### AC-10 Release and production proof
Focused state-machine/service/route/worker/agentic-runtime tests and full protected release gates pass. After exact-source production deployment, acting through the existing authenticated QA/user flow on a failed IMPLEMENT run must show a new PLAN event followed by worker `REASSIGNED` evidence and hosted implementation dispatch, or expose the next bounded failure with preserved diagnostic evidence.

## 7. Security and reliability

The new transition narrows ambiguity rather than widening autonomous authority. A terminal run remains inert until explicit human resume. The server chooses PLAN refresh only from immutable pre-mutation durable state and server-owned runtime configuration. PLAN itself remains non-mutating and cannot accept source lineage. The worker remains unleased during PLAN refresh and cannot mutate source until the existing protected reassignment boundary is crossed.

## 8. Non-goals

- Automatic retries of FAILED runs.
- Dynamic stale-plan exception recovery during ordinary autonomous execution.
- Rewriting historical PLAN attempts.
- Changing model priorities, candidate bounds or validator-guided repair.
- Changing client retry UX.
- New repository/provider permissions.
- Moving or bypassing REVIEW.
