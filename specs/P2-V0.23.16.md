# Parallax 2.0 — WebGL Capability Preflight for Reduced Graphics

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.23.16
Date: 2026-08-30
Workstream: GitHub issue #398
Architecture target: v3.28 unchanged

## 1. Objective

Ensure the authenticated web client reaches the existing functional reduced-graphics experience when a browser can load CanvasKit/Skia assets but cannot create any WebGL rendering context. Detect that capability boundary before importing and mounting the Skia application so a WebGL-unavailable browser does not enter a later Canvas failure path.

## 2. Fixed decisions

- The web entrypoint performs one bounded, synchronous capability probe before `LoadSkiaWeb` and before importing the Skia `App`.
- The probe creates an ephemeral browser canvas and treats WebGL as available when either a `webgl2` or `webgl` context can be created.
- If neither context can be created, or capability probing throws, Parallax selects the already-existing `FallbackApp` reduced-graphics experience immediately.
- If WebGL is available, the existing Skia initialization path remains unchanged, including its current catch-and-fallback behavior when CanvasKit initialization itself fails.
- The preflight is presentation capability detection only. It cannot create lifecycle, source, provider, deployment, authentication, Project, Work Specification, Engineering Run, or REVIEW authority.
- No browser fingerprint, capability result, graphics details, raw exception, or renderer payload is persisted or sent to the API by this change.
- Authentication remains outside and above the selected application surface through the existing `WebAuthRoot` registration path.

## 3. Scope

- `apps/client/index.web.tsx`;
- one small server-independent web capability helper under `apps/client/src/web/`;
- deterministic client/browser regression coverage for WebGL-unavailable and normal-WebGL startup;
- `apps/client/package.json` only if needed to include the regression in the existing visual gate;
- this specification and its protected compiled-plan evidence.

No API, persistence, database, provider, deployment-policy, Engineering Run, source-lineage, worker-recovery, model-routing, or server contract changes are in scope.

## 4. Non-goals

- Replacing Skia or changing the approved visual system.
- Treating reduced graphics as the default on WebGL-capable browsers.
- GPU/vendor fingerprinting, performance scoring, telemetry collection, or analytics.
- Detecting every possible later GPU driver reset or context-loss event after a successful mount.
- Reload loops, forced refresh, automatic graphics re-upgrade, or browser-specific user-agent rules.
- Relaxing authentication or bypassing the existing signed-in gate.
- Adding client-side lifecycle or application authority.

## 5. Security and reliability

The capability decision is derived only from browser rendering capability. Repository text, model output, API data, URL parameters, user messages, and remote provider responses cannot select the result. Probe exceptions fail closed to the existing functional reduced-graphics surface rather than leaving the application unmounted.

The probe creates no network request, reads no credential, enumerates no GPU vendor/renderer extension, persists no state, and emits no capability evidence to server APIs. The fallback continues to use the ordinary `WebAuthRoot`, Project compatibility gate, conversation/API contracts, and protected server authority.

The normal graphics path keeps the existing `LoadSkiaWeb` exception fallback, so this preflight narrows a known gap without removing the established CanvasKit failure recovery path.

## 6. Acceptance criteria

### AC-01 WebGL-unavailable browsers choose reduced graphics before Skia
When browser canvas context creation returns `null` for both `webgl2` and `webgl`, the web entrypoint selects `FallbackApp` without invoking `LoadSkiaWeb` or importing the Skia `App` first.

### AC-02 Probe exceptions fail safely
If browser capability probing throws, startup selects the same functional reduced-graphics surface rather than leaving an uncaught boot failure.

### AC-03 Normal WebGL startup is unchanged
When either `webgl2` or `webgl` context creation succeeds, startup continues through the existing `LoadSkiaWeb` and Skia `App` path.

### AC-04 Existing CanvasKit failure recovery remains
A WebGL-capable browser whose `LoadSkiaWeb` initialization later fails still selects `FallbackApp` through the existing bounded initialization catch path.

### AC-05 Authentication remains authoritative
Both normal and reduced-graphics applications continue to register through `WebAuthRoot`; the graphics decision cannot create, bypass, or alter an authenticated session.

### AC-06 Reduced graphics remains functional
The WebGL-unavailable browser reaches the signed-in reduced-graphics workspace with no Skia canvases and retains ordinary conversation/build-plan behavior already provided by `FallbackApp`.

### AC-07 No capability fingerprint or persistence
The probe does not request GPU vendor/renderer details, persist capability state, send capability data to APIs, or introduce user-agent/browser-specific allowlists.

### AC-08 Authority boundaries are unchanged
No server API, Project, Work Specification, Engineering Run, source-lineage, validation, provider, deployment, promotion, or REVIEW authority changes.

### AC-09 Browser regression covers the escaped failure mode
Automated browser acceptance explicitly makes both WebGL context requests unavailable before page startup and proves reduced graphics renders without an uncaught Canvas/WebGL error while ordinary graphics acceptance remains green.

### AC-10 Release regression suite remains green
Exact-head client typecheck/state/export/browser/Skia acceptance, protected API/contracts, Bounded Autonomy, protected promotion, Workstream Spec Validation, and DSPy release compilation pass before merge.
