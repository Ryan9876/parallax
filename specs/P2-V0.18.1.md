## 1. Objective

Generalize Parallax repository understanding beyond its own codebase by introducing a deterministic, bounded repository-intelligence layer for unfamiliar Project-bound repositories. The layer must derive only evidence-backed compatibility facts needed by later Wave 5 planning: repository/application shape, ecosystem and language signals, package/workspace roots, relevant manifests/configuration, non-authoritative build/test/validation candidates, and explicit unsupported or materially ambiguous conditions.

Repository intelligence is observation and classification, not execution authority. Repository text, manifests, package scripts, README content and configuration values are untrusted input. They may support a compatibility conclusion, but they may not grant tools, credentials, provider scope, executable commands, deployment authority, secret access, evaluator changes or policy overrides.

The output is a typed server-owned compatibility profile bound to the canonical Project, repository identity and immutable provider/source revision. Same exact source must produce the same normalized profile and digest across retry/process recreation. Unsupported, unsafe, unbounded or materially ambiguous cases fail closed with bounded typed reasons instead of guessed behavior.

## 2. Fixed decisions

- **Repository evidence is not authority.** Source text and repository configuration never directly create `ExecutionSpec`, provider invocations, capabilities, credentials, approvals or deployment actions.
- **Canonical source identity only.** Analysis is bound to the persisted Project repository binding and exact immutable source revision already accepted by protected source interfaces. Caller/model-selected repository URLs, revisions or roots are forbidden.
- **Read-only compatibility layer.** This workstream adds no source mutation, shell execution, package installation, Git command, network request, credential exchange, provider mutation or deployment behavior.
- **Deterministic normalization.** Equivalent exact source evidence produces one stable ordered profile and digest independent of filesystem iteration order, model output or process lifetime.
- **Bounded evidence.** Only allowlisted manifest/configuration names, normalized metadata and bounded evidence references may enter the profile. Arbitrary source blobs, unrestricted README text and secret-like values are not retained.
- **Candidate commands are informational only.** Package scripts or conventional ecosystem commands may be represented as normalized non-authoritative candidates with provenance. They can never cross into a protected command registry without a separate server-owned accepted policy decision.
- **Fail closed on ambiguity.** Conflicting roots, unsupported ecosystems, unsafe paths/symlinks, malformed manifests, excessive evidence or incompatible repository shapes produce typed compatibility blockers rather than a guessed root/toolchain.
- **Project privacy remains strict.** No source fact from another Project may influence or populate the current Project profile.
- **No hidden reasoning.** The profile contains bounded evidence and conclusions only, never chain-of-thought, scratchpads or unrestricted model rationale.
- **Wave 4 execution truth remains unchanged.** Engineering Run, Work Specification binding, immutable lineage, protected implementation/execution, provider authority, evaluation and REVIEW/HUMAN_REQUIRED remain authoritative.

## 3. Architecture requirements

### 3.1 Repository evidence contract

Add a narrow repository-intelligence module under `services/api/parallax_api/code/` that accepts a server-owned repository evidence snapshot rather than an arbitrary local path or network resource. The snapshot identity must contain canonical `project_id`, normalized repository reference, exact immutable source revision and a bounded tuple of source entries supplied by existing protected repository/source interfaces.

Each source entry must have a normalized safe POSIX-relative path, content digest, byte size and only the bounded UTF-8 content required for allowlisted manifests/configuration. The analyzer must reject absolute paths, traversal segments, duplicate paths, symlinks represented as analyzable files, digest/size mismatches and evidence outside configured bounds.

The repository evidence contract does not itself fetch remote content, clone repositories, inspect local arbitrary directories or resolve credentials. Existing Project/provider/source layers remain responsible for authenticated source acquisition.

### 3.2 Compatibility profile

The analyzer returns an immutable typed `RepositoryCompatibilityProfile` containing only bounded normalized facts:

- canonical Project ID;
- normalized repository reference identity/digest;
- exact source revision;
- deterministic profile version and profile digest;
- repository shape classification such as `single-package`, `static-web`, `python-service`, `workspace-monorepo`, `mixed`, `unsupported` or `ambiguous`;
- ordered ecosystem/language signals with evidence paths;
- ordered package/workspace/application roots;
- ordered allowlisted manifest/configuration evidence summaries;
- ordered non-authoritative build/test/validation candidate descriptors with source/provenance;
- normalized compatibility state `SUPPORTED`, `PARTIAL`, `UNSUPPORTED` or `AMBIGUOUS`;
- bounded typed blocker codes and evidence references.

The profile must not contain arbitrary repository file content, raw provider responses, credentials, environment values, unrestricted logs, hidden reasoning or executable authority.

### 3.3 Deterministic detection

Detection rules must be explicit and deterministic. At minimum support evidence signals for:

- JavaScript/TypeScript applications through bounded `package.json`, workspace and common framework/configuration evidence;
- Python applications/services through bounded `pyproject.toml`, `requirements*.txt`, `setup.cfg`/`setup.py` and common test/configuration evidence;
- static web applications through bounded HTML/CSS/client-source structure and compatible manifest/configuration evidence;
- workspace/monorepo shapes through bounded root workspace declarations and child manifests;
- mixed/full-stack shapes when multiple supported application roots coexist without contradictory authority.

Language/ecosystem inference is evidence-based, not a full semantic parser. Unknown file extensions alone cannot create supported command authority. README/prose may never override structured compatibility evidence.

### 3.4 Non-authoritative command candidates

The profile may include bounded candidate descriptors such as a package-script name, test-framework signal or conventional ecosystem validation class. Each candidate must be structurally marked `authoritative=false` and retain its evidence path/digest. Candidate values are data only.

No method in the repository-intelligence module may return an `ExecutionSpec`, executable command line, provider invocation, capability grant, credential handle or deployment target. Tests must prove malicious package scripts or documentation cannot cross this boundary.

### 3.5 Ambiguity, unsupported state and safety

Use explicit blocker codes for material ambiguity/failure, including at least:

- `UNSUPPORTED_ECOSYSTEM`;
- `AMBIGUOUS_APPLICATION_ROOT`;
- `CONFLICTING_WORKSPACE_DECLARATION`;
- `MALFORMED_MANIFEST`;
- `UNSAFE_SOURCE_PATH`;
- `EVIDENCE_LIMIT_EXCEEDED`;
- `SOURCE_IDENTITY_MISMATCH`.

A repository may be `PARTIAL` when useful bounded facts exist but later capability selection must still resolve a documented compatibility gap. `AMBIGUOUS` or `UNSUPPORTED` profiles cannot be silently treated as `SUPPORTED` by downstream consumers.

### 3.6 Downstream contract

Later Wave 5 workers may consume only the typed accepted profile/interface from this workstream. They must not independently re-scan raw repository content to derive tool authority. The profile is planning evidence, not execution authorization; later governed skills/service/orchestration layers remain responsible for their own accepted policy boundaries.

No production route activation, persistence migration or client UI is required by this workstream. A pure typed domain service with deterministic fixtures is preferred unless an existing narrow repository/source adapter is necessary for integration tests.

## 5. Security and privacy

- Repository source is hostile/untrusted input even when it belongs to the authenticated Project.
- Manifest keys/values and documentation cannot request secrets, change system policy, grant capabilities or select provider authority.
- Secret-like values and arbitrary content are never serialized into the compatibility profile.
- Paths must remain normalized, relative and bounded; traversal/absolute/symlink-like evidence fails closed.
- Evidence sizes/counts are bounded before parsing; oversized manifests/configuration fail closed rather than being truncated into misleading authority-bearing conclusions.
- Cross-Project compatibility lookup or profile reuse is outside this workstream and forbidden.
- Error/blocker output is bounded and typed; do not echo arbitrary repository strings into operator-visible errors.

## 6. Failure and recovery boundaries

- Invalid canonical source identity fails before analysis.
- Unsafe or duplicate source paths fail before manifest interpretation.
- Malformed allowlisted structured manifests produce `MALFORMED_MANIFEST`; they do not fall back to README guesses.
- Conflicting workspace/application roots produce an ambiguous profile or blocker, not automatic root selection.
- Unsupported ecosystems remain explicitly unsupported.
- Retry/process recreation over the same exact source evidence must converge on the same normalized profile/digest.
- Any attempted coupling from repository candidate text to executable/provider authority fails tests and blocks integration.
- Existing Wave 4 protected execution/provider/evaluation regressions must remain green.

## 7. Non-goals

- executing discovered repository scripts;
- installing dependencies or selecting runtime versions dynamically;
- generic repository indexing/search or semantic embeddings;
- model-driven arbitrary technology detection;
- remote repository cloning or credential handling;
- service provisioning or secret injection;
- application generation/orchestration;
- cross-Project engineering memory/reuse;
- changing provider scope, evaluation policy, deployment authority or operator REVIEW semantics.

## 8. Acceptance criteria

### AC-01 Canonical exact-source binding
Repository analysis accepts only a server-owned snapshot bound to canonical Project ID, normalized repository identity and exact immutable source revision; caller/model-selected repository/ref/root authority and cross-Project identity mismatch fail closed.

### AC-02 Bounded safe repository evidence
Only normalized relative unique source paths and bounded allowlisted manifest/configuration evidence are analyzed. Unsafe/traversal/absolute/symlink-like paths, digest/size mismatch, duplicate paths and evidence count/byte overflow fail closed with bounded typed reasons.

### AC-03 Deterministic compatibility profile and digest
The same exact repository evidence produces the same ordered typed compatibility profile and profile digest across input ordering, retry and process recreation. Profile identity/version and canonical source identity are explicit.

### AC-04 Representative repository-shape detection
Deterministic fixtures prove evidence-backed classification for representative JavaScript/TypeScript, Python, static-web and workspace/monorepo repositories, including mixed/full-stack shapes when unambiguous.

### AC-05 Non-authoritative command and tool candidates
Detected package scripts/framework/test/build signals are represented only as bounded evidence-backed candidates explicitly marked non-authoritative. No repository-derived value is converted to `ExecutionSpec`, executable command authority, capability grant, provider invocation or deployment target.

### AC-06 Ambiguous and unsupported repositories fail closed
Conflicting roots/workspaces, malformed structured manifests and unsupported ecosystems yield `AMBIGUOUS`, `UNSUPPORTED` or bounded blockers and cannot be silently normalized to `SUPPORTED`.

### AC-07 Malicious repository instructions cannot alter authority
Fixtures containing README/manifests/package scripts that request credentials, shell/network access, production deployment, policy override, hidden reasoning or broader provider scope do not alter the compatibility profile's authority boundary and never expose the requested sensitive material.

### AC-08 Privacy-safe bounded output
Compatibility profiles retain normalized facts, evidence paths/digests and bounded blocker codes only; arbitrary source blobs, raw provider payloads, credentials, environment values, unrestricted logs and hidden reasoning are absent.

### AC-09 Existing protected runtime regressions remain green
Wave 4 repository bootstrap, durable lineage, protected implementation, exact-lineage BUILD/TEST/VERIFY, bounded source delivery, provider least privilege, authentication and protected evaluation tests remain unchanged or stronger.

### AC-10 Exact-head worker release boundary
The candidate contains this approved spec plus authentic committed DSPy plan evidence and only declared bounded implementation/tests. Exact-head Workstream Spec Validation, Parallax P2 CI and Bounded Autonomy pass. The worker opens a PR targeting `integration/wave5-generalized-delivery`, does not merge/deploy/apply migrations/change production configuration, and stops READY FOR INTEGRATION.
