## 1. Objective

Add the missing durable authority contract between an approved Work Specification and the already-existing protected browser-validation subsystem.

P2-V0.23.40 correctly made static-web TEST/VERIFY evidence truthful: structural execution can target every protected acceptance criterion while `acceptance_ids_verified=[]`. P2-V0.16.2 already provides bounded exact-Preview browser validation primitives, but Parallax currently has no persisted, operator-approved mapping from the immutable Work Specification acceptance map to those typed workflows. `ProtectedBrowserValidator` is therefore not production-composable without risking candidate-defined tests or model-authored runtime authority.

P2-V0.23.47 introduces a separately versioned **Behavioral Verification Plan**. The plan is generated only from an exact approved Work Specification, binds exact Work Specification ID/revision/digest, covers every acceptance ID exactly once, classifies each criterion as either `BROWSER` or `HUMAN_ONLY`, and compiles every `BROWSER` criterion into the existing closed `BrowserWorkflow` action contract. The plan has its own explicit operator approval lifecycle.

This release does **not** execute a browser, alter TEST/VERIFY evidence, reduce `acceptance_ids_unverified`, mutate source, publish provider state, transition an Engineering Run, merge a PR, or promote production.

## 3. Durable Behavioral Verification Plan

### 3.1 Separate artifact

A Behavioral Verification Plan is a separate durable artifact. It does not mutate the approved Work Specification or change its digest.

The plan binds:

- exact `work_specification_id`;
- exact Work Specification revision;
- exact `work_specification_digest`;
- its own positive plan revision;
- status `DRAFT`, `APPROVED`, or `SUPERSEDED`;
- canonical plan JSON;
- canonical SHA-256 plan digest;
- generator program version and model identity;
- created/updated/approved timestamps.

This separate identity allows legacy approved Work Specifications, including frozen W9-S1, to gain a behavioral plan without rewriting historical Work Specification state.

### 3.2 Acceptance coverage partition

Every plan contains exactly one entry for every server-derived acceptance ID in the bound Work Specification.

Each entry is one of:

- `BROWSER`: deterministic browser behavior can materially verify the criterion through the existing typed browser contract;
- `HUMAN_ONLY`: the criterion is not safely reducible to the bounded browser contract in this release and remains for human REVIEW.

No acceptance ID may be missing, duplicated, invented, or mapped to both modes.

`HUMAN_ONLY` is not failure and is never reinterpreted as verified evidence.

### 3.3 BROWSER plan contract

A `BROWSER` entry contains one bounded workflow draft that compiles into the existing `BrowserWorkflow` type.

The server derives workflow identity from the exact acceptance ID and plan revision. The generator cannot choose workflow IDs.

The generator may propose only:

- registered viewport IDs from the current server-owned viewport catalog;
- existing `BrowserActionKind` values;
- relative paths;
- existing `SemanticTargetKind` values and bounded target text;
- bounded non-secret fixture values;
- bounded screenshot checkpoint labels.

The following remain impossible:

- arbitrary JavaScript/eval;
- shell or command strings;
- arbitrary CSS/XPath selectors;
- arbitrary URLs, schemes, hosts or ports;
- headers, cookies, credentials or auth material;
- generic HTTP;
- external-network authority;
- filesystem paths;
- provider payloads;
- source mutation.

Every BROWSER workflow must:

- contain at least one registered viewport;
- contain at least one deterministic assertion action;
- contain at least one screenshot checkpoint;
- satisfy the existing `BrowserWorkflow` constructor and action bounds.

### 3.4 Generation authority

Behavioral-plan generation receives only:

- the exact approved Work Specification contract;
- its exact server-derived acceptance map;
- fixed server instructions describing the bounded browser vocabulary.

Generation must not receive candidate source, repository file contents, Preview content, browser DOM, provider payloads, runtime logs, credentials, or hidden reasoning.

The dedicated DSPy program may classify a criterion `HUMAN_ONLY` whenever bounded browser proof would be unsafe or semantically weak.

A generated draft is only a proposal. It gains no browser-execution authority until:

1. the server validates exact acceptance coverage and typed workflow structure;
2. the artifact is persisted;
3. the authenticated operator explicitly approves that exact plan revision.

### 3.5 Approval and revision semantics

Only an exact `APPROVED` Work Specification may receive a Behavioral Verification Plan.

Creating a new plan draft:

- increments plan revision for that Work Specification;
- marks any older unapproved DRAFT plan as `SUPERSEDED`;
- preserves any previously approved plan until a replacement plan is explicitly approved.

Approving a plan:

- requires exact DRAFT status;
- marks any previously approved plan for that exact Work Specification as `SUPERSEDED`;
- stamps `approved_at`;
- does not mutate the Work Specification, conversation status, Engineering Run, source lineage, delivery, browser evidence, or lifecycle.

Re-approving the same already-approved plan is idempotent.

## 4. Data model and migration

Add one additive table, `behavioral_verification_plans`.

Required fields:

- `id varchar(36) primary key`;
- `work_specification_id varchar(36) not null`;
- `work_specification_revision integer not null`;
- `work_specification_digest varchar(64) not null`;
- `revision integer not null`;
- `status varchar(24) not null`;
- `plan_json text not null`;
- `plan_digest varchar(64) not null`;
- `program_version varchar(100) not null`;
- `model_id varchar(160) null`;
- `created_at`, `updated_at`, `approved_at`.

Constraints:

- FK to `work_specifications(id)` with cascade deletion alongside its owning Work Specification;
- unique `(work_specification_id, revision)`;
- positive revision;
- status limited to DRAFT/APPROVED/SUPERSEDED;
- digest shape validated by application contract;
- index on work specification and status.

Production migration remains additive and rollback-safe. No existing row or Work Specification is rewritten.

## 5. API contract

Add authenticated owner-scoped endpoints:

- `GET /v1/work-specifications/{specification_id}/behavioral-verification-plan`
  - returns the latest plan or null;
- `POST /v1/work-specifications/{specification_id}/behavioral-verification-plan/draft`
  - requires the bound Work Specification to be APPROVED;
  - runs the dedicated behavioral-plan coordinator;
  - returns the validated persisted DRAFT;
- `POST /v1/behavioral-verification-plans/{plan_id}/approve`
  - explicitly approves one exact DRAFT plan revision.

Read DTOs expose:

- exact plan identity/revision/status/digest;
- exact bound Work Specification identity/revision/digest;
- ordered acceptance entries;
- for each entry, mode and typed bounded workflow summary;
- generator metadata and timestamps.

No API accepts raw workflow JSON, caller-supplied acceptance IDs, candidate source, arbitrary URLs, browser evidence, or plan status.

## 7. Security and authority boundaries

- Work Specification identity/digest is server-authoritative.
- Acceptance IDs are server-derived and cannot be supplied by the caller/model.
- Candidate source cannot influence plan generation.
- Plan generation has no provider/browser/source/runtime mutation authority.
- Plan approval is explicit human authority and cannot be automated by the run.
- The plan cannot widen existing browser network or action vocabulary.
- No plan status changes Work Specification status or Engineering Run state.
- No plan result is treated as acceptance proof in P2-V0.23.47.
- No browser launch occurs in this release.
- No GitHub/Vercel mutation, source lineage, merge, default-branch publication or production promotion authority is added.
- Human REVIEW remains the completion ceiling.

## 8. Compatibility

### Existing approved Work Specifications

Legacy approved Work Specifications may create a new plan bound to their exact existing ID/revision/digest. Historical Work Specification rows remain byte-for-byte unchanged.

### Existing Engineering Runs

An existing Engineering Run may later consume a plan only if its exact Work Specification ID/revision/digest matches. P2-V0.23.47 does not yet perform that consumption.

### Existing static-web TEST/VERIFY

No evidence shape changes. `STRUCTURAL_ONLY`, `acceptance_ids_verified=[]`, and the complete unverified set remain exactly as in P2-V0.23.40.

### Existing browser subsystem

No existing browser action, evidence, network, screenshot or multimodal contract is weakened. P2-V0.23.47 only introduces a durable approved workflow source for a later production-composition release.

## 9. Acceptance criteria

### AC-01 Exact Work Specification binding
A Behavioral Verification Plan can be created only for an exact APPROVED Work Specification and persists its exact ID, revision and current server-computed digest. DRAFT/SUPERSEDED/missing specs fail before generation/persistence.

### AC-02 Exact acceptance partition
A persisted plan covers every bound Work Specification acceptance ID exactly once with mode BROWSER or HUMAN_ONLY. Missing, duplicate, reordered-to-wrong-text, invented, or conflicting acceptance identities fail validation.

### AC-03 Candidate source cannot define tests
The behavioral-plan coordinator input is provably limited to the exact Work Specification contract, acceptance map and fixed browser vocabulary. Repository files, candidate source, Preview/browser content and provider evidence are absent.

### AC-04 BROWSER entries compile only to existing typed workflow contract
Every BROWSER entry compiles through existing `BrowserAction`, `SemanticTarget`, registered viewport and `BrowserWorkflow` constructors. Invalid action fields, arbitrary URLs/selectors/scripts/network material or unregistered viewports fail closed.

### AC-05 HUMAN_ONLY stays explicitly unverified
A HUMAN_ONLY criterion contains no executable workflow and cannot be represented as verified behavioral evidence.

### AC-06 Draft/approval lifecycle is explicit and replay-safe
Plan drafts revision monotonically, supersede older DRAFTs, preserve older APPROVED plans until explicit replacement approval, and same-plan reapproval is idempotent.

### AC-07 Plan digest is canonical
Canonical serialized plan content produces one deterministic SHA-256 digest. Read-back recomputation matches persisted digest; structurally equivalent plan content cannot gain alternate identity through key order or incidental formatting.

### AC-08 Owner-scoped API
Only the authenticated owner of the plan's Work Specification conversation can read, draft or approve a plan. Caller-supplied plan content/status/acceptance IDs are impossible through the public API.

### AC-09 Product UI makes authority clear
Desktop and compact/mobile Build Plan surfaces can create, review and approve the plan. Copy clearly distinguishes `verification plan approved` from `application verified`, and HUMAN_ONLY items remain visible.

### AC-10 Existing Work Specification and Engineering lifecycle remain unchanged
Work Specification digest/approval semantics, conversation amendment behavior, Engineering Run state/revision, TEST/VERIFY evidence, source lineage, provider delivery and human REVIEW behavior are unchanged.

### AC-11 Migration is additive and guarded
The migration creates only the new table/indexes/constraints, preserves all existing data, and is covered by contract tests. Production schema preflight or release validation proves the table exists before plan routes are treated as ready if a feature flag/readiness guard is required by existing migration conventions.

### AC-12 Full protected release validation
Authentic DSPy SpecCritic/SpecCompiler evidence is committed. Focused plan/domain/repository/route/client tests, full API regression, client state/typecheck/export, Python compilation, Workstream Spec Validation, P2 CI, Bounded Autonomy and applicable client visual/smoke checks pass on exact reviewed heads.
