## 1. Objective

Make hosted implementation-agent selection follow the server-owned cost/capability escalation policy `openai/gpt-5.6-luna -> openai/gpt-5.6-terra -> openai/gpt-5.6-sol` instead of the lexical order of agent identity SHA-256 digests. Preserve deterministic orchestration, exact replay identity, bounded candidate recovery, protected evaluation and all existing source/deployment authority boundaries.

## 2. Triggering evidence

Production runtime evidence on 2026-08-29 showed an autonomous IMPLEMENT path invoking hosted implementation agents in the order `Sol -> Terra -> Luna`. The canonical hosted model chain is declared as `Luna -> Terra -> Sol`, but the agentic runtime admits three same-capability implementation agents into `AdmittedRoster`; orchestration then canonicalizes roster entries, unit eligibility and selected teams by identity digest. `schedule_team_plan()` assigns the first eligible digest, so an integrity identifier unintentionally became an economic/model-routing policy.

The observed behavior is deterministic but wrong. A cryptographic identity digest proves identity; it has no semantic relationship to model cost, preferred capability tier or escalation order.

## 3. Fixed decisions

- The hosted production escalation order remains `Luna -> Terra -> Sol`.
- Agent identity digests remain cryptographic identity/integrity values only and never determine model priority.
- Orchestration receives an explicit server-owned selection priority as admission metadata, separate from agent identity.
- Lower selection-priority values are attempted before higher values when otherwise equally eligible.
- The priority is finite, deterministic, included in orchestration evidence/digests, and cannot be supplied by browser text, model output, repository content or provider response.
- Generic orchestration retains deterministic input-order independence: priority ties are broken by identity digest.
- Unit eligibility order and selected-team order are canonicalized from the priority-ordered admitted roster rather than re-sorted lexically by digest.
- Candidate-rejection recovery from P2-V0.23.8 consumes the same canonical eligible-agent order, so recovery escalates to the next priority rather than the next digest.
- The smallest-capable-team rule remains. For equivalent hosted implementation agents, a serial unit selects Luna alone; two truly parallel independent units may select Luna and Terra; Sol is excluded unless needed as the next bounded eligible alternate or by a future explicit server-owned policy/capability distinction.
- Protected proposal validation remains authoritative. An earlier model is not considered successful merely because it returned provider output; existing generation/validation requirements must pass before escalation stops.

## 4. Architecture requirements

### 4.1 Admission metadata

`AdmittedAgent` gains a bounded non-negative integer selection-priority field. The default preserves generic/reference behavior. The value is server admission policy, not part of `AgentIdentity`, but it is serialized into the admitted-roster evidence so changing priority changes the roster digest and therefore plan identity.

`AdmittedRoster` canonical order is `(selection_priority, identity_digest)`. This keeps deterministic replay independent of caller tuple order while making the intended policy explicit.

### 4.2 Plan canonicalization

`UnitPlan` must preserve a supplied canonical eligible order rather than lexically sorting digests internally. `TeamPlan` is the canonical boundary that normalizes selected and eligible digest sequences against the admitted-roster order. Unknown, duplicate or non-admitted digests continue to fail closed.

This avoids relying on mutable input order while ensuring all scheduling/recovery consumers see the same priority order.

### 4.3 Hosted production mapping

The live agentic runtime maps the canonical hosted model chain to explicit selection priorities in server-owned code. Production default adapters therefore admit Luna before Terra before Sol regardless of the SHA-256 lexical values of their identities.

Injected test/reference adapters remain deterministic. They may use explicit priority where the test is exercising priority semantics; otherwise equal priority falls back to identity-digest order.

### 4.4 Scheduling and recovery

`schedule_team_plan()` continues to select the first eligible unused agent, but that sequence is now the canonical priority sequence. P2-V0.23.8 `candidate_recovery_assignment()` remains structurally unchanged and therefore automatically chooses the next not-yet-attempted agent in the same priority sequence.

No model priority may bypass capability eligibility, team-size bounds, concurrency bounds, coordination-domain serialization, retry bounds, proposal validation or protected evaluation.

## 5. Scope

Owned implementation scope:

- orchestration admission metadata and canonical priority ordering;
- hosted runtime mapping from Luna/Terra/Sol to explicit priority;
- focused deterministic routing and recovery regressions;
- authoritative architecture/current-state records after validation and deployment.

No client/UI, database migration, provider credential, model catalog, DSPy prompt contract, source-lineage format, Git publication or deployment-target change is required.

## 6. Security, reliability and economics

Priority is released server policy. Untrusted model/repository/browser/provider content cannot set or reorder it. A priority value grants no source, Git, provider, deployment, REVIEW or promotion authority and does not alter agent capabilities.

Identity digests retain their integrity purpose. Priority is not encoded by manipulating hashes or agent identifiers.

The change is economically conservative: it prevents the most capable/costly hosted model from being selected merely because its digest sorts first. It does not sacrifice quality because every selected model must still pass the existing protected generation/validation boundary; failures escalate to the next admitted model within existing bounds.

Parallelism is not allowed to inflate the team beyond the existing smallest-capable-team policy solely to increase throughput. Existing decomposition and coordination semantics remain authoritative.

## 7. Acceptance criteria

### AC-01 Canonical hosted first choice
For a serial implementation work unit with all three hosted agents equally eligible, the first scheduled model is `openai/gpt-5.6-luna` even when its identity digest does not sort first lexically.

### AC-02 Canonical escalation
When Luna is rejected before canonical mutation, candidate recovery selects Terra next; if Terra is also rejected and the existing reassignment bound permits another alternate, Sol is selected last.

### AC-03 Sol excluded from ordinary smallest team
For equivalent-capability work, a one-agent plan selects Luna; a two-agent parallel plan selects Luna and Terra. Sol is not selected merely because of digest order.

### AC-04 Deterministic replay
Equivalent graph, roster, priority metadata and policy produce identical roster digest, plan ID and schedule regardless of input tuple ordering.

### AC-05 Priority is evidence
Changing an admitted agent's selection priority changes admitted-roster evidence/digest and therefore cannot silently alter scheduling under an unchanged plan identity.

### AC-06 Tie determinism
Agents with equal selection priority retain deterministic identity-digest tie ordering.

### AC-07 Fail-closed plan integrity
Duplicate, unknown, malformed or non-admitted selected/eligible digests remain rejected. Priority cannot make an ineligible agent schedulable.

### AC-08 Existing recovery bounds preserved
Candidate recovery remains bounded by `max_reassignments_per_work_unit`; worker process/lease recovery semantics remain unchanged.

### AC-09 Existing routing parity
The ordinary non-agentic `ModelRouter` continues to use its existing `Luna -> Terra -> Sol` sequence and no provider/model authority is widened.

### AC-10 Regression and release proof
Focused orchestration/candidate-recovery tests, full API regression, Bounded Autonomy, protected spec/plan, DSPy release and protected promotion gates pass on exact head. Production runtime evidence after deployment shows a representative autonomous implementation starts with Luna, and a Luna-success path does not call Sol.

## 8. Non-goals

- Repricing or changing model provider rates.
- Dynamically choosing a model from untrusted request text.
- Adding user-facing model selectors.
- Weakening structured-output/proposal validation to reduce retries.
- Changing DSPy prompts or acceptance criteria solely to force Luna success.
- Guaranteeing Luna is always sufficient; Terra and Sol remain bounded fallbacks.
- Removing multi-agent decomposition or bounded candidate recovery.
- Changing REVIEW, deployment or production-promotion authority.

Revert the release commit. No migration or persistent schema change is introduced. Rollback does not require source-lineage or provider-state repair.
