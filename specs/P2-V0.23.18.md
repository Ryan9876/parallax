# Parallax 2.0 — Server-Owned Model Patch Canonicalization

Status: APPROVED FOR IMPLEMENTATION

Date: 2026-08-30
Workstream: GitHub issue #501
Architecture target: v3.30

## 1. Objective

Prevent provider-successful implementation candidates from exhausting the bounded agent set solely because a model reproduced mechanical unified-diff metadata incorrectly, while preserving exact source matching, fail-closed mutation, immutable Work Specification ownership, accepted lineage, protected validation, and all Git/deployment/REVIEW authority boundaries.

Production evidence after P2-V0.23.17 shows the same workload-sensitive failure on both an explicit retry of Engineering Run `2b3cd15f-c5e2-481a-8266-c92c6534b08b` and a newly created Engineering Run `fe4ea283-8d82-4a38-9fa6-a555ca0e3a4b`: Luna, Terra, and Sol each complete provider calls and return parseable proposals, but the safe proposal validator rejects every candidate and the worker ends `AGENTIC_CANDIDATE_EXHAUSTED`. The dedicated Python and OT Time production QA fixtures pass, proving provider reachability and the ordinary protected lifecycle remain healthy.

## 2. Fixed decisions

- Model text never becomes mutation authority.
- The existing strict `TextPatchEngine` remains the final source patch verifier and committer.
- A server-owned canonicalization layer may run only after an ordinary strict patch attempt fails for unified-diff format or exact-position conflict; unsafe target, secret-sensitive content, stale-base digest, size/aggregate limit, unsupported extension, symlink, missing parent, and other protected failures remain fail-closed.
- Canonicalization may repair only mechanical unified-diff metadata: accepted path header prefix form, hunk counts, hunk coordinates, and exact relocation of a hunk whose old/context record sequence exists unmodified in current protected source.
- Relocation uses exact string equality only. It may use the declared old position when that position exactly matches the hunk; otherwise the complete old/context sequence must occur at exactly one admissible non-overlapping source position.
- No fuzzy text matching, edit-distance matching, semantic patching, approximate context, shell `patch`, Git apply, network tool, model retry outside existing ceilings, or source mutation is permitted during canonicalization.
- Pure insertions into an existing file remain anchored by the model-declared old position because they contain no source text capable of unique relocation.
- New-file recovery requires `/dev/null` old-file semantics and addition-only intent; the existing empty-content SHA-256 and parent/target safety rules remain authoritative.
- The canonicalized diff is re-submitted to the unchanged strict patch engine. Only a proposal that then passes the ordinary safe implementation validator can become a disposable candidate.
- Model-provided `expected_base_sha256` remains enforced unchanged in this release; stale-base failures are not silently rebound.
- The canonicalizer emits only bounded reason-class telemetry and never logs or persists raw model output or arbitrary source text.

## 4. Non-goals

- Relaxing target/path/secret/size/source-lineage safety.
- Ignoring or replacing stale expected-base SHA-256 values.
- Accepting approximate, fuzzy, semantic, AST, or model-inferred matches.
- Rewriting malformed JSON/model schema output.
- Changing acceptance-ID ownership or allowing partial acceptance coverage.
- Increasing team size, reassignment count, model count, competition rounds, replans, or autonomous retry ceilings.
- Changing provider order, provider credentials, execution snapshots, dependency preparation, protected BUILD/TEST/VERIFY commands, source publication, deployment, promotion, or REVIEW completion authority.
- Retiring the legacy application-repository QA identities; that trust contraction remains a follow-up release after the user-visible implementation blocker is fixed.

## 5. Security and reliability

Canonicalization is a proof-producing translation, not a permissive patch application path. For an existing file, every source-consuming record in the proposed hunk (context and deletion) must match exact current UTF-8 source content. If the declared position is wrong, relocation is allowed only when the entire source-consuming sequence has one unique admissible occurrence after prior hunks. Multiple matches are ambiguity and fail closed. Pure additions cannot be relocated without source evidence and therefore remain coordinate-anchored.

The translated patch receives server-generated canonical file headers and hunk counts/positions and is then parsed again by the existing strict `TextPatchEngine`. The ordinary engine still proves target containment, extension allowlist, symlink exclusion, secret-sensitive path/content exclusion, expected base digest, exact source records, non-overlap, byte limits, no-op rejection, and atomic commit/rollback behavior.

No raw rejected proposal, source line, provider payload, credential, environment value, or arbitrary exception text becomes durable evidence. Bounded logs may state only whether strict preparation succeeded, canonicalization succeeded, or canonicalization was rejected by a fixed reason class.

## 6. Acceptance criteria

### AC-01 Strict valid patches remain unchanged
A currently valid strict single-file unified diff continues to validate and apply exactly as before without canonicalization changing its bytes or result.

### AC-02 Mechanical hunk metadata can be canonicalized
For an existing safe text target, a proposal with exact context/deletion/addition intent but incorrect hunk counts or positions is converted to a canonical strict diff and accepted only when the source-consuming sequence matches exact protected source at one admissible location.

### AC-03 Exact declared-position recovery is deterministic
When the declared old position points at an exact source-consuming sequence, that exact location is used even if equivalent text exists elsewhere; no search-based ambiguity is introduced.

### AC-04 Unique relocation is exact and bounded
When the declared position is wrong, a hunk may relocate only if its complete source-consuming sequence has exactly one admissible non-overlapping exact match. Zero or multiple matches are rejected.

### AC-05 Pure insertion remains coordinate anchored
An existing-file hunk containing additions only is never fuzzy-relocated. Its declared old position must be in bounds and non-overlapping.

### AC-06 New-file recovery remains bounded
A new safe target may canonicalize addition-only diff intent only with `/dev/null` old-file semantics. Existing empty-base SHA, parent directory, extension, path, secret, size, and no-op protections remain unchanged.

### AC-07 Stale base and safety failures remain fail-closed
Wrong expected-base SHA-256, unsafe/secret path or content, unsupported extension, symlink, missing parent, oversized patch/result/source, ambiguous relocation, mismatching context/deletion text, overlapping hunks, multi-file intent, and malformed records remain rejected.

### AC-08 No authority expansion
Work Specification binding, acceptance-ID equality, candidate/worker ceilings, model order, source lineage acceptance, disposable candidate validation, Git/deployment authority and REVIEW boundary are unchanged.

### AC-09 Bounded observability distinguishes the boundary
Runtime diagnostics may identify fixed canonicalization result/rejection classes without persisting raw model output, raw source text, provider payloads, credentials, or arbitrary exception messages.

### AC-10 User-visible production replay crosses the former blocker
After deployment, replay at least one production path that previously ended `AGENTIC_CANDIDATE_EXHAUSTED` and require evidence that IMPLEMENT crosses the candidate safe-patch boundary. Simple Python/OT Time QA fixture success alone is insufficient acceptance evidence.

### AC-11 Architecture records the durable contract
`ARCHITECTURE.md` v3.30 records server-owned exact patch-intent canonicalization followed by the unchanged strict patch verifier.

### AC-12 Release gates remain green
Exact-head API/contracts, client/browser/Skia, Bounded Autonomy, protected promotion, Workstream Spec Validation, and DSPy release compilation pass before merge.

## 7. Release gate

Before merge:

- focused tests cover AC-01 through AC-09, including ambiguous exact text, wrong hunk counts/coordinates, pure insertion, new file, stale digest, unsafe path/content and multi-hunk non-overlap;
- full protected release gates pass on the exact candidate head;

- verify the exact API source deployment is READY and aliased to production;
- verify production `/health` and `/ready`;
- inspect runtime errors;
- replay a previously failing non-trivial user path or an equivalent production fixture whose prior evidence showed all hosted candidates rejected by safe proposal validation;
- require the new run to cross that candidate boundary and record whether it reaches REVIEW or exposes a later independent defect;
- update `CURRENT-STATE.md` with exact deployment and replay evidence.

## 8. Rollback

Revert the release commit. No database migration, persisted schema migration, source-lineage rewrite, Project migration, Work Specification migration, provider credential change, or deployment-policy change is introduced. Existing strict patch semantics are restored by removing the canonicalizing composition layer.
