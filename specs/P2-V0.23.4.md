## 1. Objective

Decouple source-repository access, protected engineering execution, and deployment-provider selection so Parallax can build applications that are deployed through Vercel, downloaded for IIS/local/manual deployment, or later delivered through another provider without requiring a Vercel Project or Vercel deployment target merely to progress through the Engineering Run lifecycle.

The current production path already defers Vercel Project readiness until verified delivery, but PLAN source bootstrap still obtains GitHub read authority through Vercel Connect. That makes a deployment provider part of the source-control credential path and prevents a public GitHub Project such as `Ryan9876/ot-time` from advancing when the Vercel Connect installation does not cover that repository.

## 2. Fixed decisions

- Repository/source authority and deployment authority are separate capabilities.
- A Project may have no deployment provider configured and still progress through PLAN, IMPLEMENT, BUILD, TEST, VERIFY, and REVIEW.
- Vercel remains an optional supported Preview/deployment provider; no-deployment Projects do not create or require Vercel Projects.
- Public GitHub repositories may use bounded anonymous read-only GitHub access for canonical source bootstrap because the provider itself requires no credential for those reads.
- Anonymous public-repository access is read-only and cannot create branches, commits, pull requests, deployments, provider projects, credentials, or production authority.
- Private repositories still require an explicitly authorized exact-repository credential before source bootstrap.
- Source mutation/publication remains separately gated. A no-deployment Project may complete protected implementation and produce accepted/downloadable source lineage without publishing a GitHub branch/PR if write authority is unavailable or not selected.
- Existing exact Project / Work Specification / Engineering Run / accepted-lineage / protected validation / REVIEW boundaries remain authoritative.
- No PAT fallback, owner impersonation, cross-tenant access, all-repository silent expansion, production promotion, or REVIEW completion is introduced.

## 3. Delivery modes

Parallax supports a server-owned Project delivery policy with these initial modes:

- `vercel-preview`: existing GitHub publication plus Vercel Preview path, retaining current exact target/source binding and Preview-only autonomous ceiling.
- `source-only`: no hosting provider is required. Protected execution produces accepted source lineage and a bounded handoff/download artifact at REVIEW. No Vercel Project or Preview is created.

Future IIS, local, Azure, AWS, Cloudflare, container, or other delivery adapters must plug into the same deployment-provider seam rather than changing repository/source authority.

If a Project predates explicit delivery-mode persistence, compatibility policy is server-owned: registered existing Vercel targets continue as `vercel-preview`; otherwise the Project may operate as `source-only` until a deployment provider is deliberately selected.

## 4. Security and authorization requirements

- Canonical repository identity always comes from the owner-scoped Project binding.
- Anonymous GitHub bootstrap is allowed only for GitHub API responses that prove the exact canonical repository exists and is public.
- A repository reported private, inaccessible, ambiguous, redirected to a different identity, or otherwise unverifiable must not fall back to anonymous source reads.
- Anonymous access may execute only repository resolve, source tree read, and source file read actions under the existing read-only Project capability registry.
- Provider responses remain bounded by existing tree-entry, file-size, UTF-8, secret-sensitive-path, digest, revision, and lineage rules.
- Write/publication operations always require an explicit scoped credential and retain exact-repository scope verification.
- No bearer token, app installation token, cookie, OIDC token, provider secret, source bytes, or unrestricted provider payload is persisted in run evidence or client responses.
- Missing deployment configuration is not a source-bootstrap failure for `source-only` Projects.
- Missing GitHub write authority is not silently broadened. If source publication is requested and unavailable, the run stops at the appropriate human-required/repository-authorization boundary while preserving accepted source.

## 5. Product and lifecycle requirements

- PLAN must be able to bootstrap an exact public repository without Vercel Connect when no GitHub credential is required for read access.
- IMPLEMENT/BUILD/TEST/VERIFY remain bound to the exact accepted lineage and existing protected execution semantics.
- Reaching REVIEW in `source-only` mode must not call Vercel discovery, Vercel Project creation, Preview creation, or Vercel deployment APIs.
- `source-only` REVIEW exposes bounded handoff evidence sufficient to retrieve/export the exact accepted source lineage without exposing internal Blob credentials or raw storage URLs.
- Existing `vercel-preview` Projects continue to publish only the exact verified accepted lineage and require READY Preview evidence before successful delivery is recorded.
- The client may present deployment as optional, but server-owned Project/run truth remains authoritative.

## 6. Acceptance criteria

### AC-01 Public repository bootstrap is deployment-independent
A Project bound to exact public repository `github:Ryan9876/ot-time` can bootstrap canonical source and advance beyond PLAN without a Vercel Project, Vercel Preview target, or Vercel Connect GitHub credential.

### AC-02 Anonymous source authority is read-only
Anonymous GitHub access can perform only exact repository resolve/tree/file reads. Branch, commit, pull-request, provider-project, deployment, environment, secret, merge, or promotion operations cannot use the anonymous path.

### AC-03 Private repositories remain fail-closed
A private or non-public repository cannot use anonymous fallback. Missing exact-repository credentials return an explicit authorization-required state before source mutation.

### AC-04 Protected lifecycle remains exact-lineage bound
PLAN/IMPLEMENT/BUILD/TEST/VERIFY preserve current Project/spec/run binding, accepted-lineage identity, protected commands, deterministic validation, and fail-closed behavior.

### AC-05 Source-only REVIEW requires no Vercel
A `source-only` run that passes protected validation reaches REVIEW with exact accepted-source handoff evidence and makes no Vercel readiness, Project, Preview, deployment, alias, domain, environment, or promotion request.

### AC-06 Existing Vercel Preview delivery does not regress
`vercel-preview` retains exact registered/discovered target identity, exact GitHub publication identity, READY Preview requirement, replay behavior, and Preview-only autonomous ceiling.

### AC-07 Download/handoff evidence is bounded and replay-safe
Source-only delivery records canonical Project/run/work-spec/source-lineage/content identity and a safe handoff identifier only. It contains no raw source bytes, provider credentials, storage secrets, arbitrary URLs, or hidden reasoning, and exact retry resolves the same handoff without duplicate mutation.

### AC-08 Deployment provider is optional and extensible
Runtime composition selects source authority independently from delivery mode, with a narrow delivery interface that can support Vercel today and IIS/local/other adapters later without changing protected engineering semantics.

### AC-09 OT Time production proof
After exact release deployment, a QA-owned canonical Project bound to `github:Ryan9876/ot-time` advances beyond PLAN revision 1 through ordinary authenticated production APIs without `REPOSITORY_AUTHORIZATION_REQUIRED` or a Vercel-target prerequisite. No out-of-band source edit or auth bypass is used.

### AC-10 No authority widening
No reusable PAT, broad GitHub bearer, owner impersonation, cross-tenant Project access, arbitrary provider administration, production promotion, or REVIEW-completion authority is added.

## 7. Expected implementation areas

- `services/api/parallax_api/code/production_bootstrap.py` and a narrow provider-independent GitHub bootstrap credential/read seam;
- `services/api/parallax_api/tools/providers/github_client.py` or a compatible anonymous-read adapter without weakening authenticated write paths;
- `services/api/parallax_api/code/production_delivery_lazy.py` / source-delivery composition for explicit `source-only` versus `vercel-preview` delivery;
- bounded source-only delivery/handoff evidence using existing durable lineage/storage abstractions;
- Project delivery-policy configuration/persistence only if required by existing schema; prefer a backward-compatible server-owned policy over a migration when it fully satisfies the outcome;
- focused security/lifecycle/regression tests;
- production QA OT Time replay.

Exact files remain subject to implementation review. Unrelated refactoring is not authorized.

## 8. Non-goals

- Implementing IIS deployment automation in this slice.
- Implementing Azure, AWS, Cloudflare, container registry, SSH, SMB, or arbitrary remote deployment.
- Removing Vercel as a supported deployment provider.
- Allowing arbitrary download URLs or exposing private Blob object URLs.
- Creating GitHub repositories automatically.
- Treating a public repository as authorization for write operations.
- Weakening protected validation, accepted-lineage CAS/idempotency, source-path safety, REVIEW, or production-promotion rules.
