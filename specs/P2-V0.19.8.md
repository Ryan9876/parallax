## 1. Objective

Add a provider-neutral, configuration-driven local-first model routing capability for Parallax instances that can actually reach an operator-controlled local inference endpoint. When explicitly enabled in an admitted local/self-hosted runtime, Parallax may attempt one server-owned local model route first and then fall back through the existing hosted GPT-5.6 Luna -> Terra -> Sol chain. Protected validation, canonical model identity, Project/source authority, provider credentials, Preview, REVIEW and release governance remain unchanged.

Local-first routing is opt-in and server-owned. With no admitted local-first configuration, runtime behavior remains exactly the accepted hosted chain. Vercel production is deliberately hosted-only under this workstream: neither loopback nor remote private-inference endpoints are admitted from Vercel production. A future remote/private inference gateway for hosted Parallax requires a separate architecture, security and deployment workstream.

## 2. Fixed decisions

- Authoritative Wave 6 `P2-V0.19.7` remains intact. This workstream uses the unique identity `P2-V0.19.8` and requires fresh evidence under that identity.
- The existing hosted model order remains the compatibility default: `openai/gpt-5.6-luna`, `openai/gpt-5.6-terra`, `openai/gpt-5.6-sol`.
- Local-first routing is enabled only by validated server-owned configuration; callers, prompts, repository content and model output cannot create routes, endpoints, credentials or route order.
- One admitted local route may precede the hosted chain. Multiple arbitrary local routes are outside this workstream.
- Each route resolves its own provider transport. A local endpoint must never globally redirect hosted GPT-5.6 traffic away from the fixed Vercel AI Gateway transport.
- Existing explicit `DSPY_API_BASE` / `DSPY_API_KEY` remains a deliberate whole-transport operator/development override and is not silently combined with local-first routing.
- Protected validators remain authoritative. Local success stops escalation only when the existing validator accepts the result.

- Request-scoped Vercel OIDC remains the only automatic hosted-production GPT-5.6 credential path. Process-environment `VERCEL_OIDC_TOKEN` remains non-authoritative.

- Local model/provider content is labor/evidence only and grants no shell, unrestricted network, source mutation, provider-spending, GitHub/Vercel, approval, REVIEW or release authority.
- No database migration, client redesign or production environment change is part of this candidate.

## 3. Architecture requirements

### 3.1 Server-owned route definition

Introduce one bounded immutable route definition containing model identity, provider kind and the server-owned endpoint/key-slot references required by that provider. Configuration must reject empty or duplicate identities, unsupported provider kinds, malformed endpoints, inline secret material where a key-slot identity is required, reserved hosted credential slots and unbounded values.

### 3.2 Configuration-driven route order

Resolve effective model order from server-owned configuration. When local-first is absent or disabled, return the exact hosted order. When valid local-first configuration is enabled in an admitted runtime, the local model appears exactly once before the hosted chain. Parsing is deterministic and fails closed.

### 3.3 Runtime locality boundary

This workstream admits local-first transport only where Parallax itself is not running in Vercel production. Loopback HTTP(S) is allowed for explicitly local/self-hosted operation. Non-loopback endpoints must use HTTPS and remain server-owned, but they are still rejected when `VERCEL_ENV=production`.

No public tunnel, reverse proxy, Tailscale/Cloudflare tunnel, VPN connector, hosted private-link service or remote inference gateway is created automatically. Any such hosted-to-private transport requires a separate governed workstream covering authentication, network exposure, availability, observability, secret handling, abuse controls and rollback.

### 3.4 Per-route transport isolation

Model construction resolves transport from the selected route rather than applying one global endpoint to every model. The admitted local route may use an Ollama-compatible or OpenAI-compatible endpoint. Hosted `openai/gpt-5.6-*` routes retain the fixed Vercel AI Gateway endpoint, canonical model identities and request-scoped credential boundary.

### 3.5 Protected fallback semantics

The existing sequential model router remains authoritative for attempts. Provider failures are sanitized to bounded error-class evidence. Protected-validation rejection remains distinct from provider failure. Either may advance to the next admitted route; neither may weaken or replace the validator.

### 3.6 Bounded diagnostics

Attempt evidence and logs may include admitted model identity, provider kind, bounded status, duration and sanitized error class. They must exclude endpoint credentials, authorization headers, raw exceptions/messages, prompts, model payloads, generated source and hidden reasoning.

### 3.7 Compatibility and rollback

Default behavior remains hosted-only. Runtime rollback is disable/removal of local-first server configuration plus application rollback if required. Because no persistence schema changes are introduced, no database down-migration is required.

## 6. Security and privacy

Local inference endpoints are untrusted model transports, not authority. Only server-owned configuration determines which model/provider/endpoint combination is admissible. Caller/model/repository content cannot create routes, change endpoints, supply credentials or expand provider/network authority.

Credentials remain outside prompts, source packages, route evidence and logs. Hosted production GPT-5.6 traffic continues to use admitted request-scoped Vercel OIDC. A local endpoint credential, when needed outside Vercel production, is resolved only from a separately named server-side secret slot that cannot reuse protected hosted credential names.

A local route grants the model no filesystem, shell, canonical source mutation, arbitrary HTTP, provider-administration, deployment or approval capability. Cross-Project privacy and exact Project/Work Specification/source-lineage contracts are unchanged.

Vercel production rejects local-route activation before model execution. This prevents a configuration mistake from silently converting a hosted production deployment into an unreviewed remote-private network client.

## 7. Acceptance criteria

### AC-01 Unique spec/evidence identity
`P2-V0.19.8` is the only specification/evidence identity for the reconciled local-first candidate. Current authoritative `P2-V0.19.7` remains byte-for-byte owned by Wave 6 and is not replaced or reinterpreted.

### AC-02 Default hosted compatibility
With no admitted local-first configuration, effective runtime order remains exactly Luna -> Terra -> Sol and existing hosted transport/routing tests remain green.

### AC-03 Validated server-owned local configuration
One bounded server-owned local route can precede the hosted chain outside Vercel production. Empty, duplicate, malformed, unsupported, caller-controlled, secret-bearing or reserved-credential configuration fails closed before model execution.

### AC-04 Vercel production remains hosted-only
When `VERCEL_ENV=production`, enabling local-first routing fails closed before any local endpoint request, whether the endpoint is loopback or remote HTTPS. The accepted hosted chain remains the only automatic production route under this workstream.

### AC-05 Per-provider transport isolation
A configured local endpoint applies only to its exact admitted local model. Hosted GPT-5.6 routes continue to use the fixed Vercel AI Gateway with canonical model IDs and cannot be redirected to the local endpoint.

### AC-06 Local success stops escalation
Outside Vercel production, when the local route returns a result accepted by the existing protected validator, routing returns that result and does not attempt a hosted model.

### AC-07 Local provider failure falls back
Outside Vercel production, local unavailability/provider failure records only bounded sanitized evidence and advances to the next admitted hosted route without changing acceptance requirements.

### AC-08 Local protected-validation failure falls back
When the local route returns output rejected by the existing protected validator, routing records `validation_failed`, advances to the next admitted route and cannot lower or bypass the validator.

### AC-09 Hosted credential boundary preserved
Request-scoped Vercel OIDC remains the only automatic hosted-production GPT-5.6 credential path. Process `VERCEL_OIDC_TOKEN`, local credentials and local configuration cannot substitute for hosted-production authority.

### AC-10 Explicit DSPy override compatibility
Existing explicit `DSPY_API_BASE` / `DSPY_API_KEY` behavior remains a deliberate whole-transport operator/development override. Local-first configuration is disabled rather than silently combined when that explicit override is present.

### AC-11 Bounded diagnostics and secret safety
Logs and attempt evidence contain only admitted model/provider identity, status, duration and sanitized error class. Tests prove endpoint credentials, authorization values, raw exception text/results, prompts and generated content are absent.

### AC-12 No authority expansion
Tests and code inspection prove local-first routing grants no source acceptance, Project/spec mutation, shell/filesystem authority, unrestricted network capability, provider spending/administration, GitHub/Vercel authority, approval, REVIEW completion or production deployment authority.

### AC-13 Post-Wave-6 exact-head reconciliation
The semantic candidate is constructed from the current reconciled `main` lineage rather than by directly merging old PR #303. Wave 6 runtime/replay, model transport, safe deletion and current whole-product tests remain green.

### AC-14 Authentic spec and whole-product validation
