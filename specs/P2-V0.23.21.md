# Parallax 2.0 — P2-V0.23.21 Bounded Greenfield Inspection Diagnostics

Status: APPROVED FOR IMPLEMENTATION — SPEC-FIRST

Date: 2026-08-30
Workstream: #442
Architecture target: v3.32 (no durable authority or lifecycle change expected)
Starting baseline: `4c04d2f2df351648133980e15e77e3e724489b67`

## 1. Objective

Remove one production diagnostic blind spot in the W9-S1 empty-greenfield bootstrap without changing repository classification, provider authority, lifecycle state, error semantics, or mutation behavior.

P2-V0.23.20 correctly recognizes GitHub's exact authenticated empty-repository default-ref response. The subsequent fresh `Ryan9876/parallax-qa1` replay still failed safely at PLAN. Runtime logs expose only the earlier public-source bootstrap `PROVIDER_INVALID_RESPONSE` because `GreenfieldProjectedRepositoryLineageBootstrap.ensure()` deliberately rethrows the original public-source error whenever authenticated greenfield inspection fails for a reason other than `REPOSITORY_AUTHORIZATION_REQUIRED`.

That preservation behavior is correct for runtime semantics, but it hides the bounded normalized result code needed to distinguish missing exact repository authorization from credential, scope, provider, or response failures.

## 2. Fixed decisions

- Preserve public-first source bootstrap and the original outward failure for all non-authorization greenfield inspection failures.
- Preserve structured `REPOSITORY_AUTHORIZATION_REQUIRED` recovery exactly as released.
- Do not infer greenfield from a diagnostic code or from any provider/source failure.
- Add no repository, Git, Vercel, deployment, model, browser, user, or QA authority.
- Add no provider token, raw response body, HTTP headers, repository content, URL, credential material, Project/run identity, or arbitrary exception text to logs.
- Diagnostic output may contain only a fixed event label and the existing bounded normalized provider result code extracted from protected `ProviderActionFailed` evidence. If no such code exists, use one fixed server-owned fallback label rather than exception text.
- Logging must occur immediately before preserving the existing control flow.
- No client/API response schema change is required.
- Architecture remains v3.32 because the durable authority, lifecycle, state, provider, and recovery contracts are unchanged.

## 3. Scope

- `services/api/parallax_api/code/greenfield_composition.py` for one bounded diagnostic helper/logging boundary;
- focused API tests proving normalized-code logging, fixed fallback logging, authorization equivalence, generic outward-failure equivalence, and no raw exception leakage;
- this specification and its protected compiled DSPy plan evidence;
- `CURRENT-STATE.md` only after an exact production deployment and replay establish the material diagnostic result.

No architecture-file edit is expected because the release does not alter durable authority, lifecycle, provider, persistence, recovery, or state-machine semantics.

## 4. Non-goals

- Changing positive-empty classification or GitHub empty-ref compatibility.
- Changing public-first source bootstrap behavior.
- Replacing the original outward failure for generic greenfield inspection failures.
- Adding repository consent flows, Connect administration, PATs, reusable provider credentials, or browser-supplied provider tokens.
- Expanding GitHub/Vercel permissions or retrying provider calls.
- Moving repository initialization earlier than REVIEW.
- Changing model routing, source lineage, implementation validation, Git publication, Preview publication, or the human REVIEW ceiling.
- Surfacing raw provider payloads or external exception strings to logs, APIs, clients, or persisted evidence.
- Treating diagnostic output as authority to initialize a greenfield repository.

## 5. Required behavior

### 5.1 Safe normalized diagnostic

When authenticated greenfield inspection raises:

1. derive the existing normalized provider result code using the same protected exception-chain traversal already used by authorization recovery;
2. emit a single server log record with fixed event name `greenfield_repository_inspection_failed` and field `result_code=<bounded normalized code>`;
3. never interpolate raw exception text or provider payload;
4. if no protected normalized code exists, emit fixed `result_code=UNCLASSIFIED_PROVIDER_FAILURE`.

### 5.2 Existing authorization recovery

If the failure is or contains `REPOSITORY_AUTHORIZATION_REQUIRED`, preserve the current structured `RepositoryAuthorizationRequiredError` and same-run retry behavior. The diagnostic must not alter its user-visible message/code.

### 5.3 Existing generic failure behavior

For every non-authorization inspection failure, rethrow the original public-source bootstrap exception exactly as before. Do not substitute the diagnostic result code into API detail, run failure classification, or source/bootstrap state.

## 6. Security and reliability

The diagnostic is observation only. It must not change positive-empty criteria, initialize lineage, mutate the repository, request broader Connect permissions, retry provider calls, expose secrets/raw external input, or convert a provider failure into greenfield success.

Only the already-normalized bounded provider result code from protected `ProviderActionFailed` evidence may cross into the diagnostic. The event label and fallback value are server-owned constants. Raw exception text, provider bodies, headers, tokens, repository contents, URLs, Project/run identifiers, and arbitrary external strings are prohibited.

The original control flow remains authoritative: exact authorization-required evidence retains its structured recovery path; every other inspection failure preserves the earlier public-source exception. Therefore adding observability cannot weaken fail-closed semantics or alter externally visible runtime behavior.

## 7. Acceptance criteria

### AC-01 Normalized provider result is observable
A protected authenticated greenfield inspection failure with normalized provider evidence emits `greenfield_repository_inspection_failed` and that exact normalized result code.

### AC-02 No raw provider leakage
Raw exception text, token-like values, provider bodies and arbitrary external strings are absent from the diagnostic.

### AC-03 Unknown failures are bounded
An inspection exception without protected normalized provider evidence emits only `UNCLASSIFIED_PROVIDER_FAILURE`.

### AC-04 Authorization behavior is unchanged
`REPOSITORY_AUTHORIZATION_REQUIRED` still produces the existing structured retry-safe 503 contract.

### AC-05 Generic outward behavior is unchanged
Non-authorization inspection failures still preserve/rethrow the original public-source bootstrap failure.

### AC-06 No authority or mutation change
Provider capabilities, credential scopes, greenfield proof rules, lineage initialization, Git/deployment authority, REVIEW ceiling and pre-REVIEW mutation behavior are unchanged.

### AC-07 Regression coverage
Focused tests prove AC-01 through AC-05, and the full API/protected release gates remain green.

### AC-08 Production diagnosis
After exact-source production deployment, a bounded replay against still-empty `Ryan9876/parallax-qa1` captures the normalized authenticated inspection result code without mutating the target. That evidence determines the next #442 action; it does not itself satisfy canonical greenfield acceptance.
