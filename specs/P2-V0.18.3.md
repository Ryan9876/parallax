## 1. Objective

Add a deterministic, typed application service-binding layer that lets Parallax represent a generated application's logical external-service needs without exposing secret values or creating a generic provider/integration surface.

A service binding is server-owned configuration for one canonical Project. It maps a logical service requirement such as a database, object store, authentication service, queue, email provider, or other application dependency to an exact approved adapter contract and declared feature set. Application/model output may express logical requirements only. It may not choose credentials, raw provider endpoints, HTTP methods/bodies, environment mutations, production targets, secret values, or runtime authority.

This workstream stops at deterministic registration, selection, and bounded evidence. It does not provision services, inject environment variables, resolve secret values/handles, call providers, deploy applications, mutate runtime configuration, or add a generic adapter execution interface. Later orchestration/runtime work may consume only the accepted typed binding interface and existing protected secret/deployment mechanisms.

## 2. Fixed decisions

- **Intent is not authority.** A model/generated application may declare a logical service requirement, but only an exact server-approved Project binding can satisfy it.
- **Project scope is immutable.** Every binding and approval is bound to one canonical Project ID. Cross-Project registration, selection, or replay fails closed.
- **Exact-digest admission.** A binding ID/version is admitted only when its canonical content digest exactly matches a server-owned approval. Reusing a version with different content is an immutable version conflict.
- **No secret values.** Binding contracts contain only declared secret-slot identifiers such as schema labels. They never contain secret values, environment values, tokens, credentials, private keys, connection strings, or runtime secret-handle references.
- **No generic provider proxy.** No raw URL, host, HTTP method/body, arbitrary environment key/value, provider target, shell command, filesystem path, Git ref, or deployment action may be represented as binding authority.
- **Adapter identity is allowlisted.** Adapter IDs/versions are bounded server-owned identifiers. Repository text or model preference cannot create an adapter or broaden its scope.
- **Deterministic selection.** For the same exact Project registry and requirement, resolution is stable across ordering, retry, and process recreation. Equally eligible bindings fail to HUMAN_REQUIRED rather than using incidental ordering.
- **Safe output only.** Resolution records expose logical service ID, exact binding identity/version/digest, adapter identity/version, supported feature tokens, declared secret-slot names/count, policy digest and deterministic evidence identity. They explicitly contain no secret values/handles and grant no authority.
- **Existing S1/S2 boundaries remain authoritative.** Repository compatibility and governed skills may provide planning/evidence context, but they cannot register a service binding or convert a requirement into authority.
- **No migration/route/UI in S3.** Prefer a pure typed domain module with deterministic tests. Persistence, provisioning, user configuration UI and runtime secret resolution are later governed work.

## 3. Architecture requirements

### 3.1 Logical service requirements

Define an immutable `ServiceRequirement` containing only bounded normalized intent:

- logical `service_id` token;
- requested interface/version token;
- ordered required feature tokens;
- optional requirement flag only if deterministic semantics are explicit.

Requirements cannot contain raw URLs, provider configuration, credentials, environment assignments, commands, source paths, deployment targets, arbitrary prose, or secret material. Invalid/unbounded fields fail before resolution.

The same canonical requirement must produce the same requirement digest independent of input ordering.

### 3.2 Project-scoped binding contract

Define an immutable `ProjectServiceBinding` containing:

- canonical Project UUID;
- bounded binding ID and semantic version;
- logical service ID;
- adapter ID and adapter version;
- ordered supported feature tokens;
- ordered declared secret-slot IDs (schema labels only, not values or handles);
- bounded deterministic priority used only when eligibility is otherwise unambiguous;
- canonical binding digest.

The contract must reject secret-like/raw configuration fields by construction: there is no value/URL/header/body/environment/credential field in the public contract.

A binding digest covers all identity and compatibility fields, including Project ID, so a binding cannot be replayed into another Project.

### 3.3 Server-owned admission policy and registry

Define a Project-scoped `ServiceBindingAdmissionPolicy` containing:

- canonical Project ID;
- exact approvals for `(binding_id, version, content_digest)`;
- allowlisted logical service IDs;
- allowlisted adapter IDs/versions;
- allowlisted secret-slot identifiers;
- stable policy digest.

A `ProjectServiceBindingRegistry` admits only exact approved contracts. Admission rules:

- Project ID must equal the registry/policy Project;
- binding ID/version with the same digest is idempotent;
- binding ID/version with a different digest fails `BINDING_VERSION_CONFLICT` before other admission decisions;
- absent/digest-mismatched approval fails `BINDING_NOT_APPROVED`;
- undeclarable service, adapter or secret-slot identity fails closed;
- registration order does not affect registry ordering or resolution.

Registry safe metadata must not include arbitrary source/model text or secret values/handles.

### 3.4 Deterministic resolution

Define a resolver that accepts canonical Project ID, one logical `ServiceRequirement`, and a `ProjectServiceBindingRegistry`.

Resolution rules:

- Project mismatch fails closed;
- candidates must match the exact logical service ID and requested interface compatibility;
- required features must be a subset of the binding's supported features;
- no candidate -> HUMAN_REQUIRED / `NO_BINDING_AVAILABLE`;
- candidates exist but features/interface are insufficient -> HUMAN_REQUIRED with bounded reason;
- choose the unique highest-priority eligible binding;
- if more than one eligible binding shares the highest deterministic selection score -> HUMAN_REQUIRED / `AMBIGUOUS_BINDING_SELECTION`;
- never infer a provider from repository/framework names, README text, package scripts, skill procedure text, model preference, existing environment names or deployment provider.

A selected result is eligibility evidence only. It is explicitly `grants_authority=false` and `contains_secret_values=false` / `contains_secret_handles=false`.

### 3.5 Bounded resolution evidence and replay

Define deterministic `ServiceBindingResolutionRecord` construction for Project/run context. It records only:

- canonical Project/run IDs;
- requirement digest and normalized service/features;
- exact binding ID/version/digest;
- exact adapter ID/version;
- binding policy digest;
- supported feature tokens;
- declared secret-slot IDs or a bounded safe representation of them;
- resolution status/reason;
- deterministic resolution ID derived from canonical bounded fields.

Same inputs across retry/process recreation produce the same resolution record/ID. The record cannot contain raw application input, secret values, secret-handle references, provider payloads, environment values, arbitrary logs, source blobs, hidden reasoning, or executable authority.

### 3.6 S1/S2 integration boundary

The S3 module may consume or reference accepted S1/S2 identity/evidence types only where this materially strengthens provenance. It must not modify S1 repository classification or S2 skill admission/selection semantics.

In particular:

- a repository compatibility profile cannot create/register a binding;
- a portable/governed skill cannot create/register a binding;
- skill required capabilities remain prerequisites and are not satisfied/granted merely because an application service binding exists;
- service resolution may record an optional bounded provenance reference to a prior skill invocation/evidence ID, but such provenance never grants binding authority.

Later S4 orchestration may compose S1 compatibility + S2 selected skill + S3 service resolutions, but each retains its own authority boundary.

## 5. Security and privacy

- Logical service requirements are untrusted intent.
- Portable skill/repository/model text cannot register, select by hidden authority, or mutate a Project binding.
- Secret values, connection strings, access tokens, API keys, private keys, provider credentials and runtime secret-handle references must be structurally impossible to serialize through public safe metadata/resolution records.
- Declared secret-slot IDs are schema labels only and must be allowlisted bounded tokens.
- Adapter/service IDs are bounded allowlisted tokens, never URLs or arbitrary executable names.
- Cross-Project binding use fails closed before resolution evidence is returned.
- Error reasons are bounded typed codes and do not echo arbitrary untrusted values.
- No hidden reasoning/scratchpad enters any record.

## 6. Failure and recovery boundaries

Use explicit bounded failures including at least:

- `INVALID_BINDING_CONTRACT`;
- `PROJECT_IDENTITY_MISMATCH`;
- `BINDING_NOT_APPROVED`;
- `BINDING_VERSION_CONFLICT`;
- `SERVICE_NOT_DECLARABLE`;
- `ADAPTER_NOT_DECLARABLE`;
- `SECRET_SLOT_NOT_DECLARABLE`;
- `NO_BINDING_AVAILABLE`;
- `INCOMPATIBLE_BINDING`;
- `AMBIGUOUS_BINDING_SELECTION`;
- `RESOLUTION_IDENTITY_MISMATCH`.

Admission errors fail without mutating the registry. Resolution ambiguity/missing support returns HUMAN_REQUIRED rather than selecting a fallback provider. Retry/process recreation over the same accepted registry/requirement converges on the same result/ID.

## 7. Non-goals

- provisioning Supabase, Vercel, databases, queues, auth, email, storage or any other provider;
- exposing generic provider APIs;
- storing user credentials;
- runtime secret injection;
- generating `.env` values;
- choosing production targets;
- model-driven arbitrary provider selection;
- cross-Project binding sharing;
- implementing the full objective-to-application orchestrator;
- changing current protected execution/provider authority.

## 8. Acceptance criteria

### AC-01 Exact Project-scoped admission
A binding can be admitted only to a registry whose canonical Project ID matches the binding/policy and whose exact `(binding_id, version, digest)` approval exists. Cross-Project use fails closed.

### AC-02 Immutable binding versions and replay
Same binding ID/version/digest admission is idempotent. Same ID/version with changed content fails `BINDING_VERSION_CONFLICT` before unrelated approval checks. Registry ordering/digest behavior is deterministic across insertion ordering/process recreation.

### AC-03 No secret/provider authority in contracts
Binding/requirement contracts expose no raw URL, HTTP method/body, environment assignment, secret value, credential, token, connection string, runtime secret-handle reference, shell command, source path or deployment target field. Safe metadata proves no secret/authority material is present.

### AC-04 Declarable service/adapter/secret-slot policy
Unapproved logical service IDs, adapter IDs/versions or secret-slot IDs fail closed with typed bounded reasons. Repository/model/skill text cannot expand these allowlists.

### AC-05 Deterministic logical-service resolution
For a canonical Project requirement and accepted registry, the resolver deterministically chooses only the unique eligible highest-priority binding whose service/interface/features satisfy the requirement. Input/registration ordering does not affect the selected identity.

### AC-06 Missing/incompatible/ambiguous bindings require human action
No match, insufficient features/interface, or tied highest-priority eligible bindings return HUMAN_REQUIRED with bounded typed reasons; the resolver never guesses or falls back based on provider/framework/repository/model hints.

### AC-07 Privacy-safe replayable resolution evidence
Resolution records are deterministic for the same exact Project/run/requirement/binding/policy, contain only bounded identity/features/declared-slot metadata, and contain no raw application payload, source, secret values/handles, provider payloads, unrestricted logs or hidden reasoning.

### AC-08 S1/S2 authority remains separate
Tests prove repository compatibility and governed skill contracts/invocations cannot create, admit or grant a binding. Service-binding availability does not satisfy or broaden S2 skill capability prerequisites.

### AC-09 Existing protected runtime regressions remain green
Wave 4 protected autonomy, lineage, implementation, BUILD/TEST/VERIFY, source delivery, provider least privilege, authentication, mobile regressions, S1 repository intelligence and S2 governed-skill tests remain unchanged or stronger.

### AC-10 Exact-head worker release boundary
The candidate contains this approved spec, authentic committed DSPy plan evidence, the bounded binding domain and focused tests only. Exact-head Workstream Spec Validation, Parallax P2 CI and Bounded Autonomy pass. Worker PR targets `integration/wave5-generalized-delivery`; no production merge/deploy/migration/configuration/provider mutation occurs.
