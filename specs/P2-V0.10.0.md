# Parallax 2.0 v0.10.0 — Google Identity & Access Control

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.10.0
Depends on: P2-V0.9.1
Method: spec-first authentication-boundary upgrade + release verification

## 1. Objective

Replace the shared browser credential experience with Google sign-in brokered by the dedicated Parallax Supabase Auth project, while preserving the server-side break-glass bearer credential for automation and emergency recovery. Authentication must not imply authorization: only explicitly authorized Google identities may enter Parallax.

## 2. User outcome

The normal production entry surface becomes **Continue with Google**. The owner can authorize or revoke specific Google email identities from inside Parallax. Members receive normal product access without learning or sharing a production access token.

## 3. Scope

- Use the existing Parallax Supabase Auth project as the Google OAuth broker.
- Use OAuth authorization-code flow with PKCE in the browser.
- Keep the Supabase access token transient; exchange it with the Parallax API for the existing secure host-only HttpOnly Parallax session cookie.
- Validate the Supabase user server-side before issuing a Parallax session.
- Require the authenticated Supabase identity to be a Google identity with a usable email address.
- Introduce a durable `authorized_users` allowlist owned by the Parallax API/database, not by browser RLS.
- Support `owner` and `member` roles in v0.10.0.
- Seed the current operator as the initial owner outside repository history.
- Permit owners to list authorized users, add members by Google email, and revoke/reactivate members.
- Bind a Google identity's Supabase user ID to its authorized-user row on successful login.
- Reject authenticated-but-not-authorized Google users with HTTP 403 and a calm access-denied UI.
- Preserve the long-lived root bearer as a server-only break-glass/non-browser automation credential.
- Preserve same-origin `/p2-api`, Reason, Code, Work Specifications, approved-spec execution binding, persistence, Skia, reduced motion, and reduced-graphics behavior.

## 4. Security

- Google authentication alone never grants Parallax access.
- Authorization is controlled by the server-side `authorized_users` table.
- The Supabase publishable key may be present in client code; no Supabase service-role key, Google client secret, or root Parallax bearer may be exposed to the browser.
- The Google/Supabase OAuth access token is transient and must not be persisted to localStorage.
- PKCE verifier/state may use browser session-scoped storage only for the redirect round trip.
- Parallax issues its own HMAC-signed HttpOnly session cookie after Google identity and authorization verification.
- Session cookies remain Secure in production, SameSite=Lax, host-only, and require the existing `X-Parallax-Session: 1` marker on protected browser requests.
- Existing legacy browser sessions are not accepted as identity-bearing Google sessions after promotion; users reauthenticate through Google.
- Root bearer access remains valid for Swagger/automation and break-glass recovery, but the normal production UI does not request or persist it.
- Owner-management endpoints require an owner principal. Members cannot add, revoke, reactivate, or promote users.
- v0.10.0 does not add public sign-up, password auth, magic-link auth, domain-wide implicit access, or organization-wide wildcard authorization.

## 5. Data contract

`authorized_users` stores:

- stable Parallax user ID;
- normalized Google email, unique;
- optional bound Supabase Auth user ID, unique once established;
- display name and avatar URL when known;
- role (`owner` or `member`);
- status (`active` or `revoked`);
- created/updated/last-login timestamps.

The table has RLS enabled and direct `anon`/`authenticated` table access revoked. Parallax's trusted server database connection remains the access path.

## 6. Session contract

A Parallax browser session token contains only signed authorization claims required by the API: subject, role, authentication method, and expiry. User profile information remains server-side and is returned through a protected `/v1/access/me` endpoint.

The break-glass bearer may establish an emergency owner-equivalent session, but that session is clearly marked as `bearer` rather than `google`.

## 7. Owner-management contract

The owner can:

- list the current allowlist;
- add a new member by normalized Google email;
- revoke a member;
- reactivate a member.

v0.10.0 deliberately does not support deleting the last owner or transferring ownership. A future release may add multi-owner/admin governance after it has an explicit contract.

## 8. UX

The production access surface uses Editorial Optical styling and presents one primary action: **Continue with Google**.

States:

- checking existing Parallax session;
- redirecting to Google;
- completing secure sign-in;
- access denied (Google identity valid, Parallax authorization absent/revoked);
- recoverable OAuth failure.

Authenticated owner UI includes a restrained access-management panel reachable from the top bar. The panel shows authorized people, role/status, and owner-only member controls. It must not become a general administration dashboard.

## 9. Acceptance criteria

### AC-01 Google OAuth entry
Normal hosted production browser entry presents Google sign-in rather than a shared access-token field.

### AC-02 PKCE and transient token handling
OAuth uses PKCE. Supabase/Google access credentials are not persisted in localStorage and are cleared after Parallax session exchange.

### AC-03 Server-side identity verification
The API validates the Supabase-authenticated identity and confirms Google is an identity provider before issuing a Parallax session.

### AC-04 Explicit authorization
An active `authorized_users` row matching the verified normalized email is required. A valid Google identity without authorization receives HTTP 403 and no Parallax session cookie.

### AC-05 Owner bootstrap is private
The initial owner allowlist row is inserted directly into the production database and is not committed to public repository history.

### AC-06 Identity binding
On first successful authorized login, the verified Supabase user ID is bound to the allowlist row. A later conflicting user ID for the same row is rejected rather than silently rebound.

### AC-07 Secure Parallax session
Authorized Google login creates a Secure/HttpOnly/SameSite=Lax production cookie containing signed identity/role claims but no Google token or Parallax root bearer.

### AC-08 Existing protected routes remain protected
Conversation, Work Specification, Engineering Run, and other application endpoints accept valid Google-backed Parallax sessions or the root bearer and reject unauthenticated access.

### AC-09 Owner management
An owner can list the allowlist, add a member email, revoke a member, and reactivate a member. Members cannot invoke owner-management mutations.

### AC-10 Break-glass compatibility
The root bearer remains supported for Swagger/non-browser automation and may establish an emergency Parallax session without appearing in the normal browser UI.

### AC-11 UI identity state
The authenticated shell can show the signed-in user's profile/role and expose owner-only access management. Logout deletes the Parallax session and returns to Google sign-in.

### AC-12 Product regression protection
Reason, Code, SSE, durable conversation persistence, Work Specifications, approved-spec execution binding, Skia, reduced motion, and reduced-graphics behavior continue to pass existing release tests.

### AC-13 Database isolation
`authorized_users` has RLS enabled; direct `anon` and `authenticated` table privileges are revoked; uniqueness constraints protect normalized email and bound Supabase user ID.

### AC-14 Release verification
Specification validation, API/auth tests, client typecheck/state tests, web export, browser/Skia acceptance, Google-auth mocked browser acceptance, protected Engineering/Reason/Code evaluation, DSPy release compilation, production migration verification, Vercel READY state, health/readiness, protected-route checks, and runtime-error checks pass before v0.10.0 is recorded as deployment-verified.

## 10. Non-goals

- Google Workspace domain-wide automatic access.
- Enterprise SSO/SAML.
- Public self-registration.
- Email/password or magic-link login.
- Google API access beyond identity (`openid`, `email`, `profile`).
- Multiple owners or admin delegation.
- Per-user conversation isolation or multi-tenant data partitioning in this release.
- Billing, quotas, or user analytics.
- Broader autonomous execution, Git, merge, or deployment authority.

## 11. Risks and mitigations

- **Authentication mistaken for authorization:** keep Parallax allowlist as an independent server-side check.
- **OAuth token leakage:** use non-persistent PKCE client configuration and exchange tokens immediately for HttpOnly Parallax session.
- **Owner lockout:** preserve server-only root bearer break-glass access and seed owner directly in production DB.
- **Account identity drift:** normalize email and bind stable Supabase user ID after first authorized login; reject conflicts.
- **Public repository exposure:** never commit Google client secret, Supabase service-role secret, root bearer, or owner email.
- **OAuth redirect/config drift:** test production callback behavior and keep redirect URLs explicitly configured in Google/Supabase.
- **Scope creep into tenancy:** authorization in v0.10 controls entry only; data ownership/tenant isolation requires a separate future specification.

## 12. Release gate

Implementation is authorized by this specification. Production promotion requires the existing exact-head release validation, production migration evidence, Google-auth server/client tests, Vercel deployment evidence, and live health/readiness/auth-boundary verification.

`ARCHITECTURE.md` must be updated because the durable authentication and authorization boundary changes. `CURRENT-STATE.md` must be updated after verified production promotion. `DESIGN-SYSTEM.md` only changes if durable visual rules change; the Google entry surface should use the existing Editorial Optical system. `PROJECT-CONSTITUTION.md` remains unchanged unless governance principles themselves change.
