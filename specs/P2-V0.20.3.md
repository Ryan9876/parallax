## 1. Objective

Create the operator-facing Development Studio that makes an autonomous Parallax application build understandable, inspectable and safely controllable without requiring the operator to manage individual agents or granting the client authority owned by the server.

The Studio consumes the accepted W7-S2 projection/control API as its sole Agent Run authority. It presents exact Project/Run/Work Specification identity, bounded task/recovery/validation/evaluation/delivery/economic evidence and only the controls advertised by the server.

## 2. Fixed decisions

- The Studio is a full-screen development surface, not a management dashboard or table grid.
- W7-S2 projection identity and server-advertised controls are authoritative; the client does not invent agents, tasks, source lineage, provider identity, acceptance, run state or controls.
- The client never displays hidden reasoning/private scratchpad, raw prompts, credentials, raw provider payloads, source bytes/patches or unrestricted logs.
- Deterministic protected BUILD/TEST/VERIFY failure remains visually authoritative over positive qualitative evaluation.
- `UNKNOWN` economic evidence is rendered explicitly as unknown/unavailable, never as zero.
- REVIEW/HUMAN_REQUIRED is a visible handoff boundary, not a completion or deployment action.
- Production deploy, merge, source acceptance, provider administration and arbitrary command surfaces are absent.
- Stale/rejected control requests visibly reconcile to a fresh server projection rather than pretending success.
- Reconnect/reload reconstructs the current Studio from server projection data; client transient state is never canonical run truth.
- Preserve the existing Parallax visual language: warm cream surfaces, muted terracotta emphasis, ink typography, serif display hierarchy and restrained sans-serif operational detail.

## 3. Information architecture

### 3.1 Identity and state rail

The top region shows exact Project ID, Engineering Run ID, Work Specification ID/revision, current run state/revision and HUMAN_REQUIRED/REVIEW status when present. Identity is compact but always discoverable and copy-safe.

### 3.2 Main Stage

The primary canvas communicates the build as a coherent flow rather than a list of autonomous actors:

- left/primary: task/stage flow derived from projected attempts and dependencies available in the accepted contract;
- center/right: current artifact/progress, selected evidence, validation/evaluation and Preview/delivery context;
- recovery indicators are attached to affected work rather than shown as a disconnected infrastructure panel.

No client-authored dependency, agent roster or speculative progress percentage is introduced.

### 3.3 Evidence dock

A lower dock or collapsible evidence region presents bounded timeline/evidence summaries, deterministic validation gates, independent evaluation, routing/delivery status, recovery/reassignment facts and HUMAN_REQUIRED events. It does not render unrestricted raw logs.

### 3.4 Economic evidence

Time/cost/usage/intervention information preserves W7-S2 observed/estimated/unknown state and provenance. Estimated values are labeled as estimates. Unknown values use an explicit unknown presentation.

### 3.5 Controls

Only `advertised_controls` from W7-S2 may render as enabled actions. A request binds Project, Run, expected revision/state and a client-generated idempotent request identity. The client cannot change the action vocabulary or send source/provider/tool authority.

## 4. Interaction requirements

- `pause`, `resume` and `cancel` appear only when advertised by the current server projection.
- Pending control requests provide local interaction feedback without optimistically rewriting canonical run state.
- Stale revision/state, denied, unauthorized or unsupported responses trigger a fresh projection and a concise bounded explanation.
- Control replay with the same request identity is handled as idempotent success when the server reports replay.
- No page transition implies run mutation.
- Preview references are clearly distinguished from production deployment.
- HUMAN_REQUIRED/REVIEW handoff remains prominent and cannot be dismissed as completed by client state.

## 5. UX states

The Studio must provide intentional states for:

- initial loading;
- no current Project-bound run;
- active run with partial evidence;
- paused/recovering/reassigned run;
- deterministic validation failure;
- REVIEW/HUMAN_REQUIRED;
- projection request failure;
- reconnect/retry;
- stale control rejection;
- unavailable/unknown economics;
- narrow/mobile presentation.

Loading/error/reconnect states may not reuse stale canonical data as if current without a visible stale indication.

## 6. Responsive and accessibility requirements

- Desktop prioritizes the main build flow and evidence context without forcing horizontal page scrolling.
- Narrow/mobile collapses secondary evidence and preserves identity, current state, validation failure and HUMAN_REQUIRED before decorative detail.
- All controls are keyboard reachable and use visible focus states.
- Status is never color-only; text/icon semantics accompany color.
- Dynamic run/control status uses appropriate accessible live-region semantics without excessive announcements.
- Canvas/task relationships have a non-visual semantic representation available to screen readers.
- Text and critical controls meet existing project contrast/readability standards.
- Motion respects reduced-motion preferences.

## 7. Data and security boundaries

The client may consume only fields emitted by the W7-S2 typed projection/control API. It may retain bounded presentation state such as selected task/panel and in-flight request identity, but it may not persist or derive authoritative run/source/provider state.

The UI must not expose credentials, cookies, auth headers, server environment, raw provider payloads, hidden reasoning/private scratchpad, source bytes/patches, unrestricted logs or arbitrary browser/network capability.

Repository/model/user text is untrusted display data and cannot grant controls, redefine identity or generate executable client commands.

## 8. Scope

Authorized semantic scope may include:

- a typed client API adapter for W7-S2 projection/control endpoints;
- normalized client view model that preserves server identity/known-state semantics without adding authority;
- full-screen Agent Run Studio screen/components;
- accessible control and stale/reconnect interactions;
- bounded task/evidence/recovery/validation/economic visualization;
- focused unit/state tests and browser/Skia acceptance coverage.

## 9. Non-goals

- client-managed agent roster or orchestration;
- new task/run lifecycle or recovery semantics;
- arbitrary shell/network/browser commands;
- source editing/acceptance from this surface;
- provider/model administration;
- production deployment or merge;
- REVIEW completion/approval;
- raw log viewer;
- hidden reasoning/prompt display;
- fabricated progress, quality, cost or time values.

## 10. Acceptance criteria

### AC-01 Exact identity and state truth
Studio displays canonical Project/Run/Work Specification/revision/state identity from W7-S2 and does not synthesize replacements.

### AC-02 Understandable task/build flow
The main canvas makes current task/stage flow and progress legible without requiring operator management of individual agents or inventing dependencies.

### AC-03 Artifact/evidence context
Current bounded artifact/progress, validation/evaluation and delivery/Preview evidence is presented in context and binds the exact projected run/source identity available from W7-S2.

### AC-04 Recovery visibility
Checkpoint/recovery/reassignment/generation state is legible when present and is not fabricated from client transient state.

### AC-05 Deterministic validation precedence
Failed protected deterministic validation is visually explicit and cannot be masked by positive evaluation/routing/Preview evidence.

### AC-06 Delivery and REVIEW clarity
Preview/PR/source delivery evidence is clearly non-production; REVIEW/HUMAN_REQUIRED is an explicit handoff and the UI offers no completion/deploy shortcut.

### AC-07 Server-derived control truthfulness
Only current W7-S2 advertised controls are enabled and every request binds Project/Run/expected revision/state/request identity without extra authority fields.

### AC-08 Stale/rejection recovery
Stale, denied, unauthorized and unsupported control outcomes do not optimistically mutate the UI; the Studio refreshes canonical projection and explains the bounded failure.

### AC-09 Economic known-state integrity
Observed, estimated and unknown economics retain their state/provenance semantics; unknown is never rendered as zero and estimated is not represented as observed.

### AC-10 Private data absence
Client code/tests prove credentials, raw provider payloads, prompts, hidden reasoning, source bytes/patches and unrestricted logs are not requested or rendered.

### AC-11 Responsive and accessible operator surface
Desktop and narrow/mobile layouts preserve critical identity/state/validation/REVIEW information, keyboard access, semantic relationships, focus, contrast and reduced-motion behavior.

### AC-12 No authority expansion
Studio grants no new source acceptance, lifecycle transition, recovery ownership, provider/tool administration, arbitrary command/network, merge/deploy or REVIEW completion authority.

Before integration, S3 commits authentic DSPy evidence for `P2-V0.20.3`, reconciles to the latest accepted Wave 7 integration SHA, passes protected spec validation, client type/state/export checks, browser/Skia acceptance and applicable cumulative gates, then stops `READY FOR INTEGRATION` for Control Tower expected-head merge.
