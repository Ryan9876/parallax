## 1. Objective

Allow exact partial-publication replay verification to interpret only the universal canonical Git empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904` as an empty tree snapshot without requiring GitHub to materialize that object through a Trees GET.

This reuses the already-governed P2-V0.23.39 / Architecture v3.48 provider-compatibility rule. No arbitrary 404, missing tree, alternate tree identity, or caller assertion may be normalized as empty.

## 3. Fixed replay model

### 3.1 Exact canonical identity

The replay tree-snapshot boundary may return an empty snapshot without provider tree read only when the exact resolved tree revision equals:

`4b825dc642cb6eb9a060e54bf8d69288fbee4904`

This identity is the universal canonical Git empty tree, not repository-specific mutable state.

### 3.2 Non-canonical trees remain provider-verified

Every non-canonical tree identity continues through the existing bounded recursive GitHub Trees GET and must satisfy:

- successful provider response;
- non-truncated tree;
- `MAX_TREE_ENTRIES` bound;
- supported tree/blob modes;
- structurally valid paths/object SHAs/sizes.

A 404 or any missing non-canonical tree remains `SOURCE_NOT_FOUND`; it is never interpreted as empty.

### 3.3 Exact lineage replay proof remains unchanged

After parent/replay snapshots are constructed, P2-V0.23.44/v3.53 and P2-V0.23.45/v3.54 remain authoritative:

- deterministic exact Parallax lineage commit message;
- exactly one expected parent;
- exact resolved commit tree identities;
- exact changed accepted blob path set;
- supported mode;
- exact accepted byte size;
- exact accepted content SHA-256.

The canonical-empty shortcut supplies only the mathematically fixed empty snapshot for one exact Git object identity. It adds no adoption heuristic.
