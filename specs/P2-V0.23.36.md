## 1. Objective

Remove the verified W9-S1 Preview-target readiness blocker without broadening provider authority. P2-V0.23.35 is production READY and the authenticated frozen Decision Ledger Engineering Run `a64d56b7-ad42-42ad-9562-891783363f4a` reached protected `REVIEW` revision 6. Durable source-delivery event sequence 15 records `provider=vercel`, `action=project.ensure`, `result_code=TARGET_DISCOVERY_UNBOUNDED`.

The failure occurs because `VercelProjectReadinessRestClient._matches()` currently enumerates an unfiltered Vercel team project page and refuses any response with a continuation cursor. The admitted Vercel team contains enough unrelated historical projects to paginate, so exact Project readiness is incorrectly coupled to total account size.

The Vercel Projects API supports filtering project discovery by exact numeric `repoId`. Parallax already resolves and independently verifies the canonical numeric GitHub repository ID through the exact repository-scoped credential before Vercel discovery. P2-V0.23.36 must use that identity to narrow discovery at the provider boundary, request at most two candidates, preserve authenticated read-back, and retain every existing Preview-only and fail-closed control.

## 2. Verified root cause and fixed decisions

- P2-V0.23.35 exact source `4fca5da19e24c276c8a506dfa114266ac8320ae0` is deployed READY as `dpl_ETNgFuWpNH9vC43uqfbx4aWQqrJ7`; production `/health` and `/ready` return HTTP 200.

- The earlier public-source `PROVIDER_INVALID_RESPONSE` evidence is a recoverable source leg for this greenfield run, not the terminal failure. P2-V0.23.36 must not modify public Git parsing or greenfield authority.
- The terminal durable failure is exact: Vercel `project.ensure` returned `TARGET_DISCOVERY_UNBOUNDED` because broad project enumeration exposed pagination.
- Vercel's current Projects request contract supports `repoId` filtering. The filter must use only the numeric repository ID already obtained from exact authenticated GitHub identity verification.
- Discovery must request `limit=2`. Zero verified candidates means the existing bounded provisioning path may create one target. One candidate means existing authenticated read-back determines reuse. Two candidates are enough to prove ambiguity and must fail closed.
- Provider-side filtering is only a narrowing optimization. It does not replace authenticated Vercel read-back, exact team verification, exact Git link type/repository verification, deterministic Project reconciliation, or no-production-deployment proof.
- If a filtered response is malformed, returns a continuation cursor without already proving ambiguity, or otherwise cannot prove the bounded result set, discovery fails closed rather than falling back to broad account enumeration.
- No existing Vercel projects are deleted or cleaned up as part of this fix. Historical account clutter is operationally separate from application correctness.

## 5. Security and architecture requirements

### 5.1 Canonical repository identity remains server-owned

The `repoId` query value must come only from the existing exact repository-scoped GitHub identity flow after canonical Project repository binding and numeric identity verification. Client input, model output, repository content, Vercel project names, environment text, and benchmark fixture text cannot nominate or replace the numeric repository identity.

### 5.2 Provider query narrows authority

Vercel discovery must issue a team-scoped read using the admitted server-owned Vercel credential and query only the exact numeric GitHub repository ID. The request must use a bound of two candidate projects. It must not query another team, accept an unscoped provider list as equivalent evidence, or enumerate unrelated projects.

### 5.3 Two candidates are sufficient ambiguity evidence

The readiness contract needs only three outcomes: none, exactly one, or more than one. A result set containing two exact-repository candidates is already ambiguous and must fail as the existing target-ambiguity condition without fetching additional candidates. No nondeterministic first-match selection is permitted.

### 5.4 Filter success is not authorization

A Vercel list result is only a candidate. Before reuse, the existing authenticated read-back must still prove exact Project ID/name, admitted team/account, Git link type, exact numeric repository ID, and other accepted target fields. Name-only, stale, wrong-team, wrong-repository, malformed, or unverifiable read-back fails closed.

### 5.5 Bounded provider result semantics

If the filtered response has invalid project/pagination structure, invalid candidate identity, or a continuation cursor while fewer than two exact candidates are available, Parallax cannot prove the filtered discovery result is complete and must fail closed with normalized provider evidence. It must not silently ignore the cursor or fall back to broad project enumeration.

If two exact candidates are already returned, ambiguity is proven regardless of an additional continuation cursor and the existing ambiguous-target result remains authoritative.

### 5.6 Creation and conflict reconciliation remain replay-safe

When zero exact candidates exist, the existing deterministic project creation request may run once. On provider conflict/race, reconciliation must repeat the same exact `repoId`-filtered bounded discovery. It may accept only one exact read-back-verified project; zero after conflict or multiple candidates remain failure.

### 5.7 Production deployment remains prohibited

Target readiness may create Vercel Project metadata only under the accepted P2-V0.21.1 contract. It cannot create, promote, or select a production deployment. Existing production-deployment absence checks remain mandatory before admitting a newly created or reused target.

### 5.8 Secrets and observability

No token, OIDC credential, provider bearer, raw provider body, or private authorization detail may enter durable events, logs, client responses, specs, or authoritative records. Existing normalized provider/action/result-code evidence remains sufficient. `TARGET_DISCOVERY_UNBOUNDED` remains available for genuinely incomplete bounded filtered discovery rather than normal team pagination.

## 6. Reliability and rollback

## 9. Risks

- Simply raising the broad-list page limit would leave correctness coupled to account growth and expose unrelated Projects; exact repo filtering is required instead.
- Accepting the first filtered candidate without authenticated read-back would convert a provider filter into authority and is prohibited.
- Following arbitrary pagination until exhaustion would create an unnecessarily broad and variable provider-read surface; the exact filter plus a two-result bound is the intended solution.
- Assuming account cleanup is required would solve an operational symptom rather than the product defect; Parallax must remain correct as unrelated projects accumulate.
- Treating two exact-repository Vercel Projects as harmless would break deterministic reconciliation; ambiguity remains fail closed.
