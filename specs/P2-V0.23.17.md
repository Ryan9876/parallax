# Parallax 2.0 — Dedicated Production QA Repository Admission

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.23.17
Date: 2026-08-30
Workstream: GitHub issue #499
Architecture target: v3.29

## 1. Objective

Move the standing production-QA execution identity out of the Parallax application repository and into the dedicated `Ryan9876/parallax-qa` repository without widening the bounded QA principal or any application, source, model, lifecycle, Git, deployment, or REVIEW authority.

This release is the safe admission phase of a two-phase cutover. It adds one exact `parallax-qa` repository/workflow identity alongside the two already-trusted application-repository QA workflows so the new path can be proven against production before the old workflow identities are retired in a follow-up trust-contraction release.

## 2. Fixed decisions

- The new standing QA repository is exactly `Ryan9876/parallax-qa`.
- The new standing workflow is exactly `Ryan9876/parallax-qa/.github/workflows/production-replay.yml@refs/heads/main`.
- GitHub Actions OIDC trust is evaluated as an exact `(repository, workflow_ref)` pair rather than a repository check plus a repository-agnostic workflow set.
- Existing `Ryan9876/parallax` QA workflow identities remain temporarily admitted only for migration safety until the new repository replay is deployment-verified.
- The existing OIDC issuer, `parallax://qa-production` audience, `refs/heads/main` ref, GitHub-hosted runner requirement, allowed event names, bounded run-id validation, and bounded QA account mapping remain unchanged.
- The new workflow may exercise only the same QA session endpoint and same bounded QA principal as the existing workflows.
- Routine production acceptance in `parallax-qa` covers the Python source-only full experience and OT Time/.NET source-only full experience.
- The dormant W9-S1 greenfield trial is not admitted by the new standing workflow. It requires a separately reviewed exact workflow if a fresh approved empty target becomes available.
- After production proof of the new repository path, a follow-up release removes the two old application-repository QA identities and workflow files.

## 3. Scope

- `services/api/parallax_api/services/github_actions_identity.py`;
- `services/api/tests/test_qa_automation_identity.py`;
- `ARCHITECTURE.md`;
- this specification and its protected compiled-plan evidence.

The dedicated QA repository itself contains the canonical workflow and harness scripts, but those files live in `Ryan9876/parallax-qa` and are not application-runtime source.

## 4. Non-goals

- Creating a new QA user, role, session class, or authorization level.
- Allowing arbitrary repositories, branches, workflow paths, pull-request workflows, self-hosted runners, reusable-workflow callers, or wildcard workflow references.
- Moving product tests, application CI, protected release gates, benchmark definitions, or application source into `parallax-qa`.
- Giving QA source publication, Git mutation, deployment, production promotion, or REVIEW completion authority.
- Permanently retaining dual-repository trust after the new path is proven.
- Re-authorizing the W9-S1 greenfield reference trial as standing production trust.

## 5. Security and reliability

The trust decision is the conjunction of signed GitHub OIDC claims and one exact server-owned repository/workflow pair. The repository and workflow reference must match the same allowlisted pair; a trusted repository cannot substitute another workflow, and a trusted workflow path cannot be replayed from another repository.

The migration is deliberately two-phase to avoid losing the only production QA recovery path while changing authentication trust. The first production deployment temporarily accepts the old exact pairs plus the new exact pair. Only after the `parallax-qa` workflow proves authenticated production access and reaches the normal REVIEW boundary for both routine source-only fixtures may the old application-repository identities be removed.

No token, cookie, raw JWT claim set, provider payload, source archive, model output, or user credential is persisted by the identity verifier. The `parallax-qa` workflow receives the same bounded QA principal already used for production acceptance and cannot inherit normal-user ownership.

## 6. Acceptance criteria

### AC-01 Exact dedicated QA pair is admitted
A valid GitHub Actions OIDC token whose claims identify repository `Ryan9876/parallax-qa`, ref `refs/heads/main`, workflow `Ryan9876/parallax-qa/.github/workflows/production-replay.yml@refs/heads/main`, GitHub-hosted runner, admitted event, and correct audience is accepted.

### AC-02 Repository and workflow are bound as one pair
A token using the `parallax-qa` repository with an old `Ryan9876/parallax` workflow reference, or the application repository with the new `parallax-qa` workflow reference, is rejected.

### AC-03 Existing migration identities remain temporarily valid
During this admission release only, the two existing exact main-branch application-repository QA workflow identities continue to authenticate so rollback and migration validation remain available.

### AC-04 Existing claim guards remain fail-closed
Wrong ref, self-hosted runner, unadmitted event name, wrong audience, invalid signature/standard claims, missing run id, untrusted repository, or untrusted workflow pair is rejected.

### AC-05 QA principal authority is unchanged
Successful new-repository OIDC authentication maps to the existing bounded QA session/principal and does not create new Project, Engineering Run, source-lineage, model-routing, Git/deployment, or REVIEW authority.

### AC-06 Dedicated QA repository routine replay is bounded
The standing `parallax-qa` workflow contains routine Python and OT Time source-only acceptance only; it does not include standing W9-S1 greenfield initialization authority.

### AC-07 Production cutover is behaviorally proven before contraction
After deployment, the exact `parallax-qa` workflow authenticates against production and both routine jobs reach `REVIEW` with no failure and validate authenticated source-only ZIP handoff before old workflow trust is removed.

### AC-08 No wildcard trust
The verifier uses no repository prefix, workflow prefix, glob, substring, actor-only, branch-only, or event-only acceptance rule.

### AC-09 Architecture records the durable trust topology
`ARCHITECTURE.md` records exact repository/workflow-pair authorization and the dedicated QA repository boundary as v3.29.

### AC-10 Release gates remain green
Exact-head API/contracts, client/browser/Skia, Bounded Autonomy, protected promotion, Workstream Spec Validation, and DSPy release compilation pass before merge.

## 7. Release gate

Before merge:

- focused identity tests prove AC-01 through AC-05 and AC-08;
- the dedicated QA repository harness passes its own shell/static validation;
- protected Workstream Spec Validation, Bounded Autonomy, full P2 CI, promotion, and DSPy release gates pass on the exact candidate head.

After merge:

- verify the exact API source deployment is READY;
- verify production `/health` and `/ready`;
- inspect production runtime errors;
- run or observe the exact `Ryan9876/parallax-qa/.github/workflows/production-replay.yml@refs/heads/main` workflow against the deployed API;
- require both routine jobs to pass through REVIEW and ZIP handoff;
- only then begin the separate old-trust contraction release and update `CURRENT-STATE.md` with verified evidence.

## 8. Rollback

Revert the API release commit to restore the prior exact application-repository-only QA trust set. No database migration, persisted schema, QA-user migration, source-lineage migration, or application-data rewrite is introduced.
