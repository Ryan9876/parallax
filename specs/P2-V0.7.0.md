# Parallax 2.0 v0.7.0 — Code Run Activation Specification

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.7.0
Depends on: P2-V0.6.3, P2-V0.4.0
Method: Spec-first implementation + protected Code validation

## 1. Objective

Make Code mode operational from the normal Parallax conversation surface by automatically establishing the durable engineering run that Code 2.0 already defines.

Today the protected Code kernel exists, but a normal Code conversation does not create or activate a run. The status surface therefore appears only for runs created through lower-level API usage. v0.7.0 closes that product gap without pretending that planning, implementation, build, test, verification, review, merge, or deployment occurred.

## 2. User outcome

When an authorized user opens a Code conversation, Parallax creates or resumes the single durable engineering run bound to that conversation and its approved specification. A newly activated run advances through the protected SPECIFY binding gate and visibly lands at PLAN, making the next engineering stage truthful and inspectable.

The user can refresh or reopen the conversation and see the same run, attempts, revision, and state rather than creating duplicates.

## 3. Fixed decisions

- Code conversation activation is server-owned; the client does not manufacture passing evidence.
- Activation may create a run only for a durable Code conversation whose `spec_id` matches the requested run specification.
- Activation automatically completes only the SPECIFY binding stage. It may not auto-pass PLAN, IMPLEMENT, BUILD, TEST, VERIFY, or REVIEW.
- SPECIFY activation evidence is derived from durable conversation/spec binding and is recorded as append-only evidence.
- Repeating activation is idempotent at the product level: an existing run is reused and a passed SPECIFY attempt is not duplicated.
- Existing paused, failed, complete, cancelled, or amendment states are returned truthfully; activation does not reset or rewrite them.
- An existing run's workspace binding is immutable through activation. A conflicting workspace request is rejected rather than silently mutating the run.
- The low-level explicit run-creation and protected stage APIs remain available for automation and tests.
- Reason mode never creates an engineering run.
- The existing private-session, SSE, evaluation, visual, and deployment boundaries remain unchanged.

## 4. Scope

### 4.1 Server activation service

Add a protected `ensure_run` service operation that:

1. validates the durable conversation exists;
2. requires Code mode;
3. rejects conversations in `SPEC_AMENDMENT`;
4. requires exact durable spec binding;
5. reuses the latest run for the conversation when present;
6. creates a run when none exists;
7. if the resulting run is still at SPECIFY, records one protected passing SPECIFY attempt and advances the run to PLAN;
8. returns the durable aggregate with ordered attempt evidence.

### 4.2 Repository boundary

Move latest-run lookup into `EngineeringRunRepository` so route code does not own persistence queries. The repository returns the aggregate with attempts refreshed from durable storage.

### 4.3 API contract

Add:

`POST /v1/engineering-runs/ensure`

Input:

- `conversation_id`;
- `spec_id`;
- optional `workspace_ref`.

Output is the normal `EngineeringRunRead` aggregate.

The endpoint is protected by the same server-owned authentication boundary as all other engineering-run routes.

### 4.4 Client activation

When Code mode has a durable conversation, the Code run hook:

- reads the latest run;
- if no run exists, reads the durable conversation specification and calls the protected ensure endpoint;
- stores the returned run as the visible Code state;
- does not activate in Reason mode;
- preserves pause/resume/cancel behavior.

This allows mode switch, refresh, and reopened Code conversations to converge on one durable run without an extra dashboard or setup flow.

### 4.5 Status presentation

The existing Code run status surface remains conversation-first but should make the current protected stage understandable. It may clarify stage count/current stage and the meaning of PLAN readiness, but must not claim work beyond the evidence stored on the run.

Reduced-graphics mode must expose the same durable Code run/status semantics.

### 4.6 Specification governance

Add a release test that discovers every `specs/P2-V*.md` file and runs protected spec-only validation. This prevents later releases from existing in the repository without being exercised by CI simply because a workflow list was not manually extended.

## 5. Security and truthfulness

- No arbitrary command execution is introduced.
- No new provider or Git credentials are introduced.
- The client cannot submit a fabricated SPECIFY pass through the activation endpoint.
- No stage beyond SPECIFY is advanced automatically.
- No deployment, merge, build, test, or implementation status is inferred from model prose.
- Existing authorization applies to activation.
- Existing evidence-size and append-only controls remain intact.

## 6. Acceptance criteria

### AC-01 Code activation

A durable Code conversation with no engineering run can be activated through the protected ensure endpoint and returns one run at PLAN with exactly one passed SPECIFY attempt.

### AC-02 Idempotent reuse

Repeated activation of the same Code conversation returns the same run ID and does not append duplicate SPECIFY evidence.

### AC-03 Spec and mode protection

Reason conversations, mismatched specification IDs, and conversations requiring a specification amendment are rejected.

### AC-04 Workspace immutability

Activation cannot silently change the workspace reference of an existing run.

### AC-05 Client convergence

Opening or switching into a durable Code conversation causes the client to load or activate its run and show the durable current state. Reason mode does not create runs.

### AC-06 Truthful stage boundary

Activation advances only SPECIFY → PLAN. PLAN and every later stage still require their existing protected evidence contracts.

### AC-07 Durable recovery

Refresh/reopen restores the same run and attempt evidence from the database.

### AC-08 Reduced-graphics parity

Reduced-graphics mode can show and control the same Code run state without Skia.

### AC-09 Spec validation coverage

CI/API tests automatically discover and protected-validate all versioned Parallax specifications, including this release.

### AC-10 Regression protection

Existing API/auth/session, Reason, Code state-machine, client typecheck/state/export, browser/Skia acceptance, protected evaluation, and DSPy release checks pass before production promotion.

## 7. Non-goals

- Live shell execution.
- Automatic PLAN generation or approval.
- Autonomous repair loops.
- Git commit/push/merge.
- Deployment actions.
- New workspace credentials or repository-provider setup.
- Multi-user collaboration or RBAC.
- Replacing the conversation-first UI with an IDE/dashboard.

## 8. Risks and mitigations

- **Duplicate activation requests:** reuse the latest durable run; activation only mutates SPECIFY once.
- **False sense of progress:** stop at PLAN and use explicit protected-stage language.
- **Opening old Code conversations creates state:** activation is limited to a non-executing run plus spec binding; no external side effects or tools execute.
- **Workspace drift:** reject conflicting workspace refs on an existing run.
- **Spec-governance drift:** discover specs dynamically in tests rather than relying only on a hand-maintained workflow list.

## 9. Release gate

Production promotion requires the existing full release validation plus direct tests for activation idempotency, binding protection, and persistence. `ARCHITECTURE.md` must record Code activation as a durable orchestration boundary and `CURRENT-STATE.md` must be updated only after validated deployment evidence exists.
