# Parallax 2.0 v0.7.0 — Durable Work Specifications

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.7.0
Depends on: P2-V0.6.3
Method: Spec-first + protected AI drafting + durable human approval

## 1. Objective

Add the first user-work specification layer to Parallax. A conversation must be able to produce a durable, structured specification for the user's actual objective without confusing that work specification with Parallax's own product/release specification identity.

The release introduces AI-assisted specification drafting, durable revisions, explicit human approval, and a concise conversation-native specification surface. It does not yet bind Code execution runs to the new work specification; that is the next execution phase after this durable contract exists.

## 2. User outcome

After discussing an objective, the operator can ask Parallax to capture the conversation as a structured specification. Parallax drafts a title, objective, constraints, acceptance criteria, risks, and open questions. The draft survives refreshes, can be regenerated as the conversation evolves, and can be explicitly approved by the operator.

The specification remains visible as a compact part of the conversation rather than turning Parallax into a dashboard or form-heavy requirements tool.

## 3. Fixed decisions

- `Conversation.spec_id` remains Parallax's durable product/policy specification identity. It is not repurposed as the user's work specification.
- User work specifications are separate durable entities linked to one conversation.
- Work specifications are revisioned. Regenerating a draft creates a new revision rather than silently rewriting an approved artifact.
- Draft generation is model-assisted but schema-constrained and protected by server validation.
- Human approval is explicit. A model may draft but may not approve its own specification.
- At most one work specification revision is `APPROVED` for a conversation at a time. Approving a newer revision supersedes the older approved revision.
- A newer draft does not automatically invalidate the currently approved revision until the operator approves the newer draft.
- The conversation remains the primary interface. The specification appears as a compact expandable status surface.
- Reduced-graphics mode retains the same specification capability using normal React Native controls/text.
- Protected routes, session security, Reason/Code behavior, SSE transport, and existing engineering-run semantics remain intact.
- This release does not bind Code runs to work-spec IDs and does not enable a live executor.

## 4. Durable work-specification contract

A work specification records at minimum:

- opaque specification ID;
- conversation ID;
- integer revision;
- status: `DRAFT`, `APPROVED`, or `SUPERSEDED`;
- concise title;
- objective;
- bounded constraints list;
- bounded acceptance-criteria list;
- bounded risks list;
- bounded open-questions list;
- draft confidence;
- drafting program/model identity where available;
- created/updated timestamps;
- optional approved timestamp.

All list fields are stored durably as bounded JSON text and returned as typed arrays through the API. Conversation deletion continues to cascade to dependent work specifications.

## 5. Drafting behavior

The drafting coordinator receives bounded observable conversation context only. It uses the existing Luna → Terra → Sol model order and a typed DSPy-compatible work-specification program.

The program produces:

- `title`;
- `objective`;
- `constraints`;
- `acceptance_criteria`;
- `risks`;
- `open_questions`;
- `confidence`;
- `program_version`.

Protected validation requires a meaningful objective, at least two concrete acceptance criteria, bounded/unique list items, finite confidence, and no empty structural fields. Provider/model failures are sanitized and never expose hidden reasoning, provider credentials, or raw candidate output.

If drafting fails across all configured models, the existing conversation remains unchanged and no fake specification revision is persisted.

## 6. Revision and approval behavior

- Drafting requires at least one durable user message.
- A new draft receives the next revision number for that conversation.
- Any older unapproved `DRAFT` revision becomes `SUPERSEDED` when a newer draft is stored.
- Existing `APPROVED` revision remains approved while a newer draft is being considered.
- Approval is a protected server mutation performed only on a `DRAFT` revision.
- Approving a draft marks any prior `APPROVED` revision `SUPERSEDED` and sets `approved_at` on the selected revision.
- Approval is idempotent for an already approved revision.
- Superseded revisions remain queryable as durable history through repository/service boundaries even though the first client surface shows the latest revision only.

## 7. API contract

Protected endpoints:

- `GET /v1/conversations/{conversation_id}/work-specifications/latest`
- `POST /v1/conversations/{conversation_id}/work-specifications/draft`
- `POST /v1/work-specifications/{specification_id}/approve`

The draft endpoint accepts no model-authored approval flag. The server derives the conversation context and writes the next revision only after protected validation succeeds.

## 8. Client experience

The main conversation shell and reduced-graphics shell add one compact specification strip below the top bar.

When no work specification exists:

- no empty dashboard card is shown before the user has described an objective;
- once at least one user turn exists, a restrained `CAPTURE SPEC` action appears.

When a draft exists:

- the strip shows `SPEC · DRAFT`, revision, and title;
- the operator can expand it to inspect objective, acceptance criteria, constraints, risks, and open questions;
- the operator can `APPROVE` or `REFRESH DRAFT`;
- drafting/approval busy states are explicit and controls are disabled appropriately.

When approved:

- status changes to `SPEC · APPROVED`;
- approved state uses the verified/success semantic color rather than purple alone;
- `REFRESH DRAFT` remains available to create a newer candidate without destroying the approved revision.

## 9. Database migration and security

Add an ordered production migration for `work_specifications` with:

- primary key;
- conversation foreign key with `ON DELETE CASCADE`;
- unique `(conversation_id, revision)` constraint;
- indexes for conversation, status, and update ordering;
- row-level security enabled;
- `anon` and `authenticated` privileges revoked, matching the existing private server-owned data model.

Production startup continues to perform no implicit DDL.

## 10. Acceptance criteria

### AC-01 Product/work spec separation

Existing `Conversation.spec_id` semantics remain unchanged while user work specifications have independent opaque IDs and revisions.

### AC-02 Durable AI draft

A conversation with at least one user turn can produce and persist a typed structured work-specification draft through the protected model router.

### AC-03 No fabricated success

If all drafting candidates fail provider or protected validation, no draft row is persisted and the API returns sanitized recoverable failure.

### AC-04 Revision integrity

Regenerating creates a new revision and supersedes only older draft revisions. Existing approved work remains approved until a newer draft is explicitly approved.

### AC-05 Human approval

Only explicit operator API/client action can move a draft to `APPROVED`; approving a newer revision supersedes the older approved revision.

### AC-06 Persistence

Work specification state survives separate service/session instances and conversation deletion cascades to dependent rows.

### AC-07 Conversation-native UI

The main and reduced-graphics clients can capture, inspect, refresh, and approve work specifications without replacing the conversation-first layout.

### AC-08 Accessibility

Specification content uses normal selectable/accessibility-aware text, controls retain accessible roles/labels, and no state is communicated by color alone.

### AC-09 Protected route security

All work-specification routes inherit the existing private authentication boundary. Unauthenticated access returns the existing sanitized `401` contract.

### AC-10 Migration safety

The additive production migration is applied before the release is promoted. `/ready` remains healthy after migration and production startup performs no schema mutation.

### AC-11 Release validation

Specification validation, API compile/tests, client typecheck/state/export, browser/Skia acceptance, protected Engineering/Reason/Code promotion evaluation, DSPy release compilation, Vercel preview status, and production verification pass before v0.7.0 is recorded as deployment-verified.

## 11. Non-goals

- Binding engineering runs to work-specification IDs.
- Autonomous implementation from an approved work specification.
- Live shell/command execution.
- Multi-user collaboration, comments, permissions, or sharing.
- Rich document editing, markdown editors, or separate requirements dashboards.
- Model self-approval of specifications.
- Replacing Parallax's product/release `spec_id` contract.

## 12. Risks and mitigations

- **Product/release spec confusion:** keep work specs in a separate model/API and name the distinction explicitly in architecture.
- **Low-quality AI draft:** require typed output, protected structural validation, model escalation, visible confidence/open questions, and human approval.
- **Approved work overwritten by regeneration:** use immutable revisions and do not supersede approved work until explicit approval of the newer draft.
- **Database rollout mismatch:** use an additive ordered migration and apply it before promotion.
- **Conversation UI becoming a dashboard:** use one compact expandable strip rather than a permanent side panel.
- **Sensitive model output persistence:** persist only bounded structured observable fields and never hidden reasoning/provider diagnostics.

## 13. Release gate

Implementation is authorized by this specification. The release may be promoted only after the additive database migration is applied and the existing full release-validation path passes. Deployment records must continue distinguishing generated, validated, deployed, and deployment-verified states.
