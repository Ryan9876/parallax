## 1. Objective

Remove the next authenticated production IMPLEMENT failure by simplifying the source-authoring topology rather than adding another cross-work-unit repair layer.

On exact production deployment `dpl_4DjbFpezU1NGJNsiCKXNRqbA7DA2`, the user-authenticated retry of Engineering Run `3a1ba66a-5649-42b6-81ee-91684fe06bbc` resumed successfully. The first autonomous transition completed normally. The IMPLEMENT request then completed real hosted Luna and Terra generations, with Luna completing at approximately 20:04:31 UTC and Terra at approximately 20:04:50 UTC. No Sol generation, no final validator-repair dispatch, and no Vercel disposable candidate sandbox followed Terra before the run became failed again. The production API remained HTTP-healthy and source-lineage reads succeeded.

That flow proves the failure is no longer a provider call, model timeout, raw model diff syntax, or ordinary incremental safe-preflight exhaustion. The runtime left the bounded generation path after successful hosted generation and failed before protected candidate BUILD/TEST/VERIFY. P2-V0.23.27 and P2-V0.23.28 added increasingly complex work-unit and plan-prefix convergence to compensate for a deeper design choice: `_work_graph()` heuristically decomposes one canonical source implementation into multiple independently authored work units based only on acceptance-text keyword domains.

That decomposition is not required to satisfy Parallax's product goal. Multiple acceptance criteria may describe client, server, and data behavior while still requiring one coherent source change across shared files and invariants. Having separate agents independently author those acceptance slices against the same unchanged source context creates assembly, overlap, provenance, and repair boundaries that do not improve source authority or correctness. BUILD/TEST/VERIFY and independent evaluation already provide protected downstream validation.

P2-V0.23.29 contracts the production IMPLEMENT authoring topology to one coherent implementation work unit spanning the complete approved acceptance contract. Multiple hosted models remain available as bounded candidate recovery (Luna -> Terra -> Sol) and the existing single final validator repair. Candidate BUILD/TEST/VERIFY, independent evaluation, SafeImplementationEngine, source lineage, durable worker recovery, delivery, lifecycle, Git/deployment, and human REVIEW remain authoritative and unchanged.

## 2. Fixed decisions

- The production source-authoring work graph contains exactly one implementation work unit for one approved Work Specification execution.
- The coherent work unit owns the exact ordered approved acceptance ID set.
- Acceptance-text keyword classification must not split canonical source authoring into client/server/data work units.
- The admitted model roster remains Luna, Terra, Sol in the same server-owned priority order.
- The smallest-capable-team planner therefore selects one initial implementation agent; remaining eligible hosted agents remain available only through the existing bounded candidate-recovery path.
- At most the existing one final validator repair remains available after distinct eligible agents are exhausted.
- P2-V0.23.27 per-generation incremental patch retention remains available within the coherent work unit.
- P2-V0.23.28 plan-prefix convergence remains a compatibility/defense-in-depth path but is not exercised by ordinary production source authoring because there is no multi-unit source proposal to assemble.
- No retry budget, timeout, provider roster, source authority, mutation authority, deployment authority, lifecycle authority, or REVIEW authority is widened.
- Architecture advances to v3.40 because the durable production orchestration policy changes from heuristic multi-work-unit source co-authoring to coherent single-unit source authoring with multi-model recovery.

## 4. Non-goals

- Removing generic WorkGraph/TeamPlan abstractions; they remain available for future tasks where truly independent work units are justified by an explicit specification rather than keyword inference.
- Removing Luna/Terra/Sol recovery.
- Increasing distinct-agent reassignment count, final validator-repair count, 60-second hosted timeout, hidden provider retries, request-level autonomy budget, or candidate competition budget.
- Weakening traversal, secret, symlink, extension, size, stale-base, hierarchy, collision, canonicalization, or source-lineage rules.
- Allowing direct model filesystem, shell, Git, deployment, lifecycle, or REVIEW authority.
- Skipping disposable candidate BUILD/TEST/VERIFY or independent evaluation.
- Persisting raw source, generated content, diffs, provider payloads, credentials, environment values, or exception text in repair diagnostics.

## 5. Architecture requirements

### 5.1 Coherent production implementation unit

`AgenticControlPlane._work_graph()` must return one `WorkUnit` for ordinary implementation generation regardless of whether acceptance text contains client, server, data, browser, endpoint, schema, persistence, or other keyword domains. The unit must:

- have stable server-owned identity `implementation`;
- own exactly `tuple(item["id"] for item in acceptance)` in approved order;
- retain `work_kind="implementation"`;
- retain the existing `bounded-source-evidence` capability requirement;
- retain one source evidence reference bound to the accepted source digest;
- remain non-authoritative for canonical mutation.

### 5.2 Model diversity becomes recovery, not co-authoring

The existing roster and `UnitPlan` must still expose all eligible admitted implementation agents. `build_team_plan()` may select the smallest capable initial team, which for one coherent unit is one agent. If that candidate fails model routing or safe incremental preflight, `candidate_recovery_assignment()` may continue through the remaining eligible agents using the existing bounded reassignment rules. This preserves model diversity without requiring multiple agents to co-author one canonical proposal.

### 5.3 Existing convergence remains defense in depth

The current `IncrementalProposalAccumulator`, sanitized safe-preflight reason seam, retained-target rules, hierarchy checks, plan-prefix logic, and one final validator repair remain unchanged. With one production work unit, `prefix_patches` is normally empty, but the code must remain correct for injected/tests/future explicitly specified graphs.

### 5.4 Candidate validation and authority remain unchanged

A coherent proposal still must pass:

1. exact acceptance validation;
2. whole-proposal `ProposalSafetyPreflight`;
3. disposable safe application to a copied workspace;
4. protected BUILD/TEST/VERIFY in the Vercel sandbox;
5. independent evaluation and routing/competition admission;
6. final commit-time `SafeImplementationEngine.apply()` against the authoritative workspace;
7. immutable source-lineage acceptance;
8. durable lifecycle transition;
9. existing Git/deployment/human REVIEW boundaries.

Single-unit authoring is not permission to bypass any downstream check.

### 5.5 Observability

Durable PLAN evidence must truthfully show one production implementation work unit and one initially selected implementation agent under the standard roster. Candidate recovery evidence continues to record bounded generations and fixed sanitized reason codes. No raw generated/source content is added to telemetry.

## 6. Security

The contraction reduces coordination surface. It does not grant additional model or source authority. All models still receive only bounded protected source context and return typed semantic file-content intent. Server-owned canonicalization and SafeImplementationEngine remain the only source mutation boundary. One work unit cannot transition the Engineering Run, accept source lineage, deploy, mutate Git, or complete REVIEW.

Keeping the generic multi-work-unit orchestration types while disabling keyword-driven source co-authoring avoids a destructive rewrite and preserves future extensibility. Re-enabling multi-unit source authoring later would require an explicit governed specification and evidence that the work units are independently composable; acceptance keyword coincidence alone is insufficient.

## 7. Reliability

The change removes an entire failure class: independently generated acceptance slices no longer need to be assembled into one source proposal before candidate validation. One model generation sees the complete acceptance contract and can make coordinated edits across shared files. If it fails, the next admitted model regenerates the same coherent objective under the existing finite recovery budget.

The maximum hosted-call budget does not increase. Successful first-candidate paths may use fewer models because production no longer selects multiple agents merely to satisfy heuristic parallelism. Failures remain bounded and fail closed.
