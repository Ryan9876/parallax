# Parallax 2.0 — P2-V0.13.4

Status: Approved implementation specification
Date: 2026-08-22

## Objective

Provide a safe, explicit recovery path for conversations already left in `SPEC_AMENDMENT` with a current approved Work Specification, while also allowing an operator to deliberately abandon a pending amendment and resume the current approved scope when no replacement draft exists.

## Problem

v0.13.3 corrects future amendment approvals, but conversations that became inconsistent before that fix can still have `conversation.status == SPEC_AMENDMENT` while their latest Work Specification is already `APPROVED`. Automatically clearing that state is unsafe because the same persisted shape can also represent an operator who triggered an amendment but has not yet drafted a replacement. The ambiguity must therefore be resolved by explicit operator intent rather than timestamp inference or silent migration.

## Requirements

1. Add an explicit `Resume approved scope` action that is available only when the conversation is in `SPEC_AMENDMENT` and its latest Work Specification is `APPROVED`.
2. The server remains authoritative and must reject the action unless:
   - the conversation exists and is currently `SPEC_AMENDMENT`;
   - the latest Work Specification exists and is `APPROVED`;
   - no newer/current `DRAFT` is present (equivalent to requiring the latest specification itself to be approved).
3. A successful action transitions only the conversation status from `SPEC_AMENDMENT` to `ACTIVE`; it does not create, approve, supersede, or mutate any Work Specification.
4. The action is explicit human authority. It may be used either to recover a legacy stuck conversation or to intentionally return to the already-approved scope after deciding not to proceed with an amendment.
5. A current replacement `DRAFT` must continue to require explicit approval through the normal v0.13.3 path; the resume action must not bypass it.
6. Expose the action in both normal and reduced-graphics clients without creating mobile control overlap.
7. After a successful resume, refresh the authoritative conversation and clear the client `SPEC_AMENDMENT` presentation state.
8. Preserve existing authentication, Code binding, bounded-autonomy authority, persistence schema, and Work Specification revision semantics.

## Acceptance criteria

- A legacy/pending conversation in `SPEC_AMENDMENT` whose latest specification is `APPROVED` can be returned to `ACTIVE` only through the explicit resume action.
- The approved Work Specification remains unchanged after resume.
- A conversation with a latest `DRAFT` cannot use resume to bypass approval.
- A conversation already `ACTIVE` cannot use the recovery endpoint as an unrelated state mutation.
- The normal v0.13.3 current-draft approval path remains green.
- Client typecheck, state tests, web export, browser/Skia acceptance, API regression, bounded-autonomy checks, and protected promotion gates remain green.
- No database migration is required.

## Risks and mitigations

- **Scope bypass:** an operator could otherwise silently fall through to an older contract. Mitigation: the action is explicit, clearly labeled, and server-validated; any current draft blocks it.
- **Ambiguous legacy history:** timestamps are insufficient to distinguish a pre-v0.13.3 stuck approval from a newly requested amendment. Mitigation: do not infer intent from timestamps; require the operator action.
- **Mobile crowding:** adding another header control can overflow compact layouts. Mitigation: use the existing compact action row with wrapping and a concise action label.

## Non-goals

- Inferring operator intent from approval or conversation timestamps.
- Automatically clearing all `SPEC_AMENDMENT` rows in storage.
- Discarding or deleting Work Specification history.
- Changing scope-detection logic.
- Expanding autonomous implementation, Git, review, or production-deployment authority.
