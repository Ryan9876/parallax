## 1. Objective

Remove two concrete blockers exposed by the first authenticated real-world Parallax build attempt after P2-V0.23.24 proved the final validator repair is genuinely fresh.

Engineering Run `3a1ba66a-5649-42b6-81ee-91684fe06bbc` is trying to build an isolated prototype that naturally belongs under a new nested source directory. Production logs show an implementation proposal rejected by the safe patch boundary as `unsafe_target`. The current `TextPatchEngine._safe_target()` requires every parent directory to pre-exist, which means Parallax can create a new file only inside an already-existing directory. That is too restrictive for ordinary software development where a feature commonly introduces a new module, component, test, prototype or package directory.

The same authenticated retry also exposed a client reliability gap. The server-side `/autonomous` request completed HTTP 200 and persisted canonical progress, while the mobile browser displayed `System message: Load failed`. A transient network failure can therefore obscure server-owned truth and prompt an unnecessary manual retry even when the protected stage already completed.

P2-V0.23.25 adds bounded, side-effect-safe creation of missing parent directories only for valid new text-file patches and adds read-only authoritative reconciliation for ambiguous client transport failures. It does not widen model retries or relax existing source safety.

## 2. Fixed decisions

- Existing source path normalization, workspace containment, secret-sensitive path/content rejection, supported text-file allowlist, file/result/patch size limits, symlink rejection, strict unified-diff validation, patch canonicalization, candidate validation, source lineage, Git/deployment authority, lifecycle authority and human REVIEW ceiling remain authoritative.
- Validation/preparation remains side-effect-free. No directory is created merely because a model proposed a path.
- Only a patch that is valid as a new-file patch and is bound to the SHA-256 of empty content may carry missing parent-directory intent.
- Missing parent directories are represented as bounded relative workspace paths derived from the already-normalized target. Models do not receive directory-creation authority as a separate tool.
- Commit may create only those missing parents, one path segment at a time, after rechecking containment, directory type and symlink safety against the current workspace.
- Rollback removes a newly created file and then removes only the recorded missing parents that are still empty. Shared/non-empty directories are preserved.
- A multi-patch request is rejected before mutation if one target path would need to be a directory ancestor of another target file path.
- Existing-file patches continue to require their parent directories to pre-exist.
- A client HTTP/API response remains authoritative. Only a transport/network exception without an HTTP response is ambiguous.
- After an ambiguous autonomy transport failure, the client may perform a read-only latest-run fetch. It may recover only when the fetched run has the same run ID and a strictly greater authoritative revision than the request started from.
- Proven recovered progress may continue from the new revision under the existing maximum-eight-request continuation budget. A recovered FAILED/REVIEW/PAUSED/CANCELLED/COMPLETE or other non-autonomous boundary stops normally.
- If no revision advance is proven, the original transport error remains visible and no duplicate autonomous POST is issued from uncertain state.
- No new queue, retry loop, model, provider, credential or deployment behavior is introduced.
- Architecture advances to v3.36 because both nested source creation and ambiguity reconciliation are durable execution contracts.

## 4. Non-goals

- Increasing `MAX_VALIDATOR_REPAIR_RETRIES_PER_WORK_UNIT`, hosted-model timeout, hidden transport retries or admitted model count.
- Weakening secret, extension, path traversal, symlink, binary-content or workspace-containment rules.
- Creating arbitrary directories independently of a validated new-file patch.
- Recursive `mkdir -p` against model-provided raw paths without segment-by-segment validation.
- Allowing file deletion, rename, chmod, symlink creation or binary artifact patching.
- Hiding a server-declared HTTP error behind reconciliation.
- Treating an unchanged latest-run revision as proof that an ambiguous POST succeeded.
- Sending a second autonomous POST from the same uncertain revision.
- New Git mutation authority, deployment authority, lifecycle authority or automatic REVIEW completion.
- Fixing every possible reason a model proposal may fail protected validation in this release. This release removes the demonstrated missing-parent capability gap and preserves truthful failure evidence for anything remaining.

## 5. Required behavior

### 5.1 Side-effect-free missing-parent discovery

`TextPatchEngine.prepare()` must normalize and validate the target exactly as today. When the target does not exist and the patch is bound to `EMPTY_SHA256`, it may traverse the normalized relative parent path and record any missing directories without creating them.

Every existing traversed component must be a real directory and not a symlink. If an existing component is a file, symlink or unsafe path, preparation fails with `UnsafeTargetError`.

Validation must leave the workspace byte-for-byte and directory-structure unchanged.

### 5.2 Bounded commit-time parent creation

`PreparedPatch` may carry internal missing-parent intent. Before writing a new file, `commit()` revalidates the target path from the current workspace root and creates only the missing recorded directories in ancestor order.

Each directory creation must:
- remain inside the resolved workspace root;
- reject a symlink or non-directory component;
- create one segment at a time with ordinary source-directory permissions;
- tolerate a recorded parent already existing only when it is a real non-symlink directory, which supports multiple new files sharing the same parent;
- never create anything for an existing-file patch.

If file commit fails after creating directories, commit performs best-effort removal of only directories created by that commit that are still empty before propagating failure.

### 5.3 Rollback semantics

For a successfully committed new nested file, rollback first validates the current target still matches the prepared `after` content, then removes the file. It subsequently walks the recorded missing parents in reverse order and removes only directories that are empty and still safe real directories.

A non-empty shared parent is left intact. Rollback must not remove a directory that pre-existed preparation.

### 5.4 Target hierarchy conflicts

Before any patch mutation, `SafeImplementationEngine` rejects a request where one normalized file target is a strict path prefix of another target, for example `module.py` and `module.py/test.py`. This prevents one requested file from becoming another requested target's parent directory.

Sibling files sharing a normal directory are allowed.

### 5.5 Ambiguous autonomy transport reconciliation

`runEngineeringAutonomy()` continues to throw `EngineeringAutonomyError` for HTTP/API failures. Those errors are authoritative and are not reconciled away.

When a non-`EngineeringAutonomyError` transport exception occurs while requesting autonomy for run revision N, the client performs a read-only `latestEngineeringRun(conversationId)` fetch.

Recovered progress is admissible only when:
- the fetched run is non-null;
- fetched run ID equals the requested run ID; and
- fetched revision is strictly greater than N.

If admissible, the hook replaces local state with the fetched run and clears the ambiguous transport error. If the fetched run remains autonomously continuable, the existing loop continues from its new revision and a new revision-bound operation key. Otherwise it stops on the canonical boundary state.

If the reconciliation fetch fails, returns a different run, returns null or returns revision <= N, the original transport exception is surfaced unchanged and no additional POST is made.

### 5.6 Request budget remains finite

An ambiguous POST that is reconciled through a newer authoritative revision still counts as one completed request in the existing maximum-eight-request continuation loop. Reconciliation does not reset or extend the budget.

## 6. Security and reliability

Directory creation authority remains derived from a validated text-file target, not from a separate model-controlled filesystem command. The normalized path, supported target allowlist, secret checks and workspace containment remain the gate before missing-parent intent can exist.

Preparation remains non-mutating so rejected proposals cannot leave directories behind. Commit-time revalidation protects against a parent path changing type between validation and mutation. Rollback removes only directories known to have been absent during preparation and only while they are empty, preventing destructive cleanup of shared or pre-existing content.

Client reconciliation is read-only and revision-based. It never infers success from a timeout alone. A newer canonical revision is the only evidence that permits progress recovery, and any subsequent autonomous request is bound to that newer revision under existing idempotency controls.

The release therefore improves reliability without weakening fail-closed source validation or making network ambiguity a source of lifecycle authority.

## 7. Acceptance criteria

### AC-01 Nested new-file validation is side-effect-free
A valid patch for `prototypes/fml-data-readiness/index.html` in a workspace where `prototypes/` does not exist passes preparation/validation while creating no directory or file.

### AC-02 Commit creates only required parents
Applying the same valid new-file patch creates the required nested directories and file with exact expected content; no unrelated path is created.

### AC-03 Shared parents are safe
Two new-file patches under the same previously absent directory apply successfully without duplicate-directory failure.

### AC-04 Rollback is bounded
If a later patch in a multi-patch operation fails, previously committed nested new files are restored and newly created empty parent directories are removed; pre-existing or non-empty shared directories remain.

### AC-05 Existing safety remains fail-closed
Symlink parents, non-directory parents, workspace escape, secret-sensitive targets/content, unsupported file suffixes and existing-file missing-parent cases remain rejected.

### AC-06 Target hierarchy conflicts fail before mutation
A multi-patch request with target ancestry conflict is rejected before workspace mutation; ordinary sibling targets remain accepted.

### AC-07 Authoritative transport reconciliation is revision-bound
A transport exception followed by same-run revision N+1 is accepted as recovered server progress. Same revision, older revision, null run or different run is not accepted.

### AC-08 HTTP failures remain authoritative
`EngineeringAutonomyError` is surfaced directly and does not invoke ambiguity recovery.

### AC-09 Recovered continuation remains bounded
When recovered revision N+1 is autonomously continuable, continuation uses the new revision and existing request budget; the uncertain revision is never POSTed again.

### AC-10 Regression gates pass
Focused API/client tests, full API regression, client typecheck/state/export, Bounded Autonomy, protected promotion evaluation, Workstream Spec Validation and required DSPy validation pass on the exact PR head.

### AC-11 Exact production deployment is healthy
After merge, exact application source reaches READY production deployment. `/health` and `/ready` return HTTP 200 with database/providers ready, and production preflights remain green.

### AC-12 Real build progresses truthfully
Authenticated retry of Engineering Run `3a1ba66a-5649-42b6-81ee-91684fe06bbc` or an equivalent real nested-file build no longer fails merely because a valid new source file needs a previously absent parent directory. A mobile transport interruption with server-side revision advance reconciles to canonical state rather than showing only `Load failed`. Any later protected failure is diagnosed from its actual normalized reason rather than masked by these two limitations.
