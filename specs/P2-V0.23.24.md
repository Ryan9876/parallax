## 1. Objective

Make the one final validator-repair opportunity introduced by P2-V0.23.23 a genuinely fresh model-generation request rather than a possible replay of an earlier validator-rejected cached prediction.

Authenticated production retry of Engineering Run `3a1ba66a-5649-42b6-81ee-91684fe06bbc` on exact P2-V0.23.23 source `256254a0922e7bea113a5902c353c4038bd0cf99` exposed a deterministic request-identity defect. The IMPLEMENT request attempted Luna, Terra and Sol under the existing admitted-agent order. Luna returned a proposal rejected by protected validation after about 66.4 seconds; Terra returned a proposal rejected by protected validation after about 35.8 seconds; Sol reached the 60-second hosted-model timeout. The final repair correctly selected the most recent validator-rejected admitted agent, Terra, but the repair request contained the same Work Specification, source context and static `VALIDATOR_REPAIR_GUIDANCE` that Terra had already received on its earlier distinct-agent retry. Runtime logs show no second LiteLLM completion for that final Terra repair and `validation_failed` returned in about 7 ms while DSPy had already fallen back to its in-process memory cache. The user-visible run then recorded `AGENTIC_CANDIDATE_EXHAUSTED` and `AUTONOMOUS_IMPLEMENT_FAILED` again.

The defect is not an insufficient retry budget. P2-V0.23.23 intended one additional generation, but the final repair was not guaranteed to have a distinct generation input identity. The correction is to make that one final repair semantically and cache-distinct while preserving all existing authority and retry ceilings.

## 2. Fixed decisions

- The P2-V0.23.23 final-repair budget remains exactly one per work unit.
- Distinct-agent ordering, admitted roster, worker-loss recovery, and the deterministic most-recent validator-rejected repair-agent selection remain unchanged.
- Ordinary validator-guided distinct-agent retries continue to receive the existing static `VALIDATOR_REPAIR_GUIDANCE` unchanged.
- A final repair assignment identified by server-owned reason code `CANDIDATE_VALIDATION_REPAIR` receives an additional final-repair-only constraint that explicitly requires a fresh re-derivation from protected source context rather than reuse of a prior proposal.
- The final-repair-only constraint includes a bounded deterministic context token derived solely from server-owned run revision, work-unit identity and assignment generation. The token exists to make request identity cache-distinct and observable; it grants no authority and contains no source text, rejected output, provider payload, credential, environment value or filesystem path.
- The same server-owned context yields the same token; a later human retry/run revision yields a different token. No random nonce, hidden loop or mutable global state is introduced.
- The final repair still passes through the exact same typed proposal schema, exact acceptance coverage, `SafeImplementationEngine`, `CanonicalizingTextPatchEngine`, disposable candidate BUILD/TEST/VERIFY, independent evaluation, canonical source writer, delivery authority, durable lifecycle authority and human REVIEW ceiling.
- Do not disable DSPy caching globally. Caching remains useful for ordinary deterministic work; only the final repair must have distinct request identity from its prior rejected attempt.
- Do not increase the 60-second hosted-model timeout, hidden transport retries, admitted model count, candidate-repair count, or provider authority.
- Architecture advances to v3.35 because the durable contract now requires a final validator repair to be a fresh generation identity, not merely an additional orchestration assignment.

## 4. Non-goals

- Adding a second final repair attempt or increasing `MAX_VALIDATOR_REPAIR_RETRIES_PER_WORK_UNIT`.
- Retrying provider-only failures with validator authority.
- Disabling DSPy cache globally or changing provider SDK cache policy for unrelated reasoning/spec workflows.
- Persisting rejected model output, source text, arbitrary validator messages, provider payloads, credentials, environment values, private URLs or protected filesystem paths.
- Passing raw prior candidate content back to the model.
- Weakening safe patch validation/canonicalization or accepting a proposal the current protected validator rejects.
- Adding a new model, provider, credential, queue, background worker, source writer, Git authority, deployment authority, lifecycle authority or automatic REVIEW completion.
- Reworking the implementation proposal schema into semantic edit operations in this release. If a genuinely fresh repair still demonstrates systematic diff-authoring failure, that larger interface redesign receives a separate spec using the production evidence from this release.

## 5. Required behavior

### 5.1 Final-repair context identity

When `assignment.reason_code == CANDIDATE_VALIDATION_REPAIR`, construct one bounded final-repair context from server-owned values already in memory:

- current authoritative Engineering Run revision;
- current work-unit ID;
- current repair assignment generation.

Hash a canonical encoding of those values with SHA-256 and expose only a short lowercase hexadecimal token in the model constraint/log boundary. The raw run/work-unit values do not need to be logged.

The token function must be deterministic, bounded and domain-separated from unrelated digests. Invalid revision/generation values fail closed.

### 5.2 Cache-distinct final repair request

The final repair request must contain both:

1. existing `VALIDATOR_REPAIR_GUIDANCE`; and
2. a final-repair-only constraint containing the context token and instruction to re-derive a fresh proposal from the supplied protected source context rather than reuse a prior response.

The final-repair-only constraint must not be present on ordinary initial or distinct-agent requests.

For a given base request, the final repair contract payload must differ from the earlier validator-guided distinct-agent payload. A changed authoritative retry context must also produce a different final-repair contract payload.

### 5.3 No raw rejected-output feedback

The model receives no prior proposal text, diff, exception message or provider response. The fresh request is driven only by the approved Work Specification, protected source context, existing static repair rule and bounded server-owned final-repair context.

### 5.4 Finite recovery remains unchanged

The final repair budget remains one per work unit. A provider timeout/failure or another protected validation rejection during that fresh repair consumes the repair budget and the existing candidate-exhaustion path remains authoritative. No recursive repair is allowed.

### 5.5 Bounded operational evidence

Emit one structured application log when a final repair request is dispatched. The log may include only:

- fixed event name;
- bounded repair generation integer;
- bounded final-repair context token.

Do not log model output, source text, Work Specification text, agent/provider payloads, credentials, URLs, arbitrary exception text, raw run IDs, raw work-unit IDs or filesystem paths. This log is observability only and grants no authority.

## 6. Security and reliability

The final-repair context is generated entirely from existing server-owned state and is used only to distinguish the one already-authorized repair request. It cannot authorize a retry by itself; eligibility remains controlled by the existing admitted-plan identity, `VALIDATION_EXHAUSTED` evidence, most-recent validator-rejected agent selection and one-repair counter.

The context token is a one-way bounded digest prefix and is not a credential or source identifier. A model cannot choose it, and a user/model-provided lookalike cannot create repair authority because assignment reason and repair count remain server-owned.

Changing the prompt/request identity does not relax proposal validation. Any fresh candidate still has zero canonical mutation authority until it passes the unchanged protected implementation, candidate validation and evaluation pipeline.

The correction also avoids a misleading reliability pattern: an orchestration layer must not count a cached replay of an already-rejected proposal as a new bounded repair generation. Production acceptance therefore requires evidence of a real hosted completion for the final repair path, not merely another `CANDIDATE_VALIDATION_REPAIR` assignment.

## 7. Acceptance criteria

### AC-01 Production root cause is represented accurately
Focused regression encodes that a distinct-agent validator-guided request and a final repair can target the same admitted model while requiring different request identities.

### AC-02 Final repair request is cache-distinct
For the same Work Specification/source context, the final repair request differs from the prior ordinary validator-guided request because the final-repair-only constraint is present.

### AC-03 Retry context changes request identity
Different authoritative run revision or repair generation inputs produce different bounded final-repair context tokens and contract payloads; identical inputs are deterministic.

### AC-04 Ordinary retry behavior is unchanged
Initial and distinct-agent validator-guided requests do not receive the final-repair-only constraint. Existing `VALIDATOR_REPAIR_GUIDANCE` behavior remains unchanged.

### AC-05 One-repair ceiling is unchanged
Exactly one final repair remains possible per work unit. Provider failure or validation failure on that repair cannot create another repair assignment.

### AC-06 Authority remains unchanged
The token/constraint grants no source, lineage, Git, deployment, lifecycle, credential, network or REVIEW authority. Protected proposal/candidate validation remains authoritative.

### AC-07 Operational evidence is bounded
A final repair dispatch produces only fixed event name, repair generation and bounded context token; sensitive/raw material is absent.

### AC-08 Regression gates pass
Focused recovery tests, full API regression, Bounded Autonomy, client checks, protected promotion evaluation, protected spec/plan validation and required DSPy validation pass on the exact PR head.

### AC-09 Exact deployment is healthy
After merge, the exact application source reaches READY production deployment and `/health` and `/ready` return HTTP 200 with database/providers ready.

### AC-10 Production final repair is genuinely fresh
An authenticated retry of Engineering Run `3a1ba66a-5649-42b6-81ee-91684fe06bbc` or equivalent bounded production workload reaches the final validator-repair path and production logs show the bounded final-repair dispatch followed by an actual hosted model completion/transport attempt rather than the prior ~7 ms cached replay. If protected validation still rejects the fresh proposal, that result is accepted as truthful evidence for the next diagnosis; this release must not widen the retry budget to force success.
