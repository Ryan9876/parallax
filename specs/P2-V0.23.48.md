## 1. Objective

Make Behavioral Verification Plan drafting reliably fail closed at the **criterion** boundary instead of unnecessarily failing the entire plan when a model proposes an invalid executable browser workflow.

P2-V0.23.47 correctly established that every acceptance criterion must be represented exactly once as either `BROWSER` or `HUMAN_ONLY`, and that `HUMAN_ONLY` is a valid non-evidence state. Authenticated production acceptance exposed that the generator currently validates executable browser details too early: one malformed `BROWSER` criterion invalidates the full model proposal, causing route escalation and eventual 503 even though the safe server-owned outcome for that criterion is already defined as `HUMAN_ONLY`.

P2-V0.23.48 introduces conservative generated-proposal normalization. It does not weaken the browser contract. It changes only how invalid model-authored executable proposals are reduced before persistence.

## 3. Authority invariants

The following remain unchanged and authoritative:

1. exact approved Work Specification ID, revision and digest bind the plan;
2. exact server-derived acceptance IDs and order are authoritative;
3. every acceptance ID appears exactly once;
4. unknown, missing, duplicated, invented or reordered acceptance IDs fail the whole generated proposal;
5. only `BROWSER` and `HUMAN_ONLY` modes are recognized;
6. `BROWSER` gains no authority unless the existing strict typed browser constructors validate and compile it;
7. `HUMAN_ONLY` carries no executable workflow and no verified-evidence meaning;
8. generation receives no candidate source, repository file content, Preview/DOM content, provider evidence, credentials, runtime logs or hidden reasoning;
9. no browser execution, TEST/VERIFY evidence mutation, source/provider mutation, lifecycle transition, REVIEW completion, merge or production authority is introduced.

## 4. Conservative normalization contract

### 4.1 Top-level structure

Generated output must remain strict JSON with exactly one `criteria` array.

Each criterion may contain only:

- `acceptance_id`;
- `mode`;
- `viewport_ids`;
- `actions`.

Unknown top-level or criterion keys remain validation failures.

### 4.2 Acceptance identity

Before criterion normalization, the server validates the model-supplied acceptance IDs as an exact ordered match to the server-derived acceptance map.

Acceptance identity is never repaired, reordered, inferred or synthesized from model output.

### 4.3 HUMAN_ONLY normalization

If the model explicitly proposes `HUMAN_ONLY` for a valid exact acceptance ID, the server normalizes that criterion to:

- the exact acceptance ID;
- mode `HUMAN_ONLY`;
- empty `viewport_ids`;
- empty `actions`.

Any model-supplied executable fields for that HUMAN_ONLY criterion are discarded and cannot gain browser authority.

### 4.4 BROWSER normalization

If the model explicitly proposes `BROWSER`, the server attempts the existing strict `BehavioralCriterionProposal` validation and existing protected `BrowserWorkflow` compilation.

If strict validation succeeds, the BROWSER criterion is preserved unchanged.

If strict validation fails for action shape, viewport registration, path bounds, semantic target requirements, fixture-value requirements, screenshot requirements, assertion requirements or any other existing protected browser invariant, the server replaces **only that criterion** with the exact same acceptance ID in `HUMAN_ONLY` mode and no executable fields.

The server does not repair actions, guess selectors, invent targets, alter paths, substitute fixture values or relax any browser invariant.

### 4.5 Invalid mode or malformed criterion

Unknown mode values, non-object criteria, missing acceptance IDs, malformed acceptance identity or malformed top-level structure remain whole-proposal validation failures.

## 5. Fixed browser-vocabulary guidance

The server-owned browser vocabulary must additionally expose action-specific field rules derived from the existing protected action contract:

- `NAVIGATE`, `ASSERT_PATH`: require `path`; no target/value/checkpoint;
- `WAIT_FOR`, `ASSERT_VISIBLE`, `ASSERT_ABSENT`, `CLICK`, `ASSERT_LAYOUT`: require `target_kind` + `target_value`; no path/value/checkpoint;
- `FILL`, `SELECT`: require `target_kind` + `target_value` + bounded `value`; no path/checkpoint;
- `SCREENSHOT`: requires `checkpoint`; no path/target/value.

The vocabulary continues to expose only registered viewport IDs and existing semantic target kinds.

Generation instructions must state explicitly: when uncertain whether an executable workflow can satisfy these rules, choose `HUMAN_ONLY` instead of guessing.

## 6. Persistence and approval

Persistence, revision, digest, approval, supersession and replay semantics from P2-V0.23.47 remain unchanged.

The normalized proposal, not raw model output, is the only object eligible for compilation and persistence.

Raw model output and validation exception text remain non-durable.
