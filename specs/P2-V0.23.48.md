## 1. Objective

Make Behavioral Verification Plan drafting reliably fail closed at the **criterion** boundary instead of unnecessarily failing the entire plan when a model proposes an invalid executable browser workflow.

P2-V0.23.47 established that every acceptance criterion is represented exactly once as either `BROWSER` or `HUMAN_ONLY`, and that `HUMAN_ONLY` is a valid non-evidence state. Authenticated production acceptance exposed that executable validation currently happens too early: one malformed `BROWSER` criterion invalidates the full model proposal, causes route escalation, and can produce a 503 even though the safe server-owned outcome for that criterion is already defined as `HUMAN_ONLY`.

P2-V0.23.48 adds conservative generated-proposal normalization. It does not relax the protected browser contract.

## 2. Scope

Included:

- exact generated acceptance-ID/order prevalidation before normalization;
- criterion-local normalization of model-proposed `BROWSER` / `HUMAN_ONLY` entries;
- conservative downgrade of an invalid executable `BROWSER` proposal to `HUMAN_ONLY`;
- strict rejection of malformed top-level structure, unknown modes and invalid acceptance identity;
- action-specific fixed server-owned browser-vocabulary guidance;
- focused and full regression coverage;
- authenticated production replay of draft/read/approve/re-approve;
- Architecture v3.57 after semantic validation.

## 3. Non-goals

- execute a browser;
- repair or invent browser actions, selectors, targets, paths or fixture values;
- use candidate source, repository files, Preview/DOM state, runtime logs or provider payloads as generator input;
- persist raw model output or raw validation exception text;
- add same-model retries or an unbounded routing loop;

- mutate source lineage, GitHub state, Vercel state or production state;
- transition an Engineering Run;
- complete human REVIEW;
- merge an application PR or promote application production.

## 4. Security

The exact approved Work Specification and server-derived acceptance map remain authoritative. Model output cannot create, omit, duplicate, reorder or rename acceptance IDs.

Only the existing protected `BrowserAction`, `BrowserWorkflow`, registered viewport and semantic-target constructors can admit executable browser authority. A model-proposed BROWSER criterion that fails any existing protected constructor rule is reduced to HUMAN_ONLY with no executable workflow. The server never repairs the executable proposal.

HUMAN_ONLY is authority-reducing: executable fields are discarded and cannot be interpreted as evidence. Unknown modes and malformed proposal structure fail the full proposal rather than being guessed.

Generation input remains limited to the approved Work Specification contract, exact acceptance map and fixed server-owned browser vocabulary. Candidate/repository/Preview/provider/runtime/credential input remains excluded.

## 5. Acceptance criteria

### AC-01 Exact acceptance identity remains fail-closed
Generated acceptance IDs must exactly equal the server-derived acceptance IDs in exact order before criterion normalization. Missing, duplicated, invented, malformed or reordered IDs reject the whole generated proposal.

### AC-02 Valid BROWSER proposals remain unchanged
A BROWSER criterion that already satisfies the existing strict action, viewport, assertion, screenshot and workflow constructors remains BROWSER with the same bounded proposed fields.

### AC-03 Invalid BROWSER action shape downgrades locally
If a criterion explicitly proposed as BROWSER fails an existing protected action-shape rule, only that exact criterion becomes HUMAN_ONLY with empty executable fields; other valid criteria remain unchanged.

### AC-04 Invalid BROWSER workflow structure downgrades locally
Unregistered viewports, missing assertions, missing screenshots, invalid paths, invalid targets, invalid fixture requirements or other existing protected workflow-constructor failures cause only that BROWSER criterion to become HUMAN_ONLY.

### AC-05 HUMAN_ONLY strips executable fields
A criterion explicitly proposed as HUMAN_ONLY normalizes to the exact acceptance ID, mode HUMAN_ONLY, empty viewport_ids and empty actions even if the model supplied executable fields. Those fields never gain authority.

### AC-06 Unknown mode and malformed proposal still fail
Unknown mode values, non-object criteria, missing acceptance_id fields, unknown criterion keys, malformed top-level structure or unknown top-level keys remain whole-proposal validation failures.

### AC-07 Browser vocabulary exposes exact field contracts
The fixed server-owned browser vocabulary identifies action-specific required and forbidden fields for NAVIGATE, ASSERT_PATH, semantic target actions, FILL, SELECT and SCREENSHOT, while retaining only registered viewport and semantic-target vocabularies.

### AC-08 Generator guidance prefers HUMAN_ONLY over guessing
The generation contract explicitly instructs the model to choose HUMAN_ONLY when it cannot confidently express a criterion through the supplied bounded action-field contract, rather than inventing executable details.

### AC-09 Persistence and digest consume normalized output only
Only the normalized strict `BehavioralPlanProposal` is eligible for compile, canonical digest, persistence, read and explicit approval. Raw model output remains non-durable.

### AC-10 Authenticated production replay proves unchanged authority
Trusted production replay must successfully draft, read, approve and replay-approve a plan, independently verify exact acceptance text/ID coverage and digest, and prove the frozen Work Specification, Engineering Run and durable Engineering Run event evidence are unchanged.

## 7. Normalization design

### 7.1 Top-level structure

Generated output remains strict JSON with exactly one `criteria` array. Each criterion may contain only `acceptance_id`, `mode`, `viewport_ids` and `actions`.

### 7.2 Acceptance identity

The server extracts the model-supplied acceptance IDs before executable validation and requires exact equality with the authoritative acceptance map. Identity is never repaired, reordered or synthesized.

### 7.3 HUMAN_ONLY normalization

An explicit HUMAN_ONLY criterion becomes the same exact acceptance ID with empty viewport_ids and actions. Model-supplied executable detail is discarded.

### 7.4 BROWSER normalization

An explicit BROWSER criterion is submitted to the existing strict `BehavioralCriterionProposal` and existing protected browser constructors. If that strict validation succeeds, the criterion is preserved. If it fails, only that criterion is replaced by HUMAN_ONLY. The server does not repair actions.

## 8. Fixed browser-vocabulary guidance

The vocabulary must expose these server-owned field contracts:

- `NAVIGATE`, `ASSERT_PATH`: require `path`; forbid target/value/checkpoint;
- `WAIT_FOR`, `ASSERT_VISIBLE`, `ASSERT_ABSENT`, `CLICK`, `ASSERT_LAYOUT`: require `target_kind` + `target_value`; forbid path/value/checkpoint;
- `FILL`, `SELECT`: require `target_kind` + `target_value` + bounded `value`; forbid path/checkpoint;
- `SCREENSHOT`: requires `checkpoint`; forbids path/target/value.

Every admitted BROWSER workflow still requires registered viewport IDs, at least one deterministic assertion and at least one screenshot.
