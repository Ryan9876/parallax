## 1. Objective

Repair production Engineering Runtime GitHub source bootstrap for normal Project-bound runs by resolving the Vercel deployment OIDC credential from the server-provided runtime environment contract that Vercel Connect supports, while preserving Project scope, repository scope, existing provider authorization, source-lineage safety, Preview-only delivery, and REVIEW authority ceilings.

The observed production failure is Engineering Run `a3a32343-507a-4384-a9bd-2fddaa0ce7fc` at PLAN revision 1 returning HTTP 503 with `source_bootstrap_failed stage=provider-repository error_class=ProviderActionFailed result_code=CREDENTIAL_UNAVAILABLE`.

## 2. Root cause

`runtime_vercel_oidc_token(...)` currently assumes production Functions receive the Vercel deployment OIDC token only through request header `x-vercel-oidc-token` and deliberately rejects the environment value. Vercel Connect/OIDC runtime tooling instead supports the deployment OIDC token through `VERCEL_OIDC_TOKEN`; provider token exchange therefore receives no credential during ordinary production Engineering Runtime requests.

## 3. Fixed decisions

- The production runtime may resolve Vercel OIDC from the server-owned `VERCEL_OIDC_TOKEN` environment value when no valid request-scoped token is present.
- Any request-scoped token, when present and valid, retains precedence so existing tests/development seams remain deterministic.
- The environment value is accepted only through the same bounded printable bearer validation used for request-scoped values.
- Missing or malformed production runtime OIDC still fails closed with `ProductionDeliveryConfigurationError`.
- No client-supplied bearer header, cookie, QA credential, Supabase credential, GitHub personal token, reusable GitHub secret, database field, or service-role token is added.
- The resolved Vercel OIDC remains an input only to the existing `VercelConnectGitHubCredentialProvider`, which must still obtain and verify an exact repository-scoped GitHub App installation credential.
- Existing Project ownership checks, `ToolCapabilityRegistry`, provider action authorization, repository binding, source-lineage validation, dynamic Vercel Project readiness, Preview-only deployment, pull-request delivery, and REVIEW completion authority remain unchanged.
- The runtime OIDC value is never returned in API payloads, persisted, logged, or added to durable evidence.
- This fix does not reinterpret GitHub installation rate-limit failures as authorization success and does not change production build preflight policy.

## 4. Scope

- `services/api/parallax_api/code/runtime_credentials.py`
- focused unit/regression tests for runtime OIDC resolution
- production replay of the QA-owned canonical Engineering Run after exact API deployment
- authoritative project records only after validated/deployment evidence

No client change is required.

## 5. Non-goals

- Adding a new QA login, owner impersonation path, service account, or general-purpose machine authentication mechanism.
- Persisting Vercel OIDC or derived GitHub provider tokens.
- Replacing Vercel Connect, GitHub App installation scope verification, or Project-scoped provider authorization.
- Broadening GitHub repository access, Vercel Project authority, production promotion, merge, domain, environment-variable, or REVIEW-completion authority.
- Changing W8-S2 dynamic Vercel Project readiness semantics or treating unrelated provider failures as W8-S2 success.
- Relaxing production build/provider preflight or GitHub rate-limit handling.

## 6. Security

- Runtime credential resolution accepts only server-side sources: the existing request-scoped Vercel OIDC header and Vercel-provided `VERCEL_OIDC_TOKEN` environment value.
- The resolver must reject leading/trailing whitespace, control characters, too-short values, and values exceeding the existing bearer bound.
- Client-controlled Authorization headers, session cookies, request bodies, query parameters, Supabase credentials, GitHub PATs, and database values are never considered Vercel runtime identity.
- A valid runtime OIDC token grants no direct GitHub authority. It can only be exchanged by the existing exact Vercel Connect connector and remains subject to repository-scoped authorization details and provider-side scope verification.
- Raw Vercel OIDC and derived provider bearer material must never be logged, returned, serialized, stored in durable run evidence, or persisted.
- Invalid or absent production identity fails closed; there is no break-glass or credential fallback.

## 7. Acceptance criteria

### AC-01 Production runtime environment credential
In production, when `x-vercel-oidc-token` is absent and `VERCEL_OIDC_TOKEN` contains a valid bounded token, `runtime_vercel_oidc_token(...)` returns that environment token for server-side provider composition.

### AC-02 Request-scoped precedence
A valid `x-vercel-oidc-token` value takes precedence over `VERCEL_OIDC_TOKEN`, preserving explicit request-scoped runtime identity when available.

### AC-03 Fail closed
Production with neither a valid request token nor a valid environment token raises `ProductionDeliveryConfigurationError`. Malformed, whitespace-padded, control-character, too-short, or oversized values are not accepted.

### AC-04 Non-production behavior remains bounded
Non-production callers with no valid runtime token continue to return `None`; this fix does not inject production provider authority into local/Preview execution.

### AC-05 No reusable credential expansion
No new long-lived GitHub/Vercel/QA secret is introduced. The resolved value remains server-owned Vercel deployment identity and is not persisted or exposed.

### AC-06 Existing repository scope remains authoritative
The Vercel OIDC token can only reach GitHub through the existing Connect exchange and exact repository-scope verification. Project/repository mismatch and provider authorization failures still fail closed.

### AC-07 Production source bootstrap advances
After exact API deployment, the QA-owned canonical Engineering Run can retry from PLAN without `CREDENTIAL_UNAVAILABLE` at `provider-repository`. If a later independent failure occurs, it is recorded separately and is not relabeled as a pass.

### AC-08 W8-S2 replay integrity
Only after AC-07 is proven may the same QA-owned run be reconsidered as a valid W8-S2 canonical equivalent. W8-S2 passes only if it durably advances beyond the former missing-static-target PLAN failure without `ProductionDeliveryConfigurationError` caused by static Preview-target registration.
