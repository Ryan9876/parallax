# Parallax 2.0 — Wave 4 Warm Editorial Application Shell

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.17.3
Workstream: WS-W4-EDITORIAL-SHELL / GitHub issue #147
Base: main@80c1ca90761a2c576663c188282120a4ad040399
Depends on: integrated P2-V0.17.0 experience/design contract and integrated-but-inactive P2-V0.17.2 live-observation source
Method: mockup-faithful responsive client-shell replacement preserving existing product/runtime authority

## 1. Objective

Replace the current Deep Violet Optical application chrome with the approved Warm Editorial Parallax shell while preserving all existing authenticated conversation, Project selection/create, Work Specification, Engineering Run, response-streaming, accessibility and mobile keyboard behavior. The implementation must closely follow the approved mockup family: dark forest/olive navigation, warm ivory/cream workplane, rust active/action treatment, flat teal live interaction, restrained olive support state, charcoal copy, editorial serif hierarchy, soft rounded cards and subtle organic depth.

This workstream changes presentation architecture, not runtime authority. It must not activate Wave 4 telemetry, apply the `engineering_run_events` migration, simulate Live Build state, expose inactive observability data or rewrite the Wave 3 execution model.

## 2. Scope

- Replace the dominant client palette with centralized Warm Editorial raw and semantic tokens.
- Introduce reusable shell, navigation, card and layout components instead of embedding new visual structure directly throughout `App.tsx`.
- Compose the existing conversation product inside a responsive desktop application shell that reflects the approved mockup proportions and hierarchy.
- Preserve the existing Project, Work Specification and Engineering Run surfaces and semantics while adapting their visual container treatment to the new shell.
- Preserve private-session authentication, conversation creation/switching, Reason/Code mode, response streaming, draft persistence and existing failure states.
- Implement a responsive mobile reflow that uses focused stacked regions/drawers rather than scaling the desktop shell.
- Add deterministic browser/visual/accessibility tests for palette roles, shell geometry, mobile behavior and design-regression prevention.
- Preserve reduced-motion/reduced-graphics behavior, selectable text, user zoom and existing keyboard/visualViewport protections.

The final Live Build/Observability workspace, run-event rendering, terminal/test/evidence panels, migration application, Wave 4 activation and production deployment are out of scope for #147.

## 3. Fixed decisions

- **Conversation stays primary.** The main creation surface remains the existing conversation experience; the new shell frames it rather than replacing it with an operations dashboard.
- **Approved mockups are the visual source of truth.** Desktop composition, visual hierarchy and semantic hue roles are protected acceptance targets, subject only to deterministic accessibility/security/functionality precedence.
- **Warm Editorial replaces Deep Violet Optical.** Forest/olive, ivory/cream, rust, teal and charcoal become the dominant visual identity. Violet/cyan may not remain the dominant substrate, active state or brand treatment.
- **Semantic tokens are centralized.** Components consume named semantic roles; one-off mockup hex values are not scattered through product components.
- **No fake observability.** #147 may reserve layout affordances needed by #148, but it cannot display fabricated run metrics, alerts, timelines or live progress when authoritative data is unavailable/inactive.
- **Existing product controls keep meaning.** Project selection/create, Work Specification approval/drafting, Engineering Run controls, Reason/Code selection and authentication behavior are restyled without semantic changes.
- **Reusable shell components.** New navigation/layout/card material is factored into reusable components so `App.tsx` remains product-state orchestration rather than becoming a styling monolith.
- **Responsive reflow.** Desktop uses a stable navigation rail plus dominant warm workplane. Phone widths collapse/reflow navigation and secondary regions; the desktop dashboard is never simply scaled down.
- **Accessibility outranks fidelity.** Minimum touch size, editable text size, zoom, keyboard safety, reduced motion/graphics, selectable content, contrast and non-color state labels cannot be weakened to match a screenshot.
- **Wave 4 activation remains server-owned.** This client shell does not set, infer or bypass `PARALLAX_RUN_EVENTS_ENABLED`, does not apply schema, and does not make inactive read routes a required startup dependency.

## 4. Architecture requirements

`apps/client/src/theme.ts` becomes the single durable palette/token source for the Warm Editorial shell. Raw targets begin from the accepted Wave 4 contract:

- forest950 `#1C2A18`
- forest900 `#24341F`
- forest800 `#31442A`
- olive700 `#66753A`
- olive500 `#87954D`
- ivory50 `#FBF7EE`
- cream100 `#F5EEDF`
- cream200 `#E9DFCC`
- rust700 `#A83B17`
- rust600 `#C44A1B`
- rust500 `#D75B24`
- teal700 `#006E70`
- teal600 `#008487`
- teal500 `#15999A`
- charcoal950 `#172024`
- charcoal800 `#30383A`
- charcoal600 `#626664`

The implementation may tune exact values under visual validation, but semantic roles remain fixed: forest navigation/substrate, warm ivory workplane, rust primary/active, teal live/interactive, olive support/success, charcoal content, warm stone borders and distinct warning/danger roles.

Temporary compatibility aliases are allowed only where needed to migrate existing components safely; they cannot preserve the old violet/cyan identity as the dominant product theme.

### 4.2 Shell composition

At standard desktop width the shell provides:

1. a dark forest navigation rail approximately 16–20% of viewport width, stable enough to anchor product identity;
2. a dominant warm ivory/cream workplane containing the current conversation and contextual controls;
3. optional secondary contextual space only when backed by real existing product state; #147 does not fabricate the final #148 utility rail.

The Parallax orbital brand mark, navigation grouping, active rust treatment, profile/account context and quiet lower-rail utility treatment should follow the approved mockup language. Existing destinations that are not yet real product surfaces must not become misleading functional controls merely to match the picture.

### 4.3 Reusable presentation components

Create bounded components under `apps/client/src/components/**` for shell concerns such as application frame, sidebar/navigation, editorial card/material and workspace header. Components receive product state/actions through props and do not fetch or mutate backend authority themselves unless an existing component already owns that established responsibility.

`App.tsx` continues to own existing orchestration for authentication, conversation state, response streaming and the existing Project/Work Specification/Engineering Run hooks. The redesign should reduce presentation coupling rather than relocating business authority into shell components.

### 4.4 Existing conversation behavior

The shell must preserve:

- authentic conversation list/load/create behavior;
- Reason and Code mode selection;
- selectable assistant/user text;
- response streaming and live-edge behavior;
- draft persistence where currently supported;
- authentication/session-expiry handling;
- current Project selection/create compatibility;
- Work Specification drafting/approval and status;
- Engineering Run status/control behavior;
- current offline/failure handling without claiming successful state.

Fallback/demo copy used for offline presentation may remain clearly non-authoritative, but must not look like live engineering telemetry.

### 4.5 Typography and material

Major greeting/display hierarchy uses a reliable platform serif where available without adding an external runtime font dependency. UI controls, conversation text and metadata remain legible sans-serif; source/technical evidence remains monospace when later required.

Warm cards use low-contrast cream surfaces, restrained warm borders, approximately 14–20 px desktop corner radii and subtle depth. Decorative organic gradients/curves may reinforce the brand but must remain low contrast and reduced-graphics compatible.

### 4.6 Desktop fidelity

Permanent browser assertions must protect the broad approved composition rather than exact fragile pixel values:

- dark navigation rail remains visually distinct from the warm workplane;
- navigation occupies a bounded minority of desktop width;
- primary workplane remains dominant;
- header/greeting hierarchy precedes conversation/work controls;
- cards share consistent radius/material/spacing;
- rust identifies primary/active interaction, teal identifies live/interactive treatment and olive is restrained support state;
- old violet/cyan does not reappear as dominant background/active/brand treatment.

Screenshot baselines may be tuned during implementation, but major region order and semantic hue roles cannot be changed for implementation convenience.

### 4.7 Mobile, keyboard and reduced graphics

At phone widths navigation collapses to a focused accessible control/drawer/sheet pattern and content becomes one primary column. Existing editable composer text remains at least 16 CSS px on phone web. Touch targets remain approximately 44 pt where practical. User zoom remains enabled. VisualViewport/keyboard accommodation must preserve composer access and must not regress current mobile acceptance tests.

Reduced-motion and reduced-graphics preferences retain equivalent content and actions. Decorative optical/organic effects may be simplified or removed without removing product information.

### 4.8 Inactive observability boundary

Because #146 source is integrated but production-inactive, the shell must tolerate observability APIs being absent. No startup fetch, route assumption or fake placeholder may turn the inactive Wave 4 read surface into a client requirement. #148 will compose real run-event/source/diff/evidence views only after the governed activation/release path is ready.

## 5. Security and privacy

- Existing private authentication/session and owner-scoped Project boundaries remain unchanged.
- Shell components do not receive or persist provider credentials, root access credentials, auth headers/cookies or raw provider responses.
- The theme redesign does not add arbitrary URLs, filesystem access, shell execution, provider console or source mutation controls.
- Hidden model reasoning/scratchpad remains absent.
- No inactive Wave 4 endpoint is probed as a substitute for explicit availability.
- Existing user/content text remains selectable where it is selectable today; presentation changes cannot copy private source into generic client telemetry.
- Navigation destinations must not imply authority the backend does not provide.

## 6. Failure and recovery boundaries

- Authentication failure/session expiry retains the existing explicit locked/private-session behavior.
- API-offline and unavailable states remain truthful and do not substitute mock live values.
- Missing Project, Work Specification or Engineering Run state is rendered as unavailable/not-started according to existing semantics, not inferred success.
- Layout failure on a narrow viewport falls back to stacked accessible content rather than clipping essential controls.
- Reduced graphics/motion cannot remove functionality.
- If a visual treatment conflicts with deterministic browser/accessibility/mobile requirements, the treatment changes; the protected behavior does not.
- If #146 observability routes are absent because Wave 4 is inactive, #147 continues to function normally as the conversation shell.

## 7. Non-goals

- implementing #148 Live Build/Observability panels, run pipeline, event timeline, terminal/test/evidence tabs or live system-health rail;
- applying `20260824_0010_run_events.sql` or enabling `PARALLAX_RUN_EVENTS_ENABLED`;
- changing Engineering Run, worker, source-lineage, provider, evaluator or Work Specification authority;
- adding a generic IDE, shell, file editor, HTTP client or provider console;
- adding fictional Templates/Tools/Knowledge/Integrations functionality solely because labels appeared in the visual reference;
- changing authentication architecture or production credentials;
- production deployment from this worker branch.

## 8. Acceptance criteria

### AC-01 Warm Editorial semantic tokens replace the dominant violet identity
The client has one centralized raw/semantic theme source whose dominant navigation, workplane, action, live-interaction, support and content roles are forest/ivory/rust/teal/olive/charcoal, and permanent checks prevent a return to dominant violet/cyan treatment.

### AC-02 Desktop shell follows the approved mockup hierarchy
At protected desktop viewport sizes the application renders a dark bounded navigation rail and dominant warm workplane with approved editorial hierarchy, consistent card material and rust/teal/olive role separation; browser/screenshot evidence checks these relationships.

### AC-03 Existing product semantics survive the redesign
Authentication, conversation create/select/load, Reason/Code mode, response streaming, Project selection/create, Work Specification behavior and Engineering Run controls keep their existing functional semantics and protected tests remain green.

### AC-04 The shell never fabricates Live Build or production state
No run progress, observability metrics, provider status, alerts, test progress or deployment state is displayed as live unless backed by existing authoritative product state; inactive #146 routes are not required for shell startup.

### AC-05 Parallax brand/navigation treatment matches the Warm Editorial direction
The visible Parallax identity and navigation use the approved forest substrate, orbital brand language, restrained organic depth and rust active treatment without reintroducing Deep Violet Optical as the dominant brand expression.

### AC-06 Reusable shell components prevent presentation drift
New shell/navigation/card/header/layout concerns are encapsulated in reusable bounded components, while `App.tsx` remains the established product-state orchestration layer instead of absorbing a new monolithic styling implementation.

### AC-07 Mobile reflows and preserves keyboard/touch behavior
Phone layouts use a focused single-column/collapsed-navigation treatment, preserve practical 44 pt targets, at least 16 CSS px editable text, user zoom and visualViewport/keyboard composer clearance, and pass existing/new mobile browser checks.

### AC-08 Accessibility and reduced-motion/graphics remain equivalent
Selectable text, visible focus/labels, non-color state meaning, contrast, reduced-motion and reduced-graphics modes preserve equivalent product capability; visual fidelity does not waive deterministic accessibility failures.

### AC-09 Existing cumulative client and protected runtime gates remain green
Typecheck, state tests, web export, browser/Skia acceptance and inherited API/protected evaluation suites pass without weakening existing test expectations to accommodate the theme.

### AC-10 Visual regression checks protect palette, geometry and hierarchy
Permanent deterministic/visual assertions verify the major Warm Editorial token roles, navigation/workplane relationship, responsive region behavior and absence of dominant legacy violet treatment at protected viewports.

### AC-11 Wave 4 activation and production boundaries remain untouched
#147 does not enable `PARALLAX_RUN_EVENTS_ENABLED`, apply the run-event migration, require the live-observation route at startup, alter provider/credential authority or claim deployment from source/Preview evidence.

### AC-12 Authentic plan evidence and exact-head release gates remain mandatory
The final candidate contains authentic committed DSPy SpecCritic/SpecCompiler plan evidence and passes Workstream Spec Validation, Parallax P2 CI and Bounded Autonomy on the exact final reconciled head. The worker stops review-ready before merge or deployment.

## 9. Release gate

Before #147 is READY FOR INTEGRATION, AC-01 through AC-12 must be implemented and deterministically tested; desktop/mobile screenshots and browser assertions must demonstrate the accepted Warm Editorial direction without regressions in authentication/conversation/Project/Work Specification/Engineering Run behavior; the branch must be reconciled to current `main`; authentic DSPy plan evidence must be committed; exact-head Workstream Spec Validation, P2 CI and Bounded Autonomy must pass. No production migration, Wave 4 activation or deployment occurs from this worker workstream.
