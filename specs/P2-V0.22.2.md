## 1. Objective

Make authenticated production acceptance genuinely runnable by Parallax automation without asking the owner to enter, disclose, or relay the QA password. Preserve the existing dedicated QA identity, active `authorized_users` allowlist, Google binding, signed Parallax session cookie, project ownership isolation, and all protected runtime authority boundaries.

## 2. Fixed decisions

- Normal `/` remains Google-only and the existing `/?qa=1` human fallback remains unchanged.
- Automation authentication uses short-lived GitHub Actions OIDC, not a reusable password, Supabase refresh token, service-role key, database mutation, or Parallax break-glass token.
- The API trusts only GitHub issuer `https://token.actions.githubusercontent.com`, audience `parallax://qa-production`, repository `Ryan9876/parallax`, ref `refs/heads/main`, exact workflow ref `Ryan9876/parallax/.github/workflows/qa-production-replay.yml@refs/heads/main`, GitHub-hosted runners, and the bounded `workflow_dispatch` or exact-main-workflow-change `push` events used by this release mechanism.
- OIDC signature, issuer, audience, expiry/not-before and exact claims are verified server-side against GitHub's current JWKS.
- A valid automation assertion maps only to the existing `parallax.qa.ai@gmail.com` authorized user. That row must be active and already Google-bound before a Parallax session can be issued.
- The resulting cookie is the ordinary signed HttpOnly Parallax session and receives no additional application authority.
- QA automation must not impersonate the owner or cross the normal project ownership boundary. When an historical acceptance target is owner-scoped, the workflow creates a canonical QA-owned equivalent through ordinary production APIs using the same repository identity and acceptance objective, then exercises the same protected runtime path.
- For W8-S2 the canonical equivalent is bound to `github:Ryan9876/ot-time` and preserves the original objective: implement and verify an About page in the bound project.
- No long-lived machine QA credential is stored in GitHub or Vercel.

## 4. Non-goals

- General-purpose machine authentication.
- Allowing arbitrary repositories, branches, workflows, self-hosted runners, or pull-request code to obtain QA sessions.
- Replacing Google or the hidden password fallback for humans.
- Increasing QA user privileges, impersonating the owner, or granting QA access to owner-scoped Projects/Runs.
- Direct database mutation, service-role authentication, or bypassing `authorized_users`.
- Declaring W8-S2 complete unless the production replay—original target when legitimately accessible, otherwise the canonical QA-owned equivalent—advances beyond the former PLAN failure and evidence is verified.

## 5. Security and reliability requirements

- Authentication fails closed on malformed, unsigned, expired, not-yet-valid, wrong issuer/audience, wrong repository/ref/workflow/event/runner claims, JWKS failure, inactive QA user, missing QA row, or missing Google binding.
- Raw OIDC tokens are never logged, persisted, returned, or placed in URLs.
- The workflow requests `id-token: write` and `contents: read` only.
- The workflow does not run on `pull_request` or arbitrary branch push. Automatic push execution is limited to `main` when the exact QA production replay workflow file changes.
- Session issuance reuses the existing server-side signing key, TTL, cookie settings, and downstream `access_principal` checks.
- The automation endpoint exposes no email selector; the QA identity is server-fixed.
- A failure in OIDC verification cannot fall back to bearer/break-glass auth.
- Canonical QA fixtures are created only through the same authenticated production APIs available to the QA member; no direct database writes or ownership override are permitted.

## 6. Acceptance criteria

### AC-01 Exact machine identity only
A GitHub-signed OIDC token is accepted only when issuer, audience, repository, main ref, exact workflow ref, an explicitly allowed bounded event, and GitHub-hosted runner claims all match.

### AC-02 Existing QA authorization remains authoritative
The API issues a session only when `parallax.qa.ai@gmail.com` exists in `authorized_users`, is active, and already has a bound Google auth user ID.

### AC-03 No reusable QA secret
Neither repository code nor workflow configuration stores the QA password, refresh token, Supabase service-role key, Parallax access token, or another long-lived QA credential.

### AC-04 Normal auth and tenant isolation are unchanged
Google login, hidden human QA password fallback, session expiry, logout, owner/member access, project ownership isolation, and protected-route behavior remain unchanged; QA automation cannot read or mutate an owner-scoped run merely because it is machine-authenticated.

### AC-05 Production replay is autonomous without impersonation
The dedicated workflow can establish a production Parallax session and, when the historical owner-scoped OT Time run is correctly inaccessible, create a QA-owned canonical equivalent through normal APIs using repository `github:Ryan9876/ot-time` and the original About-page objective, then invoke the existing protected autonomous endpoint without owner browser interaction.

### AC-06 W8-S2 proof remains evidence-based
A replay passes only if the canonical run durably advances beyond the former missing-static-target PLAN failure without `source_bootstrap_failed` / `ProductionDeliveryConfigurationError`; provider/runtime evidence stays within the existing REVIEW/Preview authority ceiling.

### AC-07 Trust failures remain fail-closed
Forged, malformed, expired, not-yet-valid, wrong-audience, wrong-repository, wrong-ref, wrong-workflow, unapproved-event, self-hosted-runner, and JWKS-verification failures produce no Parallax session and cannot fall back to another authentication method.

### AC-08 QA revocation and binding remain effective
If the dedicated QA allowlist row is missing, revoked, inactive, or no longer Google-bound, the machine assertion is denied even when the GitHub Actions OIDC assertion itself is valid.

### AC-09 Automation is auditable without credential leakage
The GitHub workflow run provides a durable provider-side run identity and bounded execution evidence while raw OIDC tokens, cookies, passwords, refresh tokens, and provider credentials remain absent from committed artifacts and application logs.

### AC-10 Production verification is exact and regression-safe
The exact qualified API source is deployed READY before the workflow runs; the automation session endpoint succeeds only from the merged trusted workflow; ordinary Google and hidden human QA login behavior remain unchanged; post-replay API/runtime errors and durable run state are inspected before any completion claim or authoritative-record update.
