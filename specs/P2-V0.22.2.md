## 1. Objective

Make authenticated production acceptance genuinely runnable by Parallax automation without asking the owner to enter, disclose, or relay the QA password. Preserve the existing dedicated QA identity, active `authorized_users` allowlist, Google binding, signed Parallax session cookie, Project ownership isolation, and all protected runtime authority boundaries.

## 2. Fixed decisions

- Normal `/` remains Google-only and the existing `/?qa=1` human fallback remains unchanged.
- Automation authentication uses short-lived GitHub Actions OIDC, not a reusable password, Supabase refresh token, service-role key, database mutation, or Parallax break-glass token.
- The API trusts only GitHub issuer `https://token.actions.githubusercontent.com`, audience `parallax://qa-production`, repository `Ryan9876/parallax`, ref `refs/heads/main`, explicitly enumerated QA workflow refs on `main`, explicitly allowed bounded events, and GitHub-hosted runners.
- OIDC signature, issuer, audience, expiry/not-before and exact claims are verified server-side against GitHub's current JWKS.
- A valid automation assertion maps only to the existing `parallax.qa.ai@gmail.com` authorized user. That row must be active and already Google-bound before a Parallax session can be issued.
- The resulting cookie is the ordinary signed HttpOnly Parallax session and receives no additional application authority.
- QA automation must not impersonate the owner or cross Project ownership boundaries. An owner-scoped historical acceptance target that is correctly inaccessible to QA is replaced only by a QA-owned canonical equivalent that reproduces the material defect preconditions through normal production APIs.
- For W8-S2, canonical equivalence is defined by the defect boundary, not by application content: a QA-owned Engineering Run at PLAN with an approved Work Specification, a valid GitHub repository binding, and no existing Vercel Project linked to that repository exercises the same missing-static-preview-target precondition as the historical OT Time run.
- The admitted W8-S2 production fixture is Engineering Run `a3a32343-507a-4384-a9bd-2fddaa0ce7fc`, owned by the QA principal, at PLAN revision 1 before replay, with an approved Work Specification and repository `github:ryan9876/sickbeard`. Provider inspection before replay confirms the Vercel team has no Project linked to `Ryan9876/sickbeard`.
- No long-lived machine QA credential is stored in GitHub or Vercel.

## 4. Non-goals

- General-purpose machine authentication.
- Allowing arbitrary repositories, branches, workflows, self-hosted runners, or pull-request code to obtain QA sessions.
- Replacing Google or the hidden password fallback for humans.
- Increasing QA user privileges, impersonating the owner, or granting QA access to owner-scoped Projects/Runs.
- Direct database mutation, service-role authentication, or bypassing `authorized_users`.
- Requiring a canonical equivalent to share the historical application's objective when the defect under test is independent of objective content.
- Declaring W8-S2 complete unless the authenticated production replay advances beyond the former PLAN failure and evidence is verified.

## 5. Security and reliability requirements

- Authentication fails closed on malformed, unsigned, expired, not-yet-valid, wrong issuer/audience, wrong repository/ref/workflow/event/runner claims, JWKS failure, inactive QA user, missing QA row, or missing Google binding.
- Raw OIDC tokens are never logged, persisted, returned, or placed in URLs.
- QA workflows request `id-token: write` and `contents: read` only.
- QA workflows do not run on `pull_request` or arbitrary branch push. Any automatic execution is restricted to `main` and exact QA workflow/security-path changes.
- Session issuance reuses the existing server-side signing key, TTL, cookie settings, and downstream `access_principal` checks.
- The automation endpoint exposes no email selector; the QA identity is server-fixed.
- A failure in OIDC verification cannot fall back to bearer/break-glass auth.
- Canonical acceptance fixtures remain ordinarily owner-scoped to the QA principal and are read/mutated only through the same authenticated product APIs available to that principal.
- Machine-QA authentication grants no source acceptance, provider administration, merge, production promotion, deployment, lifecycle transition, or REVIEW-completion authority beyond the existing QA user's normal application permissions.

## 6. Acceptance criteria

### AC-01 Exact machine identity only
A GitHub-signed OIDC token is accepted only when issuer, audience, repository, main ref, an explicitly enumerated QA workflow ref, an explicitly allowed bounded event, and GitHub-hosted runner claims all match.

### AC-02 Existing QA authorization remains authoritative
The API issues a session only when `parallax.qa.ai@gmail.com` exists in `authorized_users`, is active, and already has a bound Google auth user ID.

### AC-03 No reusable QA secret
Neither repository code nor workflow configuration stores the QA password, refresh token, Supabase service-role key, Parallax access token, or another long-lived QA credential.

### AC-04 Normal auth and tenant isolation are unchanged
Google login, hidden human QA password fallback, session expiry, logout, owner/member access, Project ownership isolation and protected-route behavior remain unchanged; the machine-authenticated QA member cannot read or mutate the historical owner-scoped OT Time run.

### AC-05 Canonical W8-S2 fixture reproduces the material precondition
Before replay, Engineering Run `a3a32343-507a-4384-a9bd-2fddaa0ce7fc` is QA-owned, at PLAN revision 1, bound through an approved Work Specification to a valid GitHub repository, and the Vercel team has no Project linked to `Ryan9876/sickbeard`.

### AC-06 Production replay is autonomous
The isolated W8-S2 workflow establishes a production Parallax session and invokes the existing protected autonomous endpoint for the admitted QA-owned canonical run without owner browser interaction, auth bypass, direct database mutation, or owner impersonation.

### AC-07 W8-S2 proof remains evidence-based
The replay passes only if durable run evidence advances beyond the former missing-static-target PLAN failure without `source_bootstrap_failed` / `ProductionDeliveryConfigurationError`; provider/runtime evidence stays within the existing Preview/REVIEW authority ceiling.

### AC-08 Trust failures and QA revocation remain fail-closed
Forged, malformed, expired, not-yet-valid, wrong-audience, wrong-repository, wrong-ref, non-enumerated-workflow, unapproved-event, self-hosted-runner and JWKS-verification failures produce no Parallax session; a missing, inactive, revoked or no-longer-Google-bound QA row also produces no session.

### AC-09 Automation is auditable without credential leakage
The GitHub workflow run provides durable provider-side run identity and bounded execution evidence while raw OIDC tokens, cookies, passwords, refresh tokens and provider credentials remain absent from committed artifacts and application logs.

### AC-10 Production verification is exact and regression-safe
The exact qualified source is merged and deployed READY before replay; ordinary Google and hidden human QA behavior remain unchanged; post-replay GitHub workflow evidence, Vercel runtime evidence, durable Engineering Run state and provider readiness state are inspected before any W8-S2 completion claim or authoritative-record update.
