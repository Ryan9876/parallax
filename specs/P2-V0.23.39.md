## 1. Objective

Correct exact greenfield baseline replay for the canonical Git empty-tree behavior proven by the P2-V0.23.38 production replay, without accepting arbitrary missing trees or weakening any repository, source, actor, lineage, lifecycle, or REVIEW authority.

P2-V0.23.38 is production READY and its frozen W9-S1 replay proves provider-owned timestamp compatibility works: `GREENFIELD_BASELINE_MISMATCH`, `PROVIDER_CONFLICT`, and `TARGET_DISCOVERY_UNBOUNDED` did not recur. Verification advanced through exact cleanup-commit read-back and then failed because GitHub returned 404 for Trees GET of the cleanup commit's exact canonical Git empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`.

The canonical Git SHA-1 empty-tree identity is deterministic. For existing baseline replay, exact equality to that one server-owned constant is stronger and narrower evidence of emptiness than requiring a provider to materialize the universal empty-tree object through a separate Trees GET. P2-V0.23.39 therefore requires the cleanup commit tree SHA to equal the canonical empty-tree SHA and omits only that redundant provider read for exact replay. New initialization retains the existing provider-returned tree verification before cleanup commit/ref mutation.

## 5. Architecture requirements

### 5.1 Canonical empty-tree identity is exact and server owned

Define exactly one private constant equal to Git SHA-1's canonical empty-tree object ID: `4b825dc642cb6eb9a060e54bf8d69288fbee4904`.

During existing baseline replay, the cleanup commit's `tree.sha` must equal that exact value. Any other value fails `GREENFIELD_BASELINE_MISMATCH` before bootstrap acceptance or delivery continuation.

The constant cannot be set by request input, model output, browser state, repository files, provider response configuration or environment variables.

### 5.2 Exact canonical identity replaces only redundant replay read-back

When `_verify_baseline` reads the cleanup commit and obtains the exact canonical empty-tree SHA, it must treat that SHA identity as deterministic proof that the cleanup tree is empty and must not call GitHub Trees GET for that cleanup tree.

This is not a 404 normalization rule. `_tree_payload` and `_tree` behavior remain unchanged. Missing bootstrap trees, arbitrary trees and every other provider tree read continue to fail under existing behavior.

### 5.3 New initialization keeps provider verification

The P2-V0.23.37 initialization sequence remains:

1. verified positive empty-repository inspection;
2. fixed Contents bootstrap marker creation;
3. exact bootstrap ref/commit/tree/blob/provenance read-back;
4. Git Data tree creation deleting only `.parallax-greenfield` from the verified bootstrap tree;
5. provider read-back of the returned cleanup tree and proof it has zero entries;
6. fixed one-parent cleanup commit creation/read-back;
7. canonical default-ref recheck;
8. exact non-force ref update;
9. final exact baseline verification.

P2-V0.23.39 changes step 9 replay behavior only for the canonical cleanup-tree read; step 5 remains mandatory.

### 5.4 All other exact baseline invariants remain authoritative

Replay still requires:

- exact repository and canonical default branch;
- cleanup commit at current default ref;
- exact cleanup actor name/email and valid offset-aware timestamp metadata;
- exact cleanup message;
- exactly one cleanup parent;
- exact canonical empty-tree SHA;
- exact bootstrap commit actor/name/email/timestamp shape;
- exact bootstrap message and zero parents;
- exact one-entry bootstrap tree;
- exact marker path `.parallax-greenfield`, blob type, `100644` mode and blob identity;
- exact marker bytes/version/provenance digest;
- final current default ref equal to baseline revision.

### 5.5 Failure semantics remain bounded

A non-canonical cleanup tree is deterministic baseline mismatch, not a provider retry opportunity. A missing bootstrap tree/blob/commit remains source/provider failure under existing mappings. No hidden retry is introduced.

## 6. Security

The optimization is narrower than accepting provider read-back absence: it accepts only one universally deterministic object identity embedded in the already verified cleanup commit. It therefore does not allow an attacker or provider to substitute an arbitrary missing tree and have it interpreted as empty.

Exact actor identity, commit structure, bootstrap marker/provenance and default-ref binding continue to establish Parallax ownership of the baseline. The canonical empty-tree constant carries no repository, credential, lifecycle, approval or promotion authority beyond proving the cleanup tree's content identity.

## 7. Reliability and rollback

This is a replay-verification compatibility change with no data migration. Repositories initialized under P2-V0.23.37 remain byte/history compatible. New initialization remains unchanged up to the final replay verification, so provider behavior during creation is still independently checked before any cleanup commit/ref mutation.

Rollback to P2-V0.23.38 is operationally safe but reintroduces `SOURCE_NOT_FOUND` on providers that do not materialize the canonical empty-tree object through Trees GET. Forward release is required for W9-S1 continuation.

## 10. Risks

The primary risk is converting one provider object-materialization quirk into broad acceptance of missing Git objects. The mitigation is exact: only the universal canonical empty-tree SHA bypasses one replay Trees GET, while all other object reads and baseline invariants remain exact.

A second risk is accidentally weakening new-repository initialization by reusing the replay shortcut during tree creation. The mitigation is explicit separation: newly created cleanup tree read-back remains mandatory before cleanup commit/ref mutation.
