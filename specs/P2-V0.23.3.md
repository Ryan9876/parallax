## 1. Objective

Enable a normal Parallax Project bound to a greenfield GitHub repository to obtain the exact repository-scoped source authority required for Engineering Runtime bootstrap, without PAT fallback, owner impersonation, broad runtime tokens, direct database mutation, or weakening Project ownership, source-lineage, Preview, REVIEW, or production-promotion boundaries.

This specification addresses the remaining production finding after `P2-V0.23.2`: runtime Vercel OIDC is present, but Vercel Connect rejects token exchange for Project repository `Ryan9876/sickbeard` because the existing `github/parallax-runtime` installation is statically scoped to the registered Parallax repository.

## 2. Verified production root cause

Authenticated QA replay run `33232396195` successfully established the existing bounded Parallax QA session and read Engineering Run `a3a32343-507a-4384-a9bd-2fddaa0ce7fc` at PLAN revision 1. The protected autonomous continuation returned HTTP 503.

Production deployment `dpl_FPWh6qSvxWhWbDd7Cmpo2XHoe9mw` (`main@e9c931518d2b378952024ba0105ca638559244d2`) recorded:

`source_bootstrap_failed stage=provider-repository error_class=ProviderActionFailed result_code=CREDENTIAL_UNAVAILABLE`

and Vercel Connect returned HTTP 422 for `POST /v1/connect/token/github/parallax-runtime`.

The same deployment's production build preflight passed exact Vercel Connect token issuance and GitHub scope verification for one registered repository target. Therefore runtime identity exists; the mismatch is repository coverage. A greenfield Project may bind `github:Ryan9876/sickbeard`, while the current connector installation is authorized only for the statically registered Parallax repository.

## 3. Fixed decisions

- Repository coverage and runtime token scope are separate authority layers.
- A Project may proceed to source bootstrap only when its exact canonical GitHub repository is covered by an approved Parallax GitHub App / Vercel Connect installation.
- Runtime source credentials remain short-lived and exact-one-repository scoped through Vercel Connect `authorizationDetails`; broader installation coverage must never imply a broad runtime bearer token.
- Parallax must verify the derived GitHub credential sees exactly the Project repository before any source read or mutation.
- If installation coverage is absent, Parallax fails before Engineering Runtime source mutation with a typed, durable `REPOSITORY_AUTHORIZATION_REQUIRED` readiness state rather than a generic PLAN-time `CREDENTIAL_UNAVAILABLE` failure.
- Project onboarding/readiness may expose a provider-consent action that authorizes the exact repository or a user-chosen broader installation scope. Parallax itself may not silently broaden GitHub App installation coverage.
- A user may deliberately choose a one-time GitHub App installation scope that covers all repositories Parallax is allowed to manage. Even under that broader installation, every Parallax runtime exchange remains exact-repository scoped and verified.
- Existing Project ownership and tenant isolation remain authoritative. Repository authorization for one Project does not grant another Project access unless that second Project is independently bound to a repository covered by the installation and receives its own exact scoped token.
- No GitHub personal access token, reusable GitHub installation token, Supabase credential, QA password, service-role key, Vercel static account token, or application break-glass token is introduced.
- No source acceptance, merge, production promotion, domain, environment-variable, deployment, lifecycle-transition, or REVIEW-completion authority is added.

## 4. Scope

Expected implementation areas:

- production GitHub/Vercel Connect credential readiness and repository-scope verification;
- Project/provider readiness contracts and typed failure/result codes;
- bounded repository-authorization metadata required to determine whether an exact Project repository is covered;
- Engineering Runtime source-bootstrap gating so missing repository coverage is detected before source mutation;
- API/client presentation only where needed to surface an actionable repository-authorization requirement;
- production/provider preflight coverage for exact token scoping under an installation that may cover multiple repositories;
- focused tests plus the existing QA-owned W8-S2/W9 canonical replay.

Exact files are determined by the DSPy-compiled plan and implementation review; this specification does not authorize unrelated refactoring.

## 5. Non-goals

- Automatically granting Parallax access to every repository in a GitHub account or organization.
- Circumventing GitHub's consent/installation model for repositories not already covered by the Parallax GitHub App installation.
- Replacing Vercel Connect with PATs, SSH keys, static GitHub tokens, or direct GitHub credential storage.
- Allowing a runtime credential to span multiple repositories.
- Treating repository-name ownership alone as authorization.
- Creating or deleting GitHub repositories as part of this finding unless separately governed.
- Changing W8-S2 dynamic Vercel Project readiness semantics.
- Increasing QA identity privileges or allowing QA to read owner-scoped Projects/Runs.

## 6. Security and authorization requirements

- Canonical repository identity must be derived from the Project binding and compared case-insensitively only for provider identity matching; persisted identity is not silently rewritten.
- Provider-consent URLs, installation identifiers, connector identifiers, and repository coverage metadata must be bounded and validated before use.
- Raw Vercel OIDC, GitHub access tokens, GitHub refresh tokens, connector tokens, cookies, and provider secrets must never be logged, persisted in Project/run records, returned to the client, or embedded in URLs.
- A derived GitHub token is accepted only after `/installation/repositories` or an equivalent provider-verifiable scope check proves it is restricted to exactly the Project repository.
- Installation-level access to multiple repositories is acceptable only when explicitly authorized by the GitHub account/organization owner and must not alter exact token-scope verification.
- Missing, revoked, expired, ambiguous, mismatched, or unverified repository coverage fails closed before source mutation.
- Pull-request code, arbitrary branches, self-hosted QA runners, client-supplied credentials, and database-supplied bearer material cannot influence provider identity or repository authorization.

## 7. Product requirements

- A user binding a Project to a repository Parallax cannot yet access receives a clear natural-language state such as: `Connect this repository before Parallax can build in it.`
- The state must identify the repository but never expose credentials or provider token details.
- If provider consent is required, the user is given one explicit action to authorize access; after successful consent, readiness can be rechecked without recreating the Project or Engineering Run.
- Advanced implementation details such as Vercel OIDC, installation tokens, connector IDs, or authorizationDetails remain secondary diagnostic information rather than primary UX.
- Existing Projects whose repositories are already authorized continue without a new prompt.

## 8. Acceptance criteria

### AC-01 Exact repository readiness
For a Project bound to `github:<owner>/<repo>`, Parallax can determine before source mutation whether the approved GitHub App / Connect installation covers that exact repository.

### AC-02 Explicit consent boundary
If the repository is not covered, Parallax returns `REPOSITORY_AUTHORIZATION_REQUIRED` and no source mutation occurs. Parallax does not silently broaden installation coverage.

### AC-03 Exact runtime token scope
When repository coverage exists, Vercel Connect issues a short-lived GitHub credential requested for exactly the Project repository, and Parallax independently verifies the resulting credential is scoped to exactly that repository.

### AC-04 Multi-repository installation remains safe
An explicitly owner-approved installation may cover more than one repository, but a runtime credential requested for Project A cannot read or mutate Project B's repository and fails scope verification if it can see more than the requested repository.

### AC-05 Existing registered Parallax target remains compatible
The current `Ryan9876/parallax` delivery path remains green and production preflight continues to verify exact derived-token repository scope.

### AC-06 No reusable credential expansion
No PAT, reusable GitHub installation token, Supabase secret, QA password, service-role credential, or broad runtime bearer is introduced or persisted.

### AC-07 Greenfield canonical bootstrap advances
After exact production deployment and required provider consent for `Ryan9876/sickbeard`, Engineering Run `a3a32343-507a-4384-a9bd-2fddaa0ce7fc` retries from PLAN without `CREDENTIAL_UNAVAILABLE` or `REPOSITORY_AUTHORIZATION_REQUIRED` and durably advances beyond revision 1. Any later independent failure is recorded separately.

### AC-08 W8-S2 acceptance
The same authenticated QA-owned canonical run must advance beyond the former missing-static-target PLAN failure with no `source_bootstrap_failed` caused by static Vercel target registration or missing GitHub repository authority before #377 may close.

### AC-09 Revocation remains effective
Removing repository coverage or revoking the GitHub App / Connect installation causes subsequent readiness/token exchange to fail closed without reusing cached or persisted credentials.

### AC-10 Auditability
Provider readiness decisions record non-secret evidence sufficient to identify Project, canonical repository, readiness result, and provider-side installation/connector identity where safe, while excluding raw credentials and tokens.
