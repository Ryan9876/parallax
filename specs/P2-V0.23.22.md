# Parallax 2.0 — P2-V0.23.22 Request-Bounded Autonomous Builds

Status: APPROVED FOR IMPLEMENTATION — SPEC-FIRST

Date: 2026-08-31
Workstream: #508
Architecture target: v3.33
Starting baseline: `325294d7d891939806c23f4065d1916cfb377ea5`

## 1. Objective

Make ordinary user-initiated Parallax builds complete reliably under the hosting runtime's finite request lifetime without weakening protected implementation validation, source-lineage authority, worker recovery, model-routing governance, delivery authority, or the human REVIEW ceiling.

The first real user build after the app-builder infrastructure work exposed a production defect. Engineering Run `3a1ba66a-5649-42b6-81ee-91684fe06bbc` entered the synchronous `/autonomous` route and remained inside one Vercel Function invocation for 300 seconds. Hosted implementation generation produced output-validation failures on Luna and Terra, continued toward Sol, and the platform terminated the request with HTTP 504 before protected coding completed. The durable run survived, but retrying the same synchronous lifecycle can repeat the same timeout.

This release fixes the observed failure at its two material causes: too much lifecycle work is coupled to one HTTP request, and implementation proposals are requested as JSON encoded inside a free string with hidden adapter/transport retry capacity rather than through the strongest available typed structured-output boundary.

## 2. Fixed decisions

- Preserve the canonical Engineering Run state machine and all existing stage-transition authority.
- Preserve the existing durable source-lineage, worker checkpoint, selected-candidate artifact, recovery, validation, delivery and REVIEW contracts.
- Production `/autonomous` invocations execute at most one protected lifecycle stage before returning authoritative server state to the client.
- PLAN executor preflight remains part of PLAN and does not count as a second lifecycle transition.
- After a bounded stage, the server must classify the resulting authoritative state before returning. If one stage reaches REVIEW, FAILED, PAUSED, CANCELLED or another existing stop boundary, return that boundary rather than an artificial `MAX_STEPS_REACHED` result.
- The client may automatically continue only from an authoritative returned revision that remains in an existing autonomous state. It must use a fresh deterministic revision-bound operation key for each subsequent request and enforce a finite client continuation bound.
- Implementation generation must use a typed DSPy structured-output contract backed by the existing closed Pydantic proposal schema. The existing server-owned semantic proposal validator, strict patch canonicalization, disposable candidate validation and final safe implementation engine remain authoritative.
- Explicit JSON structured output replaces JSON-as-text generation; it does not relax schema validation or permit unstructured fallback acceptance.
- Production hosted-model transport uses a finite server-owned per-call timeout and no hidden transport retry. Candidate recovery across admitted Luna/Terra/Sol identities remains the explicit governed retry mechanism.
- Do not introduce Vercel Queues, Workflows, a new background-worker persistence model, new credentials, or new provider authority in this release. Existing durable state is sufficient for request-to-request continuation of the observed lifecycle.
- Do not increase the Vercel Function duration as the primary remedy.
- Architecture advances to v3.33 because the production execution/request boundary and hosted structured-generation contract are durable runtime behavior.

## 4. Non-goals

- Replacing the Engineering Run state machine.
- Creating a second job queue, worker database, source store or checkpoint format.
- Replacing the existing durable worker lease/recovery subsystem.
- Increasing model count, candidate count, candidate-reassignment ceiling or competition budget.
- Accepting malformed, partial, prose-wrapped or otherwise invalid implementation proposals.
- Weakening exact acceptance coverage, safe patch rules, source-context binding, candidate BUILD/TEST/VERIFY, independent evaluation or canonical lineage acceptance.
- Changing GitHub/Vercel repository authorization, greenfield semantics, source-only handoff, Preview publication or production promotion authority.
- Completing REVIEW automatically.
- Solving every theoretical long-running validation ecosystem in one release. If an exact one-stage IMPLEMENT invocation still demonstrates a platform timeout after this correction, that measured evidence will authorize the next bounded execution decomposition rather than speculative infrastructure.
- Retrying the failed production run by fabricating a different specification or easier workload.

## 5. Required behavior

### 5.1 One protected lifecycle stage per production request

The ordinary production `/autonomous` route must compose its coordinator with `max_steps=1`.

A request starting in:

- PLAN may perform PLAN preflight/planning and persist only the PLAN transition;
- IMPLEMENT may perform the existing protected implementation operation and persist only the IMPLEMENT transition;
- BUILD, TEST or VERIFY may perform only that stage's existing protected execution and persist only that transition.

The API response contract remains `EngineeringAutonomyRead`; no synthetic client-owned state is introduced.

Internal/test compositions may retain an explicit larger bound where they intentionally exercise multi-stage behavior, but the production route must be pinned to one.

### 5.2 Correct stop classification at the step boundary

After consuming the configured step budget, `AutonomyCoordinator` must reload canonical run state and apply the existing terminal/stop classification before returning `MAX_STEPS_REACHED`.

This prevents a one-step VERIFY request from transitioning the run to REVIEW and then returning a non-REVIEW stop reason that would bypass the existing verified source-delivery hook.

No new stop reason is required.

### 5.3 Finite automatic client continuation

When one autonomy response returns `MAX_STEPS_REACHED` and its returned run is still an approved-spec-bound autonomous state, the client automatically submits the next request using that returned run revision.

Requirements:

1. update local run state after every successful response so authoritative progress is visible;
2. derive each continuation operation key from the newly returned run identity/revision rather than reusing an older mutation identity;
3. stop immediately when the returned run is no longer autonomously continuable or the server returns any stop reason other than `MAX_STEPS_REACHED`;
4. enforce a hard maximum of eight API autonomy requests for one client continuation sequence;
5. if the client bound is reached while the server still reports autonomous work, surface a normal retryable failure without changing server state;
6. do not automatically resume FAILED/PAUSED runs; existing explicit resume behavior remains authoritative.

The busy state may span the bounded continuation sequence, but run/progress state must be committed between requests.

### 5.4 Typed protected implementation output

`DspyImplementationGenerationProgram` must stop requesting one unconstrained `proposal_json: str` field.

The DSPy signature must expose typed output fields corresponding to the existing protected proposal contract, including exact acceptance IDs and typed generated patch objects. The invocation must use DSPy's JSON structured adapter so provider output is requested in machine-readable structured form when supported by the Vercel AI Gateway.

After DSPy returns:

- construct/validate the same `ImplementationProposal` Pydantic model;
- retain exact ordered acceptance validation in `validate_implementation_proposal`;
- retain all existing patch/source/candidate validation downstream;
- map structured-decoding/schema failures to the existing sanitized `ModelOutputValidationError` boundary;
- never persist or log rejected raw model output.

Provider/transport failures must remain provider failures rather than being mislabeled as schema failures.

### 5.5 Hosted model call budget

For production hosted OpenAI models routed through Vercel AI Gateway, `build_lm` must apply:

- a fixed 60-second model-call timeout;
- zero hidden transport retries.

Explicit local/development DSPy overrides retain their existing development policy. The explicit admitted candidate recovery sequence remains responsible for trying another hosted model when protected candidate generation rejects an attempt.

The timeout/retry constants are server-owned and not user-controlled. Timeout/provider failure cannot be converted to implementation success.

### 5.6 Existing durable recovery remains authoritative

Request segmentation does not create new source or worker authority. A later request always reloads canonical Engineering Run state, exact current lineage and any existing durable worker/candidate checkpoint through the established runtime composition.

Revision conflicts remain fail-closed. Duplicate operation keys remain subject to existing replay/idempotency behavior. A client refresh may continue only from server-returned state.

## 6. Security and reliability

The change reduces request lifetime without reducing validation depth. Stage segmentation occurs at existing authoritative state transitions; it does not move authority to the browser. The client can request continuation but cannot claim that a stage passed, choose a source lineage, bypass a failed stage, select arbitrary provider credentials, or complete REVIEW.

Typed structured model output strengthens the provider/output boundary. The provider still proposes non-authoritative source patches; Pydantic schema validation, exact acceptance ownership, strict patch verification/canonicalization, disposable candidate validation, independent evaluation and the canonical implementation writer remain server-owned.

The hosted model timeout is a resource/reliability bound only. A timeout is a failed provider attempt. Zero hidden transport retries prevents one logical admitted-agent attempt from silently multiplying provider calls inside a request. Explicit server-owned candidate recovery remains finite and observable.

The eight-request client cap prevents accidental infinite request chaining if server state does not progress. Because every continuation is revision-bound and canonical state is reloaded by the server, a dropped client connection or refresh cannot fabricate progress and can safely re-enter through the existing latest-run path.

No new secret, queue credential, persistent token, provider capability, Git authority, deployment authority or production-promotion authority is introduced.

## 7. Acceptance criteria

### AC-01 Production autonomy is one-stage bounded
Focused route/runtime tests prove one `/autonomous` invocation can persist no more than one PLAN/IMPLEMENT/BUILD/TEST/VERIFY transition under production composition.

### AC-02 Step exhaustion preserves real stop boundaries
A coordinator with `max_steps=1` that advances VERIFY into REVIEW returns `REVIEW_REQUIRED`, allowing the existing verified delivery path to run. Equivalent existing terminal boundaries are classified before `MAX_STEPS_REACHED`.

### AC-03 Client safely chains authoritative revisions
Client tests prove `MAX_STEPS_REACHED` causes a next request only from the newly returned authoritative revision, progress state is applied between calls, terminal/human stop reasons stop chaining, and no more than eight requests occur.

### AC-04 Typed structured generation replaces JSON-as-text
Implementation-generation tests prove the production DSPy signature/adapter consumes typed acceptance/patch fields, valid structured output becomes the existing `ImplementationProposal`, and invalid typed/schema output fails through sanitized `ModelOutputValidationError` without raw output persistence.

### AC-05 Strict proposal authority is unchanged
Exact ordered acceptance coverage and downstream safe patch/candidate validation remain unchanged; malformed or semantically invalid proposals are still rejected.

### AC-06 Hosted model calls are finitely bounded
Focused model-transport tests prove production hosted Gateway models receive a 60-second timeout and zero transport retries, while existing local-development behavior remains intact.

### AC-07 Failure and replay semantics remain truthful
Revision conflicts, provider failures, output-validation failures, failed implementation recovery, worker checkpoint authority, source-lineage identity, delivery authority and the REVIEW ceiling retain their existing fail-closed behavior.

### AC-08 Full regression gates pass
Protected spec validation, committed DSPy plan validation, applicable API/client tests, Bounded Autonomy, protected promotion evaluation and full exact-head PR gates pass.

### AC-09 Production 504 regression is behaviorally disproven
After exact-source production deployment, a real or bounded production-QA app-building run progresses beyond the previous synchronous model-routing point without a 300-second `/autonomous` timeout. The exact same user run may be resumed when principal access permits; otherwise an equivalent production-bound workload must exercise typed generation and request-to-request continuation. A synthetic unit test alone is insufficient for deployment verification.

## 9. Rollback

Rollback restores the previous multi-stage-per-request production composition, one-call client behavior and prior DSPy proposal string transport only if the new release introduces a more severe regression. No database migration or persisted schema change is required.

Because server state transitions and worker/source persistence formats are unchanged, runs created during v3.33 remain readable by the prior runtime. A rollback must not discard durable runs, lineage, worker checkpoints or selected-candidate artifacts. Production rollback must use an exact previously deployment-verified application source and re-run health/readiness verification.
