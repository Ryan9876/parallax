## 1. Objective

Make ordinary user builds recover from one final safe-validator rejection without weakening the protected implementation boundary or reintroducing the production request timeout fixed by P2-V0.23.22.

The production retry of Engineering Run `3a1ba66a-5649-42b6-81ee-91684fe06bbc` on P2-V0.23.22 no longer timed out at the HTTP layer. Instead, IMPLEMENT exhausted the admitted candidate set: Luna hit the server-owned 60-second model timeout, Terra returned a parsed proposal rejected by the server-owned safe proposal validator, and Sol received the existing validator-guided repair constraint but its parsed proposal was also rejected. The request returned HTTP 200 and the durable run failed safely with `AUTONOMOUS_IMPLEMENT_FAILED`; no canonical source mutation, lineage acceptance, Git mutation, deployment mutation, or REVIEW completion occurred.

The remaining reliability defect is that validator-guided repair is available only while a distinct untried admitted agent remains. Once all distinct agents are exhausted, a validator-rejected model that could repair its own structured proposal gets no final bounded repair opportunity.

## 2. Fixed decisions

- `SafeImplementationEngine`, `CanonicalizingTextPatchEngine`, source-context authority, exact acceptance coverage, disposable candidate validation, independent evaluation, canonical lineage acceptance, Git/deployment authority, and the human REVIEW ceiling remain authoritative and unchanged.
- Provider-only failures do not gain validator-specific retry authority.
- A candidate attempt classified `VALIDATION_EXHAUSTED` may authorize exactly one additional validator-guided repair attempt for the same work unit after distinct admitted agents are otherwise exhausted.
- The repair attempt reuses only an already-admitted implementation agent identity that previously returned `VALIDATION_EXHAUSTED`; it does not add a new provider, model, credential, capability, tool, source, or network authority.
- The selected repair agent is deterministic: use the most recent validator-rejected admitted agent for that work unit.
- The repair attempt increments the work-unit generation and receives the existing static `VALIDATOR_REPAIR_GUIDANCE` before generation.
- The repair retry is bounded by a server-owned constant of one per work unit. It is not counted as worker-loss reassignment and cannot loop.
- If the one repair retry also fails, the existing fail-closed candidate-exhaustion path remains authoritative.
- Do not increase hidden transport retries or the per-model 60-second timeout.
- Architecture advances to v3.34 because the finite candidate-recovery policy changes durably.

## 5. Required behavior

### 5.1 Validation-only final repair eligibility

For a work unit, candidate recovery continues to try distinct admitted agents under the existing deterministic eligible-agent ordering. If a candidate generation fails with bounded routing reason `VALIDATION_EXHAUSTED`, record only that bounded failure kind and the admitted agent identity digest.

When no untried distinct admitted agent remains, the runtime may synthesize one final repair assignment only when all of the following hold:

1. at least one candidate rejection for the work unit has failure kind `VALIDATION_EXHAUSTED`;
2. no validator-repair retry has already been consumed for the work unit;
3. the chosen agent identity is already present in the plan's admitted eligible-agent set;
4. the chosen identity is the most recent validator-rejected identity;
5. the generated assignment increments the prior work-unit generation and uses a server-owned reason code `CANDIDATE_VALIDATION_REPAIR`.

If these conditions are not met, candidate recovery must exhaust exactly as before.

### 5.2 Static repair guidance

The final repair request must pass through `validator_guided_candidate_request(..., VALIDATION_EXHAUSTED)` so it receives the existing static safe-patch guidance. No rejected candidate text or arbitrary exception content may be included.

### 5.3 Finite budget

The final repair budget is exactly one per work unit. A second validation failure after that retry must fail closed. Provider failures during the repair consume the repair attempt and do not authorize another one.

The existing provider call timeout remains 60 seconds and hidden transport retries remain zero. The new retry adds at most one hosted model call to the IMPLEMENT candidate-generation phase.

### 5.4 Bounded diagnostics

The candidate-generation exhaustion diagnostic envelope may add only server-owned fields proving whether a final validator repair was attempted and its bounded agent/generation identity. All existing false mutation/authority claims remain false. No raw candidate output or validation message is included. Whether that envelope is projected into the separate durable ImplementationRuntime failure schema remains governed by its existing owner and is not changed here.

## 6. Security and reliability

The repair attempt is proposal generation only. It cannot mutate canonical source, accept lineage, publish Git content, deploy an application, transition REVIEW, or claim a protected stage pass. Its output is processed by the exact same Pydantic proposal schema, exact acceptance ownership check, safe patch validator/canonicalizer, disposable candidate BUILD/TEST/VERIFY, independent evaluation, canonical implementation writer, and durable lifecycle authority as every other candidate.

Retry eligibility derives only from server-owned admitted plan identity and the bounded `VALIDATION_EXHAUSTED` classification. Provider failure, rate limiting, worker loss, arbitrary exception text, or user/model claims cannot authorize the extra repair attempt.

The one-repair ceiling prevents hidden retry multiplication. If the extra attempt does not produce a safe proposal, the run remains failed and resumable under the existing human recovery contract.

## 7. Acceptance criteria

### AC-01 Production failure shape is correctly diagnosed
Regression evidence encodes the observed sequence of one provider failure followed by safe-validator rejection(s) without converting provider failure into validator failure.

### AC-02 Final validator repair becomes available
When distinct admitted agents are exhausted and a validator rejection exists, exactly one deterministic same-agent repair assignment is produced for the most recent validator-rejected admitted agent.

### AC-03 Provider-only exhaustion remains unchanged
If all failures are provider/rate-limit failures, no final validator repair assignment is produced.

### AC-04 Existing guidance is reused
The final repair request receives `VALIDATOR_REPAIR_GUIDANCE` and no rejected model output or arbitrary validator exception text.

### AC-05 One-repair ceiling is enforced
A work unit cannot receive more than one final validator repair retry, including when that retry itself times out or returns another rejected proposal.

### AC-06 Authority remains unchanged
The repair assignment grants no canonical source, lineage, Git, deployment, REVIEW, credential, network, or lifecycle-transition authority.

### AC-07 Exhaustion diagnostics remain bounded
If repair still fails, the candidate-generation diagnostic envelope exposes only bounded failure kind, admitted identity/generation, repair-attempted state, and existing false mutation/authority claims. No durable diagnostic-schema expansion is required by this release.

### AC-08 Success path remains unchanged
A candidate that passes before distinct-agent exhaustion follows the existing path without a final repair attempt.

### AC-09 Regression gates pass
Focused candidate-recovery tests, full API regression, Bounded Autonomy, client checks, protected promotion evaluation, protected spec/plan validation, and required DSPy validation pass on the exact PR head.

### AC-10 Production behavior is verified
After exact-source deployment, `/health` and `/ready` return HTTP 200 and the affected production run or an equivalent bounded workload proves that a final validator-rejected candidate no longer fails solely because the distinct-agent set was exhausted before one bounded repair retry.
