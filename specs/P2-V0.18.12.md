# Parallax 2.0 — Safe Deletion Hardening

Spec ID: P2-V0.18.12
Status: APPROVED FOR IMPLEMENTATION
Date: 2026-08-27
Workstream: #290 / `WS-SAFE-DELETION`
Base: `a6d7a6fd4d556d5544ede9c43b93972a8c590011`

## 1. Objective

Harden the already merged safe conversation/Project deletion release before it is accepted as deployment-verified. Correct two post-merge audit gaps without broadening the feature: (1) deletion must use the authoritative protected Engineering Run terminal-state contract rather than an independently duplicated subset, and (2) historical unbound conversations must not inherit compatibility read visibility as destructive delete authority for non-owner users.

The production database migration and logical-deletion product model remain unchanged.

## 2. Evidence driving this correction

PR #291 merged as `a6d7a6fd4d556d5544ede9c43b93972a8c590011` and automatically produced READY production deployments for both API and client. The database migration had already been applied successfully.

Post-merge audit found:

1. conversation/project repositories define terminal deletion states locally as only `COMPLETE` and `CANCELLED`, while the authoritative protected runtime defines `TERMINAL_STAGES = {COMPLETE, SPEC_AMENDMENT, CANCELLED}`. This can incorrectly block deletion for a run already in terminal `SPEC_AMENDMENT`.
2. historical unbound conversations are readable through an intentional compatibility path because they predate canonical Project ownership. The new DELETE route currently reuses that same broad read path, which could let a non-owner authorized user delete an unbound historical conversation despite the absence of durable per-conversation ownership identity.

These defects must be corrected before the release is called deployment-verified.

## 3. Scope

- derive deletion terminal-state checks from `parallax_api.code.domain.TERMINAL_STAGES` or an equivalent single authoritative import, never from a second handwritten lifecycle list;
- preserve `FAILED` as non-terminal under the existing protected runtime contract;
- allow `COMPLETE`, `SPEC_AMENDMENT`, and `CANCELLED` runs to stop blocking logical deletion;
- preserve existing Project-bound conversation ownership checks through canonical Project owner identity;
- require application `owner` role to logically delete a historical unbound conversation because those compatibility rows do not carry per-conversation ownership identity;
- preserve member/non-owner ability to read historical unbound conversations exactly as before unless a separate approved ownership migration changes that compatibility contract;
- keep Project deletion ownership semantics unchanged: the authenticated principal must still own the canonical Project row;
- add focused tests for terminal-state parity and destructive authorization;
- keep all existing tombstone persistence, active list/read filtering, Project identity reuse, client confirmation UX and external-resource preservation unchanged.

## 4. Non-goals

- redesigning historical conversation ownership;
- adding `owner_subject` to conversations;
- changing read visibility for historical unbound conversations;
- changing Engineering Run lifecycle semantics;
- changing Project ownership or role models;
- hard purge, restore, bulk delete, automatic retention or archive scheduling;
- changing GitHub/Vercel provider resources;
- changing Work Specification, source-lineage, worker, validation, REVIEW/HUMAN_REQUIRED, merge or production authority;
- changing Wave 6 semantics.

## 5. Security and authority

Compatibility read access is evidence visibility, not destructive authority. A historical unbound conversation has no canonical Project from which Parallax can derive per-user ownership, so DELETE must fail closed for any authenticated principal whose application role is not `owner`.

Project-bound conversations remain owner-scoped by canonical Project identity; cross-owner reads/deletes continue to return not found and must not reveal ownership metadata.

No caller/model/provider input may redefine terminal Engineering Run states. The deletion guard consumes the same server-owned `TERMINAL_STAGES` contract used by the protected runtime.

## 6. Acceptance criteria

### AC-01 Authoritative terminal-state source
Conversation and Project deletion guards derive their terminal-state set from the protected runtime `TERMINAL_STAGES` contract rather than maintaining an independent handwritten lifecycle list.

### AC-02 SPEC_AMENDMENT is terminal for deletion
A conversation or Project whose relevant Engineering Runs are in `SPEC_AMENDMENT` is not blocked by the active-run deletion guard, matching the protected runtime's terminal-state contract.

### AC-03 FAILED remains non-terminal for deletion
A relevant Engineering Run in `FAILED`, `REVIEW`, `PLAN`, or any other state outside `TERMINAL_STAGES` blocks deletion with HTTP 409. A failed attempt or run failure signal does not fabricate terminal completion.

### AC-04 No independent lifecycle drift
Focused tests bind deletion behavior to the protected runtime contract and fail if deletion logic silently drops a protected terminal state or independently adds a non-terminal state without the corresponding runtime contract changing.

### AC-05 Historical unbound destructive authority
An authenticated non-owner user cannot DELETE a historical unbound conversation and receives HTTP 403 without mutation. An authenticated application owner can delete the same kind of historical unbound conversation, subject to the ordinary active-run guard. Existing compatibility read visibility is unchanged.

### AC-06 Project-bound ownership remains fail-closed
A user who does not own the canonical Project cannot delete its bound conversation or the Project. Existing not-found behavior is preserved and no cross-owner metadata is disclosed.

### AC-07 Existing logical-deletion and evidence behavior remains intact
Successful logical deletion still returns 204, active list/read surfaces hide tombstoned data, protected Work Specification/Engineering Run/evidence rows remain persisted, deleted Project slug/repository identity remains reusable, and no GitHub/Vercel delete call is introduced.

### AC-08 Client failure handling remains server-authoritative
Existing desktop and compact/mobile deletion controls continue to remove local active state only after API success. HTTP 403, 409, 404, and other safe server details are surfaced through the existing bounded deletion error path without client-side authorization guesses or false success.

### AC-09 Regression protection
Existing deletion tests plus authentication, Project binding, Work Specification, Engineering Run, client typecheck/response-state/export and Bounded Autonomy checks remain green. No provider, source-lineage, worker, evaluation, REVIEW/HUMAN_REQUIRED, merge, or deployment authority changes.

### AC-10 Governed corrective release
The exact corrective head passes Workstream Spec Validation, Bounded Autonomy and P2 CI; merge uses expected-head protection; production API/client promotion is tied to the merged corrective SHA; `/health`, `/ready`, runtime-error scans and authenticated deletion behavior are verified before #290 is closed and `CURRENT-STATE.md` is reconciled.
