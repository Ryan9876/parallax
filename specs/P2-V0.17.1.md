# Parallax 2.0 — Wave 4 Durable Run-Event Telemetry

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.17.1
Workstream: WS-W4-RUN-EVENTS / GitHub issue #145
Base: main@97886b4437e5c5ab4aab4c18820ef76db8717e4a
Depends on: integrated P2-V0.17.0 and deployed Wave 3 protected runtime
Method: append-only observation projection over existing authoritative runtime state

## 1. Objective

Add one durable, append-only, Project/run-scoped event projection that records meaningful observable actions from the existing Wave 3 app-builder without creating another Engineering Run, worker, source-lineage, provider or evaluation state machine.

The event record is the future data source for Wave 4 Live Development/Observability. It must preserve exact authoritative identities and enough bounded context to explain what happened, when, at which protected stage, against which source lineage/attempt/subsystem and whether the observation was new, replayed, failed, recovered or human-blocked. It must never contain raw private source, unrestricted logs, credentials, raw provider payloads, prompts/scratchpads or hidden reasoning.

## 2. Scope

- Add the durable `engineering_run_events` table through one explicit migration.
- Add typed run-event domain contracts and an event-sink interface.
- Add an append-only repository/service using stable event identity plus monotonic per-run sequence.
- Instrument existing Wave 3 authoritative service/runtime boundaries through the narrow sink.
- Record stage lifecycle, attempts, source-lineage transitions, bounded execution/provider/evaluation references, replay/retry/failure/recovery/human-boundary observations when those facts are available at the integration seam.
- Prove process recreation, duplicate emission and replay do not create duplicate accepted event identities.
- Preserve all existing Wave 3 transition/mutation/evaluation behavior and tests.

Public live streaming, source/diff read APIs and client UI are out of scope and owned by later Wave 4 workstreams.

## 3. Fixed decisions

- **Projection only.** Existing Engineering Run, attempt, worker, source-lineage, provider and evaluation records remain authoritative.
- **Append-only replay safety.** `(run_id,event_key)` is deterministic and idempotent; accepted sequence is positive and monotonic per run.
- **Canonical scope.** New telemetry requires exact canonical `project_id` + `run_id`; historical unbound runs cannot gain Wave 4 authority.
- **Privacy bounded.** Events may carry safe identities/digests/codes and short allowlisted metadata, never raw source/log/provider bodies, prompts, reasoning, credentials or environment.
- **Failure truthfulness.** Event persistence cannot turn runtime failure/denial into success, and conflicting replay fails closed.
- **Server-owned sink.** Production composition injects the sink; clients/models receive no arbitrary event-append or generic logging surface.

## 4. Architecture requirements

Use one additive `engineering_run_events` table plus frozen event contracts, an append-only repository/service and a narrow `RunEventSink`. Database constraints are final authority for `(run_id,event_key)` and `(run_id,sequence)`. Existing services emit only after authoritative facts exist; telemetry never causes a stage/worker/provider/source transition. The repository exposes bounded ascending reads by exact run and `after_sequence` for #146. Production Project-bound autonomy must persist configured Wave 4 events rather than silently discard them.

## 5. Detailed event contract

### 5.1 Durable model

`engineering_run_events` contains at minimum:

- `id` — opaque durable UUID;
- `project_id` — canonical Project UUID, indexed;
- `run_id` — Engineering Run foreign key, indexed;
- `sequence` — positive integer, unique with `run_id`;
- `event_key` — bounded deterministic idempotency key, unique with `run_id`;
- `event_type` — bounded event enum/value;
- `stage` — optional protected Engineering Run stage;
- `outcome` — bounded state such as STARTED / PROGRESSED / SUCCEEDED / FAILED / DENIED / REPLAYED / RECOVERING / HUMAN_REQUIRED / INFO;
- `subsystem` — bounded source such as RUN / IMPLEMENTATION / EXECUTION / WORKER / SOURCE_LINEAGE / GITHUB / VERCEL / EVALUATION / REVIEW;
- optional `attempt_id`, `worker_execution_id`, `source_lineage_ref`, `parent_source_lineage_ref`, `operation_ref`, `artifact_ref`, `evidence_ref`, `failure_code`;
- optional bounded `summary` and allowlisted `metadata_json`;
- `occurred_at` plus durable `created_at`.

No event field stores credentials, headers/cookies/environment, prompt/scratchpad, raw provider response, unrestricted command output or raw source.

### 5.2 Sequence allocation

Per-run sequence allocation is database-authoritative. The repository must serialize/compare-and-swap sequence allocation sufficiently to prevent duplicate sequence acceptance under concurrent appends. SQLite tests may use transaction/retry behavior appropriate to development; PostgreSQL production semantics must retain unique constraints as the final authority.

A collision on deterministic `event_key` resolves to the existing identical event when its protected identity/content matches. A conflicting reuse of the same key with materially different identity/content fails closed.

### 5.3 Typed event contract

A frozen `RunEvent` / `RunEventAppend` contract validates:

- canonical UUID Project/run identity;
- bounded event key/type/subsystem/outcome/stage;
- safe optional lineage IDs/digests/references;
- maximum summary and metadata sizes;
- metadata key allowlist and scalar/list value types;
- rejection of obvious secret-bearing keys/values and raw-source/log/provider fields.

The public representation contains only the bounded contract.

### 5.4 Sink interface

Runtime code depends on a small interface such as `RunEventSink.emit(event) -> persisted event`. Production composition injects a persistent sink. Focused tests may inject a deterministic in-memory/recording sink.

No-op behavior is permitted only for deliberately legacy/test composition where Wave 4 event persistence is not part of the asserted production route. The production Project-bound autonomous route must not silently discard configured Wave 4 events.

### 5.5 Stage and attempt projection

The Engineering Run service emits meaningful events only after it has authoritative facts to describe. Examples:

- stage started / attempt created;
- stage passed or failed with exact attempt ID;
- pause/resume/cancel/spec-amendment/review boundary where available;
- replayed operation where the service resolves an existing attempt.

The event does not cause the state transition and cannot substitute for `complete_stage` validation.

### 5.6 Implementation/source-lineage projection

The protected IMPLEMENT/runtime composition may emit:

- implementation proposal/validation started or completed where a stable authoritative seam exists;
- accepted source-lineage transition with exact prior/result lineage identity and safe file/digest summary;
- rejected/stale mutation outcome;
- correction candidate/LKG change when Wave 3 exposes the authoritative fact.

Event data references lineage identity rather than embedding source bytes.

### 5.7 BUILD/TEST/VERIFY projection

Registered protected execution can emit start/completion/failure observations tied to exact stage, attempt, source lineage, command identity and bounded evidence/artifact reference. Raw stdout/stderr is not copied to this table; later read surfaces resolve already-bounded execution evidence.

### 5.8 Provider/evaluation/review projection

Where runtime composition receives accepted provider/evaluation results, events may record safe GitHub branch/commit/PR identity, Vercel Preview identity/status, evaluation identity/score class and REVIEW/HUMAN_REQUIRED boundary. Provider success never substitutes for stage/evaluation authority.

### 5.9 Worker recovery projection

When integrated at an authoritative worker service boundary, record meaningful `CHECKPOINTED`, `STALLED`, `RECOVERING`, `REASSIGNED`, `HUMAN_REQUIRED`, `READY_FOR_INTEGRATION` observations with exact execution/generation/checkpoint/lineage references. Heartbeat/lease-renewal chatter is not a product event unless needed to explain a material state transition.

### 5.10 Query seam for later transport

The repository/service exposes bounded reads by exact run with `after_sequence` and `limit`, sorted ascending. #145 does not add the external authenticated HTTP/SSE route; #146 consumes this seam.

## 6. Security and privacy

- Event append is internal server composition only; no model/client arbitrary append API.
- Canonical Project/run mismatch fails before persistence.
- Cross-Project event association is rejected even if the run ID exists.
- Metadata rejects keys implying token, secret, password, authorization, cookie, credential, environment, prompt, reasoning, scratchpad, raw provider payload, source content or unrestricted log data.
- Metadata values are bounded and recursively limited to safe primitives / short primitive lists; arbitrary objects/blobs are rejected.
- Summaries are bounded and scrub obvious credential-like material; production producers should prefer fixed templates over provider exception text.
- Secret-sensitive source paths may be referenced only if the existing source policy explicitly permits safe identity display; source content is never persisted here.
- Evidence links/URLs are not arbitrary. Provider/event producers persist opaque IDs or existing safe bounded URLs already accepted by the provider contract.
- Database RLS/direct-client privilege posture follows the existing server-owned control-plane pattern: FastAPI is the application authorization boundary and direct `anon` / `authenticated` mutation is not granted.

## 7. Failure and recovery boundaries

- Duplicate identical `(run_id,event_key)` append returns/replays the existing event without a new sequence.
- Duplicate conflicting event key fails closed.
- Unique sequence races retry only within a small bounded database retry; they do not fabricate sequence gaps as completed events.
- Database append failure is surfaced as telemetry persistence failure; no event success is fabricated.
- Process recreation reconstructs the repository/sink and continues from durable max sequence.
- Missing prior events are not synthesized from guessed state. A later snapshot event may describe current authoritative state explicitly, but historical timestamps/actions are never invented.
- A runtime replay records `REPLAYED` only when the underlying authoritative service says it replayed/resolved prior work.
- Provider/runtime failures retain failure/denial status and safe code; raw exception text is not persisted.
- Event consumers can tolerate a sequence gap caused by rolled-back allocation; they cannot treat sequence continuity as engineering success.

## 8. Non-goals

- replacing Engineering Run attempts or worker checkpoints with an event-sourced runtime;
- implementing a message broker or external observability vendor;
- adding public SSE/WebSocket routes in this workstream;
- storing raw source files/diffs in event rows;
- storing raw stdout/stderr, DOM/screenshots, provider payloads, prompts or reasoning;
- adding generic log append, shell, filesystem, HTTP or provider authority;
- changing existing stage acceptance/evaluation thresholds;
- production deployment, migration application or credential/storage provisioning from the worker branch.

## 9. Acceptance criteria

### AC-01 Durable append-only model is Project/run scoped
An explicit migration creates `engineering_run_events` with canonical Project/run binding, stable event identity, per-run sequence, timestamps, bounded event fields and database constraints. Existing authoritative runtime tables remain unchanged in meaning.

### AC-02 Event contract is typed and privacy bounded
Run-event construction validates canonical identity, event/stage/outcome/subsystem vocabulary, bounded summaries/references and allowlisted metadata while rejecting raw source, unrestricted logs/provider payloads, credentials, prompts/scratchpads and hidden reasoning.

### AC-03 Idempotent replay uses deterministic event identity
Appending the same exact `(run_id,event_key)` observation returns the accepted existing event without allocating another sequence; reuse with conflicting protected content fails closed.

### AC-04 Per-run ordering is monotonic and durable across process recreation
Accepted events receive positive increasing per-run sequence values enforced by database constraints. Reconstructed repositories/sinks continue after the durable maximum and bounded `after_sequence` reads return stable ascending order.

### AC-05 Stage/attempt events reflect authoritative service results only
Engineering Run stage start/completion/failure/replay/control observations are emitted only around existing validated service transitions and carry exact attempt/replay/failure facts; events cannot advance or satisfy a stage themselves.

### AC-06 Source-lineage and implementation events preserve exact lineage identity without source bytes
When IMPLEMENT/correction/runtime composition exposes accepted lineage transitions, events carry exact prior/result lineage and bounded artifact/path/digest identity only. Raw source content is absent and stale/rejected mutation is never represented as accepted lineage.

### AC-07 BUILD/TEST/VERIFY observations reference protected execution evidence
Execution events bind to exact run/stage/attempt/source lineage and registered command/evidence identity. Raw unrestricted stdout/stderr is not persisted in the event table, and failure/timeout/redaction remains truthful.

### AC-08 Provider/evaluation/review observations remain non-authoritative and secret safe
Safe GitHub/Vercel Preview/evaluation/REVIEW identities/status may be projected from accepted runtime results, while provider failure/denial and human boundaries remain explicit. No raw provider body, credential or production-promotion authority is introduced.

### AC-09 Worker recovery events project the accepted worker protocol without creating another worker state machine
Meaningful checkpoint/stall/recovery/reassignment/human/integration transitions can be observed with exact worker execution/generation/checkpoint/lineage references; telemetry cannot acquire/renew/reassign a worker or validate stale ownership.

### AC-10 Event persistence and runtime failure cannot be misrepresented as success
Database/sink failure, conflicting replay, invalid metadata or identity mismatch fails explicitly. Existing runtime failure/denial remains failure/denial and event recording cannot convert it to success.

### AC-11 Permanent tests prove replay, concurrency boundaries, privacy and process recreation
Deterministic tests cover ordered append/read, duplicate identical replay, conflicting key, wrong Project, secret/raw-field rejection, process recreation continuing sequence and runtime integration without duplicate mutation/attempt/provider semantics.

### AC-12 Exact-head Wave 3 gates remain green
The final candidate has authentic committed DSPy plan evidence and passes Workstream Spec Validation, Parallax P2 CI and Bounded Autonomy on the exact head with existing Wave 3 protected reference/recovery/evaluation suites unchanged or stronger. The worker stops review-ready before merge, migration application or deployment.

## 10. Release gate

Before #145 is READY FOR INTEGRATION, AC-01 through AC-12 must be implemented and deterministically tested; the migration must be additive and reversible; the event projection must remain non-authoritative, privacy bounded and replay-safe; authentic DSPy SpecCritic/SpecCompiler evidence must be committed; the final branch must be current with its accepted base and pass Workstream Spec Validation, P2 CI and Bounded Autonomy on the exact final head. No production migration or deployment occurs from this worker workstream.
