# Parallax 2.0 — Structured-Output Validation Classification

Status: APPROVED FOR IMPLEMENTATION — SPEC-FIRST
Spec ID: P2-V0.23.15
Date: 2026-08-30
Workstream: #488
Architecture target: v3.28

## 1. Objective

Make hosted implementation-generation routing telemetry truthful when a provider call succeeds but the returned structured proposal cannot be decoded into Parallax's protected `ImplementationProposal` schema. Such failures are model-output validation failures, not provider/transport failures.

## 2. Triggering production evidence

Authenticated production replay `33336924912` on current OT Time source proved the released hosted order is correctly `Luna -> Terra -> Sol`, but also exposed a classification defect:

- Luna was invoked first through Vercel AI Gateway;
- LiteLLM reported the provider call completed;
- `ImplementationProposal.model_validate_json(...)` then raised a Pydantic `ValidationError` while decoding the model's structured proposal;
- the generic router exception boundary recorded that attempt as `provider_failed`;
- later bounded fallback continued to Terra and Sol and the run ultimately reached REVIEW.

The existing router currently treats every exception raised by the model-attempt function as a provider failure. That is correct for transport/configuration/rate-limit/provider exceptions, but incorrect for deterministic protected output/schema validation performed after a successful provider response.

## 3. Fixed decision

Introduce one bounded server-owned exception class representing structured model-output validation failure.

- The implementation-generation program catches only protected proposal decoding/schema-validation failures and re-raises the bounded output-validation exception without raw model output.
- `ModelRouter` catches that exception before its generic provider boundary and records the attempt as `validation_failed`.
- The ordinary validator returning `False` remains `validation_failed` exactly as today.
- All other attempt exceptions remain `provider_failed` and retain only sanitized exception-class evidence.
- When all configured attempts fail through either structured-output validation or ordinary protected validation, routing classification remains `VALIDATION_EXHAUSTED`.
- An all-rate-limit provider chain remains `RATE_LIMITED`.
- Mixed provider and validation failures remain `PROVIDER_EXHAUSTED`; this release does not invent a new mixed-outcome authority.

No raw model output, provider payload, validation message, repository text, secret, or arbitrary exception text becomes durable diagnostic evidence.

## 4. Prompt-quality correction

The implementation proposal output field will carry a more explicit fixed server-owned JSON contract describing the exact top-level keys and patch-entry keys already enforced by `ImplementationProposal`.

This is guidance only. It does not relax parsing, accept Markdown wrappers/prose, repair malformed JSON, add fields, alter required acceptance coverage, or bypass the existing safe-patch validator. The parser remains strict and fail-closed.

## 5. Scope

- Hosted model order remains `Luna -> Terra -> Sol`.
- Agent-team selection priority, candidate-recovery ordering and reassignment ceilings remain unchanged.
- Work Specification, source-context, exact-path/digest binding, strict unified-diff validation, candidate validation, canonical mutation, source lineage, Git/provider/deployment authority and REVIEW boundaries remain unchanged.
- No database migration and no public API field is introduced.
- Browser/user text, repository content and model output cannot choose the classification.
- The output-validation exception carries no raw output or protected validation details.

## 6. Acceptance criteria

### AC-01 Structured proposal decode failure is validation
A provider-successful attempt whose proposal fails `ImplementationProposal` JSON/schema decoding is recorded as `validation_failed`, not `provider_failed`.

### AC-02 Provider failures remain provider failures
Transport, configuration, rate-limit and unrelated program exceptions remain `provider_failed` with only sanitized exception-class evidence.

### AC-03 Validation exhaustion remains correct
If every configured model attempt ends in structured-output validation failure or ordinary protected validation rejection, the resulting routing failure is `VALIDATION_EXHAUSTED`.

### AC-04 Rate-limit exhaustion remains correct
If every configured model attempt fails as `provider_failed / LMRateLimitError`, the routing failure remains `RATE_LIMITED`.

### AC-05 Mixed outcomes remain conservative
A route containing both provider failures and validation failures remains `PROVIDER_EXHAUSTED` rather than inferring a more specific cross-provider conclusion.

### AC-06 No raw output persistence
Bounded implementation-generation diagnostic evidence continues to persist only status, provider kind and provider error class where applicable. Raw model output and provider payloads remain absent.

### AC-07 Prompt contract is stricter, parser is not looser
The fixed implementation proposal prompt explicitly names the exact JSON keys already enforced by the protected schema. No Markdown stripping, JSON repair, prose extraction or permissive fallback parser is added.

### AC-08 Authority remains unchanged
No source mutation, candidate validation, lineage, Git, deployment, approval, worker, Engineering Run transition or REVIEW authority changes.

### AC-09 Regression suite remains green
Focused router/generation regressions plus the full protected API, client/browser, promotion, Bounded Autonomy and DSPy release gates pass on the exact candidate head.

### AC-10 Production telemetry is truthful
After exact-source deployment, an authenticated production replay proves Luna-first hosted selection and, if a structured-output decode failure occurs, records it as validation rather than provider failure. A clean Luna success also satisfies this criterion by demonstrating the corrected path does not regress normal execution.

## 7. Security and reliability

The distinction is derived only from a typed server-owned exception emitted by protected proposal decoding. Generic exception text is not inspected and exception strings do not influence control flow. This prevents arbitrary provider/model text from manufacturing validation authority while keeping provider failures separately observable.

The prompt-quality change is fixed application code. It does not accept new syntax or widen output authority; strict Pydantic schema validation and the downstream safe-patch validator remain mandatory.

## 8. Non-goals

- Changing model order or pricing policy.
- Adding same-model retries.
- Persisting raw invalid model output for debugging.
- Automatic JSON repair or Markdown/prose extraction.
- Relaxing exact acceptance coverage or source patch validation.
- Changing candidate-recovery or worker-recovery ceilings.
- Client UX changes.
