## 1. Objective

Make protected BUILD/TEST/VERIFY execution appropriate to the canonical application repository without allowing a model, operator, prompt, repository script, or deployment provider to choose arbitrary executable commands.

Production P2-V0.23.4 verification proved that public `Ryan9876/ot-time` can bootstrap and advance beyond PLAN without Vercel Connect repository authorization. Its IMPLEMENT candidate then failed protected validation because the current `ProtectedCommandRegistry` always runs Parallax's own Python compile/pytest commands. OT Time is a .NET solution (`OtTime.sln`), so the generic lifecycle is correct but the execution profile is wrong.

## 2. Fixed decisions

- Protected executable commands remain finite, server-owned release code.
- Models, prompts, users, repository files, package scripts, CI files, and deployment providers cannot inject command text or arbitrary arguments.
- Parallax selects an execution profile only from bounded, trusted source-manifest evidence in the exact materialized lineage.
- Initial profiles are:
  - `parallax-python`: preserves the existing protected Parallax Python BUILD/TEST/VERIFY commands and behavior.
  - `dotnet-solution`: selected only for an unambiguous bounded root-level `.sln` solution, with server-owned .NET BUILD/TEST/VERIFY commands.
- Unsupported or ambiguous repositories fail explicitly with an execution-profile readiness result; Parallax must never silently run the Parallax/Python profile against another stack.
- Execution-profile selection is independent from delivery mode. `source-only` and `vercel-preview` use the same protected engineering semantics.
- The protected execution environment must prove the selected toolchain is available before candidate admission. Missing `dotnet` is an execution-environment readiness failure, not an application test failure.
- Existing deny-all sandbox networking, empty application environment, exact-lineage reconstruction, immutable accepted lineage, and REVIEW authority ceilings remain unchanged.

## 3. Profile detection requirements

- Profile detection reads only the already materialized exact Project/run source lineage.
- Detection considers bounded path/manifest facts, not arbitrary executable metadata.
- `dotnet-solution` requires exactly one eligible root-level `.sln` path. Multiple root solutions are ambiguous and fail closed in this slice.
- `parallax-python` is selected only when the repository contains the established Parallax API/test markers required by the existing protected commands.
- Selection returns a stable profile ID and profile digest suitable for bounded run evidence.
- No `package.json` scripts, Makefile targets, shell files, MSBuild custom commands, GitHub Actions commands, or model-provided text become command authority.

## 4. .NET protected commands

For the `dotnet-solution` profile, commands are release-owned and bind to the single detected solution path:

- BUILD: `dotnet build <solution> --no-restore --nologo`
- TEST: `dotnet test <solution> --no-build --no-restore --nologo`
- VERIFY: `dotnet test <solution> --no-build --no-restore --nologo`

The execution environment must provide the pinned .NET SDK and required restored package cache/assets before these deny-all commands are admitted. If the current snapshot cannot satisfy that prerequisite, runtime returns `EXECUTION_PROFILE_UNAVAILABLE` (or an equivalent bounded readiness code) before application test semantics are evaluated.

A future release may add a separately governed restore-capable dependency preparation stage or additional profiles; this slice does not grant network access to application validation.

## 5. Acceptance criteria

### AC-01 Deterministic profile selection
Exact Parallax source selects `parallax-python`; exact OT Time source selects `dotnet-solution`; unsupported or ambiguous manifests do not select either profile.

### AC-02 No arbitrary command authority
No model/user/repository/provider value can alter executable, arguments, working directory, environment forwarding, network policy, or protected stage mapping beyond the finite release-owned profile definitions.

### AC-03 Candidate validation uses the selected profile
Disposable IMPLEMENT candidate validation derives BUILD/TEST/VERIFY from the exact candidate workspace profile rather than the global Parallax command set.

### AC-04 Same-lineage execution uses the same profile
After IMPLEMENT acceptance, BUILD/TEST/VERIFY reconstruct the exact accepted lineage, independently derive the same profile, and execute only that profile's registered commands. Profile drift fails closed.

### AC-05 Toolchain readiness is distinct from application failure
If the selected profile's required runtime is unavailable in the pinned execution environment, Parallax records an explicit bounded execution-profile/toolchain readiness failure and does not label the application tests as failed.

### AC-06 Existing Parallax protected execution does not regress
The current Parallax Python protected commands, deny-all execution, evidence, tests, and promotion gates remain behaviorally unchanged for Parallax's own repository.

### AC-07 Delivery remains independent
`source-only` .NET execution does not require a Vercel Project/Preview target or Vercel Connect GitHub repository authorization merely because the protected runner implementation currently uses Vercel Sandbox infrastructure.

### AC-08 OT Time production acceptance
After exact release deployment and any required governed execution-snapshot update, an authenticated QA-owned `github:Ryan9876/ot-time` `source-only` run advances PLAN → IMPLEMENT → BUILD → TEST → VERIFY → REVIEW and the authenticated exact-lineage ZIP contains the requested `PARALLAX_QA.md`, without `REPOSITORY_AUTHORIZATION_REQUIRED` or Vercel Preview creation.

### AC-09 Failure remains mutation-safe
Any profile detection, toolchain readiness, build, test, or verify failure before lineage acceptance records bounded evidence and does not accept candidate mutation or fabricate lifecycle progress.

## 6. Implementation areas

Expected implementation areas include:

- a narrow server-owned execution-profile module;
- `code/sandbox_execution.py` registry integration;
- `code/agentic_runtime.py` disposable candidate validation;
- `code/lineage_sandbox_execution.py` accepted-lineage execution;
- execution snapshot/toolchain readiness handling;
- focused profile/security/regression tests;
- the existing OT Time authenticated production replay.

Exact files remain subject to implementation review. Unrelated refactoring is not authorized.

## 7. Non-goals

- Arbitrary user-defined build commands.
- Reading CI workflow commands as runtime authority.
- Enabling sandbox network access for restore/install.
- Adding every language ecosystem in one release.
- IIS deployment automation.
- Removing Vercel Sandbox as the current protected execution implementation.
- Weakening source-only/provider-independent delivery from P2-V0.23.4.
