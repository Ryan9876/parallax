## 1. Objective

Replace the Parallax-repository-specific protected BUILD/TEST/VERIFY command assumption with a finite server-owned execution-profile contract. A Project's exact accepted source lineage determines which pre-registered validation profile is eligible; models, users, Work Specifications, provider payloads, and repository contents never supply executable command text.

This is required by the authenticated OT Time production replay under P2-V0.23.4. Public `github:Ryan9876/ot-time` now advances beyond PLAN without Vercel repository authorization, but IMPLEMENT candidate validation incorrectly executes Parallax's Python pytest paths against the .NET solution and fails before mutation.

## 2. Scope

In scope for this release:

- deterministic protected execution-profile detection from exact server-owned candidate/lineage workspaces;
- preservation of the current Parallax/Python BUILD/TEST/VERIFY profile;
- a bounded .NET solution profile suitable for OT Time;
- profile-specific server-owned command/spec construction for candidate validation and accepted-lineage execution;
- explicit pinned execution-environment identity and unavailable-environment classification;
- bounded profile/environment evidence;
- focused and full regression testing plus authenticated OT Time production acceptance.

## 3. Non-goals

This release does not:

- make Vercel a required deployment provider for source-only Projects;
- add arbitrary shell/command execution or model-selected build commands;
- support every language/package manager in one release;
- silently install project dependencies during protected BUILD/TEST/VERIFY;
- broaden sandbox network access as a fallback;
- grant source acceptance, Git publication, provider mutation, production deployment, or REVIEW-completion authority;
- replace the existing Engineering Run state machine, accepted-lineage contract, or delivery-policy architecture;
- make IIS/local deployment itself autonomous; source-only remains a verified handoff outcome unless a future governed delivery adapter is selected.

## 4. Fixed decisions

- Protected execution commands remain server-owned code/release decisions.
- Execution profile selection is deterministic from bounded source markers in the exact candidate or accepted-lineage workspace.
- Initial profiles are `parallax-python-v1` and `dotnet-solution-v1`.
- The existing Parallax/Python command behavior remains unchanged for repositories that match that profile.
- A .NET solution profile is admitted only when a bounded root-level `.sln`/`.slnx` identity and `.csproj` project set prove the stack unambiguously.
- Unknown, mixed, or ambiguous stacks fail closed with an explicit unsupported/ambiguous profile condition; Parallax never falls back to an unrelated command set.
- Candidate validation and same-lineage BUILD/TEST/VERIFY must select the same profile from the source they actually execute.
- Profile selection cannot accept source lineage, mutate canonical source, change Engineering Run state, deploy, or complete REVIEW.
- The execution environment/toolchain is part of the profile identity. A missing pinned environment must fail explicitly rather than opening arbitrary network or installing model-selected packages during protected validation.
- Dependency preparation, where required, is a separately bounded server-owned environment-build concern. BUILD/TEST/VERIFY retain no application environment and deny-all network.

## 5. Security and execution requirements

- Profile detection inspects only normalized relative paths and bounded manifest content from the already server-owned workspace.
- No shell command, argument list, working directory, environment name, package source, image reference, or snapshot ID may come from model output or API input.
- Every profile defines fixed BUILD/TEST/VERIFY commands, timeouts, working directory, and execution-environment identity in code.
- The protected command policy continues to reject shell metacharacters, path escape, undeclared environment access, unsupported stages, and unregistered tool IDs.
- Candidate workspaces remain disposable and cannot accept canonical lineage.
- Same-lineage execution reconstructs and verifies the exact accepted lineage before selecting a profile and executing it.
- Profile evidence records only bounded profile/environment identity plus existing command/evidence digests; it contains no credentials or unbounded process output.
- Unsupported profile and unavailable execution environment are distinct fail-closed classifications.

## 6. Initial profiles

### `parallax-python-v1`
Detection requires the canonical Parallax source markers used by the current protected runtime. BUILD/TEST/VERIFY commands remain the existing compileall/pytest contract so current protected regressions do not silently change.

### `dotnet-solution-v1`
Detection requires exactly one bounded root-level `.sln` or `.slnx` solution and at least one `.csproj` below the repository root. Initial protected commands are server-owned .NET 8 solution operations:

- BUILD: `dotnet build <solution> --no-restore --configuration Release`
- TEST: `dotnet test <solution> --no-build --no-restore --configuration Release`
- VERIFY: `dotnet test <solution> --no-build --no-restore --configuration Release`

The profile requires a pinned execution environment containing the .NET 8 SDK and the exact dependency closure needed for offline restore/build. If that environment is not available, execution stops as `VALIDATION_ENVIRONMENT_UNAVAILABLE`; it must not silently enable broad network.

## 7. Acceptance criteria

### AC-01 Deterministic server-owned profile selection
Exact candidate/accepted source selects a pre-registered profile solely from bounded source markers. External callers and model output cannot provide or override command text, arguments, working directory, profile ID, snapshot/image identity, or toolchain.

### AC-02 Existing Parallax protected execution does not regress
The Parallax repository selects `parallax-python-v1` and retains its existing protected BUILD/TEST/VERIFY commands, policy checks, evidence, and test coverage.

### AC-03 .NET solution profile is bounded
OT Time source selects `dotnet-solution-v1`; the exact root solution path is derived from the verified workspace and the profile emits only the fixed .NET 8 BUILD/TEST/VERIFY command shapes defined by this release.

### AC-04 Unsupported or ambiguous stacks fail closed
A repository with no admitted profile, multiple ambiguous root solutions, or conflicting admitted profile markers returns an explicit profile-selection failure before protected process execution and before source mutation/lineage acceptance.

### AC-05 Candidate and accepted-lineage validation agree
Disposable candidate validation and post-IMPLEMENT same-lineage BUILD/TEST/VERIFY independently derive the same profile from the exact source bytes they execute. Neither trusts an earlier model/provider profile claim.

### AC-06 Execution environment is explicit and pinned
Each profile has a server-owned execution-environment identity. Missing/mismatched .NET toolchain or offline dependency environment is classified separately from source/test failure and never causes network widening or arbitrary package installation during protected validation.

### AC-07 Security boundaries remain unchanged
Validation remains disposable or exact-lineage bound, deny-all network, no application environment, no arbitrary commands, no credential propagation, no Git/provider mutation, no production deployment, and no REVIEW-completion authority.

### AC-08 OT Time production continuation
After exact release deployment and an admitted .NET execution environment are available, the authenticated QA-owned `github:Ryan9876/ot-time` `source-only` replay passes candidate validation, advances through BUILD/TEST/VERIFY to REVIEW, and produces the authenticated exact-lineage ZIP handoff without Vercel deployment-target or repository-provider authorization.

### AC-09 Evidence is bounded and diagnosable
Failure/success evidence includes profile ID, execution-environment identity, stage, existing invocation/output digests, exit/timing status, and source/candidate identity sufficient to distinguish profile-selection, environment, build, test, and verify failures without exposing secrets or unbounded logs.

### AC-10 No authority widening
No PAT, owner impersonation, cross-tenant access, arbitrary package command, arbitrary OCI image, broad network fallback, source-acceptance bypass, deployment authority, or REVIEW completion is introduced.
