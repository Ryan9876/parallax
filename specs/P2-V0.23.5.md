## 1. Objective

Generalize protected candidate and accepted-lineage validation so Parallax can validate supported Python, JavaScript/Node, and .NET applications using deterministic server-owned command profiles selected from bounded repository evidence instead of the current Parallax-repository-specific Python command registry.

Authenticated production replay of the public `github:Ryan9876/ot-time` source-only Project proved P2-V0.23.4 removes the Vercel repository-authorization prerequisite: PLAN passed without `REPOSITORY_AUTHORIZATION_REQUIRED`. The same run then failed before source mutation at IMPLEMENT candidate validation because the protected TEST invocation is hard-coded to Parallax's own pytest paths. The failure is `AUTONOMOUS_IMPLEMENT_FAILED`, `ImplementationContractError`, candidate TEST exit code 4, with `mutation_applied=false`.

This slice fixes that generalization defect without allowing repository manifests, model output, benchmark identity, or user text to become executable command authority.

## 2. Fixed decisions

- Repository compatibility evidence and executable command authority remain separate layers.
- Existing Wave 5 repository intelligence is the deterministic source of ecosystem/root evidence and is extended narrowly to recognize .NET solution/project markers.
- Protected executable commands remain fixed in server-owned released code.
- Initial validation profiles are `python`, `node`, and `dotnet`.
- Profile selection is deterministic from the exact materialized source tree and must fail closed when the repository is unsupported or materially ambiguous.
- Candidate validation and accepted-lineage BUILD/TEST/VERIFY use the same selected profile identity and registered commands.
- Repository-defined package scripts, README instructions, project targets, MSBuild custom commands, shell text, model suggestions, or benchmark identity cannot directly supply executable command strings or arguments.
- Validation remains offline/deny-all, receives no application environment, cannot install packages from the network, and cannot accept or publish source lineage.
- P2-V0.23.4 delivery modes remain unchanged: source-only validation does not imply Vercel deployment; Vercel Sandbox may remain the current isolated execution provider.
- REVIEW remains the autonomous ceiling.

## 3. Repository intelligence extension

The deterministic compatibility analyzer may add these bounded .NET evidence signals:

- `*.sln` at an admissible application/package root;
- `*.csproj` at an admissible application/package root;
- language signal `csharp` for `.cs` files;
- ecosystem signal `dotnet` tied to the manifest path.

Raw `.sln`/`.csproj` contents are evidence only. No target, command, Exec task, package source, URL, environment value, or arbitrary XML content becomes command authority.

A repository with multiple materially conflicting ecosystem roots must remain ambiguous unless an existing deterministic application-root contract resolves one exact root without model/user choice.

## 4. Server-owned validation profiles

A protected validation profile is immutable released policy containing only server-owned values:

- profile ID/version;
- admitted ecosystem;
- executable command;
- fixed argument tuple per BUILD/TEST/VERIFY;
- bounded working directory derived only from the admitted application root;
- timeout bounds;
- required toolchain identity.

Initial profiles:

### Python
Preserve existing protected Python behavior for Parallax-compatible Python repositories. Commands remain fixed by released policy; repository pytest arguments/scripts cannot replace them.

### Node
Use only fixed Node/npm commands admitted by server policy. Repository `scripts` fields may be compatibility evidence but are never copied into an execution spec. If a safe fixed validation route cannot be proven without executing repository-defined script text, the profile fails closed rather than invoking it.

### .NET
Use fixed `dotnet` CLI commands against the deterministically admitted solution/project root. The profile may select a unique `.sln` or `.csproj` identity as a bounded path argument, but no repository-supplied command text, MSBuild property, target, environment value, package source, or shell fragment is accepted.

The intended initial .NET route is bounded equivalent of restore-free/offline-safe BUILD/TEST/VERIFY where the pinned execution environment already contains required dependencies. If the required toolchain/dependencies are unavailable offline, return typed toolchain/dependency unavailability rather than adding network/package-install authority.

## 5. Security and authority requirements

- Profile selection consumes only canonical Project/run/lineage-bound server materialization.
- Every selected path must be normalized relative, remain under the protected workspace, reject symlink/path escape, and satisfy existing source bounds.
- Command/executable/argument templates are code constants or equivalent immutable server registry entries.
- No generic shell (`sh -c`, `bash -c`, PowerShell command text), arbitrary subprocess string, manifest script expansion, or model-proposed invocation is introduced.
- No network broadening, package-manager install authority, application secrets, provider credentials, deployment credentials, environment propagation, Git mutation, or production authority.
- Candidate validation remains disposable and cannot call lineage acceptance.
- Accepted-lineage execution remains exact-lineage bound and uses the identical profile ID/digest selected for candidate validation.
- A missing required executable or unavailable offline dependency is a protected validation failure with bounded typed evidence, not a reason to fall back to a different ecosystem or ungoverned command.
- Unsupported or ambiguous repositories fail before command execution.

## 6. Acceptance criteria

### AC-01 Deterministic .NET compatibility evidence
Repository intelligence recognizes representative `.sln`, `.csproj`, and C# source evidence deterministically, records bounded evidence identities, and does not execute or trust repository command text.

### AC-02 Fixed server-owned toolchain profiles
Python, Node, and .NET profiles contain only server-owned command templates. Repository/model/user text cannot change executable, argument template, environment, network, provider, Git, deployment, or approval authority.

### AC-03 Deterministic fail-closed selection
An exact source tree produces one stable profile/root identity or a typed unsupported/ambiguous result. Mixed/conflicting roots never trigger guessed execution.

### AC-04 .NET protected validation
A representative OT Time-like C# repository selects the .NET profile and candidate BUILD/TEST/VERIFY use fixed `dotnet` invocations against the admitted solution/project identity instead of Parallax pytest paths.

### AC-05 Python behavior does not regress
Representative existing Python/Parallax fixtures retain protected BUILD/TEST/VERIFY behavior and all inherited execution-policy tests remain green.

### AC-06 Node remains bounded
A representative Node repository is either validated through a fixed admitted Node profile or explicitly rejected when safe offline fixed commands cannot be proven. Repository `scripts` values never become command authority.

### AC-07 Candidate and canonical validation agree
The selected validation profile identity is bound to candidate-validation evidence and accepted-lineage BUILD/TEST/VERIFY; canonical execution cannot silently switch profile/toolchain after candidate admission.

### AC-08 Toolchain/dependency absence fails closed
Missing executable, pinned-snapshot toolchain, or offline dependency returns bounded non-success evidence and performs no source-lineage acceptance, network/package installation, provider mutation, or deployment mutation.

### AC-09 Existing authority and delivery contracts remain intact
Project/spec/run identity, single-writer source acceptance, immutable lineage, evaluator precedence, tenant/auth, source-only handoff, Vercel Preview delivery, provider scopes, and REVIEW boundaries do not regress.

### AC-10 OT Time authenticated production proof
After exact release deployment, a QA-owned source-only Project bound to `github:Ryan9876/ot-time` progresses from PLAN through IMPLEMENT/BUILD/TEST/VERIFY to REVIEW and the authenticated exact-lineage ZIP handoff verifies, without Vercel deployment target, Vercel repository-provider authorization, out-of-band source edit, owner impersonation, or DB mutation.

## 7. Scope

Expected implementation areas:

- `services/api/parallax_api/code/repository_intelligence.py` — narrow .NET evidence support;
- `services/api/parallax_api/code/sandbox_execution.py` — immutable validation-profile registry/selection contract;
- `services/api/parallax_api/code/agentic_runtime.py` — candidate validation profile selection/binding;
- same-lineage execution composition so accepted-lineage BUILD/TEST/VERIFY consume the same selected profile identity;
- focused tests for Python/Node/.NET selection, ambiguity, injection resistance, and candidate/canonical agreement;
- W8-S2 OT Time production replay.

Exact files may vary after implementation diagnosis. Unrelated refactoring is not authorized.

## 8. Non-goals

- Arbitrary repository script execution.
- Generic user/model-provided shell commands.
- Adding network access to protected validation.
- Installing packages from NuGet/npm/PyPI during protected execution.
- Replacing Vercel Sandbox in this slice.
- Implementing IIS/Azure/AWS/local deployment adapters.
- Changing P2-V0.23.4 delivery-mode semantics.
- Supporting every language/toolchain in one release.
- Benchmark-specific or OT-Time-specific runtime branches.
