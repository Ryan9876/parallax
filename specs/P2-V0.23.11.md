## 1. Objective

Allow an explicit successful human resume of a FAILED Engineering Run to re-arm that run's terminal durable worker for exactly one new bounded worker generation, so the already-authorized autonomous continuation can dispatch again instead of being blocked by the prior worker's terminal FAILED state.

## 2. Triggering evidence

Production Engineering Run `2b3cd15f-c5e2-481a-8266-c92c6534b08b` exhausted its bounded implementation candidates and correctly persisted a terminal worker failure. PR #466 subsequently fixed the client so a user retry performs `resume -> autonomous`. Production logs then showed repeated authenticated `/resume` and `/autonomous` requests returning HTTP 200 and new run events being persisted, but later autonomous calls stopped before any hosted-model invocation.

The server-side cause is a recovery boundary mismatch. Candidate exhaustion marks the durable worker `FAILED` and releases its lease. Engineering Run `/resume` moves the authoritative run back to `IMPLEMENT`, but it does not re-arm the durable worker. Ordinary worker acquisition intentionally refuses to restart any existing unowned worker row, and the protected runtime only automatically reassigns workers already in `STALLED` or `RECOVERING`. The resumed run is therefore active while its durable worker remains terminal and blocks dispatch.

## 3. Fixed decisions

- A terminal worker is never restarted automatically merely because a client reconnects, refreshes, or calls `/autonomous`.
- A successful explicit resume of an Engineering Run that was authoritatively `FAILED` is the human authority boundary that may re-arm that run's durable worker.
- Re-arm moves only an unleased `FAILED` worker to `RECOVERING`; the existing protected `RECOVERING -> REASSIGNED` path remains responsible for issuing the new mutation lease generation.
- Re-arm resets worker-local retry/no-progress/oscillation counters and progress fingerprints for the new human-authorized generation.
- Prior Engineering Run attempts, persisted run events, checkpoint payload/revision, source lineage, last-known-good lineage, current step and lease-generation history remain preserved as historical evidence.
- Re-arm clears the prior terminal stall classification and blocker from current worker state and sets the next protected recovery action to `REASSIGN`.
- Repeated/replayed resume requests are idempotent: once the worker is no longer `FAILED`, the re-arm operation is a no-op.
- PAUSED, HUMAN_REQUIRED, READY_FOR_INTEGRATION and SUCCEEDED workers are not converted to a new generation by this rule.
- Candidate recovery remains bounded within each autonomous attempt. This change does not create an automatic cross-attempt loop; another terminal failure requires another explicit human resume.

## 4. Architecture requirements

### 4.1 Repository transition

`WorkerExecutionRepository` owns a compare-and-swap transition from an unleased `FAILED` execution to `RECOVERING`. The transition must fail closed on concurrent state/revision/lease changes. It preserves checkpoint and lineage fields and the prior lease generation while resetting only worker-local anti-loop counters/fingerprints and current terminal recovery markers.

### 4.2 Recovery service

`WorkerRecoveryService` exposes a bounded human-resume preparation operation. It validates the canonical Engineering Run binding, returns a no-op when no worker exists or the worker is not `FAILED`, performs the protected repository transition when eligible, and emits a persisted worker recovery event when event observation is enabled.

### 4.3 Resume composition

The authenticated Engineering Run `/resume` route keeps the existing Engineering Run state-machine transition authoritative. After a successful resume that began from `FAILED`, it invokes the worker human-resume preparation operation. The subsequent existing client/autonomous handoff then encounters `RECOVERING`, and the existing durable worker bridge performs the protected reassignment and fresh lease generation.

No `/autonomous` call by itself may re-arm a terminal worker.

Owned implementation scope:

## 6. Security and reliability

The new transition is narrower than ordinary mutation authority: it is available only after the existing authenticated/authorized Engineering Run resume succeeds and only while the corresponding worker is terminal `FAILED` and unleased. It grants no source mutation by itself; the normal protected worker reassignment and candidate/runtime validators still gate execution.

Historical failure evidence is not deleted or rewritten. Reset counters apply only to current worker-local loop detection for the newly human-authorized generation. The immutable Engineering Run attempt/event history continues to show prior failures and resumes.

The transition is compare-and-swap guarded and idempotent. Concurrent retries cannot create multiple new generations because the first successful transition changes the worker out of `FAILED`; lease generation increments only later through the existing single `reassign()` path.

## 7. Acceptance criteria

### AC-01 Failed worker remains fail-closed without human resume
An unleased `FAILED` worker continues to reject ordinary acquisition and autonomous dispatch when no explicit Engineering Run resume has re-armed it.

### AC-02 Human resume re-arms exactly the terminal worker
After a successful explicit resume from Engineering Run `FAILED`, an existing unleased worker in `FAILED` transitions to `RECOVERING` with next recovery action `REASSIGN`.

### AC-03 Historical evidence is preserved
Re-arm preserves worker ID, checkpoint JSON/revision, current step, source lineage, last-known-good lineage and lease generation. Prior Engineering Run attempts/events are unchanged.

### AC-04 New-generation loop counters are reset
Re-arm resets retry, no-progress and oscillation counters plus current/previous progress fingerprints. Prior stall classification and blocker are cleared from current worker state.

### AC-05 Existing reassignment path is reused
The next protected durable-worker acquisition observes `RECOVERING`, invokes the existing reassignment path, increments lease generation once, and obtains a fresh mutation lease.

### AC-06 Idempotent replay
A second human-resume preparation against a worker already in `RECOVERING` or later state does not reset it again or create another lease generation.

### AC-07 Non-failed boundaries are unchanged
PAUSED resume does not reset a healthy worker. HUMAN_REQUIRED, READY_FOR_INTEGRATION and SUCCEEDED worker states remain protected from this re-arm rule.

### AC-08 Candidate and authority bounds remain unchanged
`max_reassignments_per_work_unit`, validator-guided candidate repair, hosted Luna -> Terra -> Sol ordering, source-lineage authority, Git/provider/deployment ceilings and REVIEW remain unchanged.

### AC-09 Persisted observation is truthful
When run-event observation is enabled, the eligible human re-arm emits a worker RECOVERING event; historical FAILED events remain visible.

### AC-10 Release proof
Focused worker/recovery/API tests, full API regression, Bounded Autonomy, protected promotion and DSPy release gates pass on exact head. After exact-source production deployment, `/health` and `/ready` pass and a representative failed-run retry demonstrates a new worker generation can reach hosted implementation dispatch instead of stopping at the terminal-worker conflict.

## 8. Non-goals

- Unlimited automatic retries.
- Automatically reviving a terminal worker on page refresh or `/autonomous` alone.
- Rewriting or deleting prior failures.
- Resetting canonical Engineering Run attempt history.
- Bypassing candidate validation or worker leases.
- Converting HUMAN_REQUIRED into automatic execution.
- Changing model selection policy.
- Moving the REVIEW boundary.
