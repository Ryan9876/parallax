## 1. Objective

Add the first concrete repository and preview provider actions required for a usable app-building loop while preserving the accepted Wave 1 project-scoped authority boundary. GitHub source/review operations and Vercel preview delivery must be narrow, typed, project-bound, auditable, and incapable of becoming a generic HTTP, shell, Git, deployment, or production-promotion escape hatch.

The autonomous ceiling for this workstream is a Vercel preview deployment. Production promotion remains operator/release authority.

## 2. Scope

This workstream owns additive provider-specific contracts and adapters under `services/api/parallax_api/tools/providers/`, focused provider tests, and the protected workstream specification/compiled plan.

GitHub scope:

- resolve one configured `github:owner/repository` identity and its bounded source/default revision metadata;
- read bounded source tree and file content required by trusted workspace initialization;
- create one bounded app-builder branch from an allowed base revision;
- write an accepted implementation lineage to that branch through a typed commit operation with deterministic safe evidence;
- create and read an app-builder pull request through typed operations.

Vercel scope:

- request one preview deployment for a registered Project/provider target from an accepted repository/source revision;
- read bounded preview deployment identity, status, and URL evidence;
- reject Project/repository/source mismatches before provider mutation.

All provider operations consume Wave 1 `ToolCapabilityRegistry`, `ToolAuthorityRequest`, `AuthorityDecision`, `ToolExecutionResult`, and `ToolAuditRecord` contracts. Provider adapters translate an already authorized typed action into one bounded provider method; they are not an alternate authority system.

This workstream may define opaque adapter seams for #59 canonical Project binding, #60 source-lineage identity, and #61 protected implementation publication, but it must not edit those workstreams' owned runtime/persistence paths.

## 3. Fixed decisions and interfaces

- `project_ref` for every provider action is canonical `Project.id`; `workspace_ref` and `repository_ref` are never substitutes for Project identity.
- Repository metadata selects a registered provider resource but grants no capability by itself.
- Provider credentials are server/connector-owned and never appear in request models, return evidence, logs intended for models/UI, or protected evaluation payloads.
- No provider contract exposes arbitrary URL, HTTP method/body/header, environment variables, shell command, subprocess command, Git command string, or unrestricted provider payload fields.
- Authority is checked through the existing immutable Wave 1 registry before every provider mutation and before protected reads that require a registered action.
- Destructive actions retain the existing human-approval invariant. This first slice does not require destructive GitHub or Vercel operations.
- Provider denial, provider failure, and provider success remain structurally distinct and auditable.
- GitHub write operations are limited to one explicitly named app-builder branch, bounded accepted source changes, and pull-request creation/read operations.
- Vercel deployment is preview-only. Production promotion, alias mutation, environment mutation, domain mutation, and secret management are absent from the typed surface.
- Provider return types contain bounded identifiers, normalized states, URLs where safe, and canonical digests; raw response dictionaries are not protected evidence.
- Provider protocols are specific to GitHub or Vercel actions; there is no generic transport protocol available to model/user request data.

## 4. Non-goals

- Generic GitHub or Vercel API proxying.
- Generic HTTP, arbitrary URLs, arbitrary request bodies/headers, shell, subprocess, or command execution.
- Production deployment, production promotion, alias/domain mutation, environment-secret mutation, or deployment configuration mutation.
- Canonical Project schema/persistence changes owned by #59.
- Workspace allocator or source-lineage implementation owned by #60.
- IMPLEMENT generation/orchestration owned by #61.
- Client UX.
- Autonomous repository deletion, branch deletion, force push, merge, release publication, or repository settings mutation.
- Treating repository metadata or a successful provider call as protected stage authority.

## 5. Architecture and failure semantics

Provider-specific modules define immutable bounded request/result records and narrow client protocols. A provider action service receives a canonical Project/provider binding plus a caller-selected capability ID and actor identity, constructs the exact Wave 1 authority request server-side, obtains the registry decision, and only invokes the matching provider method when authority is allowed.

GitHub action identities are fixed to bounded operations such as repository/source read, app-builder branch creation, accepted-lineage commit, and pull-request create/read. Vercel action identities are fixed to preview create/read. The action service does not accept arbitrary action names from a generic execution request.

Each operation returns deterministic safe evidence and a Wave 1 audit record. Provider exceptions are translated to normalized provider-failure results without exposing raw provider payloads. Authority denial returns denial evidence without calling the provider. Success is recorded only when the typed provider result satisfies Project/repository/source binding checks.

GitHub source reads are bounded by explicit maximum entry/content sizes. Commit publication accepts only bounded file records associated with an accepted lineage identity and expected base revision. It does not accept shell/Git commands. Vercel preview creation requires a registered Vercel target, matching canonical Project/repository identity, and an accepted source revision/lineage identity.

## 6. Security

- Treat provider resource metadata, branch names, file paths, source revisions, pull-request text, preview identities, and provider-returned values as untrusted bounded inputs.
- Reject traversal-like source paths, unbounded text/content, malformed repository identities, malformed revisions, malformed branch names, and unsafe preview URLs.
- Never accept or return provider credentials, authorization headers, cookies, environment secrets, private keys, unrestricted request/response payloads, or hidden reasoning/scratchpad fields.
- Provider interfaces expose no raw transport primitive and no arbitrary metadata bag that could smuggle executable authority.
- Exact canonical Project and repository binding is verified before any provider mutation.
- Tool authority denial must short-circuit provider execution.
- Provider failure must remain `FAILED`, never be coerced into success.
- Production deployment/promotion operations are absent and fail closed by construction.
- Audit/evaluation evidence uses bounded identifiers, normalized codes/states, and SHA-256 digests rather than secret-bearing raw state.

## 7. Acceptance criteria

### AC-01 Spec-first provider authorization
This approved `P2-V0.15.4` specification exists on `ws/app-provider-actions` before substantive provider implementation and passes the protected spec contract gate.

### AC-02 Wave 1 authority reuse
Every provider operation is mediated through the accepted Wave 1 capability/approval registry and exact `ToolAuthorityRequest`/`AuthorityDecision` contracts. Repository metadata or provider configuration never bypasses registered capability authority.

### AC-03 Canonical Project and repository binding
Provider requests require canonical `Project.id` as `project_ref` plus a registered repository/provider target. Wrong Project, repository, source revision, or target binding fails closed before mutation, and `workspace_ref` is never treated as provider authority.

### AC-04 Narrow GitHub source operations
The GitHub adapter provides only bounded repository/source resolution and bounded tree/file reads required for trusted workspace initialization. Paths, entry counts, text sizes, repository identities, and source revisions are validated and bounded.

### AC-05 Narrow GitHub mutation operations
The GitHub adapter provides bounded app-builder branch creation, accepted-lineage commit, and pull-request create/read operations. It exposes no generic Git command/API proxy, force push, merge, deletion, settings mutation, release publication, or unrestricted repository write surface.

### AC-06 Preview-only Vercel operations
The Vercel adapter provides preview create/read operations bound to canonical Project/repository/source identity. Production promotion, alias/domain mutation, environment/secret mutation, and arbitrary deployment configuration are absent and rejected.

### AC-07 Deterministic safe evidence and audit
Successful provider operations return bounded provider/tool/action identity, Project/repository/source identity digests, result identities, normalized status/result codes, and Wave 1 audit records. Given the same typed provider result, safe evidence digests are deterministic.

### AC-08 Denial and provider-failure truthfulness
Authority denial does not call the provider and produces `DENIED` audit evidence. Provider exceptions or negative typed results produce `FAILED` audit evidence. Neither denial nor provider failure can be represented as provider success.

### AC-09 Secret and generic-execution exclusion
Tests prove provider tokens, headers, environment secrets, arbitrary HTTP fields, shell/subprocess fields, hidden reasoning/scratchpads, and raw provider payloads are not accepted by or emitted from the typed provider contracts/evidence.

### AC-10 Bounded publication lineage seam
GitHub commit and Vercel preview requests require explicit accepted lineage/source revision identity suitable for #60/#61 integration. `applied: true` or arbitrary caller content alone cannot authorize publication, and the provider layer does not redefine protected IMPLEMENT authority.

### AC-11 Positive and negative isolated provider tests
Provider fakes or isolated boundaries prove authorized source read, branch/commit/PR, preview create/read success plus negative wrong-Project, wrong-repository, missing/invalid capability, approval mismatch where applicable, generic execution attempt, production-promotion attempt, oversized/malformed input, secret-bearing evidence, and provider-failure behavior.

### AC-12 Integration readiness and worker boundary
The branch carries the committed DSPy compiled plan, passes deterministic Workstream Spec Validation, Parallax P2 CI, and Bounded Autonomy on latest `main`, and has a review-ready PR with explicit #59/#60/#61/#46 interface notes. The worker does not merge or deploy.

## 8. Risks and mitigations

- **Provider API drift:** keep provider-specific protocols narrow and translate provider SDK/connector changes behind typed server-owned adapters rather than broadening model-visible contracts. AC-04, AC-05, and AC-06 remain the protected surface.
- **Authority confusion:** reuse the Wave 1 registry for every action and preserve exact `project_ref`/tool/action matching; provider configuration never becomes authorization. AC-02 and AC-03 cover this risk.
- **Publishing stale or unaccepted source:** require expected base/source revision plus accepted lineage identity and fail on mismatches. AC-05 and AC-10 cover this risk.
- **Secret leakage:** typed provider results contain only safe bounded fields; raw provider responses and credentials never enter evidence. AC-07 and AC-09 cover this risk.
- **Production escalation:** omit production operations from the Vercel surface and reject production-like requests by construction. AC-06 covers this risk.
- **Parallel interface drift from #59/#60/#61:** depend on opaque canonical Project/source-lineage/accepted-implementation seams and leave cumulative binding to serialized Integration. AC-03, AC-10, and AC-12 cover this risk.
