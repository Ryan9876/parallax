# Parallax 2.0 — Wave 2 Project Selection and Code Creation Compatibility

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.15.8
Workstream: WS-APP-PROJECT-SELECTION-UX / GitHub issue #71
Depends on: integrated Wave 2 canonical Project binding P2-V0.15.1 (#59)
Integration target: `integration/wave2-app-builder`
Method: minimum client compatibility UX using existing protected Project and Conversation APIs

## 1. Objective

Add the minimum client capability required to select or create one canonical owner-scoped Project before starting new Code work, and send only that Project's canonical `Project.id` to the existing Code conversation creation API.

This slice closes the rollout gap introduced intentionally by P2-V0.15.1: the backend correctly rejects new unbound Code conversations, while the current client still creates conversations with only `{mode}`. The fix is client-side compatibility. The backend Project requirement must not be weakened.

The resulting experience must preserve the existing Parallax design language, mobile/iOS geometry, conversation behavior, Work Specification behavior, live-edge/composer protections, and Reason mode semantics. This is not a Project dashboard or repository-management surface.

## 2. Fixed decisions

- Canonical `Project.id` from the protected `/v1/projects` API is the only client value that may bind a new Code conversation.
- `workspace_ref` is display-irrelevant for this slice and must never be sent as a path, execution handle, Project selector value, or Code creation authority.
- `repository_ref` is optional bounded metadata for Project creation only. It is not authority and is never substituted for canonical Project ID.
- Existing Reason conversation creation remains unbound unless the accepted backend contract changes; this worker does not add Project requirements to Reason mode.
- Historical `HISTORICAL_UNBOUND` conversations remain readable and visibly compatible. The client never guesses or silently assigns a Project to them.
- New Code creation fails closed when no valid Project is selected or when Project refresh/creation fails. The client must not fall back to an unbound Code request.
- Project selection/create UX must reuse the current visual system and fit within existing desktop and 390x844-class mobile geometry without introducing a new navigation architecture.
- Work Specification drafting/approval/resume behavior and Engineering Run controls are unchanged.

## 3. Architecture requirements

Extend the existing typed client API layer with a bounded `ProjectDto`, owner-scoped Project list/create calls, and a Code-aware conversation creation contract that accepts canonical `project_id` only when creating Code work.

Project selection state must be deterministic and explicit. The selected Project ID must either resolve to the current owner-scoped Project list or be cleared. Creating a Project may select the server-returned canonical Project automatically, but no client-generated ID or workspace metadata may become the binding.

The main application may present a compact selector/creation surface adjacent to the existing mode/new-conversation flow. It must not add a Project dashboard, repository browser, deployment controls, analytics, provider credentials, or broad settings surface.

Failure handling must be bounded: authentication failures retain existing access-lock behavior; Project API failures surface a local actionable error; stale/removed/cross-owner Project IDs are cleared and Code creation remains blocked until a valid Project is selected. No retry loop or silent unbound fallback is permitted.

## 4. Scope

- extend client DTOs for Project identity and Project binding state on conversations/runs;
- add `listProjects` and `createProject` API helpers using existing protected endpoints;
- update `createConversation` so Code creation requires a canonical Project ID while Reason creation continues to send no Project binding;
- load owner-scoped Projects after authenticated workspace initialization;
- add a minimal Project selector for Code mode;
- add a compact create-Project affordance with required name and optional bounded repository identity metadata;
- automatically select the canonical server-returned Project after successful creation;
- clear invalid/stale selection when it no longer exists in the owner-scoped list;
- prevent Code conversation creation and Code-mode message bootstrap without a valid selected Project;
- show explicit historical-unbound compatibility state when opening a Code conversation whose binding state is `HISTORICAL_UNBOUND`;
- add deterministic state tests and browser acceptance coverage at desktop and 390x844-class mobile;
- preserve current Work Specification, Engineering Run, Reason, composer, live-edge, auth and visual behavior.

## 5. Security and authority invariants

- The client never manufactures Project IDs.
- The client never sends `workspace_ref` during Project selection, Project creation, conversation creation, Engineering Run activation, or response operations.
- The client never treats `repository_ref` as authorization or execution identity.
- A new Code conversation request contains exactly the selected canonical `project_id` returned by the owner-scoped Project API.
- Missing or stale Project selection blocks Code creation locally and the backend remains the final enforcement boundary.
- Cross-owner Project denial from the backend is surfaced as failure; the client does not retry with an unbound request.
- Historical-unbound conversations are never silently rebound.
- No provider credentials, generic URL, arbitrary HTTP method/body, shell, Git, deployment, filesystem, secret-management, or production-promotion authority is added.

## 6. Non-goals

- weakening or changing P2-V0.15.1 backend Project requirements;
- a Project dashboard, Project analytics, repository browser, repository management, or deployment management;
- provider connection/credential UX;
- Project deletion, rename, lifecycle administration, or workspace allocation;
- source lineage, IMPLEMENT generation, provider actions, production deployment or release promotion;
- redesigning navigation, typography, color, animation, composer geometry, mobile safe-area behavior, Work Specification UX, Engineering Run UX, or Reason mode;
- changing the four authoritative project records from this worker.

## 7. Acceptance criteria

### AC-01 Owner-scoped Project loading
After authenticated workspace initialization, the client loads Projects through `GET /v1/projects` using the existing authenticated transport. The typed Project contract carries canonical `id`, display name/slug, optional repository metadata and status without using `workspace_ref` as execution authority.

### AC-02 Deterministic valid selection
Project selection is explicit and deterministic. A selected ID must resolve to the current owner-scoped Project list; stale/missing IDs are cleared. If exactly one valid Project exists, the client may select it automatically for convenience, but it may never invent or infer a Project from repository/workspace metadata.

### AC-03 Minimal Project creation
The Code-mode Project surface can create a Project through `POST /v1/projects` with required bounded name plus optional bounded `repository_ref`, preserving current backend validation/conflict semantics. On success the server-returned canonical Project is added to the list and selected. Failure does not create a local synthetic Project.

### AC-04 Canonical Code conversation binding
Every new Code conversation created from mode switching, NEW conversation, or first-message bootstrap calls the existing conversation API with `mode: "code"` and the currently selected canonical `project_id`. Code creation is blocked locally when no valid Project is selected and never retries as unbound.

### AC-05 Reason behavior preserved
Reason conversation creation, mode switching to Reason, response streaming and existing conversation history behavior remain unchanged and do not require a Project selection. No Project-selection state may alter Reason Work Specification or response behavior.

### AC-06 Historical compatibility without guessed binding
Opening a historical Code conversation with `project_binding_status == "HISTORICAL_UNBOUND"` remains supported and presents a concise compatibility indication. The client does not mutate, rebind, or silently assign that conversation to the currently selected Project.

### AC-07 Failure states fail closed
Project list/create failures, stale selection and backend missing/removed/cross-owner Project failures surface bounded user-visible error state without retry loops. Authentication expiry preserves the existing private-session lock behavior. No failure path sends unbound Code creation.

### AC-08 Existing product behavior and geometry preserved
The selector/create surface reuses the existing Parallax palette, type hierarchy, controls and interaction language. Desktop and 390x844-class mobile browser acceptance proves no regression to safe-area/composer clearance, live-edge behavior, mode controls, Work Specification status, Engineering Run controls or core conversation geometry.

### AC-09 Deterministic client and browser evidence
Focused deterministic tests prove selection validity, stale-selection clearing, single-Project auto-selection behavior, canonical Code creation payload, Reason payload preservation and failure-to-unbound denial. Browser acceptance proves Project list/select/create and successful canonical Code creation at desktop and 390x844-class mobile, plus representative API failure behavior.

### AC-10 Worker release boundary
The candidate contains this approved specification, authentic committed DSPy compiled plan, only the minimum declared client compatibility implementation/tests, exact validation evidence, and an open PR targeting `integration/wave2-app-builder`. Workstream Spec Validation, Parallax P2 CI, Bounded Autonomy Pilot, backend API regression, client typecheck/state/export and browser acceptance are green. The worker does not merge, deploy, edit authoritative records, or broaden into dashboard/product redesign scope.

## 8. UX constraints

The Code-mode Project control should be compact and subordinate to the existing conversation surface. It may use a small inline selector/status treatment and a lightweight create form/panel that appears only when needed. It must not permanently consume significant vertical space on 390x844-class mobile or obstruct the composer.

Project creation inputs require accessible labels and visible failure text. Selection controls must expose selected/disabled state correctly. Historical-unbound state should be understandable but visually quiet.

No new visual tokens are introduced. Reuse `palette`, existing radii, type scale, spacing conventions and button treatment.

## 9. Risks and mitigations

- **Project selector could become a dashboard.** Mitigation: restrict this slice to list/select/create and one concise binding status.
- **Mobile composer geometry could regress.** Mitigation: keep Project controls outside the fixed composer footprint and require 390x844 browser acceptance.
- **Single-project convenience could become silent inference.** Mitigation: auto-selection is allowed only when the authenticated Project API returns exactly one valid Project; never infer from metadata.
- **Historical Code records could be accidentally rebound.** Mitigation: active conversation binding is read-only; selection applies only to creation of future Code conversations.
- **API failures could tempt fallback to unbound Code.** Mitigation: local fail-closed guard plus unchanged backend enforcement.
- **Project creation validation could diverge from backend.** Mitigation: keep client validation minimal; backend remains authoritative and its detail is surfaced.
