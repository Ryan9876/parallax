# Parallax 2.0 v0.14.3 — Project-Scoped Tool Authority Contracts

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.14.3
Depends on: P2-V0.14.0 parallel-development foundation and the v0.13 protected execution/authentication boundaries
Method: spec-first, provider-neutral authority contracts with fail-closed negative testing

## 1. Objective

Establish a small, typed, server-owned tool-authority boundary that can later let Parallax use explicitly authorized external capabilities for one application Project without exposing provider secrets to model-visible state, allowing user/model text to grant itself authority, or turning connector access into arbitrary shell, HTTP, deployment, or database execution.

The first slice is deliberately provider-neutral. It defines immutable capability, request, approval, decision, result, and audit contracts plus a deterministic in-memory registry that proves project/action scoping and negative authority behavior. Final production project binding must consume the Project/App identity accepted by workstream #43; this specification's opaque `project_ref` is only the integration seam and is not a competing durable Project identifier.

## 2. Scope

- Add a bounded `parallax_api.tools` subsystem with immutable typed authority contracts.
- Represent a capability as a server-owned grant bound to exactly one opaque project reference, one specific tool identity, and an explicit finite action-policy set.
- Represent each action policy with an explicit consequence level and human-approval requirement.
- Require an authority request to name an already-registered capability; request content cannot define, widen, or mutate the grant.
- Resolve authorization deterministically through a registry that fails closed for unknown capability IDs, project mismatches, tool mismatches, unknown actions, disabled grants, and missing or mismatched approvals.
- Bind human approval evidence to the exact request/capability/project/tool/action tuple so approval for one operation cannot authorize a materially different one.
- Forbid generic transport/execution escape hatches such as shell, command execution, subprocess, raw HTTP, and raw network tools at the capability-contract boundary.
- Record audit evidence from safe identifiers, stable digests, consequence, decision/outcome, approval identity, and normalized result codes only; do not persist raw provider payloads, credentials, hidden reasoning, or error bodies in this contract.
- Produce truthful result semantics that distinguish denied, successful, and failed provider/tool outcomes.
- Add focused tests for valid authority and required negative cases while leaving provider adapters, routes, persistence, deployment, and Code/autonomy orchestration unchanged.

## 3. Non-goals

- Implementing GitHub, Vercel, Supabase/database, cloud, browser, or other concrete provider adapters.
- Creating a generic connector endpoint, arbitrary HTTP client, arbitrary shell command runner, subprocess interface, or model-defined executable tool.
- Creating a durable Project/App table, repository, route, migration, or competing project identifier while workstream #43 owns that contract.
- Binding capabilities into the protected Code autonomy coordinator in this parallel slice.
- Granting Git commit, push, merge, history rewrite, production deployment, destructive database mutation, or other high-consequence action without later explicit integration and human-control policy.
- Persisting capability grants or audit events to the production database in this slice.
- Modifying current authentication/session policy, protected command registry policy, evaluation thresholds, or application UI.
- Treating successful unit tests as deployment or deployment-verification evidence.

## 4. Security

Tool access is authority, not convenience metadata. This boundary therefore fails closed and follows the existing server-owned authorization model.

- Capabilities are constructed and registered by trusted server code; model/user requests may only reference a capability ID and request an action already present in that grant.
- Every capability is bound to exactly one `project_ref`; a request for another project must be denied even when the tool and action match.
- Tool and action identifiers are constrained identifiers. Generic execution/transport identities are denied so the registry cannot be used as a disguised arbitrary shell or HTTP tunnel.
- Action policies explicitly classify consequence. A destructive action always requires human approval, and any action marked approval-required is denied without matching bound approval evidence.
- Approval evidence is immutable and request-bound. A grant for a different capability, project, tool, action, or request ID is invalid.
- Capability and audit contracts intentionally contain no credential, token, environment, header, body, command, URL, or arbitrary metadata field into which a secret or executable payload can be smuggled.
- Observable audit evidence contains digests and normalized identifiers/results, never hidden chain-of-thought, scratchpad content, raw provider payloads, or raw error bodies.
- Tool/provider failure remains failure. No failed or denied operation can be represented as a successful audit outcome.
- Provider secrets remain in future provider-adapter/server boundaries and are not arguments to the authority contracts.
- The production authentication boundary remains unchanged; this subsystem supplements authorization and does not replace identity/session verification.

## 5. Authority model

### Capability

A capability contains a stable capability ID, opaque project reference, specific tool ID, finite action policies, and enabled state. Action policies contain the exact action ID, consequence class, and explicit approval requirement.

### Request

An authority request contains a request ID, the capability ID being invoked, project reference, tool ID, action ID, and actor reference. It contains no executable payload. A request does not become authoritative merely because its fields resemble a capability.

### Approval

Human approval is represented as immutable server-owned evidence bound to the exact request and requested authority tuple. The registry validates that binding only when the selected action policy requires approval.

### Decision

A decision is an observable allow/deny contract. Denials carry a normalized reason code; successful decisions carry the matched capability/action policy. No private reasoning trace is stored.

### Result and audit

A result states success or failure using a normalized result code and optional bounded result identity. Audit records combine safe request identity, decision/outcome, digests, consequence, approval identity, and normalized result identity. Raw tool/provider content is outside this contract.

## 6. Acceptance criteria

### AC-01 Immutable typed authority contracts
The new tool-authority subsystem exposes frozen typed contracts for capability grants, action policies, requests, approvals, authority decisions, tool results, and audit records; callers cannot mutate a registered grant through request data after construction.

### AC-02 Explicit project-scoped binding
Every capability is bound to exactly one non-empty opaque project reference, and authorization rejects a request whose project reference differs from the registered capability even when capability ID, tool, and action would otherwise match.

### AC-03 Server-owned fail-closed registry
Authorization succeeds only by resolving an already-registered enabled capability. Unknown capability IDs, disabled grants, or request-supplied lookalike authority are denied; request content cannot create or widen registry authority.

### AC-04 Exact tool and action allowlist
Authorization requires exact tool identity and an exact action policy from the registered capability. Tool mismatch and unknown action requests are denied rather than falling back to a broader permission.

### AC-05 Consequence and approval binding
Each action has an explicit consequence classification. Destructive actions require approval by invariant, and every approval-required action is denied unless immutable approval evidence matches the exact request ID, capability ID, project reference, tool, and action.

### AC-06 No arbitrary execution or transport escape hatch
Capability construction rejects generic shell, command, subprocess, raw HTTP/network, or equivalent reserved tool/action identities, and the authority request contract contains no command, URL, headers, body, environment, or generic payload field.

### AC-07 Secret-safe observable evidence
Capability, request, decision, result, and audit contracts expose only bounded identifiers, policy state, normalized result codes, and digests. They contain no provider credential fields, raw payload/error fields, hidden-reasoning fields, or arbitrary metadata map capable of persisting secrets.

### AC-08 Truthful tool-result semantics
Audit construction distinguishes DENIED, SUCCEEDED, and FAILED outcomes. A denied authority decision cannot produce an execution-success record, and a provider/tool failure cannot be converted into a successful audit outcome.

### AC-09 Deterministic decision and digest behavior
Equivalent registry state and equivalent authority input produce the same normalized decision and canonical request/result digests independent of Python object identity or unordered collection iteration.

### AC-10 Provider-neutral integration seam
The first slice imports no provider SDK, executes no provider call, opens no network/shell escape hatch, adds no API route or database migration, and makes no change to shared authentication, Code/autonomy, or deployment paths.

### AC-11 Protected negative authority coverage
Focused tests prove denial for cross-project use, unknown capability/action, tool mismatch, disabled capability, missing/mismatched approval, generic shell/HTTP escape attempts, and any attempt to treat request data as a self-granted capability.

### AC-12 Project-contract compatibility
The subsystem treats `project_ref` as an opaque caller-supplied authoritative binding and documents that serialized integration must adapt it to workstream #43's accepted Project identity without introducing a competing persistent project model.

## 7. Risks

- **Project identity drift:** #43 may expose a different concrete identity shape than fixtures anticipate. Mitigation: keep `project_ref` opaque and provider-neutral, then adapt the integration seam after #43 is accepted.
- **Overly generic capability naming becoming an escape hatch:** broad identifiers such as shell or raw HTTP could bypass action policy. Mitigation: explicit reserved tool/action denial and no arbitrary payload field.
- **Approval replay:** a valid human approval could otherwise authorize a different operation. Mitigation: approval evidence is bound to request ID plus the complete capability/project/tool/action tuple.
- **False success from provider failure:** adapter errors could later be misreported. Mitigation: result/audit contracts make success versus failure explicit and test the failure path independently of provider integration.
- **Audit evidence leaking sensitive content:** free-form metadata or raw errors would create a secret/hidden-reasoning path. Mitigation: no arbitrary metadata or raw provider payload fields in this contract.
- **Premature integration pressure:** wiring into Code or project persistence while parallel contracts are moving could create collisions. Mitigation: additive provider-neutral modules only; shared integration is serialized after accepted interfaces stabilize.
