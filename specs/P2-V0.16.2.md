# Parallax 2.0 — Wave 3 Deterministic Browser and Multimodal Visual Validation

Status: APPROVED FOR IMPLEMENTATION

Workstream: WS-W3-VISUAL-VALIDATION / GitHub issue #96
Base: main@ec65c00eec5bdd1b1b66afdfb0c287834cfc1aa9
Depends on: deployed P2-V0.15.9/.10 durable source-delivery and runtime-evidence contracts; P2-V0.16.1 recovery protocol is an integration dependency only, not a browser-execution identity source
Method: validate the exact persisted Wave 2 Preview in a separately bounded browser execution plane; deterministic evidence is authoritative and multimodal review is secondary

## 1. Objective

Add a protected application-validation plane that exercises the exact Preview already persisted by Wave 2 source delivery and produces bounded browser, accessibility, network, screenshot-regression and multimodal evidence that later autonomous correction and protected promotion can trust. Browser validation must never accept an arbitrary target URL from a model/caller, must never create a competing Preview identity, and must never gain source mutation, provider mutation or production-promotion authority.

The validation plane must make visual QA autonomous enough for Wave 3: it should detect ordinary functional, accessibility, layout, console, request and visual regressions and return machine-readable defect evidence. Deterministic failures remain authoritative even when a multimodal reviewer considers the screenshot visually acceptable.

## 2. Scope

- Resolve browser target provenance from the existing durable `VerifiedDeliveryResult` / `SOURCE_DELIVERY` record for the canonical Project/run/accepted source lineage. Require the exact persisted Preview deployment ID, status and safe Preview URL; caller/model URL selection is forbidden.
- Define server-owned, versioned browser workflow specifications with bounded route/path, viewport, semantic assertion, interaction and screenshot instructions. Workflows may select registered validation scenarios but cannot contain arbitrary JavaScript, shell, commands, headers, cookies, credentials or external URLs.
- Add a narrow browser executor protocol and production adapter suitable for Vercel Sandbox/Node Playwright execution. Network policy remains deny-all except the exact canonical Preview hostname derived from the persisted delivery record; redirects or requests to unrelated hosts are recorded/rejected according to protected workflow policy.
- Capture deterministic semantic/DOM assertions without persisting raw unbounded DOM. Capture bounded accessibility violations, console errors, page errors, failed requests and unexpected external-network attempts with redaction and cardinality/size limits.
- Validate responsive/layout invariants including required element visibility, viewport overflow/clipping and protected overlay/obstruction checks at server-owned viewports.
- Capture screenshots bound to exact Project/run/Work-Spec/source-lineage/Preview/workflow/viewport identity. Screenshot bytes are artifacts; ordinary evaluation/evidence retains digests, dimensions, artifact references and bounded findings rather than embedding raw images in JSON.
- Add screenshot-regression comparison against provenance-bound baselines. A baseline is valid only for the exact registered reference scenario/design state it declares and cannot silently cross Project/workflow/viewport identity.
- Add a multimodal-review protocol that consumes only approved screenshot artifacts plus bounded semantic context after deterministic validation. It produces structured visual findings/confidence, never hidden reasoning, and cannot override a deterministic failure.
- Produce one normalized protected validation result that later #97 can consume without rerunning provider delivery or widening browser authority.
- Maintain reusable permanent reference-app fixtures/scenarios with deliberate deterministic and visual regressions.

## 3. Security

- Canonical target identity is: authenticated Project -> Engineering Run -> approved Work Specification -> accepted source lineage -> persisted Wave 2 `VerifiedDeliveryResult` -> exact Preview deployment. Any mismatch fails closed before browser launch.
- Preview URLs are loaded only from the durable delivery record and must be HTTPS hosts belonging to the persisted Vercel Preview result. Workflow paths are relative and bounded. Callers/models cannot provide schemes, hosts, ports, arbitrary request headers, cookies or authentication material.
- Browser execution uses a separate bounded network policy from source BUILD/TEST/VERIFY: deny-all base with only the exact Preview domain allowed. No wildcard internet access, generic HTTP client, proxy escape, arbitrary DNS target or raw network authority is exposed.
- Browser workflows are server-owned typed data. They cannot inject arbitrary JavaScript/evaluate strings, shell commands, filesystem paths, provider payloads or unbounded selectors/actions.
- Browser evidence must not persist cookies, local/session-storage values, authorization headers, request/response bodies, secrets, environment values, hidden reasoning, full raw DOM, full console streams or unrelated Project data. URLs are normalized to safe origin/path evidence with query/fragment removed unless a protected workflow explicitly owns a bounded non-secret query key.
- Screenshot artifacts and baselines are provenance-bound. Cross-Project or mismatched run/spec/lineage/Preview/workflow/viewport artifacts are rejected.
- Multimodal output is advisory quality evidence below deterministic checks. It cannot alter acceptance criteria, baseline provenance, evaluator thresholds, source/provider authority or production authority.
- Validation has no GitHub/Vercel mutation capability beyond reading the already-persisted delivery evidence; Preview remains the autonomous provider ceiling established in Wave 2.

## 4. Preview provenance contract

A browser validation request is constructed server-side from a canonical Engineering Run and an accepted source lineage. The resolver loads the durable Wave 2 source-delivery record and verifies:

- `project_id` equals the canonical Project;
- `run_id` equals the Engineering Run;
- `lineage_id` equals the accepted implementation/VERIFY lineage;
- Preview deployment ID is non-empty;
- Preview status is an allowed ready/success state;
- Preview URL is present, HTTPS, host-only provenance is bounded and consistent with the persisted delivery result;
- Work Specification ID/revision/digest still match the Engineering Run used to create the validation request.

The resulting immutable validation target contains Project/run/spec/lineage/content/Preview identities and a normalized Preview origin. The model/caller cannot replace any field.

## 5. Browser workflow contract

A protected workflow is identified by server-owned `workflow_id` + version and contains only bounded typed operations such as:

- navigate to a relative path on the canonical Preview origin;
- use one of a registered viewport set;
- wait for a bounded semantic condition;
- assert text/role/label/test-id visibility or absence using bounded selectors;
- click/fill/select only registered semantic targets with bounded non-secret fixture values;
- assert URL path within the canonical origin;
- assert no blocking overlay/viewport overflow for declared critical regions;
- capture a named screenshot checkpoint.

Arbitrary script evaluation, dynamic code, arbitrary selectors/payloads and external navigation are not supported. Workflows have bounded action count, timeout and screenshot count.

## 6. Deterministic validation and evidence

The executor returns normalized evidence for each workflow/viewport:

- action/assertion outcomes and bounded failure codes;
- accessibility violation summaries with rule ID, impact, bounded locator summary and count;
- console/page-error summaries with type and redacted bounded excerpt;
- failed/unexpected request summaries with method, safe origin/path, status/failure class and count;
- layout/overflow/overlay findings with bounded geometry summaries;
- screenshot artifact reference, digest, width/height and capture identity.

A protected deterministic result is FAIL when any required semantic assertion, disallowed accessibility severity, page/console error policy, required network request, external-network policy, layout invariant or screenshot-capture requirement fails. Multimodal review is not invoked as a way to reinterpret those failures as success.

## 7. Screenshot regression and multimodal review

Screenshot regression compares provenance-compatible artifacts using a deterministic image-difference contract with protected thresholds owned by the workflow/baseline registry. Comparison records bounded metrics/digests and optional diff-artifact reference. Baseline updates are separate governed mutations and are not automatic consequences of a failing candidate.

Multimodal review runs after deterministic evidence is available and consumes the candidate screenshot plus bounded workflow/design context. It returns a typed result such as `PASS`, `REVIEW` or `FAIL`, bounded findings, affected regions/categories and confidence. It may identify visual issues that pixel regression misses, but it cannot override deterministic failure or automatically change a baseline.

## 8. Reference harness

Maintain permanent deterministic browser scenarios for representative Parallax-developed web applications. The harness must include deliberate cases for:

- missing/incorrect semantic content;
- accessibility regression;
- console/page exception;
- failed required request and unexpected external request;
- clipped/overflowing critical UI;
- hidden blocking overlay;
- screenshot visual regression;
- multimodal disagreement with deterministic evidence;
- stale or wrong Preview/Project/spec/lineage provenance.

Fixtures are reusable and versioned; they are not one-off screenshots created only to make this workstream pass.

## 9. Non-goals

- autonomous repair/correction planning or source mutation;
- worker lease/checkpoint ownership implementation;
- critical-path scheduling/work stealing;
- changing Wave 2 provider delivery/persistence semantics;
- automatic baseline acceptance/update from a failing candidate;
- generic browser automation supplied by user/model scripts;
- production deployment/promotion autonomy;
- native-device visual automation beyond the web/Preview browser slice required for the first Wave 3 reference proof.

## 10. Acceptance criteria

### AC-01 Browser target uses only durable Wave 2 Preview provenance
Validation resolves exact Project/run/approved Work-Spec/source-lineage/Preview identity from persisted delivery evidence. Caller/model supplied URL, wrong Project/run/spec/digest/lineage, stale/conflicting delivery record or non-ready/missing Preview fails closed before browser execution.

### AC-02 Browser workflows are server-owned and non-programmable
Versioned workflows expose only bounded typed relative navigation, semantic interaction/assertion, registered viewports and screenshot checkpoints. Arbitrary JavaScript/eval, shell, generic HTTP, arbitrary hosts/headers/cookies/credentials and unbounded selectors/actions are impossible through the workflow contract.

### AC-03 Browser network authority is exact-host allowlisted
Production browser execution retains deny-all network posture except the exact persisted Preview hostname. Unexpected external requests are blocked/recorded. Wildcard internet, model-selected domain and redirect escape cases fail closed without weakening BUILD/TEST/VERIFY network policy.

### AC-04 Deterministic semantic/accessibility/console/network checks are authoritative
Required semantic assertions, accessibility policy, page/console errors, failed required requests and unexpected external-network behavior produce bounded deterministic evidence and protected pass/fail. A multimodal PASS cannot convert a deterministic FAIL into success.

### AC-05 Responsive layout and obstruction defects are detected deterministically
Registered viewports detect protected overflow/clipping, hidden required UI and blocking overlays/obstructions with bounded geometry evidence. Deliberate layout/overlay regressions in the reference harness fail before visual-model judgment.

### AC-06 Screenshot artifacts retain exact provenance without leaking browser secrets
Screenshots are bound to Project/run/Work-Spec/source-lineage/Preview/workflow/viewport identity and represented in ordinary evidence by artifact ref/digest/dimensions. Cookies, storage values, auth headers, secret query data, raw unbounded DOM/log/network payloads and unrelated Project data are never persisted in browser evidence.

### AC-07 Screenshot regression uses governed provenance-compatible baselines
Deterministic comparison rejects cross-Project/workflow/viewport or stale baseline provenance, records bounded difference metrics/digests, and fails candidates exceeding protected thresholds. Baselines are never automatically updated to make a candidate pass.

### AC-08 Multimodal review is structured, bounded and secondary
Multimodal review consumes approved screenshot artifacts and bounded context only after deterministic evidence, returns typed findings/confidence without hidden reasoning, and cannot alter deterministic outcomes, acceptance criteria, baseline thresholds or authority.

### AC-09 Reference harness rejects deliberate functional and visual negatives
Permanent reusable scenarios prove wrong/stale provenance, semantic failure, accessibility failure, console/page failure, required-network failure, external request, clipping/overflow, blocking overlay, screenshot regression and deterministic-vs-multimodal disagreement are rejected as specified.

### AC-10 Validation evidence is reusable by autonomous correction without rerunning delivery
One normalized protected browser-validation result can be consumed by #97 after process recreation and remains bound to the persisted delivery/lineage facts. Evaluation/diagnosis does not recreate GitHub commits, PRs or Vercel Preview deployments.

### AC-11 Existing Wave 2 authority boundaries remain unchanged
Browser validation adds no source mutation, provider mutation, generic network, production promotion or evaluator-threshold authority. Existing source lineage, provider replay, #46 scoring/critical-failure and operator REVIEW/production boundaries remain intact.

### AC-12 Exact-head protected validation
P2-V0.16.2 has authentic committed DSPy critic/compiler evidence. The exact worker head passes Workstream Spec Validation, P2 CI and Bounded Autonomy plus browser/reference-harness validation before integration, and final Wave 3 integration reruns protected cumulative gates.
