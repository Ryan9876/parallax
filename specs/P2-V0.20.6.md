## 1. Objective

Prove that the cumulative Wave 7 product can complete materially different real-world application objectives through the ordinary protected Parallax runtime while preserving exact identity/lineage, bounded autonomy, operator visibility, safe browser evidence, trustworthy observability, objective evaluation and the existing Preview/REVIEW authority ceilings.

S6 is primarily an integrated proof/release-qualification layer. It should reuse the accepted S1-S5 and Wave 6 runtime contracts rather than creating new execution, source, browser, telemetry or deployment authority.

## 2. Fixed decisions

- The accepted cumulative Wave 7 baseline is exactly `00a9e66e2f87a1f992d375b4217845b8f072e11d` until a governed reconciliation changes it.
- S6 proves the ordinary Project → approved Work Specification → Engineering Run → accepted source lineage → BUILD/TEST/VERIFY → Preview → REVIEW path. It does not substitute a second test-only lifecycle.
- Proof requires at least three materially different application-objective classes. A single golden demo cannot satisfy the workstream.
- Every proof case must retain exact Project, Work Specification revision/digest, Engineering Run, acceptance IDs and source-lineage identity through evaluation and delivery evidence.
- Agent/team planning, routing, competition and correction remain bounded non-authoritative candidate mechanisms. Protected deterministic validation and the single-writer source acceptance boundary remain authoritative.
- S3 projection/canvas truth must match fresh server-owned run evidence; presentation cannot become lifecycle/source/provider authority.
- S4 browser proof may use only the accepted bounded browser capability and server-admitted targets/actions. No direct Playwright/eval/fetch bypass may be counted as product evidence.
- S5 economics/telemetry must preserve `OBSERVED`, `ESTIMATED` and `UNKNOWN`; absent cost/usage is never zero-filled merely to make proof dashboards complete.
- ParallaxBench compares the accepted Wave 7 result to an admitted pre-Wave-7/reference baseline using protected criteria. Deterministic correctness/safety/privacy/governance regressions are release-blocking even if another metric improves.
- At least one meaningful non-protected dimension must materially improve across the proof set or S6 must report that Wave 7 has not demonstrated product value sufficient for release.
- Preview is the ordinary autonomous publication ceiling. `REVIEW` / `HUMAN_REQUIRED` remains the autonomous authority ceiling. S6 cannot complete production promotion merely because product proof passes.
- S6 adds no new credentials, provider administration, arbitrary command/network, source acceptance, merge, production-deployment or REVIEW-completion authority.

## 3. Proof scenario portfolio

S6 must define and execute a small immutable server-owned scenario portfolio with at least three materially different objective classes. The exact fixture wording may evolve before qualification, but the semantic classes and acceptance requirements are fixed.

### 3.1 Stateful workflow application

Representative objective: a responsive task/workflow application with create/update state, input validation, meaningful empty/error states and a clear completion flow.

Proof must exercise stateful interaction rather than a static page-only artifact.

### 3.2 Data/operations application

Representative objective: an operator-facing dashboard or analysis application with structured data presentation, filtering or derived summaries, loading/empty/error behavior and responsive layout.

Proof must exercise data interpretation/presentation rather than only CRUD controls.

### 3.3 Public information/utility application

Representative objective: a search/filter/decision-support or content utility with navigable information architecture, usable mobile behavior and accessible interaction semantics.

Proof must exercise materially different information retrieval/navigation behavior rather than re-skinning either previous scenario.

### 3.4 Scenario governance

- Scenario IDs, required acceptance dimensions and baseline references are immutable server-owned fixtures for a proof version.
- Caller/model-generated text cannot silently redefine the proof criteria after execution begins.
- Scenario source fixtures or generated source may differ, but every case uses the same canonical runtime/evidence contracts.
- A scenario may fail honestly. S6 records failure and blocks release qualification rather than replacing it with an easier case after seeing the result.

## 4. Integrated proof contract

Each proof case must emit a bounded machine-readable record containing only approved evidence references and derived proof status.

Required identity fields:

- scenario ID/version;
- Project ID;
- approved Work Specification ID/revision/digest;
- Engineering Run ID/revision/state;
- required acceptance IDs;
- accepted source-lineage ref and parent where applicable;
- exact Preview delivery identity when Preview exists;
- ParallaxBench evaluation identity;
- S3 projection fingerprint/revision;
- S5 observability fingerprint/coverage state.

The proof record contains no source bytes, patch, prompt, hidden reasoning, credentials, raw provider payloads or unrestricted logs.

## 5. Ordinary runtime and lifecycle proof

For each scenario, S6 must prove the accepted server-owned path rather than a parallel harness-specific authority path:

1. canonical Project and approved Work Specification binding;
2. Engineering Run activation and exact revision progression;
3. PLAN/IMPLEMENT through existing protected agent/runtime seams;
4. source acceptance only through the existing single-writer protected implementation/lineage contract;
5. exact-lineage BUILD, TEST and VERIFY;
6. bounded delivery to GitHub/Preview only when the existing provider/delivery contract admits it;
7. operator-facing S3 projection from fresh canonical evidence;
8. S4 browser evidence through admitted browser capability only;
9. S5 observability/economics projection from canonical evidence;
10. ParallaxBench objective evaluation;
11. final autonomous stop at `REVIEW` / `HUMAN_REQUIRED`.

A proof harness may provide deterministic test adapters for external systems where required by CI, but it may not replace or bypass the protected service contracts being proven. External/adaptor simulation must be explicit in evidence and cannot be presented as a production Preview/deployment fact.

## 6. Bounded autonomy and recovery

At least one proof case must exercise a bounded recoverable failure/retry path using the existing durable worker/revision/checkpoint/recovery contracts.

The recovery proof must show:

- stale/replayed mutation cannot duplicate canonical source or provider action;
- recovery remains bound to the same Project/run/spec/source identities;
- bounded retry/reassignment does not erase deterministic failure evidence;
- no-progress/oscillation/human-required conditions stop rather than loop indefinitely;
- a process/reconnect replay resolves existing durable state rather than inventing a new run.

## 7. S3 operator visibility proof

For every scenario, the S3 projection/canvas evidence must be derivable from the same canonical run and must expose enough bounded status for an operator to understand:

- current lifecycle state and revision;
- tasks/attempts and deterministic validation disposition;
- recovery state where present;
- source/delivery lineage references;
- available existing controls only;
- S5 known-state metrics where available;
- final `HUMAN_REQUIRED` handoff when REVIEW is reached.

Client presentation cannot supply canonical revisions, lineage, provider result or pass/fail truth that is absent from the server projection.

## 8. S4 browser proof

At least one browser-backed assertion per scenario is required when an admitted Preview/target is available.

Browser evidence must:

- use the accepted S4 capability registry/policy path;
- remain same-origin/server-admitted and non-destructive;
- use bounded navigate/inspect/declarative-assert/screenshot evidence only;
- redact sensitive observation content under the accepted policy;
- preserve deterministic validation precedence;
- fail closed on off-origin redirect, unsupported action, unrestricted JavaScript/eval, arbitrary network/fetch or credential/header/cookie attempts.

A test that calls an unrestricted browser library directly may validate implementation internals but cannot satisfy the integrated product proof requirement.

## 9. S5 observability/economics proof

For every scenario, S6 must consume the accepted S5 projection and prove:

- metric catalog and provenance remain server-owned/bounded;
- elapsed/retry/recovery/intervention evidence is deterministic for the same canonical inputs;
- `UNKNOWN` remains null/unknown and is not zero-filled;
- incomplete bounded event coverage is explicit and downgrades/withholds event-dependent claims;
- deterministic quality failure remains authoritative over positive qualitative or Preview evidence;
- no cross-Project history/economic access is admitted;
- retention remains the accepted query-time no-op unless a separately governed persistence decision changes the architecture.

## 10. ParallaxBench value proof

Each scenario receives a protected benchmark result against the admitted reference/pre-Wave-7 baseline.

The aggregate S6 release-qualification record must report:

- protected correctness/safety/privacy/governance disposition;
- objective quality/acceptance coverage;
- bounded autonomy/recovery outcome;
- operator visibility completeness;
- browser-evidence availability/status;
- known-state observability/economics coverage;
- at least one declared product-value dimension suitable for comparison, such as intervention count, retry/recovery burden, evidence completeness, operator visibility coverage, or completion quality.

A release-qualified result requires:

- no protected regression in any scenario;
- no deterministic failure hidden by benchmark/UI/browser/telemetry success;
- all required scenario classes executed rather than cherry-picked after results;
- at least one meaningful declared non-protected product-value dimension materially improved for the Wave 7 candidate across the portfolio or an explicit `VALUE_NOT_DEMONSTRATED` outcome.

The proof system must not invent a favorable baseline or metric after candidate results are known.

## 11. Adversarial authority proof

S6 must include negative/adversarial cases proving that each productization surface remains non-authoritative:

- benchmark result cannot transition an Engineering Run or accept source;
- S3 client/projection input cannot invent a newer revision/state/source lineage or complete REVIEW;
- S4 browser result cannot write source, invoke arbitrary network/commands, mutate providers or deploy;
- S5 telemetry/economic result cannot convert deterministic failure to pass, create lifecycle transitions or delete canonical evidence;
- replayed/stale proof records cannot duplicate source/provider/Preview actions;
- cross-Project IDs/evidence fail closed;
- caller-supplied Preview/deployment/lineage/provider identities cannot become canonical truth merely by appearing in a proof request.

## 12. Security

- Proof fixtures and response schemas are bounded and server-owned.
- No credentials, cookies/auth headers, access/session tokens, server environment, raw provider payloads, prompts, hidden reasoning/private scratchpad, source bytes/patches, unrestricted logs or sensitive full URLs are persisted in S6 proof records.
- Exact opaque IDs/digests and approved reason/result codes are permitted where required for auditability.
- Public proof summaries must be non-secret and non-reversible to private raw payloads.
- Scenario/evidence cardinality is bounded; arbitrary user/model/repository strings cannot become metric dimensions or proof categories.
- Project/run/spec/source/provider/delivery identities are accepted only from existing server-owned evidence; caller-supplied identifiers cannot create authority.
- Benchmark, projection, browser, observability and proof output remains evidence only and cannot invoke provider/tool administration, mutate canonical source, execute arbitrary commands/network, merge, deploy or complete REVIEW.

## 13. Scope

Authorized semantic scope may include:

- immutable proof-scenario and proof-dimension catalogs;
- integrated proof record/domain objects and deterministic aggregation;
- a proof runner/composition service that calls existing protected S1-S5/Wave 6 seams without bypassing them;
- deterministic CI reference adapters and fixtures explicitly labeled as simulated external systems;
- focused API/projection helpers only if required to expose already-existing evidence safely;
- browser/observability/benchmark composition tests;
- replay/recovery/privacy/authority-boundary tests;
- release evidence artifacts suitable for Control Tower review.

Prefer tests/composition over new production runtime primitives. New database tables/migrations, provider actions or public APIs require a demonstrated necessity and a separate security/data review within this spec before acceptance.

## 14. Non-goals

- a new application framework or generator unrelated to the accepted runtime;
- a second Engineering Run/source-lineage state machine;
- changing Work Specification approval rules;
- weakening deterministic validation to improve benchmark scores;
- unrestricted browser/network/command capability;
- a new billing ledger or telemetry store;
- production data deletion;
- automatically merging to `main`;
- automatically promoting to production;
- completing operator REVIEW.

## 15. Acceptance criteria

### AC-01 Materially different scenario portfolio
At least three immutable server-owned proof scenarios from materially different application-objective classes execute under one proof version; the portfolio cannot be cherry-picked or weakened after results are known.

### AC-02 Canonical identity continuity
Every scenario proof preserves exact Project, approved Work Specification revision/digest, Engineering Run/revision, acceptance IDs and accepted source-lineage identity through validation/evaluation/delivery evidence; cross-boundary evidence fails closed.

### AC-03 Ordinary protected lifecycle
Proof uses the existing protected Engineering Run/source-lineage/BUILD/TEST/VERIFY/delivery contracts and cannot satisfy acceptance through a parallel test-only authority path.

### AC-04 Bounded autonomy and recovery
At least one scenario proves bounded retry/recovery/reconnect behavior with durable revision/checkpoint/replay semantics and no duplicate canonical mutation/publication or indefinite loop.

### AC-05 S3 operator visibility
Every scenario's S3 projection is bound to fresh canonical run evidence and exposes bounded lifecycle/task/validation/recovery/delivery/metric/handoff truth without client-side canonical inference.

### AC-06 S4 browser evidence boundary
Applicable browser proof uses only the accepted S4 admitted non-destructive capability and fails closed on off-origin, unrestricted JavaScript/network, credential or destructive-action attempts.

### AC-07 S5 known-state evidence
S5 proof preserves deterministic provenance, bounded coverage and `OBSERVED`/`ESTIMATED`/`UNKNOWN` semantics; unknown never becomes zero and incomplete event coverage cannot masquerade as complete observation.

### AC-08 Protected quality precedence
Deterministic/protected failure remains release-blocking and cannot be overridden by ParallaxBench, model/evaluator, S3 UI, S4 browser, S5 telemetry/economics or Preview status.

### AC-09 Objective value evidence
ParallaxBench/reference comparison demonstrates no protected regression across the portfolio and material improvement in at least one predeclared meaningful non-protected product-value dimension, otherwise the aggregate result is `VALUE_NOT_DEMONSTRATED` and cannot be release-qualified.

### AC-10 Exact-lineage Preview and REVIEW ceiling
Where real Preview delivery is exercised, delivery is bound to exact accepted lineage/provider evidence; autonomous execution stops at `REVIEW`/`HUMAN_REQUIRED` and S6 cannot complete production promotion.

### AC-11 Replay and process-recreation safety
Re-running the same proof or reconnecting after process recreation is deterministic/idempotent: existing run/source/provider/proof identities resolve rather than duplicate canonical mutation or publication.

### AC-12 Adversarial authority isolation
Negative tests prove benchmark, projection/client, browser and observability/proof payloads cannot gain lifecycle, source acceptance, provider/tool administration, arbitrary command/network, merge/deploy or REVIEW-completion authority.

### AC-13 Privacy and bounded evidence
Proof records/responses contain only bounded allowlisted identities/status/provenance and exclude credentials, prompts, hidden reasoning, raw provider payloads, source bytes/patches, unrestricted logs and sensitive raw URLs.

### AC-14 Release and exact-head gate
Before S6 acceptance, authentic DSPy evidence for `P2-V0.20.6` is committed, the worker remains based/reconciled to the latest accepted cumulative Wave 7 integration SHA, applicable protected API/client/browser/evaluation/replay/privacy gates pass on the exact head, and the worker stops `READY FOR INTEGRATION` for Control Tower expected-head handling. Any `main` merge or production release requires a separate explicit Control Tower decision and deployment verification.
