# Parallax 2.0 v0.9.0 — Editorial Optical

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.9.0
Depends on: P2-V0.8.0
Method: Spec-first visual refinement + Skia material evolution + release verification

## 1. Objective

Evolve Parallax from a technically polished dark optical interface into a more distinctive editorial product without weakening the v0.8.0 execution trust boundary.

The design reference is the editorial character observed in Anna's House: strong hierarchy, asymmetrical composition, generous negative space, softly framed content groups, selective color-coding, and a slightly hand-made graphic quality. Parallax must interpret those principles rather than copy restaurant branding, typography, illustrations, layout, or palette.

The intended balance is approximately **80% Deep Violet precision / 20% editorial personality**.

## 2. User outcome

Parallax should feel less like a generic AI/HUD interface and more like a designed reasoning instrument with a recognizable visual voice. Conversation remains the dominant surface; Work Specification and Code state become distinct editorial sections rather than dashboard cards.

## Scope

This release is a client visual/material refinement. In scope are the shared palette, Skia living surface, reusable governed-state trace, Work Specification presentation, Code-run presentation, optical response inscription styling, responsive spacing, and reduced-graphics visual parity.

The release may alter presentation-only component structure where necessary to support open/asymmetric framing, but it must preserve all existing API contracts, state transitions, accessibility semantics, server-owned authority, durable persistence, and deployment topology.

## 3. Durable visual decisions

### 3.1 Preserve the Deep Violet core

Keep:

- deep navy/black substrate;
- violet/indigo identity and selection hierarchy;
- cyan active optical energy;
- pale high-contrast narrative text;
- conversation-first layout;
- optical response inscription;
- reduced-motion and reduced-graphics parity.

### 3.2 Add restrained editorial accents

Introduce small secondary accents only where they improve hierarchy:

- warm cream for selected display labels and reading warmth;
- dusty peach for human/operator annotations and soft emphasis;
- muted sage for verified/ready editorial markers;
- no pastel wash across the whole product;
- accents never replace semantic success/warning/error colors.

### 3.3 Hierarchy

- stronger display-scale section labels for Work Specification and Code state;
- tighter small technical metadata beneath display labels;
- larger negative-space separation between conversation, specification, and execution sections;
- fewer simultaneous borders and card boxes;
- content grouping through spacing, asymmetrical rules, and optical traces.

### 3.4 Framing

Replace rigid rectangular card language where practical with:

- open-sided frames;
- offset rules;
- irregular soft-radius corners;
- short editorial strokes that do not fully box content;
- state-linked Skia tracing accents.

## 4. Skia material system

### 4.1 Living surface

Retune the living surface away from drafting-grid/HUD language.

Use:

- slow low-frequency violet/indigo ink fields;
- soft overlapping optical stains with asymmetric centers;
- hand-drawn contour ribbons with slight controlled irregularity;
- extremely subtle print/paper grain generated procedurally;
- one low-energy cyan optical focus region tied to response energy;
- dark center bias behind conversation copy.

Remove or materially reduce:

- obvious drafting grid;
- scanner-like calibration line;
- uniform topographic repetition;
- high-frequency neon motion.

### 4.2 Editorial trace

Create a reusable Skia editorial trace primitive for specification/execution surfaces.

It may include:

- one imperfect open contour line;
- a short cyan/violet focus mark;
- slow trace motion only while a section is active or newly changed;
- static equivalent under reduced motion;
- no continuous spinning/orbiting behavior.

### 4.3 Optical typesetter

Keep the existing live response inscription contract. Adjust fresh-glyph energy toward illuminated ink: softer lavender edge, smaller cyan hot point, less scanner-like beam dominance.

## 5. Product surfaces

### 5.1 Work Specification

- treat the specification as an editorial 'contract' section, not a card;
- show `SPEC` as quiet metadata and title/objective as the dominant reading hierarchy;
- DRAFT/APPROVED state remains explicit;
- approval action remains obvious and accessible;
- acceptance criteria are readable without resembling a ticketing dashboard.

### 5.2 Code run

- show run stage as the display anchor;
- show exact Work Specification revision and acceptance-count binding immediately below;
- preserve pause/resume/cancel controls;
- retain all v0.8 exact binding semantics;
- state presentation may use trace strokes and editorial accent, but must not imply execution progress that is not durably true.

### 5.3 Conversation

- preserve assistant content as the highest-contrast layer;
- user content remains contained but loses unnecessary box weight;
- metadata becomes quieter;
- composer remains visually strong enough to anchor the interaction but not a floating glossy pill.

## 6. Accessibility and restraint

- core narrative text targets WCAG AA contrast;
- minimum interaction targets remain unchanged;
- reduced motion freezes or removes trace/ink movement;
- reduced graphics preserves the same hierarchy without Skia;
- state meaning must not depend on color alone;
- grain/ink effects may not interfere with reading;
- decorative traces are `pointerEvents="none"` and excluded from accessibility semantics.

## 7. Functional non-regression

The visual release must not change:

- private session architecture;
- Reason state machine/SSE behavior;
- Work Specification persistence/revision/approval policy;
- approved Work Specification → EngineeringRun binding;
- server-owned acceptance map;
- protected Code stage validation;
- database schema;
- deployment authority boundaries.

## Security

Editorial Optical introduces no new trust authority, network path, credential flow, persistence class, or database capability.

Security requirements:

- no secret, provider credential, root access token, or database connection material may enter client-visible theme, trace, shader, or diagnostic state;
- decorative Skia state cannot mutate Work Specification approval, EngineeringRun binding, acceptance criteria, Code stage state, or release authority;
- operator approval remains a protected server mutation;
- protected Code acceptance ownership remains server-defined;
- the same-origin `/p2-api` browser boundary and signed HttpOnly session model remain unchanged;
- reduced-graphics fallback must not bypass authentication or protected API behavior;
- no external-site assets, fonts, code, trackers, or runtime dependencies are copied or embedded from the design reference.

## 8. Acceptance criteria

### AC-01 Editorial hierarchy

Specification and Code sections use stronger display hierarchy and more negative space than v0.8 without becoming dashboard cards.

### AC-02 Editorial framing

At least the Work Specification and Code run surfaces use open/asymmetrical framing rather than full uniform rectangular cards.

### AC-03 Living ink field

The Skia workplane visibly uses low-frequency violet/indigo ink fields, irregular contour ribbons, subtle procedural grain, and a response-linked optical focus; the prior obvious drafting-grid/calibration-line character is removed.

### AC-04 Trace primitive

A reusable Skia editorial trace primitive is present on governed product state surfaces and respects reduced motion.

### AC-05 Optical response continuity

The live optical typesetter remains functional, selectable, accessible, and state-driven with softened illuminated-ink energy.

### AC-06 Reduced-graphics parity

The fallback retains the new editorial hierarchy, accents, and open framing without requiring CanvasKit.

### AC-07 v0.8 trust preservation

Approved-spec binding, acceptance ownership, Code activation, pause/resume/cancel, Reason behavior, auth, and persistence tests continue to pass unchanged.

### AC-08 Responsive quality

Mobile, tablet, and desktop layouts remain free of horizontal overflow, clipped primary controls, and unreadable metadata.

### AC-09 Release integrity

Specification validation, API tests, client typecheck/state/export, browser/Skia acceptance, Code binding browser acceptance, protected Engineering/Reason/Code evaluation, DSPy release compilation, Vercel preview, and production verification pass before v0.9.0 is recorded as deployed.

## 9. Non-goals

- copying Anna's House branding, illustrations, menu layout, fonts, logos, or palette;
- replacing Deep Violet with a pastel theme;
- dashboard conversion;
- new navigation architecture;
- new backend behavior;
- autonomous execution/deployment;
- adding custom font binaries;
- high-frequency particles, spinning rings, scanning grids, or decorative HUD clutter.

## 10. Release gate

Implementation is authorized by this specification. `DESIGN-SYSTEM.md` must advance because Editorial Optical is a durable visual-language change. `CURRENT-STATE.md` updates only after validated preview/production evidence. `ARCHITECTURE.md` and `PROJECT-CONSTITUTION.md` change only if implementation crosses their durable boundaries.
