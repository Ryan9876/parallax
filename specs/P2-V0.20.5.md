## 1. Objective

Consolidate trustworthy operator-facing runtime telemetry, development economics and bounded retention around the existing Wave 4 run-event plane, Wave 6 durable runtime evidence, W7-S1 evaluation outcomes and W7-S2 known-state projection semantics.

S5 is an evidence/aggregation layer. It does not create a competing run/event state machine, execution scheduler or billing ledger and does not infer missing facts as zero.

## 2. Fixed decisions

- Existing Project, Work Specification, Engineering Run, source-lineage, worker, tool/provider and run-event stores remain authoritative.
- S5 derives summaries from persisted evidence; it does not become an execution authority or second source of run truth.
- Every metric has an explicit ownership/provenance contract and known state: `OBSERVED`, `ESTIMATED` or `UNKNOWN`.
- Unknown time/cost/usage/intervention values remain null/unknown, never zero-filled.
- Estimated values must identify the estimation method/version and cannot be promoted to observed merely because multiple estimates agree.
- Observed cost requires provider/runtime evidence that actually reports cost or billable usage under a documented conversion; request count alone is not observed cost.
- Quality trend evidence is derived from accepted protected deterministic/evaluation outcomes and never overrides deterministic failure.
- Retention is bounded by category/cardinality/age and may summarize or expire non-authoritative telemetry without deleting canonical Project/run/source or protected release evidence.
- No raw prompts, hidden reasoning/private scratchpad, credentials, cookies/auth headers, raw provider payloads, source bytes/patches or unrestricted logs are retained by this layer.
- Aggregation is Project-scoped by default; cross-Project aggregation requires an explicit server-owned aggregate scope and contains no per-Project private payload.
- S5 does not add production deploy, merge, source acceptance, provider administration, arbitrary command/network or REVIEW-completion authority.

## 3. Evidence model

### 3.1 Evidence ownership

Define a bounded metric/evidence catalog whose entries specify:

- metric identity and unit;
- authoritative input source(s);
- Project/run/source/evaluation identity dimensions that may be retained;
- observed versus estimated derivation rules;
- allowed aggregation dimensions;
- retention class;
- privacy/redaction class.

Caller/model/repository text cannot register metrics, change retention or reclassify estimated evidence as observed.

### 3.2 Core runtime economics

Initial supported metric families should remain small and useful:

- elapsed run/stage/attempt time when durable timestamps exist;
- model/provider usage when durable provider evidence contains bounded usage counts;
- cost when directly observed or computed from explicitly versioned server-owned price evidence;
- retry/recovery counts from durable worker/run facts;
- human intervention counts from durable pause/resume/cancel/spec-amendment/HUMAN_REQUIRED evidence;
- quality disposition/trend from protected deterministic and accepted independent-evaluation results.

If a metric lacks authoritative inputs, S5 returns `UNKNOWN` instead of attempting a guess.

### 3.3 Provenance

Every non-unknown value includes bounded provenance sufficient to identify derivation class/version and source evidence identity without returning raw private payloads. Aggregates preserve sample count and known/unknown coverage where material.

## 4. Aggregation and history

Provide bounded run/history summaries suitable for S3/S6 consumption:

- per-run summary;
- bounded recent-run trend for a Project;
- stage/attempt/recovery/intervention aggregates;
- quality pass/fail/pending trend;
- known-state economics coverage;
- retention/telemetry freshness status.

History requests have server-owned maximum windows/cardinality. No endpoint returns unbounded event history or raw logs.

## 5. Retention contract

### 5.1 Classes

Define at least:

- `CANONICAL_REFERENCE`: identity/digest references needed to bind telemetry to canonical evidence; S5 does not delete the canonical source record;
- `PROTECTED_RELEASE_EVIDENCE`: protected validation/evaluation/release verification references governed by existing release policy;
- `OPERATIONAL_SUMMARY`: bounded derived run/metric summaries retained for an explicit operational window;
- `EPHEMERAL_DIAGNOSTIC`: privacy-safe bounded diagnostics with the shortest permitted window.

### 5.2 Safety

Retention cleanup may delete/compact only S5-owned derived telemetry that is outside its retention window. It cannot delete Projects, Work Specifications, Engineering Runs, source lineage, protected attempts, source delivery, production evidence or other upstream authoritative data.

Deletion/compaction is idempotent, Project-safe and auditable. A retention failure cannot mutate canonical runtime state.

## 6. Privacy and cardinality

- Metric names/dimensions are an immutable server-owned allowlist.
- Free-form repository/model/user strings are not metric-label dimensions.
- IDs are bounded opaque canonical identities; high-cardinality arbitrary strings are rejected or normalized to fixed reason classes.
- No full URL query strings, auth headers, environment values, prompts, source contents or provider response bodies enter telemetry labels/payloads.
- Bounded summaries may contain approved reason/result codes, stage/status, provider/tool identity where already safe and necessary, and exact evidence references/digests.
- Cross-Project queries fail closed unless an explicit aggregate-only server authority exists.

## 7. Reliability and replay

- Re-projecting the same durable evidence produces the same metric identity/value/known-state/provenance.
- Duplicate event/replay ingestion cannot double-count a metric.
- Late evidence may advance an `UNKNOWN`/`ESTIMATED` value only under explicit derivation precedence; it cannot silently downgrade observed truth.
- S5 aggregation does not mutate Engineering Run revision/state, worker ownership or provider/source actions.
- Missing telemetry infrastructure degrades to explicit unavailable/unknown state rather than blocking protected run execution.

## 8. Scope

Authorized semantic scope may include:

- immutable metric/retention catalog;
- Project-scoped aggregation service over existing repositories/event plane;
- bounded economics and quality projection records compatible with W7-S2 known-state semantics;
- recent-history/query API suitable for later S3/S6 composition;
- privacy/cardinality guards;
- S5-owned derived telemetry persistence only if needed and justified by retention/query requirements;
- bounded idempotent retention cleanup for S5-owned derived rows only;
- focused tests for derivation, replay, privacy, cardinality and retention boundaries.

A database migration is permitted only if an S5-owned derived summary store is demonstrably necessary. Prefer query-time derivation from existing durable evidence when it meets bounded performance/reliability needs.

## 9. Non-goals

- new run/event state machine;
- job scheduler/resource scheduler;
- billing/accounting system;
- fabricated or zero-filled economics;
- arbitrary metrics/labels supplied by clients/models;
- raw tracing/log storage;
- prompt/reasoning/source/provider payload retention;
- deletion of canonical or protected evidence;
- source/provider/tool authority;
- production deployment/merge/REVIEW completion.

## 10. Acceptance criteria

### AC-01 Canonical evidence ownership
Every metric/summary derives only from documented server-owned Project/run/event/worker/evaluation/provider evidence and preserves exact canonical binding.

### AC-02 Known-state economics
Observed, estimated and unknown states are explicit; unknown never becomes zero and estimated never masquerades as observed.

### AC-03 Versioned provenance
Every known value includes bounded provenance/derivation identity sufficient to audit how it was produced without exposing private raw payloads.

### AC-04 Deterministic quality authority
Protected deterministic failure remains authoritative in quality summaries/trends and cannot be overridden by positive qualitative evaluation or Preview status.

### AC-05 Replay-safe aggregation
Duplicate/replayed event evidence does not double-count time, usage, retry, recovery, intervention or quality results; exact re-projection is deterministic.

### AC-06 Bounded history/cardinality
History windows, rows, metric names and dimensions are server bounded; arbitrary high-cardinality user/model/repository strings cannot become telemetry dimensions.

### AC-07 Project privacy
Cross-Project metric/history access fails closed except for an explicitly authorized aggregate-only server scope, and aggregate output exposes no private per-Project payload.

### AC-08 Safe retention ownership
Retention cleanup can affect only S5-owned derived telemetry in permitted retention classes and cannot delete/mutate Projects, Work Specifications, Engineering Runs, source lineage, protected attempts, delivery or release evidence.

### AC-09 Retention idempotency and auditability
Repeated cleanup is safe/idempotent, produces bounded audit evidence and cannot mutate canonical runtime state when cleanup fails.

### AC-10 Privacy-safe payloads
No credentials, cookies/auth headers, server environment, raw provider payloads, prompts, hidden reasoning, source bytes/patches, unrestricted logs or raw sensitive URLs are persisted or returned.

### AC-11 S2 compatibility
S5 metric output can populate/extend W7-S2 known-state economic presentation without redefining S2 identity/control authority or requiring client-side metric inference.

### AC-12 No authority expansion
S5 grants no new lifecycle, source acceptance, provider/tool administration, arbitrary command/network, merge/deploy or REVIEW-completion authority.

Before integration, S5 commits authentic DSPy evidence for `P2-V0.20.5`, reconciles to the latest accepted Wave 7 integration SHA, passes protected spec validation and applicable API/data/replay/privacy/cumulative gates, then stops `READY FOR INTEGRATION` for Control Tower expected-head merge.
