## 1. Objective

Correct the protected evidence semantics exposed by the first real W9-S1 Decision Ledger application. `static-web-v1` BUILD/TEST/VERIFY currently proves only bounded structural properties, but the autonomy coordinator unconditionally labels every protected acceptance criterion as verified after successful TEST and VERIFY. P2-V0.23.40 must make that evidence truthful without weakening structural validation, changing the immutable execution contract, inventing benchmark-specific checks, or bypassing human REVIEW.

For PLAN-bound `static-web-v1` runs, successful structural TEST/VERIFY must explicitly record that all protected acceptance criteria remain unverified by that structural profile. The run may still progress to the existing REVIEW boundary because REVIEW is already the human completion authority, but protected execution must not claim behavioral proof it did not produce.

Python and .NET execution evidence retains the existing exact-acceptance verification contract in this slice.

## 2. Verified finding and fixed decisions

- P2-V0.23.39 is merged and production-accepted; frozen W9-S1 source delivery succeeded through exact branch, accepted-lineage commit, GitHub PR and READY Vercel Preview while the Engineering Run remained REVIEW revision 6.
- The delivered Decision Ledger candidate contains only `index.html`, `styles.css` and `app.js`.
- `static_web_validator.py` checks root/file safety, `index.html`, JavaScript syntax and local references. It does not execute CRUD, persistence, import/export, responsive, accessibility or other behavioral acceptance tests.
- `AutonomyCoordinator.run()` currently assigns the full run acceptance map to `acceptance_ids_verified` for TEST/VERIFY whenever execution returns `protected_success=true`, regardless of the selected execution contract's actual verification capability.
- `EngineeringRunService.complete_stage()` then requires that full list and records the stage as passed, converting structural success into protected universal acceptance proof.
- Source inspection proves the false-positive is material, not semantic nitpicking: the Decision Ledger import validator accepts records with only string `id`, string `title` and a supported `status`; malformed values such as non-array `tags` can therefore be persisted and later break rendering even though the frozen import requirement says invalid import must fail safely without corrupting existing valid data.
- The delivered candidate also contains no automated test files while the frozen objective explicitly requires automated coverage of core CRUD, persistence, search/filter and import behavior.
- The fix must be generic to the closed server-owned execution contract. No benchmark/template ID, acceptance keyword, fixture digest, repository name or candidate content may create the evidence mode.
- `static-web-v1` itself remains unchanged in this slice. Browser/behavioral verification is a later capability unless separately governed.

## 5. Architecture requirements

### 5.1 Structural success and acceptance verification are separate facts

A successful static-web structural TEST/VERIFY proves only that the immutable server-owned static-web command completed successfully against the exact accepted source lineage. It must not imply that the Work Specification's behavioral acceptance criteria were proven.

The structural-only evidence envelope is exactly:

- `acceptance_verification_scope = "STRUCTURAL_ONLY"`;
- `acceptance_ids_targeted` exactly equals the protected acceptance map;
- `acceptance_ids_verified = []`;
- `acceptance_ids_unverified` exactly equals the protected acceptance map.

No duplicates, omissions, additions or alternate scope strings are valid.

### 5.2 The admissible evidence mode is derived from durable PLAN authority

`EngineeringRunService` must independently inspect the latest passed PLAN attempt for the run, parse `ExecutionContractIdentity`, resolve it through the existing closed server catalog, and require exact identity equality before admitting structural-only TEST/VERIFY evidence.

Only resolved `ExecutionContractCode.STATIC_WEB` / `GREENFIELD_STATIC_WEB` may use the structural-only envelope. Missing, malformed, partial, drifted or forged PLAN execution-contract identity fails closed under existing protected evidence/contract failure behavior.

Current-stage evidence cannot self-declare a structural-only privilege.

### 5.3 Full verification semantics remain exact for other contracts

Existing Parallax Python and bounded .NET TEST/VERIFY continue to require `acceptance_ids_verified` to exactly equal the protected acceptance map. P2-V0.23.40 does not broaden partial verification to arbitrary validators or caller-selected tools.

### 5.4 REVIEW remains the completion authority

A static-web run with structural-only TEST/VERIFY may still transition through VERIFY to REVIEW when the structural commands pass. REVIEW completion remains governed by the existing `validate_review` requirement: an operator review recommending PASS must verify the exact protected acceptance map against the current implementation workspace digest.

Therefore P2-V0.23.40 reduces false protected claims without adding a new autonomous completion path.

### 5.5 Observability must expose the distinction safely

Durable execution evidence and safe observability may expose the fixed scope plus acceptance targeted/verified/unverified IDs and counts. They must not expose hidden reasoning, secrets, provider credentials or unrestricted candidate content.

Existing event identity, lineage, operation, stage outcome and source evidence remain unchanged.

## 6. Security and authority

The structural-only mode is a contraction of claimed authority, not an expansion. It is available only when durable PLAN evidence independently resolves to the exact existing static-web contract. Candidate code, user text, model output at TEST/VERIFY, browser state and request payloads cannot manufacture it.

No new command or external system is introduced. Structural BUILD/TEST/VERIFY still runs under the same sandbox, network policy, source-lineage reconstruction and immutable execution contract. Human REVIEW remains required before completion.

## 7. Reliability, compatibility and rollback

No database migration or execution-contract digest change is allowed. Existing durable PLAN identities therefore remain byte/identity compatible. Runs already at REVIEW remain untouched; new or resumed static-web TEST/VERIFY attempts after the release use truthful structural-only evidence.

Rollback is operationally safe but reintroduces false universal acceptance claims for static-web TEST/VERIFY. Python/.NET behavior must be regression-identical before and after the release.

## 10. Risks

The primary risk is replacing false full verification with a generic partial-verification escape hatch. The mitigation is exact durable PLAN resolution: only the existing closed-catalog static-web contract can admit `STRUCTURAL_ONLY`, and its partition is fixed server-side.

A second risk is breaking old execution-contract identities by adding verification capability to their digest. The mitigation is explicit: no execution-contract/profile digest change is part of this release.

A third risk is reducing product quality by treating truthful partial evidence as sufficient. It is not sufficient for completion: the run still stops at REVIEW and the remaining criteria are explicit. A later governed browser/behavioral verifier may reduce the unverified set, but P2-V0.23.40 does not manufacture that proof.
