# Parallax 2.0 — Safe Conversation and Project Deletion

Spec ID: P2-V0.18.11
Status: APPROVED FOR IMPLEMENTATION
Date: 2026-08-27
Workstream: #290 / `WS-SAFE-DELETION`
Base: `f99996d3c04cd23a81845fac87ec658ccf8702fd`

## 1. Objective

Add an explicit, safe way for an authenticated Parallax operator to remove old conversations and Projects from the active workspace while preserving protected engineering evidence, exact source lineage, provider resources, auditability, authentication boundaries, and the existing Project/Work Specification/Engineering Run authority model.

User-visible **Delete** is a logical lifecycle operation. It removes an item from active product surfaces; it is not a destructive purge of protected engineering records or external provider resources.

## 2. Product behavior

- Old conversations expose an explicit Delete action with a confirmation step before mutation.
- Old Projects expose an explicit Delete action with a confirmation step before mutation.
- The currently open conversation and currently bound Project are not offered as one-tap delete targets in the ordinary UI; the operator must first move to another context.
- A deleted conversation disappears from active conversation lists and ordinary direct reads.
- A deleted Project disappears from active Project selection and ordinary direct reads. Conversations bound to that deleted Project also disappear from active conversation history.
- A deleted Project's owner-local slug and repository identity may be reused by a newly created Project.
- If deletion is blocked because engineering work is still active, the UI shows the server-provided safe explanation rather than pretending deletion succeeded.

## 3. Persistence contract

### Conversations

Add nullable `deleted_at` to `conversations`. Logical deletion sets that timestamp and updates `updated_at`. The conversation row, messages, Work Specifications, Engineering Runs and downstream protected evidence remain persisted.

Active conversation queries and ordinary conversation reads exclude rows with `deleted_at IS NOT NULL`. Conversations bound to a logically deleted Project are also excluded from active conversation surfaces even when the conversation row itself is not tombstoned.

### Projects

Add nullable `deleted_at` to `projects`. Logical deletion sets `status = 'deleted'`, sets `deleted_at`, and updates `updated_at`.

Existing owner-local uniqueness for `(owner_subject, slug)` and `(owner_subject, repository_ref)` becomes active-row-only uniqueness so a logically deleted Project does not permanently reserve its prior slug or repository identity. `workspace_ref` remains globally unique and immutable for the retained tombstone.

The migration must be additive, rerunnable where supported by the migration runner, and compatible with a database where the migration has already been applied before application promotion.

## 4. Engineering Run deletion guard

Deletion is blocked with HTTP 409 when a relevant Engineering Run is not terminal.

The authoritative terminal-state definition is the existing protected runtime contract in `code.domain.TERMINAL_STAGES`; deletion logic must not invent a narrower or wider independent lifecycle. At this revision the terminal set is `COMPLETE`, `SPEC_AMENDMENT`, and `CANCELLED`.

- Conversation deletion checks Engineering Runs bound to that conversation.
- Project deletion checks Engineering Runs bound to that Project.
- `FAILED` is not treated as terminal merely because the latest attempt failed; the protected run must reach an existing terminal state before deletion proceeds.

## 5. Authentication and ownership

All deletion routes remain behind `access_principal`.

Project-bound conversation access continues to derive ownership from the canonical Project owner relationship. Cross-owner Project/conversation mutation must remain fail-closed and return the same not-found behavior used by protected reads.

Historical unbound conversations predate canonical Project ownership and are intentionally readable under the existing compatibility contract. Because they do not carry a durable per-conversation owner identity, destructive deletion of an unbound historical conversation requires application `owner` role. A non-owner may not use the compatibility read path as destructive authority.

Project deletion continues to require the authenticated principal to own the canonical Project row; no caller-supplied owner identity is accepted.

No delete route accepts provider, repository, workspace, source-lineage, credential, deployment, or filesystem authority from the caller.

## 6. Evidence and external-resource preservation

Logical deletion must not delete, cascade-delete, rewrite, or invalidate:

- Work Specification rows or approved specification evidence;
- Engineering Runs;
- Engineering Attempts;
- Engineering Run Events;
- worker execution/checkpoint/recovery records;
- source-lineage manifests, heads, immutable source objects or last-known-good evidence;
- release/deployment evidence;
- GitHub repositories, branches, commits, pull requests or credentials;
- Vercel Projects, deployments, Preview deployments or credentials.

The feature adds no external provider delete call.

## 7. Client surfaces

### Desktop

- Recent conversation history exposes Delete only for non-current entries.
- Confirmation is inline or modal, clearly names the destructive workspace action, and does not imply protected evidence or GitHub/Vercel resources are erased.
- The Project workspace exposes active Projects and permits deletion of a non-current Project with explicit confirmation.

### Compact/mobile

- Project/history management exposes the same governed Project deletion behavior.
- Recent conversation cleanup is reachable from the compact Project/history management surface.
- Controls meet the existing touch-target/accessibility conventions and provide accessibility labels/hints for delete and confirmation actions.

Client state removes the item only after the API returns success. HTTP 409/401/403/404 responses remain visible as bounded safe errors.

## 8. Non-goals

- hard purge, retention scheduling, bulk delete, recycle-bin/restore UI, or automatic archival;
- deleting GitHub/Vercel resources;
- deleting protected engineering evidence;
- changing Work Specification approval, Engineering Run transition, source-lineage, worker, tool, provider, REVIEW/HUMAN_REQUIRED, merge, or production authority;
- adding a second Project identity system;
- broad multi-user conversation-ownership migration;
- changing Wave 6 semantic agent-control-plane contracts;
- allowing deletion of an active run by treating a failed attempt as run completion.

## 9. Acceptance criteria

### AC-01 Conversation logical deletion
An authenticated authorized operator can delete an inactive conversation they have destructive authority over. The API returns 204; the conversation remains persisted with `deleted_at`, but active list/read surfaces return no active record for it.

### AC-02 Conversation active-run guard
If any Engineering Run for the conversation is outside `TERMINAL_STAGES`, DELETE returns 409 and the conversation remains active. A run in `COMPLETE`, `SPEC_AMENDMENT`, or `CANCELLED` does not block deletion.

### AC-03 Project logical deletion
An authenticated principal that owns an inactive Project can delete it. The API returns 204; the Project remains persisted with `status='deleted'` and `deleted_at`, while active Project list/read surfaces hide it and active conversation history hides conversations bound to it.

### AC-04 Project active-run guard
If any Engineering Run for the Project is outside `TERMINAL_STAGES`, DELETE returns 409 and the Project remains active.

### AC-05 Protected evidence preservation
Focused tests prove successful conversation/Project deletion retains the underlying conversation/Project tombstone where applicable, Work Specifications, Engineering Runs and representative downstream evidence rows. No GitHub/Vercel delete integration is added.

### AC-06 Project identity reuse
After Project deletion, a new Project owned by the same principal can reuse the deleted Project's slug and repository identity without reusing the deleted Project's canonical ID or workspace identity.

### AC-07 Fail-closed destructive authorization
Cross-owner bound Project/conversation deletes return not found and do not mutate data. Historical unbound conversation deletion requires application `owner` role because those rows have no durable per-conversation owner identity.

### AC-08 Desktop deletion UX
Desktop recent-conversation and Project management surfaces expose explicit confirmation, do not offer ordinary one-tap deletion for the current context, remove successful deletions from local active state, and show server conflict errors when blocked.

### AC-09 Compact/mobile deletion UX
Compact/mobile Project/history management exposes Project and conversation deletion with explicit confirmation, accessible labels/hints and server-authoritative success/error behavior.

### AC-10 Migration safety
The additive migration creates `deleted_at` columns/indexes and active-row-only Project uniqueness without deleting or rewriting existing business rows. Application code remains compatible when production already has this migration applied.

### AC-11 Regression protection
Existing authentication, Project binding, conversation, Work Specification, Engineering Run, response-state, browser/export and bounded-autonomy checks remain green. The feature changes no provider, source-lineage, tool, evaluation or deployment authority.

### AC-12 Governed release verification
The exact implementation head passes Workstream Spec Validation, Bounded Autonomy and P2 CI. Merge uses expected-head protection. Production client/API deployments are tied to the merged application SHA; `/health`, `/ready`, authenticated list/delete behavior and post-cutover runtime-error scans pass before the feature is called deployment-verified.
