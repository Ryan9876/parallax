## 1. Objective

Establish the durable Wave 4 product contract for two changes that must ship as one coherent experience: a mockup-faithful warm editorial Parallax design system and operator-facing Live Development / Observability over the existing protected autonomous app-builder runtime.

Wave 4 must make the deployed Wave 3 execution system understandable while it is working. The operator should be able to see authoritative run stage, actual file/diff changes, bounded registered-command and test evidence, retry/correction/recovery events, exact source-lineage identity, GitHub/Vercel Preview delivery, protected evaluation and human-review boundaries in near real time. The product must not simulate work, expose hidden chain-of-thought, create a generic IDE/shell, or introduce a second execution/provider/evaluation authority.

The visual target is the user-approved Parallax mockup family from the active product conversation: dark forest/olive navigation, warm ivory/cream workplane, rust-orange primary action and active navigation, teal live/interactive accents, restrained olive support/success, charcoal text, editorial display hierarchy, soft rounded cards, subtle organic depth and a calm premium engineering workspace.

## 2. Scope

This contract owns the durable Wave 4 experience and design rules only. It authorizes later bounded workstreams to implement:

- append-only Project/run-scoped runtime event projection;
- resumable authenticated live event transport;
- protected read-only exact-lineage source and diff views;
- bounded command/test/evidence views derived from protected execution evidence;
- mockup-faithful responsive application shell;
- Live Build / Observability workspace;
- permanent end-to-end browser, accessibility, visual and runtime reference proof.

This workstream itself changes no application runtime, migration, provider contract, API route or client implementation.

## 3. Fixed product decisions

- **One product cycle.** Theme replacement and Live Development/Observability are one Wave 4 program. They may be implemented in narrow dependent workstreams but are validated together before release.
- **Wave 3 remains authoritative.** Canonical Project identity, approved Work Specification binding, Engineering Run state, accepted source lineage, worker lease/checkpoint authority, protected mutation, registered commands, deterministic browser validation, correction/LKG policy, tool/provider authority, protected evaluation and operator REVIEW are not replaced or weakened.
- **Observation is not execution.** Live event streams and UI state project persisted runtime truth. Browser presence, scrolling, selected tab or observer connection does not own worker execution.
- **No simulated progress.** UI stages, events, status pills and percentages may advance only from authoritative server facts. Loading placeholders may indicate unavailable data but cannot imply completed engineering work.
- **No hidden reasoning.** Product telemetry may expose actions, bounded inputs/outputs, file/diff identity, command/test evidence, provider actions, evaluation and recorded decision/stop codes. Hidden chain-of-thought, scratchpad and private model reasoning remain forbidden.
- **Not a general IDE.** Code/diff/source inspection is exact-lineage read-only product evidence. Terminal output is registered protected command/test evidence, never arbitrary shell access. Provider panels expose bounded identities/status, never generic HTTP/provider payloads.
- **Conversation remains primary.** Live Build is an inspectable governed surface reachable from the active Project/conversation/run. It must not turn the default product into an always-dense operations dashboard.
- **Desktop follows the approved mockup closely.** Major column proportions, sidebar treatment, header hierarchy, cards, run pipeline, central event workspace, right utility rail and bottom summary rhythm are explicit visual acceptance targets.
- **Mobile reflows.** Phone layouts use focused tabs/drawers/stacked cards; they do not shrink the desktop dashboard to unreadable scale.
- **Observer controls are distinct from run controls.** `Follow Live`, `Pause View` and `Jump to Latest` affect presentation only. Protected `Pause Run`, `Resume Run`, `Cancel Run` and REVIEW actions retain server-side authorization/state-machine rules.
- **Theme tokens are centralized.** Production surfaces consume semantic tokens rather than accumulating one-off mockup colors.
- **Standing release authorization remains bounded.** `PROJECT-CONSTITUTION.md` v1.4 may authorize final validated Parallax production promotion while single-user conditions remain true, but it never waives exact-head gates, rollback, migration safety, least privilege or deployment verification.

## 4. Architecture requirements

### 4.1 Experience information architecture

Desktop uses a three-region product composition when Live Development is open:

1. dark forest navigation rail with Parallax identity and product navigation;
2. warm primary workplane containing greeting/context, run pipeline, metrics and event/Live Build workspace;
3. warm right utility rail containing System Health, Active Run and Recent Alerts / activity.

Normal conversation remains available as the primary creation surface. Observability may be a navigation destination and a run-level detail surface, but the operator must not need to understand worker internals to start or continue a Project.

### 4.2 Live run projection

The run pipeline uses the authoritative lifecycle:

`SPECIFY -> PLAN -> IMPLEMENT -> BUILD -> TEST -> VERIFY -> REVIEW -> COMPLETE`

The product may visually shorten `SPECIFY` to `SPEC` where space requires, but server identity remains `SPECIFY`. Completed/current/pending visual states must derive from persisted run/attempt facts. Recovery states such as `STALLED`, `RECOVERING`, `REASSIGNED`, `HUMAN_REQUIRED` and failure/stop codes are surfaced without inventing a competing stage machine.

### 4.3 Live Build workspace

The central Live Build surface supports these operator views when data is available:

- `Code` — exact accepted/candidate lineage file content selected through protected read contracts;
- `Diff` — bounded diff between exact immutable lineage identities;
- `Terminal` — bounded redacted output from registered protected execution only;
- `Tests` — normalized test/build/validation progress and outcomes;
- `Events` — ordered durable run events;
- `Evidence` — bounded Project/spec/run/lineage/attempt/provider/evaluation identities and links.

A file tree is a bounded projection of the exact lineage, not a general server filesystem browser. Source content is not copied into telemetry merely for display.

### 4.4 Durable event semantics for later workstreams

Wave 4 event implementation must be append-only and Project/run scoped, with monotonic per-run sequence and stable event identity. Events may reference exact worker execution, stage, attempt, source lineage, operation, artifact and evidence identities. Reconnect/replay must not duplicate runtime/provider mutation or duplicate displayed accepted events.

Event persistence is observation evidence. Existing Engineering Run, worker, source-lineage, provider and evaluation stores remain authoritative for their domains.

### 4.5 Streaming behavior

Live transport must support reconnect from durable sequence. Observer disconnection cannot be interpreted as run cancellation/success. The interface defaults to following the live edge while allowing operator scroll/selection to pause auto-follow without stopping execution. `Jump to Latest` restores follow behavior.

Where infrastructure cannot guarantee work continues after request/process loss, the existing Wave 3 worker recovery/reassignment contract remains the only authority for recovery; Wave 4 must not claim stronger background guarantees than runtime evidence proves.

### 4.6 Warm editorial visual system

The durable palette direction is:

- forest substrate/navigation: very dark olive/forest rather than navy/violet;
- warm workplane: ivory/cream rather than dark optical substrate;
- primary action/active navigation: burnt rust/orange-red;
- live/interactive accent: flat deep teal;
- support/verified accent: restrained olive/green with explicit state text;
- primary text: near-charcoal;
- secondary/muted text: warm grey/olive-charcoal;
- borders: low-contrast warm stone/olive;
- danger/warning: warm red/amber distinct from the rust brand action.

### 4.7 Typography and material

Display/greeting/major editorial headings use a serif presentation on platforms where a reliable bundled/system serif is available; ordinary UI controls, technical metadata, source, tests and conversation body remain highly legible sans-serif/monospace as appropriate. No external font dependency is required to satisfy the design.

Cards use warm low-contrast surfaces, approximately 14–20 px desktop corner radii, subtle warm shadow/depth and restrained borders. Decorative organic curves/landscape treatment remain low contrast and cannot compete with content.

### 4.8 Desktop mockup fidelity

The later client workstream must preserve these visual relationships at standard desktop width:

- navigation rail approximately 16–20% of the viewport, visually dark and stable;
- primary workplane is the dominant width;
- utility rail is narrower than the workplane and remains secondary;
- greeting/header stays above the primary run/workspace surface;
- run pipeline is a prominent horizontal card;
- KPI cards form one restrained compact row rather than dominating the page;
- event/Live Build content receives the largest central working area;
- right-rail cards share consistent radius, spacing and warm material;
- summary cards/sparklines are subordinate context, not the main task.

Browser screenshot acceptance may tune precise responsive percentages, but major region order/proportions cannot be changed merely for implementation convenience.

### 4.9 Mobile and accessibility

At phone widths the product exposes focused sections such as `Run`, `Activity`, `Code`, `Tests`, `Evidence` and `Health`. File selection may use a drawer/sheet. Code/diff/terminal content receives full available width. Right-rail information stacks below or moves to tabs.

Existing protected rules remain: accessible selectable text, non-color state labels, minimum practical touch targets around 44 pt, at least 16 CSS px editable text on phone web, visualViewport keyboard accommodation, user zoom preserved, reduced-motion/reduced-graphics equivalents and no information available only through animation/hover.

### 4.10 Visual validation

The approved warm editorial home and Observability mockups are product references, not runtime evidence. Later implementation must convert them into machine-checkable browser/screenshot assertions for geometry, hierarchy, token use and responsive behavior. Deterministic functional/accessibility failures always outrank visual similarity.

## 5. Security and privacy

- Observability remains behind the existing authenticated owner-scoped Project/run boundary.
- Cross-Project event/source/diff/evidence access fails closed.
- Raw private source is fetched only through exact-lineage protected reads and is not persisted into generic telemetry events.
- Secret-sensitive paths, credentials, auth headers/cookies/environment, provider tokens, root credentials and Vercel execution credentials are never emitted to the client.
- Raw provider responses and generic provider transport bodies are forbidden.
- Hidden reasoning, prompts/scratchpads and model-private deliberation are forbidden from events, command views, evidence views and persisted telemetry.
- Command output is bounded and redacted; Live Build does not add arbitrary command/shell/network authority.
- Source/diff display does not add write authority. Mutation continues only through the existing protected implementation/correction seams.
- GitHub/Vercel links/status do not add merge, production-promotion, alias/domain, environment or secret-management authority.
- A visual theme change cannot weaken authentication, Project identity, Work Specification, lineage, worker, validation/evaluation or production-control boundaries.

## 6. Failure and recovery boundaries

- Missing/unavailable event data renders an explicit unavailable/degraded state; the UI must not infer success from silence.
- Event persistence/replay failure cannot advance the authoritative Engineering Run.
- Duplicate/replayed event identity is de-duplicated for presentation without suppressing distinct retries/attempts.
- Observer disconnect/reconnect resumes from durable sequence when available and never creates a second worker/provider mutation.
- Process loss remains governed by the Wave 3 worker lease/checkpoint/recovery contract.
- Recoverable provider/test/dependency failures are shown as recoverable only when the server classification says so.
- `HUMAN_REQUIRED`, specification amendment, credential/authority boundary and REVIEW remain explicit operator boundaries and cannot be styled as ordinary retry.
- Exact-lineage source/diff content unavailable or rejected yields a bounded error state rather than a fallback to unrelated fresh checkout/source.
- Reduced graphics/motion or narrow viewport preserves all product capability.
- If visual fidelity conflicts with accessibility, security or authoritative state truth, those protected requirements win; the visual discrepancy is then resolved by design adjustment rather than policy weakening.

## 7. Non-goals

- rewriting the Wave 3 autonomous runtime, worker state machine, source-lineage system, tool registry, provider clients, evaluator or correction policy;
- exposing model chain-of-thought, scratchpad or unrestricted prompt traces;
- adding a generic terminal, shell, HTTP client, filesystem editor, provider console or production deployment button;
- allowing the client to define Project/run/source-lineage identity or event success;
- making Observability the mandatory default landing page for ordinary conversation work;
- introducing a separate analytics/telemetry vendor as an authority dependency merely to render the product surface;
- optimizing for dense developer dashboards at the expense of a non-technical operator;
- claiming production deployment solely because a mockup, fixture, test adapter or Preview looks correct.

## 8. Acceptance criteria

### AC-01 Wave 4 preserves the deployed Wave 3 authority model
The durable experience contract explicitly keeps canonical Project/Work Specification/run/source-lineage/worker/tool/provider/evaluation/REVIEW authority server-owned and forbids Live Development/Observability from creating a competing state or mutation path.

### AC-02 Live Development exposes real bounded engineering activity without hidden reasoning
The product contract permits actual stage/action/file/diff/registered-command/test/provider/evaluation/recovery evidence while explicitly rejecting hidden chain-of-thought, scratchpad, raw provider payloads, credentials and unrestricted logs.

### AC-03 Run progress is authoritative and never simulated
SPECIFY/PLAN/IMPLEMENT/BUILD/TEST/VERIFY/REVIEW presentation, completion state, retries, recovery and stop reasons derive only from persisted runtime facts; fixture/placeholder/loading state cannot masquerade as live successful work.

### AC-04 Observation remains independent from execution authority
Follow Live, Pause View, tab selection, scrolling, disconnect and reconnect cannot pause, cancel, resume, advance or duplicate the worker. Protected Pause/Resume/Cancel/REVIEW controls remain distinct server-authorized actions.

### AC-05 Source, diff and terminal views remain bounded read-only evidence surfaces
Code/diff views are tied to exact immutable source-lineage identities, and terminal/test views consume bounded redacted registered-command evidence. No general filesystem write, shell, command or network surface is authorized.

### AC-06 Warm editorial design replaces the prior dominant violet visual identity
The durable design direction specifies dark forest/olive navigation, warm ivory/cream workplane, rust active/action color, flat teal live interaction, restrained olive status/support and charcoal content, with centralized semantic tokens and no silent fallback to the previous dominant violet/cyan theme.

### AC-07 Desktop implementation is constrained by the approved mockup composition
Later client acceptance must preserve the three-region desktop hierarchy, prominent run pipeline, compact KPI row, dominant central event/Live Build workspace, secondary right utility rail and subordinate summary rhythm, with screenshot/browser assertions rather than subjective prose alone.

### AC-08 Mobile, accessibility and reduced-motion behavior remain first-class
Phone layouts reflow into focused tabs/drawers/stacked content; touch, text size, zoom, keyboard/visualViewport safety, selectable content, explicit state labels, reduced motion and reduced graphics preserve equivalent capability.

### AC-09 Durable event projection is append-only, scoped and replay-safe
Later telemetry implementation must use stable Project/run-scoped event identity with monotonic per-run ordering, preserve source/attempt/evidence references, resume after process/observer recreation and avoid duplicate accepted event display or duplicate runtime/provider mutation.

### AC-10 Failure and human boundaries remain truthful
Unavailable/degraded telemetry, recoverable execution failures, process recovery, HUMAN_REQUIRED, specification amendment, credential/authority boundaries and REVIEW are visually/textually distinct and cannot be converted into success or generic retry by the client.

### AC-11 Visual validation is subordinate to deterministic correctness and security
Mockup/screenshot similarity is a protected product requirement, but deterministic functional/accessibility/security/runtime evidence remains higher precedence. Visual acceptance may not waive protected failures or production boundaries.

### AC-12 Wave 4 releases retain Wave 3 exact-head and production evidence rules
Every implementation workstream remains spec-first with authentic DSPy evidence and exact-head protected gates. Final integrated release requires browser/accessibility/visual proof, migration readiness where applicable, Preview/rollback evidence and deployment verification before `CURRENT-STATE.md` records production; standing single-user release authorization removes only a repeated approval wait.
