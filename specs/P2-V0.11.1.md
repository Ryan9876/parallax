# Parallax 2.0 v0.11.1 — Mobile Viewport Polish

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.11.1
Depends on: P2-V0.11.0
Method: screenshot-driven mobile regression correction + exact-head release verification

## 1. Objective

Correct the mobile layout defects exposed by production use without changing Parallax product behavior, identity, authentication, reasoning, specification, execution, or backend contracts.

## 2. User outcome

On phone-sized viewports the active conversation remains the visual center. Work Specification chrome no longer consumes a disproportionate share of the screen, the signed-in account control no longer floats across governed content, and all controls remain reachable without clipping or horizontal overflow.

## 3. Scope

- Preserve the v0.11.0 Editorial Optical conversation material and living surface.
- Add a compact mobile presentation for Work Specification status.
- Keep the specification state, capture/refresh/approve actions, revision identity, and explicit expansion behavior unchanged.
- On mobile, hide secondary specification copy until the governed surface is expanded.
- Keep the compact collapsed Work Specification surface materially shorter than the desktop presentation.
- Reposition and compact the signed-in account control on mobile so it occupies top-bar space instead of overlapping Work Specification content.
- Ensure the access-management panel fits within a phone viewport.
- Preserve minimum 44 pt primary mobile interaction targets where applicable.
- Add browser acceptance assertions for mobile Work Specification and account-control geometry.
- Preserve Google OAuth/authorization, Reason, Code, SSE, durable conversations, Work Specifications, approved-spec execution binding, Engineering Runs, persistence, Skia, reduced motion, and reduced graphics.

## 4. Security

This release does not change the v0.10.0 authentication or authorization boundary.

- Google/Supabase remains the identity provider boundary.
- Parallax server-owned authorization remains authoritative.
- No provider token, root bearer, service secret, or private credential is added to mobile UI state.
- The account-control change is presentation-only; owner/member privileges and server-side enforcement are unchanged.
- Existing protected browser requests and signed HttpOnly session behavior remain unchanged.

## 5. Mobile Work Specification contract

At widths below the existing compact breakpoint:

- the collapsed surface uses reduced outer margins and padding;
- the title remains legible but is limited to a compact reading height;
- the explanatory subtitle is omitted while collapsed;
- actions remain visible and accessible without forcing the title into an unusably narrow column;
- action layout may wrap or stack to preserve readable text and touch targets;
- the decorative trace remains subordinate and may be reduced in visual prominence;
- expanding the specification reveals the full objective and governed contract content;
- desktop/tablet behavior remains materially unchanged.

## 6. Mobile account-control contract

At phone widths:

- the account launcher becomes a compact control rather than the full name/role pill;
- it occupies reserved top-bar space and must not overlap Work Specification or conversation content;
- its accessible label remains `Parallax access menu`;
- opening it shows the same owner/member controls as desktop;
- the panel width is bounded to the available viewport with safe side margins;
- sign-out and owner-management behavior are unchanged.

## 7. Accessibility

- All state remains available in explicit text when the relevant governed surface is opened.
- The compact account launcher retains an accessible name even when visual name/role text is hidden.
- Expansion state remains exposed through accessibility state.
- No content depends on color or motion alone.
- Reduced-motion and reduced-graphics behavior remains unchanged.

## 8. Acceptance criteria

### AC-01 Mobile governed-surface density
At a 390x844 viewport, the collapsed Work Specification surface is compact and does not dominate the conversation viewport.

### AC-02 No account overlap
At a 390x844 viewport, the account launcher does not geometrically overlap the Work Specification surface.

### AC-03 Mobile access panel fit
The opened access panel remains fully within the phone viewport width with safe side margins.

### AC-04 Action usability
Capture, refresh, approve, expand/collapse, send, and access controls remain reachable and correctly labeled.

### AC-05 Specification semantics preserved
Drafting, approval, revision identity, expansion, and durable specification content behave exactly as before.

### AC-06 Desktop regression protection
Desktop Work Specification and account-control presentation retain the established v0.11.0 hierarchy.

### AC-07 No horizontal overflow
Mobile, tablet, and desktop browser acceptance report no document or composer horizontal clipping.

### AC-08 Product regression protection
Google identity/authorization, Reason, Code, SSE, durable conversations, Work Specifications, approved-spec execution binding, Engineering Runs, API protection, persistence, Skia, reduced motion, and reduced graphics continue to pass existing tests.

### AC-09 Release verification
Specification validation, API tests, client typecheck/state tests, web export, browser/Skia acceptance, Google-auth browser acceptance, Code-binding browser acceptance, protected evaluation, DSPy release compilation, Vercel READY state, health/readiness, protected-route checks, and runtime-error checks pass before v0.11.1 is recorded as deployment-verified.

## 9. Non-goals

- Redesigning desktop Work Specification.
- New Work Specification capabilities or workflow states.
- Authentication, authorization, API, schema, or database changes.
- Navigation redesign.
- Replacing the v0.11.0 conversation material or living surface.
- Broad typography or color-system changes.

## 10. Risks and mitigations

- **Compact mode hides too much context:** keep status/title/actions visible and preserve full contract behind explicit expansion.
- **Account launcher becomes ambiguous:** retain the existing accessible label and role-colored dot while hiding verbose mobile text.
- **Responsive changes drift desktop:** isolate compact behavior behind the existing phone breakpoint and keep desktop styles unchanged.
- **Screenshot-specific overfitting:** validate 390x844, tablet, and desktop browser geometry rather than targeting one device screenshot only.

## 11. Release gate

Implementation is authorized by this specification. Production promotion requires exact-head release validation and production deployment evidence. `CURRENT-STATE.md` must be updated after verified production promotion. `DESIGN-SYSTEM.md` changes only if the implementation establishes a durable new responsive rule beyond this corrective compact behavior. `ARCHITECTURE.md` and `PROJECT-CONSTITUTION.md` remain unchanged unless implementation reveals a durable architecture or governance change.
