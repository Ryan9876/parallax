# Parallax 2.0 v0.2.0 — Evaluation Spine Specification

Status: APPROVED FOR IMPLEMENTATION
Spec ID: P2-V0.2.0
Depends on: P2-V0.1.0
Method: Spec-first + DSPy-governed optimization

## 1. Objective

Build the protected evaluation spine that Parallax 2.0 will use to measure, compare, and promote AI-program behavior before broad DSPy optimization begins.

The purpose of v0.2.0 is not to make Parallax produce smarter answers by itself. It is to make future improvements measurable and difficult to game. The release must establish versioned benchmark cases, deterministic protected scoring, development-versus-promotion suite separation, immutable evaluation evidence, and a challenger-promotion gate that can reject regressions even when an optimizer reports improvement on its own development set.

This is the foundation for the later Reason 2.0, Code 2.0, closed-loop repair, and MIPROv2 optimization phases.

## 2. User outcome

A Parallax engineer can run a reproducible benchmark against a named AI-program version, inspect per-case scores and failure reasons, compare a challenger against a baseline, and receive a deterministic promotion decision.

The benchmark system must distinguish development evidence from protected promotion evidence. Optimizers may consume development cases and metrics, but they may not modify protected evaluation code, protected suite thresholds, or the promotion decision rules used to determine whether a challenger is acceptable.

## 3. Fixed decisions

- Evaluation is a first-class subsystem, not ad-hoc test code embedded in DSPy programs.
- Benchmark inputs, expected contracts, evaluator versions, model/program identifiers, and result artifacts are versioned.
- A benchmark suite has an explicit purpose: `development` or `promotion`.
- Development suites may be used by DSPy optimizers.
- Promotion suites and promotion thresholds are not optimizer inputs.
- v0.2.0 uses deterministic protected metrics for promotion. Model-as-judge evaluation may be added later as supplemental evidence, but it cannot be the only promotion authority in this release.
- Evaluation artifacts contain observable outputs and scores only; no hidden chain-of-thought is stored.
- The first benchmark cases are repository-safe synthetic engineering cases that exercise Parallax behavior without embedding private project data or credentials.
- The evaluation framework must run fully offline in CI using recorded candidate outputs/fixtures.
- A live-program benchmark adapter may be included, but provider availability must not be required for the protected CI gate.
- A challenger may not be promoted merely because its aggregate score is higher; protected category floors and regression limits also apply.

## 4. Scope

### 4.1 Benchmark data model

Define typed benchmark structures for at least:

- suite ID and suite version;
- suite purpose: `development` or `promotion`;
- case ID;
- category;
- objective;
- context;
- candidate output;
- required contract terms or behaviors;
- forbidden terms or behaviors;
- optional reference facts;
- scoring weights;
- protected minimum score for the case or category.

The loader must reject malformed suites, duplicate case IDs, unsupported suite purposes, invalid weight totals, and cases with no executable protected contract.

### 4.2 Initial Parallax Engineering Benchmark

Create a small but meaningful repository-safe benchmark with separate development and promotion suites.

The first cases must cover at least these behavioral categories:

1. specification fidelity;
2. conversation continuity;
3. implementation-plan completeness;
4. protected-boundary preservation;
5. failure/degradation handling;
6. evidence/status honesty;
7. security-sensitive secret handling;
8. concise engineering communication.

Cases should be synthetic but representative of real Parallax engineering work. They must not contain private user data, credentials, proprietary ticket content, or copied confidential project artifacts.

### 4.3 Protected scoring

Implement deterministic scoring outside optimizer-controlled modules.

At minimum, scoring must support:

- required-term/behavior coverage;
- forbidden-term/behavior violations;
- exact protected assertions;
- category-weighted scoring;
- pass/fail thresholds;
- explicit failure reasons.

A case result must be explainable from stored evidence. The scorer must not silently award points for unspecified qualities.

### 4.4 Evaluation runs and evidence

An evaluation run artifact must record at minimum:

- evaluation run ID;
- timestamp;
- spec ID;
- suite ID/version/purpose;
- evaluator version;
- candidate program version;
- candidate model identifier when applicable;
- input artifact identity or digest;
- per-case scores;
- per-case failures;
- category summaries;
- aggregate score;
- protected pass/fail;
- no-chain-of-thought marker.

Artifacts are written to a deterministic repository-local evidence directory for CI and local development. v0.2.0 does not require production database persistence for evaluation runs.

### 4.5 Baseline and challenger comparison

Implement a protected comparison gate that accepts a baseline evaluation artifact and a challenger evaluation artifact for the same promotion suite.

The challenger passes only when all of the following are true:

- both artifacts are structurally valid and use the same suite version;
- the challenger satisfies every protected case/category floor;
- the challenger has no new critical protected failure;
- aggregate score does not regress beyond the configured protected tolerance;
- no protected category regresses beyond its configured tolerance;
- evaluator version is compatible;
- promotion evidence was produced from a `promotion` suite, not a `development` suite.

The gate must return machine-readable reasons when promotion is rejected.

### 4.6 Optimizer boundary

DSPy optimization code may receive development-suite examples and development metric results.

DSPy optimization code must not receive or modify:

- promotion-suite expected contracts;
- promotion thresholds;
- protected evaluator implementation;
- baseline/challenger promotion rules;
- release-state records.

The repository structure and imports should make this separation explicit. Promotion code must live outside optimizer-controlled modules.

### 4.7 CLI tooling

Provide commands/scripts that can:

- validate benchmark suites;
- evaluate recorded candidate outputs against a suite;
- write an evaluation artifact;
- compare baseline and challenger promotion artifacts;
- fail with a non-zero exit code when protected evaluation or promotion fails.

CLI output should be concise enough for CI logs while retaining detailed JSON evidence on disk.

### 4.8 CI

Extend CI so every P2 change can run a credential-free evaluation smoke gate.

The CI gate must:

1. validate the v0.2.0 spec;
2. run benchmark schema/unit tests;
3. evaluate a known-good recorded fixture against the development suite;
4. evaluate a known-good recorded fixture against the promotion suite;
5. run a baseline-versus-equivalent challenger promotion check that passes;
6. run a known-regression challenger check in tests and prove that it is rejected;
7. retain evaluation evidence as a workflow artifact.

A provider-backed/live-model benchmark is not required for v0.2.0 validation.

## 5. Non-goals

- Optimizing Reason 2.0 prompts or modules in this release.
- Choosing a production model based on the initial benchmark.
- Using a model-as-judge as the sole release authority.
- Storing hidden chain-of-thought.
- Production evaluation database/API/UI.
- Automatically changing protected thresholds based on benchmark performance.
- Automatically merging or deploying a challenger that passes evaluation.
- Treating the initial synthetic benchmark as a complete measure of engineering quality.

## 6. Architecture requirements

### Evaluation package

Create an evaluation package separated from runtime DSPy program code. A recommended shape is:

```text
services/api/parallax_api/evaluation/
  ├─ schema.py
  ├─ loader.py
  ├─ protected_scoring.py
  ├─ runner.py
  └─ promotion.py

benchmarks/
  └─ parallax-engineering/
      ├─ development-v0.1.json
      ├─ promotion-v0.1.json
      └─ fixtures/
```

Exact file names may change if a simpler structure preserves the same boundaries.

### Dependency direction

- DSPy programs may depend on public development-evaluation interfaces.
- Protected promotion code must not depend on optimizer implementations.
- Benchmark data structures must not depend on provider SDKs.
- CLI scripts may compose loaders, runners, and promotion gates but must not reimplement scoring logic.

## 7. Scoring contract

Each case produces a normalized score from `0.0` to `1.0` and an explicit pass/fail result.

The initial deterministic contract should combine:

- required coverage score;
- forbidden-violation penalty;
- exact protected assertion result.

The suite aggregate is a weighted mean of case scores, accompanied by per-category scores.

Promotion thresholds are protected configuration owned by the evaluation subsystem. The exact initial numeric values may be selected during implementation, but they must be conservative, explicit, versioned, tested, and not optimizer-modifiable.

A higher aggregate score cannot compensate for a failed critical protected assertion.

## 8. Security and privacy

- No secrets in benchmark cases, fixtures, or evaluation artifacts.
- No private project exports or user-identifying data in the initial benchmark.
- Candidate outputs are treated as untrusted text.
- Evaluation artifacts must not include environment variable values.
- Paths written by CLI tooling must remain inside the configured evidence directory.
- No hidden chain-of-thought is requested, stored, scored, or emitted.

## 9. Observability

Evaluation artifacts are the source of truth for benchmark claims.

Every artifact includes evaluator version and suite version so historical comparisons remain interpretable after metrics evolve.

Human-readable CI logs may summarize results, but promotion claims must be traceable to a machine-readable artifact.

## 10. Acceptance criteria

### AC-01 Spec-first continuation
`P2-V0.2.0` exists before evaluation implementation commits and CI validates the approved specification.

### AC-02 Typed benchmark schema
Malformed suites, duplicate case IDs, invalid purposes, invalid weights, and cases without executable protected contracts are rejected by automated tests.

### AC-03 Development/promotion separation
Suites are explicitly labeled `development` or `promotion`, and promotion logic rejects artifacts produced from development suites.

### AC-04 Protected deterministic scoring
Required coverage, forbidden violations, protected assertions, case thresholds, category scores, and aggregate score are computed deterministically with explicit failure reasons.

### AC-05 Versioned evidence
Evaluation artifacts record run identity, spec ID, suite/evaluator/program/model versions, per-case outcomes, category summaries, aggregate score, protected result, and a no-chain-of-thought marker.

### AC-06 Promotion regression gate
An equivalent or better challenger can pass, while a fixture with a protected regression is rejected with machine-readable reasons.

### AC-07 Optimizer boundary
Protected promotion thresholds/evaluator code are outside DSPy optimizer-controlled modules, and tests prove optimizer-facing evaluation interfaces cannot promote using a development suite.

### AC-08 Offline CI
The complete protected evaluation smoke gate runs without provider credentials or network model calls.

### AC-09 Initial benchmark coverage
The repository-safe benchmark includes the eight required behavioral categories and separate development/promotion suites.

### AC-10 Security/privacy
Automated checks verify benchmark/evidence fixtures contain no configured secret values and evaluation tooling does not expose environment values or chain-of-thought fields.

### AC-11 CLI contract
Suite validation, recorded-output evaluation, artifact writing, and baseline/challenger comparison are available through documented scripts with non-zero failure exits.

### AC-12 Existing foundation regression
v0.1.0 backend tests, frontend typecheck/state tests, web export, responsive/Skia browser gate, and mandatory DSPy development gate remain green.

## 11. Release gate

v0.2.0 may be called **generated** when the spec and implementation artifacts exist.

It may be called **validated** only after:

- all v0.2.0 acceptance tests pass;
- the offline evaluation smoke gate emits valid evidence;
- the protected promotion rejection test is demonstrated;
- the existing v0.1.0 foundation regression gates remain green.

It may be called **deployed** only after an explicit deployment succeeds.

It may be called **deployment-verified** only after target-environment health and behavior evidence are collected.

Passing v0.2.0 does not authorize an optimizer to change protected benchmark criteria or automatically promote/deploy a model/program.
