## 1. Objective

Correct the partial GitHub publication recovery defect exposed by production acceptance of P2-V0.23.43 without weakening exact-lineage source authority, provider least privilege, canonical branch identity, durable delivery replay, default-branch protection, Preview-only delivery or the human REVIEW ceiling.

A delivery request that receives an exact successful GitHub ref mutation response must not fail solely because the immediately following read is temporarily stale. If an earlier attempt already advanced the canonical lineage-scoped branch to the exact accepted Parallax lineage commit but failed before durable delivery persistence, a later retry may reconcile that exact partial commit and continue. Any ambiguous, externally modified or differently authored branch head remains a hard failure.

## 3. Fixed recovery model

### 3.1 Durable record remains first authority

Exact `SOURCE_DELIVERY` durable-record replay remains the first delivery authority. If an exact record exists for the accepted lineage, it is returned before any provider call and no recovery logic executes.

### 3.2 One-shot Git ref mutation acknowledgment

The concrete authenticated GitHub client may retain one request-local, in-memory acknowledgment for an exact repository+branch immediately after GitHub itself returns a validated successful ref mutation response.

An acknowledgment contains only:

- exact repository identity;
- exact canonical branch;
- prior ref head, or `None` for branch creation;
- exact new ref head returned by the successful GitHub mutation response.

The acknowledgment:

- is created only after a 2xx GitHub ref mutation response is structurally validated to match the requested ref and exact requested SHA;
- is never persisted and grants no authority across process recreation;
- is consumed at most once by the immediately following exact branch-head check;
- may reconcile only a live read that returns the exact prior head or `None` where the acknowledged mutation itself proves the new head;
- may not mask any third/unexpected live head;
- adds no sleep, polling loop, random delay, mutation retry, force update or alternate branch.

A successful branch-create POST therefore permits the following commit stage to treat an immediate 404 as the acknowledged base head. A successful non-force ref PATCH permits the following pull-request stage to treat an immediate stale prior-head read as the acknowledged exact commit. Any unrelated head remains fail-closed.

### 3.3 Exact partial-commit retry

If canonical `branch.create` fails specifically with normalized `BRANCH_CONFLICT` because a prior attempt already advanced the branch, ordinary and greenfield delivery may continue only by invoking the existing accepted-lineage commit action against:

- the exact canonical branch;
- the exact expected base revision;
- the exact accepted `AcceptedSourceLineage`;
- the exact bounded accepted commit files.

The existing `GitHubRestProviderClient.commit_files()` replay boundary remains authoritative. Recovery succeeds only if the current branch head is already an exact lineage replay under the existing deterministic Parallax lineage commit contract and expected parent. An arbitrary different head, stale parent, different lineage, different parent or malformed commit fails closed.

No branch reset, branch deletion, branch rename, suffix branch, force ref update or default-branch mutation is permitted.

### 3.4 Successful delivery evidence

A final `VerifiedDeliveryResult` continues to contain only successful provider action/audit pairs. A failed `branch.create` action that is safely reconciled by a successful exact commit replay remains represented by the provider executor's failure audit but is not converted into successful delivery evidence.

The action-count ceiling remains unchanged.

## 4. Shared ordinary/greenfield behavior

One shared server-owned helper in the source-delivery composition layer should own branch-create plus exact partial-commit reconciliation so ordinary `VerifiedLineageDelivery` and `GreenfieldVerifiedLineageDelivery` cannot drift.

Greenfield repository classification and P2-V0.23.42 baseline rules remain unchanged. P2-V0.23.43 canonical lineage-scoped branch derivation and multi-record delivery-ledger semantics remain unchanged.

## 7. Reliability and compatibility

### Clean first publication

A newly created canonical branch may be temporarily unreadable after GitHub returns 201. The one-shot branch-create acknowledgment permits only the immediately following commit-stage check to use the acknowledged base head if the live read is absent. The commit still uses a non-force ref update and exact accepted-lineage content.

### Commit ref propagation

After GitHub returns 200 for the non-force ref PATCH and the response identifies the exact requested commit, the immediate PR-stage branch check may use that acknowledgment only when the live read is absent or still reports the exact prior head. A different head fails.

### Retry after partial commit

A later process/request has no in-memory acknowledgment. If the canonical branch is visible at a non-base head, `branch.create` still reports conflict. The composition may then invoke exact commit replay. Only the already-present exact accepted-lineage commit with the expected parent can recover.

### Historical replay

Existing durable delivery records, historical run-scoped branches, prior PRs/Previews and earlier lineage-scoped artifacts are not rewritten.

### Concurrent movement

The acknowledgment cannot hide an unexpected live head. Non-force Git ref mutation semantics remain authoritative. Any unexpected concurrent branch state fails closed.

## 8. Acceptance criteria

### AC-01 Production root cause is preserved
Tests and release evidence distinguish P2-V0.23.44 from P2-V0.23.43: lineage naming/ledger identity are already fixed; this slice addresses only successful Git ref mutation propagation and exact partial-publication replay.

### AC-02 Branch-create propagation is bounded
After an exact successful branch-create response, an immediately absent ref read can be reconciled only from a matching one-shot acknowledgment for the same repository/branch/base head.

### AC-03 Commit-ref propagation is bounded
After an exact successful non-force ref PATCH response, an immediate absent or exact-prior-head read can be reconciled only from the matching one-shot acknowledgment for the same repository/branch/new commit.

### AC-04 Unexpected heads remain fail-closed
If a live ref read returns a head different from both the acknowledgment's exact prior state and exact new state, no acknowledgment is applied and delivery fails.

### AC-05 Acknowledgments are one-shot and process-local
Acknowledgments are consumed at most once, are not durable state, do not survive client/process recreation and cannot authorize another repository or branch.

### AC-06 Ordinary exact partial commit recovers
For ordinary delivery, a canonical branch already advanced by a prior partial attempt to the exact accepted-lineage commit may recover from branch `BRANCH_CONFLICT` only through successful existing `commit_files()` lineage replay.

### AC-07 Greenfield exact partial commit recovers identically
Greenfield delivery uses the same branch/commit reconciliation helper and exact replay rule after its unchanged delivery-base classification.

### AC-08 Arbitrary branch conflicts still fail
A canonical branch at a different commit, lineage or parent cannot be adopted, reset or overwritten by the recovery path.

### AC-09 Clean delivery remains unchanged
A normal non-stale provider path still creates the canonical lineage branch, exact commit, PR and Preview under existing provider actions and persists the exact lineage-scoped durable record.

### AC-10 Durable replay remains first
An existing exact durable delivery record returns before provider mutation and is unaffected by this release.

### AC-11 No authority expansion
