## 1. Objective

Complete Wave 4 as one production release by proving that the Warm Editorial Live Build / Observability experience is a faithful, privacy-safe, read-only projection of the existing protected engineering runtime and then activating that projection through the governed database and deployment boundary.

The release must prove the actual runtime facts that matter to an operator: canonical Project/spec/run identity, SPECIFY/PLAN/IMPLEMENT/BUILD/TEST/VERIFY/REVIEW progress, process recreation and recovery, bounded failure/correction, exact accepted source lineage, replay-safe provider publication, protected evaluation and the explicit human-review boundary. The UI may explain those persisted facts but may not become a second execution authority, invent success, expose hidden reasoning, broaden provider authority or turn bounded evidence into a generic terminal/filesystem/provider console.

Production rollout is part of this workstream. Source integration, a green Preview, an applied migration and a deployed binary are distinct states. Production is declared only after the exact validated application head is deployed and post-deploy health/readiness/auth/observability/runtime evidence passes.

## 2. Scope

- Add a permanent Wave 4 reference proof that composes the real Engineering Run service, persistent run-event sink/repository, protected implementation/runtime recovery, immutable source lineage, bounded BUILD/TEST/VERIFY evidence, protected AppBuilder evaluation, GitHub/Vercel Preview delivery evidence and explicit REVIEW.
- Prove persisted run-event sequence covers the governed lifecycle and remains deterministic across process recreation/retry without duplicate runtime mutation or provider publication.
- Prove a deliberate protected TEST failure is represented as failure, enters bounded correction/recovery, and is followed by a fresh exact-lineage successful attempt rather than normalization of the failed fact.
- Prove protected source tree/file/diff reads resolve only the run-owned accepted lineages and cross-Project/run/lineage/evidence probing fails closed.
- Prove browser observer replay/SSE resume consumes the same persisted sequence without duplicate UI events and without acquiring execution authority.
- Preserve the accepted Warm Editorial desktop/mobile Live Build visual contract and all inherited authentication, conversation, Project, Work Specification and Engineering Run behavior.
- Reconcile durable architecture/design/current-state records for the Wave 4 release boundary.
- Validate the exact integrated head through Workstream Spec Validation, Parallax P2 CI, Bounded Autonomy, protected promotion evaluation, browser/accessibility/visual acceptance, authentic DSPy release compilation and exact Vercel checks.
- Apply the additive `engineering_run_events` migration to the production PostgreSQL/Supabase database only after the exact release candidate is validated and migration readiness is proven.

- Verify production health, readiness/database state, authentication boundary, active observability route boundary, web client, deployment source SHA and deployment-scoped error/fatal logs before recording Wave 4 as deployment-verified.

## 3. Fixed decisions

- **One execution truth.** Engineering Run, attempts, worker checkpoints/leases, source lineage, provider records and protected evaluation remain authoritative; run events and Live Build are observational projections.
- **Real reference proof.** Release evidence uses real repository/service/runtime composition and persisted event records. Browser-only fixtures remain UI tests, not the integrated runtime proof.
- **Failure remains failure.** Deliberate TEST failure is persisted and visible before bounded correction; no evaluator/UI layer rewrites it as success.
- **Replay is idempotent.** Process recreation/retry cannot duplicate accepted source mutation, event sequence, GitHub branch/commit/PR publication or Vercel Preview publication.
- **Exact lineage only.** Source and diff evidence must bind to accepted run-owned immutable lineage identities; unrelated or stale lineage fails closed.
- **Human review is a boundary.** Autonomous work stops at REVIEW/HUMAN_REQUIRED. COMPLETE may occur only after an explicit operator review action in the permanent reference proof.
- **Migration before activation.** Production flag remains off until `engineering_run_events` exists and its constraints/RLS/revokes are verified.
- **Exact activation only.** Only `PARALLAX_RUN_EVENTS_ENABLED=1` enables event emission and observability routes; absent, `true`, `yes` or other values remain disabled.
- **Rollback is flag-first.** On release failure, disable the Wave 4 flag first, then return web/API to the previous exact production deployments. The additive dormant events table may remain.
- **No new provider authority.** Wave 4 does not add merge, production-promotion, arbitrary shell/filesystem, credential or unrestricted provider capabilities.
- **No hidden reasoning.** Chain-of-thought/scratchpads, credentials, raw provider payloads, unrestricted logs and private execution internals are never exposed through run events or Live Build.
- **Deployment evidence is mandatory.** Merged source or READY Preview is not production deployment evidence.

## 4. Architecture requirements

### 4.1 Permanent integrated reference harness

Extend the existing protected AppBuilder reference infrastructure rather than creating a parallel fake runtime. The permanent proof must use database-backed Engineering Run/attempt records, a `PersistentRunEventSink`/`RunEventRepository`, immutable lineage storage, protected implementation and exact-lineage execution, worker/process recreation seams, bounded delivery drivers and the protected evaluator.

The harness must produce a run-owned durable event sequence whose facts can be queried through `EngineeringObservabilityService`. Required lifecycle evidence includes SPECIFY, PLAN, IMPLEMENT/source-lineage acceptance, BUILD, TEST failure, recovery/correction, TEST success, VERIFY/evaluation, provider delivery and REVIEW/HUMAN_REQUIRED. If the existing runtime vocabulary represents one lifecycle transition through a normalized non-stage event, the proof may use that canonical event instead of inventing a new event type.

### 4.2 Process recreation and replay

The proof must close/reopen runtime composition between meaningful steps. Re-created services use the same durable database/event/lineage/provider state and must converge without duplicate accepted mutation/publication. Stable event keys and per-run monotonic sequence remain the durable event replay contract. Provider counters or equivalent audit facts must prove one branch, one accepted commit, one PR and one Preview for the accepted publication despite replay/retry.

Worker/recovery facts must show stale execution authority is not reused. Process loss/reassignment is observed through persisted worker/run events, not simulated by UI-only state.

### 4.3 Deliberate failure and correction

The reference proof must include a deliberate protected TEST failure followed by bounded recovery/correction and a fresh successful exact-lineage attempt. Both attempts remain queryable and the failed attempt preserves its normalized failure code/evidence. The final success must bind to the corrected accepted lineage and may not rely on unrelated/fresh checkout evidence that violates lineage authority.

### 4.4 Observation/read proof

Use the production `EngineeringObservabilityService` and repository contracts to prove:

- paginated replay is sequence ordered;
- reconnect cursor resumes after the last accepted sequence;
- run-owned source tree/file reads match immutable object digests;
- lineage-to-lineage diff reflects the accepted correction;
- BUILD/TEST/VERIFY evidence is allowlisted/bounded/redacted;
- foreign Project/run/lineage/attempt requests fail closed;
- secret-like metadata, raw provider payloads and unrestricted logs cannot enter the observable payload.

### 4.5 Browser proof

Retain P2-V0.17.4 browser/mobile acceptance and add no weaker substitute. The release must demonstrate persisted REVIEW, recovery/failure, exact-lineage Code/Diff, bounded Terminal/Tests, provider evidence and mobile navigation. SSE reconnect/dedup remains deterministic through the client cursor contract.

### 4.6 Production schema activation

The existing additive migration `services/api/migrations/20260824_0010_run_events.sql` is the only Wave 4 production DDL in this release. Before applying it, verify the target database identity and current migration history. Apply it through the governed database migration mechanism, then verify table existence, unique sequence/event-key constraints, allowed vocabulary checks, indexes, RLS and revoked `anon`/`authenticated` access.

Do not set the activation flag until schema verification succeeds. Startup/build preflight with the exact flag must fail closed if the table is absent.

### 4.7 Production promotion and verification

Only the exact release head that passed cumulative gates may be promoted. Verify both API and web deployment metadata identify that source head or its exact merge commit as intended by the repository deployment model.

Post-deploy verification must include:

- API `/health` = 200/ok;
- API `/ready` = 200/ready with database ok;
- unauthenticated protected endpoint = 401 with the existing auth boundary;
- observability route is registered under the active flag and still requires authentication;
- production web resolves to the Warm Editorial application and retains authentication/session behavior;
- deployment-scoped error/fatal logs contain no release regression;
- no new source-bootstrap/provider failure is introduced;
- production run-event activation does not mutate existing run state merely by observation.

### 4.8 Rollback

Rollback sequence is deterministic: set `PARALLAX_RUN_EVENTS_ENABLED` away from exact `1`, verify observability routes/emission are inactive, then restore the previous known-good web/API deployment if needed. The additive table is not dropped during routine rollback because destructive rollback is unnecessary and outside standing authority. Existing Wave 3 execution must continue when Wave 4 observation is inactive.

## 5. Security and privacy

- Production authentication remains mandatory for every protected run/source/evidence endpoint.
- PostgreSQL event rows remain server-owned; RLS is enabled and API roles do not receive direct table access.
- Event metadata remains allowlisted and bounded before persistence; source bytes stay in immutable object storage and are fetched only through protected exact-lineage reads.
- Live Build never receives credentials, auth headers/cookies, raw provider payloads, environment dumps, private keys, unrestricted stdout/stderr or hidden reasoning.
- Cross-Project/run probing normalizes to fail-closed protected responses without confirming foreign identities.
- Provider publication remains project-scoped and Preview-only; Wave 4 UI adds no merge/Production controls.
- Production activation changes observation availability only. It does not widen Engineering Run execution, migration, database or provider authority.

## 6. Failure and recovery boundaries

- Any exact-head gate failure blocks integration/release until corrected and revalidated.
- Any migration failure leaves the feature flag off and production on the previous runtime.
- Schema verification failure blocks activation even if the migration command returned success.
- Activation/preflight failure disables the flag and blocks deployment.
- Deployment health/readiness/auth failure triggers rollback; do not record deployment verified.
- Observability/SSE failure after cutover may be contained by flag rollback without reverting the additive schema.
- Process recreation/retry that produces duplicate mutation/publication or non-monotonic event sequence fails the release proof.
- REVIEW/HUMAN_REQUIRED cannot be auto-converted into COMPLETE by observation or deployment.

## 7. Non-goals

- changing evaluator scoring thresholds or weakening existing protected benchmarks;
- granting autonomous merge or project-production deployment authority;
- adding a generic IDE/editor/shell/filesystem/provider console;
- destructive database rollback/drop of the additive event table;
- provisioning materially broader production credentials or provider scopes;
- exposing chain-of-thought, scratchpads, secrets, raw provider responses or unrestricted logs;
- redesigning the accepted Warm Editorial shell beyond fixes required by deterministic release acceptance.

## 8. Acceptance criteria

### AC-01 Permanent integrated events represent real protected runtime facts
A database-backed reference run using the production event sink/repository produces an ordered persisted observation sequence covering the governed lifecycle through REVIEW without creating a second state authority.

### AC-02 Process recreation and retry remain mutation/publication idempotent
Recreating runtime/services and replaying operations preserves one accepted mutation/publication path, monotonic event sequence and exactly one accepted GitHub branch/commit/PR plus Vercel Preview publication.

### AC-03 Deliberate failure and bounded correction are both durable and visible
The permanent reference proof records a real failed TEST attempt with normalized failure evidence, recovery/correction, and a subsequent successful exact-lineage TEST/VERIFY path; the failed fact remains queryable and is never normalized to success.

### AC-04 Source and diff observations bind to exact accepted lineages
Protected source tree/file and diff reads match immutable accepted lineage digests/content and demonstrate the correction relationship. Stale, unrelated or foreign lineage identities fail closed.

### AC-05 Terminal/Test/Evidence observations remain bounded and privacy-safe
BUILD/TEST/VERIFY reads expose only allowlisted normalized evidence and durable identities; deliberate secret/raw-provider/unbounded-log cases are redacted/rejected and cannot reach the observer payload.

### AC-06 Cross-Project/run/evidence probing fails closed
Foreign Project, run, lineage and attempt-evidence reads cannot disclose protected state or content, while owner-scoped reads remain functional.

### AC-07 Browser reconnect and Live Build remain faithful projections
The permanent client/browser acceptance proves ordered replay/SSE resume without duplicate UI events, evidence-backed failure/recovery/REVIEW/provider/source views and usable desktop/mobile Warm Editorial composition.

### AC-08 Human REVIEW remains an explicit autonomous stop
The reference run reaches REVIEW/HUMAN_REQUIRED before operator action; observation does not mark the run COMPLETE. A separate explicit operator review may then complete the permanent reference flow.

### AC-09 Existing Wave 3 protected regressions remain green
Reference-app restart/replay/provider/evaluation tests, worker recovery, source-lineage protection, protected promotion evaluation, auth/Project/Work Specification/Engineering Run tests and browser/mobile suites remain unchanged or stronger.

### AC-10 Migration readiness and rollback are proven before production change
The additive run-event migration is reviewed/tested for idempotent application, constraints/RLS/revokes are defined, startup guard requires the table under exact activation, and the flag-first rollback path is recorded before production migration.

### AC-11 Exact integrated release gates pass with authentic DSPy evidence
The final candidate contains an authentic committed P2-V0.17.5 SpecCritic/SpecCompiler plan and passes Workstream Spec Validation, Parallax P2 CI, Bounded Autonomy, protected promotion evaluation, browser/accessibility/visual acceptance and required Vercel checks on the exact head.

### AC-12 Production migration is applied and verified before activation
After AC-01 through AC-11 pass, the production database receives the additive `engineering_run_events` migration and verification proves expected table/constraints/indexes/RLS/revokes before the activation flag changes.

### AC-13 Exact Wave 4 activation and deployment are verified
`PARALLAX_RUN_EVENTS_ENABLED` is set to exact `1` only after schema verification, the exact validated Wave 4 application head is promoted, and deployment metadata plus health/readiness/auth/observability/web/runtime-log checks pass.

### AC-14 Authoritative records distinguish validated, migrated, activated and deployment-verified state
`ARCHITECTURE.md` and `DESIGN-SYSTEM.md` reflect durable Wave 4 architecture/design changes; `CURRENT-STATE.md` records exact production deployment/migration/activation evidence only after those facts are verified; `PROJECT-CONSTITUTION.md` changes only if durable governance policy changes.

## 9. Release gate

The release proceeds in strict order: authentic spec/DSPy authorization -> permanent integrated proof -> exact-head cumulative gates -> migration readiness review -> production migration -> schema verification -> exact flag activation -> exact validated API/web production promotion -> post-deploy verification -> deployment-evidence record update.

No later step may be inferred from an earlier one. A green Preview is not production. An applied migration is not activation. An active flag is not deployment verification. If a protected gate or post-deploy check fails, stop promotion, preserve evidence and execute the bounded rollback appropriate to that phase.
