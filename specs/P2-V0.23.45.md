## 1. Objective

Correct the exact-tree replay implementation defect exposed by production acceptance of P2-V0.23.44 without weakening its partial-publication recovery contract.

When an existing canonical lineage branch is already at a candidate Parallax lineage commit, replay verification must resolve each Git commit object to its exact `tree.sha` before reading recursive tree contents. The parent and replay trees must then satisfy the existing exact changed-path, mode, size and content-digest proof before delivery can continue.

## 2. Verified production evidence and root cause

P2-V0.23.44 merged as `be367408e8878e5a896be5ea437e401ff7ca2e0f` and exact production deployment `dpl_GiF9VzzX1fVcE5VmJ8csBH9B5gvc` reached READY. Production provider, exact delivery-permission, projected-source, private Blob, lineage-composition, agentic-runtime, projected-bootstrap, execution-snapshot, candidate-validation and run-event-schema preflights passed. Independent QA curl verified `/health` HTTP 200 and `/ready` HTTP 200 with database/providers `ok`.

Frozen W9-S1 Engineering Run `a64d56b7-ad42-42ad-9562-891783363f4a` remained REVIEW revision 12 with `last_failure_code=null`. Its replacement accepted lineage remained `src:001736ab731e243956cf78ede7a0087d2b81595f1008568850eac1e9acc3e809`, and canonical replacement branch remained at exact partial commit `54d2d28880e1cfdcaf9632bb342049821a5a6be1`.

The P2-V0.23.44 acceptance request reached exact replay verification, loaded the candidate commit, validated its deterministic lineage message and expected parent, then attempted:

`GET /repos/Ryan9876/parallax-qa1/git/trees/b24c029be916f8b1f0ab07347a988f814cc8d567?recursive=1`

where `b24c029...` is the parent **commit SHA**. GitHub correctly returned 404 because the Trees API requires a tree object SHA. P2-V0.23.44 therefore failed as `SOURCE_NOT_FOUND` before exact tree-delta proof could finish.

The root cause is local: `_blob_tree_snapshot()` was given commit revisions instead of validated commit `tree.sha` identities.

## 3. Fixed replay model

### 3.1 Commit object remains authoritative

For an exact replay candidate, the concrete GitHub client must retrieve the exact parent commit object and exact replay commit object with the existing fixed Git Data commit endpoint.

Each commit payload must contain a structurally valid non-empty `tree.sha`. Missing, malformed or empty tree identity is `PROVIDER_INVALID_RESPONSE`.

### 3.2 Tree reads use only resolved tree identities

Recursive tree snapshot reads must operate on the exact validated `tree.sha`, never a commit SHA inferred or substituted by the caller.

The existing bounds remain:

- recursive tree must not be truncated;
- entry count remains bounded by `MAX_TREE_ENTRIES`;
- only existing supported tree/blob modes are accepted;
- exact changed path set must equal the accepted commit-file set;
- every changed accepted file must be mode `100644`;
- exact byte size must match accepted UTF-8 content;
- exact content SHA-256 must match accepted source evidence.

### 3.3 No replay trust regression

The replay candidate still must satisfy all P2-V0.23.44 checks:

- exact deterministic Parallax lineage commit message;
- exactly one parent equal to the exact expected parent revision;
- exact parent/replay tree delta set;
- exact mode, size and accepted-content digest proof.

Resolving commit-to-tree identity is not a fallback, heuristic adoption rule or authority expansion.

### 3.4 Existing clean-write path stays unchanged

New commit creation already reads the expected parent commit payload and extracts its `tree.sha` before creating a child tree. P2-V0.23.45 changes only the replay-verification tree snapshot path unless tests prove a shared helper is materially safer.

## 6. Compatibility and failure behavior

### Exact historical partial commit

An exact existing Parallax lineage commit with the expected parent and exact accepted changed files succeeds replay verification after parent/replay commit objects resolve to exact tree identities.

### Forged or drifted commit

A commit with the right message and parent but any extra/missing/different changed blob path, unsupported mode, wrong size or wrong accepted content digest remains rejected as stale parent/conflict behavior under the existing provider boundary.

### Malformed provider commit

A parent or replay commit whose `tree` object or `tree.sha` is absent/malformed fails as `PROVIDER_INVALID_RESPONSE`; no tree read or adoption follows.

### Clean publication

A branch still at the expected parent continues through normal commit creation without replay adoption and preserves current mutation semantics.
