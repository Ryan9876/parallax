## 1. Objective

Establish the first controlled real-world app-builder benchmark and extend existing ParallaxBench only enough to admit an immutable objective template before a real run, then bind that template fail-closed to the canonical Project and approved Work Specification created by ordinary Parallax behavior.

The first benchmark is **Decision Ledger v1**, an independent responsive web application with browser-persistent state, CRUD, search/filter, import/export, accessibility and automated tests. It requires no third-party backend, production secret or external account.

The benchmark must expose ordinary product quality and failure modes. It must not create a benchmark-only runtime, provider, source, lifecycle, authentication or expected-answer path.

## 2. Fixed decisions

- Existing ParallaxBench remains the evaluation contract and protected correctness remains a hard floor.
- The objective template is immutable/versioned before the run starts; material brief drift changes its digest.
- Benchmark identity is evaluation evidence only and grants no source, provider, deployment, merge, lifecycle, approval or REVIEW authority.
- Runtime/provider/source-delivery/client code may not inspect benchmark ID/version/digest or expected result to special-case behavior.
- The real trial uses normal authenticated Project → Build plan → Engineering Run → accepted source → Preview → REVIEW behavior.
- After the real trial begins, no human or external agent manually edits target source. Corrections go through Parallax and remain observable as intervention/recovery evidence.
- Required plan approval and final REVIEW are expected boundaries, not undesirable intervention. Pre-approval clarification is recorded separately from post-approval correction.
- Missing cost/time/intervention evidence remains unknown/unavailable; no favorable zero defaults.
- Preview remains the autonomous publication ceiling and REVIEW remains human-required.
- The first admitted real-world run is a reference observation only. Cross-Project challenger comparison requires a later governed contract.
- Product defects discovered by the trial are recorded before fixes and receive their own approved spec if product behavior changes.

## 3. Decision Ledger v1 benchmark brief

The ordinary objective submitted to Parallax preserves these requirement tokens and outcomes. Tokens are deterministic evaluation anchors, not runtime commands.

- `DL-01` — users can create, view, edit and delete decision records.
- `DL-02` — each decision supports title, status, decision date, owner, context, final decision, options considered and tags.
- `DL-03` — statuses are Proposed, Accepted and Superseded, with meaning not conveyed by color alone.
- `DL-04` — records persist across browser reload/reopen without an external account, production credential or third-party backend.
- `DL-05` — users can search and filter by status/tag with deterministic understandable ordering.
- `DL-06` — users can export all records to JSON and import a prior export; invalid import fails without corrupting valid data.
- `DL-07` — empty states, validation, deletion confirmation and import failures are clear and recoverable.
- `DL-08` — the app is usable at 390px and 1440px without horizontal clipping or inaccessible primary actions.
- `DL-09` — primary controls are keyboard reachable, form controls are accessibly labeled and focus remains usable.
- `DL-10` — automated tests cover core CRUD, persistence, search/filter and import behavior, and the production build passes.
- `DL-11` — the repository contains no embedded secrets, real user data, analytics/tracking credential or benchmark-specific runtime branch.
- `DL-12` — delivery reaches existing Preview/REVIEW with exact accepted source and protected-validation evidence; REVIEW is not presented as autonomous production completion.

Technology is intentionally not fixed. Parallax chooses the simplest maintainable architecture satisfying the outcomes. Browser-local persistence is required; the mechanism is not prescribed.

## 4. Architecture requirements

### Immutable real-world template

Introduce a bounded immutable evaluation record containing stable template ID/version, title, objective class, repository-shape class, ordered requirement IDs/text, existing ParallaxBench comparable dimensions, expected protected ceiling and deterministic fixture digest. Identity validation follows existing ParallaxBench token/version/digest conventions. Duplicate `(template_id, template_version)` with different content fails closed.

### Canonical acceptance binding

A binder accepts only canonical Project and approved Work Specification evidence: Project ID, Work Specification ID/revision/digest, complete canonical acceptance criteria IDs/text and repository shape.

Every `DL-01` through `DL-12` token must appear exactly once across canonical acceptance text. Missing or duplicate requirement tokens fail closed. Extra canonical acceptance criteria are allowed and become part of the exact resulting acceptance-ID set. No model/evaluator may decide missing coverage is “close enough” or silently rewrite the Work Specification.

Successful admission returns the existing `BenchmarkCase`, binding exact canonical Project/spec/acceptance identity, repository shape, existing dimensions/ceiling and the immutable template digest as fixture identity. Existing `CandidateBinding`, protected-floor, dimension evidence, comparison and safe-serialization semantics remain authoritative.

### Evidence policy

The runbook distinguishes required approval/review, pre-approval clarification, post-approval corrective messages, explicit retry/recovery actions and prohibited out-of-band source edits. Elapsed/cost/UX evidence is admitted only with trustworthy existing provenance. UX evidence is considered only after deterministic/protected admission for the exact candidate.

### Repository-safe fixture

Commit Decision Ledger v1 under a benchmark/evaluation fixture path with only the frozen brief, requirement IDs/text, dimensions/ceiling, digest metadata and trial protocol. It contains no reference implementation, expected source tree, hidden solution, credentials, production secret or real user data.

### No benchmark backdoor

Focused static/adversarial tests prove ordinary runtime/provider/source-delivery/client modules do not import or branch on the new benchmark template identity or benchmark mode. Evaluation code may reference benchmark identity; product/runtime behavior may not.

### Real trial protocol

After the evaluation extension is qualified/released: use an independent target repository with no reference solution; create/select a normal authenticated Parallax Project; submit the frozen DL-01…DL-12 brief; record clarification; approve a suitable ordinary Build plan; allow the Engineering Run to proceed normally; request corrections only through Parallax; at REVIEW collect exact canonical Project/spec/run/source/Preview identity and trustworthy protected/intervention/retry/time/cost/UX evidence. Do not bypass auth, mutate the database directly, inject source out of band or promote production merely to complete the benchmark.

## 5. Scope

After the authentic DSPy gate passes, owned implementation scope is limited to:

- this spec and authentic compiled plan evidence;
- a narrow real-world template/binding extension under `services/api/parallax_api/evaluation/`;
- repository-safe Decision Ledger fixture/manifest and trial runbook/evidence schema;
- focused tests for identity, canonical binding, token drift, existing BenchmarkCase compatibility, safe artifacts and runtime-backdoor rejection;
- minimal evaluation exports/composition required by tests.

No client, conversation, Engineering Run, agent runtime, provider, source-delivery, repository-mutation, browser, deployment or production-promotion behavior changes are in S1 scope unless a trial-discovered defect receives a separate approved spec.

## 6. Non-goals

- Building Decision Ledger directly inside the Parallax repository.
- Creating a reference implementation or hidden solution.
- A public leaderboard or scalar quality score.
- Cross-Project comparison semantics.
- Automatic production promotion or REVIEW completion.
- Model-routing/promotion-policy changes.
- W8-S2 replay, safe-deletion testing, hosted-to-private inference or unrelated dependency upgrades.

## 7. Security, privacy and reliability

Benchmark brief, repository, source, model, browser and evaluator content is untrusted evidence. It cannot redefine Project ownership, canonical acceptance, source lineage, provider/capability scope or REVIEW authority.

The fixture is synthetic and repository-safe. Safe benchmark artifacts exclude source bytes/patches, prompts, hidden reasoning, raw provider payloads, credentials, arbitrary command/URL authority, unrestricted logs and real user content.

Binding is deterministic and fail-closed. Invalid IDs/digests, malformed or duplicate acceptance identity, missing/duplicate requirement tokens and template drift cannot be coerced into support. A failed/HUMAN_REQUIRED real trial remains useful evidence and must not be converted into success by weakening gates.

## 8. Acceptance criteria

### AC-01 Immutable template identity
The template validates stable bounded ID/version and deterministic digest; duplicate identity with different material content fails closed.

### AC-02 Frozen Decision Ledger fixture
The committed fixture contains exactly DL-01 through DL-12 with frozen outcomes, repository shape, comparable dimensions and REVIEW ceiling, and contains no reference implementation.

### AC-03 Deterministic canonical binding
The binder accepts valid canonical Project + approved Work Specification identity only, including positive revision, exact digest and unique canonical acceptance IDs.

### AC-04 Exact requirement coverage
Every DL-01…DL-12 token appears exactly once across canonical acceptance text. Missing/duplicate tokens fail closed; extra canonical acceptance criteria remain in the resulting case.

### AC-05 Existing BenchmarkCase compatibility
Successful binding returns the existing BenchmarkCase with exact canonical identity and template digest; protected-floor/comparison semantics remain unchanged.

### AC-06 No unconstrained semantic admission
No model/evaluator rewrites or semantically substitutes missing requirement coverage during admission.

### AC-07 Evidence integrity
Intervention/time/cost/UX evidence uses trustworthy state/provenance; missing evidence remains unknown/unavailable rather than favorable zero.

### AC-08 Intervention protocol
The runbook distinguishes required approvals, clarification, corrective intervention, retry/recovery and prohibited out-of-band source edits.

### AC-09 Safe artifacts
Fixture/template/safe evidence contain no credentials, secrets, real user data, hidden reasoning, provider payloads, source bytes/patches or reference solution.

### AC-10 No benchmark-only runtime path
Static/adversarial coverage proves runtime/provider/source-delivery/client behavior does not inspect Decision Ledger template identity, benchmark mode or expected outcome.

### AC-11 No authority expansion
The extension cannot accept source, transition Engineering Runs, grant capability/provider authority, mutate target repositories, merge, deploy production, approve or complete REVIEW.

### AC-12 Compatibility regressions remain green
Existing ParallaxBench, protected evaluation, integrated product proof and full API authority/regression tests remain green.

### AC-13 Authentic DSPy gate
Authentic DSPy SpecCritic + SpecCompiler evidence for this exact spec is committed and protected `--require-dspy` validation passes before semantic implementation; any temporary evidence workflow is restored byte-for-byte.

### AC-14 Exact-head implementation qualification
Final implementation head passes focused tests, Workstream Spec Validation, P2 CI, Bounded Autonomy and applicable protected release gates; changed production components are deployment-verified before being recorded as deployed.

### AC-15 Controlled reference trial
After release, Decision Ledger v1 runs through a normal authenticated Project with no out-of-band source editing and records exact Project/spec/run/source/Preview/REVIEW identity plus trustworthy evaluation evidence.

### AC-16 Failure remains evidence
A failed or HUMAN_REQUIRED first trial is recorded honestly and may establish reference diagnostic evidence; no gate or authentication boundary is weakened to manufacture success.

### AC-17 Follow-up fixes are separately governed
Any semantic product fix discovered by the trial is documented first and receives its own approved workstream/spec boundary.
