## 1. Objective

Establish the first controlled real-world application-building benchmark for Parallax and extend the existing ParallaxBench evaluation contract only as needed to admit a fixed objective template before a real run and then bind that template fail-closed to the canonical Project and approved Work Specification created by the ordinary Parallax workflow.

The first objective is **Decision Ledger v1**, an independent greenfield responsive web application with browser-persistent data, multiple user surfaces, validation, import/export, accessibility and automated tests. The benchmark is intentionally independent of the Parallax repository and requires no external account, production secret or third-party data service.

The benchmark exists to expose product quality and failure modes. It must not create a benchmark-only runtime path, source path, provider path, lifecycle path or expected-answer backdoor.

## 2. Fixed decisions

- Existing ParallaxBench remains the measurement/evaluation contract. S1 extends it; it does not introduce a second benchmark engine or scalar score.
- Deterministic/protected correctness remains a hard floor. Visual quality, evaluator judgment, cost or speed cannot offset failed acceptance, validation, safety, privacy or governance.
- A real-world objective template is immutable and versioned before a run begins. Its digest changes if any material brief, required outcome, comparable dimension or expected ceiling changes.
- Runtime, provider, source-delivery, Engineering Run and client code may not inspect benchmark template ID/version/digest or expected outcome to special-case implementation behavior.
- Benchmark template identity is evaluation evidence only. It grants no source, provider, deployment, merge, approval, lifecycle or REVIEW authority.
- The real benchmark runs through ordinary authenticated Parallax Project → Build plan → Engineering Run → accepted source → Preview → REVIEW behavior. No benchmark-only endpoint or auth bypass is permitted.
- After the real benchmark run begins, no human or external agent may manually edit the target repository. Corrections must be requested through ordinary Parallax interaction so intervention/recovery evidence remains observable.
- Required Build-plan approval and final REVIEW are expected human boundaries and are not counted as undesirable intervention.
- Pre-approval clarification and post-approval corrective intervention are distinct evidence. A necessary clarification must not be mislabeled as a failure merely to favor a lower count.
- Missing cost, time or other evidence remains `UNKNOWN`/`UNAVAILABLE` according to the existing ParallaxBench evidence contract and is never converted to a favorable zero.
- Preview remains the ordinary autonomous publication ceiling; REVIEW remains human-required. S1 adds no production-promotion authority.
- The first admitted real-world run is a reference observation. Cross-Project comparison semantics are not introduced in S1; future repeat/challenger comparison across separately bound canonical Projects requires separately governed semantics.
- Any product defect discovered by the benchmark is recorded before corrective implementation and requires its own approved semantic spec if it changes product/runtime behavior.

## 3. Fixed Decision Ledger v1 benchmark brief

The benchmark objective supplied to Parallax must preserve these requirement tokens and outcomes. Requirement tokens are evaluation anchors, not runtime commands.

### DL-01 Decision lifecycle
Users can create, view, edit and delete decision records.

### DL-02 Decision fields
Each decision supports title, status, decision date, owner, context, final decision, options considered and tags.

### DL-03 Status semantics
Supported statuses are `Proposed`, `Accepted` and `Superseded`, presented in clear ordinary language with meaning that is not color-only.

### DL-04 Persistent state
Records persist across browser reload/reopen without requiring an external account, production credential or third-party backend.

### DL-05 Find and organize
Users can search decisions, filter by status and tag, and use deterministic understandable ordering.

### DL-06 Export/import
Users can export all records to JSON and import a prior export. Invalid import fails safely without corrupting existing valid data.

### DL-07 Recovery-oriented UX
Empty states, validation errors, destructive deletion confirmation and import failures are clear and recoverable.

### DL-08 Responsive layout
The application is usable at 390px mobile and 1440px desktop without horizontal clipping or inaccessible primary actions.

### DL-09 Accessibility
Primary interactive controls are keyboard reachable, form controls have accessible labels, focus remains usable and meaning is not conveyed by color alone.

### DL-10 Automated quality
Automated tests cover core CRUD, persistence, search/filter and import behavior, and the production build passes.

### DL-11 Repository safety
The delivered repository contains no embedded secrets, real user data, analytics/tracking credential or runtime branch keyed to benchmark identity.

### DL-12 Governed delivery
The application reaches the existing Parallax Preview/REVIEW boundary with exact accepted source and protected validation evidence; REVIEW is not presented as autonomous production completion.

The implementation technology is not fixed. Parallax chooses the simplest maintainable architecture that satisfies the outcomes. Browser-local persistence is an outcome requirement; the storage mechanism/framework is deliberately not prescribed.

## 4. Architecture requirements

### 4.1 Immutable real-world objective template

Introduce a bounded immutable ParallaxBench real-world objective-template record with at least:

- stable `template_id` and `template_version`;
- objective/application class;
- repository-shape class;
- human-readable title;
- ordered immutable required outcomes with stable requirement tokens and exact frozen text/digest;
- declared comparable ParallaxBench dimensions;
- expected protected ceiling;
- fixture/brief digest.

Identity fields use bounded canonical validation consistent with the existing ParallaxBench token/version/digest rules. Duplicate `(template_id, template_version)` identity with different content fails closed.

Template serialization is deterministic. Material content drift produces a different digest and cannot silently reuse the original template identity.

### 4.2 Canonical Work Specification acceptance binding

A real-world template may be bound only to canonical Project + approved Work Specification evidence supplied from the ordinary Parallax workflow.

The binding input contains only canonical/evaluation identity needed for admission, including:

- Project ID;
- Work Specification ID, revision and digest;
- canonical Work Specification acceptance criteria IDs and text;
- repository/application shape where required.

For Decision Ledger v1, every frozen `DL-01` through `DL-12` requirement token must appear exactly once across the approved canonical acceptance criteria. A canonical criterion may contain more than one requirement only if each requirement token appears exactly once overall; duplicate or missing requirement tokens fail closed. Additional canonical acceptance criteria are permitted and become part of the resulting exact benchmark case acceptance-ID set.

The binder must not decide semantic equivalence by unconstrained model judgment. Requirement-token coverage is deterministic admission evidence. If the ordinary Work Specification loses or duplicates explicitly supplied requirement tokens, the benchmark does not silently repair it; that is observable specification-fidelity evidence.

### 4.3 Existing BenchmarkCase output

Successful real-world binding produces the existing `BenchmarkCase` contract rather than a parallel case type. The resulting case binds:

- exact canonical Project ID;
- exact approved Work Specification ID/revision/digest;
- the complete canonical acceptance-ID set;
- repository shape;
- existing comparable dimensions;
- existing expected protected ceiling;
- the immutable real-world template digest as fixture identity.

Existing `CandidateBinding`, `ProtectedFloor`, `CandidateBenchmarkEvidence`, dimension evidence, comparison and safe serialization semantics remain unchanged unless an explicit compatibility fix is necessary and separately covered.

### 4.4 Reference observation boundary

S1 may persist or serialize a safe reference-observation envelope for the first candidate only if it contains bounded evaluation identity and existing safe ParallaxBench evidence. It must not add cross-Project comparison authority or claim that separately bound cases are comparable merely because they derive from the same template.

A future cross-Project repeat/challenger comparison requires a separate spec defining comparability. S1 stops at trustworthy template admission, canonical binding and first-run evidence capture.

### 4.5 Intervention evidence policy

The runbook/evidence contract distinguishes:

- required approval/review actions — expected human boundary, not undesirable intervention;
- pre-approval clarification messages — recorded separately;
- post-approval corrective user messages — counted as human intervention evidence when mechanically attributable;
- explicit human retry/recovery actions — recorded as recovery evidence when observable;
- out-of-band/manual repository edit — benchmark protocol violation, not a successful low-intervention run.

No evaluator may infer hidden operator actions. Unobservable intervention evidence remains unknown rather than guessed.

### 4.6 Time, cost and UX evidence

- elapsed-time evidence is admitted only from trustworthy timestamps tied to the exact canonical run/candidate boundary;
- cost/usage is admitted only under existing provider/economic provenance rules; otherwise unknown/unavailable;
- visual/UX evidence is admitted only after the exact candidate passes required deterministic/protected checks;
- objective-completion evidence binds exact canonical acceptance coverage and the frozen template admission evidence.

### 4.7 Repository-safe benchmark fixture

Commit the Decision Ledger v1 benchmark definition in a repository-safe fixture location. It contains only the brief, requirement IDs/text, expected evaluation dimensions/ceiling, digest metadata and protocol/runbook information.

It contains no reference implementation, expected source tree, hidden code solution, provider credential, production secret, real user data or prompt designed to leak an implementation answer.

### 4.8 No benchmark runtime backdoor

Focused static/adversarial tests must demonstrate that ordinary runtime/provider/source-delivery/client modules do not import or inspect the new real-world benchmark template identity. The benchmark extension remains under evaluation/benchmark-owned paths plus repository-safe fixture/runbook paths.

A benchmark template ID/digest may appear in evaluation artifacts and tests, but it cannot become a runtime branch selector.

## 5. Real run protocol

After the implementation/evaluation extension is exact-head qualified, merged and any changed production component is verified, run Decision Ledger v1 through a normal authenticated Parallax session.

The controlled run protocol is:

1. use an independent target GitHub repository with no reference solution and no manually prepared application source;
2. create/select a normal Parallax Project bound to that repository;
3. submit the frozen Decision Ledger v1 brief including `DL-01` through `DL-12` tokens;
4. permit necessary pre-approval clarification but record it;
5. review the generated Build plan; do not manually rewrite target source;
6. approve through the ordinary Parallax approval boundary only when the plan is suitable for the benchmark;
7. allow the ordinary Engineering Run to continue through protected PLAN/IMPLEMENT/BUILD/TEST/VERIFY and Preview/REVIEW behavior;
8. if correction is needed, request it through Parallax and record corrective intervention/retry evidence; do not edit repository source out of band;
9. at REVIEW, collect exact canonical IDs/digests, source/Preview identity, protected acceptance evidence, observable interventions/retries, elapsed/cost only where trustworthy, and admitted visual/UX evidence;
10. record discovered product gaps before implementing fixes.

The real run may not weaken authentication, bypass Project/Work Specification identity, mutate the database directly, inject source outside ordinary delivery authority or promote to production merely to complete the benchmark.

- creating a hidden/reference implementation for the benchmark;
- introducing a public leaderboard or single aggregate quality score;
- cross-Project benchmark comparison semantics;
- automatic production promotion;
- changing model routing or evaluator promotion policy;
- modifying W8-S2 authenticated replay behavior;
- safe-deletion testing;
- hosted-to-private inference;
- dependency/toolchain upgrades unrelated to the benchmark contract.

## 8. Security, privacy and reliability

All benchmark brief, repository, source, model, browser and evaluator content is untrusted evidence. It cannot redefine canonical acceptance, capability scope, source lineage, provider identity, Project ownership or REVIEW authority.

The benchmark fixture is synthetic/repository-safe and contains no secrets or real user data. Safe serialization excludes source bytes, patches, prompts, hidden reasoning, raw provider payloads, credentials, arbitrary commands/URLs and unrestricted logs.

Binding is deterministic and fail-closed. Missing/duplicate requirement tokens, invalid canonical IDs/digests, malformed acceptance criteria or template drift cannot be coerced into a supported case.

The benchmark must remain useful when Parallax fails. Failure, human-required state, incomplete evidence and protocol violations are recorded honestly rather than converted into a passing result.

## 9. Acceptance criteria

### AC-01 Immutable template identity
A bounded immutable real-world objective-template contract validates stable template ID/version and deterministic digest; duplicate identity with different material content fails closed.

### AC-02 Frozen Decision Ledger fixture
Decision Ledger v1 is committed with exactly `DL-01` through `DL-12`, frozen requirement text/outcomes, repository shape, comparable dimensions, expected REVIEW ceiling and deterministic fixture digest; no hidden/reference implementation is present.

### AC-03 Deterministic canonical binding
The binder accepts canonical Project + approved Work Specification identity only and requires valid Project/spec ID, positive revision, exact spec digest and a unique canonical acceptance-ID set.

### AC-04 Exact benchmark requirement coverage
Binding requires every `DL-01` through `DL-12` token exactly once across canonical acceptance text. Missing or duplicate benchmark requirement tokens fail closed. Extra canonical acceptance criteria are allowed and remain in the exact resulting BenchmarkCase acceptance set.

### AC-05 Existing BenchmarkCase compatibility
Successful binding produces the existing `BenchmarkCase` with exact canonical Project/spec/acceptance identity, existing comparable dimensions/ceiling and the immutable template fixture digest. Existing ParallaxBench comparison/protected-floor semantics are not replaced.

### AC-06 No unconstrained semantic admission
No model/evaluator may silently decide that missing requirement-token coverage is "close enough" or rewrite the approved Work Specification for benchmark admission.

### AC-07 Evidence-state integrity
Intervention, elapsed-time, cost/usage and UX evidence use existing evidence state/provenance rules where applicable. Missing/unobservable evidence remains unknown/unavailable and never receives favorable zero defaults.

### AC-08 Human-intervention protocol
The committed runbook distinguishes required approvals/review, pre-approval clarification, post-approval corrective intervention, observable retry/recovery and prohibited out-of-band source edits.

### AC-09 Safe benchmark artifacts
Fixture, template and safe evidence serialization contain no credentials, secrets, real user data, hidden reasoning, raw provider payloads, source bytes/patches, arbitrary command/URL authority or reference solution.

### AC-10 No benchmark-only runtime path
Static/adversarial coverage proves runtime/provider/source-delivery/client behavior does not import, inspect or branch on Decision Ledger template ID/version/digest, benchmark expected outcome or benchmark mode.

### AC-11 No authority expansion
The S1 evaluation extension cannot accept source, transition Engineering Runs, create capability/provider authority, mutate target repositories, merge, promote production, approve or complete REVIEW.

### AC-12 Compatibility regressions remain green
Existing ParallaxBench, protected evaluation, integrated product proof, API regression and authority-boundary tests remain green.

### AC-13 Authentic DSPy implementation gate
Before semantic implementation, authentic DSPy SpecCritic + SpecCompiler evidence for this exact spec is committed, protected `--require-dspy` validation passes, and any temporary evidence-workflow change is removed/restored byte-for-byte.

### AC-14 Exact-head implementation qualification
Final implementation head passes focused W9-S1 tests, Workstream Spec Validation, P2 CI, Bounded Autonomy and all applicable protected release gates. Changed production components are Preview/deployment-verified before their state is recorded as deployed.

### AC-15 Controlled real-world reference trial
After the evaluation extension is released, Decision Ledger v1 is run through a normal authenticated Parallax Project with no out-of-band source editing. The evidence record binds exact canonical Project/spec/run/source/Preview/REVIEW identity and records objective/protected result plus interventions/retries/time/cost/UX only where trustworthy.

### AC-16 Benchmark failure remains useful evidence
A failed or HUMAN_REQUIRED first trial may satisfy the evidence-capture portion of AC-15 if it is honestly bound and complete enough to diagnose the product gap; the workstream must not falsify success or weaken protected gates merely to obtain a passing application.

### AC-17 Product fixes remain separately governed
Any semantic Parallax fix discovered by the real-world trial is documented before implementation and receives its own approved spec/workstream boundary rather than being smuggled into benchmark evaluation code.
